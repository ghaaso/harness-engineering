# A. Do the four enforcement pieces reach every place a build will work? (r57-0517, part A)

Checked 2026-11-19 from the code, from synthetic hook inputs (session_id "probe-r57-0517", no file touched) and from one throwaway detached worktree (removed, pruned). Nothing committed or installed.

## Answer in 5 lines

1. Sessions started at the repo root and in library/ are covered by all four pieces today (start hook and refused Edit seen live, r57-0154); but the record guard, start hook, commit check and their settings are uncommitted.
2. The record guard does NOT cover any worktree: every path inside a worktree (in `.claude/worktrees/x/` or elsewhere) is judged "not archived, not a journal" and allowed (exit 0). Helpers with `isolation: "worktree"` and app child sessions in worktrees are unguarded.
3. A worktree cut from HEAD gets only the tier hook (settings at HEAD list it alone; the guard, start hook, commit check, `tools/git-hooks` are not in HEAD).
4. `core.hooksPath` is stored ABSOLUTE (main checkout's tools/git-hooks), not relative as r57-0151/0156 say. In a worktree the hook is found, then dies (exit 1, MODULE_NOT_FOUND) because the worktree has no `tools/check-commit.mjs`: every commit there is refused for the wrong reason, and the rules are not checked.
5. Blind spots: backslash-free Windows forms `\\?\`, `//?/`, `/c/...`, 8.3 short names, trailing dot, `:stream`; MultiEdit and Bash writes; node missing or crashed = fail open (exit 127 or 0).
