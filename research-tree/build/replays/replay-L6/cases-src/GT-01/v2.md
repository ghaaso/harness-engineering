## 6. What is proven on the rig, what is only desk evidence, what needs a real host

**Proven on the rig (measurements, synthetic data, one PC):** items in section 3, section 4 and the drill result files.

**Fresh-host restore (T15): wiped variant only.** The plan allows "a second fresh VM or a wiped one". The second VM could not be created: Hyper-V needs an administrator prompt and it was not answered (three attempts across the session, one earlier session twice). What ran: [c_backup_restore_wiped](evidence/c_backup_restore_wiped-20261105T205508Z.md) on the 581,243-row volume database: backup 19 s including the pull to the PC and the key check; database dropped and recreated empty as the role script makes it (so the runtime role has TEMPORARY again), documents emptied; `clinic-restore` from the PC's copy and the key (set hash compared strictly, "set hash verified" in the log) finished in about 11 s with the grant re-apply and verification; all 104 tables identical by row count and md5; journal totals equal; six document files identical by mode, owner and SHA-256; a synthetic account signs in; `clinic-audit` passes on the restored host; the seed re-run found every keyed posting (idempotency records restored: `created={}` for the stock, issues, finance and pay layers). **What this does not measure:** it is not an RTO. A wiped target keeps the operating system, packages, certificate and application code, so building and provisioning a host (the first deploy took 109 s on this rig in the earlier drill, plus about 30 s per release), fetching the set from a real store, bringing the key and the human steps are all missing. The RPO is the timer's three hours; a scheduled run was not waited for. To run the fresh variant, an administrator accepts one prompt: `C_TARGET=fresh bash deploy/drills/c_backup_restore.sh` from Git Bash at the repository root (needs about 2 GB of free RAM).

**Desk evidence only:** the recurring-cost estimate ([hosting-cost-estimate](../../application/hosting-cost-estimate.md); prices read on 5 November 2026 from public pages by a subagent; not a quote); the classification rules of `release_compat.py` (operation names, not SQL); the three-hourly RPO as a schedule (a scheduled run was not waited for: the unit was started by hand, and the timer's next-run times were listed).

**Cannot be proven without a real host:** the PC-off half of T17 (the rig runs on the PC); an independent offsite store, write-only token and retention locks (the PC held the copy; it proves the pull, the hash check and the age bookkeeping); a real RTO including key custody and people; a real quote, region, tax and renewal (Q-13, Q-10); a domain, a real certificate and HSTS behaviour; performance on a hosted vCPU (this CPU is a fast desktop core, so hosted numbers will be worse); the clinic's network; a notification channel (the watcher exits non-zero and appends to a file; nothing sends a message); a second maintainer following the runbook.

**Harness faults found and fixed during the work (each would have produced a false result):** `ssh` inside a `while read` loop swallowed the list of sets so only the first set was pulled and a restore ran from an old one (the comparison caught it); the backup disturber's arithmetic was wrong so the first contention run took **no** backups during load (those results were discarded and rerun); the classifier counted Django's own migrations as newer and misread `db_default`; the restricted-figure markers collided with a till variance; the probe's lockout check was masked by the new proxy limit (it now paces under the limit and tests the burst separately); the audit's key scan matched its own text; the volume drill's table names lacked the `clinic_` prefix; Git Bash converted `/stock/` into a Windows path. Runs that produced these false results were deleted and rerun; none is cited.
