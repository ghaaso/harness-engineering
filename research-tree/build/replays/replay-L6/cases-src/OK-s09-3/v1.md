# Slow-connection, keyboard and touch record (T19, T23)

Date: 4 November 2026. Environment: Windows 11, headless Chromium from Playwright (the same browser the UI track's layout test uses), the synthetic S02 to S08 test worlds. Everything is synthetic. This is a structural and layout record, not a usability test: no person used these pages, no screen reader was involved, and no network was throttled or measured.

## What was checked, and the test that checks it

| Claim | How it is checked | Test (`src/clinic/reporting/tests/test_pages.py`) |
| --- | --- | --- |
| Every S09 page (overview, four category pages, export, and every report page and its transactions list) renders within four regions that match the screen registry, with every control labelled, one `h1`, a `main` landmark with the skip link first, and every table cell labelled for the phone layout | static audit of the server-rendered HTML (the T23 audit helper) in the empty, populated and partial-coverage states and for the restricted viewer | `test_every_page_is_within_four_regions_labelled_and_script_free_when_empty`, `test_every_page_is_within_four_regions_when_populated_and_partial`, `test_the_restricted_viewer_gets_the_refusal_page_and_a_smaller_overview` |
| No client-side computation of totals: no page carries a script, an event-handler attribute or an inline style | every page's HTML is searched for `<script`, `on...=` attributes and `style="` | the same tests, and `test_a_page_read_without_its_stylesheet_and_scripts_keeps_every_fact` |
| The page without its stylesheet and scripts still reads: the as-of date, generated time, filters, coverage, figures and basis are in the document text in reading order | the HTML text is read in order and the stylesheet request is aborted in Chromium (the slow connection that delivers only the document); the visible text of `main` still holds the facts and one heading | `test_a_page_read_without_its_stylesheet_and_scripts_keeps_every_fact`, `test_the_browser_check_without_the_stylesheet_reads_the_same_text` |
| Phone width (375 px) and laptop width (1280 px): no horizontal scroll, no content past the right edge, at most four regions as rendered and exactly the declared ones, at most four fields per step, tables stacking at phone width and not at laptop width, a visible heading, a global bar of four items at most | the UI track's browser measurements applied to every S09 page, in three states (empty, populated with partial coverage, and the stock-only viewer's pages including the refusal page) | `test_every_page_fits_phone_and_laptop_width_when_empty`, `test_every_page_fits_phone_and_laptop_width_when_populated_and_when_restricted` |
| Touch targets: every button, link-button and input in `main` is at least 43.5 px tall at both widths (the stylesheet sets 2.75 rem, 44 px) | measured in the browser for every page and width | the same two browser tests |
| Keyboard: only real controls (links, buttons, inputs), no positive `tabindex`, no `onclick`, no element acting as a button; the first link on every page is the skip link to `main`; every filter field has a label with text | static audit of every page | `test_every_control_is_a_real_focusable_control_with_a_label_and_a_large_target` |

## Result

All of the tests above passed on the machine and the date above (see [check-summary.md](check-summary.md) for the run). They prove structure and layout of synthetic data in one browser. They do not prove that a person can find the first exception on a phone, that a screen reader reads the tables sensibly, that the colours are readable in sunlight, or that the pages are fast on a real mobile connection. Those belong to S12's observed walkthrough with the people who will use them (O-14 asks whether the doctor reviews on a phone or a laptop).
