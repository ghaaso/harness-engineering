## Known limits and remaining risks

- Race evidence is from one Windows 11 machine and a local PostgreSQL 17 container; "second call was blocked" is timing evidence there, the outcomes are asserted independently; nothing was measured under production load or on the target host.
- The deadlock tests force a deadlock with raw locks in opposite orders; the claim that two S02 commands cannot deadlock rests on the lock order (D02-08), reviewed, not exhaustively tested.
- No typed business command exists yet; S03-S08 must use `run_command` and the ledgers and inherit their checks.
- Screens: structural audit only; no navigation entry until the root adds it (proposal 6).
- `committed_db` does not undo changes to rows that existed before the test.
- The race world now creates the period-control row first; before that, a race that began without a committed posting could wait on that row's first insert instead of the named lock (outcomes unaffected; see review round 1).
- Python ORM reads could be shadowed by a temporary table only if TEMPORARY were granted back to the runtime role.
- Advisory locks use 32-bit `hashtext`; a collision serializes two unrelated keys or shows "in progress" for a key that is not.
- At database level the runtime role can still append rows to another open-period document by raw SQL; only `Posting.require_own` prevents it in code.
- The reversal's settlement-first lock order and the allocation lock plan are reviewed, not race-tested.
- Review findings left open are listed in [review round 1](evidence/review-round-1.md).
