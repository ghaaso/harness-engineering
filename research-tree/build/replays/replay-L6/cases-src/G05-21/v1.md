# S05 races and fault injection

Date: 4 November 2026. Machine: the user's Windows 11 PC, PostgreSQL 17 in Docker (Compose project `clinic-s05`, port 55441), two real connections per race through S02's harness (`pause_then_race`: the first command stops at a named checkpoint with its locks held, the second starts, then the first resumes). `second_was_blocked` is timing evidence on this machine; the asserted outcomes do not depend on timing. These tests show the named lock decides the interleavings they set up; they do not prove no other interleaving exists and say nothing about production load.

## Races (`src/clinic/reconciliation/tests/test_races.py`)

| Race | Lock it depends on | Result with the lock | Lock-removal experiment | Result without it |
| --- | --- | --- | --- | --- |
| Count start (stopped after setting the gate) vs an issue of the same item | the item's `StockScope` rows, FOR UPDATE in the ledger's order (`ledger.lock_scopes`) | the issue waits, then reads the committed gate: COUNT_IN_PROGRESS; no issue movement; stock 75 | `ledger.lock_scopes` replaced by a stand-in that reads the same rows without FOR UPDATE and inserts only missing rows | the issue posts during the count: its movement's sequence is after the count's cutoff while the count is still a draft, so the snapshot no longer matches the shelf |
| An issue (stopped after its movements) vs a count start | the same scope rows | the count start waits, then snapshots the committed book (72) with a cutoff that covers the issue | — (the same lock as above) | — |
| Two reviewers close one case | the case row FOR UPDATE, then the version each loaded (`cases._lock_case`) | the second waits, then VERSION_CONFLICT; one `closed` event; the first reason kept | `cases._lock_case` replaced by a plain read with the same version check | the second passes the check on the old row; its UPDATE waits and meets the closed row; the database trigger ("a closed case never changes") refuses it, not the application |
| Two reviewers record a cause | the case row FOR UPDATE and the version | the second gets VERSION_CONFLICT; the first cause kept | the same stand-in | a lost update: the second cause replaces the first, two `cause` events share one version step |

A finding while building the first experiment: the ledger's `bulk_create(..., ignore_conflicts=True)` (`INSERT ... ON CONFLICT DO NOTHING`) waits on a scope row another transaction is updating, so a stand-in that keeps that insert is still serialized by the count's gate UPDATE. The stand-in inserts only missing rows so that the experiment removes exactly one lock. The ledger itself is unchanged; recorded for the root as an observation, not a defect (the insert's wait is harmless and the FOR UPDATE that follows is the documented lock).

## Fault injection (`src/clinic/reconciliation/tests/test_faults.py`)

The races and the fault tests are in commit `d5a31dd`.

Each command is failed at every checkpoint it passes (kernel `after_document`, `after_audit`, `after_operation_record`, `before_commit`; stock `after_movements`; and the S05 checkpoints `count.after_count`, `count.after_gate`, `count.after_snapshot`, `count.after_release`, `count.after_followups`, `adjustment.after_lines`, `boundary.after_document`, `period.after_document`, `count.after_set_aside`, `item_mode.after_update`, `case.after_event`), with real commits. After each failure nothing changed: posted documents, movements, balances, layers, scope gates, counts and their versions, count lines, adjustment drafts, periods, assignments, reviews, set-asides, cases and their versions, case events, item modes, operation records and audit rows. The same request then succeeds once and the stock projections verify.

Commands covered: count start, save and cancel; a non-count adjustment; a count correction; boundary assignment; acknowledgement; count-derived usage; set aside; item mode; and each case action (notify, owner, bill track, cash explanation, cause, bill link, close).

Closed periods: with the business date 8 October closed (the clock set back behind a close, which only a test can do), count save, adjustment post, acknowledgement and count-derived usage each refuse with PERIOD_CLOSED and change nothing. Count start, observation entry, set aside, item mode and case actions post no document and are not period-bound.
