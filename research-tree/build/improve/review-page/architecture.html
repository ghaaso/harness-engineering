One model that answers "which files?" on any repository

25 November. A design, reasoned from your lecture deck, the published work and our own measurements. None of the model is built yet.

The chain of reasoning: what the problem needs, the choice, and why

It must work on a repository it never sawNo learned vector per file and no global coordinates. Inputs are text features and structure only.A Laplacian position is a coordinate of one graph: costly, ambiguous in sign, rebuilt at every commit, blind to direction. It means nothing in the next repository.
It must hold pair factsMark the seeds, and let every file's state depend on them.Your deck: message passing cannot count structures without a label that breaks the symmetry. For a pair question the right label is the question's own seed. One pass then scores every candidate.
Counting must live inside the modelEach message is scaled by its edge (how often, how recently, how big the commit), and messages are summed.Your deck: real data is anisotropic, and the sum is the aggregator that can count. A mean cannot. With one layer this is exactly weighted counting.
All of history, nothing staleHistory as time-stamped edges read at question time. Time enters as a gap. No per-file memory.A relative time is the same function in every repository, and nothing has to be replayed or can fall out of a window.
Files with no shared historyA parsed code graph (functions, calls, imports, tests, folders) under the same messages. Three hops.File to function to function to file is three hops. Over-squashing starts near four, so depth stops at three and attention does the rest.
No n-squared costRetrieve about 300 candidates, then attend only among them.Your deck: dense attention is practical to about a thousand tokens, and retrieval can select the relevant subgraph instead of the whole graph.
Position without coordinatesEach token says how it relates to the seeds: hops, walk mass, time since change, place in the folder tree.It meets the deck's tests for an encoding, follows edge direction, means the same in every repository, and cannot see the future. The tree row of your screenshot is the folder tree here.
Never below counting, and the right targetScore = counting + a learned correction. The loss is over the whole candidate list.Five earlier learned models fell to or below counting. This one equals it at the first step. The candidates are the hard cases, which is what the score measures.

What our earlier models did instead

  • Averaged a file's neighbours. An average cannot count, and counts are the main signal here.
  • Kept one vector per file. That cannot hold a fact about a pair of files.
  • Looked at the last 20 to 32 events. Half of the history stayed out of sight.
  • Trained against random easy examples, then were scored against the hard ones.
  • Kept state per repository. Such a model cannot be carried to another repository at all.

Each was a published model run with its default settings. Each of these faults follows from theory and could have been reasoned out before a single card hour was spent.

What this design promises, and how it can fail

  • Files with shared history: equal to counting at the start, better after training.
  • Files without shared history: better than today's ranker, through paths in the code.
  • An unseen repository: no worse than counting there, with no training on it.
  • The limit of reasoning: it can make sure the design is not crippled. It cannot promise the size of the gain. The best possible score on this task is about twice what counting reaches.
  • It fails if the parsed graph misses the links that matter, or if paths add nothing over hand-made features.

Built today: the history tables, counting, the learned rankers, text vectors. Not built: the code graph, this model, training across repositories, any test on an unseen repository, any set of real errors with their fixes.
