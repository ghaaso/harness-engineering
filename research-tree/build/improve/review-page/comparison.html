Our work, held against what the course material teaches

A first reading, to work through together. It covers the models we built, the way we chose them, and our data. Nothing was trained or run for it.

The models that stalled could not have worked. Each one broke a demand that the material states plainly. The one model that leads is the only one that met them.

The fault was in how we chose. We picked forms by the gains papers reported and then varied their size. The material teaches to choose by what a model can and cannot represent.

The data needs more work than the models. Three repositories are no sample for a model that has to work on one it never saw.

1. What the problem demands of any model

The three questions (which files for a task, for a change, for an error) and the condition that it works on a repository it never trained on, put in the material's terms.

1The answer is relative to the question

"Which files go with this one" is a fact about a pair, not about a file. A model that gives each file one summary of its own surroundings cannot answer it, however large it is.

2Counts must survive

How often and how recently files moved together is the signal. Averaging over neighbours throws the count away. Summing keeps it.

3No memorised identities

A model that learns one vector per file knows nothing about a new file or a new repository. Every input has to be in the repository's own scale, not in raw amounts.

4Only what was known then

Every input as it stood at the moment the question is asked.

5Different links mean different things

Changed together, imports, same folder, test of: these are not one kind of connection, and some run one way only.

6Reach beyond history

Part of the right answer has never changed together with the file asked about. Content, names and code structure have to be inputs too.

3. How we chose, and how the material says to choose

What we did

  • Ranked forms by the gains papers reported and by a guessed chance.
  • Built them at library settings and varied their size.
  • Read a stall as a fact about the problem.
  • Ran tests to find faults an argument would have named.

What the material teaches

  • A design is a choice of what the model can represent.
  • A larger model is not a better one.
  • First find which patterns the data has, then take a form that can represent them.
  • A stall says "this form, on this input". Check it against the demands before running anything else.
  1. State the question exactly: what is known when it is asked, and what the answer is.
  2. Count the patterns in the data that decide the design. No training.
  3. Write the demands on the model.
  4. For each decision: the alternatives, what each can and cannot do, the choice, and what would refute it.
  5. You see that document before anything is built.
  6. Test only what the argument leaves open.

4. The data

What holds

  • Splits follow time, with a strict cut-off: no model sees the future.
  • A file keeps its identity when it is renamed.
  • Every learned model is scored against plain counting and plain text search.
  • Results are given per repository, not only pooled.

The largest gap

For a model that must work on a repository it never saw, the repository is the unit of the sample. We have three, picked because they were at hand, all three used for both training and testing, and one of them makes up four fifths of the pooled score. This needs many repositories, chosen on purpose, with whole repositories held out. That is a download, so it needs your word; I am not asking for it yet.

We feed models a flattened history

Pairs of files that changed together, not the changes themselves. From pairs nobody can tell one change that touched three files from three changes that touched two each. The change itself, with its content, should be what a model reads.

"Changed together" is partly our own making

It depends on each team's commit habits and on our rules (no merges, 2 to 50 files). Raw counts are therefore not comparable between repositories.

Large changes flood the training set

They produce many more examples. The fix, weighting a change by one over its size, we found by trial. Sampling theory gives it directly, and should also decide how examples are drawn.

One input is mostly missing in training

A content input is empty for most training cases in two repositories. That builds a difference between training and use into the model.

The error question has no data yet

Task and change have their answers in the history. "Which file is at fault for this error" needs error texts tied to the change that fixed them. Whether our repositories hold enough is a count to make first.
