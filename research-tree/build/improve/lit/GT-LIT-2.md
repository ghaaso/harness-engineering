# GT-LIT-2: over-squashing, temporal link prediction, recommender reality checks, co-change models, data, inflated evaluation

Collected 2026-11-25 by web search and page fetch only (no PDF, no download). The fetch tool returns a small model's summary of the page, so "in quotation marks" means the fetched text gave it as the paper's own words; anything else is a paraphrase. "How read": A = arXiv abstract page fetched; H = paper HTML/ar5iv page fetched; D = dataset card page fetched; S = search result only (the search tool's summary, not the source); M = from memory, not fetched.

Generic task used for the "carries over" lines: given one file a change touches, predict the other files of the same change from earlier changes (hundreds to about 20,000 changes per repository), scored by how many of the top ten are right, against a baseline that counts past co-changes.

Naming notes: the Poursafaei paper is titled "Towards Better Evaluation for Dynamic Link Prediction" (the fetched page lists only arXiv). Alon and Yahav's arXiv date is 2020 (ICLR 2021). The "next-basket reality check" is arXiv 2109.14233 (Li, Jullien, Ariannezhad, de Rijke; ACM TOIS 2023), first author Ming Li. "TIFU-KNN" is the method of Hu, He, Gao, Zhang (2020), arXiv 2006.00556; the fetched abstract does not use that name.

What this does and does not carry over to: every source ties over-squashing to tasks whose answer lies several hops away (Alon: radius 4 and up in a synthetic tree), and Alon himself says short-range tasks are less affected; the 2026 position paper reports relevant information often within a small k-hop neighbourhood. A co-change task whose signal is the direct co-change edge (one hop) is the case these papers do not predict trouble for; none tested a software-history graph. Whether a co-change graph has useful signal three or more hops out (transitive co-change) is not answered by any row, and the Tönshoff row warns that a gap credited to graph transformers over message passing was in one benchmark an artefact of tuning.

For co-change, the share of test file pairs seen before in history decides which regime applies, and that share can be measured on our data before any run. Not found in fetched text: a source on stale memory or on many events sharing one timestamp (only Lampert's batch point, abstract-level). None tested file-level software history.

What this does and does not carry over to: all rows say tuned simple methods (counting, nearest neighbour, linear) are the bar a neural model must clear, and Dacrema and Rendle show the bar was often set too low by untuned baselines; a co-change count baseline should itself be tuned (recency weighting, normalisation) before a learned model is compared with it. The next-basket rows say repeat items carry most of the score and new items little; the analogue is file pairs that co-changed before vs pairs never seen together. These are user-item results; none was tested on files in commits. EASE is itself a learned item-item model and could serve as a stronger "simple" baseline.
