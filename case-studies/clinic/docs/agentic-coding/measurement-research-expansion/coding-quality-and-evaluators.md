# Coding quality and trustworthy evaluators

Research date and source access date: **2026-10-02**. Status: **DOCUMENTED desk research; recommendations and clinic examples are PROPOSED**. No measurement implementation, application implementation, package installation, new agent/model experiment, security scan or product trial was performed for this report.

The most useful next step is to make each task's acceptance evaluator demonstrate that it rejects important wrong implementations and accepts materially different correct implementations. Add randomized invariant checks, real database failure/concurrency tests and targeted mutation testing where they answer an actual risk. Treat coverage, static findings and reviewer opinions as separate evidence. None is a defensible universal code-quality score.

## 1. Build an acceptance oracle before selecting a scorer

A test oracle decides whether observed behavior is acceptable; generating many inputs does not supply that decision. The original [test-oracle survey](https://philmcminn.com/publications/barr2015.pdf) distinguishes specification, alternative implementations, metamorphic relations, regression and human judgment, including their incompleteness. Its practical implication here is to document the authority and limits of every assertion, rather than counting all passing checks as equivalent evidence.

For each bounded task, propose an acceptance contract containing:

1. **Behavior and authority:** affected requirement/T-case, permitted alternatives, preconditions, units, boundaries, forbidden side effects and unresolved rules. Separate a confirmed requirement from a provisional synthetic rule.
2. **Observable result:** persistent state, returned result, authorization exposure and relevant audit effects. An HTTP success or screen message alone cannot prove that a transaction committed exactly once.
3. **Evaluator ownership and coverage:** independently authored expected values, required regression cases, development tests, protected holdout cases and a short risk-to-case map. Worker-written tests remain useful development evidence; they should not be the sole independent acceptance oracle.
4. **Execution identity:** source/code/test/configuration hashes, interpreter/database/tool versions, selected test IDs, seeds, fixture version, timestamps, actual process status and raw result artifact. A result must bind to the submitted artifact, not an earlier green run.
5. **Decision rule:** predeclared critical gates and clearly separate `accepted`, `contract failed`, `evaluator invalid`, `infrastructure unavailable` and `policy unresolved` outcomes. Do not turn the last three into an application pass. Preserve the original assignment/run in analysis when acceptance cannot be determined.

Evaluate externally visible semantics where possible. Do not require a particular private helper, SQL shape, exact patch or incidental output order unless that form is itself required. Test seams may be justified for fault injection, but should not become an undocumented implementation mandate. A corrected requirement requires a versioned oracle change and rerun of affected conditions, not selective repair of a losing condition's tests.

### Validate both rejection and acceptance

Before relying on a task evaluator, independently inspect a small calibration set appropriate to that task. Include at least one simple correct implementation and a different correct implementation, ordinary erroneous implementations, and deliberately subtle defects for each critical risk. The purpose is to expose faulty assertions as well as weak assertions; no particular set size establishes sufficient statistical accuracy by itself.

Proposed clinic-specific negative controls include replacing an adjustment with set-to-count, adding rejected delivery units to available stock, posting an accrual again when cash is paid, authorizing only the HTML page while leaking an export, allowing same-key/different-body replay, or returning success before a partial write rolls back. Each calibration defect should have a reasoned label and a reproducible failure. A correct result with a different internal representation should still pass.

Keep a mapping from each required risk to the negative control that tests whether the evaluator can detect it. Uncaught controls invalidate that portion of the evaluator; fixing them increases evaluator adequacy, not the measured worker's skill. Periodically rerun the calibration set after tool, framework, fixture or test changes. A good suite can still share the same misunderstood requirement as the implementation.

## 2. Combine example, property, model and metamorphic checks

These methods answer different questions. They should complement the concrete examples in T01-T20, with explicit preconditions and known limitations.

| Method | What it can establish in the tested scope | What it cannot establish | Proposed clinic application and gate |
| --- | --- | --- | --- |
| Example and boundary tests | A named input/state/action has the expected result; a previous defect stays fixed | Correct behavior on untested states; correctness of an unreviewed expected value | Keep plan examples such as count75/73, later issue3, adjustment−2 ending70. Gate on a confirmed or explicitly synthetic contract. |
| Property-based generation | Many generated cases obey an independently specified invariant; failures can reveal unforeseen boundaries | That the property is correct, exhaustive or sensitive to every important error | T01 conversion/precision rejection; T08/T10/T11/T18 exact balances. Start with pure helpers after they exist; generate valid and deliberately invalid cases separately. |
| Stateful/model-based testing | Selected operation sequences agree with a small independent model and preserve invariants at intermediate steps | Exhaustive concurrent schedules, real recovery behavior, or correctness when model and application share an error | T02/T05/T06/T08/T14: receipt, issue, count, retry, allocation and reversal sequences on synthetic data; gate on implemented command APIs and resettable fixtures. |
| Differential testing | Independently implemented alternatives disagree, giving an actionable case for adjudication | Which implementation is correct, or the absence of a shared error | Compare a simple immutable movement/journal summation model against application results. Do not reuse the application's own conversion, posting or rounding helpers as the reference. |
| Metamorphic testing | Related runs respect a required relation without requiring one exact output for every input | Unspecified behavior or all wrong outputs that preserve the same relation | Same-key/same-body retry has no new posting; supported input-row permutation preserves totals; transfer preserves consolidated net cash. Verify each relation's preconditions first. |
| Regression/snapshot testing | Behavior remains stable for preserved cases and reviewed snapshots | That the old output was correct, or that changed requirements should retain it | Every independently confirmed defect gets a durable reproducer. Snapshot only stable, meaningful output; review updates instead of treating regeneration as acceptance. |

[Hypothesis stateful testing](https://hypothesis.readthedocs.io/en/latest/stateful.html) supports generated action sequences, state-machine invariants and shrinking failures. Use it to search for short reproducible sequences, not to convert a finite run into a proof. Explicitly version settings, seeds/derandomization, generator bounds and the model. Preserve the minimized example as an explicit regression: the [failure database and replay mechanisms](https://hypothesis.readthedocs.io/en/latest/tutorial/replaying-failures.html) help reproduce failures but should not be the only durable evidence. The [settings reference](https://hypothesis.readthedocs.io/en/latest/reference/api.html) shows that deterministic generation also depends on test code and runtime/library versions.

The method has a demonstrated evaluation use: [EvalPlus](https://kristoff-starling.github.io/pubs/neurips2023_evalplus.pdf) expanded HumanEval inputs, checked input contracts and compared outputs against references, finding errors missed by the original tests and correcting some original reference programs. Its input mutation is distinct from source-code mutation. Its results concern that benchmark and study, not this clinic stack or today's agents. The transferable lesson is to validate the expected result and broaden meaningful inputs, not to import its leaderboard percentage.

Proposed property examples, subordinate to the local plan:

- **Quantity conservation:** accepted postings produce the expected sum of immutable movements and allocations; damaged/rejected receipt quantities contribute no owned stock. Historical conversion versions remain unchanged. Quantity generators must respect configured quanta; a blanket reversible floating-point conversion property would be wrong.
- **Separate event lifecycles:** dispatching a return alone does not recognize supplier credit; accruing expense and later paying it recognizes expense once. An independent model records distinct event kinds instead of deriving them from the application balance.
- **Idempotency with authorization:** repeated same-key/same-body requests have one durable result, changed content conflicts, and a later unauthorized caller cannot learn the prior protected payload. Mere equality of returned IDs misses the last condition.
- **Correction context:** reversal nets the original posting once only where the plan permits reversal and dependencies are addressed. Do not assume all operations commute; expiry, close cutoffs, count gates and allocations are deliberately order-sensitive.

The plan already requires randomized ledger comparison and real-database concurrency/fault injection. This report refines their evaluation role; it does not add a new clinic requirement or authorize implementation.

## 3. Test transactional behavior with the actual database boundary

Django explicitly warns that `TestCase`'s enclosing transaction can make `select_for_update()` appear to work outside an explicit transaction; SQLite applies no such row lock. Its [queryset reference](https://docs.djangoproject.com/en/5.2/ref/models/querysets/#select-for-update) directs this testing toward `TransactionTestCase`. The [testing tools documentation](https://docs.djangoproject.com/en/5.2/topics/testing/tools/) distinguishes tests that need actual commit/rollback behavior from tests isolated by the normal test case.

For the proposed PostgreSQL application, T04/T05/T13 therefore need a disposable instance of the selected PostgreSQL version, real separate connections, deliberate synchronization so operations overlap, bounded waits and inspection of committed state after both processes finish. A sequence of two mocked calls, a single shared transaction, an in-memory counter or SQLite success is insufficient evidence for this boundary.

Proposed fault points include failure after movement, journal and audit writes, replay after a response is lost following commit, deadlock/serialization retry exhaustion, and a worker dying while processing a leased job. Distinguish a failure that should roll back everything from a lost response that should recover the same already committed outcome. Independent assertions inspect movement count, journal balance, allocation ownership, idempotency record and authorized result together. Tests of recovery need separate process/lifecycle control when that is the mechanism under test; raising a convenient exception inside a helper may not reproduce worker death.

These probes establish the observed schedules and injected failures, not every possible schedule or production incident. Record the synchronization mechanism, selected isolation level, database image/configuration and fault injection point. Run a known unsafe implementation against the probe to demonstrate it really exposes the intended race. T15-T17 restore/upgrade/capacity evidence requires the separate operational exercises in the plan; unit tests cannot substitute for them.

## 4. Use mutation and coverage to examine tests, not certify code

Source mutation introduces controlled code defects and asks whether tests notice them. [Google's original industrial study](https://arxiv.org/html/2102.11378v1) describes incremental mutation of changed, covered code and filtering unhelpful/equivalent mutants to make feedback usable. That is evidence for selective diagnostic use, not a requirement to run every mutant on every task. Filters must be domain-aware: time, authorization, rounding and configuration changes may be central clinic risks even when a general heuristic considers them unproductive.

[Just et al.'s original FSE study](https://homes.cs.washington.edu/~mernst/pubs/mutation-effectiveness-fse2014.pdf) found a relationship between mutant detection and real-fault detection beyond coverage in its five Java projects. This supports mutation as an imperfect test-adequacy surrogate; it supplies neither a Python clinic defect probability nor a universal acceptance threshold.

Proposed procedure after application code and an independently reviewed suite exist:

1. Select small changed areas tied to critical risks: quantity comparison, allocation limit, replay conflict, authorization predicate, posting sign or cutoff. Freeze the operator/tool version, selected files, baseline suite and budget before comparing workflows.
2. Establish that the unmutated baseline runs correctly. Report generated, executed, killed, surviving, uncovered, invalid/uncompilable and timed-out mutants, with tool errors separately. A timeout is not automatically proof of useful defect detection.
3. Inspect survivors. Equivalent, redundant and irrelevant mutants require documented reasoning; unknown equivalence is not a license to delete an inconvenient survivor. Strengthen only assertions justified by the contract. Avoid brittle checks against implementation detail.
4. Show the scoped raw counts and exclusions. If displaying a kill proportion, state its exact denominator and whether exclusions were adjudicated. A changed mutant scope or denominator prevents direct comparison without re-evaluation.

[mutmut's maintained project documentation](https://github.com/boxed/mutmut) makes it a plausible Python candidate but requires `fork` support: native Windows is not supported, and WSL is its documented Windows route. Its runner/process model also needs care around inherited database connections and threads. Defer it until a bounded Linux/WSL compatibility probe on isolated code succeeds; do not silently adopt an older major version to evade a platform gate.

[Coverage.py branch coverage](https://coverage.readthedocs.io/en/latest/branch.html) reveals unexecuted branch transitions as well as unexecuted statements. It does not show that assertions are sound or that all data/schedules/security states are tested. Exclusions can remove coverage opportunities, so preserve their configuration and changes. Inspect missing high-risk paths; reject an arbitrary 80%, 90% or 100% universal quality target. A tiny suite can execute every branch while asserting little.

## 5. Keep security and maintainability evidence separate

[NIST SSDF 1.1 PW.7/PW.8](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-218.pdf) calls for selecting appropriate code analysis/executable tests, recording and triaging findings and using production-relevant conditions where needed. It is a process framework, not a scanner certificate. [OWASP ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md) gives explicit function-, data- and field-level authorization requirements and trusted-service-layer enforcement. Map selected versioned requirements to T12/T20, including changed grants and non-page read/export paths; this subset is not a full ASVS conformance claim.

Use deny-case and authorized-case tests together: a system that denies everyone can pass an incomplete security suite. Inspect responses, files, jobs, audit views and aggregates for protected data, not just status codes or whether a menu is hidden. Test after revocation/delegation expiry and across fresh and existing sessions. Resolve named payroll viewers before real data; synthetic capability fixtures can exercise the proposed permission contract beforehand.

Static analyzers and dependency scanners have narrower roles. [Bandit](https://bandit.readthedocs.io/en/latest/) checks common Python security patterns through AST plugins; no findings does not establish correct business authorization. [pip-audit's security model](https://github.com/pypa/pip-audit#security-model) concerns known dependency vulnerabilities, not malicious-package detection or complete application security. Missing dependencies, service failures and ignored advisories need explicit outcomes. Package resolution can execute build-related code; use a bounded trusted environment and do not mutate dependencies with automatic fixes during sealed evaluation. [Django's deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/) recommends `check --deploy` against the intended settings; that checks only a subset of deployment concerns.

For maintainability, use a modest documented review of design, complexity, tests, naming, documentation and unnecessary abstraction. [Google's code-review guidance](https://google.github.io/eng-practices/review/reviewer/looking-for.html) provides a practical checklist and explicitly asks whether tests themselves are valid. Reviewers should cite concrete files/behaviors and distinguish required repair from style preference. Do not count every lint nit as a separate defect or equate a long diff with poor code.

A stronger proposed maintainability outcome is a later, independently assigned small change to each accepted implementation, under the same constraints: can another maintainer understand it, implement the change correctly and avoid regressions? Record active effort, clarification/rework and the resulting correctness evidence. Skill/familiarity and task difficulty remain confounds; one follow-up change cannot establish lifetime maintenance cost. Without such follow-up evidence, label the result **reviewed maintainability concerns**, not measured future maintenance productivity.

[SonarQube's metric definitions](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition) illustrate why a tool label is not a construct: its maintainability rating derives from estimated remediation debt relative to code size. Complexity, duplication and such ratings may guide inspection, but are not independent truth about maintainability. Defer a Sonar platform for this project unless a later concrete need justifies its operating cost and configuration; no Sonar edition/license or local integration was evaluated.

## 7. Calibrate code reviewers and model judges

Use human review for specification interpretation, meaningful severity and maintainability tradeoffs, with independent reasons and adjudication for disagreements. If a reviewer helped implement or saw the treatment identity, report that exposure. Different accounts from the same reviewer/model family are not automatically independent evidence.

[CodeJudgeBench's original research](https://arxiv.org/html/2507.10535v2) examines execution-free code-functionality judgments and reports sensitivity to order, randomness and writer identity across its sampled tasks/models. It does not validate an arbitrary current model for clinic transactions, security or maintainability. A language-model review can propose a reproducible defect investigation; its confident prose is not an acceptance oracle.

Proposed code-review calibration uses independently adjudicated correct and defective patches from the affected risk classes. Hide workflow/author identity, vary presentation order, include abstention, pin model/prompt/tools and retain the full reason plus referenced evidence. Separately measure false acceptance of defective artifacts, false rejection of correct artifacts, per-risk detection and severity disagreement. Count an alleged issue as confirmed only after independent reproduction or an explicit requirement-backed review finding. A second model repeating the same unsupported claim does not confirm it. Local calibration must precede use of a judge in an acceptance gate; keep human adjudication for critical contested findings.

To reduce review cost without fabricating accuracy, let cheap static/deterministic checks find candidates, then ask reviewers to investigate concrete cases. Report raw confirmed defects and unresolved findings separately. Duplicate allegations about one root defect do not increase defect count. Do not invent a weighted quality composite blending test percentage, stylistic preferences, model scores and security severity.

## 8. Protect evaluation integrity and recognize contaminated benchmarks

Holdout tests should hide cases, not hide essential requirements. Keep the task contract visible while withholding exact inputs/answers and evaluator internals from workers. A hash records identity but does not enforce secrecy: an unrestricted agent in a shared checkout can read supposedly hidden files. The proposed controlled evaluator needs a separate boundary, protected test/configuration inputs and a fresh evaluation environment that imports only the submitted application artifacts and intentionally permitted dependencies. Before calling answers inaccessible, demonstrate denied access from the actual worker identity and permitted sandbox through filesystem permissions, mounts, network routes, Git history, caches and available tools. Merely placing files outside the worker checkout is insufficient; no such isolation has been demonstrated here.

Concrete integrity checks should catch changed test selection, new skip/xfail markers, relaxed assertions, altered lint/coverage suppressions, evaluator imports redirected by path/configuration hooks, stale result files, stub runners returning success and untrusted objects intercepting comparisons. Inspect the final diff and evaluator-run provenance, preserve actual subprocess status and required case counts, and use ordinary serialized result values where appropriate. Any permitted test/configuration update needs independent review and a new evaluator version. These are proposed harness checks; this report makes no allegation that local agents have gamed tests.

[METR's original reward-hacking observations](https://metr.org/blog/2025-06-05-recent-reward-hacking/) include visible scorer manipulation and misleading evaluation outputs in its own tasks/scaffolds. They establish that such failure modes can occur, not their prevalence in this project or every model. That evidence supports checking the measurement boundary rather than trusting an agent's self-reported test success.

Public coding benchmarks need a separate integrity assessment. [OpenAI's February 2026 SWE-bench Verified audit](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/) found specification/test issues and evidence of benchmark recall. Its reported problem percentage concerned an audited failure-selected subset, not a random estimate of every benchmark item. The [July 2026 follow-up](https://openai.com/index/separating-signal-from-noise-coding-evaluations/) found additional problems with SWE-bench Pro and explicitly withdrew its earlier endorsement. Do not preserve the February recommendation without this later correction, or treat vendor-reported percentages as independent universal truth.

Use public benchmarks for background and evaluator ideas, not a claimed local clinic quality multiplier. For workflow comparisons, prefer newly constructed private representative tasks with versioned requirements, independently validated evaluators and recorded exposure history. Fresh task wording, renaming or private tests cannot prove that no relevant training material existed. Repeated feedback also turns a holdout into development data: record exposure, reserve fresh confirmatory cases and do not compare a highly rehearsed treatment against an unrehearsed baseline.

## 9. Prioritized recommendations and rejection rules

| Priority | Recommendation | Why it improves trust / completion gate |
| --- | --- | --- |
| P1 | Extend M00-M02 contracts/results with risk-to-oracle mapping, evaluator/version binding, required case counts and explicit invalid/unavailable outcomes | Reviewable offline design now; later implementation must demonstrate pass, real failure, no tests, all relevant tests skipped, collection error, stale artifact and tampered configuration outcomes before accepting application evidence. |
| P1 | Independently validate each critical task evaluator on known defective and alternative correct artifacts | Acceptance needs evidence of both sensitivity and legitimate flexibility. No acceptance gate should rely exclusively on worker-authored tests or an uncalibrated judge. |
| P1 | Preserve T01-T20 and unresolved Q gates; test real PostgreSQL transactions for T04/T05/T13 | Prevents fabricated business oracles and falsely convincing mocked/SQLite evidence. Gate on authorized S00+ code and correct real database prerequisites. |
| P2 | Add bounded properties and state-machine/differential models for posted quantities, balances, replay and correction order | Exercises varied inputs/sequences while keeping the oracle independent. Gate on reviewed properties, resettable synthetic fixtures and durable reproducer capture. |
| P2 | Use a small pinned tool set and a triaged defect ledger; coverage guides missing-risk inspection | Maintained diagnostics are useful but overlap, configuration and skips can mislead. Gate on a local compatibility probe, inspected output and intact evaluator configuration. |
| P2 | Apply targeted mutation to critical changed logic on a suitable Linux/WSL runner | Tests whether assertions notice plausible controlled defects. Gate on unmutated baseline success, defined scope/operator set and documented survivor/exclusion review. |
| P3 | Calibrate model review locally and measure maintainability with a bounded follow-up change when justified | Separates opinions from observed defect detection/change effort. Gate on blinded adjudicated cases, explicit uncertainty and an actual independent follow-up task. |
| P3 | Add browser and passive web-security checks only after their boundaries exist | Observes real UI paths and selected web findings. Gate on runnable synthetic target, backend assertions, authentication coverage and pinned runner/browser/add-on state. |

Reject these proposed measurement shortcuts: a universal quality composite; passing all visible tests as proof of correctness; coverage or mutation percentage as production-defect probability; no scanner findings as a security guarantee; exact equality to a reference patch; green status despite missing mandatory cases; counting warnings/nits/duplicate allegations as independent defects; deleting inconvenient runs or unresolved mutants; calling worker-readable files a protected holdout; and treating public benchmark rank as validated local outcome.

The honest initial claim is narrower: **an artifact satisfied a named, independently reviewed and calibrated contract under recorded tests and conditions, with remaining uncertainty and other quality evidence shown separately**. No current local trial establishes that claim for a clinic application.
