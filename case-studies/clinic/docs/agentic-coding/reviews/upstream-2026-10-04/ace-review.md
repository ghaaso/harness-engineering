## Original research–plan–implement account (`ace-fca.md`)

[The original article](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/f2bc7aec4575418d2d2e83fec078266cc56d3e6a/ace-fca.md) proposes structured repository research, a reviewed plan and iterative implementation, with deliberate compression and separate sessions/subagents. Research means investigating existing code and behavior. It is not an external prior-art stage, and it does not require Perplexity or prohibit a writer from encountering new evidence. It explicitly allows skipping research for a suitable task and repeating it after a bad research account. In its BAML bug example the initial researcher wrongly dismissed the bug; that report was discarded and research was repeated. A frozen false summary is therefore a failure mode the source itself exposes.

Its 40–60% context-window guidance is a heuristic rather than a measured universal optimum. Subagents isolate exploration and return relevant evidence, but a concise answer can still be wrong. File paths, actual call flows and tests are needed to validate the compressed account. The Rust/BAML examples are reported successful interventions in a large unfamiliar codebase. A multi-feature example reports approximately seven hours, roughly three in research/planning and four in implementation; the counterfactual of several senior-engineer days is an estimate, not an observed matched baseline. Pairing also means elapsed hours cannot automatically be counted as one person's labor. Other examples include abandoned/unsuccessful dependency research and difficult race-condition work. One referenced follow-on change was still open at writing. These negative/incomplete accounts must remain in the interpretation.

The original article's choice to inspect plans rather than every generated code line does not demonstrate that code review is unnecessary. Its cited commit-volume trend, capability claims and author cost anecdotes are contextual claims with external sources; this tree contains no underlying dataset that verifies them. Its disclosure also concerns the author's own product/practice.

## Revised practice and long-term maintainability (`wsff.md`)

[Writing Software for the Future](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/f2bc7aec4575418d2d2e83fec078266cc56d3e6a/wsff.md) is material later guidance. It describes lights-off coding in July 2025, further incidents and a two-week rewrite after a third incident in November. Functional tests and early delivery can coexist with costly accumulated design problems. The claimed maintainability improvement is author experience, not a controlled result; the author explicitly cannot prove parts of the training/design explanation.

The updated process begins with product requirements: user outcome, workflow/mockups, feasibility checks and uncertainties. It adds a program design with types, method signatures, interaction/call paths and file structure. It then implements **vertical slices**, reviewing actual code and outcomes. This differs from assuming that an old fixed horizontal phase template is always sufficient. For smaller work, combined documents and direct implementation are allowed; the source reports roughly 40% of tasks were one-shot or completed with light feedback. Specification review is opt-in rather than mandatory ceremony for every task. Thus the relevant synthesis is proportionate preparation with a real review/check loop, not always maximizing documents or always avoiding plan mode.

The article's 2–3× direction is a goal/hypothesis. The time-allocation figures do not measure our team. Our existing technical plan and S00–S12 slices should be reused, selecting a bounded vertical result and affected contracts/tests. Recreating all architecture and every research stage for each routine change would add overhead contrary to the proportionality described here. For workflow-only work, the local resume route is the relevant context; the clinic PDF route is not a prerequisite.

## First benchmark (`benchmarking-opus-5-on-slop-code-bench.md`)

[The first benchmark article](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/f2bc7aec4575418d2d2e83fec078266cc56d3e6a/benchmarking-opus-5-on-slop-code-bench.md) reports three selected problems (8, 5 and 4 checkpoints), three model runs per problem and a shared Claude Code harness/prompt. The problem selection was itself assisted by Claude. Fresh sessions retain generated workspace state across checkpoints; later strict failures can inherit earlier defects. Opus 5 passes 4/17 strict checkpoints and the other models 1/17; no model finishes all final acceptance tests. These are single trajectories on selected tasks, not repeated trials with an uncertainty estimate or a complete workflow comparison.

The 41 structural metrics are proxies. Detector density is almost saturated in places (roughly 89–98% of lines flagged), and rule counts differ substantially across Python and TypeScript. A cross-language density ratio therefore is not a causal measure of maintainability. Raw line volume mixes tests and production: the article's reported 29,065 total lines includes 14,762 test lines, with 14,303 production lines versus 7,858 for the compared solution. More lines can mean tests, duplication or scope; it is not a productivity outcome by itself. Reviewability, subsequent change effort and actual defects require separate evidence. The article also notes runner cost accounting under-reports an Opus 5 run by approximately 24%; estimated prices and actual billed charges need distinct fields.

Most importantly, small-model follow-on modifications, adversarial review and linter/backpressure combinations are proposed **next experiments**, not treatments already shown to improve performance. The repo's prose cannot justify an auto-fix loop or guarantee that adding a second model improves net results.

## Second benchmark (`benchmarking-sol-fable-kimi-on-slop-code-bench.md`)

[The newer comparison](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/f2bc7aec4575418d2d2e83fec078266cc56d3e6a/benchmarking-sol-fable-kimi-on-slop-code-bench.md) reports six problems and 30 checkpoints, using different model/provider harnesses: Fable in Claude Code 2.1.219, Sol in Codex 0.145.0 and Kimi in OpenCode 1.18.0. These are explicit confounders for a model-only conclusion. Inference was sponsored; the Modal figure of $26.93 is estimated using Baseten-equivalent rates. No repeated seeds/trajectories or raw artifact bundles appear in this tree.

The published strict totals are Fable 10/30, Sol 10/30, Kimi Modal 8/30 and Kimi Baseten 7/30. Isolated totals are Fable 16/30, Sol 14/30, Baseten 13/30 and Modal 12/30. Sol's broader coverage also ends with more final failures (104 versus Fable 43 and Kimi 65/66). No overall final defect-free winner is established. Ranking strict checkpoints alone would conceal important differences in accepted behavior and residual defects.

Direct comparison with the earlier benchmark is unsafe: the circuit problem changed from 557 to 566 tests, acquired new coverage from checkpoint 3 and changed difficulty labeling. The article acknowledges earlier limitations. Its source has editorial remnants: an unfinished sentence, a placeholder heading, a conclusion still referring to the previous three-problem/Opus run, and an inconsistency between a plot's CK3–CK8 range and nearby CK1–CK8 wording. These do not make all results meaningless, but they prevent treating the writeup as a fully reconciled dataset. A reported absence of persistent Python test lines for some agents does not prove they ran no tests; shell/temporary tests and harness checks can be outside that proxy.

Review+linters and cheap-model maintenance tasks remain unrun/proposed follow-ups here as well. Published aggregates are useful for choosing evaluation questions; they do not establish our outcome.

## What changes for our workflow and measurement

The evidence supports the proposed narrow vendor loop as an experiment: external public-web prior art when an approach decision truly needs it; Claude repository understanding/planning/implementation; independent Codex findings; human disposition and accepted repairs. These exact role assignments and the immutable research-note rule are **our local policy**, not an ACE result. A plan may correct repository understanding and feasibility assumptions. New public-web approach discovery should return through the research boundary with a recorded reason, rather than silently drifting or being prohibited when the selected approach fails.

We need a comparator to claim improvement. A readiness pilot can test the ledger/checks without estimating ROI. A later comparison must define the baseline workflow, bounded acceptance criteria, task family/complexity, same source starting state, permitted information, model/harness versions, review policy and task allocation before outcomes are known. Record all human minutes (including research, discarded planning, review and accepted repair), elapsed time, usage/cost, aborted runs, missing evidence and deferred work. Keep actual bills separate from token-price estimates. Freeze check versions and data; changing an acceptance suite requires a new comparison cohort or rescoring all relevant artifacts against the same suite.

Count final independently checked success, severity of escaped defects, accepted/rejected/disputed review findings, time to acceptance and follow-up maintainability effort. Strict checkpoint success and isolated requirement success answer different questions; report both if applicable. Preserve failure lineage and do not convert inherited failures into independent samples. Agents doing the work or measuring themselves are not independent validators. Matched/isolated tasks with randomized or counterbalanced order help, but repetition, learning and model nondeterminism remain explicit limitations. A tiny pilot supplies directional evidence, not a stable causal estimate.

The existing local September 30 review already captured the newer maintainability and benchmark concerns. This refreshed review adds complete hash verification and an explicit authored/media manifest; it does not discover a changed upstream branch or revoke the completed local technical plan. The highest-ROI immediate work is a bounded real task with reliable acceptance checks and complete comparable records, while preserving the no-orchestrator constraint. Infrastructure and permanent multi-agent automation should wait for demonstrated recurring demand and measured benefit.
