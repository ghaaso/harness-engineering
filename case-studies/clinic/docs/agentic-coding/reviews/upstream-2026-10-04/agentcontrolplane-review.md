## Context, control and human interaction

The current authored API has `LLM`, `Agent`, `Task`, `MCPServer`, `ToolCall` and `ContactChannel` resources. Agent configuration references its model, MCP servers, subagents and human channels. Task input is either `userMessage` or an initial `contextWindow`; ongoing history belongs to task status. The validation checks permitted roles and a user message. If supplied history already contains any system message, task helpers do not prepend the Agent's system prompt. Thus the input artifact can affect actual policy/context, and measurements must preserve **the realized context and its version**, not just the nominal Agent resource. [Task API](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/api/v1alpha1/task_types.go), [task helpers](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/controller/task/task_helpers.go), [validation](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/validation/task_validation.go).

Task status explicitly distinguishes initialization, LLM requests, pending tools, final answers, backoff and failure. ToolCall status separately distinguishes execution, human input, subagent waiting, approval waiting and rejection. This supports our separation of lifecycle completion from artifact quality. A final answer is a model/controller state; it is not evidence that requirements, safety constraints or acceptance checks passed.

Approval is configured at the **MCP-server** level through `ApprovalContactChannel`, not as a universal human gate over every tool or agent step. Human-contact and delegate tools do not use this same approval check. A rejected action returns a rejection message to the model and is marked `StatusSucceeded` while its phase is `ToolCallRejected`: successful handling of denial differs from successful execution of the requested effect. The local measurement contract should retain that distinction. [Current executor](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/controller/toolcall/executor.go), [tool state machine](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/controller/toolcall/state_machine.go).

Important static limits attach to the advertised human control:

- The MCP approval request records function/arguments, but later execution reads the current ToolCall arguments; there is no frozen argument digest checked against the approved request in this path. Mutation while waiting needs an independent approval-binding test.
- The real Slack wrapper forwards channel/context/thread but omits `AllowedResponderIDs`; the real email wrapper omits the configured subject. Fields in the CRD and generated SDK therefore do not establish downstream enforcement.
- Approval requests generate a fresh random external call ID, ignoring the wrapper's configured call ID. A retry after an unpersisted request can create another approval request.
- Several authored wrappers access `resp.StatusCode` after an API call without guarding a nil HTTP response. Static source suggests an error-path risk, not a reproduced panic.
- Final-answer notification is an asynchronous goroutine with a few transient retries and logging, not a durable delivery queue or independent human-receipt record.

[Authored HumanLayer wrapper](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/humanlayer/hlclient.go), [task final notification](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/controller/task/state_machine.go). These findings reinforce local requirements for accepted/rejected/disputed review dispositions bound to a stable artifact. They do not authorize external approval/contact actions.

## Persistence and recovery: useful mechanisms with qualifications

Kubernetes status holds conversation history, phase, tool-call-group identity and span identity. Deterministic delegated child-task names allow reuse when the existing child belongs to the same parent. The operator uses in-process locks and Kubernetes leases around LLM/tool-group coordination. These are meaningful mechanisms for explicit resumability and diagnosis. They do not by themselves demonstrate exactly-once effects or complete crash recovery. [Task state machine](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/controller/task/state_machine.go), [locking account](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/docs/distributed-locking.md).

Static concerns needing tests before runtime adoption include:

- Executing an MCP effect precedes persisting its successful status. A crash/status-write failure leaves a possible repeat-effect window; no idempotency/fencing protocol appears in this path.
- Task group/status changes precede completion of creating every ToolCall. An empty or partially created list can be treated as all complete. The zero-content/zero-tool response case does not gain an independent acceptance judgment.
- Task mutex and lease identity use task names; lease namespace defaults to the operator pod namespace. MCP connection identity also uses names. Same-name resources in different namespaces require explicit isolation tests.
- The 30-second lease is not renewed/fenced around a potentially longer model call. A declared `LLMRequestTimeout` is not applied with a timeout in the actual send path. State read before locking is not freshly rechecked there. The default one-replica/leader-election deployment reduces some concurrency, but does not prove correctness of every supported configuration.
- Ready Agent/LLM/contact states do not continuously revalidate changed dependencies/specification. MCP connection reuse checks transport rather than all changes, and tool-change comparison checks names rather than schemas/descriptions.
- Deterministic delegated child creation does not set a child-task owner reference in that path. No general whole-task step/budget cap, expiry/cancel protocol or context compaction policy was found.

The locking documentation's race-free, self-healing and nanosecond/millisecond assertions were not accompanied by a benchmark or complete failure-injection evidence in the reviewed source. Our future trials must record resume behavior, repeated effects, aborted/failed attempts and their costs instead of inferring them from documentation.

## Diagnostics are not the measurement system

ACP initializes OpenTelemetry tracing/meter providers, emits Kubernetes events and includes an observability demonstration. Current code can attach model/tool/context characteristics to spans. It does not provide our task/stage/attempt/worker/call/artifact/human-interval ledger, independent artifact acceptance, full failed-attempt usage or comparative ROI report. [OTel initialization](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/otel/otel.go), [example observability setup](https://github.com/humanlayer/agentcontrolplane/tree/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp-example).

Specific reasons a trace screenshot would not settle measurement readiness:

- Task initialization starts a root span and intentionally leaves it unended; terminal code creates an `EndTaskSpan` child instead of ending the original. Root task duration/export is therefore not a calibrated elapsed-time measure.
- ToolCall initialization starts and immediately ends its span. Its duration covers initialization, not the full human wait/execution. Reconstructed IDs do not recreate an active ended span.
- The LLM client returns only the converted message. Provider usage is not retained in its interface/result; requested temperature/token limits and provider-specific configuration are not all forwarded by the actual client. Validation code's more complete option setup does not prove the execution adapter uses those settings.
- The example Grafana file queries counters such as task reconcile counts; the active authored Go tree does not define those named custom counters/histograms. Initializing a meter provider is not emitting those metrics.
- `otel-test-traces.py` fabricates random parent/child durations, logs and metrics and posts them to the collector. It is a transport/demo fixture, not real task accuracy, acceptance, human effort or ROI data.
- Kubernetes events and diagnostic logs are not guaranteed complete, deduplicated, immutable accounting. Exporter initialization fallback does not prove delivery or quantify telemetry loss.

[Actual LLM adapter](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp/internal/llmclient/langchaingo_client.go), [synthetic telemetry demonstration](https://github.com/humanlayer/agentcontrolplane/blob/eaa2a7ed1d9cb4e13dc53defaf420e36f481dcad/acp-example/otel/otel-test-traces.py). Preserve null/unknown/partial when data is absent. Do not turn absence of token usage, an unended span or an accepted tool approval into zero cost, short duration or accepted artifact.

## Implications for the workflow bridge and ROI comparison

The reviewed [workflow bridge assessment](../../workflow-bridge-assessment.md), [measurement design](../../measurement-system-design.md), [implementation plan](../../measurement-implementation-plan.md), [evaluation plan](../../evaluation-plan.md) and [open defect task](../../../tasks/documentation-red-team/task.md) already distinguish proposed collectors from implemented checks. ACP supplies additional reasons to preserve those boundaries:

| ACP lesson | Local requirement it supports | Disposition now |
|---|---|---|
| Typed task/tool/status identities | Separate task, stage, attempt, worker, call and artifact records | Retain in measurement contract; do not import CRD/operator |
| Denial can be handled successfully | Outcome kinds distinguish refused action, completed run and accepted artifact | Retain explicit acceptance/dispositions |
| Configuration can differ from actual adapter request | Record realized model/version/options/context and verify adapter behavior | Qualification requirement before comparing treatments |
| Visible fixture can be special-cased | Stable, independent artifact checks and unseen variant cases | Resolve acceptance binding and use held checks |
| Trace duration can omit/overlap work | Wall-clock anchors plus explicit human intervals; no summing overlapping spans | Resolve null/time semantics and qualify calculations |
| Retries can repeat calls/effects | Preserve all failed/aborted/repaired attempts and usage; account for cleanup | Required measurement scope |
| Dev scripts autoaccept/merge | User approval owns plans and review findings; writer stays the selected implementer | Do not adopt automatic merge/rewrite loop |
| Kubernetes adds operational surfaces | Include setup/maintenance/qualification time in ROI | Defer ACP runtime pending an actual application-agent need |

The external public-web note still has a role: it records approaches before the writer selects one. Reading this runtime or its source in a **workflow-research review** is different from giving the writing session permission to discover new approaches. No ACP feature enforces that research boundary. Repository exploration in approved plan mode remains necessary. Codex's read-only report remains a human-disposition stage rather than automatic implementation.

We are therefore **ready to implement and qualify a bounded measurement slice**, not to claim that the complete measurement system already works or the candidate has high ROI. Resolve the affected open RT findings first or in the slice's declared dependencies: source/check identity, artifact-bound acceptance, time/null semantics and first-slice routing. Start with one controlled baseline and one changed workflow component using comparable bounded tasks, stable acceptance and matched resource constraints. Capture all research/planning/review/repair time, human effort, calls and failures. Report costs per accepted task and acceptance/rework differences with sample size and missing-data coverage. Small pilot results diagnose feasibility; they do not establish universal superiority.

ACP's potential long-term contribution is conceptual and conditional. If a future clinic feature truly needs durable background agents, typed state and human control can become application requirements. A runtime decision would then require current alternatives, failure/approval binding tests, privacy/permission design, resource evidence and team maintenance fit. Repeated task-routing friction could also justify scoped instruction files or better context packs. Introduce each as a separate measurable change, rather than bundling runtime, parallel agents, telemetry and instructions into one experiment whose cause cannot be identified.
