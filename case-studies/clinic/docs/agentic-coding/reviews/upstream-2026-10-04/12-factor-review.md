# 12-Factor Agents: pinned source review, 4 October 2026

The repo supplies useful engineering principles, demonstrations and a tutorial generator. It does **not** provide evidence that our coding workflow earns positive ROI, a comparison protocol for developer productivity, or a requirement to build an orchestrator. The strongest local fit is to keep context explicit, operations bounded, human decisions visible and task state recoverable using ordinary documents and vendor controls.

The root file is generated PromptX persona guidance. It demands persona selection, large persona reads and frequent commits, while the referenced ignored `.promptx/personas` files are absent from this tree. It is not an appropriate clinic policy. The nested workshop file contains local notebook/BAML conventions: synchronous client use, common notebook namespace, generated-client import cache handling, chapter scope and simulation commands. Its claim that XML is more token efficient is not accompanied by a tokenizer measurement. Claims that notebooks cannot handle async are scoped tutorial choices, not a general technical prohibition. Neither upstream instruction file authorizes local commits, execution, installation or external communication.

Our appropriate inference is one owner for global policy with local additive instructions only where actual code/tool differences justify them. Whether and when a tool loads ancestors, descendants, overrides or imports must be verified in that tool's current official documentation. It cannot be inferred from two upstream filenames.

## Complete factor map

| Source | Useful connection to our workflow | Boundary or future trigger |
|---|---|---|
| Brief history / README | Introduce small model-assisted steps into existing software and deterministic processes. | Anecdotes from founders and the claimed 70–80% framework plateau are not a controlled study of our workflow. |
| 1: Natural language to tool calls | Distinguish a suggested action from executable structured input. | Schema validation does not establish authorization or successful execution. |
| 2: Own prompts | Version our launcher, instructions and acceptance criteria so changes can be attributed. | Changing prompts and models together prevents attributing a result to either. |
| 3: Own context window | Route relevant source, contract and state evidence; keep provenance and avoid irrelevant bulk. | XML/JSON and compression choices require task/model-specific measurement. Compression can preserve an incorrect account. |
| 4: Tools are structured outputs | Separate model proposal, approval, validation and deterministic action. | Structured output itself provides neither business validation nor permission. |
| 5: Unify execution/business state | Give current task state one owner, retain an event/evidence history and project handoffs from it. | A trace is not independent correctness evidence. Do not duplicate current state across documents. |
| 6: Launch/pause/resume | Record stop reason, dependencies and exact next action for resumable work. | Vendor sessions plus existing task documents suffice now; a custom distributed runtime needs demonstrated demand. |
| 7: Humans as tools | Make clarification, rejection and approval explicit decision events. | Upstream SDK email examples are product demos, not authorization to send messages or apply review findings. |
| 8: Own control flow | Bound implementation, review and accepted repairs; retain human choice. | A prompt cannot enforce permissions by itself. Automatic fix-until-pass rounds add cost and change the workflow under test. |
| 9: Compact errors | Keep actionable failure details and limit retries before escalation. | Suppressing stack/context evidence can conceal a persistent defect; count every failed attempt. |
| 10: Small focused agents | Bound tasks and use focused repository readers/reviewers with compact evidence outputs. | More agents also mean coordination and verification cost; parallel wall-clock improvement is not equal human effort reduction. |
| 11: Trigger anywhere | Possible future queue/notification integration when multiple people need asynchronous work. | It is unnecessary scope for the present CLI/plugin loop. |
| 12: Stateless reducer | Make current state plus events sufficient to explain the next step and recover work. | Deterministic, durable and idempotent effects still require engineering; model outputs are stochastic. |
| Optional 13: Prefetch context | Gather predictable repository facts before a narrow decision step. | Prefetch everything conflicts with relevance/token cost; selective routing is preferable until measured otherwise. |

These are principles for building LLM applications. Applying them to development practice is an inference, not a claim that the repo tested our Perplexity → Claude → Codex process.

## Templates, workshop progression and test evidence

The TypeScript template and May workshops progress from one model response to calculator tools, a tool loop, prompt assertions, clarification, serialization, HTTP endpoints, in-memory state and human approval/email. The May 17 provider version switches GPT-4o to a Baseten Qwen3 configuration and adds `/nothink` handling; these are provider-specific experimental/tutorial choices. The July Python notebook covers chapters 0–7 and explicitly skips server chapters 8–12. Its `get_baml_client()` regenerates and unloads cached generated modules; the notebook fetches BAML from mutable `refs/heads/main` rather than the review pin. Local notebook auto-responses are synthetic test inputs, not actual independent human review.

The template's `ThreadStore` uses a process-local map. Tutorial approval endpoints inspect the last event and then execute a division; they do not demonstrate durable restart recovery, authorization identity, cryptographic callback authentication, replay protection, concurrency control or idempotent external effects. The webhook chapter has unfinished narrative placeholders, an empty `handleHumanResponse`, and handlers that validate a thread but never finish the response/resumption flow. These are examples to study, not a deployable orchestration blueprint. Generated packages also drift between `baml: ^0.0.0`, `@boundaryml/baml: latest`, generator versions 0.85.0/0.202.0 and workshop-specific declarations. Reproducibility requires recording the actually used environment.

The walkthrough generator accepts declarative YAML, performs file/command steps and emits Markdown/checkpoint folders. Its unit/e2e tests exercise file copying, diffs, directory generation, malformed input and expected tutorial output. Command-bearing YAML and cleanup examples can execute real shell operations **if someone runs the generator**; none were run in this review. Passing generator tests would establish generator behavior, not agent implementation quality or developer ROI. The notebook simulation creates a fresh local virtual environment and executes cells with a Jupyter processor; this is not native Google Colab verification. Both checked-in notebooks have no saved successful execution evidence (all code execution counts null and saved outputs empty). The log-capture document's sample output is an authored example, not a run independently reproduced here. Its shell test references additional test inputs that are absent from this snapshot.

`drafts/a2h-spec.md` is unfinished protocol design, not a settled integration contract; the adjacent OpenAPI draft is empty. Contributor scripts and packaging/configuration were covered but do not supply productivity results. Licenses distinguish Apache-2.0 code from CC BY-SA content/images.

## Measurement and ROI consequences

The repo provides no baseline cohort, repeated developer trials, task allocation procedure, complete run-level productivity dataset or causal comparison of workflow variants. It therefore cannot answer whether we are doing better. Its value is in hypotheses and operational controls we can test locally.

For a pilot, freeze a bounded task, acceptance criteria, source commit, model/tool versions and workflow variant before the run. Measure human research/planning/implementation supervision/review/repair minutes, elapsed time, model charges, accepted/rejected/disputed findings, check outcomes and subsequent defects. Include aborted runs, discarded plans and research notes, stale-context repairs and reopened work. Use independent acceptance checks and later maintainability/change tasks; agent confidence and generated prose are not success metrics. Compare reasonably matched tasks or isolated duplicate tasks with randomized/counterbalanced ordering, keeping each variant's information exposure explicit. Duplicate-task reuse introduces learning, so do not pretend it is eliminated by fresh sessions.

Our public-web prior-art boundary is a local experimental control absent from this repo. It may reduce approach drift, but external research also costs time and may become stale. For a routine pattern already present in code, skip it as the current bridge allows. If evidence during planning invalidates the frozen option list, explicitly return to research and record that exception; forbidding correction would preserve a bad approach. Count both the discovery effort and the downstream verification effort. Start with documents and available vendor features; add infrastructure only when repeated observed failures or coordination demand justify its maintenance cost.

The previous review's principles remain applicable. This review chiefly strengthens pinned-file verification and visual coverage, makes example incompleteness explicit, and limits claims of evidence. It does not close the RT-01–RT-09 defect register or establish clinic implementation readiness.
