## 1. HumanLayer + GenSX: executable path versus sketches

### What the executable path actually does

The entrypoint checks `HUMANLAYER_API_KEY`, constructs a HumanLayer client, holds a small weather map in process memory, and exposes two schema-defined tools. The read tool retrieves the map entry or a default; the write tool awaits an SDK-wrapped mutation. A GenSX `Respond` component places both tools in an OpenAI `ChatCompletion`; an `OpenAIProvider` supplies the OpenAI key; a workflow executes one hardcoded Paris-weather request. The model and generic system prompt are fixed in source. The underlying GenSX/OpenAI libraries own the completion/tool loop, rather than a custom state machine in this repository. See [the complete entrypoint](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/src/index.tsx#L11-L119).

The central transferable pattern is concrete: the SDK approval decorator wraps `_changeWeather` at the function execution boundary, while `fetchWeather` remains independently callable. Tool selection is therefore separated from permission to carry out a mutation. This is stronger than asking the model to remember to request permission in its prose. The repository demonstrates the wrapping call, but the SDK's live approval, rejection, polling and delivery behavior was not exercised in this research. See [the actual SDK wrapper](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/src/index.tsx#L27-L32) and [the tool execution callback](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/src/index.tsx#L68-L82).

The Zod schemas supply argument structure, and `GSXTool` keeps a tool's name, description, schema and executable function together. Composable `Respond`, provider and workflow components make each layer inspectable. These are useful ideas for an application that actually needs an agent runtime, but installing GenSX or HumanLayer is not a prerequisite for making a normal repository easier for Codex to work in. See [schemas and tools](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/src/index.tsx#L56-L99).

### Critical incompleteness: the proposed approval package does not approve

`pkg/@gensx/humanlayer.ts` is labeled a package outline. Its `requireApproval` method constructs a new tool with the original name, description and schema, then assigns `run: fn.run` unchanged. It never invokes HumanLayer approval. The earlier statement that this necessarily executes the underlying mutation directly was too strong: the locked `GSXTool.run` depends on its receiver, and this adapter forwards it without preserving that receiver. The constructor then calls it through its parameter object, which lacks the required `executionComponent`; this path is expected to fail before the original tool body. That failure is a static deduction, not a reproduced runtime result. The adapter supplies neither approval enforcement nor a working protected call path against the locked API. See [the non-enforcing wrapper](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/humanlayer.ts#L22-L31), [its use](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/weather-example-with-pkg.tsx#L77-L82), and [the version-matched tool implementation](https://github.com/gensx-inc/gensx/blob/65fcf3c36bcd27bf72cc4bb98da32d2d0096ab28/packages/gensx-openai/src/tools.tsx#L45-L56).

The actual SDK wrapper in `src/index.tsx` has a separate result-propagation problem. Its outer tool callback awaits the wrapped mutation but discards its returned value, then returns the existing weather entry. The locked HumanLayer implementation returns denial text and the human comment without performing the mutation. Therefore denial prevents the write, but its feedback is lost before reaching the model. This does not prove that the model will claim success. It demonstrates why both effect enforcement and accurate outcome reporting need checking across adapters. See [the outer callback](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/src/index.tsx#L79-L80) and [the locked approval implementation](https://github.com/humanlayer/humanlayer/blob/df4a0e761f6a3db79080773bacfd867ce4c1dcc0/humanlayer-ts/src/approval.ts#L198-L204).

The same sketch implements `humanAsTool` by exposing a `contact_human` tool with a message schema and delegating its callback to the SDK. That illustrates treating a human request as a tool interaction, but no runnable path uses it and no tests establish its behavior. See [human-as-tool adapter](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/humanlayer.ts#L33-L43).

### Webhook state sketch: a useful boundary, not durable execution

The async sketch shows the intended sequence: checkpoint execution, create a function-call approval containing the proposed arguments and a state identifier, stop execution, then resume once a human response arrives. It correctly identifies the pause boundary between selecting and executing a tool. However:

- `__checkpointState()` returns the constant `fake-state-id` and persists nothing.
- `__getFromState()` returns fabricated message content rather than retrieving state.
- Stopping is `throw new Error("interrupt")`, without a supported typed interruption/resume protocol.
- `__resume()` has comments in the approved/rejected branches and performs neither tool execution nor continuation.
- There is no HTTP webhook endpoint, signature/authentication validation, duplicate-delivery handling, durable store, pending-call registry, timeout, cancellation, or crash recovery.

The file itself calls these mechanisms pseudocode and conditions the design on future GenSX interrupt support. Copying it into production would leave a stopped workflow, not a functioning approval-resume system. See [checkpoint and request](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/humanlayer-webhook-state.ts#L18-L51), [fabricated state](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/humanlayer-webhook-state.ts#L53-L80), and [comments-only resume](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/pkg/%40gensx/humanlayer-webhook-state.ts#L82-L101).

For a future agent service, the missing implementation would need to bind an approval to the exact tool name, validated arguments, run identity and code/state version; persist before awaiting; enforce at execution; resume only once; and distinguish approved, rejected, expired and cancelled calls. For a coding workflow in this repository, the lighter equivalent is a saved research/plan/handoff artifact containing concrete scope and completed validation, plus explicit existing tool permissions. Routine reversible edits already authorized by the user should not acquire an unnecessary approval gate.

### Build, dependencies and repository memory

The only scripts are `dev` (nodemon), `start` (tsx entrypoint) and `build` (tsc). There is no test script, test suite, CI configuration, lint script, executable package export or deployment configuration. `tsconfig.json` includes only `src/**/*.ts` and `src/**/*.tsx`; it excludes the `pkg` sketches from normal compilation. Nodemon watches only `src`. A successful default build would therefore not demonstrate that the proposed adapter or webhook implementation is correct. See [scripts and dependencies](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/package.json#L9-L30), [compilation scope](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/tsconfig.json#L20-L26), and [watch scope](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/nodemon.json).

Locked direct runtime versions are `@gensx/core` 0.3.7, `@gensx/openai` 0.1.19, `humanlayer` 0.7.6 and `openai` 4.90.0; the lockfile is version 3 with 107 package entries including the root. These are a March 2025 snapshot, not verified current APIs. Source imports `zod` directly, although the manifest relies on it as a transitive GenSX dependency. The manifest allows Node >=18.0.0, while locked `ini` 5.0.0 specifies Node ^18.17.0 or >=20.5.0, a mismatch for early Node 18/20 versions. The model string, older OpenAI API wrapper and proposed SDK integration would require fresh compatibility checks before adoption. See [the exact lockfile](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/package-lock.json). Node 18 itself is now EOL; Node 22 and 24 are listed as LTS on the [official Node release page](https://nodejs.org/en/about/previous-releases).

`CLAUDE.md` is mostly generated GenSX instructions: concrete commands, naming/style preferences, component/provider usage examples, and a managed section with a warning about overwrite. The custom project section is still a placeholder. The useful pattern is a small persistent entrypoint with verified commands and project-specific conventions. The limitation is equally important: generic framework examples do not explain the actual weather state, approval boundary, unimplemented package files, known failure cases, safe validation path or required environment variables. See [generated memory file](https://github.com/dexhorthy/humanlayer-gensx-example/blob/ea977e3a6abbbe0f56e7dfaff5daff889bb0ddc9/CLAUDE.md).

The entrypoint validates only the HumanLayer key explicitly; OpenAI configuration is delegated to its provider. `verbose: true`, tool console logging and workflow `printUrl: true` express observability intent; trace export depends on additional GenSX configuration and credentials. A diagnostic trace is not durable executable resume state. The weather state is global, mutable and lost on restart; the app defines no user/run isolation, persistence, configurable step budget, application-level retry policy or idempotency. The original 30 September review did not audit dependency behavior. The 1 October [dependency follow-through](gensx-adoption-audit.md) establishes that the inspected dispatcher validates arguments, runs same-turn tool calls concurrently, propagates thrown tool errors out of the loop, and appends history without a step cap or compaction. The inspected backend approval method polls every three seconds without an overall decision deadline. These are source deductions about the pinned versions, not live measurements. No standalone `LICENSE` file is tracked, although package metadata says ISC.

## 2. Enterprise GTM Starter: business application, useful engineering seams

### Actual architecture and behavior on default master

This 2019 example lets customers self-service a trial license via Replicated vendor APIs. Express serves `/healthz`, `/api/v1/config` and `/api/v1/signup`. Environment parsing constructs UI and signup defaults. The UI retrieves configurable markdown/title, then posts name, organization and email. The signup handler checks a truthy email, calculates an expiration using an injectable clock, calls an injected vendor-client interface to create a trial license, then downloads the license body and responds with JSON. The concrete vendor client builds authenticated POST and GET requests. See [README purpose](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/README.md#L1-L4), [server wiring](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/server/server.ts#L14-L38), [business logic](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/server/handler_signup.ts#L39-L60), and [vendor implementation](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/vendorclient/impl.ts).

The most useful coding-agent pattern is the seam between business logic and external dependencies. `ReplicatedVendorClient` declares two methods; `Signup` accepts that interface and a clock; one unit test uses a mock client and a fixed injected clock to verify expiration and call behavior without network writes. This makes a feature understandable and locally testable with a small context bundle. Adopt the separation and testability, rather than the dated stack. See [client contract](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/vendorclient/api.ts), [injection seam](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/server/handler_signup.ts#L6-L15), and [unit test](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/src/server/signup_test.ts).

Tilt orchestrates separate backend, frontend, unit-test, lint and integration-test images. Package manifests/configuration are added before source, and dependency installation is triggered on manifest changes. Kustomize separates base resources from development and distribution patches; user-specific development overlays are ignored by Git. Ship collects deployment configuration and renders Kubernetes artifacts. These are examples of making commands, environments and validation paths concrete for contributors. They do not provide an agent instruction hierarchy, context-compaction system or evaluation harness. See [Tilt development loop](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/Tiltfile), [base and overlays](https://github.com/dexhorthy/enterprise-gtm-starter/tree/b2a1108673618f8f7a5d99867600573b2938fd57/kustomize), and [Ship configuration](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/ship.yaml).

### Dated dependencies and reproduction limits

The Dockerfiles use `node:8` / `node:8-alpine`. The direct locked dependencies include React 16.8.1, Express 4.16.4, TypeScript 2.9.2, ts-node 3.3.0, TSLint 5.12.1, Mocha 5.2.0, react-scripts 2.1.3, request 2.88.0 and request-promise 4.2.2. The v1 lockfile contains 1,228 root dependency records and 2,194 records including nested dependencies. These facts show an old snapshot; this review does not invent a vulnerability count or certify current API compatibility. Node 8 is officially EOL. See [manifest](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/package.json), [lockfile](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/package-lock.json), [Dockerfile](https://github.com/dexhorthy/enterprise-gtm-starter/blob/b2a1108673618f8f7a5d99867600573b2938fd57/Dockerfile), and [official Node release status](https://nodejs.org/en/about/previous-releases).

`npm install --pure-lockfile` appears in the Dockerfile rather than a reproducible clean install. The distributed frontend uses nginx to proxy `/api/v1` to the backend; the same image contains both compiled frontend and backend. There is no ingress/load-balancer in the distribution resources shown; frontend exposure belongs to additional deployment setup. Development setup assumes Unix shell commands, Kubernetes and older Tilt APIs. None is warranted as a new prerequisite for this repository's coding-agent setup.

`LICENSE` says MIT, while `package.json` says Apache-2.0. This discrepancy should be resolved before treating metadata as a reliable copying policy. Source provenance, rather than assumptions from an author or repository name, matters.

### Supplementary non-default branch: what master misses

The `fix-install` branch adds a browser download via `FileSaver.saveAs`, webhook delivery, and a Pipedrive integration that finds or creates an organization, person and deal, adds participants to an existing deal, then records a note. These are actual additional implementations absent from the default snapshot. Its README explicitly calls the application a minimal POC and recommends copying relevant pieces rather than expecting rich customization. See [supplementary README](https://github.com/dexhorthy/enterprise-gtm-starter/blob/659c8712053af68f4ea3457fd138c49ec48e753b/README.md), [download implementation](https://github.com/dexhorthy/enterprise-gtm-starter/blob/659c8712053af68f4ea3457fd138c49ec48e753b/src/client/Form.js#L25-L76), [integration sequencing](https://github.com/dexhorthy/enterprise-gtm-starter/blob/659c8712053af68f4ea3457fd138c49ec48e753b/src/server/handler_signup.ts#L43-L92), and [Pipedrive client](https://github.com/dexhorthy/enterprise-gtm-starter/blob/659c8712053af68f4ea3457fd138c49ec48e753b/src/server/integration_pipedrive.ts).

These additions are still not agentic coding functionality. They illustrate external side-effect orchestration and its limits:

- License creation occurs before webhook/CRM work, and license download after it. If a downstream integration fails, signup returns an error even though the license may already exist. There is no durable outbox, workflow checkpoint, replay key or compensation.
- Find-then-create CRM operations are not atomic; concurrent signups can create duplicates, and organization search takes the first match rather than a verified unique identifier.
- Salesforce is displayed as an option and parsed, but its execution branch only logs that it is unimplemented.
- The distribution Secret adds webhook target but omits the webhook-enabled variable that the application requires; Pipedrive, trial duration and other `data` values still omit base64 encoding. ## 3. What to transfer into this repository

| Evidence from these examples | Practical adaptation | Evidence of improvement to measure |
|---|---|---|
| Clear interface and injected clock/client make one workflow understandable and locally testable. | Document real module boundaries and key files; expose external actions through small adapters; provide deterministic local checks. | Faster correct file selection, lower dependency on external services, fewer mistaken changes. |
| Actual approval decorator sits on the mutating function, whereas named no-op wrappers only create an appearance of control. | Put any required authorization in the tool/execution boundary. Preserve existing user authorization for ordinary coding; require a concrete reviewable artifact only for actions that need approval. | Zero unauthorized side effects; fewer unnecessary approval interruptions. |
| Incomplete checkpoint/resume code is outside compilation scope. | Distinguish implemented, experimental and proposed mechanisms in instructions; ensure verification covers changed files and their actual call sites. | Lower rate of passing checks that miss the changed feature; fewer unfinished mechanisms shipped as complete. |
| Generic `CLAUDE.md` remembers commands but lacks project-specific operational facts. | Use a concise verified repository entrypoint and task-relevant deeper docs, including commands, environment assumptions, file map and known traps. | Lower context/search cost and lower time to first correct implementation. |
| Live integration tests mutate licenses despite looking like tests. | Label test commands by effect; make default checks deterministic and credentials-free; document the explicit environment/authorization needed for external integration checks. | Fewer accidental external writes; more repeatable agent validation. |
| Source/config/backend/UI drift leaves advertised features incomplete. | Define acceptance behavior across layers and validate outputs that users actually receive; keep short handoff records of implemented versus incomplete work. | Fewer regressions, less rework and higher accepted-task success rate. |
| Source snapshots and default/non-default branches differ materially. | Pin external research, record version, and attach findings to exact code; refresh before adopting SDK/runtime code. | Fewer stale API errors and unsupported assumptions. |

For the proposed threefold goal, evaluate matched repository tasks under the same acceptance and agent/model/tool conditions. The primary metric is accepted tasks per human engineering hour, including active planning, supervision, review and rework; report elapsed delivery time and agent/tool runtime/cost separately. Use the explicit accounting and uncertainty rules in the [evaluation plan](../evaluation-plan.md). These repositories alone provide no guaranteed multiplier. The strongest near-term value is improving the local workflow and verification contract, rather than introducing the legacy Enterprise stack or deploying the GenSX sketches.
