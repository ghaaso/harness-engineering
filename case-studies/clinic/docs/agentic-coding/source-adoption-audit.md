# Audit: what this repository has learned from the four references

Completed 1 October 2026, America/Los_Angeles. Status: source/documentation review with a proposed adoption plan. No application implementation, framework installation, paid model experiment, external business action or deployment was performed.

## Answer

**The repository has learned most of the important principles accurately, but it has not carried all of them into the instructions used during coding. It has not demonstrated the requested quality, context or cost improvements.** The strongest missing transfer is between the detailed source reviews and the shorter launcher, templates and evaluation plan—not wholesale missing research and not a need to redesign the clinic application.

The existing material already gets important choices right: evidence authority, task-specific reading, proportional research/planning, complete observable slices, bounded delegation, independent expected results, durable handoffs and honest cost accounting. Selectively declining GenSX/HumanLayer, webhooks, CRM and Kubernetes is appropriate. These are not four interchangeable coding-agent frameworks, and copying every mechanism would add cost without demonstrated benefit.

The source-first reread found one factual overstatement to correct, a previously unrecorded denial-feedback defect in the GenSX example, and several operational details worth transferring. “Learned” here means represented in repository documents and usable by future tasks; it does not mean a model has been trained or that a documented workflow has been installed.

## What is already properly adopted

These strengths should be credited rather than rediscovered as missing work:

- **Authority and freshness:** source status, proposals, unknowns, source revisions and invalidation are explicit; a source document does not grant operational permission.
- **Selective context:** a small entrypoint routes to relevant domain/contracts/code, with broader reading only when the task requires it. There is no justification for injecting all four reference repositories into every coding task.
- **Proportional work:** simple edits do not require an elaborate research-plan-review ritual; complex work gets evidence and bounded design.
- **Observable delivery:** slices describe behavior across the necessary layers, with negative/integrity cases and actual check evidence.
- **Coordination:** bounded questions, scoped handbacks, disjoint ownership and one integration owner are already specified. Extra agents are a cost to justify, not a success metric.
- **Recovery:** handoffs record current revision, actual results, unresolved questions and next action. The docs distinguish passed, failed and unrun checks and automated review from human acceptance.
- **Evaluation discipline:** the existing plan includes realistic baselines, isolated starting states, task-order/familiarity controls, held-out acceptance, failures, rework, setup costs and uncertainty. This is a strong foundation to extend.

These are documented practices. The folder still has no clinic application, Git baseline or verified application commands, so their effectiveness in actual development remains untested. That absence is an execution stage, not evidence that the source lessons were misunderstood.

## Measuring the requested gains without changing their meaning

Keep four distinct outcomes. Select one primary metric per claim before running an experiment; do not choose whichever ratio looks largest afterward.

| Claim | Operational definition to select and record | Required interpretation |
| --- | --- | --- |
| **Quality** | Task acceptance, first-attempt acceptance, independently found defects by severity, escaped regressions and follow-up change success. If a multiplier is required, define a specific comparable defect-rate reduction: baseline rate / treatment rate. | A threefold defect-rate reduction is approximately 67% fewer defects per declared exposure. It is not “three times the quality.” Critical integrity/permission failures remain blockers. Zero denominators require counts/bounds, not an infinite success claim. |
| **Context efficiency** | Primary candidate: total model input tokens across all calls/workers per accepted comparable task, including repeated reads and cached inputs; compare baseline / treatment. Separately measure packet size, resume time, redundant reads, stale facts and required-fact retention. | A 5x token-efficiency result means one fifth the input tokens at comparable completion and quality. A fivefold smaller summary alone does not establish this. Measure cache discounts separately as cost; do not hide child-agent context or failures. |
| **Productivity** | Existing accepted tasks per total active human engineering hour, with elapsed delivery time separately reported. | This remains useful, but label a 3x productivity gain as productivity. Include setup, coordination, review and rework. |
| **Cost** | Total development model/tool spend plus human effort, setup/maintenance and repair, reported per accepted task and for the whole run. Keep application hosting costs in their own budget. | The clinic's USD 8/month hosting constraint is not a development-agent budget. A cheaper initial model call is not cheaper delivery if it causes escalation or repair. |

If the active toolchain cannot expose reliable token totals, record that limitation and use a clearly named proxy such as selected-file bytes or measured resume time. Do not relabel character counts as tokens or report an unmeasured 5x gain. Capture model/provider/version, pricing basis/date when converting usage to currency, cached/uncached input, output usage and all worker runs. Fixed instruction overhead can limit attainable token savings even when retrieval improves.

The context-quality test should have a predeclared list of decisive facts and statuses. It should check whether a fresh session retains the governing constraint, affected unknown, current revision, unresolved failure and exact next action, while detecting a deliberately stale source reference in a disposable fixture. Losing one decisive fact can negate a smaller packet. This evaluates information preservation and freshness as well as size.

The iterative-change test should start both conditions from isolated equivalent bases. Within each condition, keep that condition's own generated workspace across the initial task and two later requirements; do not replace it with a reference solution. Keep ordinary developer tests available, but separate evaluator holdouts. Use fresh sessions for the resume component, and explicitly state whether the treatment's handoff is available. Never leak the other condition's solution or future change requests.

Hold task scope, acceptance, model/settings, tools, budgets and eligible evidence constant for the workflow comparison. Test a cheaper-model policy later as a separate condition, so model changes are not confused with context improvements. Use pilot variance to design confirmation; neither a handful of successful tasks nor a point estimate establishes a general 3x/5x result.

## What should remain deliberately unadopted

No reviewed evidence warrants installing the example runtimes, a hosted approval platform, A2H/webhook services, email/Slack triggers, Kubernetes/Ship, a vector database or a large orchestration layer merely to improve this repository's coding workflow. The clinic application has no established requirement to be an LLM agent system. Runtime factors remain useful design references if that requirement appears later.

Do not copy the source repositories' historical model settings, arbitrary reading quotas, fixed context percentages, tentative XML-efficiency claims, incomplete checkpoint code, unbounded loops or automatic approval pauses. Do not treat generated expected output, saved unexecuted notebook cells, traces or a rendered deployment file as proof of successful behavior. Do not optimize code-line counts or static complexity scores instead of accepted outcomes and maintainability.

The efficient next step is to carry the narrow missing lessons into the existing workflow and measure them. More source material in every prompt would work against that objective. The original technical plan can remain the application planning baseline while these development practices are improved; its separate proposed corrections are retained in the secondary review, without being treated as accepted requirements.
