# A shipped system for smaller context without throwing away the work

The strongest match found is **[Claude Code Infinite](https://github.com/crizCraig/claude-code-infinite), version 1.0.14, using MemTree**. It is an existing Claude Code wrapper, not a proposed framework we would first need to build. It manages the request sent to Claude continuously, organizes older history into a topic hierarchy, retains access to original conversation messages and lets the agent recover details during work. It also has the closest published comparison to the user's actual scale and model.

Use it as the leading choice if a hosted memory service is acceptable. **[Virtual Context 0.6](https://pypi.org/project/virtual-context/0.6/)** is the strongest inspected alternative when local canonical storage and configurable request assembly are the priority. Its quality evidence is much less directly applicable to this case. YesMem offers a broader project continuity stack but requires WSL2 on this Windows machine. These are actionable existing systems; a bare token cap, handoff template or tool-output reducer does not substitute for them.

## The requirement and why the previous answer was wrong

The user reports a project process reaching around 700k tokens, writing a state file and opening a new chat. Two or three later runs return near 800k as file reads, shell output, retrieval and startup content enter the model again. The latest clarification adds the central success condition: the smaller 300–400k representation must retain the useful information and reasoning/task quality of the much larger accumulated history, with the workflow automated so manual handoffs, repeated rereading and compression delays do not become the next bottleneck.

The workload is incidental. Corpus structure, clinic requirements and graph provenance are not additional selection gates. The initial report wrongly made those part of the question and then overemphasized universal hard admission limits. Its source audits still establish specific tool behavior, but its integrated recommendation is superseded.

Two different meanings of preservation matter. **Recoverable originals** means the omitted text still exists and can be fetched exactly. **Preserved task quality** means Claude actually uses enough of the right information to produce comparable results without excessive recovery work. The first is an implemented mechanism in several candidates. The second requires task-level evidence. Neither a claim of “lossless” storage nor a large compression percentage proves it. Here, 300–400k is an intended active token range, not an interchangeable count of bytes or billed cumulative input.

## Why MemTree is the leading match

The wrapper launches the real Claude Code process behind a local proxy and keeps the supplied model and authentication. MemTree indexes batches in the background into topic summaries and a session tree. At a compression event, the outgoing history becomes a memory representation plus recent messages. Later requests reuse a stable compressed prefix and append subsequent messages verbatim. Compression is revisited as that combined representation grows, including inside tool loops and in separate subagent lanes. This changes the ongoing request construction that the state-file/new-chat loop left untouched. [Pinned implementation](https://github.com/crizCraig/claude-code-infinite/blob/6aaf6d59262bd6806ab73fba6a9ab9e69a5df57d/src/proxy.ts).

The agent receives tools to search sessions by exact words or meaning, open tree nodes and read original transcript lines. Project/directory/repository metadata accompanies indexing, and search can be scoped by project and date. Thus a later run can recover work from earlier indexed sessions. The source establishes access and automatic indexing; it does not prove that every fresh session proactively restores every relevant project decision without the agent searching. [Memory tools](https://github.com/crizCraig/claude-code-infinite/blob/6aaf6d59262bd6806ab73fba6a9ab9e69a5df57d/src/memtree-tools.ts).

The most relevant quality evidence is the maintainer's published long-session comparison:

| Arm | Mean score | Total input per run | Completion time |
| --- | ---: | ---: | --- |
| MemTree / Claude Code Infinite | 68.7/100 | 39M tokens | 11–22 minutes |
| Full-history Claude Code | 69.3/100 | 113M tokens | 24–54 minutes |
| Native compact before the task | 48.7/100 | 17M tokens | 29–40 minutes |

All arms resumed the same roughly 775k-token history and addressed previously identified security issues recorded in the conversation. The reported model was Opus 5.5, with three rounds and blind grading against a fixed answer key. MemTree first passed the history through, then compressed at an 800k trigger to about 420k. The full-history arm grew to roughly 970k and encountered native compaction during each round. Therefore this is a comparison with ordinary full-history continuation, **not a baseline that remained uncompressed forever**, and it does not isolate all effects of late native compaction. [Published benchmark](https://github.com/crizCraig/claude-code-infinite#long-session-benchmark).

The two approximately 69 scores are parity within the stated 10-point noise floor; they are not perfect task performance. The 39M figure is accumulated input over a run, not the resident prompt size. Three runs in one task family are promising evidence, not a universal equivalence guarantee. The inspected repository does not publish the individual run transcripts, answer key and machine-readable benchmark outcomes needed to independently reproduce this particular result. Ultracode mode is not specified. The exact target of 300–400k and many successive recompressions/restarts have not been demonstrated by that table.

## What the automatic operating setup would be

The shipped entry point is `npm install -g claude-code-infinite@1.0.14`, then `ccc`, with a PolyChat/MemTree key. Node 20.3 or newer is required. The wrapper forwards Claude's Anthropic credentials directly to Anthropic; conversation content is separately sent to the hosted MemTree service. Native login or an Anthropic API key is supported. This research verified the published npm version and matching Git commit; it has not performed the installation or account setup. [Release metadata](https://registry.npmjs.org/claude-code-infinite/1.0.14), [setup and architecture](https://github.com/crizCraig/claude-code-infinite#privacy--architecture-your-anthropic-credentials-never-leave-your-machine).

One project launcher should consistently run `ccc` from the same project path, preserving model/Ultracode selection and memory access across processes. Indexing, threshold checks, compression and recovery tool availability then run without a human generating a new handoff for each cycle. Automatic work does not mean zero model-directed retrieval calls.

The published default reproduces the broad benchmark behavior: an approximately 800k trigger, then a target around half of that. `CCC_COMPACT_TARGET=350k` selects a smaller compressed target but **does not lower the trigger**: without another change, the prefix can grow back toward 800k before recompression. The source also exposes `CCC_BUDGET_TOKENS=400k`, which lowers the ongoing trigger, but documents it as a **test-only override**. Combining the two is a concrete candidate setting for an automated 350k-to-400k operating cycle, not a production-certified or benchmark-proven configuration. A setup that merely selects a 350k target and leaves the 800k trigger untouched would miss the user's refill requirement. [Environment parsing](https://github.com/crizCraig/claude-code-infinite/blob/6aaf6d59262bd6806ab73fba6a9ab9e69a5df57d/src/cli-main.ts), [target/trigger planning](https://github.com/crizCraig/claude-code-infinite/blob/6aaf6d59262bd6806ab73fba6a9ab9e69a5df57d/src/proxy.ts).

The source limits ordinary blocking compression calls to 15 seconds and normally avoids them while the stable prefix is still below the trigger. Background indexing and prompt-cache reuse reduce routine overhead. Initial indexing or missing-tree recovery can nevertheless wait; retrieval adds work; there is no proof of zero delay. If MemTree is unavailable, too slow or payment is required, the wrapper can pass through an uncompressed request or the old prefix. The smaller operating range is then not maintained. This is an explicit service dependency, not a reason to pretend the candidate has no useful continuous mechanism.

Opus 5.5 preserved-thinking rules also matter. Successful recompression replaces the entire outgoing message history with a single flattened user message, after removing typed reasoning blocks from the copy sent to MemTree. It therefore does not retain old typed thinking blocks behind that changed prefix. Subsequent ordinary requests append a suffix to the stable prefix. Historical internal reasoning is omitted; raw-history fallback/resume remains an unresolved binding path in this audit. No successful-recompression signature failure was demonstrated. The native benchmark supports a narrow working case, while Ultracode and newer-account behavior remain unverified here. [Shipped transformation](https://github.com/crizCraig/claude-code-infinite/blob/6aaf6d59262bd6806ab73fba6a9ab9e69a5df57d/src/memtree.ts), [official preserved-thinking rules](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking).

Parsec's results are especially relevant to the demand for smaller context with comparable completed work: the test uses an actual task grader rather than a compression ratio alone. Its vendor owns both the system and benchmark, and the tested context scale is roughly one tenth of the user's history. Repeating a source tool call is its recovery path; that does not recreate an earlier version of a mutable file or shell result. It is therefore a serious alternative for tool-heavy work, with different preservation guarantees from MemTree/Virtual Context. ## The local framework notes help explain the mechanism

The local [context-engineering review](../../docs/agentic-coding/reviews/context-engineering.md) treats context as a managed working set: preserve durable evidence, bring in the material relevant to the current reasoning and evaluate performance. The [12-factor review](../../docs/agentic-coding/reviews/twelve-factor-agents.md) specifically distinguishes stored history from presented history and assigns routing/compaction to deterministic control flow. Those principles favor the continuous memory/request systems above. They do not establish a quality multiplier or prove a particular summary format is sufficient.

For this problem, the practical form is: keep the full original history in durable memory, carry a richer compact representation and recent working material in the active prompt, automatically recover original details when the task needs them, and keep applying that process throughout reads, tool loops and later runs. Its success is comparable completed work with manageable recovery/latency, not a screenshot of a smaller token count.

## Research result and limits

**Select Claude Code Infinite / MemTree as the closest shipped solution found; retain Virtual Context as the alternative for configurable local canonical memory.** The former has directly relevant but small Opus 5.5 evidence; the latter has more explicit source-visible retrieval and assembly controls but weaker applicable quality evidence. Neither can honestly be described as having proven universal 800k-equivalent reasoning at 300–400k with no slowdown or degradation.

This research supplies a real system, its automatic mechanism and a concrete target/trigger configuration distinction. It does not substitute an invented corpus design or a new framework-build task. Installation and live quality measurement are separate actions. Focused local mocked implementation tests for Infinite passed 89/89; these verify history validation, route isolation, sizing and fallback behavior, **not compression semantics, actual authentication, task parity or Ultracode operation**. Original project evidence remains unchanged.
