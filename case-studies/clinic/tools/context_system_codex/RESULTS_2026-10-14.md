# Three-way context-harness screen

**Verdict: inconclusive for context gains; stop larger live expansion.** All three
approaches reached their per-task limits before finishing the workload. The adapter
restored exact notes through two automatic compactions within 4 KiB, but produced
less completed work than either control at similar reported input. This is one
development case, so it does not establish general superiority or inferiority.

## Capped work results

Each approach used a fresh synthetic retry-worker repair with changing evidence,
a corrected policy and target, and intervening inventory audits. Same resolved
`gpt-6-astra` / `ultra`, 20k total-scope automatic trigger, controlled file tools,
3 KiB note ceiling and a 450k-input / 12k-output per-task soft cap. Normal working
notes were permitted in every arm; the notes and adapter arms had equal explicit
note-maintenance guidance. Agents wrote their own memory; no correct notes were
supplied by the evaluator.

| Approach | Partial completion score | Reported input | Reported output | Automatic compactions |
| --- | ---: | ---: | ---: | ---: |
| N: native, optional notes | 76.19/100 | 456,586 | 12,038 | 3 |
| M: native, maintained notes | 76.19/100 | 462,765 | 9,015 | 3 |
| A: full adapter | 71.43/100 | 455,234 | 7,570 | 2 |

These scores combine required artifacts, current configuration, evidence coverage
and observed checks. They are **partial completion scores, not fact-recall accuracy**.
Every approach retained the final worker configuration; no graded critical violation
occurred. Later audits and final verification/reporting remained unfinished. There
is no successful full-task control here, so equivalent-quality context savings
cannot be computed. The workload exceeded the completion-cost forecast.

The adapter's slightly lower cumulative input reflects a capped unfinished attempt;
it does not demonstrate savings on completed equivalent work. Its reported request
input median was 13,495 versus native's 13,789 and maintained notes' 14,701.5. Publish
all requests and outcomes together rather than treating those medians as a gain.
No arm used journal recall. This case therefore supplies no live evidence for an
incremental retrieval benefit.

## What worked

Two distinct adapter snapshots matched delivered text before observable continuation
output. Complete reconstructed hook envelopes measured **2,406 and 2,979 bytes**,
with no omitted blocks, below 4,096. This establishes bounded delivery of selected
notes. It does not measure the native summary's bytes or whole-context compression.
Exact network request timing remains unobserved; the behavior uses supported
[hook events](https://learn.chatgpt.com/docs/hooks) and
[app-server notifications](https://learn.chatgpt.com/docs/app-server).

Every measured tool RPC stayed below 2,048 bytes; observed maxima were 1,779 bytes
for native/adapter and 1,811 for maintained notes. Raw-event accounting matched the
runner totals with no cumulative regressions. Final offline suite: **151 tests,
149 passed, two Windows symlink-capability skips**.

Model-free profiling used 30 repetitions per path. Median in-process hook/storage
work was 4.9 ms, direct Python startup 71 ms, and the registered Windows wrapper
243 ms. First invocation is not guaranteed to be OS-cache cold. These local timings
explain only part of the earlier roughly 2.1-second native hook duration; remaining
native/runtime overhead is unattributed. Core hooks were kept unchanged.

## Interruption, amendments and complete reported usage

The first adapter attempt stopped during a host suspension. Its event log has a
14,227-second gap, aligned with independent Windows sleep/wake records; the native
client reports a websocket idle timeout. Its 105,642 input and 1,488 output tokens
are retained in the budget and excluded from quality comparison. One fresh adapter
retry ran with unchanged task, scoring, model and token limits. A temporary process
request prevented idle sleep during the resumed command and was released on exit;
its behavior follows the [Windows API contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate).

All four attempts used **1,480,227 reported evaluation input and 30,111 output**,
within the 1.5M / 40k stage allowance. In-flight input overrun above each 450k soft
cap was 6,586 (N), 12,765 (M) and 5,234 (A); native output also exceeded 12k by 38.
Compaction model usage, complete interrupted-request billing and this operator
chat's usage are outside those reported test totals. They are not billing ceilings.

Elapsed wall time including suspension was **16,888.984 seconds**. The original
two-hour wall-time limit was exceeded. A disclosed interruption amendment excluded
only the verified suspended gap from the remaining awake-runtime allowance. Total
awake runtime was **2,661.859 seconds**, within that amended two-hour allowance.
No end-to-end latency comparison is qualified by this run.

The first driver also treated reaching a task cap as invalid telemetry. A recorded
amendment allowed valid, observed interrupted outcomes to be scored, preserving the
native run without repeating it. Missing telemetry and transport failures remained
invalid. After all arms stopped unfinished, the raw runner labelled its stop
`adapter_quality_gate_failed`. The written plan requires **inconclusive when all
arms fail to finish**. This label was corrected offline and regression-tested;
expansion remains false, the scores are unchanged, and raw evidence is preserved.
All three executed driver versions are retained with their source hashes.

## Next decision

Do not launch the second family, byte-budget grid or held-out study from this screen.
First establish an affordable workload with a completed, competent control. The
current facade requires bounded raw reads and lacks ordinary shell/calculation
tools, so repeated reads, note writing and manual audit work can dominate usage.
A revised evaluation should provide realistic executable tools equally to every
arm and demonstrate feasible completion before interpreting memory quality.

The adapter remains a working experimental checkpoint layer. High context gains,
complete cost savings, long heterogeneous sessions and concurrent worker compaction
remain unproven. No cinema application changes, host installation, deployment or
production rehearsal occurred. Only the completed context harness and its adapter
were used as implementation sources.
