# O-08 design

DRAFT O-08 (for the Stage-3 critic). Unknowns are variables: BOX_LOC (Karachi | Islamabad | other), DOMAIN, ISP, OS, CASE (a Supabase restorable | b R2 dump only | c nothing), RPO_TARGET, MON_LOC. Facts are labelled VERIFIED (read or fetched), DERIVED (computed from verified numbers) or HYPOTHESIS (needs a test).

0. PRINCIPLES
P-A. The only thing the fleet ever sees is https://api.${DOMAIN}. It is baked into the APK (eas.json:21/29, config.ts:14), so it never changes again; DNS is the only indirection. Every move afterward (new box, VPS, back to a PaaS) is a DNS or tunnel change, not an APK release. This is the root-cause fix for this incident: the hostname belonged to Railway.
P-B. Phones PUT/GET media straight to R2 via backend-signed URLs (storage.py:1-12, :103-117), so the home uplink and tunnel carry only small JSON. That is why R2 stays and the box needs no object store.
P-C. Anything that must report the box's death lives OFF the box (error tracking, uptime, backups).
P-D. The backend never answers a 4xx for infrastructure reasons. 4xx means "your write is wrong" (syncClassification.ts:15 parks 400/403/404/409/422). Infra problems must be 5xx/429 or a network error, which the phones retain.

1. COMPOSE TOPOLOGY (docker-compose.prod.yml; the repo docker-compose.yml is dev-only, see O08-F04)
Networks: db (internal: true, no internet), app (default egress). No service publishes a port except optional 127.0.0.1:2222 style admin binds. Router forwards nothing. Docker bypasses ufw for published ports (VERIFIED, R-03 F16), so "no ports:" is the control, not ufw.
Services:
 postgres: image postgres:17 (Debian/glibc; pin minor and digest; the dump is from a PG17 server, loading into 16 is not guaranteed, R-03 F7). Named volume pg_data:/var/lib/postgresql/data. command: postgres -c fsync=on -c full_page_writes=on -c synchronous_commit=on -c max_connections=60 -c log_min_duration_statement=500 -c archive_mode=off (explicit so nobody tunes durability away; R-03 F15). env POSTGRES_USER=postgres, POSTGRES_PASSWORD, POSTGRES_DB=fixflow; a second role fixflow_app (DB owner, no superuser) is created by a one-shot init SQL; the app needs no extensions (gen_random_uuid is core, no CREATE EXTENSION found in alembic or app) but does use pg_advisory_xact_lock (chain). stop_grace_period 60s, shm_size 256mb, restart unless-stopped, healthcheck pg_isready. networks: db only.
 backend: build ./backend (same Dockerfile; pg_dump client 17 matches server 17). env_file /etc/fixflow/backend.env (root:root 0600, outside the repo). No ports; reached as backend:8000 on the app and db networks. command default (start.sh: alembic upgrade head, then ONE uvicorn process; never --workers, scheduler/limiter/metrics are per-process). healthcheck: curl -fsS -H "X-Ops-Proxy-Token: $FIXFLOW_OPS_PROXY_TOKEN" http://localhost:8000/api/ops/health (curl is in the image) - NOT /api/health (O08-F07). Gate: profiles: ["app"] so postgres can run alone during restore. logging json-file max-size 10m max-file 5 (unrotated Docker logs fill small disks).
 cloudflared: image cloudflare/cloudflared pinned; tunnel run with locally managed config.yml mounted read-only plus credentials file as a compose secret. ingress: api.${DOMAIN} -> http://backend:8000 (direct, no Caddy; see O08-F03); app.${DOMAIN} -> http://web:80; ops.${DOMAIN} -> http://ops:8080 only if behind Cloudflare Access; FINAL catch-all MUST be service: http_status:503 (a catch-all is mandatory, VERIFIED; the documented example is http_status:404, which would hand phones a definitive 4xx for any mis-routed hostname). Outbound 7844 only (VERIFIED F1).
 web: caddy:2-alpine (or a 5-line nginx) serving /srv from a build stage (node:22-alpine, ARG VITE_API_URL=https://api.${DOMAIN}, optional VITE_SENTRY_DSN) with try_files {path} /index.html, auto_https off (TLS is Cloudflare's, origin is plain HTTP on the private network), security headers incl. a CSP that allows api.${DOMAIN}, fonts.googleapis.com/fonts.gstatic.com and the Sentry ingest host (JWT sits in localStorage, so XSS hardening matters). Replaces serve@14/node:20 (O08-F11). Rebuild is mandatory whenever the API URL changes (Vite bakes it).
 ops: existing Dockerfile.ops (bump to node:22), env OPS_PASSWORD, OPS_SESSION_SECRET (set it; otherwise a redeploy invalidates sessions), OPS_BACKEND_URL=http://backend:8000, OPS_PROXY_TOKEN (= FIXFLOW_OPS_PROXY_TOKEN), OPS_HEALTH_TARGETS="api|https://api.${DOMAIN}/api/health,web|https://app.${DOMAIN}/", SENTRY_AUTH_TOKEN/SENTRY_ORG/SENTRY_PROJECTS if Sentry SaaS kept; OPS_RAILWAY_* and RAILWAY_* left UNSET (Railway pages then render "not configured", VERIFIED ops-server.mjs:415-421; overall status stays permanently degraded until O08-F09 is fixed). Not published unless behind Cloudflare Access or LAN-only (O08-F08).
 Optional, not on the critical path: glitchtip (+ its own postgres, valkey; recommended 512 MB, R-03 F12) and uptime-kuma (VERIFIED F13). Both are on the same box and therefore cannot tell you the box is dead - see section 2.
Backend env (every name; all prefixed FIXFLOW_, source of truth config.py):
 REQUIRED: DATABASE_URL (postgresql+asyncpg://fixflow_app:***@postgres:5432/fixflow; write the +asyncpg scheme by hand), ENVIRONMENT=production (O08-F01), JWT_SECRET (openssl rand -hex 32; compose uses ${...:?}), OPS_PROXY_TOKEN, CORS_ORIGINS (JSON list: ["https://app.${DOMAIN}"] - native app and same-origin ops need no CORS), R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET.
 SET DELIBERATELY: ENABLE_DISPATCHER=false (stays OFF through cutover; CLAUDE.md dispatcher invariants), ENABLE_SCHEDULER=true, SCHEDULER_TIMEZONE=Asia/Karachi, BACKUP_ENABLED=false until restore sign-off, then true with BACKUP_PREFIX=backups/db-selfhost/ and BACKUP_RETENTION_DAYS=30 (O08-F02), BACKUP_HOUR/MINUTE 2:30.
 OPTIONAL: SENTRY_DSN, FCM_SERVICE_ACCOUNT_B64, WHATSAPP_* (off), R2_MAX_UPLOAD_BYTES, JWT_EXPIRE_MINUTES (default 30 d), and the tunables inherited from H-02 (attendance_* ceilings, jobs_*, travel_sample_accuracy_ceiling_m, labour/fuel rates seed defaults) which stay at defaults: they are what the fleet was tuned against (S10).
Where secrets live: /etc/fixflow/*.env root 0600 plus tunnel credentials; NOT in git, NOT only on the box. An encrypted copy (password manager plus a printed recovery sheet) is part of the deliverable, because losing Railway's environment is what made this incident unrecoverable by configuration. Re-mintable if their accounts live: R2 keys, FCM service account, tunnel, Sentry tokens, JWT secret (old tokens are expired anyway after 30 days). Not re-mintable: the Android keystore (W0 item 3, export it), the Meta/WhatsApp templates (off).
Host: Linux (Ubuntu Server LTS) strongly preferred over Windows+Docker Desktop (needs a logged-in user, WSL2 VHDX power-loss semantics) - OWNER PARAM. systemctl enable docker; BIOS "power on after AC loss"; chrony/timesyncd (the server judges device clock drift at 120 s and re-buckets punches beyond 24 h/120 s, S10, so a wrong server clock corrupts attendance timing); SSH key-only and ideally reached over a private overlay, not a forwarded port; unattended-upgrades with the reboot window at 04:30, clear of the 02:30/03:00/03:30 jobs; no auto-updating of images; docker group treated as root (VERIFIED F17).
Sizing: DERIVED, 2 vCPU/4 GB/SSD is ample (about 0.35 req/s, 302 KB DB, ADR 0001). Consumer SSD without power-loss protection plus a UPS is the durability stack; fsync stays on.

2. WHAT STAYS EXTERNAL AND WHY
 R2 for media AND backups: phones PUT to presigned URLs (the box never carries video), 10 GB-month free, free egress (VERIFIED F10), and backups are off-box by construction. MinIO community is archived (F11); the endpoint is hard-coded anyway (O08-F10). Watch the 10 GB cap and 1M Class A ops; deep-health's list_keys is a Class A op per poll.
 FCM: only transport for push to Android; outbound from the box (notifications/service.py hosts www.googleapis.com, fcm.googleapis.com). Needs the Firebase project and a regenerated service account.
 Error tracking: recommend KEEPING Sentry SaaS for now. A GlitchTip on the same box dies with the box and costs about 512 MB plus its own Postgres; the APK DSN is already baked and cannot change without a new APK. GlitchTip (SDK-compatible) is a later owner option; ops-server's Sentry pane would then need a base-URL setting (backlog).
 Uptime/dead-man: MUST be off-box (MON_LOC). Preferred: a host cron every minute that runs a DB-touching check (row counts above a floor + /api/ops/health) and only then pings an external heartbeat service; silence pages the owner. Uptime Kuma off-box is the alternative. The heartbeat services are not researched in W1.
 DNS/tunnel/TLS: Cloudflare. Concentration risk: one Cloudflare account now holds DNS, tunnel, R2 media and backups. Keep a second-provider weekly copy of the newest dump (owner laptop plus e.g. a second object store), 2FA and recovery codes, auto-renew multi-year domain registration.
 Cloudflare Access for ops/web admin, optional. Free tier seat figure unverified (R-03 F4).
 Backup tiers: T1 existing nightly pg_dump to R2 (RPO up to 24 h; restore drilled at 4 s for 302 KB). T2 (owner decision RPO_TARGET) add pgBackRest WAL archiving to R2 (VERIFIED F8/F9: PITR needs base backup plus WAL; unmonitored archive failures fill pg_wal). The outbox covers technician writes, not manager web writes (no outbox).

3. CUTOVER SEQUENCE (the drain protocol itself is O-10; this is everything before it and the gate to it)
Common pre-flight (any case)
 1. Fleet holds: techs do not open the app, discard, update or clear data (design doc 4.0 item 1). Nothing below touches phones until step 12.
 2. W0 outputs known: Supabase state, R2 dump listing, EAS build and keystore, Railway control of the old hostname, workshop coordinates. Supabase clock: ADR 0001 says free projects auto-pause after a week idle; the docs page I fetched says a 1-year restore window while an image caption reads "90 Days Remaining" - VERIFY the real deadline in the dashboard today; it is the only irreversible clock in the program.
 3. Decide DOMAIN, put it on Cloudflare DNS, create the tunnel and R2 keys; box built; secrets generated; compose.prod.yml on the box. Tunnel up but hostname routes to a maintenance responder that returns 503 + Retry-After (never 404/403).
 4. Build gate: backend gates against postgres:17 (O08-F12); web image built with VITE_API_URL=https://api.${DOMAIN}.
Restore (postgres alone: docker compose up -d postgres; the backend must NOT start first - if it boots on an empty DB, alembic builds a schema and seeds dispatch_cursor, then a restore collides)
 CASE a (Supabase restorable): restore the project in the dashboard (or at minimum download its logical backup); from the box run pg_dump 17 through the SESSION pooler (port 5432, never 6543; RUNBOOK) with exactly backup.py's flags: --format=custom --schema=public --no-owner --no-privileges. Also pull the newest R2 dump as the cross-check and as fallback. Prefer the live dump; compare the two with the Appendix B counts.
 CASE b (R2 dump only): re-mint R2 keys, list backups/db/, take the newest fixflow-db-<stamp>.dump. RPO = outage start minus that stamp (known newest 20260802T023008Z at head 0045, 302 KB). Anything the fleet synced after that stamp is lost server-side; it only survives where a phone still holds it. Media objects uploaded after the dump remain in R2 without DB rows (orphan sweep only flags, main.py:163-180, it does not delete).
 CASE c (nothing): fresh DB from alembic; accept that only phone queues carry data. See "case c extras".
 Common restore steps (a, b): copy dumps to archive/pre-selfhost/ in R2 and to the laptop FIRST (O08-F02). In the empty target: psql -c 'DROP SCHEMA public CASCADE' (avoids the benign 'schema public already exists' error, O08-F06), then pg_restore --no-owner --no-privileges --exit-on-error -d fixflow dump. Then ALTER ... OWNER (or restore as fixflow_app) so the app role owns objects. Do not run alembic yet.
Verification gate (Appendix B, run with psql) - all must pass before the backend starts:
 - alembic_version equals 0045 or 0046 (dump head must not exceed code head 0046; the code head is the end of the down_revision chain). A 0045 dump gets 0046 on first backend boot, which seeds dispatch_cursor at the restored job_event head (forward-only, correct). A 0046 dump already has the row.
 - Row counts for every public table are at or above the last drill (42 app tables + alembic_version; 3,268 rows in the 2026-08-02 drill), job_payment non-voided sum reconciles (Rs 34,400 at that drill), staff_ledger and staff_ledger_chain counts, and the chain head verified later via GET /api/attendance/ledger/verify.
 - Sequences: job_token_seq, job_event_seq, shop_setting_seq (three, not two; migrations 0016/0027/0040). A full custom-format restore replays SETVAL; check each is at or above its table max (job_token_seq floor 1052 start; 1057 at the last drill). A sequence below max makes every write a 500 while reads stay green.
 - dispatch_cursor: the whatsapp row exists with last_seq at or near the max job_event.seq; ENABLE_DISPATCHER=false in the env file (verify by reading the file, not from memory).
 - attendance_geofence: the active row has the workshop coordinates and is_active (S11); if the live fence is the (0,0) placeholder or inactive, every phone will call stopGeofencing the moment it connects. Set it from W0 item 9 before admitting traffic.
 - Technician PINs: the restored real PINs are fine; for case c rotate t1..t5 and m1 PINs BEFORE the tunnel is routed (seed PIN 1234 is public in the repo, S14).
Admit traffic: docker compose --profile app up -d (start.sh runs alembic upgrade head then serves). Check /api/ops/health (db, migrations head, config jwt_secret_overridden true, r2). Smoke on localhost then through app.${DOMAIN}: login, a job read, a test write on a throwaway job, ledger verify. Only then flip api.${DOMAIN} from the 503 responder to backend:8000. Enable BACKUP_ENABLED with the new prefix only after the owner signs off the restore; run one manual backup and one restore drill into a scratch DB.
Order, as required: backend on the owned domain (steps above) -> new APK (same applicationId com.fixflow.technician, same keystore, higher versionCode, EXPO_PUBLIC_API_URL=https://api.${DOMAIN}, non-empty Sentry DSN per the CLAUDE.md traps; installed over the old build, never uninstall because uninstall erases AsyncStorage queues) -> drain per O-10 (pilot on one phone, then the fleet). Queued items hold paths only (api.ts:93), so they flush to the new host. Existing JWTs are expired (30 d) so the first request 401s; the outbox pauses on 401 and never fails the write (syncClassification.ts header), so the tech logs in with name/PIN. Open question for O-10: queued items carry no author, so a shared phone's items drain under whoever logs in.
Case c extras: set setval('job_token_seq', N) with N well above the highest token seen in any phone's jobsCache (customers hold printed tickets with 1051-1057+), set the fence, rotate PINs, create real catalogue/customer data as needed. Expect job-scoped queued writes for vanished jobs to 404 and park in the phones' failed lists (visible, Discardable); idempotent creates (client_id) and attendance punches for t1..t5 replay fine. Media for those jobs may exist in R2 under old keys with no DB rows.
Rollback: the source of truth stays untouched (Supabase project, R2 dumps) until sign-off. Never alembic downgrade; never roll an image back below the DB's applied head (ADR 0001 rules apply unchanged).

4. CONSTRAINT: NO OLD HOSTNAME MAY EVER ANSWER 4xx TO THE FLEET
 - Existing *.up.railway.app: unfixable from the box (O08-F14). Only W0 item 2 can: regain the service and bind a stub returning 503, or a pass-through proxy to api.${DOMAIN} that never fabricates a 4xx; if it cannot be regained, the APK update is the only road and no phone may run the old build online.
 - The new hostname must hold the rule for ever: (i) tunnel catch-all http_status:503 not 404; (ii) Cloudflare WAF, Bot Fight Mode, Browser Integrity Check, managed challenges and Access must be OFF for api.${DOMAIN} - a challenge returns 403, a definitive park, to okhttp-style clients; (iii) rate-limiting rules only as 429 with Retry-After (429 is retained, syncClassification.ts); (iv) maintenance and restore windows answer 503; (v) a down tunnel should surface as a Cloudflare 5xx (docs: 530 means origin cannot be reached; that a stopped tunnel yields exactly 530/1033 is HYPOTHESIS - test by stopping cloudflared and curl -i); (vi) DNS or TLS failures are network errors the phones retain; (vii) domain expiry or a registrar parking page is the same failure class as Railway's 404 - multi-year, auto-renew, registrar lock, 2FA; (viii) no path-based routes: unknown paths reach FastAPI, whose 404 is a real "no such route", not an infra answer.
 - Do not reuse an old hostname for anything else, and never stand up a stub that answers 200 with a non-JSON body.

ADR's DB-move projection (DERIVED, not measured): POST p95 about 805 ms, about 16.7 s per job.
 Self-hosted legs (all DERIVED/HYPOTHESIS until the section-1 tests):
  L1 phone -> Cloudflare edge: HYPOTHESIS 30-120 ms on Pakistani mobile data if a PK PoP serves; the 675 ms to Railway was routing-bound, so Cloudflare could be worse; test via cf-ray suffix.
  L2 edge -> cloudflared connector: 0 if the connector registers at the same PoP; HYPOTHESIS 30-100 ms if it hairpins via Mumbai/Dubai. BOX_LOC=Karachi minimises L1+L2 for Karachi users; BOX_LOC=Islamabad adds a domestic Karachi-Islamabad leg of about 20-40 ms (HYPOTHESIS) only if both ends use PoPs in different cities, otherwise nearly nothing.
  L3 cloudflared -> backend (same host): under 1 ms. L4 backend -> Postgres (docker bridge): about 0.1-0.5 ms per statement; the 9-11 statement job detail (S-09 F16) is about 5-20 ms server time, floor about 2-10 ms; pool_pre_ping now costs sub-millisecond instead of 230 ms.
  L5 R2: signed URL minting is local compute (generate_presigned_url); only finalize's head_object and the deep-health list_keys cross to R2 from the home ISP, HYPOTHESIS 50-300 ms, once per media finalize, not per API request. Large uploads/downloads bypass the box.

 Predicted end-to-end = R_c + server (10-40 ms) with R_c = L1+L2 in 60-250 ms (HYPOTHESIS): GET about 100-300 ms, POST p95 about 150-400 ms, versus 1703 / 2461 ms today and about 805 ms in the ADR's California projection; per home-visit job about 3-7 s versus 30.7 s / 16.7 s. Hold this as a range until a field-phone curl timing run is done. The 15 s client timeout is no longer approached.
 Manager at the shop: hairpins out to Cloudflare and back (2x R_c) unless split-horizon DNS points api.${DOMAIN} at the box LAN IP with a DNS-01 certificate (Caddy; needs a custom build and Cloudflare API credentials, F5) - OWNER PARAM P8; it also lets the shop work during an ISP outage.

6. FAILURE MODES AND RUNBOOK SKELETON
 Power cut: UPS covers box, modem/ONT and router (the router is the usual forgotten link); BIOS auto power-on; fsync on; unless-stopped only restarts containers that were running (a manually stopped container stays stopped, F14); systemd enables docker. LUKS with a passphrase prompt blocks unattended boot - choose between disk encryption and self-recovery (P13). Fleet effect: tunnel down -> 5xx/network error -> queues retained.
 ISP outage: outbound-only tunnel survives CGNAT and dynamic IPs (F2) and fails over transparently to a second uplink (LTE/second ISP) with no phone-side change; without one, expect outage-length queueing. CGNAT: irrelevant for the tunnel, fatal for any port-forward plan (so Caddy ACME HTTP-01 is not the plan).
 Disk failure: single SSD loses up to 24 h (T1); mitigate with RAID1/second disk, SMART alerts, T2 WAL archive if RPO_TARGET demands, weekly restore drill into a scratch DB (the drill table in RUNBOOK-BACKUPS.md continues). Disk full: Docker log rotation, pg_wal, archive failures; alert at 80%.
 Clock: wrong server time re-buckets punches (S10); chrony, alert on drift.
 Cloudflare account lock/lapse: tunnel, DNS and R2 backups fail together; second-provider backup copy; documented fallback to a cheap VPS running the same compose (restore procedure identical; only DNS changes).
 Postgres container crash or bad migration: start.sh exits non-zero, container restart-loops; read the log, never downgrade, restore from the last dump if needed.
 Theft/fire/physical access: customer and employee data now sit in the shop; encrypted backups, secured location (P13).
 Runbook skeleton (write each as a one-page checklist): R0 daily - heartbeat alive, disk, last backup age; R1 box will not boot; R2 ISP down; R3 restore from R2 (this document section 3 verbatim, including archive-first); R4 tunnel/DNS/domain/Cloudflare issue; R5 deploy (git pull, build, up -d; image digest logged; rollback rule); R6 rotate secrets (JWT secret invalidates all sessions - schedule it; ops proxy token both sides together); R7 monthly restore drill; R8 box replacement or move to a VPS; R9 PIN lock recovery (set_pin or scripts/unlock_account.py per CLAUDE.md); R10 new APK release (URL never changes).

 P9 Cloudflare Access for ops/web admin; ops published or LAN-only.
