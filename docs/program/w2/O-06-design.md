# O-06 design

AUDIT/FORENSICS MINIMUM (what must exist before the pakka-khata flows to Odoo)
1. Void metadata on every voidable money row. job_payment gains voided_by/voided_at (staff_ledger already has them, models.py:479-482). Every void writes a job_event whose payload is {payment_id, amount_paisa, method, reason}, so a void can be tied to its row. Payment-create events carry the same payload (today they carry only text: service.py:1478-1484).
2. Bill snapshot history. Add an append-only job_bill_revision table (job_id, rev, kind completion|override|negotiate|send, original_paisa, negotiated_paisa, materials JSONB, labour_rate, time_spent, fuel_paisa/basis, actor, reason, created_at), written in the same transaction as every completion upsert, negotiate and bill send. This stops clear_materials (service.py:1225) and the bill_original_paisa overwrite from destroying evidence. A manager override and a post-send negotiate require a reason.
3. Append-only approval records. A single approval table (subject_type: advance|bill_override|negotiate_over_cap|erp_batch|ledger_entry, subject_id, decision, decided_by from the principal never the body, decided_at, reason). Self-approval is refused (decided_by != subject tech, or != recorded_by). Rejections are never deleted. This is also the shape the Odoo supervised transfer (S-04 F35) needs: Odoo receives only rows with an 'approved' decision, and the export batch carries its approval id.
4. Actor from the principal everywhere. Fix attendance_adjustment.manager_id (O6-F10) and audit other body-supplied actor fields.
5. One tamper-evident money chain. Generalise attendance/chain.py into a per-shop chain covering staff_ledger, job_payment create/void and job_bill_revision. Verify daily on the scheduler, write the result to app_event, and push the head_hash to the owner out of band (WhatsApp/email) or to a locked object under a different account. That anchor is the only thing that defeats an operator who can recompute an unkeyed chain.
6. Client-side destruction becomes visible. A discard sends a droppable telemetry record. A per-tech count of discards and of mock or uncorroborated days appears on the manager board and in the owner digest.
7. DB-enforced append-only. With the role split (O6-F18), REVOKE UPDATE/DELETE/TRUNCATE on job_event, staff_ledger_chain, attendance_event, attendance_adjustment, shop_setting and job_bill_revision from the runtime role, and grant column-level UPDATE only on void columns. Code conventions then become DB facts.
8. An owner role, or at minimum an owner-only read-only digest, so that manager-on-manager money (O6-F16) has a second pair of eyes. Today there are only tech and manager.

HOME-BOX OPERATOR MODEL
Threat actors: (a) internet scanners hitting tunnel hostnames; (b) a technician with a valid PIN/JWT; (c) a manager; (d) the operator, the person with a shell on the box, who may not be the owner; (e) anyone who walks off with the box or its disk; (f) Cloudflare as TLS terminator.
What the tunnel changes: no inbound port is needed (R-03 F1/F2), but every hostname in the ingress is public, and the tunnel token itself lets any holder run a connector for that tunnel. That is from my own knowledge and was not fetched in W1, so verify it. The tunnel token is therefore a top-tier secret. It does not remove LAN exposure: Docker-published ports bypass ufw (R-03 F16), and docker-group membership or a mounted docker.sock is root on the host (R-03 F17).
Network layout:
- Postgres, the backup job and any admin UI have no published ports (or bind to 127.0.0.1) on an internal Docker network.
- cloudflared is the only egress-to-edge path.
- Ingress has three hostnames: api.<domain> (open; the phones need it; rate-limited at Cloudflare), manager.<domain> and ops.<domain> (both behind Cloudflare Access with owner/manager email OTP; Free plan up to 50 users per R-03 F4, to be verified).
- Do not mount docker.sock into any container (Uptime Kuma, watchtower and the like).
- SSH is key-only, and admin happens over a tailnet or LAN rather than a published hostname.
Boot safety: the backend must fail closed on DEV_JWT_SECRET regardless of Railway detection (O6-F01). Rotate all seeded PINs before the tunnel goes up (O6-F05). Disable /docs in production (O6-F19).
Secrets at rest: one env file today grants JWT forgery, R2 read/write/delete and WhatsApp/FCM sending (config.py:35-36,133-140,151). Move secrets to root-only 0600 files or Docker secrets, keep them out of any backup of the box, and split them by process: the API never needs the backup-encryption private key or the tunnel token.
Database: use least-privilege roles (O6-F18). Keep fsync and full_page_writes on, and put the box on a UPS because Karachi load-shedding makes power loss routine (R-03 F15). The local superuser password is not kept on the box in plaintext.
Backups: encrypt with age to the owner's offline key; ship to a separate bucket or account with a put-only token and provider-side retention or lock; copy a second set off-box. The operator can read or edit live data but cannot silently delete or alter history once it has left the box. Monthly restore drills (RUNBOOK-BACKUPS.md) also verify the chain anchor against the restored head.
Who can read staff_ledger: through the API, any manager for any tech (router.py:515-526) and each tech for themselves (/ledger/me). Through the DB, the single app role, any dump holder and the operator. After the redesign: managers and the owner through the API; fixflow_app and fixflow_backup in the DB; dumps readable only with the owner's key.
Residual risk to accept explicitly: an operator with root on the live box can still alter live rows. The design does not stop that. It makes the alteration detectable within a day through the out-of-band head-hash anchor and the encrypted, put-only backups.
