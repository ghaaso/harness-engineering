# c1 collect mergeq: batch testing, bisection and merge queues in practice

`P:` = `docs/program/evidence/round3-2026-11-18/papers/check/`. Line numbers are lines of `paper.txt` made with
`pdftotext -raw` (two-column papers read badly with -layout), except P5 and P6, which are web pages stripped to text.
Quotations are exact. Anything I read only inside another paper is marked "reported in".

## Gate summary
- P1 Uber SubmitQueue 2019: SubmitQueue P50 turnaround up to 2.98x an oracle that predicts every outcome; 1.2x with 500 workers at 500 changes/hour; Speculate-all up to 15x; Single-Queue (one change at a time) 80x P50 at 500/hour. Replay of one iOS monorepo. quoted, txt l.1146-1167.
- P2 Najafi, Rigby, Shang 2019 (Ericsson): batching saves 72% of test runs at failure rate 2.8% (batch 9); flakiness cuts the saving to 41% (batch 4); culprit rate 6.8% and 8.6% give batch 4 and 46-50% at best. quoted, l.37-43, 549-555, 614-621.
- P3 Fallahzadeh, Bavand, Rigby 2023 (FSE): BatchAll (batch = everything waiting) keeps average feedback time with up to 91% fewer machines (Chrome, 8.5% failing builds); a constant batch of 4 loses at Ericsson (-14.29% machines). quoted, l.36-47, 760-778, 840-848.
- P4 Fallahzadeh, Rigby, Adams 2025 (EMSE, 285 million results): batching up to 99% less feedback time with no missed failure; test selection up to 96% but misses up to 55% of failures. quoted, l.20-27.
- P5 Zuul gating docs: speculative testing of every queued change; window starts at 20, +1 per merge, halved per failure. No numbers. quoted from documentation, l.919-975.
- P6 GitHub merge queue docs: group of changes ahead in the queue, build concurrency 1 to 100, merge limits 1 to 100; no numbers. quoted from documentation, l.179-221.
- P7 Juloori and others 2025 (Uber, ICSE): speculation threshold plus build-time prediction: builds-per-change 3.39 to 1.85 (Go), 4.93 to 2.57 (iOS), 5.43 to 1.96 (Android); CPU hours -44.70%, -34.86%, -52.23%. Production, 21 weeks. quoted, l.1013-1036.
- P8 Memon and others 2017 (Google TAP): one test run per "milestone" (about every 45 minutes) instead of per change; cost "growing quadratically"; 99:1 pass:fail per change. quoted, l.46-80, 176-182, 316-349.
- Not opened: Beheshtian, Bavand, Rigby TSE 2021 and Bavand, Rigby ICSME 2021 (no open copy); their headline numbers are only reported in P3. See "Could not open".

## Papers

### P1. Ananthanarayanan and others, "Keeping Master Green at Scale", EuroSys 2019. Read from: https://lethain.com/static/blog/2019/eurosys19uber.pdf. Saved: `P:uber-submitqueue/paper.txt`. Read: sections 1-2, 4 (mechanism), 8 (evaluation), 8.5, by grep and range; not every page.
- Problem: keep the main branch always green while thousands of changes a day arrive; testing in order is too slow, testing independently lets semantic conflicts through.
- Mechanism: a queue builds a change speculatively on top of the pending changes ahead of it; a probabilistic model scores which speculative builds to run (greedy best-first); a conflict analyzer on the build graph finds independent changes and runs them in parallel; the first build whose assumptions hold commits.
- Result (conflicts, why a queue is needed): "Observe that with even two concurrent and potentially conflicting changes, there is a 5% chance of a real conflict. This number grows to 40% with only 16 concurrent and potentially conflicting changes." (l.229-231). "even changes with one to ten hour staleness have between 10% to 20% chance of making the mainline red" (l.243-244).
- Result (before): "Over a span of one week, the mainline was green only 52% of the time" (l.1427-1428). After: "Since its launch, our mainlines have remained green at all times." (l.1431-1432).
- Result (turnaround): "leads to maximum of 2.98x slower 50-percentile turnaround time, compared to the optimal Oracle solution" (l.1146-1148). "with 500 workers, 50-percentile, 95-percentile and 99-percentile turnaround time gets reduced to 1.2x of the Oracle's" (l.1154-1156). Speculate-all "suffers up to 15x" at P50 and "up to 24x" at P99 (l.1158-1159). "Interestingly though, the Optimistic approach results in better turnaround times compared to Speculate-all ... Thus, speculating deep instead of going wide helps." (l.1160-1164). Single-Queue "grow 80x, 129x and 132x" for P50, P95, P99 at 500 changes/hour (l.1166-1167).
- Result (throughput): "up to 60% slowdown compared to Oracle, the slowdown reduces to around 20% with 500 workers" (l.1314-1315); Single-Queue "95% slowdown" (l.1391); "Optimistic ... remains unchanged as we increase the number of workers" because "its throughput is limited by the number of contiguous changes that succeed" (l.1391-1397).
- Result (conflict analyzer): "The turnaround time of Oracle improves by up to 60% with the conflict analyzer." (l.1409); only 20% for Optimistic "due to the fact that the build graph on the iOS monorepo is very deep" (l.1414-1418).
- Measured gain: against the one-at-a-time Single-Queue, SubmitQueue is roughly 27x better at P50 at 500 changes/hour (80x vs 2.98x; my division of the two quoted ratios, both against the same oracle, so a reasoned ratio, not a quoted one). Baseline for the other figures is an oracle, not a real system. Workload: iOS monorepo changes of the first 9 months of 2018 replayed at 100, 200, 300, 400, 500 per hour (l.1130-1132). Scale: up to 2000 workers for the oracle, 500 for SubmitQueue.
- Assumes: a model trained on history predicts success well (accuracy "97%" l.1041); builds deterministic; a build graph that says which changes touch which targets; enough parallel workers (the gain at 500 workers is 1.2x, at fewer it is up to 2.98x); the share of failing changes is lowish (Speculate-all assumes a 50% chance of success, l.1058-1060, and loses 15x).
- With model sessions (reasoned): the speculative build of a change on top of changes ahead costs one check run per path, which is a cost in minutes not tokens; the token cost arises only when a worker is told to redo its work after a rejection. A worker-minutes unit (minutes per change) is slow against Uber's build seconds-to-minutes mix, so queue depth and the odds that the changes ahead fail matter more than the model; with 3 to 16 workers the speculation tree is shallow (at most 16 levels) and the 5% to 40% conflict figure is a model figure for a monorepo, not for 3 to 16 sessions on one repository. A rerun after a failure is not the same run (a worker revises), so speculative builds on a failed change are lost work as in the paper, but the revised change must start again.
- Needs to know about a project: which change touches which build targets (a build graph), history to train the success model, whether builds are deterministic.
- Status: quoted.

### P2. Najafi, Rigby, Shang, "Bisecting Commits and Modeling Commit Risk during Testing", ESEC/FSE 2019. Read from: https://ece.uwaterloo.ca/~wshang/pubs/Armin_FSE_2019.pdf. Saved: `P:najafi2019/paper.txt`. Read: abstract, sections 1, 2, 4, 5.1-5.3, 7 (about 80% of the text).
- Problem: how large a batch of changes to test as one, given the failure rate, when a failing batch is split by bisection; effect of flaky tests.
- Mechanism: test several commits together; if the batch fails, bisect (a binary search over its commits, "2 x log2(n) + 1 executions" to find one culprit, l.212-213 region, 2log2(n) quoted at l.481); a risk model can test the riskier commits alone (TestTopK).
- Result (abstract): "batch testing saves 72% of test executions compared to testing each commit individually" (l.37-38); "test flakiness reduces the cost savings to 42%" (l.42-43; the body gives 41% for the best project); culprit prediction "reduce test executions up to 9% compared to Ericsson's current bisection approach" (l.47-49).
- Result (failure rate sets batch size): "The higher the CulpritRate the smaller the most cost-effective BatchSize. For example, Project A has a CulpritRate 2.4 times higher than Project C and with a BatchSize of 4, the savings are 46%. In contrast, Project C can have a BatchSize up to 9 and saves 72% of test executions when compared with testing all commits." (l.549-555). Culprit rates: "6.8%, 8.6%, and 2.8%" for projects A, B, C (l.421-422). "the savings are logarithmic, with the majority of the savings occurring with BatchSizes up to 4" (l.539-540); batch 2 already gives "34%, 34%, and 44% fewer executions" (l.537-539). Limiting case: "all commits could be placed in a single massive batch requiring a single passing execution and saving n-1 executions" when nothing fails (l.523-526).
- Result (flakiness): "The higher the FlakeRate the smaller the BatchSize and smaller the savings in executions. For example, Project B has a FlakeRate 1.37 times higher than Project C and a BatchSize of 4 saves 14% of the executions compared to 41%" (l.614-619). "Project C's most cost-effective BatchSize and savings are reduced from a BatchSize of 9 and execution savings of 72% to 4 and 41%" (l.619-621). Flake rates (share of batches that failed flakily): "23.6%, 23.1%, and 16.9%" (l.577-579 region); project A with the highest flake rate gets batch 2 and only 7%.
- Measured gain: 72% fewer test runs than one commit at a time, best case (2.8% of commits are culprits, batch 9); 41% to 7% once flaky failures are counted. Baseline: test every commit alone. Workload: simulation over 9 months, 14k commits, three Ericsson projects (1.3k, 3.5k, 9.5k commits) (l.405-406, 292).
- Assumes: independent commits ("At Ericsson each commit under test should be independent of the other commits", l.817-818), so bisection works on an unordered group; failure rate known from history (CulpritRate, FlakeRate "can be trivially calculated from historical test results", l.131-132); resources counted as executions (not time); one failure per batch. Does not model waiting time or parallel machines.
- With model sessions (reasoned): the best batch size falls as the failure rate rises, in a form that a ratio states: at a culprit rate near 3% a batch of 9, near 7% to 9% a batch of 4 or 2. Model-session changes are likely to fail more often than Ericsson's commits (a unit is large, minutes, written by a model), and "a rerun is not the same run" means a batch's failure may not reproduce, which acts as flakiness and caps batch size near 2 to 4. At 3 to 16 workers a batch of 2 to 4 matches the observed best sizes. Cost is check runs; tokens only appear when the worker must redo. Holds for check lengths of minutes and an hour more than for seconds (fixed start-up time of a run dominates in seconds, my reasoning).
- Needs to know about a project: its culprit rate (share of changes that fail the check) and flake rate, both measured from history.
- Status: quoted.

### P3. Fallahzadeh, Bavand, Rigby, "Accelerating Continuous Integration with Parallel Batch Testing", ESEC/FSE 2023. Read from: https://arxiv.org/pdf/2308.13129.pdf. Saved: `P:beheshtian2021/paper.txt` (folder name predates my finding the authors; it is this paper). Read: abstract, sections 1, 2, 4.1-4.4 results, 6 (validity), about 70%.
- Problem: earlier batching work counted test executions and ignored waiting time and running tests in parallel on many machines.
- Mechanism: TestAll (one change at a time) as baseline; ConstantBatching (batch of 2 or 4); BatchAll (the batch is every change waiting in the queue); TestCaseBatching (new changes may join a batch before the full run). Failing batch: only the failed tests are re-run, no re-bisection of passing tests.
- Result (abstract): "The results reveal a non-linear impact of test parallelization on feedback time, as each test delay compounds across the entire test queue." (l.36-37). "ConstantBatching, with a batch size of 4, utilizes up to 72% fewer machines to maintain the actual average feedback time" (l.38-40); "BatchAll maintains the actual average feedback time with up to 91% fewer machines" (l.41-43); "TestCaseBatching ... up to 81% fewer machines" (l.44-45).
- Result (the queue has a knee): "TestAll needs 7 machines to achieve the actual average feedback time of 8.33 hours for Ericsson. For Chrome, we see TestAll needs 217 available machines to achieve the 36.48 minutes" (l.643-646). "in Ericsson, when we increase from 6 to 7 machines there is a speedup of 2.65 times ... but the increase from 7 to 8 machines only adds 1.5 times" (l.649-651).
- Result (constant batches can lose): "Batch4 achieves the same average feedback time using 8 machines, resulting in a negative reduction (-14.29%) in machine usage compared to the baseline" at Ericsson (l.767-770); for Chrome Batch2 saves 47.93% and Batch4 71.89% of machines (l.771-774). "BatchAll ... 5 machines ... 28.57% reduction" at Ericsson, "20 machines ... 90.78%" at Chrome (l.840-848). Constant batching "plateau with a relatively high feedback time and TestAll outperforms them" when machines far exceed the baseline (l.761-762).
- Reported in this paper from others (not read by me): Najafi et al. 42% (as P2), Beheshtian et al. "BatchStop4 ... reduce build test executions on average by 50%" and "when fewer than 40% of builds fail, batching and bisection effectively reduce overall feedback time" (l.81-82, 88-89), Bavand et al. "about 47%" (l.90-92). Status of those: summary.
- Measured gain: up to 91% fewer machines for the same average feedback time. Baseline: TestAll at the project's actual machine count. Workload: Ericsson, over 11,000 changes in six weeks (l.178); Chrome, 276 million test results for 9,524 changes in January 2021, failure rate of builds "about 8.5%" (l.198-201). Scale: 5 to 375 machines.
- Assumes: failure rate low ("The build failure rate in Chrome dataset is 8.5%, which is well below the 40% threshold", l.1079-1081); "all changes can be batched and none lead to merge conflict" (l.1100-1101); tests independent ("we only batch tests that Ericsson guarantees are independent", l.1090-1092); flaky failures handled as in Chrome; compile times ignored.
- With model sessions (reasoned): the "knee" result is the finite-source queue's behaviour seen in measurement: waiting grows sharply near the slot count and the first machine count past the knee gives most of the gain. BatchAll is the better fit for 3 to 16 workers because the batch is whatever is waiting, so it needs no failure-rate parameter and grows when the queue is long. With a 10-minute check it needs changes independent (they are not when sessions edit the same files) and a way to re-run only the failed tests; conflicts between model-written changes may be common, which breaks the "none lead to merge conflict" assumption. Check length: the gain comes from waiting time, so it matters at minutes and an hour, not at seconds.
- Needs to know about a project: the share of changes failing, whether tests are independent and can be re-run singly, how many check slots exist.
- Status: quoted.

### P4. Fallahzadeh, Rigby, Adams, "Contrasting test selection, prioritization, and batch testing at scale", Empirical Software Engineering 30:33, 2025. Read from: https://link.springer.com/content/pdf/10.1007/s10664-024-10589-8.pdf. Saved: `P:contrast-tsp-batch/paper.txt`. Read: abstract, introduction, setup grep and range (abstract and headline claims only of the results).
- Problem: compare three families (selection, prioritisation, batching) on the same data.
- Mechanism: BatchAll against test-selection and prioritisation algorithms, replayed on Chrome pre- and post-commit results, a Google project and JMRI Travis.
- Result: "test selection can reduce actual median feedback time by up to 96% with the same number of machines but may miss up to 55% of failures. In contrast, batching achieves up to a 99% reduction in feedback time without missing any failures." (l.19-22). "Test selection cuts machine usage by up to 66%, while batching achieves up to an 88% reduction." (l.22-23). "The studied test prioritization algorithms significantly underperform compared to the test selection and batching algorithms." (l.26-27).
- Measured gain: up to 99% less median feedback time, baseline the actual feedback time on the same machine count; 285 million test results (title); no missed failure (the check is still complete).
- Assumes: flaky failures treated as non-blocking (l.141); "does not miss any failures" because every test of every change still runs; in the text batching performs best "except in scenarios with few concurrent builds" (l.161, my reading of the cut line).
- With model sessions (reasoned): shows the order of gains: the large gains come from the queue (waiting time), larger than from running fewer tests, and batching keeps full coverage. With 3 to 16 workers there are few concurrent builds, so the gain is smaller than at Chrome's scale; the paper itself says batching helps less with few concurrent builds.
- Needs to know about a project: same as P3.
- Status: quoted (abstract and headline lines; the body tables were not all read).

### P5. OpenStack Zuul project, "Project Gating" (documentation page), https://zuul-ci.org/docs/zuul/latest/gating.html, fetched 2026-11-19. Saved: `P:zuul-gating/paper.txt` (page text from `curl`, tags stripped; no figures). Read: the whole section "Testing in parallel" and "Pipeline Window".
- Problem: test every change "exactly as it is going to be merged" without testing one at a time.
- Mechanism: "it assumes that all jobs will succeed and tests them in parallel accordingly" with each change tested on top of those ahead; "if one fails, then changes that were expecting it to succeed are re-tested without the failed change" (l.919-923). Window for resource control: "starts with the window set to a certain value (twenty changes by default). Each time a change successfully merges, the window is increased by one. Each time a change fails, the window is halved." (l.970-973), borrowed from TCP flow control.
- Result: "In the best case, as many changes as execution contexts are available may be tested in parallel and merged at once. In the worst case, changes are tested one at a time" (l.923-926). "Ideally if builds frequently succeed, the window should be large in order to maximize throughput, and if they frequently fail, it should be small in order to minimize waste." (l.966-968).
- Measured gain: none stated (documentation, no numbers).
- Assumes: independent builds per change, a failure leaves later builds lost ("build results are discarded", l.962-964).
- With model sessions (reasoned): the window rule is a parameter-free way to track the failure rate (additive increase, halve on failure) and needs no knowledge of the failure rate beforehand, which suits a project with an unknown rate. Each lost build costs a check-run of minutes; the token cost occurs only if the worker must redo. At 16 workers, a window of at most 16 is the natural cap.
- Needs to know about a project: nothing beforehand (it learns from outcomes); the check must be deterministic.
- Status: quoted from documentation (primary, but unmeasured).

### P6. GitHub, "Managing a merge queue" (documentation page), https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue, fetched 2026-11-19. Saved: `P:github-mq/paper.txt`. Read: the settings and behaviour sections.
- Problem and mechanism: each pull request is grouped "with the latest version of the base_branch as well as changes from pull requests ahead of it in the queue" and its checks run on that group (l.194); on failure the request is removed and the ones behind it are built without it (l.204-212).
- Settings (l.179-191): "Build concurrency: The maximum number of merge_group webhooks to dispatch (between 1 and 100)"; "Merge limits: Select the minimum and maximum number of pull requests to merge into the base branch at the same time (between 1 and 100)"; "Merge limits do not combine merge_group builds." So by default the queue tests a change on top of those ahead (testing ahead) and merges in groups; batching of builds into one run is not done by this setting. "Jumping to the top of a merge queue will cause a full rebuild of all in-progress pull requests" (l.221).
- Measured gain: none stated.
- Assumes: required checks reported on `merge_group` events; independent failures; a setting for how long to wait for the check ("Status check timeout").
- With model sessions (reasoned): the queue gives an order and a rebuild rule but not a check-sharing batch; Uber's 2025 paper (P7, l.196-203) says GitHub and GitLab queues "only speculate the success paths" and retest when an earlier change fails, "especially when the failure rate is high". Marked reasoned.
- Needs to know about a project: nothing; concurrency is a setting.
- Status: quoted from documentation. The Rust project's bors was not read beyond a one-page Bors-NG essay (see Could not open).

### P7. Juloori, Lin, Williams, Shin, Mahajan, "CI at Scale: Lean, Green, and Fast", ICSE SEIP 2025. Read from: https://arxiv.org/pdf/2501.03440. Saved: `P:uber-ci-at-scale/paper.txt`. Read: abstract, introduction, model assumptions, evaluation and limitations (about half).
- Problem: SubmitQueue aborts many builds early and makes small changes wait behind large ones.
- Mechanism: predict build time, prioritise speculative builds by it, and run only builds above a "speculation threshold" of success probability.
- Result: "CI resource usage by approximately 53%, CPU usage by 44%, and P95 waiting times by 37%" (l.28-30). Before: "an estimated 40-65% of builds being affected" by premature abort (l.93-95). Builds per change: Go "from a pre-rollout average of 3.39 to a post-rollout average of 1.85", iOS "from 4.93 to 2.57", Android "from 5.43 to 1.96" (l.1013-1019). CPU hours: Go "from a pre-rollout average of 1,485 to a post-rollout average of 821 hours", iOS 472 to 307, Android 729 to 348 (l.1027-1035).
- Note: the builds-to-changes ratio before the rollout was 3 to 6 (l.1000): speculation alone cost several builds per change.
- Measured gain: about half the CI resources at the same landing rate, baseline the earlier SubmitQueue; 21 weeks (May 13 to Sept 30, 2024), three monorepos, thousands of changes a day (l.979-990).
- Assumes: a trained build-time and success model (retrained weekly on three months of builds, l.892-897); a static threshold "may not align with real-time workload" (l.1131-1135).
- With model sessions (reasoned): in speculation, builds per change of 3 to 6 is the cost of testing ahead without a threshold; a threshold on success odds is the lever. A model session's changes are few, so a shallow speculation window of 2 to 4 changes bounds the cost.
- Needs to know about a project: history of builds for the success and time models; a build graph.
- Status: quoted.

### P8. Memon, Gao, Nguyen, Dhanda, Nickell, Siemborski, Micco, "Taming Google-Scale Continuous Testing", ICSE-SEIP 2017. Read from: https://huang.isis.vanderbilt.edu/cs8395-f23/paper/google-testing-icse-seip-17.pdf (university course copy). Saved: `P:google-ct-2017/paper.txt`. Read: abstract, sections 1-3 and findings list, by range (about 40%).
- Problem: Google cannot run every affected test for every change.
- Mechanism: TAP bundles consecutive commits into a "milestone" and runs each affected test once, at its latest affecting change: "TAPs milestone strategy is to bundle a number of consecutive code commits together, and run (or cut) a milestone as frequently as possible given the available compute resources" (l.55-58); a milestone is "typically cut every 45 minutes during peak" (l.59-60). Tests are "executed only at their latest affecting CL" (l.336-338). On a break, any change between the last pass and the first failure may be the culprit (l.615-618).
- Result: "In an average day, TAP integrates and tests ... more than 13K code projects, requiring 800K builds and 150 Million test runs" (l.38-41). Testing each change had resources "growing quadratically with two multiplicative linear factors: (1) the code submission rate ... and (2) the size of the test pool" (l.46-50). "the ratio of PASSED vs. FAILED test targets per code change is 99:1" (l.180). "of the 5.5 Million affected tests ... only 63K ever failed" (l.75-76). Cost of batching: "unacceptably large delays of up to 9 hours" in the infrastructure (l.68-69).
- Measured gain: not a gain figure; it is the justification for batching at scale: the test count grows with the product of change rate and suite size, and a milestone cuts one factor.
- Assumes: low failure rate per change (99:1); the culprit inside a milestone is found afterwards.
- With model sessions (reasoned): the result states why waiting grows when both the number of workers and the size of the check grow (product), which matches the finite-source picture; a 45-minute milestone is far beyond the minutes a model session can wait, so only the principle (one run for several changes, run as often as the machines allow) carries over, not the interval.
- Needs to know about a project: which tests each change affects (dependency map).
- Status: quoted.
