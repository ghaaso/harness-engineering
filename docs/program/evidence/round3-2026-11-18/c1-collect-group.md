## Gate summary
- P1 Dorfman 1943: expected tests E(T) = N/n + n(N/n)p', relative cost C = 1/n + 1 - (1-p)^n; at p = 1 % best n = 11, 20 % of the tests; at p = 10 % best n = 4, 59 %; at p = 30 % n = 3, 99 % (txt 121, 128-130, 157-187). quoted.
- P1 break-even: group testing pays only if the rate is small and "it be easier or more economical to obtain an observation on a group" (txt 196-206). quoted.
- P2 Aldridge/Johnson/Scarlett survey: counting bound, any algorithm needs T >= log2 C(n,k); P(suc) <= 2^T / C(n,k) (txt 819, 841-849). quoted.
- P2 Hwang's generalized binary splitting: k log2(n/k) + O(k) adaptive tests, rate 1 (capacity of adaptive testing) in the sparse regime (txt 1103, 1122-1124). quoted.
- P2 Dorfman optimal pool in the survey: n/k pools of size n/k under known k (txt 1033-1035); i.i.d. prior: m = 3 beats individual testing for p < 1 - 3^(-1/3) = 0.307 (txt 7608-7611). quoted.
- P2 individual testing is optimal for adaptive i.i.d. testing at p >= (3 - sqrt5)/2 = 0.382 (txt 7481-7483); zero-error adaptive: p >= 0.369 (txt 1147-1148). quoted.
- P2 two stages are enough for rate 1 in the sparse regime (txt 6349-6351); in the linear regime conservative two-stage reaches ln 2 = 0.693 as p goes to 0, "rate" meaning information per test (txt 7475-7476, 7694). quoted.
- P3 group-commit preprint arXiv 2606.18187 (June 2026, small company, not peer reviewed): greedy "flush the instant the device is free" is within about 0.1 % of the best tuned timer; timer is vacuous above lambda* = 2/F0 (txt 8-23, 66-91). quoted, one measured case.
- P3 same, PostgreSQL pgbench on EBS: 32 clients commit_delay = 0 within 10 % of best tuned, 2 clients 17 % gain (txt 118-121). quoted.
- P4 PostgreSQL documentation, commit_delay: the delay helps "if system load is high enough that additional transactions become ready to commit within the given interval"; default 0 (documentation text, pgdocs txt 426, 427). quoted (documentation page, not a paper).
- Not read: Helland and others 1987; DeWitt and others 1984 (see "Could not open").

## Papers

### P1. Robert Dorfman, "The Detection of Defective Members of Large Populations", Annals of Mathematical Statistics 14(4), 436-440, 1943. Read from: https://webpages.tuni.fi/uta_statistics/liski-arkisto/mtt-perusteet10/mttp-kurssi10/Materiaalia/Dorfman-Ann1943.pdf (a university course copy of the JSTOR scan; the publisher's Project Euclid page is behind a bot check, see below). Saved: R:papers/check/dorfman/paper.txt. Read: all (5 pages, the paper is pages 1-4; the rest of the file is a different note).
- Problem. Find every defective item in a large population with the fewest tests, when one test can be run on a pool.
- Mechanism. Pool n items; test the pool; if negative all n are cleared; if positive test the n individually. Group size n is chosen from the known rate p.
- Result: "p' = 1 - (1 - p)^n = the probability of obtaining by random selection a group of n with at least one infected member." (txt 104-109, exponent lost in the scan [restored]) "E(T) = N/n + n(N/n)p'" (txt 121) "or the number of groups plus the number of individuals in groups which require retesting." (txt 123-124) The relative cost is "C = T/N = 1/n + p'" (txt 128), that is 1/n + 1 - (1-p)^n. "The optimum group size for a population with a known prevalence rate is the integral value of n which has the lowest corresponding value on the relative cost curve" (txt 147-149).
- Table I (txt 154-187), relative cost as a percentage of one test per item: p 1 % -> n 11, 20; 2 % -> 8, 27; 3 % -> 6, 33; 5 % -> 5, 43; 10 % -> 4, 59; 15 % -> 3, 72; 20 % -> 3, 82; 25 % -> 3, 91; 30 % -> 3, 99.
- The two conditions of use: "1. That the prevalence rate be sufficiently small to make worthwhile economies possible; and 2. That it be easier or more economical to obtain an observation on a group than on the individuals of the group separately." (txt 196-206, OCR spacing restored)
- Footnote: the variance of T is small relative to its mean as N grows, "The coefficient of variation of T becomes small rapidly as N increases." (txt 135-137). The paper ignores test error: "no attention will be paid to the possibility of technical failure or operator's error" (txt 56-57).
- Measured gain: Table I above, computed by formula, not a measurement on a workload: 80 % fewer tests at p = 1 %, 41 % fewer at p = 10 %, 1 % fewer at p = 30 % (txt 157, 177, 187). Dorfman's own worked case was syphilis screening (rate 0.0185 in the first million inductees, txt 199-200).
- Approximation, not in the paper (reasoned, from the formula): for small p the best n is about 1/sqrt(p) and the best cost about 2 sqrt(p). Checks against Table I: p = 1 % gives n = 10, cost 20 %, the table says 11 and 20 %.
- Assumes: each item defective independently with the same known probability p; a group test is exactly as informative as one test of an item (one test costs the same whatever the pool size; a positive pool means at least one defective); no test error; tests run in two rounds.
- With model sessions: the cost model is counted in "tests" of equal cost. Here the pooled run (a suite run over k merged changes) costs about the same as a run of one change only if the suite time does not grow with the batch; if it grows, the first condition (condition 2 above) fails in part. A failure rate per change is not constant or independent in our work (changes touching the same files fail together; a rerun of a model session is not the same run). The condition "p small" is the one to measure. Check length: the formula has no time scale, so seconds, minutes and an hour of check give the same batch size for the same p; what changes is how long a worker waits for the group (see P3). With 3 workers there are rarely k = 4 ready changes at once; with 16 there are. Marked reasoned.
- Needs to know about a project before use: the probability that one change fails the check (p), and whether failures are independent across changes. Both are measurable from the check's own log.
- Status: quoted.

### P2. Matthew Aldridge, Oliver Johnson, Jonathan Scarlett, "Group testing: an information theory perspective", Foundations and Trends in Communications and Information Theory 2019 (arXiv 1902.06002). Read from: https://arxiv.org/pdf/1902.06002 (10,775 text lines). Saved: R:papers/check/aldridge/paper.txt. Read: Sections 1.4, 1.5, 1.6 (zero-error part), 1.8 (Covid use), 5.2 (limited stages) and 5.5 (linear regime) in full; the nonadaptive chapters 2 to 4 only by search.
- Problem. The standard survey of group testing: minimum number of tests to find k defectives among n items, adaptive and nonadaptive.
- Mechanism. Counting argument gives a lower bound; binary splitting (halve a positive pool) and Hwang's version of it reach that bound for few defectives; Dorfman's two-stage scheme is best for moderate rates.
- Result (counting bound): "that we require T >= log2 C(n,k): There are only 2^T combinations of test results, but there are C(n,k) possible defective sets that each must give a different set of results." (txt 819-823) "Theorem 1.1 (Counting bound). Any algorithm (adaptive or nonadaptive) for recovering the defective set with T tests has success probability satisfying P(suc) <= 2^T / C(n,k)." (txt 841-846 [restored])
- Result (Dorfman, known k): "the optimal partition (assuming that k is known) comprises sqrt(nk) pools, each of size sqrt(n/k). Dorfman's strategy therefore requires at most T = sqrt(nk) + k <= 2 sqrt(nk) tests" (txt 1033-1037 [restored]).
- Result (binary splitting): "binary splitting finds a defective item in at most log2 |A| adaptive tests, or confirms there are no defective items in a single test." (txt 1081-1083) "Theorem 1.3. Using Algorithm 1.2, we can find the defective set with certainty using k log2(n/k) + O(k) adaptive tests. Thus, the capacity of adaptive group testing in the sparse regime k = Theta(n^beta) is C0 = C = 1 for all beta in [0,1)." (txt 1122-1124) "This theorem follows directly from the work of Hwang [158]" (txt 1126). The idea of Hwang's step: "unless there are very few defectives remaining, the first tests in each round of the repeated binary splitting algorithm are overwhelmingly likely to be positive, and are therefore very uninformative." (txt 1105-1108) Algorithm 1.2 is: split into k subsets of size n/k and run binary splitting in each (txt 1110-1111). Allemann reduced the O(k) term to "0.255k" (txt 1139).
- Result (when it stops paying): "when k is a large enough fraction of n, it turns out that adaptive group testing offers no performance advantage over the simple strategy of individually testing every item once." (txt 1144-1146) "no algorithm can outperform individual testing if k >= 0.369n" (zero-error, txt 1148) and, small-error i.i.d.: "Individual testing is optimal for p >= (3 - sqrt5)/2 = 0.382" (txt 7481-7483 [restored]).
- Result (Dorfman under an i.i.d. rate): "ET = (n/m)(1 + (1 - (1-p)^m) m) ... each pool requires 1 test in the first round, each pool is positive with probability 1 - (1-p)^m, and for each positive outcome there are another m individual tests in the second round. With m = 3, this improves on individual testing for p < 1 - 3^(-1/3) = 0.307. (It turns out that m = 2 is never optimal here, as it is always beaten by either m = 3 or individual testing.)" (txt 7600-7613 [restored]). This matches Dorfman's Table I (3 at 20 to 30 %).
- Result (stages): "Theorem 5.5 ... the capacity of two-stage adaptive group testing ... is C2 = 1." (txt 6349-6352) The binary splitting algorithm "uses O(log n) stages" (txt 6254). In the linear regime Dorfman's scheme "becomes competitive again" (txt 7581) and Dorfman's algorithm was "the most widely used method in practice" in Covid-19 tests, "preferred for several reasons including ... the requirement of only two stages of testing (which is important since PCR testing is quite slow)" (txt 1385-1388); "quite effective in the 'uncommon but not super-rare' region where the prevalence is roughly between 2% and 25%" (txt 1389-1390).
- Result (nonadaptive): in the linear regime "individual testing is optimal for all p in (0,1)" for nonadaptive testing (txt 7471).
- Measured gain: this is a theory survey; the gain is a bound, not a measurement. Quoted numbers: Dorfman 2 to 25 % region above; two-stage rate up to ln 2 = 0.693 as p goes to 0 (txt 7475-7476, 7694). The survey reports a field use (Cambridge University students, pools of about 8, txt 1391-1392), without a measured saving in this paper.
- Assumes: items defective independently (i.i.d. prior) or exactly k defectives (combinatorial prior); a test answers "at least one defective in the pool" without error (noisy testing is in Chapter 3); k or p known (Sobel and Groll handle unknown k, txt 1040-1043).
- With model sessions: the count of "tests" is a count of rounds that each cost the same. Binary splitting needs O(log n) sequential rounds (txt 6254); a round here is a suite run of minutes (about ten here) so the number of rounds matters as much as their number: log2 of 16 changes is 4 sequential runs of ten minutes each, 40 minutes, against 2 rounds for Dorfman (txt 1387). The survey itself says the two-stage form is preferred when each test is slow. Marked reasoned (the arithmetic is mine, the preference is quoted). A failing change is not an independent "defective" if it fails because of another change in the batch (an interaction): the model has no term for that.
- Needs to know about a project before use: the rate p of a failing change; the number of changes ready at once (k); the time per round.
- Status: quoted (read in full for the parts above; chapters on noise and nonadaptive designs not read).

### P3. Madhulatha Mandarapu, Sandeep Kunkunuru, "Group Commit Self-Clocks: Why Tuning Is Unnecessary Above a Device-Set Load Threshold", arXiv 2606.18187, June 2026 (VaidhyaMegha Private Limited, India; a preprint, not peer reviewed). Read from: https://arxiv.org/pdf/2606.18187. Saved: R:papers/check/gc2606/paper.txt. Read: all (5 pages).
- Problem. Group commit in a database log: batch the commits of many transactions into one durable flush. When is a timer or batch-size knob worth tuning?
- Mechanism. A flush of K records costs F(K) = F0 + K*delta (fixed barrier plus per record). Open loop (Poisson arrivals) the best timer is T* = sqrt(2 F0 / lambda). Closed loop (N clients, think time Z, each blocked until its commit flushes) the "greedy" rule, flush the moment the device is free, self-clocks to a batch size that fits the closed queueing network.
- Result: "Group commit amortizes the fixed cost of a durable log flush across many committing transactions" (txt 8). "The per-transaction overhead of a periodic timer is F0/(lambda T) + T/2, minimized at the EOQ square-root rule T* = sqrt(2 F0 / lambda)" (txt 53-54, from the page text [restored]). "A flush of a batch of K records costs F(K) = F0 + K delta" (txt 80). "By Little's law X = N/(Z + L) and, with the device back-to-back at load, X = K/F and L ~ F; eliminating gives the fixed point K = N F(K)/(Z + F(K))" (txt 83-85 [restored]). "T* = sqrt(2 F0 / lambda) < F0 iff lambda > lambda* := 2/F0. Above lambda* the prescribed wait T* is shorter than a single flush, so a timer fires while the device is still busy and the batch flushes at device-free time regardless of T*" (txt 91-93 [restored]).
- Measured gain (a simulator plus two measured devices, one preprint): "Across every closed-loop load, greedy is within a median 0.1% of the best oracle-tuned timer." (txt 111-112) "Greedy's batch size and throughput match (1) across N in {2, ..., 256} (batch error 10%, throughput error 7%)" (txt 108-110). "EBS gp3 has F0 = 0.90 ms (p99 2.5 ms), so lambda* ~ 2200/s ... Instance-store NVMe has F0 = 0.036 ms (25x faster), so lambda* ~ 55000/s" (txt 126-130 [restored]). On PostgreSQL pgbench with WAL on EBS: "at 32 clients (6.6k tps, above lambda*) commit_delay=0 is within 10% of the best tuned value with no reliable or monotonic signal; at 2 clients (below lambda*) the benefit is slightly larger (17%)" (txt 135-138). Open loop with rate shifts: ski-rental policy "lands at 1.34x the offline optimum versus the fixed timer's 1.44x" (txt 121-122).
- The authors' own limits: "The closed-loop competitive bound is conjectured, not proven" (txt 168); "pgbench has non-commit bottlenecks and spot/EBS latency is variable, so the PostgreSQL arm is noisy" (txt 168-170). "We claim no new logger" (txt 61).
- Related work given in the preprint (not read by me): group commit originates with DeWitt and others 1984 and Gawlick and Kinkade 1985 (txt 31-32, 151); flush pipelining is Johnson and others 2010 (Aether); the bulk-service optimum is Deb and Serfozo 1973 (txt 38, 155).
- Assumes: batching costs F0 once per batch and a small delta per record; N clients blocked on their own commit (a closed loop with finite sources); one flush device.
- With model sessions: the closed-loop structure is the same as ours: N workers think for Z (work alone), then block at one serial server until their change passes. Here the preprint's batch K = N F(K)/(Z + F(K)) says that with a long service time F relative to Z the queue holds about N * F/(Z+F) workers and the batch fills by itself; "flush the instant the server is free, take whatever has queued" needs no timer and no knowledge of p. For a check of ten minutes against work of tens of minutes this predicts a standing queue at 16 workers and rarely a queue at 3. The cost per record delta is not small for a suite run (running 4 changes' tests in one suite costs more than one) and a failed batch must be re-run, neither of which the model has; so the "greedy = best" result is shown for a log flush, not for a suite. Marked reasoned. The 0.1 % figure is a log, one simulator and two devices; it is not evidence for suites.
- Needs to know about a project before use: F0 (fixed cost of one suite run), delta (extra cost per added change), Z (work time outside the check), N. The preprint's lambda* = 2/F0 is a ratio-like threshold: timers matter only below it.
- Status: quoted (read in full). Preprint, not peer reviewed; one measured case.

### P4. PostgreSQL documentation, "Write Ahead Log" settings, parameters commit_delay and commit_siblings (https://www.postgresql.org/docs/current/runtime-config-wal.html, fetched 2026-11-19). Saved: R:papers/check/pgdocs/paper.txt (HTML with tags stripped). Read: the two parameters.
- Problem. How a production engine releases a group commit.
- Mechanism. The first backend ready to flush waits commit_delay; later backends wait only until that leader's flush completes; the delay applies only if at least commit_siblings other transactions are open.
- Result: "Setting commit_delay adds a time delay before a WAL flush is initiated. This can improve group commit throughput by allowing a larger number of transactions to commit via a single WAL flush, if system load is high enough that additional transactions become ready to commit within the given interval. However, it also increases latency by up to the commit_delay for each WAL flush." (pgdocs txt 426) "The default commit_delay is zero (no delay)." (txt 426) "In PostgreSQL releases prior to 9.3, commit_delay behaved differently and was much less effective ... Beginning in PostgreSQL 9.3, the first process that becomes ready to flush waits for the configured interval, while subsequent processes wait only until the leader completes the flush operation." (txt 427) "Minimum number of concurrent open transactions to require before performing the commit_delay delay ... The default is five transactions." (txt 431)
- Measured gain: none given in the documentation.
- Assumes: transactions arrive while the flush waits; the default is no wait.
- With model sessions: the same picture as P3: the production default is "do not wait, take what is queued"; waiting is an option only when others are likely to join within the interval. For us: do not hold a ready change back to fill a batch unless the arrival rate of ready changes in that wait is high. Marked reasoned.
- Needs to know about a project before use: the rate at which ready changes arrive during one check.
- Status: quoted (documentation page; not a paper; one engine).

## Notes for the analyst
- Group testing and group commit are two forms of one idea, with one difference that matters: Dorfman and Hwang minimise the count of tests; group commit (P3, P4) minimises the cost per record and the waiting time. Our case has both costs: a run of the suite costs tokens and minutes, and a worker waits.
- The Dorfman formula in ratios: with p the failure rate of one change and k the batch, runs per change = 1/k + 1 - (1-p)^k; break-even k = 2 at p = 0.293, k = 3 at p = 0.307 (the survey, txt 7610); above p of about 0.38 (adaptive, i.i.d.) individual testing is best (txt 7481). The best k for small p is about 1/sqrt(p) (reasoned; my approximation, checked on Table I at p = 1 % and 10 %). Dorfman retests a failed batch one change at a time; binary splitting (P2) retests by halves and needs fewer runs when p is very small but takes more sequential rounds (survey: O(log n) stages, txt 6254); Aldridge's text gives a reason to prefer two rounds when each test is slow (txt 1387).
- No paper read here gives a measured gain on software suites; for that, see sub-topic 3 (mergeq). The measured gains in this file are one log-flush result (P3, within 0.1 %; one device, simulator) and formula values (P1).
