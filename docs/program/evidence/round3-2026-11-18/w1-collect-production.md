## 1. Figma: how its multiplayer system resolves simultaneous edits
- **Citation:** Figma Blog, "How Figma's multiplayer technology works", 16 Oct 2019. URL fetched: https://www.figma.com/blog/how-figmas-multiplayer-technology-works/ . Status `quoted` (company blog, read as text). `P:figma-multiplayer/paper.txt`.
- **Problem.** Many people edit one design file at once; all copies must converge and edits must feel instant.
- **Mechanism.** A central server keeps the latest value of each (object, property) pair; the server's arrival order decides, last writer wins per property. Clients apply their own change at once and ignore incoming server changes that conflict with an unacknowledged local change.
- **Measured gain.** None given: the post reports no figures (checked: no throughput, latency or conflict-rate number). Self-reported design account only.
- **Quotes.**
  - Grain: `figma-multiplayer/paper.txt:130` "two clients changing unrelated properties on the same object won't conflict, and two clients changing the same property on unrelated objects also won't conflict. A conflict happens when two clients change the same property on the same object, in which case the document will just end up with the last value that was sent to the server."
  - Order from the centre: `paper.txt:118` "Since Figma is centralized (our server is the central authority), we can simplify our system"; `paper.txt:130` "we don't need a timestamp because the server can define the order of events".
  - Loss accepted: `paper.txt:132` "simultaneous editing of the same text value doesn't work in Figma. If the text value is B and someone changes it to AB at the same time as someone else changes it to BC, the end result will be either AB or BC but never ABC."
  - Rejected OT: `paper.txt:86` "we didn't want to use operational transforms ... OTs were unnecessarily complex for our problem space."
  - Tree cycles: `paper.txt:146` "Figma's multiplayer servers reject parent property updates that would cause a cycle"; the client may briefly hold a cycle (`paper.txt:148`, objects temporarily removed from the tree until the server rejects the change).
  - Per-document process: `paper.txt:93` "Our servers currently spin up a separate process for each multiplayer document".
- **Assumes.** One central server per document (a sequencer); data as a map of independent properties; losing one of two simultaneous values of the same property is acceptable; changes are small and instant.
- **For model-session writers (`reasoned`).** The grain idea fits: claim (file, symbol, property) smaller than the file, conflict only on the same cell. It does not fit where a unit is a multi-line edit of text: Figma accepts losing one of two edits of the same value, and a session's edit that is silently dropped costs minutes of tokens and may break what other edits read. The central sequencer holds (the harness is the server). No dependency between properties is tracked: Figma has no write skew check, so this is the "lost update" remedy only, and it is last-writer-wins, not first-writer-wins.
- **Frame.** Bears on means (1) smaller units and (2) order fixed by a sequencer; and shows a design that gives up the lost-update guarantee on purpose for the same cell. The frame's table has no row for "a structural invariant across items" (the tree must stay acyclic): Figma enforces it at the server, which is a write-skew check done per write.

## 2. Google Docs: operational transformation with a revision log
- **Citation:** Google Drive Blog posts of 21 to 23 Sep 2010, "What's different about the new Google Docs: Working together, even apart" and the two that follow (operational transformation; the collaboration protocol), by Google engineers. URL fetched: https://idl.uw.edu/future-scholarly-communication/files/2010-GoogleDocs-OT.pdf (a University of Washington copy of the three posts, `%PDF-` confirmed); the "conflict resolution" post page https://drive.googleblog.com/2010/09/whats-different-about-new-google-docs_22.html was also saved (`P:google-docs/conflict.txt`, it repeats the OT text). Status `quoted`. `P:google-docs/ot.txt`.
- **Problem.** Several editors change one document at nearly the same time over a slow link; all sessions must converge on the same correct text.
- **Mechanism.** Every edit is one of three change types appended to a server revision log; the server transforms a late change against every change committed since the editor last synced, so it lands as the next revision; a client sends one pending change at a time and transforms what it receives against its own pending change.
- **Measured gain.** None given in the posts (no throughput or conflict figure). Self-reported design account.
- **Quotes.**
  - Old design and its failure: `ot.txt:30-37` the old Docs compared document versions on the server and merged "as best it can"; `ot.txt:46-49` "if you just compare versions, you can't make sure that changes are merged in the way that an editor would expect".
  - Locks rejected: `ot.txt:52-55` "locking paragraphs isn't a great solution: you're sidestepping the technical challenges by hampering the collaborative editing experience"; `ot.txt:56-59` two editors can begin together, "one of the editors will find out that he didn't actually acquire the paragraph lock and any changes that he made ... will need to be merged ... or discarded".
  - Log: `ot.txt:106-109` "they are appending their change to the end of the revision log. To display a document, we replay the revision log from the beginning."
  - Guarantee: `ot.txt:128-130` "If OT is implemented correctly, it guarantees that once all editors have received all changes, everyone will be looking at the same version of the document."
  - One in flight: `ot.txt:235-237` "we never send more than one pending change at a time".
  - Server transform: `ot.txt:257-259` "The server received John's pending change, a change that John believes should be Revision 2. But the server has already committed a Revision 2 ... The server will use OT to transform John's change so that it can be stored as Revision 3."
  - Pairs that need no transform: `ot.txt:144-147` a style change against a different style type "there is no conflict".
- **Assumes.** A centralised server that orders changes; a small closed set of change types with a transform function for every pair; edits that are small and positional; "if OT is implemented correctly" (the posts' own hedge).
- **For model-session writers (`reasoned`).** An edit by a session is an arbitrary text patch, not one of three types, so the transform table cannot be written. The library already holds that OT algorithms fail to converge for three or more sites (`r57-0304`); Google's design avoids that by routing everything through one server (a central order), which a harness can imitate. The revision log "append, then replay" matches an append-only record of edits per file. The key content for the lane: where a change was made against an older revision, the server rebases it (as a transform), and where that is impossible a person has to resolve it.
- **Frame.** Bears on means (2) order fixed by a sequencer and (4) merge by structure (here, by operation, not by line). Shows the check of "which revision did this change read" (the revision number it is based on) is the lost-update remedy; it also shows that locks were considered and rejected because of the false-acquire race.

## 3. Google: one repository, one trunk (Piper), 2016
- **Citation:** Potvin and Levenberg, "Why Google Stores Billions of Lines of Code in a Single Repository", Communications of the ACM 59(7), July 2016. First attempt: ACM page (https://dl.acm.org/doi/pdf/10.1145/2854146 and the cacm.acm.org fulltext): 403 (blocked). Second attempt: the publisher's own fulltext page as kept by the Internet Archive, https://web.archive.org/web/2020/https://cacm.acm.org/magazines/2016/7/204032-why-google-stores-billions-of-lines-of-code-in-a-single-repository/fulltext , read as text. (A University of Sao Paulo course copy was behind a login page and was not used.) Status `quoted` (publisher text via an archive copy; the figures are Google's, self-reported). `P:google-piper-cacm/paper.txt`.
- **Problem.** One company, tens of thousands of developers, one codebase, no existing version-control system that scales to it.
- **Mechanism.** All work lands on one trunk in a single serial order; developers edit in per-person cloud workspaces; pre-submit tests and analysis gate each change, a post-commit rebuild of affected dependencies runs, and a bad change that breaks widely is rolled back automatically.
- **Measured gain.** No before-and-after comparison; the paper gives scale only. Self-reported.
- **Quotes.**
  - Scale: `google-piper-cacm/paper.txt:81` "approximately one billion files and has a history of approximately 35 million commits ... 86TB of data, including approximately two billion lines of code in nine million unique source files" (January 2015).
  - Rate: `paper.txt:83` "more than 25,000 Google software developers ... they commit 16,000 changes to the codebase, and another 24,000 changes are committed by automated systems"; about 800,000 read queries per second at peak.
  - Order: `paper.txt:101` "Changes are made to the repository in a single, serial ordering." and "Immediately after any commit, the new code is visible to, and usable by, all other developers."
  - Against branches: `paper.txt:102` trunk-based development "avoids the painful merges that often occur when it is time to reconcile long-lived branches"; "Use of long-lived branches with parallel development on the branch and mainline is exceedingly rare."
  - The safety net: `paper.txt:105` "an automated testing infrastructure that initiates a rebuild of all affected dependencies on almost every change committed ... If a change creates widespread build breakage, a system is in place to automatically undo the change." and "presubmit" analyses run before a change is added.
- **Assumes.** A central serial order; changes small enough to land at 16,000 plus 24,000 a day; a very large automated test and rebuild farm (affected-dependency selection); automatic rollback of a breaking change; code owners review per directory.
- **For model-session writers (`reasoned`).** Direct match to our shape: one trunk, a serial landing order, a test gate, an undo. What Google does not say is how often a change was rejected or rolled back, and nothing about two changes that touch the same lines (that question is left to the author's rebase). The 596 s serial suite (library `r57-0103`) is the equivalent of the presubmit, but Google runs affected tests only, not the whole suite (this paper says "affected dependencies").
- **Frame.** Bears on means (2) order before work (the serial order of landing, not of work) and on write skew: the post-commit rebuild is the "check as last judge", with rollback as the abort.

## 4. Google: a survey of engineers on the single repository, 2018
- **Citation:** Jaspan, Jorde, Knight, Sadowski, Smith, Winter, Murphy-Hill, "Advantages and Disadvantages of a Monolithic Repository: A Case Study at Google", ICSE-SEIP 2018. URL fetched: https://storage.googleapis.com/gweb-research2023-media/pubtools/4479.pdf (link from the Google Research page; the author-page copy people.engr.ncsu.edu timed out twice and the stateful.com copy gave 404). Status `quoted`. `P:google-monorepo-icse/paper.txt`.
- **Problem.** Does the single repository pay off in the view of those who work in it?
- **Mechanism.** A mixed-methods study (survey plus commit and view logs), not a mechanism.
- **Measured gain.** Preference and satisfaction results, not throughput or conflicts; the paper does not report a merge-conflict rate. Self-reported company study, survey.
- **Quotes.** `paper.txt:113-114` "Synchronization: The development process is trunk-based; engineers commit to the head of the repo."; `paper.txt:84-88` unversioned dependencies, "projects must use whatever version of their dependency is at the repo head". The build-time cost of a large shared repo is a stated drawback (`paper.txt:477-483`).
- **Assumes.** Same as block 3.
- **For model-session writers (`reasoned`).** Adds nothing on conflict mechanics; confirms the whole setup depends on one head and on dependencies always at head (so there is no version skew between writers, only an ordering).
- **Frame.** Weak. Kept to show that no merge-conflict rate exists for the Google trunk in public text.

## 5. Microsoft: Windows moved onto one Git repository (GVFS), 2017
- **Citation:** Brian Harry (Microsoft), "The largest Git repo on the planet", Microsoft DevBlogs, 24 May 2017. URL fetched: https://devblogs.microsoft.com/bharry/the-largest-git-repo-on-the-planet/ . The announcement post https://devblogs.microsoft.com/devops/announcing-gvfs-git-virtual-file-system/ was saved (`P:msft-gvfs/`) but not read for this file. Status `quoted` (company blog; every figure self-reported). `P:msft-bharry/paper.txt`.
- **Problem.** About 4,000 Windows engineers, 40-plus depots, one very large history: Git alone took "30 minutes up to hours" on common commands.
- **Mechanism.** A virtual file system fetches files when first read; work in Git was changed so commands scale with files read or modified, not with repo size; a proxy serves distant offices; engineers were moved in waves.
- **Measured gain (self-reported).** `msft-bharry/paper.txt:70` "approximately 3.5M files ... a repo of about 300GB ... about 4,000 engineers and the engineering system produces 1,760 daily 'lab builds' across 440 branches"; `paper.txt:88` "vanilla Git ... many of the commands would take 30 minutes up to hours and a few would never complete. The fact that most of them are less than 20 seconds is a huge step"; `paper.txt:79` "over 250,000 reachable Git commits ... over the past 4 months".
- **What broke on the way, relevant to merging.** `paper.txt:73` "Windows ... often has VERY large merges across branches (10,000's of changes with 1,000's of conflicts). We discovered that first week that our UI for pull requests and merge conflict resolution simply didn't scale to changes that large."
- **Assumes.** Many long-lived branches merged in bulk (not trunk-based); the cost is in size of the repo and the tools, not in concurrent writers to one file.
- **For model-session writers (`reasoned`).** Gives a count of conflicts in bulk merges ("1,000's of conflicts" in a merge of "10,000's of changes") but no rate and no way to tell clean merges that fail. It shows the opposite choice to Google (many branches, big merges) and that the tool, not the algorithm, failed first.
- **Frame.** Bears on the cost of merging by lines at scale; adds nothing on the four database failures.

## 6. Discord: message store, MongoDB to Cassandra (2017) and Cassandra to ScyllaDB (2023)
- **Citations:** (a) Discord Blog, "How Discord Stores Billions of Messages", 2017, https://discord.com/blog/how-discord-stores-billions-of-messages ; (b) Discord Blog, "How Discord Stores Trillions of Messages", 2023, https://discord.com/blog/how-discord-stores-trillions-of-messages . Status `quoted` both (company blogs, all figures self-reported). `P:discord-billions/paper.txt`, `P:discord-trillions/paper.txt`.
- **Problem.** (a) A single MongoDB replica set whose data and index no longer fit in RAM (`billions/paper.txt:94`). (b) A 177-node Cassandra cluster with hot partitions, compaction backlog and garbage-collection pauses.
- **Correction of the lane's wording.** The lane file calls this "a storage migration forced by write contention". Neither post says so: the stated pressure is hot **read** partitions, not contended writes (`trillions/paper.txt:101` "In Cassandra, reads are more expensive than writes ... Lots of concurrent reads as users interact with servers can hotspot a partition"). So this system is evidence about hot spots, not about concurrent writers of one object. The 2017 post does give a real write-conflict lesson (below).
- **Mechanism (b).** Data services in front of the database coalesce identical concurrent requests into one query, routed by consistent hashing on the channel id so one instance sees all requests of a channel (`trillions/paper.txt:122`, `:125`); then migration to ScyllaDB (C++, no garbage collector) with dual writes and a custom migrator.
- **Measured (self-reported, uncontrolled).** `trillions/paper.txt:97` 12 Cassandra nodes in 2017 against 177 at the start of 2022; `paper.txt:140` "going from running 177 Cassandra nodes to just 72 ScyllaDB nodes"; `paper.txt:141` "fetching historical messages had a p99 of between 40-125ms on Cassandra, with ScyllaDB having a ... 15ms p99 latency, and message insert performance going from 5-70ms p99 on Cassandra, to a steady 5ms p99"; migration `paper.txt:135` "up to 3.2 million per second", estimated three months for the stock tool against nine days for their own. No baseline workload given; the database and the service layer changed at the same time, so the gain cannot be split between them.
- **Write conflict seen in production (2017 post).** `billions/paper.txt:126` Cassandra resolves conflicts "using 'last write wins' semantics on a per column basis" and every write is an upsert; `billions/paper.txt:127` an edit at the same moment as a delete "we ended up with a row that was missing all the data except the primary key and the text"; their fix was to detect the corrupt row by a null required column and delete it (`:128-130`) rather than write the whole message back, which "had the possibility of resurrecting messages that were deleted and adding more chances for conflict for concurrent writes to other columns" (`:128`).
- **Assumes.** Independent keys (channel plus time bucket); read hot spots are absorbed by coalescing and by routing a key to one process (an owner per key).
- **For model-session writers (`reasoned`).** Two carry over: (1) routing all work for one key to one owner process (partition ownership) removes cross-writer contention; (2) per-column last-writer-wins with upserts produced a half-written row from edit against delete, which is the lost update plus a dirty merge, and the fix was a check for an invariant (a required field present), i.e. validation at read time, not prevention. The coalescing of identical reads has no counterpart for writes.
- **Frame.** Bears on means (3) layout and ownership; adds a failure the frame's table lacks: a **resurrection or half-written row** when a delete and a field update race under per-field last-writer-wins.

## 7. Meta (Facebook): server-side rebase on push
- **Citation:** no primary Meta text found that describes server-side rebase. Seen: (a) Gregory Szorc's notes of a Facebook F8 talk, 28 Mar 2015, https://gregoryszorc.com/blog/2015/03/28/notes-from-facebook's-developer-infrastructure-at-scale-f8-talk (a third party's notes, not Meta's words). (b) Facebook Engineering, "Scaling Mercurial at Facebook", 7 Jan 2014, https://engineering.fb.com/2014/01/07/core-infra/scaling-mercurial-at-facebook/ (read; it does not mention rebase on push). Status `summary` (secondary source only).
- **Problem (per the notes).** `meta-szorc/paper.txt:59-61` "Push-pull-rebase bottleneck: if you rebase and push and someone beats you to it, you have to pull, rebase, and try again. This gets worse as commit rate increases and people do needless legwork."
- **Mechanism (per the notes).** `meta-szorc/paper.txt:61-63` "Facebook has moved to server-side rebasing on push to mostly eliminate this pain point."; and `:122-123` developers do not push to the master repository, a landing service does ("It is not OK at Facebook to land a diff without using Landcastle"), and it runs tests again after landing, with backouts "fairly aggressively" (`:126-129`).
- **Measured gain.** None given in either source. From the 2014 post only: `meta-hg/paper.txt:36` "thousands of commits a week across hundreds of thousands of files"; `:49` "thousands of commits being made every day"; `:47` status command "more than 5x faster than Git's" and `:55` clones and pulls "10x faster" (self-reported, about file scanning and cloning, not about landing).
- **Assumes.** Two changes that rebase without textual conflict can land in either order; a test run after landing catches wrong clean merges.
- **For model-session writers (`reasoned`).** This is the same idea as a retry loop moved to the server: removes the "pull, rebase, retry" race for the author and costs nothing when the rebase is clean. The remaining risk is the wrong clean rebase (write skew), which they handle after landing by test and backout, not before. For a session this saves tokens only if the server rebase needs no model call.
- **Frame.** Bears on means (4) merge by structure only in the weak sense (a textual rebase); and on write skew: validate after landing, back out on failure. Not read in primary text: the claim is `summary` and must not be used for a decision.
