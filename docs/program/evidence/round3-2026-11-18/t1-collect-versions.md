## Gate summary
1. Rodeh 2006 (IBM report of the 2008 paper): a change rewrites the whole path, "2 x tree-depth" pages at most per insert; leaf links and in-place splits are lost; append-only growth leaves 50 % occupancy; bounds [b,3b] give average about 2b (lines 66, 369, 580). `quoted`.
2. Rodeh: a clone copies only the root and counts references; the cost of sharing is paid lazily, only on the path a later write touches (lines 143, 436). Ten tasks reach about x6 on disk-bound work and a checkpoint costs 3 to 10 % (lines 685, 3 tables). `quoted`.
3. Driscoll et al. 1989: copying the access path costs O(log n) space per update; node copying with spare slots costs O(1) amortised, a saving of "a logarithmic factor" (lines 1446-1449, 357). `quoted` (OCR text).
4. Becker et al. 1996: copy-on-write with versions on entries; an update touches at most 5 x log_d m blocks (Theorem 3), space per update O(1) if d is at least 2 (Theorem 4); after a copy a block holds between (1+e)d and (k-e)d entries, so at least e*d+1 changes pass before the next structure change (lines 179, 371, 437). `quoted`.
5. Gray and Graefe 1997: node size from a ratio. Benefit/cost = log2(entries) / (latency + size/rate); 8 to 32 KB best, 16 KB peak at 0.78 (lines 288, 324, Table 6 at lines 346-368). `quoted`.
6. Chu 2011 (LMDB): one writer, copy-on-write, readers never block (lines 240, 255, 268); naive append-only without reuse left over 99 % of pages wasted (line 200); 16 concurrent searches 12.0 s against 3 min 4 s (Table 3, lines 346-352; row labels garbled by the text extraction). `quoted`.
7. Safavi and Seybold 2023 (secondary): B-tree floor 1/2, expected 69 % under random insertion; B* floor 2/3, expected 81 %; wider sharing "further increases the write-bounds" (lines 69-77). `quoted` as their statement of Yao.

## Papers

### P1. Rodeh, "B-trees, Shadowing, and Clones", IBM Research Report H-0245, Nov 2006 (the version of ACM TOS 2008). Read from: https://rtheunissen.github.io/bst/docs/references/2006_rodeh.pdf (copy of the IBM report). Folder: `R:papers/tree/versions-rodeh/`. Pages read: all (14 pages). Note: this is the report, not the journal text.
- Problem: shadowing (copy-on-write) and B-trees clash: leaf chaining, in-place split (B-link) and neighbour shuffling all break.
- Mechanism: top-down B+ tree with proactive split on the way down and proactive fix (merge or borrow) on the way up when a node is at minimum; every node on the path is shadowed during one downward pass; clones share pages through per-page reference counts that are charged lazily.
- Measured gain: "ten tasks ... speedup of about x6" against one task on a disk-bound lookup load (line 685, Table 2 line 579); with 2 clones throughput 1303, 733, 394, 350 against 1307, 763, 407, 359 ops/s without (Table 8, lines 738-749): clone cost 0.3 to 4 %. Checkpoint "between 3% and 10% degradation" (section 8.5). Workload: 16-byte entries, 4 KB pages, trees of about 64,000 leaves and 4 levels, a single machine with disk array. Baseline is an ideal computed from the disk rate, not another tree ("no existing data-structures to compare it against", line 550 region: "Our b-tree construction is novel"). `quoted`.
- Operations: insert "On the way down to a leaf each full index node is split" (section 5.3); remove "each node with a minimal amount of keys is fixed" (5.5); "The number of modified disk-pages can be 2 x tree-depth" and 3 memory pages at worst (line 332, 5.6); root change: a full root splits and "a level was added" (Figure 10 caption), two children of the root merging replaces the root (Figure 11 caption); clone: "Copy the root-node of Tp into a new root. Increment the free-space counters for each of the children of the root" (6.1); first write to a shared page "splits C into two versions" (6.3). Delete of a clone only walks nodes whose count is 1 (6.4). Buffer flush: not applicable; dirty pages are held in cache until the checkpoint (section 4).
- Occupancy: bounds are [b, 2b+1] then "expanded to [b, 3b]"; "The average capacity of a node is around 2b" (line 369); "Both T235 and T150 have an average occupancy of 50%. This is caused by the append-only workload ... the right edge of the tree keeps splitting leaving behind half-full nodes" (lines 580-581). Why not 2b and 2b-1: "a node with 2b entries would split into two nodes of size b which would immediately need to be merged back" (section 5, thrashing). `quoted`.
- Assumes: one machine, short exclusive locks on top nodes ("every tree modification has to exclusively lock the root and one of its children"; it "was not a problem" because root and children are cached, line 541); free-space map in memory; nodes of 4 KB fixed; write-back cache.
- With sessions as nodes (reasoned): (a) Cost law: a change in one leaf forces new versions of all ancestors, so cost per change grows with depth, about 2 x depth node rewrites, not 1. For a session tree a changed leaf report would force a rewrite of each ancestor's summary; the figure is a ratio to depth, true for small and large trees alike. (b) Without leaf links, a node cannot ask its neighbour: any "move work to the sibling" goes through the parent. (c) The serialisation at the top holds only because the top is cached and a visit is microseconds; for a session at minutes per visit the top-down exclusive-lock rule would stall 3 to 16 writers. So the top-down proactive scheme does not carry over; the copy-on-write idea does (a parent never edits a child's finished report in place, it writes a new version). (d) 50 % occupancy under append-only growth is the case a growing job meets: new work arrives at the right edge. A bulk load at 0.75 (x20-0474) avoids it only for work known in advance.
- Status: quoted (report version).

### P2. Driscoll, Sarnak, Sleator, Tarjan, "Making Data Structures Persistent", J. Computer and System Sciences 38(1), 1989. Read from: https://lgreco.github.io/cdp/_downloads/a602bacfc886e36e34470274c46b6d09/making-data-structures-persistent.pdf (a text-layer copy; the other copies were scans with no text). Folder: `R:papers/tree/versions-driscoll/` (use `alt.txt`; OCR noise, so words may be misspelt). Pages read: abstract, introduction, section 2 (fat node, node copying), section 3 outline, section 4 conclusion on search trees (about 40 of 40 pages skimmed by search, sections 2.2 and 2.3 read).
- Problem: keep every old version of a linked structure readable at small time and space cost.
- Mechanism: fat node (every field keeps a list of versions) or node copying (a node has spare pointer slots; when full it is copied and its predecessors updated).
- Measured gain: a proof, not a measurement. "amortized space cost of 0(1) per update step and a constant factor in the amortized time" for nodes of constant in-degree (line 187-190); against path copying: "copying the entire access path ... requires O(1ogn) space and time in the worst case per insertion or deletion. Thus our method saves a logarithmic factor in space" (lines 1446-1449). `quoted`.
- Operations: update only on the newest version in the partially persistent form; a version list orders versions (line 600-610); a full node is copied "If there is no space in a predecessor ... the predecessor, too, must be copied" (lines 360-364).
- Assumes: pointer machine, constant in-degree, main memory (Becker, P3, says blocks break the space bound: one block per item).
- With sessions as nodes (reasoned): the ratio that matters is path copying O(depth) per change against O(1) amortised with spare room per node. Spare room per node is exactly slack in a session's window (fill below 1). Whether the O(1) result holds depends on constant in-degree (a report referenced by few parents), which holds for a tree and fails for a graph. Small project: depth 1 or 2, path copying is cheap and simple; large project: depth 4 or more, the saving is a factor of depth. A rerun differs, so "version" here means a rerun, not a time stamp.
- Status: quoted (OCR text).

### P3. Becker, Gschwind, Ohler, Seeger, Widmayer, "An asymptotically optimal multiversion B-tree", VLDB Journal 5(4), 1996. Read from: https://vldb.org/journal/VLDBJ5/60050264.pdf (needed a browser User-Agent). Folder: `R:papers/tree/versions-becker/`. Pages read: sections 1 to 3 in full; later sections only by search.
- Problem: a B-tree that keeps all versions with the same asymptotic bounds as the one-version B-tree, where a block holds many items.
- Mechanism: each entry carries an insertion and a deletion version; on overflow a "version split" copies only the live entries into a new block; then a key split or a merge keeps the new block within bounds. Multiple roots partition the versions.
- Measured gain: a proof. Lower bounds met: space "O(i/b)" blocks for i versions; an update "accesses and modifies O(log_b m_i) blocks"; exact-match "O(log_b m_i)" (lines 63-80). Constants: "Theorem 3 The number of block accesses and modifications for the (i+1)-th update operation is 5 x log_d m_i in the worst case" (line 371); "Theorem 4 The worst-case amortized space cost per update operation S = S_dat + S_dir is O(1) if d >= 2" (line 437). Data-block amortised space cost "<= 2 x k x d / (e x d + 1)" (lines 418-421, inequality 3). Not a measurement on a machine. `quoted`.
- Operations: "block overflow occurs as the result of an insertion into a block that already contains b entries" (line 150); "weak version underflow occurs if an entry is deleted in a block with exactly d current entries" (line 153); "The structural modification after a block overflow copies the block and removes all but the current entries from the copy. We call this operation a version split" (lines 162-164); after a version split "the number of current entries ... must be in the range from (1 + e) x d to (k - e) x d; we call this the strong version condition" (line 178-179); outside the range: merge with a copy of a sibling, or key split. Root change: a root can be version-split into new roots and a new root is allocated when a key split reaches it (Figures 4 to 6).
- Occupancy as a ratio: block capacity b = k x d; the fraction d/b = 1/k is the weak minimum; an inequality ties k to e: "(k - e) x d + 1 >= 2 x (1 + e) x d" (line 375) and for merges "e <= 1 - 1/d". For B-trees the fraction guaranteed in a new node is 0.5 (line 383). So the number of changes absorbed before the next structure change is at least e x d + 1 (line 173), a law in ratios of the block capacity, not an absolute threshold. `quoted`.
- Assumes: blocks are read and written by an access path, one writer per version, updates only to the current version, d large.
- With sessions as nodes (reasoned): the version split is a "copy only what is still alive, into a fresh node" step, the same move as handing live work to a new session at a hand-over; the strong version condition gives the amount of slack a fresh node must have so that the next hand-over is at least e x d + 1 changes away (it stops a node that comes back nearly full from handing over again at once). Whether e x d is a few items or a few thousand tokens depends on d; for small jobs where d is below 2, Theorem 4 does not apply (needs d >= 2). Update touches 5 nodes per level, so total rewrite per change is 5 x depth at worst.
- Status: quoted (sections 1 to 3).

### P4. Gray and Graefe, "The Five-Minute Rule Ten Years Later, and Other Computer Storage Rules of Thumb", ACM SIGMOD Record 26(4), 1997. Read from: https://arxiv.org/pdf/cs/9809005. Folder: `R:papers/tree/versions-grayGraefe/`. Pages read: all (6 pages, two columns; text lines interleave).
- Problem: choose index page size (fan-out) from the price of a visit against the benefit of a visit.
- Mechanism: "IndexPageUtility = log2(EntriesPerPage)" (line 288); "IndexPageAccessCost = Disk Latency + PageSize / DiskTransferRate" (line 324); "IndexPageBenefit/Cost = IndexPageUtility / IndexPageAccessCost" (line 329); the best page balances the two. "Indexheight ~ log2(N)/log2(EntriesPerPage) pages" (line 280).
- Measured gain: not a measurement; a calculation for 20-byte entries, 70 % full, 10 ms latency, 10 MB/s: benefit/cost 0.60 (2 KB, 68 entries), 0.68 (4 KB), 0.75 (8 KB), 0.78 (16 KB, 541 entries), 0.76 (32 KB), 0.68 (64 KB), 0.53 (128 KB) (Table 6, lines 346-368); "index page sizes in the range of 8 KB to 32 KB are preferable" (line 306). `quoted`.
- Operations: none (a sizing law).
- Assumes: cost of a visit = fixed latency plus a part proportional to size; utility grows as the log of fan-out; the top levels cached so a constant number of visits is saved.
- With sessions as nodes (reasoned): the law carries over as a ratio. If a node visit costs L (a fixed start cost: a brief plus prefix, about 70k tokens per window, x12-0302) plus s (work proportional to what the node holds), and a node's usefulness is log of its fan-out, the best size satisfies s x (ln(fanout) - 1) = L, so s is about L / (ln f - 1). Worked from the paper's own table: for 541 entries ln f is 6.3, so s about 0.19 L, which agrees with the table's peak (1.6 ms transfer against 10 ms latency, ratio 0.16). With a fan-out of 4 to 6 and L = 70k tokens, s would be about 100k to 170k tokens of work per node. This is my arithmetic, not the paper's, and the log-utility assumption has not been shown for routing questions. Result is stated as a ratio of start cost to work, so it speaks to small and very large projects alike; it says only a minimum size below which a session is mostly overhead. The rule moves with the technology ratio: "These rules-of-thumb change in predictable ways as technology ratios change."
- Status: quoted.

### P5. Chu, "MDB: A Memory-Mapped Database and Backend for OpenLDAP", 2011 (LMDB design paper). Read from: https://mail.openldap.org/pub/hyc/mdb-paper.pdf. Folder: `R:papers/tree/versions-lmdb/`. Pages read: all (about 12 pages; text 521 lines).
- Problem: a read-heavy database with no tuning, no locking for readers and no garbage collector.
- Mechanism: copy-on-write B+ tree, two alternating meta pages hold the current root, one writer at a time, reader table of snapshot ids, freed pages reused when no reader's snapshot is older.
- Measured gain: "16 concurrent searches": back-mdb "0m12.023s" against back-hdb "3m04.464s" (Table 3, lines 346-352; the extraction mixes row labels, so I take the smallest and largest row as mdb and hdb and mark it uncertain); "37% as much RAM" as back-hdb (line 341). Workload: OpenLDAP search on a fully cached database of the authors' test set. Writes were slower: "Write performance has been traded for read performance" (line 420). `quoted` (labels uncertain).
- Operations: "Writes are performed using copy-on-write semantics; whenever a page is to be written, a copy is made and the copy is modified instead of the original" (line 258); commit writes the older meta page, "readers are guaranteed to always see a valid root node" (lines 222-227); "the MDB library allows only one writer at a time" (line 240); "nothing that can block the operation of readers" (line 255); "The only consequence of a reader holding onto an old snapshot for a long time is that page reclaiming cannot be done" (lines 268-270). Cost of copy-on-write without reuse: "the DB occupied 1027 pages but only 10 pages actually contained current data; over 99% of the space was wasted" (line 200); with garbage collection, "twice as much disk space as the actual data occupies" and I/O "much more than 2N operations/second" for N writes (lines 161-166, symbol lost in extraction).
- Assumes: single machine, memory-mapped file, short write transactions, one writer.
- With sessions as nodes (reasoned): maps cleanly to 3 to 16 sessions that mostly read a shared record and rarely write it: readers hold a snapshot (the version of the parent file they were briefed on), one writer at a time changes the parent, nothing is edited in place. The cost it names is also ours: old versions pile up until no reader needs them (a long-running leaf holds back clean-up), and write throughput is traded for read. Fine for small jobs (one writer is enough); for very large projects one writer at the top is the serialisation point. Law in ratios: space amplification of about 2 with a collector, over 99 % waste without one.
- Status: quoted.

### P6. Safavi and Seybold, "B-Treaps Revised: Write Efficient Randomized Block Search Trees with High Load", arXiv 2303.04722, 2023. Read from: https://arxiv.org/pdf/2303.04722. Folder: `R:papers/tree/versions-btreaps/`. Pages read: introduction and the load-factor corollary only; used for its statement of earlier results, not for its own structure. A secondary source for Yao 1978 and the B* variant.
- Problem: it is about uniquely represented block trees; I use only its summary of classic occupancy.
- Mechanism and gain: "Classic B-Trees guarantee that every block, beside the root, has a load-factor of at least 1/2 ... The B*-Tree variant guarantees a load-factor of at least 2/3 based on ... an overflow strategy that shares keys among the two neighboring nodes ... Yao's Fringe Analysis showed that inserting keys under a random order in (deterministic balanced) B-Trees yields an expected asymptotic load-factor of ln(2), about 69%, and ... 2 ln(3/2), about 81% for B*-Trees. For general workloads however, maintaining higher load-factors (with even wider overflow strategies) further increases the write-bounds of updates" (lines 69-77). `quoted` (secondary).
- With sessions as nodes (reasoned): occupancy with and without redistribution before a split is 0.69 against 0.81 under random growth, at the cost of touching a neighbour on each overflow; a neighbour is a second live session that must be paused. Both are ratios of capacity and hold at any scale of tree, but they are for random order of arrival; Rodeh (P1) measured 50 % for ordered (append) arrival, the case a growing job meets. So a fill of 0.75 at load (x21-0452: "a chosen slack rather than a theorem") lies between the two measured values, not at one.
- Status: partly read.

### P7. Comer, "The Ubiquitous B-Tree", ACM Computing Surveys 11(2), 1979. Read from: https://users.cs.utah.edu/~pandey/courses/cs6530/fall24/papers/trees/p121-comer.pdf (1.37 MB, `%PDF-`, 1034 text lines). Folder: R:papers/tree/s2-comer-utah/. Pages read: B*-trees, the concurrency section and the survey of variants.
- Correction to the first pass: "scanned PDF with no text layer" was a damaged download; a fresh download has a text layer and `pdftotext` reads it. (pdftotext interleaves the two columns, so line numbers below are approximate.)
- Problem: survey of B-tree forms, their occupancy and their use in a multi-user database.
- Mechanism (two lines): B-tree (nodes at least half full); B*-tree (a local redistribution to a neighbour before splitting); B+-tree (data in the leaves, linked sequence set).
- Measured gain: no benchmark; analytic guarantees. "Knuth defines a B*-tree to be a B-tree in which each node is at least 2/3 full ... B*-tree insertion employs a local redistribution scheme to delay splitting until 2 sibling nodes are full. Then the 2 nodes are divided into 3, each 2/3 full. This scheme guarantees that storage utilization is at least 66%" (paper.txt lines 484-495, quoted); B+-trees give "guaranteed storage utilization of 50%" (line 781, quoted); "increasing storage utilization has the side effect of speeding up the search since the height of the resulting tree is smaller" (lines 497-501, quoted).
- Operations: a split key is "promoted to the parent node where it serves as a separator", and "splitting propagates all the way" to the root in the worst case (lines 297-311, quoted); underflow is handled by redistribution among two neighbours (lines 353-354, quoted); "instead of splitting a node as soon as it fills up, keys could merely be distributed into a neighboring node, splitting only when two neighbors fill" (lines 484-490, quoted).
- Assumes: nodes are disk blocks; fixed-size nodes.
- With sessions as nodes (reasoned): redistribution before a split touches a neighbour as well (two units read and written instead of one new unit started); a running session cannot take work moved into it, so the B* step is likely unusable and a plain split is the form that fits. Ratios: occupancy 1/2 (B), 2/3 (B*), ln 2 = 0.69 (random insertion, P8).
- Status: quoted.

### P8. Yao 1978 and Bayer and Schkolnick 1977, as reported in P7 (second-hand)
- Yao: "Yao [YAO78] reports the results of analyzing 2-3 trees built from a uniformly distributed set of n keys ... Extending the analysis to B-trees of higher order, Yao has shown that the expected storage utilization is ln 2 = 69%" (P7 paper.txt lines 731-741, quoted from Comer, not from Yao).

Also, "using the top-down splitting suggested in [GUIB78] ... only one pair of nodes will ever be locked at a given time", at "the price ... a slight decrease in storage utilization" (lines 786-800, quoted from Comer).

### P9. LMDB reference documentation (Chu, Symas), main page. Read from: http://www.lmdb.tech/doc/ (HTML saved as paper.txt, 155 lines). Folder: R:papers/tree/s2-lmdb-doc/.
- Problem / mechanism: B-tree database with copy-on-write pages and a single writer.
- Measured gain: none on this page.
- Operations: "Data pages use a copy-on-write strategy so no active data pages are ever overwritten, which also provides resistance to corruption and eliminates the need of any special recovery procedures after a system crash. Writes are fully serialized; only one write transaction may be active at a time, which guarantees that writers can never deadlock. The database structure is multi-versioned so readers run with no locks; writers cannot block readers, and readers don't block writers" (paper.txt line 74, quoted). "LMDB tracks free pages within the database and re-uses them for new write operations" (line 75, quoted). "Avoid long-lived transactions. Read transactions prevent reuse of pages freed by newer write transactions, thus the database can grow quickly. Write transactions prevent other write transactions, since writes are serialized" (line 119, quoted).
- With sessions as nodes (reasoned): one writer with readers that never block is the shape "one coordinator writes the record, leaves read it". The line-119 warning is the cost: a long reader (a session working for minutes) pins old versions, so space grows with reader duration. No ratio given.
- Status: quoted (documentation, not a paper).
