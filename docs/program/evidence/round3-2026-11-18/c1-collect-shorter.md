## Gate summary
- P1 Ekstazi 2015: "reduced the end-to-end testing time 32% on average, and 54% for longer-running test suites"; slower on short suites (up to 138%); useful from about a minute of suite. quoted, ekstazi l.29-31, l.525-534.
- P2 Elbaum, Rothermel, Penix 2014: pre-submit selection by failure and execution windows detects 70-80% of failing suites (Wf=96 h), random of equal size "approximately six times worse"; the skipped share costs under 0.17% of pre-submit load at 0.5% failure rate. quoted, elbaum l.446-455, l.480-483.
- P3 Machalica 2019 (Facebook predictive selection): "over 95% of individual test failures and over 99.9% of faulty changes", fewer than a third of the tests that build dependencies pick, "total infrastructure cost ... by a factor of two". quoted, pts l.17-19, l.100-112, l.456-463.
- P4 Kondareddy 2025 (Google speculative cycles): "median (p50) reduction of approximately 65% (from 107 to 37 minutes)" in time to detect novel breakages; 25% of targets gives 85% recall. quoted, tap25 l.24-29, l.77-79.
- P5 Fallahzadeh, Bavand, Rigby 2023 (parallel batch testing): batch size 4 uses "up to 72% fewer machines" at the same feedback time; the effect of machine count on feedback time is "non-linear". quoted, pbatch l.31-40.
- P6 Luo 2014 (flaky tests): first three causes of 161 classified fixes are async wait 45%, concurrency 20%, test order 12%; a failing test is rerun 10 times at Google. quoted, luo l.38-41, l.346-352, l.417.
- P7 Schwendner and others (BMW) 2025: a Bazel-affected-target step already "heavily reduces load" yet pipelines still run 34 and 56 minutes; 58% of test targets fail in post-submit; the merge gate deliberately runs the full suite. quoted, bmw l.77, l.96-112 (see the text for exact lines).
- P8 Mossige and others 2019 (TC-Sched, scheduling tests on machines): random assignment is "30 %-60 % worse than greedy"; a solver beats greedy for most instances; no single gain figure. quoted, tcsched l.33-35, l.640-650. Weak evidence (synthetic suites).

## Papers

### P1. Gligoric, Eloussi, Marinov, "Practical Regression Test Selection with Dynamic File Dependencies" (Ekstazi), ISSTA 2015. Read from: https://users.ece.utexas.edu/~gligoric/papers/GligoricETAL15Ekstazi.pdf. Saved: R:papers/check/ekstazi/paper.txt. Read: abstract, introduction, evaluation of times (l.1-60, 300-340, 489-540), related work on flaky tests (l.685-695).
- Problem. Rerunning all tests on each revision is slow; classic selection needs version-control integration or heavy instrumentation.
- Mechanism. Record which files each test touches during a run (dynamic file dependencies, checksum per file); on the next revision rerun only tests whose files changed. Class-level granularity by default.
- Result: "Ekstazi reduced the end-to-end testing time 32% on average, and 54% for longer-running test suites, compared to executing all tests" (txt line 29-31). "the time for AEC varies between 9% and 138 % (slowdown)" and "all slowdowns are for projects with short-running test suites" (txt line 525-529). "Ekstazi appears useful for projects whose test suites take over a minute: Ekstazi on average roughly halves their testing time" (txt line 532-534). Cucumber: "Ekstazi selects on average 12% of test entities, but the time that Ekstazi takes is 99% of RetestAll" (txt line 516-519).
- Measured gain: 32% mean, 54% on long suites, 615 revisions of 32 open-source projects, almost 5M lines, against RetestAll (txt line 29-31); 47% and 66% with the collection phase run off-line (txt line 122-124). The selection ratio per revision varied "between 5% and 38%" (txt line 524-525).
- Assumes. A deterministic test (its flaky-tests paragraph, l.689, says a non-deterministic test can make dependency information differ between runs); dependencies tracked through files, not reflection (l.585 lists reflection as a gap); the previous revision's run is available; Java and JUnit; a suite that takes over a minute.
- With model sessions: the gain is time per check run, so it applies to a check of minutes or an hour and not to a check of seconds (the paper's own short-suite slowdown). Model-session edits often touch widely shared files, which select nearly everything (the paper's own Cucumber-type cost); reasoned. A rerun is not the same run: selection needs a recorded dependency map per test, so a brand-new test or a session that edits test and code together selects at least the new tests; reasoned.
- Needs to know about a project before use. Test-to-file dependency map from a previous full run (collected by the tool, costs the collection phase); whether the suite is over about a minute; share of changes touching widely shared files (not measured in the paper as a number, only per project).
- Status: quoted.

### P2. Elbaum, Rothermel, Penix, "Techniques for Improving Regression Testing in Continuous Integration Development Environments", FSE 2014. Read from: https://cs.uwaterloo.ca/~m2nagapp/courses/CS846/1171/papers/elbaum_fse14.pdf. Saved: R:papers/check/elbaum/paper.txt. Read: abstract, algorithms, evaluation of selection and its threats (l.1-45, 270-420, 430-490).
- Problem. Pre-submit testing is expensive; post-submit must report failures fast. Both without coverage data.
- Mechanism. Select a test suite pre-submit only if it failed within a "failure window" Wf or has not run within an "execution window" We; skipped suites go to post-submit, where they are prioritised by the same recency signals within a prioritisation window Wp.
- Result: "The gains, as measured by the detection of failing test suites, reach between 70% and 80% when Wf = 96. The other 20% to 30% of failing test suites were not selected" (txt line 449-452). "Random test suite selection with the same number of test suites selected for execution performed approximately six times worse in terms of failure detection" (txt line 452-455). "Assuming that test suite execution failures rates are 0.5% (as in our dataset), selecting 33% of the test suites ... implies that the test executions added to post-submit testing form less than 0.17% of the pre-submit testing load" (txt line 479-483).
- Measured gain: from Wf around 12 on, "the percentage of failing test suites selected is at least three times greater than the percentage of test suites selected for execution and the percentage of test suite execution time" (txt line 446-449); dataset: "over 3.5 million test suite executions" over 30 days at Google (txt line 185-186; library x06-0207 states it is a small sample).
- Assumes. Recency of failure predicts failure; suites are the unit; 0.5% suite failure rate; a post-submit stage that still runs the skipped suites (so failures are delayed, not lost). Their threats paragraph says infrastructure availability was not modelled (txt line 480-483).
- With model sessions: the recency signal needs a stream of many runs per suite (3.5 million executions); with 3 to 16 workers and a few runs per hour the history is thin, so Wf and We cannot be set from it; reasoned. The "delay to post-submit" is only acceptable if a post-submit stage exists; in a single serial check that is the same check, so skipped tests move cost, not remove it, except for the 0.17% figure, which assumes a 0.5% failure rate; reasoned.
- Needs to know about a project before use. Per-suite failure history with times; the failure rate of suites (0.5% here).
- Status: quoted.

### P3. Machalica, Samylkin, Porth, Chandra, "Predictive Test Selection", ICSE-SEIP 2019 (arXiv 1810.05286v2). Read from: https://arxiv.org/pdf/1810.05286. Saved: R:papers/check/pts/paper.txt. Read: abstract, introduction, selection model and results (l.1-115, 200-330, 380-470).
- Problem. Tens of thousands of changes a week each impact about ten thousand tests (txt line 44-50, interleaved with a figure); running all is infeasible.
- Mechanism. A gradient-boosted classifier scores each (change, test) pair from features of change, test and history; select the highest-scored tests until a budget; trained on the past three months of outcomes with flaky results removed by re-running.
- Result: "the strategy reduces the total infrastructure cost of testing code changes by a factor of two, while guaranteeing that over 95% of individual test failures and over 99.9% of faulty changes are still reported" (txt line 16-19). "The test selection procedure selects fewer than a third of the tests that would be selected on the basis of build dependencies" (txt line 107-109). "If we train our classifier on flaky test results, we get very poor predictions" (txt line 92-94). "deploying it has reduced total number of test executions by a factor of three and total infrastructure cost ... by a factor of two, relative to test selection based on build dependencies" (txt line 456-463).
- Measured gain: x2 infrastructure cost, x3 test executions, against selection by build dependencies, in production at Facebook's mobile repository for several months (txt line 112-113).
- Assumes. A build graph that gives the impacted tests first (this is the baseline it improves on: build-dependency selection, Bazel/Buck style, txt line 35-48); three months of outcomes; non-conservative: it "may miss some of the impacted tests" and is applied only at stages where later stages run the rest (txt line 201-207, land-time races mean the stages are not the last line of defence).
- With model sessions: this is the one with the largest published ratio but needs a large history of (change, test) outcomes; a project with a handful of workers does not have it; reasoned. Missing tests are acceptable there because a later stage runs them; for our single serial check, a missed failure would pass to the shared branch unless a final run still exists; reasoned. A model session's changes are not like human diffs the model was trained on; not tested.
- Needs to know about a project before use. Three months of per-test outcomes per change; a dependency graph; flakiness labels per test.
- Status: quoted.

### P4. Kondareddy, Azad, Singh, Henderson, "Speculative Testing at Google with Transition Prediction", ICST 2025. Read from: https://hackthology.com/pdfs/icst-2025.pdf. Saved: R:papers/check/tap25/paper.txt. Read: abstract, introduction, background, contributions (l.1-135, 200-270, 300-345).
- Problem. Post-submit testing batches many changes into one cycle; a break takes 1-2 hours to show; double-digit yearly growth in demand.
- Mechanism. Between full "comprehensive" cycles (batch every affected test, where affected is by the Bazel build graph), run frequent small cycles of the targets a shallow model predicts newly break (pass to fail transition), with a budget.
- Result: "Using Speculative Cycles we observed a median (p50) reduction of approximately 65% (from 107 to 37 minutes) in the time taken to detect novel breaking targets" (txt line 27-29). "With a budget of 25% of the total targets, Transition Prediction achieves a 85% recall rate in detecting breakages" (txt line 77-79). "it takes 1-2 hours for a test broken by a developer's change to start failing in TAP Postsubmit" (txt line 72-73). Comprehensive cycles "run all tests that are 'affected' since the previous cycle. 'Affected' is our term for dependence as implied by the build system's package graph" (txt line 124-127).
- Measured gain: p50 time to detect 107 to 37 minutes, on 3 months of production data, "120 billion test-cycle pairs, 7.7 million breaking targets, with 20 thousand unique breakages" (txt line 22-26); a replay-style evaluation against random scheduling and an optimal scheduler (txt line 354-356).
- Assumes. Many cycles and many breakages to learn from; build/test failures tagged to a culprit change by an automatic culprit finder with 98% estimated accuracy (txt line 177-181); flakes filtered.
- With model sessions: it speeds up detection and does not shorten one run; it is a post-submit device. Training needs a very large history; reasoned. The idea of "affected by the build graph first, then predict" holds at any scale; the learned part does not for 3 to 16 workers; reasoned.
- Needs to know about a project before use. Dependency graph of targets; per-target pass/fail history; a culprit-labelled set of breakages.
- Status: quoted.

### P5. Fallahzadeh, Bavand, Rigby, "Accelerating Continuous Integration with Parallel Batch Testing", ESEC/FSE 2023 (arXiv 2308.13129). Read from: https://arxiv.org/pdf/2308.13129. Saved: R:papers/check/pbatch/paper.txt. Read: abstract, introduction, method and data (l.1-160); results tables not read line by line.
- Problem. Earlier batch-testing studies assumed one machine, reran everything on a failed batch, and counted resources, not feedback time (txt line 44-52, right column).
- Mechanism. Simulate several machines over a recorded test history; compare TestAll, constant-size batching, BatchAll (batch size from the queue length) and TestCaseBatching, with bisection on failure. Both batching and parallelism sit in this paper; here it is the evidence on splitting a check over machines. Its own topic is mergeq.
- Result: "The results reveal a non-linear impact of test parallelization on feedback time, as each test delay compounds across the entire test queue" (txt line 31-32). "ConstantBatching, with a batch size of 4, utilizes up to 72% fewer machines to maintain the actual average feedback time and provides a constant execution reduction of up to 75%" (txt line 32-35). "BatchAll maintains the actual average feedback time with up to 91% fewer machines" (txt line 36-37). "Analyzing historical data to find the threshold where adding more machines has minimal impact on feedback time is also crucial" (txt line 42-43).
- Measured gain: up to 72% (constant batch 4) and up to 91% (BatchAll) fewer machines at the same average feedback time, on Ericsson integration data (over 11,000 changes in six weeks) and Chrome (276 million test outcomes, 9,524 changes, failure rate of builds about 8.5%) (txt line 79-80, 100-105). By simulation: "We do not re-run any tests" (txt line 119-120).
- Assumes. A recorded failure per test is the failure of a batch ("we assume that a test will fail in a batch if it failed in any of the builds", txt line 129-132); batch worst-case time taken as the maximum of included builds; no flakiness model beyond recorded outcomes.
- With model sessions: batching in this study pays because most builds pass (8.5% fail in Chrome); a change whose redo costs tokens makes a failed batch costlier than a CPU rerun; reasoned. Test-level split over machines applies where one check has many tests and 16 workers at once would queue; reasoned.
- Needs to know about a project before use. Per-test durations and results per change; failure rate of builds (batch size depends on it); machines available.
- Status: quoted.

### P6. Luo, Hariri, Eloussi, Marinov, "An Empirical Analysis of Flaky Tests", FSE 2014. Read from: https://huang.isis.vanderbilt.edu/cs8395/paper/flakytest.pdf (a course-site copy). Saved: R:papers/check/luo/paper.txt. Read: abstract, introduction, causes (l.1-130, 200-240, 340-420).
- Problem. The effect of flaky tests on regression testing and what causes them.
- Mechanism. Mine 201 commits that likely fix flaky tests in 51 Apache projects; classify cause, manifestation, fix.
- Result: "TAP system at Google had 1.6M test failures on average each day in the past 15 months, and 73K out of 1.6M (4.56%) test failures were caused by flaky tests" (txt line 30-32). "at Google, a failing test is rerun 10 times against the same code version ... if it passes in any of those 10 reruns, it is labeled as a flaky test" (txt line 38-41). Causes among the 161 classified commits: "74 out of 161 (45%) ... Async Wait", "32 out of 161 (20%) ... Concurrency", "19 out of 161 (12%) ... Test Order Dependency" (txt line 346-352, 417); 40 of the 201 were hard to classify (txt line 207-209).
- Measured gain: not applicable; it is a cause study. The Google rate (4.56% of failures) is passed on from personal communication (txt line 31-32, footnote l.62).
- Assumes. Fix commits found by keyword ("intermit", "flak") represent flakiness; open-source Apache projects.
- With model sessions: an order-dependent or time-dependent test that passes alone and fails in a shared check is cheap to mistake for a regression; a failed batch followed by a rerun of the same state would make a flaky failure look like a culprit; reasoned. Test order dependency (12%) is what grows when selection or sharding changes the order; reasoned.
- Needs to know about a project before use. Which tests are flaky (rerun history per test).
- Status: quoted.

### P7. Schwendner and others (BMW Group), "Practical Pipeline-Aware Regression Test Optimization for Continuous Integration", arXiv 2501.11550 (2025). Read from: https://arxiv.org/pdf/2501.11550. Saved: R:papers/check/bmw/paper.txt. Read: abstract, introduction, setting (l.1-130, 575-600).
- Problem. A monorepo with Bazel and Zuul; pre-submit and post-submit pipelines of 34 and 56 minutes remain after selecting by the build graph.
- Mechanism. A reinforcement-learning prioritiser with a cost-aware reward, applied to check and post pipelines, not to the Zuul gate.
- Result: "we have many failing test targets (e.g., 58% in our case)" in post-submit, which makes failure-likelihood selection hard (txt line 77-79). "we identify changed files in each PR and use Bazel to identify affected build and test targets ... This approach heavily reduces load" yet "our pre- and post-submit pipelines still have ... execution times of 34min resp. 56min" (txt line 108-118, columns interleaved). "We did not apply our regression test optimization [to the gate], as we want to have a fail-safe mechanism" (txt line 95-97). At a 50% time budget "over 87% of transitions are detected immediately by our approach, and over 98% within three CI cycles" (txt line 587-589).
- Measured gain: at a 20% budget CostChangeRank finds 25.43% of relevant transitions against 20.69% random (txt line 584-586); at 50% budget over 87% immediately; evaluated on the company's own history.
- Assumes. Pre-submit tests deterministic; post-submit contains flaky and long tests (hardware in the loop).
- With model sessions: shows build-graph affected-test selection and a full-suite gate used together, the same split our builder pre-check and gate use (library x15-0409); reasoned. The numbers are weaker than P3 and P4 (small gains against a random baseline).
- Needs to know about a project before use. A Bazel-style build graph or an equal dependency map.
- Status: quoted for the lines named; the results sections (l.400-580) were skimmed by search, not read in full.

### P8. Mossige, Gotlieb, Spieker, Meling, Carlsson, "Time-aware Test Case Execution Scheduling for Cyber-Physical Systems" (TC-Sched), CP 2017 (arXiv 1902.04627). Read from: https://arxiv.org/pdf/1902.04627. Saved: R:papers/check/tcsched/paper.txt. Read: abstract, definitions, experiment set-up and first results (l.1-130, 160-185, 575-650).
- Problem. Assign tests to machines under shared-resource and machine-eligibility constraints to minimise the time to the last result.
- Mechanism. A constraint-programming model (Cumulatives) of tests, machines and shared resources, with a search that splits durations.
- Result: "TC-Sched can schedule 500 test cases over 100 machines in less than 4 minutes for 99.5% of the instances" (txt line 33-35). "random is 30 %-60 % worse than greedy" (txt line 640-641). "For all test suites but the hardest subset of TS1 and some instances of TS2, Cf is better than greedy" (txt line 648-651).
- Measured gain: against greedy, no single number; figure 4 only (l.645-655); suites are randomly generated from three real suites of 33 to 132 tests (l.596-612), durations 1 s to 800 s. Test durations known in advance.
- Assumes. Known test durations and machine eligibility; one run of each test.
- With model sessions: its setting (many hardware machines, shared devices) is not ours; durations known from history; weak evidence for us; reasoned. Greedy longest-first on known durations is the baseline it beats only by a margin on hard instances.
- Needs to know about a project before use. Per-test duration.
- Status: quoted.
