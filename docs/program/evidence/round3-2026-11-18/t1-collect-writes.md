## Gate summary
1. Arge 1996 (buffer tree): N mixed updates cost O((n) log_m n) I/Os, amortised O((1/B) log_m n) each, because a buffer is emptied only when it holds m/2 blocks and each block is touched a constant number of times per level. `quoted`, paper.txt line 492. Queries are lazy (batched), not online, line 312.
2. Brodal-Fagerberg 2003 (lower bound): used online, buffer trees answer a query in O((m/B)... log_{M/B}(N/M)) while a B-tree with buffers of fan-out ε/log N gets a continuous insert/query trade-off; the trade is tight. `quoted`, paper.txt lines 143-150 and 569-607.
3. Bender and others 2015 (B-epsilon intro): insert cost divides by the batch size B^(1-ε); query cost multiplies by 1/ε; B=1024, ε=1/2 gives 16 times faster inserts for 2 times the point-query I/Os. `quoted`, plain.txt lines 62-75 and 118-124.
4. Jannen and others, BetrFS, FAST 2015: worked ratio 14.3 times faster random inserts than a B-tree (1 TB, 1 MB nodes, fan-out 10); microwrites 0.17 s against about 11.6 s for ext4, XFS, btrfs-class systems. `quoted`, plain.txt lines 148-152 and 414-421.
5. O'Neil and others 1996 (LSM-tree): insert cost ratio LSM to B-tree = K1 * (COST/COSTP) * (1/M), "nearly two orders of magnitude"; levels sized in a geometric progression with equal ratios r; total merge I/O H = (2R/Sp)(K(1+r) - 1/2). `quoted`, plain.txt lines 187-189 and 237-250.
6. Luo and Carey 2020 (LSM survey): leveling write cost O(T*L/B), tiering O(L/B); reads and space move the other way by a factor of T; many "improvements" were measured against an untuned size ratio of 10. `quoted` (table text and prose), plain.txt lines 592-606, 668 and 811.
7. Dayan and Idreos 2018 (Dostoevsky): merging only at the largest level (lazy leveling) cuts update cost from O(T*L/B) to O((L+T)/B) with the same point-lookup and space bounds; no single policy wins across workload mixes; the text states no single speed-up number (it is in figures). `quoted`, plain.txt lines 815, 1212-1214 and 2190.
8. Dayan, Athanassoulis and Idreos 2017 (Monkey): lookup cost is the sum of the Bloom false-positive rates; 50 % to 80 % lower lookup latency at 1 GB to larger scales, from filter allocation alone, update cost unchanged. `quoted`, plain.txt lines 7 and 39. Weak fit: about filters, not batching.

## Papers

### P1. Lars Arge, "The Buffer Tree: A New Technique for Optimal I/O Algorithms" (BRICS RS-96-28, August 1996; the WADS 1995 and Algorithmica 2003 versions are the same technique)
Read from: http://www.brics.dk/RS/96/28/BRICS-RS-96-28.pdf (open BRICS copy). Folder: `R:papers/tree/writes-arge-buffertree/`. Pages read: sections 2 (main ideas), 3 (the structure, the emptying process, rebalancing, Theorem 1), the start of 4; not the applications (sections 5 to 7).
- Problem: do N dictionary operations on data far larger than memory when each random operation costs one block transfer; a B-tree pays Theta(N log_B n) and "the B-tree solution will be slower" (line 253-254) than sorting.
- Mechanism (two lines): a search tree whose internal nodes have fan-out Theta(m) (m = blocks that fit in memory) and a buffer of Theta(m) blocks each; an update is a time-stamped message put in the root buffer and pushed one level down only when a buffer runs full.
- Measured gain: none measured (theory). Bound: "The total cost of an arbitrary sequence of N intermixed insert and delete operation on an initially empty buffer tree is O(n log_m n) I/O operations, that is, the amortized cost of an operation is O((1/B) log_m n) I/Os" (paper.txt lines 492-494). The same sequence on a B-tree is Theta(N log_B n) (line 143, 253). `quoted`.
- Operations:
  - Message: "we construct a new element consisting of the element to be inserted or deleted, a time stamp, and an indication of whether the element is to be inserted or deleted" (lines 354-356). So insert and delete are messages; a delete is a message too; there is no upsert here.
  - Insert path: "When we have collected B such elements in internal memory, we insert the block in the buffer of the root. If the buffer of the root still contains less than m/2 blocks we stop. Otherwise, we empty the buffer" (lines 357-360). The batch is first collected in memory, then the root buffer fills to m/2 blocks.
  - Flush: "When a buffer 'runs full' the elements in the buffer are 'pushed' one level down to buffers on the next level. We call this a buffer-emptying process" (lines 304-306). The whole buffer is sorted and spread to all children in one pass (Figure 2, lines 376-405), so one flush touches every child that gets a message, not only one. Cost O(m) I/Os, paid by credits: each block in a buffer holds credits for the height of its subtree (lines 322-327): "we touch each block a constant number of times on each level of the structure" (lines 331-332).
  - Split and rebalance: the tree is an (a, b)-tree with a = m/4 and b = m, "all nodes except for the root have fan-out between m/4 and m" (lines 350-352). Rebalancing "consists of doing a buffer-emptying process before every rebalance operation... when it is involved in a fuse or share rebalancing operation" (lines 439-441), so a node is always empty of messages when it splits, fuses or shares. Rebalancing is done only after all leaf buffers are emptied, so one structure change is never in flight inside a half-emptied node (lines 483-488: "to prevent different rebalancing operations from interfering with each other"). Total rebalance cost O(n) because there are O(n/m) of them (lines 546-550).
  - Search: queries are messages too; "the result of a query may be generated (and reported) lazily by several buffer-emptying processes" (lines 311-313). So a query is answered only when its message has reached the leaf side, which is not an online answer. Online use needs the whole root-to-leaf path of buffers read (see P2).
  - Root change and merge: the root has no minimum fan-out; fuse and share are the merge and redistribution (line 441). Bulk load: not as such; Theorem 2 empties all buffers top to bottom to get the leaves in sorted order (lines 566-572).
- Assumes: one process drives the whole tree (a batched, offline model); memory holds m blocks; a buffer is read and written as a sorted whole in one pass. No concurrency is treated.
- With sessions as nodes (reasoned): the model, "wait until a block of messages is collected, then push down in one pass", fits a tree where a child session is expensive to start and a parent writes its questions for a child as one brief, not one at a time. What does not fit: the cost model counts block transfers, not minutes; a buffer-emptying that reads and re-sorts a whole buffer is cheap for a machine and costly for a model, which has no sort. Constants such as m/2 for the trigger and m/4 for the lowest fan-out are ratios of the memory size, and are the law to copy: the trigger is a fraction of capacity, not a count. Small work: the claimed gain needs n much larger than m; with n below m the whole tree is one buffer and there is nothing to push. Very large work: the O(log_m n) depth law is the one that matters, and it needs a large fan-out m. Answers are lazy, so it suits reports flowing up, not a coordinator that needs an answer now.
- Status: quoted.

### P2. Gerth Stolting Brodal and Rolf Fagerberg, "Lower Bounds for External Memory Dictionaries", SODA 2003
Read from: https://www.cs.au.dk/~gerth/papers/soda03.pdf (the author's open copy). Folder: `R:papers/tree/writes-brodal-fagerberg/`. Pages read: introduction, Theorem 1.1 and the lower-bound idea, sections 3.1 to 3.4 (upper bounds); not the full proofs of 2.2 and 2.3.
- Problem: what is the exact trade between the cost of an insert and the cost of a member query in an external-memory dictionary.
- Mechanism (two lines): lower bounds from an adversary argument, and three matching upper bounds: truncated buffer trees, B-trees with buffers, B-trees.
- Measured gain: none measured (theory). The result as stated: "If N insertions perform at most lambda * N/B I/Os, then (1) there exists a query requiring at least log_{B+1}(N/M) - O(1) I/Os [for lambda up to about log_B N]; (2) there exists a query requiring N/(M * (M/B)^O(lambda)) I/Os for N > M; (3) there exists a query requiring Omega(log_2 (N/M)/ log(lambda...)) I/Os provided lambda <= B/log^3 N and N >= M^2" (lines 126-140; the extraction drops the symbols in (2) and (3); the structure of (2) and (3) is from the text and the abstract, lines 6-12; `quoted` with symbols restored by me, so also `reasoned` for the exact exponents).
- Operations: "B-trees with buffers" (section 3.4, lines 569-630): "a B-tree of degree Theta(lambda/log N)... Each node has a buffer that is stored in O(1) blocks containing O(B) delayed updates to the subtree below the node. Like in buffer trees, delayed updates in buffers are only propagated down whenever a buffer overflows. When the buffer of a node overflows, there exists a child such that Omega((B log N)/lambda) elements can be moved from the buffer of the node to the buffer of the child. The remaining elements stay in the buffer" (lines 587-601). So one flush moves to one child, and only if at least a fixed fraction of the buffer goes there (pigeonhole). The cost of N updates is O(lambda * N/B) because there are at most O(log N) levels and at most O(N / ((B log N)/lambda)) overflows per level (lines 618-626). "For lambda = B^epsilon... the resulting tree has degree O(B) and height O((1/epsilon) log_B N)... queries require O((1/epsilon) log_B (N/M)) I/Os and B updates require amortized O((1/epsilon) B^(1-epsilon) log_B (N/M)) I/Os" (lines 636-640; the epsilon symbol restored by me from the surrounding text). That is the B-epsilon trade-off.
  - Buffer trees used online: "buffer trees support N updates with O(Sort(N)) I/Os... online queries can be supported in O((m/B) log_{M/B}(N/M)) I/Os, since all buffers along one root-to-leaf path must be examined... While the I/O bound for updates is significantly better than for B-trees, namely a factor B * log_B(M/B), online queries are a factor sqrt(M/B)/log_B(M/B) slower" (lines 456-482; the last ratio is garbled by the extraction, so `quoted` for the sentence and the factor is only as I restored it).
  - A read finds unpushed messages by reading every buffer on the path (same lines).
- Assumes: comparison-based external memory, one operation at a time, a fixed block size B, update cost counted amortised.
- With sessions as nodes (reasoned): the useful part is the shape of the law, not the exponent. A parameter (here lambda, or epsilon) sets the batch size and the fan-out together, and the read cost grows by a fixed ratio, 1/epsilon, in depth. For a tree of sessions: a deeper tree with bigger buffers costs more per read in hops and less per write; the ratio is stated and can be computed once the cost of one hop (one brief and one report) and of one session start are measured (not recorded: our files give a start only as an estimate, see `b1-0113`). The lower bound also says the trade cannot be beaten for a comparison-based structure, so a design that claims both cheap writes and cheap reads without a cost elsewhere (memory, filters, a cache) is suspect. Small work: for N below M all curves are flat. Very large work: the ratio matters most there.
- Status: quoted (symbols restored where marked).

### P3. Michael A. Bender, Martin Farach-Colton, William Jannen, Rob Johnson, Bradley C. Kuszmaul, Donald E. Porter, Jun Yuan, Yang Zhan, "An Introduction to B-trees and Write-Optimization", ;login: 40(5), October 2015
Read from: https://www.usenix.org/system/files/login/articles/login_oct15_05_bender.pdf (USENIX open access). Folder: `R:papers/tree/writes-bender-login/`. Pages read: all (6 pages, 248 plain lines; I used `plain.txt` line numbers).
- Problem: a B-tree needs one I/O per random insert; how to make inserts, deletes and key-value updates fast without losing point-query speed or range-scan speed.
- Mechanism (two lines): internal nodes keep part of their space as a message buffer; messages (insert, tombstone, upsert) enter at the root and move down in batches when a buffer is full.
- Measured gain: "Compared to a B-tree, batching messages divides the insertion cost by the batch size (B^(1-epsilon)). For example, if B = 1024 and epsilon = 1/2, a B-epsilon-tree can perform inserts = 16 times faster than a B-tree" (plain.txt lines 69-75; the 16 equals epsilon * B^(1-epsilon) = 0.5 * 32). On a file system benchmark: "create 3 million 200-byte files in a balanced directory tree... The steady-state performance of BetrFS is an order of magnitude faster than the other file systems" (line 203). "upsert... can accelerate updates by one to two orders of magnitude without slowing down queries" (line 155). `quoted`.
- Operations:
  - Message kinds: insert, tombstone (delete), upsert (lines 41-43, 141-146). "An upsert is a type of message that encodes an update with a callback function which does not require first knowing the value of the key" (line 141). Tombstones are a special case of upserts (line 142). Messages are ordered by "target key, followed by timestamp" (line 56).
  - Insert and flush: "Insertions are encoded as 'insert messages,' addressed to a particular key and added to the buffer of the root node... When enough messages have been added to a node to fill the node's buffer, a batch of messages are flushed to one of the node's children. Generally, the child with the most pending messages is selected" (line 41). "Messages are only flushed to a child when the buffer of a node is full, containing B - B^epsilon ~ B messages... at least (B - B^epsilon)/B^epsilon ~ B^(1-epsilon) messages are moved from the parent's buffer to the child's on each flush. Consequently, any node in a B-epsilon-tree is only rewritten if a sufficiently large portion of the node will change" (line 81). So a flush touches one child and moves a guaranteed minimum batch.
  - Shortcut: "a series of keys are inserted that will completely fill one leaf... these messages should flush directly to the leaf" (line 44), a heuristic to skip intermediate nodes.
  - Split: "When a leaf node becomes too full, it splits, just as in a B-tree. Similar to a B-tree, when an interior node gets too many children, it splits and the messages in its buffer are distributed between the two new nodes" (line 41). Merge and root change: not described.
  - Search: "answering a query also means checking the buffers in nodes on this path for messages, and applying relevant messages before returning the results... if a query for key k finds an entry (k,v) in a leaf and a tombstone message for k in the buffer of an internal node, then the query will return 'NOT FOUND'... the query need not update the leaf" (line 55). The invariant: "Messages addressed to a key k are guaranteed to be applied to k's leaf or in some buffer along the root-to-leaf path towards key k" (line 45).
  - Parameter: point query costs a factor 1/epsilon more (a tree taller by 1/epsilon); inserts cost divided by B^(1-epsilon); epsilon = 1 is a B-tree, epsilon = 0 a buffered repository tree (lines 64-65, 118-120). Practical choice: "nodes are approximately 4 MB, and the branching factor ranges from 4 to 16. As a result, the B-epsilon-tree can always flush data in batches of at least 256 KB" (line 136).
  - Compared with the LSM-tree: LSM can be tuned to "the same insertion complexity", but a range query must visit every level, and upserts spoil Bloom filters because a message "may be present in every level" (lines 183-190; paper's claim, its own side).
- Assumes: nodes are large (about 4 MB) so the I/O cost of a flush is amortised; one writer thread per node in the reference code is not stated; messages are small relative to the batch.
- With sessions as nodes (reasoned): the vocabulary is the most useful result: a "message" can be an insert, a delete or an upsert that does not need the old value, and the upsert is the one that fits a model session: "update this finding" without reading it first, applied when the message reaches the node. The read-modify-write pattern "will be bound to the speed of a query" (line 140): the same holds for a parent that must read a child's report before it can write the next brief. The read rule (check every buffer on the path) means a coordinator that wants the current state of a leaf must read all briefs not yet delivered on the way down, so briefs in flight need to be listed in files, not held in a session. The ratio law is directly usable: batch size = B^(1-epsilon), read cost x 1/epsilon, with B replaced by the number of messages that fit one node's window. Small work: with a few messages the fixed rewrite cost of a node is paid for nothing (the claim needs a full buffer). Very large work: the claim is strongest here.
- Status: quoted (the article is a summary-level introduction by the authors of the structure; measured numbers cited from BetrFS, see P4).

### P4. William Jannen, Jun Yuan, Yang Zhan, Amogh Akshintala, John Esmet, Yizheng Jiao, Ankur Mittal, Prashant Pandey, Phaneendra Reddy, Leif Walsh, Michael Bender, Martin Farach-Colton, Rob Johnson, Bradley C. Kuszmaul, Donald E. Porter, "BetrFS: A Right-Optimized Write-Optimized File System", FAST 2015
Read from: https://www.usenix.org/system/files/conference/fast15/fast15-paper-jannen_william.pdf (USENIX open access). Folder: `R:papers/tree/writes-betrfs/`. Pages read: abstract, section 2 (the B-epsilon-tree), the file-system schema (upserts), section 5.1 and 5.2, microbenchmarks and the application benchmarks; not the klibc port section.
- Problem: file systems do small writes badly (one I/O per microwrite) and write-optimised indexes seemed to give fast small writes or fast scans, not both.
- Mechanism (two lines): a kernel file system whose metadata and data live in two B-epsilon-trees; every small write is an upsert message into the root buffer.
- Measured gain: "On one microdata benchmark, BetrFS provides more than 4x the performance of ext4 or XFS... an in-place rsync of the Linux kernel source realizes roughly 1.6-22x speedup over other commodity file systems" (plain.txt line 20). Microwrites: "1,000 random 4-byte writes within a 1GiB file, followed by an fsync()... BetrFS was two orders of magnitude faster" (lines 414-421: 0.17 s against 11.60, 11.71, 11.60, 14.75 s for the four other file systems; on a 4-core machine, 1 GiB file). Honest limit in the paper: it still loses "on some operations such as deletes, directory renames, and large sequential writes" (line 20). `quoted`.
- Operations: worked model, lines 148-152: "1TB of data, with 128-byte keys and records... B-epsilon-tree has branching factor of 10 and nodes of size 1MB... each item is therefore involved in 14 I/Os... each flush moves 1MB/10 = 100kB of data, in other words, 100 items. Thus, the average per-item cost of flushing an item to a leaf is 14/100. Since a B-tree would require 2 I/Os for each item, the B-epsilon-tree is able to insert data 2/(14/100) = 14.3 times faster than a B-tree. As key-value pairs get smaller... this speedup factor grows." That is a ratio law: gain = (cost per item in a B-tree) divided by (levels x 2 divided by items per flush). Upsert: "(k, (f, delta))", applied when it reaches the leaf or when a flush finds the old value in the child's buffer (lines 155-161). The paper also warns that the cache must not turn writes into reads: FUSE "can transform write-intensive into read-intensive workloads... These searches can choke a write-optimized data structure, where insertions are two orders of magnitude faster than searches" (lines 304-306), and that writes that hit one block hundreds of times are better absorbed in cache (line 300). Cleaner threads "flush pending data from 5 internal nodes per second" (line 541): the flush is also done in the background, not only when full.
- Assumes: large nodes (1 MB in the model, 4 MB in the system), small items, a mostly-write workload, disks where a seek dominates.
- With sessions as nodes (reasoned): two useful warnings. (a) A write-optimised structure turns into a slow one when something around it reads before every write (FUSE did): a parent that reads a child's full state before every brief loses the gain, which agrees with our token measurement that the long coordinator window, not file reads, is the sink (library `project-token-bottleneck`; not re-read here). (b) The gain formula 14.3 uses items per flush (100) against the number of levels (7): the gain is a ratio of batch size to depth, and falls to nothing when the batch is one item. Small work: the example is 1 TB; at small scale the tree has one level and the ratio is 1. Large work: the ratio improves as items get smaller.
- Status: quoted.

### P5. Patrick O'Neil, Edward Cheng, Dieter Gawlick, Elizabeth O'Neil, "The Log-Structured Merge-Tree (LSM-Tree)", Acta Informatica 33(4), 1996
Read from: https://www.cs.umb.edu/~poneil/lsmtree.pdf (the author's open copy). Folder: `R:papers/tree/writes-oneil-lsm/`. Pages read: sections 1 to 3 (design, cost, size ratios, examples), the start of 4 (concurrency and recovery); not section 5 on temperature-based choices or section 6 in full. Line numbers are of `plain.txt`.
- Problem: a history table is inserted into at a high rate; a B-tree index costs one disk-arm use per insert; "the Five Minute Rule" makes memory-resident indexes too expensive.
- Mechanism (two lines): inserts go to a memory tree C0 with no I/O; a "rolling merge" moves ranges of entries into a disk tree C1 (and further into C2, ... CK) in multi-page blocks, defer and batch.
- Measured gain: "Typically the product of the two ratios will give a cost ratio improvement of nearly two orders of magnitude" (plain.txt line 189); "at an order of magnitude lower cost" in the introduction (line 22). Formula: "COST_LSM-ins / COST_B-ins = K1 * (COST/COSTP) * (1/M)" with "K1 ... approximately 0.67" (lines 188-189), where COST/COSTP is the ratio of the cost of a page in a multi-page block to a random page I/O ("about 1/10", line 141) and M is the average number of C0 entries inserted into one C1 leaf per merge. Example: ratio 0.02 = 1/50 (line 190). Analytic, with worked costing in dollars (lines 332-340); no running system. `quoted`.
- Operations:
  - Size ratios: "to minimize the total I/O rate H of a multi-component LSM-tree, with fixed SK, S0, and insertion rate R, we size intermediate components in a geometric progression between the smallest and largest" (line 237); "Theorem 3.1... the total page I/O rate H to perform all merges is minimized when the ratios r_i = S_i/S_{i-1} are all equal to a common value r... H = (2R/Sp) * (K * (1 + r) - 1/2)" (lines 242-250); "useful values of r_i are fairly large, say 20 or more" (line 303). So write cost per entry is about 2(1+r)/Sp per level, linear in r and in the number of levels K, and K falls as r rises: the product K*r is minimised at an equal ratio.
  - Reads: "first the C0 tree and then the C1 tree is searched... In LSM-trees with more than two components, there may also be an I/O overhead" (line 82). Finds that must be answered at once stay costly: "Only finds that require immediate response remain relatively costly" (line 22). A find that hits an early component can stop (line 83).
  - Messages: deletes are "delete node entries" that "migrate out to larger components during merge and annihilate the associated entry" and "find requests must be filtered through delete node entries" (line 92). Predicate delete as a batch (line 93).
  - Concurrency and recovery: "Nodes are the unit of locking" (line 364); the cursor of one rolling merge may overtake another's (line 361); new blocks are written to new positions so old ones survive a crash (line 67), and a checkpoint with a log restart point gives recovery (lines 377-381). So merges are asynchronous and per component pair.
- Assumes: disk with a multi-page block cheaper per page than a random page (ratio about 1/10); memory for C0; a steady insert rate; entries rarely deleted before reaching the last component (line 235).
- With sessions as nodes (reasoned): the law "equal ratio between adjacent levels" is the ratio law this lane should carry: for a tree of sessions, each level holds a fixed multiple of the level above in work units, with the multiple chosen once. That law needs a cost per hand-over of a batch (a "multi-page I/O") against a cost per hand-over of a single item (a "random I/O"); for sessions the first is one brief covering many questions, the second is one brief per question, and the ratio is not recorded (our records give the cost of a session start only as a guess, `b1-0113`). Entries are never rewritten by an LSM's merge in place: new blocks go elsewhere and old ones stay until the merge commits, a recovery pattern that fits a session that can be killed. Small work: with S0 near S the whole tree is C0 and K = 1; no gain. Very large work: K grows with the log of S/S0 to base r. The LSM read cost of "every level" is the weak side: a coordinator asking "what is the state of X" must look at every level, which is the same as the buffer path of P3.
- Status: quoted (upgrades `x03-0707`).

### P6. Chen Luo and Michael J. Carey, "LSM-based Storage Techniques: A Survey", VLDB Journal 29 (2020); arXiv 1812.07527
Read from: https://arxiv.org/pdf/1812.07527. Folder: `R:papers/tree/writes-luo-carey/`. Pages read: sections 1 to 3.1 (the structure, merge policies, Table 1), the passages on write amplification and tuning (lines 590-760, 800-860), the concluding remarks on the RUM conjecture; not the sections on hardware, secondary indexes and application systems. Line numbers are of `plain.txt`.
- Problem: a map of the LSM-tree design space and its known trade-offs, for a reader choosing a policy.
- Mechanism (two lines): memory component flushed as an immutable sorted run; runs merged by one of two policies, leveling (one run per level) or tiering (up to T runs per level), with size ratio T between levels.
- Measured gain: a survey, no own measurement. Cost table, quoted: "Write: Leveling O(T * L / B), Tiering O(L / B); Point Lookup (zero-result): O(L * e^(-M/N)) and O(T * L * e^(-M/N)); ... Short Range Query: O(L), O(T * L); Space Amplification: O((T+1)/T), O(T)" (Table 1, lines 602-606; the symbols in the extraction are scattered, restored by me from the table's caption and the prose). Prose: "leveling is optimized for query performance and space utilization by maintaining one component per level. However, components must be merged more frequently, which will incur a higher write cost by a factor of T. In contrast, tiering is optimized for write performance by maintaining up to T components at each level. This, however, will decrease query performance and worsen space utilization by a factor of T" (line 668). `quoted`.
- Operations: write cost counted "for this entry to be merged into the largest level... For leveling, a component at each level will be merged T - 1 times until it fills up and is pushed to the next level. For tiering, multiple components at each level are merged only once and are pushed to the next level directly" (lines 306-318). Partitioned leveling (LevelDB): a merge picks one fixed-size file and the overlapping files of the next level, so the unit of merge is a file (lines 146-151). A message is a key with a sequence number and a delete marker (tombstone); the survey describes it in section 2.1 (not read in full here: `summary` for that sentence). A read checks the memory component and then every run, newest first.
- Assumes: write cost is I/O of page-sized blocks, memory large enough for the buffer, Bloom filters for point lookups.
- With sessions as nodes (reasoned): two ratios to carry. (a) leveling against tiering is a factor of T in write cost against a factor of T in read cost and in space: a tree where a parent merges every child's report into one summary at every level (leveling) costs T times more rewriting than one that keeps up to T reports per level and merges once (tiering); the choice is made by the read share. (b) The survey's own warning about methodology: "these improvements have mainly been evaluated against a default (untuned) configuration of LevelDB or RocksDB, which use the leveling merge policy with a size ratio of 10. It is not clear how these improvements would compare against well-tuned LSM-trees" (line 811): any gain we measure for one form must be compared with a tuned size ratio, not the default, which agrees with the owner's rule "test the best form of an idea". Small work: write cost O(T*L/B) with L = 1 is just one merge; the whole difference between policies vanishes. Very large work: L grows with log_T of the size, the factor T is what you control.
- Status: quoted for the table and the prose lines cited; `summary` for the sections not read.

### P7. Niv Dayan and Stratos Idreos, "Dostoevsky: Better Space-Time Trade-Offs for LSM-Tree Based Key-Value Stores via Adaptive Removal of Superfluous Merging", SIGMOD 2018
Read from: https://nivdayan.github.io/dostoevsky.pdf (the author's open copy). Folder: `R:papers/tree/writes-dostoevsky/`. Pages read: abstract, introduction, section 2 background, section 4 (lazy leveling, Fluid LSM-tree), the evaluation text (section 5); not the appendices. Line numbers are of `plain.txt`.
- Problem: all mainstream LSM designs merge equally at every level, which pays full update cost where it buys little read or space benefit.
- Mechanism (two lines): lazy leveling merges only at the largest level (tiering at smaller levels, leveling at the largest); Fluid LSM-tree adds two knobs, K (runs allowed in each smaller level) and Z (runs at the largest), so that K = 1 and Z = 1 is leveling, K = Z = T - 1 is tiering, K = T - 1 and Z = 1 is lazy leveling (line 1355).
- Measured gain: the text gives a ratio law, not a single number: "Lazy Leveling ... (1) improves the cost complexity of updates, (2) maintains the same complexity for point lookups, long range lookups, and space-amplification, and (3) provides competitive performance for short range lookups" (line 815); "An updated entry with Lazy Leveling participates in O(1) merge operations per level across Levels 1 to L-1 and in O(T) merge operations at Level L. The overall number of merge operations per entry is therefore O(L + T), and we divide it by the block size B" (lines 1212-1214), against O(T*L) for leveling (line 350). Evaluation: "inserting 1TB of data to an empty database. Every entry is 1KB" on "a RAID of 500GB 7200RPM disks, 32GB DDR4 main memory, 4 2.7 GHz cores" (lines 1977 and 2185); "No Single Merge Policy Rules... As the proportion of lookups increases, the best fixed policy changes from tiering to Transition 1, then to Lazy Leveling, then to Transition 2, and finally to leveling" (line 2190); "update cost with Lazy Leveling scales at a slower rate than with leveling as the data size grows" (line 2192). The numeric throughput gain is only in figures (not extracted), so I do not state it. `quoted`.
- Operations: the Fluid rule: "K = 1 and Z = 1 give leveling" etc. (line 1355); transition from lazy leveling to tiering by "merging less frequently at the largest level by increasing Z" (line 1357). A merge recurses to level i if levels 0 to i - 1 are all at capacity (appendix, line 2616); scheduling of merges is in the appendix (not read).
- Assumes: a read-skew-insensitive worst-case workload; memory for filters; a workload mix known or estimated so the cost model can choose K, Z, T.
- With sessions as nodes (reasoned): the strongest transferable idea is "merge less at the small levels, because the work there is repeated and cheap to lose, and pay the merge once at the largest level". For sessions the analogue is: do not rewrite a summary at every level of the tree each time a leaf reports; keep several reports in a small level and merge them once when the level fills. The result is a ratio: update cost O((L + T)/B) rather than O(T*L/B), the saving is the factor L, i.e. the depth. The model needs a workload mix to tune (the read to write ratio of questions); we have it recorded only in part. Small work: with L = 1 the two forms are identical. Very large work: L large, the saving grows with depth, as the paper says in line 2192.
- Status: quoted (numbers from figures not read).

### P8. Niv Dayan, Manos Athanassoulis, Stratos Idreos, "Monkey: Optimal Navigable Key-Value Store", SIGMOD 2017
Read from: https://nivdayan.github.io/monkeykeyvaluestore.pdf. Folder: `R:papers/tree/writes-monkey/`. Pages read: abstract, introduction, section 3 (design space, cost table, tuning of size ratio and policy); not the Bloom-filter derivations or the evaluation beyond the setup. Line numbers are of `plain.txt`.
- Problem: an LSM-tree has a fixed trade between update, lookup and memory; filters, size ratio, merge policy and buffer size were tuned separately and badly.
- Mechanism (two lines): allocate Bloom filter bits across levels so the sum of false-positive rates is smallest (exponentially lower rates at smaller levels); and a closed-form model that picks policy and size ratio for a workload.
- Measured gain: "Monkey improves lookup latency by 50% - 80% in these experiments" (line 39), "reduces lookup latency by an increasing margin as the data volume grows (50% - 80% for the data sizes we experimented with)" (line 7), implementation on LevelDB; set-up: 1 GB of 1 KB entries, uniformly random keys, 500 GB 7200 RPM disk, 32 GB memory, 4 cores (lines 1471-1473, 1557-1562). `quoted`.

## What these papers say about the questions asked

1. Write cost against read cost against batch size, as ratios (all `quoted` above):
   - B-epsilon tree (P3, P2): insert cost divided by B^(1-epsilon) (the batch size moved by one flush); point query cost multiplied by 1/epsilon (extra depth). Worked: B = 1024, epsilon = 1/2: 16 times faster inserts, 2 times the point-query I/Os (P3).
   - LSM (P5, P6, P7, P8): leveling write O(T*L/B), tiering O(L/B), lazy leveling O((L+T)/B); reads and space move the other way by a factor T (P6); with equal ratio r between levels the merge I/O rate is H = (2R/Sp)(K(1+r) - 1/2) (P5).
   - Batching gain: cost ratio against a B-tree = (cost of a block I/O against a random I/O) x (1/entries merged per leaf) (P5); BetrFS shows the same law as items per flush against depth: 14.3 times (P4).
   - Lower bound (P2): for comparison-based structures the trade cannot be beaten; the bounds are tight for a wide range of parameters.
2. When a buffer flushes and how many children one flush touches: Arge: when the buffer holds m/2 blocks, the whole buffer to all children (P1). Brodal and Bender: when full; to one child, the one with most pending messages, with a guaranteed minimum of (B - B^epsilon)/B^epsilon = B^(1-epsilon) messages (P2, P3). LSM: when a component exceeds its threshold; a merge of a range or a file, not a push (P5, P6). BetrFS adds a background cleaner flushing 5 internal nodes a second (P4).
3. What a message is: insert, delete (tombstone) and, in B-epsilon trees, upsert (a function and its argument, applied later) (P3, P4); Arge: element plus timestamp plus insert/delete flag (P1); LSM: delete node entries that annihilate on merge (P5).
4. How a read finds messages not yet pushed down: read every buffer on the root-to-leaf path and apply the messages in timestamp order (P3 line 55, P2 lines 478-482); for LSM, read newest to oldest component (P5 line 82); for Arge's buffer tree, no online read, the answer is produced lazily when the query message arrives (P1 line 312).
5. Structure change under buffers: always empty the buffer first (Arge, lines 439-441), so splits and fuses never see messages in the node; B-epsilon: a split divides the buffer between the two new nodes (P3 line 41).
6. What none of these papers address: a node that is a model session (minutes per unit, window bound, cannot be paused, 3 to 16 writers). None of the eight is about concurrent writers to one tree except P5's per-node locking (line 364). Concurrent structure change is the `concurrent` lane.
