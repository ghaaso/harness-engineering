### O10-F1 [P1/gap] The field APK cannot produce the per-phone BEFORE counts the proof needs
cite=- | skeptic=n/a (gap/design) | conf=0.85 effort=M apk=unknown
CLAIM: On the field APK, the only queue state a person can read is parked punches/crossings (ClockScreen) and the jobs-outbox queued/failed totals (banner, across all techs). Unsent pings, unsent travel samples, pending media and pending-but-unparked crossings have no UI consumer, so the BEFORE manifest for step 6 cannot be taken without a new build.
WHEN: Any phone running the field APK, before the update; for example, a phone holding queued pings from an airplane-mode stretch and an unparked crossing.
    - technician-app/src/features/attendance/useAttendance.ts:86 — const [fp, fpr] = await Promise.all([failedPunches(), failedPresence()]); (the only attendance counts rendered)
    - technician-app/src/lib/useOutboxSync.ts:24 — setCounts(await outboxCounts());

IMPACT: Without app support, 'nothing was lost' cannot be proven for four queues. For a K=no phone, the BEFORE record is reduced to photographs of two screens.

### O10-F2 [P1/defect/INV] Rows parked during the outage stay parked after any classifier fix; recovery is per-row Retry only
cite=LOCATED | skeptic=NO VERDICT | conf=0.9 effort=S apk=unknown
CLAIM: Each sync skips parked rows (pendingPunches/pendingPresence filter on failed_reason; the flush skips status 'failed'). Only per-id retryPunch/retryPresence/retryItem un-park them. So an update that only reclassifies the edge 404 as transient drains none of the months of 'rejected (404)' rows, and each would need a manual tap, which also lands at server_now under the 24 h ceiling.
WHEN: Update installed with origin-aware classification but no un-park migration; the phone holds punches/crossings/outbox items parked as 'rejected (404)'.
    - technician-app/src/features/attendance/queue.ts:100-101 — filter((i) => !i.done && i.failed_reason === undefined)
    - technician-app/src/features/attendance/presenceQueue.ts:88-89 — same filter for crossings
    - technician-app/src/lib/outboxSync.ts:202 — if (item.status !== "queued") continue; // failed items wait for the user
    - technician-app/src/features/attendance/queue.ts:128-135, presenceQueue.ts:121-128, outbox.ts:214-221 — retry is by single id
IMPACT: The drain stalls on exactly the outage data it exists to recover. A tech mass-tapping Retry before the ceiling is widened stamps months of punches into today (O3-F4).
FIX: Run a one-time migration at first launch of the new versionCode, before any sync and after the manifest snapshot. It resets to queued every punch/presence/outbox row whose reason matches /^rejected \(\d{3}\)$/ (no app detail), or /^gave up after \d+ attempts \(server 5\d\d\)$/ with failed_at inside the outage window, and resets parked pending-media attempts. Rows with an app detail stay parked. Pin it with unpark.test.ts.

### O10-F3 [P1/risk/INV] A 503 stub on the old hostname parks every queued item after five flushes
cite=MOVED | skeptic=NO VERDICT | conf=0.9 effort=S apk=unknown
CLAIM: Every non-OK response becomes an ApiError, and each 5xx ApiError bumps attempts and parks the item at MAX_ATTEMPTS=5. With the 4 s to 60 s outbox backoff and the 3 s to 60 s punch backoff, a '503 maintenance' stub parks queued job writes and punches one by one within minutes, while a 503 batch of pings/travel is kept. So the 503 stub the brief proposes is not safe.
WHEN: The old hostname is reclaimed and made to answer 503 to everything while field APKs with queued items are online.
    - technician-app/src/lib/api.ts:153-157 — if (!response.ok) { ... throw new ApiError(method, path, response.status, text); }
    - technician-app/src/lib/outboxSync.ts:226-231 — if (e instanceof ApiError) { const attempts = await bumpAttempts(item.id); if (attempts >= MAX_ATTEMPTS) { await markFailed(...)
    - technician-app/src/features/attendance/sync.ts:206-213 — same bump/park for punches
    - technician-app/src/features/attendance/presenceSync.ts:209-216 — same bump/park for crossings
IMPACT: The stub turns 'kept and retried' into 'parked, waiting for a manual tap' for the whole fleet. It does exactly the harm it was meant to prevent.
FIX: If the old host is controlled, use a hang stub: accept, send no bytes for at least 20 s, then close. The client's 15 s abort becomes a non-ApiError ('timed out'), which every queue treats as connectivity, with no count. Or proxy the host to the recovered backend only in the K=no branch.

### O10-F4 [P1/risk/INV] Any 2xx JSON or 204 from the old hostname deletes queued items as 'landed'
cite=MOVED | skeptic=NO VERDICT | conf=0.9 effort=S apk=unknown
CLAIM: request() treats any OK response as success: 204 returns undefined, and any parseable JSON body returns as the result. The jobs flush then removes the item, presence/ping/travel mark it done and prune it, and nothing checks that the body is the expected row. A placeholder or health stub answering 200 {} or 204 on every path silently erases the fleet's queues.
WHEN: The old hostname is pointed at any service that answers 2xx with a JSON body, or 204, for unknown paths (for example a generic health stub, or a catch-all route).
    - technician-app/src/lib/api.ts:158-159 — if (response.status === 204) return undefined as T; return (await response.json()) as T;
    - technician-app/src/lib/outboxSync.ts:210-211 — await reconcile(await send(item)); await removeItem(item.id);
    - technician-app/src/features/attendance/presenceSync.ts:185-200 — await attendanceApi.recordPresence(...); await markPresenceDone(...); settled.push
    - technician-app/src/features/attendance/pingSync.ts:141-157 — recordPings then markPingsDone(ids)
IMPACT: Irreversible, silent loss of every queue on every phone that reaches the stub, including cash records in the outbox.
FIX: Protocol rule: the old host may only hang (timeout) or proxy to the real backend; never 2xx/204 from anything else. In the update, require the app-origin marker header on a 2xx before treating a write as landed.

## Challenges to settled facts
- O3-F8 (failing_condition): set_pin does NOT bump token_version, so a PIN reset never 401s a phone. Only revoke_sessions does. The failing condition 'token_version bump via set_pin' is wrong; the live-tap 401 loss still holds for expired tokens and revoke_sessions.
    - backend/app/features/identity/service.py:125-128 — Deliberately does NOT bump token_version
    - backend/app/features/identity/service.py:149 — tech.token_version = (tech.token_version or 0) + 1 (revoke_sessions only)
- O3 design ('every token expired (30 days)'): Token expiry after revival depends on the unknown outage start (H6). A token issued less than 30 days before revival stays valid if the old JWT secret is reused, and a fresh DB has the same ids at token_version 0. Rotating FIXFLOW_JWT_SECRET is what makes re-login deterministic for every phone, and in the update branch it also keeps headless tasks from draining before the manifest snapshot.
    - backend/app/core/config.py:154 — jwt_expire_minutes: int = 60 * 24 * 30
    - backend/app/features/identity/service.py:110-115 — create_access_token(tech_id=..., token_version=tech.token_version or 0)
- Brief step (1) '503 stub': A 503 stub is not safe. Every 5xx ApiError counts toward MAX_ATTEMPTS and parks the item after 5 flushes. The safe old-host behaviours are a hang longer than 15 s (a client timeout, i.e. connectivity) or a proxy to the real backend. Any 2xx/204 deletes items.
    - technician-app/src/lib/outboxSync.ts:226-231
    - technician-app/src/features/attendance/sync.ts:206-213
