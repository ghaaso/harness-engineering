### O3-F1 [P1/defect/INV] Online job writes against the dead edge were refused at tap time, never queued
cite=LOCATED | skeptic=CONFIRMED -> P2 | conf=0.9 effort=S apk=unknown
CLAIM: When NetInfo reports connected and the API answers a non-FastAPI 404, sendOrQueue rethrows instead of enqueuing. So every job write tapped online during the outage (create, depart/arrive punch, customer pin, completion, payment) existed only on screen.
WHEN: Phone online; config.apiUrl answers Railway's edge 404 (both documented URLs since prod died); the tech taps Create job / START TRAVEL / ARRIVE / Save pin.
    - technician-app/src/lib/outboxSync.ts:267-271 — only isConnected === false enqueues without trying
    - technician-app/src/lib/outboxSync.ts:287 — if (isDefinitiveRejection(e) || isAuthFailure(e)) throw e;
    - technician-app/src/lib/syncClassification.ts:18 — DEFINITIVE_4XX = new Set([400, 403, 404, 409, 422])
    - technician-app/src/features/jobs/create-job/CreateJobWizard.tsx:164-171 — Alert 'Couldn't create the job' then return (nothing persisted, voice notes not queued)
IMPACT: For months the offline-first engine behaved as online-only for jobs. No intake, travel, arrival or bill could be recorded unless the phone was in airplane mode, and even then the flush parks it (F14). A self-hosted backend behind Cloudflare or a captive portal returning 403/404 HTML will cause the same failure.
FIX: Classify by origin (design step 1): a 4xx without the app marker is connectivity, so sendOrQueue enqueues it. A 401 on a live tap also enqueues (F8).
SKEPTIC: I traced the path myself and it holds. In technician-app/src/lib/api.ts:115-118, request() throws ApiError(status) for every non-OK response. Nothing checks whether a 404 came from FastAPI (a JSON body with a `detail` key) or from Railway's edge. In outboxSync.ts:267-271, sendOrQueue only queues without trying when NetInfo says isConnected === false. Otherwise it calls send(), and at :287 it rethrows any isDefinitiveRejection error. syncClassification.ts:18 puts 404 in DEFINITIVE_4XX, so an edge 404 is rethrown and enqueue (:290) never runs. I checked every caller of sendOrQueue: CreateJobWizard:164-171 (Alert, then return before queueVoiceNotes), TravelScreen sendPunch:182-185 (returns false, so startJobTravel never runs), TravelScreen savePin:277-278, CompleteJobScreen:227-237, ArrivalJobWizard:242-248, ArrivalJobBillScreen negotiate/payment catches, JobDetailScreen note/ready/transition/void, and closeJobWithVideo:121. All of them catch and show an error. None of them queues. I probed the preview URL baked into eas.json:21 live. Both POST /api/jobs and GET /api/health return HTTP 404 with body {"status":"error","code":404,"message":"Application not found"}. That body has no `detail` key, so the tech sees "rejected (404)". No commit since 906b990 touches this path: a31924a only changed eas.json env, 24184b2 only the consent default, and da988e2 the completion guards. One scoping note: the production profile's URL (api.fixflow.example) fails at DNS with a TypeError, not an ApiError, so those writes would queue. That URL is outside the stated failing condition, which needs the URL to answer a 404, so this does not narrow the claim. I rated it P2, not P1, for two reasons. First, the failure is loud, not silent: every site shows an Alert or error text, and ArrivalJobWizard keeps its AsyncStorage draft on the throw path. Second, queuing alone would not have saved these writes. flushOutbox (outboxSync.ts:218-221) treats the same edge 404 as definitive and parks the item as failed at the first flush, so a fix has to tell the two kinds of 404 apart in both paths. The real harm is that taps made during the outage leave no durable record, and punches and their timestamps are lost unless the tech taps again later.
SETTLE: Already settled by code trace plus live probe. To reproduce: write a Jest test in outboxSync.test that mocks NetInfo.fetch to {isConnected:true} and jobsApi.create to reject with new ApiError('POST','/api/jobs',404,'{"status":"error","code":404,"message":"Application not found"}'). ### O3-F2 [P1/defect/INV] Parked punches make dutyStatus stop on-duty pings after every landed clock-in
cite=MOVED | skeptic=CONFIRMED | conf=0.85 effort=S apk=unknown
CLAIM: dutyStatus picks the latest of ALL the tech's local punches, parked ones included, and pruneSettled removes only done punches. Once a fresh clock_in lands and is pruned, a months-old parked punch becomes the 'latest': a clock_out makes the tech off duty, a clock_in makes the session expired. Either way the sampler stops, and coverage stays dead every shift until the tech discards every parked punch.
WHEN: Tech has at least one parked punch (every tech who punched during the outage), clocks in against a live backend, the punch syncs and is pruned, and the next location fix arrives.
    - technician-app/src/features/attendance/pingTracker.ts:118-124 — mine = (await loadQueue()).filter(tech) — no done/failed filter; latest by device_time decides; kind != clock_in -> off duty; aged -> expired
    - technician-app/src/features/attendance/sync.ts:236-249 — pruneSettled removes only i.done
    - technician-app/src/features/attendance/queue.ts:100-112 — parked = failed_reason set, never done
    - technician-app/src/features/attendance/pingTracker.ts:271-282 — expired -> autoStopExpiredDuty; !onDuty -> stopDutyPings
IMPACT: After revival the field APK records no on-duty pings, so coverage reads no_data (S12, nothing alerts on it). Techs with a parked clock_in get a 'duty auto-stopped' notification every day. The fix the tech is offered (Retry) corrupts attendance days (O3-F4).
FIX: In dutyStatus, consider only punches that are !done && failed_reason === undefined; otherwise fall to the duty cache. Share one pure 'latestLivePunch' helper with useAttendance's clockedIn.
SKEPTIC: I followed the path from clock-in to the next location fix. punch() enqueues a fresh clock_in with device_time=now, starts duty pings and calls syncNow. syncOne marks the punch done once the server records it and its selfie has settled. pruneSettled then removes it, because it removes only done items. After that, the tech's queue holds only parked punches: failed_reason set, done false, device_time older than the fresh punch.

dutyStatus loads the whole queue with loadQueue(), not pendingPunches(), and filters only by tech_id. So the latest parked punch decides. If it is a clock_out, the result is off duty and handlePingUpdate calls stopDutyPings and drops the fix. If it is a clock_in older than 14h, the session is expired and autoStopExpiredDuty runs. Either way the sampler stops. ensurePingTracking reads the same dutyStatus, so it will not re-arm on foreground or launch.

Parked punches are only removed when the tech acts (discardPunch, or retryPunch followed by a successful sync), so this happens again every shift. The only gap I found is the edge case where every remaining parked punch is a clock_in younger than 14h. In that case the session runs and then ends early at 14h after that punch, so the failure does not trigger immediately. Remediation is by discard or a successful retry, not by discard alone.

Severity stays P1. It fails closed on privacy, but ping coverage is silently lost for every shift of every tech whose punches were parked during an outage. A 404 outage parks every punch on the first attempt. Those techs also get a spurious "forgot to clock out" notification every shift.
CORRECTED: The claim holds as written, with two refinements. (1) A parked clock_in less than maxDutyHours (14h) old does not stop the sampler straight away. It ends the session early instead, 14h after the parked punch's device_time. A parked clock_out of any age, or a parked clock_in older than 14h, stops the sampler after every landed clock-in. (2) Recovery means clearing every parked punch, either by discarding it or by retrying it successfully, since a landed retry is marked done and pruned. In the clock_in case there is also a side effect: the "forgot to clock out" notification fires again every shift, because startDutyPings clears autoStopNotifiedAt whenever a new session starts.
SETTLE: Add a Jest case to pingTracker.test.ts. Seed loadQueue with one punch for the signed-in tech: {kind:"clock_out", device_time: 90 days ago, failed_reason:"rejected (404)", done:false}. Seed the duty cache as {clockedIn:true, startedAt: now}. Call handlePingUpdate([fix]). Expect stopLocationUpdatesAsync to be called and enqueuePing not to be called. Run it again with a parked clock_in 90 days old and expect notifyDutyAutoStopped to be called.
