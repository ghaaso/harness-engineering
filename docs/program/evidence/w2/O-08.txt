### O08-F01 [P1/risk/INV] Boot guard against the dev JWT secret is Railway-only; off Railway it is open unless FIXFLOW_ENVIRONMENT=production is set
cite=LOCATED | skeptic=CONFIRMED | conf=0.9 effort=S apk=no
CLAIM: On any host without the RAILWAY_ENVIRONMENT variable and without FIXFLOW_ENVIRONMENT=production, the backend boots and serves with the public repo default jwt_secret, so anyone can forge a manager bearer token.
WHEN: Self-hosted compose omits FIXFLOW_ENVIRONMENT=production (default is 'dev') and omits FIXFLOW_JWT_SECRET: assert_safe_for_production() is a no-op and ops config_presence reports status 'ok' (it degrades only when is_production). Forge an HS256 token with sub=m1, ver=0 (token_version default 0, a seeded manager id per S14) signed with the dev secret; get_current_principal then accepts it because it checks only the live row (deps.py:46-57).
    - backend/app/core/config.py:218-221 — is_production = environment.lower()=="production" or bool(os.getenv("RAILWAY_ENVIRONMENT"))
    - backend/app/core/config.py:223-231 — guard raises only if is_production and jwt_secret == DEV_JWT_SECRET
    - backend/app/core/config.py:151 and :15 — jwt_secret default DEV_JWT_SECRET, a literal in the repo
    - backend/app/features/ops/health.py:121 — config component is 'degraded' only when settings.is_production and the secret is not overridden
IMPACT: Full manager takeover of an internet-facing API (payments, payroll, staff ledger, PIN reset) on the first self-hosted deploy that forgets one env var. Fail-open on exactly the platform change this program makes.
FIX: (1) compose: FIXFLOW_ENVIRONMENT=production and FIXFLOW_JWT_SECRET: ${FIXFLOW_JWT_SECRET:?required} so compose refuses to start if empty. (2) code, small PR: make the guard also trip when jwt_secret is the dev default and the database host is not localhost, or invert so the guard is on unless FIXFLOW_ENVIRONMENT=dev. (3) make the deploy smoke test assert /api/ops/health config component says jwt_secret_overridden.
SKEPTIC: I traced the path myself and it holds. In config.py, DEV_JWT_SECRET is a repo literal (line 17), jwt_secret defaults to it (151) and environment defaults to "dev" (160). is_production (218-221) is true only when environment.lower()=="production" or RAILWAY_ENVIRONMENT is set. assert_safe_for_production (223-232) raises only when is_production is true AND the secret is the dev default. Its only caller is main.py:251 in create_app(), so on a host with neither variable the app boots silently. health.config_presence (health.py:120-122) returns "degraded" only when settings.is_production is true; otherwise it returns "ok" even though the detail string lists jwt_secret_overridden as unset. decode_access_token (identity/security.py) is a plain jwt.decode(token, settings.jwt_secret, algorithms=["HS256"]). get_current_principal (deps.py:35-61) checks only that the row exists and is active and that ver == token_version, and it takes role from the live row. Migration 0012 seeds id "m1" with role manager and active True, and models.py:65-67 defaults token_version to 0. A fresh self-hosted DB therefore accepts HS256 {sub:"m1", ver:0} signed with the public literal as a full manager, and require_manager passes. No migration deactivates or re-keys m1. In the git log, the config.py change in da988e2 predates the cited lines and does not touch the guard. The only shipped compose file (docker-compose.yml) sets only FIXFLOW_DATABASE_URL and is labelled a local dev stack. An operator who reuses it for the planned home-server self-host (docs/ORCHESTRATION-DESIGN-2026-10.md Q4/Q7) gets exactly the failing condition. The Dockerfile comment also names Render/Fly as targets, where the Railway auto-detect does not apply. On the narrower reading, the claim needs both omissions (no FIXFLOW_ENVIRONMENT=production and no FIXFLOW_JWT_SECRET), and current production on Railway is protected by the RAILWAY_ENVIRONMENT auto-detect. I keep P1 because the impact is total (forged manager) and the stated next deployment target falls outside the auto-detect. A related gap I found but did not test: backend/.env.example ships `FIXFLOW_JWT_SECRET=` empty. pydantic-settings keeps empty strings by default (env_ignore_empty=False), so a copied .env would give jwt_secret="", which is != DEV_JWT_SECRET. That would pass the guard and show as "overridden" in health even on Railway. I could not confirm this because no Python interpreter is available here.
SETTLE: Run a dynamic test from backend/: unset RAILWAY_ENVIRONMENT, FIXFLOW_ENVIRONMENT and FIXFLOW_JWT_SECRET, then call `python -c "from app.main import create_app; create_app()"`. It should return without raising. Next, against a DB migrated to head, send GET to a manager-only endpoint with Authorization: Bearer jwt.encode({'sub':'m1','ver':0}, 'dev-insecure-secret-change-me-in-production-32b', algorithm='HS256'). Expect 200, and expect GET /api/ops/health to report config status "ok". To check the empty-secret gap, set FIXFLOW_JWT_SECRET= (empty) with FIXFLOW_ENVIRONMENT=production and confirm create_app() does not raise.

### O08-F02 [P1/risk/INV] First successful nightly backup on the new stack prunes every pre-death dump older than 30 days, including the dump just restored from
cite=LOCATED | skeptic=PARTIALLY | conf=0.9 effort=S apk=no
CLAIM: The first run of run_db_backup on a self-hosted backend that shares the old bucket and the default backup_prefix deletes every fixflow-db-*.dump whose filename timestamp is older than 30 days, which is every dump from before the outage.
WHEN: Recovery case (a) or (b): the new backend is pointed at the same R2 bucket with FIXFLOW_BACKUP_PREFIX=backups/db/ (the default). Production died more than 30 days ago (last commit 2026-08-03, today 2026-11-01), so the newest old dump is older than the cutoff. At 02:30 Asia/Karachi the job uploads a fresh dump, then lists the prefix and deletes all stale keys. If the restore had a defect that is found later, the original dump is gone.
    - backend/app/core/backup.py:67-76 — keys_to_prune returns keys whose stamp is older than now - retention_days
    - backend/app/core/backup.py:125-132 — after upload, stale = keys_to_prune(list_keys(settings.backup_prefix)) and each stale key is store.delete()d
    - backend/app/core/config.py:197-202 — backup_enabled default True, retention 30, prefix backups/db/
    - docs/RUNBOOK-BACKUPS.md:128 — the newest pre-death dump known in the repo is fixflow-db-20260802T023008Z.dump, already older than 30 days
IMPACT: The only off-box copy of the pre-outage ledger, payroll history and the staff_ledger_chain evidence can be destroyed by the new stack's own housekeeping the first night, before the restore has been verified in use.
FIX: Before the first scheduler run: copy all backups/db/ objects to a prefix the pruner never lists (e.g. archive/pre-selfhost/), AND set FIXFLOW_BACKUP_PREFIX to a new prefix (backups/db-selfhost/) or FIXFLOW_BACKUP_ENABLED=false until the restore is signed off. Optionally download the dumps to the owner's laptop and a second provider.
SKEPTIC: I traced the path from the cited lines. The lifespan registers run_db_backup daily at 02:30 by default. run_db_backup uploads, then lists the whole backups/db/ prefix (paginated) and deletes every key whose filename stamp is older than now-30d. No positive counter-evidence exists. There is no keep-latest-N rule, no guard against dumps from another deployment, no dry-run, and no commit since 906b990 changed the behaviour (da988e2 only threadpooled the calls). So the code behaviour in the claim is confirmed. One premise is not: that "every dump from before the outage" is older than the cutoff on the first run. The claim rests on "Production died more than 30 days ago (last commit 2026-08-03)". A last-commit date is not the date the old Railway scheduler stopped taking nightlies. The G1 record lists the unreachable period (H6) as open with W0. The runbook's 20260802 dump is only the newest one written into the repo. If the old backend ran into October, some old dumps survive the first run, but the same code removes them over the next nights. The irreversible loss of the original prod dump therefore holds in every case, within at most 30 days of the old backend's last run. I am narrowing the claim from "on the first run" to "on the first run if the old nightlies stopped more than 30 days earlier, otherwise over the following nights". I keep P1 because in recovery case (b) that dump is the only original copy. The new nightly backs up the restored DB, not the original, so a restore defect found later (a pg_restore error that looked benign, or a 17 to 16 load problem) could not be recovered from.
CORRECTED: The prune mechanism is real and nothing guards it. A new backend with default settings (enable_scheduler=True, backup_enabled=True, retention 30, prefix backups/db/, bucket job-media) runs at 02:30 Asia/Karachi. It uploads a fresh dump, lists backups/db/, and permanently deletes (R2 delete_object) every fixflow-db-<stamp>.dump stamped more than 30 days ago. There is no keep-at-least-N floor and no check for a foreign or old-stack dump. Nothing on the new stack keeps the old dumps. Whether the FIRST run deletes ALL of them depends on when the old Railway backend last ran its nightly job, and that is not established: H6, the unreachable period, is still with W0. The last commit date (2026-08-03) is not that date. If the old backend's last nightly ran more than 30 days before the new first run, every pre-outage dump is gone on night one, including the one restored from. If it ran more recently, the old dumps go one by one over the following nights, and all are gone 30 days after the old backend's last run. Either way, in recovery case (b) the original prod dump, the only copy, is deleted inside a short window. The restored state does survive as the new dump. What is lost is the ability to re-restore from the original if a restore defect turns up later.
SETTLE: Run `list_objects_v2(Bucket='job-media', Prefix='backups/db/')` read-only against the R2 bucket and take the newest fixflow-db-*.dump stamp. If it is older than the planned first 02:30 run minus 30 days, the first run deletes every old dump. If not, they go over the following nights. A unit test that calls keys_to_prune(['backups/db/fixflow-db-20260802T023008Z.dump'], now=datetime(2026,11,2,tzinfo=UTC), retention_days=30) and gets that key back confirms the mechanism.

### O08-F03 [P2/risk/INV] Per-IP login limiter reads the LAST X-Forwarded-For entry, which is only the real client when exactly one proxy hop appends it
cite=LOCATED | skeptic=no skeptic (P2/P3 or non-invariant P1) | conf=0.7 effort=S apk=no
CLAIM: With two proxy hops between Cloudflare and uvicorn (for example Caddy in the API path), _client_ip returns the inner proxy's address for every caller, so all logins share one 20-per-60-second bucket.
WHEN: cloudflared -> Caddy -> backend, where Caddy replaces or appends X-Forwarded-For with the cloudflared container address. Any 21 login attempts in 60 s from any callers (one attacker spraying, or a morning when six techs log in and retry) make every further login return 429 for the window. Conversely, with no XFF-setting hop the header is client-forgeable but the last entry is still the one Cloudflare appended.
    - backend/app/features/identity/router.py:56-64 — _client_ip splits X-Forwarded-For and returns the last entry, with a docstring assuming Railway is the single trusted proxy
    - backend/app/features/identity/throttle.py:107-123 — IpRateLimiter max_attempts=20, window 60 s, in-memory
    - backend/app/features/identity/router.py:75-81 — 429 returned when the limiter denies
IMPACT: Login denial of service for the whole fleet from one source, or the roster-wide spray defence silently ineffective. The per-account lockout remains the real defence (CLAUDE.md), so it is availability, not a PIN-guessing bypass.
FIX: Route api.<domain> from cloudflared straight to backend:8000 (no Caddy in the API path), and prove with the XFF echo test in SH8. If a second hop is required, make the limiter take the Nth-from-last entry via a setting (FIXFLOW_TRUSTED_PROXY_HOPS), default 1.
