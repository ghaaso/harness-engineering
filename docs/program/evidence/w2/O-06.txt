### O6-F01 [P0/risk/INV] Booting the backend on a non-Railway host without FIXFLOW_ENVIRONMENT=production signs JWTs with the public dev secret
cite=LOCATED | skeptic=CONFIRMED -> P1 | conf=0.9 effort=S apk=no
CLAIM: The production JWT boot guard only fires when FIXFLOW_ENVIRONMENT=production or RAILWAY_ENVIRONMENT is set. A home-server backend started without that variable therefore serves HS256 tokens signed with DEV_JWT_SECRET, a constant committed in the repo, and anyone can mint a manager token.
WHEN: Self-hosted deploy (no RAILWAY_ENVIRONMENT in the env) where FIXFLOW_ENVIRONMENT is unset or not 'production' and FIXFLOW_JWT_SECRET is unset. The API hostname is reachable through the tunnel.
    - backend/app/core/config.py:17 — DEV_JWT_SECRET = "dev-insecure-secret-change-me-in-production-32b"
    - backend/app/core/config.py:151 — jwt_secret: str = DEV_JWT_SECRET
    - backend/app/core/config.py:160 — environment: str = "dev"
    - backend/app/core/config.py:221 — return self.environment.lower() == "production" or bool(os.getenv("RAILWAY_ENVIRONMENT"))
IMPACT: Complete authentication bypass from the internet: forged manager tokens give every money, ledger, attendance and media endpoint. The guard was correct on Railway only because Railway injected RAILWAY_ENVIRONMENT. The migration removes that crutch silently.
FIX: Fail closed. Refuse to boot with DEV_JWT_SECRET unless FIXFLOW_ENVIRONMENT is explicitly 'dev' AND the database host is localhost/127.0.0.1, or default environment to 'production' and require dev to opt in. Also enforce a minimum jwt_secret length. Add a deep-health check that reports 'dev secret in use'.
SKEPTIC: I traced the path myself and the failing condition holds. config.py:160 defaults `environment` to "dev". config.py:221 sets `is_production` true only when environment=="production" or RAILWAY_ENVIRONMENT is present. config.py:228 makes the boot guard (called first thing in create_app, main.py:251) raise only when is_production is true AND jwt_secret == DEV_JWT_SECRET. On a self-hosted box with neither variable set, is_production is False, the guard does nothing, and jwt_secret keeps its default from config.py:151, which is the constant committed at config.py:17. security.py:62/67 then signs and verifies HS256 tokens with that public string.

Forging a manager token works in practice. In identity/deps.py:42-60, get_current_principal decodes the token, loads the row by `sub`, and checks only `active` and `ver == token_version`. The role comes from the DB row, so an attacker needs a manager id and its token_version. Migration 0012 seeds the manager id 'm1' in the public repo (tech ids are slugs t1..t5, per models.py:3). A missing `ver` claim counts as 0, the column default, and it is a small integer anyone can guess if it was ever bumped. So {sub:'m1', exp:...} signed with the dev secret gives a manager principal.

Nothing else blocks this. backend/Dockerfile and start.sh never set FIXFLOW_ENVIRONMENT, docker-compose.yml does not either, and backend/.env.example has no FIXFLOW_ENVIRONMENT line, so an operator copying it gets no prompt to set one. ops/health.py:121 reports 'degraded' only when is_production is true, so the deep-health check stays silent in this case too. Commits since 906b990: da988e2 changed config.py only in the database_url validator, and none of the listed commits touch the guard.

Adjacent issue I noticed but did not run: .env.example ships `FIXFLOW_JWT_SECRET=` blank. pydantic-settings does not ignore empty env values by default (no env_ignore_empty in model_config), so a .env copied verbatim would make jwt_secret "". That differs from DEV_JWT_SECRET, so the guard would pass even WITH FIXFLOW_ENVIRONMENT=production.

Why P1 and not P0: if the condition occurs, the impact is full auth bypass (P0-class). But the self-hosted deploy does not exist yet (the docs/ORCHESTRATION-DESIGN-2026-10.md and G1 gate describe it as planned), and the bug needs an operator to leave the variable out. The fix is cheap: fail closed when not explicitly 'dev', or reject any secret shorter than N bytes or equal to the default, regardless of environment.
SETTLE: Run in backend/ with RAILWAY_ENVIRONMENT and FIXFLOW_ENVIRONMENT unset and no FIXFLOW_JWT_SECRET: `python -c "from app.main import create_app; create_app(); from app.core.config import settings, DEV_JWT_SECRET; print(settings.is_production, settings.jwt_secret == DEV_JWT_SECRET)"`. Expect it to boot and print `False True`. Then sign a token with `jwt.encode({'sub':'m1','exp':<future>}, DEV_JWT_SECRET, 'HS256')` and call a CurrentManager endpoint against a migrated DB. Expect 200.

### O6-F02 [P1/defect/INV] Any authenticated technician can renegotiate any job's bill to any amount, including after the customer saw or paid it
cite=LOCATED | skeptic=CONFIRMED -> P2 | conf=0.9 effort=M apk=yes
CLAIM: negotiate_bill checks only that the job is not closed and has a bill. Every authenticated principal can reach it. It does not check the assigned tech, bill_sent_at, existing payments or any lower bound. So a technician can set bill_negotiated_paisa to Rs 0 on another technician's already-sent, already-paid job, and no manager approves or is alerted.
WHEN: Tech JWT; POST /api/jobs/{any non-closed job with a bill}/bill/negotiate {amount_paisa: 0}, including when job.bill_sent_at is set or a non-voided payment exists.
    - backend/app/features/jobs/router.py:309-323 — negotiate_bill takes principal: CurrentPrincipal, no Depends(require_manager)
    - backend/app/features/jobs/service.py:1385-1388 — the only guards are status == 'closed' and bill_original_paisa is None
    - backend/app/features/jobs/service.py:1392-1393 — row.bill_negotiated_paisa = amount_paisa; row.bill_status = 'negotiated'
    - backend/app/features/jobs/schemas.py:146 — amount_paisa: int = Field(..., ge=0) (no upper/lower bound relative to original)
IMPACT: This is the classic cash-skim path. The customer pays the sent figure, the tech records a lower negotiated amount and logs matching cash, and the difference disappears. It also undercuts the CLAUDE.md claim that a bill the customer has seen is frozen. The only trace is a 'Bill negotiated Rs a → Rs b' text line on the job timeline.
FIX: Server-side: a non-manager negotiate requires the caller to be the assigned tech. After bill_sent_at or the first payment, a tech negotiate becomes a pending request that a manager approves. Add a per-shop shop_setting cap on tech discounts (percent or absolute) above which approval is required. Record the negotiate in a bill-revision table with a payload (from, to, actor). Deployed APKs keep working: below the cap it is unchanged; above it they get a 409 the outbox parks with the reason.
SKEPTIC: I traced the path myself. router.py:308-335: POST /jobs/{job_id}/bill/negotiate takes `principal: CurrentPrincipal` and has no `dependencies=[Depends(require_manager)]`, while other routes in the same file do have it (lines 111, 128, 233, 369, 450). The router is mounted with a plain `app.include_router(jobs_router, prefix="/api")` (main.py:300), so no router-level role gate is added. identity/deps.py:64 shows CurrentPrincipal accepts any valid token of any role. service.py:1381-1402: negotiate_bill loads the row with `_load`, which only checks that the job exists and shop_id matches (service.py:1910-1914), with no assignment scoping. The only guards are `status == "closed"` (409) and `bill_original_paisa is None` (400). After those it sets bill_negotiated_paisa = amount_paisa and bill_status = "negotiated" unconditionally. It never reads assigned_tech_id, bill_sent_at, payments, or the original amount. schemas.py:145-147: NegotiateRequest.amount_paisa is `Field(..., ge=0)`, so 0 is accepted and there is no bound relative to the original. Compare the customer-pin action at service.py:1612, which has `if not actor_is_manager and row.assigned_tech_id != actor: raise JobForbiddenError`; negotiate has no equivalent check. The negotiated figure really does change what the customer owes: _detail (service.py:1955-1962) uses bill_negotiated_paisa as `payable` when it is set, so balance_paisa = payable - received. Setting it to 0 after a payment leaves a zero or negative balance. The bill freeze (bill_sent_at, negotiated, or non-voided payment) only guards completion resubmits; log_customer_message's own comment (service.py:1427-1431) says so. No notification is raised; the call only adds a `bill` timeline event. The uncommitted working-tree diff only touches tech_metrics, and no commit since 906b990 in gitLog.txt changes negotiate_bill. So the failing condition holds: a tech JWT can POST {amount_paisa: 0} to any non-closed job that has a bill, whoever it is assigned to, whether or not the bill was sent or paid. Why I rated it P2 rather than P1: (1) tech access to negotiate is intended. The mobile app's outbox has a "negotiate" kind (technician-app/src/lib/outbox.ts:28, JobDetailScreen.tsx:89) because haggling happens on site, often after the customer has seen the bill. So the real gaps are the missing assigned-tech check and the missing freeze once a payment exists, not tech access as such. (2) It needs an authenticated staff member, so it is an insider risk. (3) Every renegotiation is logged with actor=principal.tech_id and the prior and new amounts in the event text, so it can be detected after the fact. There is no approval step or real-time alert, though.
SETTLE: An integration test against real Postgres: seed tech A and tech B and a non-closed job assigned to A with bill_original_paisa=500000, bill_sent_at set and one non-voided payment. As tech B, POST /api/jobs/{id}/bill/negotiate {"amount_paisa": 0}. Expect 200, bill_negotiated_paisa=0 and balance_paisa=-received. This test would confirm the gap; it is not needed to refute anything, since the code path is unambiguous.

### O6-F03 [P2/defect/INV] Payments can be logged by any technician on any job, closed jobs included, and a manager can void a payment on a closed job
cite=LOCATED | skeptic=no skeptic (P2/P3 or non-invariant P1) | conf=0.85 effort=S apk=yes
CLAIM: log_payment and void_payment check neither job status nor assignment. So a payment row can be added to, or voided on, a job that is already closed. The web UI hides Void on closed jobs, but the API does not refuse it.
WHEN: Tech JWT: POST /api/jobs/{closed job}/payments → 200 and a new job_payment row. Manager JWT: POST /api/jobs/{closed job}/payments/{id}/void → 200, received total changes after settlement.
    - backend/app/features/jobs/router.py:339-353 — log_payment takes CurrentPrincipal only
    - backend/app/features/jobs/service.py:1456-1468 — _load then add_payment with no status or assigned_tech check
    - backend/app/features/jobs/service.py:1501-1508 — void_payment loads and flips voided with no closed-job guard
    - backend/app/features/jobs/service.py:1155-1156 — contrast: submit_completion refuses a closed job
IMPACT: A settled, closed job's cash can be rewritten after the fact. A manager voiding cash on a closed job is invisible to anyone who trusts 'closed is terminal'. A future Odoo export keyed on closed jobs would export figures that later change.
FIX: Refuse log_payment and void_payment when status == 'closed' (409 with the plain-text '(current status: closed)' suffix the clients already regex). Require the assigned tech or a manager for log_payment. Post-close corrections become an explicit manager 'reopen-for-correction' or reversal record.

### O6-F05 [P1/risk/INV] A fresh database seeds every account, including the manager, with PIN 1234 and never forces a change
cite=LOCATED | skeptic=CONFIRMED | conf=0.85 effort=M apk=no
CLAIM: Migrations 0004 and 0012 seed t1–t5 and manager m1 with a PIN hash of the literal '1234', and nothing forces a change at first login. So a home-server database built with `alembic upgrade head` and exposed through the tunnel accepts a manager login with a publicly known PIN until someone changes it.
WHEN: Fresh DB (W0 unknown: no restorable dump) and the tunnel published before PINs are rotated. POST login as m1 with PIN 1234.
    - backend/alembic/versions/0004_create_technicians.py:28 — _DEFAULT_PIN = "1234"
    - backend/alembic/versions/0004_create_technicians.py:70 — "pin_hash": hash_pin(_DEFAULT_PIN)
    - backend/alembic/versions/0012_dedicated_manager_account.py:31 — _DEFAULT_PIN = "1234"
    - Grep of backend/app/features/identity for must_change/pin_changed/default_pin: no match
IMPACT: Full manager takeover without guessing. The per-account lockout (CLAUDE.md) is irrelevant because the first attempt succeeds.
FIX: Add a must_change_pin flag set by the seed and cleared by set_pin, and refuse all non-identity endpoints for a must_change principal. Or seed with a random PIN printed once by a bootstrap script. Add a deep-health 'default PIN still active' warning. W0 checklist: rotate PINs before the tunnel goes up.
SKEPTIC: I traced it from the seed to the login path. 0004:28 sets _DEFAULT_PIN = "1234" and :70 bulk-inserts t1–t5 with hash_pin("1234"). 0012:31 does the same for m1 (role 'manager', active True) at :59. No later migration changes these rows: a grep for pin_hash, 1234 and _DEFAULT_PIN across alembic/versions, with 0004 and 0012 left out, finds nothing. The only other technician UPDATE/DELETE statements are in 0012 itself (demote t1, and the downgrade). start.sh runs `alembic upgrade head` on every boot, so a fresh DB comes up with these seeds already in place. On login, POST /api/auth/login takes {tech_id, pin} (router.py:72-83; LoginRequest accepts pin lengths 3–12). IdentityService.login (service.py:63-116) loads the row, checks active and the lock, calls verify_pin, and mints a JWT. Nothing in that path checks whether the PIN is a default, carries a must-change flag, or tracks PIN age. The Technician model has no such column either: it holds only pin_hash, active, throttle columns and token_version. The 6+ digit manager PIN policy (_check_pin_policy) runs only in set_pin (service.py:133), so the seeded 4-digit m1 PIN gets around it. The only production boot guard (config.py:223-232, assert_safe_for_production) checks the dev JWT secret and nothing about default PINs. The account id is easy to find: GET /api/technicians is a public roster, and docs/HANDOFF.md:24 publishes "m1, PIN 1234". The per-account lockout does not help, because 1234 works on the first try. Nothing in the git log since 906b990 touches the seeds: 1c546a3 changed lockout recovery only, and 0a40416 (with the boot guard) predates the window and covers only the JWT secret. The failing condition holds whenever a fresh DB is built with migrations and reachable before someone rotates the PINs with set_pin.
SETTLE: Already settled by code trace. For empirical confirmation: on an empty Postgres run `alembic upgrade head`, start the app, then `curl -X POST /api/auth/login -d '{"tech_id":"m1","pin":"1234"}'`. A 200 response with a JWT whose role claim is 'manager' confirms the claim.

### O6-F06 [P1/risk/INV] Nightly DB dumps are unencrypted, stored in the media bucket, and deletable with the same credential the API holds
cite=LOCATED | skeptic=CONFIRMED -> P2 | conf=0.85 effort=M apk=no
CLAIM: run_db_backup uploads a plaintext pg_dump (customer PII, cash, staff ledger, PIN hashes) into the single r2_bucket used for media. It uses the same R2 key that also lists and deletes backups. So anyone holding the backend's env, or code execution in the API, can read every dump and delete every backup.
WHEN: Leak of FIXFLOW_R2_ACCESS_KEY_ID/SECRET (env file on the home box, a container compromise, a backup of the env), or a buggy prune.
    - backend/app/core/backup.py:87-96 — pg_dump --format=custom ... no encryption step
    - backend/app/core/backup.py:122 — store.put_bytes(key, data, 'application/octet-stream')
    - backend/app/core/backup.py:125-131 — list_keys + store.delete(old) with the same client
    - backend/app/core/storage.py:148-149 — delete_object on self._bucket
IMPACT: Confidentiality: the whole business dataset leaks in one object read. Availability: the 'separate provider' backup is one credential away from deletion, and that same deletion removes the external anchor chain.py relies on for tail-truncation detection.
FIX: Encrypt before upload with age/gpg to a public key whose private key the owner holds offline. Use a separate backups bucket and a separate token scoped to PutObject only, with no List/Delete. Move retention to a bucket lifecycle rule plus a bucket lock/retention policy (check that R2 supports it) instead of app-side delete. On the home box, also keep a second copy off-box.
SKEPTIC: I traced the path myself. run_db_backup takes the default get_storage() R2Storage, which is the single boto3 client keyed with settings.r2_access_key_id/secret and bound to settings.r2_bucket (default and documented prod value: job-media). The dump bytes from pg_dump go to put_object unmodified, with no application-level encryption. The same client then lists the backups/db/ prefix and calls delete_object on stale keys. A credential that can PUT, LIST and DELETE in that bucket can therefore read and delete every dump, and the code has no line that narrows the credential, the bucket or the delete scope. The runbook confirms the shared bucket and shared credential in prod and lists them as an open known limit, so the claim holds.

I lowered the severity from P1 to P2 for three reasons:
(1) The failing condition needs the backend env or code execution in the API. That same env carries DATABASE_URL, so reading the dumps adds little beyond direct DB access. The incremental harm is the attacker destroying both the DB and every backup, a total-loss scenario for a single-tenant shop.
(2) The "buggy prune" path is bounded in the current code. keys_to_prune only deletes keys matching fixflow-db-<stamp>.dump under the prefix that are older than retention_days, so a bug would need a code change.
(3) Bucket-side controls such as an R2 bucket lock, versioning or a scoped token cannot be seen from the repo and might mitigate deletion. Nothing in the repo or runbook says they exist, so I did not count them.
CORRECTED: The mechanics are as claimed. The confidentiality impact is mostly not new, though: the same env that holds the R2 key also holds FIXFLOW_DATABASE_URL, which gives live read/write on the DB. The real gap is availability and integrity. Whoever can wipe the DB with that env can also delete every backup with the same R2 key, so the backups do not survive the compromise they most need to survive. "Plaintext" means no application-level encryption. R2's provider-side at-rest encryption does nothing against someone holding the key.
SETTLE: Two account-side checks would settle the severity:
- Cloudflare R2 bucket job-media: look for a bucket-lock / retention rule on backups/db/ and check whether versioning is on. A lock would block deletion inside the retention window.
- R2 API token behind FIXFLOW_R2_ACCESS_KEY_ID: check whether it is scoped to Object Read & Write on job-media (it can delete) or is narrower.

A practical test: with the prod token, run `railway run python -c "from app.core.storage import get_storage; s=get_storage(); s.put_bytes('backups/db/probe.txt', b'x', 'text/plain'); s.delete('backups/db/probe.txt')"`. If the delete succeeds, the deletion path is live.

### O6-F07 [P1/design/INV] The staff-ledger hash chain is unkeyed, unanchored and never verified automatically
cite=- | skeptic=n/a (gap/design) | conf=0.85 effort=M apk=no
CLAIM: row_hash is a plain sha256 over a canonical form published in chain.py. Verification runs only when a manager calls GET /ledger/verify, and no web screen or scheduler calls it. So anyone with DB write access can rewrite staff_ledger rows, recompute the whole chain so verify returns ok, or truncate its tail, and nothing raises an alarm.
WHEN: An operator or attacker with write access to the Postgres database (home-box superuser, the app role, or a restored dump edited and reloaded).
    - backend/app/features/attendance/chain.py:20 — row_hash = sha256(version ‖ payload ‖ prev_hash)
    - backend/app/features/attendance/chain.py:128-132 — compute_row_hash uses hashlib.sha256, no key
    - backend/app/features/attendance/chain.py:38-44 — 'cannot ... detect truncation of the whole tail ... The external anchor for that is the nightly DB backup'
    - backend/app/features/attendance/router.py:532-546 — verify is an on-demand manager GET
IMPACT: The chain detects only clumsy tampering and only if someone remembers to look. Against the home-box operator, the actor this task is about, it gives no protection.
FIX: (1) Schedule a daily verify that writes ok/head_hash to app_event and alerts the owner on failure. (2) Anchor the daily head_hash outside the operator's control: a WhatsApp or email to the owner, or a write-once object in a locked bucket under a different account. (3) Optionally HMAC the chain with a key held outside the DB, for example in an env that only the API process reads. That still does not stop an operator who has both.

### O6-F08 [P1/design/INV] Customer cash (job_payment) has no tamper evidence, and its void is not attributable to the voided row
cite=- | skeptic=n/a (gap/design) | conf=0.85 effort=M apk=no
CLAIM: job_payment has no voided_by/voided_at and no hash chain. The void's job_event carries neither the payment id nor the amount in its payload. So a direct-DB edit of amount_paisa or voided goes undetected, and when a job has two voids nothing links a void event to the row it voided.
WHEN: DB write access (operator), or two payments voided on the same job with similar reasons.
    - backend/app/features/jobs/models.py:481-495 — columns id, job_id, client_id, amount_paisa, method, recorded_by, recorded_at, voided, void_reason only
    - backend/app/features/jobs/service.py:1507-1515 — payment.voided = True; job_event text 'Payment voided — {reason}' with no payload
    - backend/app/features/jobs/service.py:1478-1484 — payment event text 'Payment Rs {amount // 100}' (whole rupees, no payment id, no payload)
IMPACT: The money table most exposed to skimming is less protected than the staff ledger. Forensics can only rebuild 'who voided which payment when' by matching free text, and a future Odoo pakka-khata export cannot prove its inputs were unaltered.
FIX: Add voided_by/voided_at (migration 0047, nullable, backfill none). Emit payment and void events with payload {payment_id, amount_paisa, method}. Generalise chain.py to a money chain covering job_payment create/void and bill revisions, with the same advisory-lock append.

The only history is a 'Work completed — bill Rs N' text event in whole rupees, so the bill the customer actually saw cannot be reconstructed.
