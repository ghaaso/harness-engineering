## Findings

### O05-01 [P0/risk/INV] JWT boot guard is fail-open off Railway: committed dev secret or a blank secret lets anyone forge a manager token
cite=MOVED | skeptic=NO VERDICT | conf=0.85 effort=S apk=no
CLAIM: A self-hosted backend started without FIXFLOW_ENVIRONMENT=production (and without RAILWAY_ENVIRONMENT) skips the only secret check, so with the committed DEV_JWT_SECRET default (or the blank FIXFLOW_JWT_SECRET= copied from .env.example, which the guard never tests) an unauthenticated attacker can sign {sub:'m1',ver:0} and get full manager access.
WHEN: Home-server deploy whose env omits FIXFLOW_ENVIRONMENT=production and leaves FIXFLOW_JWT_SECRET unset or blank (the .env.example template has the blank line and no ENVIRONMENT line); attacker sends Authorization: Bearer <HS256 token signed with the repo's DEV_JWT_SECRET or ''>.
    - backend/app/core/config.py:17 — DEV_JWT_SECRET = "dev-insecure-secret-change-me-in-production-32b" (committed)
    - backend/app/core/config.py:151 — jwt_secret: str = DEV_JWT_SECRET
    - backend/app/core/config.py:221 — return self.environment.lower() == "production" or bool(os.getenv("RAILWAY_ENVIRONMENT"))
    - backend/app/core/config.py:228 — if self.is_production and self.jwt_secret == DEV_JWT_SECRET: (blank secret never rejected, no length check)
IMPACT: Total compromise of the self-hosted system from the internet: payroll, staff ledger writes, all customer PII, PIN resets for every account.
FIX: Invert the guard: refuse to boot unless environment is explicitly 'dev'/'test' OR jwt_secret is not the dev default AND len(jwt_secret) >= 32; treat an empty value as unset-and-fatal; add FIXFLOW_ENVIRONMENT=production and a generated secret to the self-host compose/runbook; unit-test the guard for blank, short and default secrets with RAILWAY_ENVIRONMENT absent.

### O05-02 [P0/risk/INV] Seeded manager m1 / PIN 1234 plus a public roster gives a manager token in one request on any fresh or seed-restored DB
cite=LOCATED | skeptic=NO VERDICT | conf=0.8 effort=M apk=no
CLAIM: On a database built by alembic upgrade head, POST /api/auth/login {tech_id:'m1',pin:'1234'} returns a manager JWT, because migration 0012 seeds m1 with PIN 1234, the 6-digit manager policy is enforced only in set_pin (never at login), and GET /api/technicians tells an unauthenticated caller which id is the manager.
WHEN: Self-host rebuilt from migrations (or a restored prod DB where the owner never ran set_pin on m1/t1..t5) exposed to the internet before every seeded PIN is rotated.
    - backend/alembic/versions/0012_dedicated_manager_account.py:30-31 — _MANAGER_ID = "m1"; _DEFAULT_PIN = "1234"
    - backend/alembic/versions/0012_dedicated_manager_account.py:58-59 — "role": "manager", "pin_hash": hash_pin(_DEFAULT_PIN)
    - backend/app/features/identity/service.py:31-32 — MIN_PIN_DIGITS_MANAGER = 6 (used only by _check_pin_policy)
    - backend/app/features/identity/service.py:160-165 — _check_pin_policy called from set_pin only; login (63-116) verifies against whatever hash exists
IMPACT: Immediate manager takeover by anyone who reads the public repo or guesses the most common PIN; same for every technician seed (S14).
FIX: Ship a must_rotate flag (migration 0047) set on every seeded account and refuse to mint a token for a flagged account until set_pin succeeds via a one-time bootstrap path (e.g. backend/scripts/set_pin.py run on the box); alternatively seed with no usable hash and require the script. Add a pre-exposure checklist step 'rotate all PINs' to the self-host runbook.

### O05-03 [P1/defect/INV] Unauthenticated attacker keeps every account (including the only manager) locked indefinitely
cite=MOVED | skeptic=NO VERDICT | conf=0.85 effort=M apk=no
CLAIM: Sending one wrong PIN per roster id each time its lock lapses (every <=15 min, ~24 requests/hour for six accounts from one IP, well under the 20/60s IP cap) keeps all accounts locked, and the correct PIN is refused while locked, so no technician or manager can log in.
WHEN: API reachable from the internet (Railway before, Cloudflare Tunnel hostname on self-host) and the attacker uses the public roster ids; escalation never decays because the attacker never stays quiet for DECAY_AFTER_SECONDS.
    - backend/app/features/identity/service.py:87-89 — escalation_has_decayed resets only after a quiet hour
    - backend/app/features/identity/service.py:94-95 — if is_locked(...): raise AccountLockedError (before verify_pin, correct PIN refused)
    - backend/app/features/identity/service.py:97-103 — a wrong PIN after the lock lapses bumps failed_attempts and re-arms next_lock_until
    - backend/app/features/identity/throttle.py:204 — MAX_LOCK_SECONDS = 15 * 60
IMPACT: Field-wide login outage: phones that lose their token (401, S8) cannot re-login, the manager web is unusable; unlock_account.py is re-locked by the next attacker request.
FIX: Do not let a correct PIN through (CLAUDE.md invariant). Instead make the lock cost the attacker, not the account: key the escalating lock on (account, client IP or device id) with a much slower shop-wide per-account ceiling; let a known device (token-bound device id from /api/devices) bypass a lock it did not cause; put the login route behind a Cloudflare WAF rate rule; stop publishing the roster pre-auth (or require an app/Access header for it).

### O05-04 [P1/risk/INV] Per-account lock allows ~96 online guesses per account per day: a 4-digit tech PIN falls in weeks, not years
cite=MOVED | skeptic=NO VERDICT | conf=0.75 effort=M apk=no
CLAIM: After the 10th consecutive failure each further guess costs only one 900 s lock, so an attacker retrying at every lapse gets ~96 guesses per account per day (10^4 space exhausted in ~104 days, ~29% chance per tech per 30 days, ~87% that at least one of six accounts falls in 30 days for uniform PINs, far faster for 1234/0000-style PINs), contradicting the module's 'brute force takes years' claim.
WHEN: Internet-reachable /api/auth/login, tech PINs of 4 digits (MIN_PIN_DIGITS_TECH = 4), attacker spreading across the six public roster ids; IP limiter irrelevant at 4 req/hour/account.
    - backend/app/features/identity/throttle.py:184-186 — 'with the lock throttling, brute force takes years'
    - backend/app/features/identity/throttle.py:200-204 — LOCK_THRESHOLD = 5, BASE_LOCK_SECONDS = 30, MAX_LOCK_SECONDS = 15 * 60
    - backend/app/features/identity/throttle.py:233-239 — 30 << (n-5) capped at 900 s (cap reached at n=10)
    - backend/app/features/identity/service.py:31 — MIN_PIN_DIGITS_TECH = 4
IMPACT: A cracked tech PIN yields a 30-day token with shop-wide reads and money writes (O05-05/O05-06).
FIX: Raise the post-threshold floor (e.g. MAX_LOCK to hours with per-(account,IP) keying so the owner is not locked by it), require 6 digits for techs on next set_pin, add Cloudflare rate-limiting on /api/auth/login, alert (telemetry/ops) on failed_attempts >= threshold, and fix the docstring arithmetic.

### O05-09 [P2/risk] Ops console login has no throttle, reads unbounded bodies, and issues unrevocable 12 h tokens
cite=LOCATED | skeptic=no skeptic (P2/P3 or non-invariant P1) | conf=0.8 effort=S apk=no
CLAIM: POST /api/ops/login compares a single shared OPS_PASSWORD with no attempt counter or delay and buffers the entire request body before parsing, so an internet attacker can guess the password at line rate and push arbitrarily large bodies into memory, and any issued token stays valid for 12 h with no revocation short of rotating OPS_SESSION_SECRET.
WHEN: ops service reachable publicly (Railway before, a tunnel hostname on self-host) with a guessable OPS_PASSWORD; or a multi-hundred-MB POST to /api/ops/login.
    - ops-server.mjs:39-41 — OPS_PASSWORD shared secret; SESSION_SECRET falls back to random per boot; TOKEN_TTL_MS = 12h
    - ops-server.mjs:446-456 — readBody concatenates all chunks with no size cap
    - ops-server.mjs:499-505 — login: passwordValid then issueToken, no rate limit
    - ops-server.mjs:93-107 — stateless HMAC token over exp only (no session id, no revocation list)
IMPACT: Read access to deploy logs/metrics, Sentry issues and backend deep-health (which may echo config state); memory exhaustion of the ops process.
FIX: Put the whole ops hostname behind Cloudflare Access (humans only, no phone dependency); additionally add an in-process per-IP backoff and a 16 KB body cap on /api/ops/login, and require OPS_SESSION_SECRET to be set.
