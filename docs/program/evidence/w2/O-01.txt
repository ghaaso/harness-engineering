## Findings

### O01-F01 [P1/defect/INV] On-duty/travel sampler comes back without its foreground service after any restart, and nothing repairs it
cite=LOCATED | skeptic=NO VERDICT | conf=0.85 effort=M apk=unknown
CLAIM: After a process restart while on duty or travelling (reboot restore, OEM kill, crash), restoreTasks re-registers the ping/travel task without starting LocationTaskService because the app is not foregrounded. Opening the app does not start it either, because startDutyPings/startJobTravel return on isRunning() before startLocationUpdatesAsync is ever reached.
WHEN: Tech is clocked in or on a travel leg. A reboot or OEM kill happens, the OS restores the task, and logcat shows 'Foreground location task cannot be started while the app is in the background!'. The tech then opens the app, and `dumpsys activity services com.fixflow.technician` still lists no LocationTaskService while hasStartedLocationUpdatesAsync returns true.
    - technician-app/src/features/attendance/pingTracker.ts:185 — if (await isRunning()) return;  (startLocationUpdatesAsync only at :187)
    - technician-app/src/features/jobs/travelTracker.ts:193 — if (await isRunning()) return;
    - technician-app/src/features/attendance/pingTracker.ts:261 — if (onDuty && !running) await startDutyPings(techId); (no onDuty && running branch)
    - expo-location-18.0.10 LocationModule.kt:284-286 — hasStartedLocationUpdatesAsync -> taskHasConsumerOfClass (registration only)
IMPACT: For the rest of the shift, pings and breadcrumbs drop to the background location rate ('a few times each hour', R-01), so coverage reads as no_data. The location that is still sampled is recorded with no visible notification, which breaks the visibility layer of the privacy design. The 14 h and 4 h bounds still hold, because handlePingUpdate and handleTravelUpdate check them on every batch.
FIX: 1. In ensurePingTracking/ensureTravelTracking, run only on AppState 'active' and only after dutyStatus says onDuty && !expired (14 h) or travel !expired (4 h).
2. In that case always call startLocationUpdatesAsync again, dropping the isRunning early return. TaskService.registerTask then goes through setOptions and maybeStartForegroundService, which starts or rebinds the FGS. startLocationUpdatesAsync throws when not foregrounded (LocationModule.kt:267-269), so never call it headless.
3. patch-package expo-location: the #49424 guard (startService plus a catch in onServiceConnected) and the #52230 stop fallback (context.stopService when mService is null).
4. Headless 'sampler gap' check in handlePingUpdate: if the previous ping is older than 3x the interval, post one debounced notification ('Tracking was interrupted — open FixFlow') and log a telemetry event.
5. Native follow-up: start the FGS in the BOOT_COMPLETED restore path, which S4 exempts, so post-boot sampling is visible.
No new sampling path; bounds unchanged.

### O01-F04 [P1/defect] Phone and server judge 'inside the fence' differently; real indoor arrivals are suppressed
cite=LOCATED | skeptic=no skeptic (P2/P3 or non-invariant P1) | conf=0.85 effort=S apk=unknown
CLAIM: For an arrival fix with accuracy a <= 100 m and raw distance d where r < d <= r + a, the phone rules 'contradicted' and, after a 20 s dwell, suppresses the prompt. For the same fix the server stores inside_geofence=true, so one presence row carries both confirmed=false and inside_geofence=true.
WHEN: 80 m fence. The tech is indoors 40 m from the centre, but a 60 m-accuracy Wi-Fi fix puts the raw point 95 m out, twice in a row. No arrival notification fires, and the server row has confirmed=false, inside_geofence=true, distance_m about 95, accuracy_m 60.
    - technician-app/src/features/attendance/geofence.ts:94-105 — arrive verdict is distance <= fence.radius_m on the raw point; accuracy only gates 'unknown' at > 100 (:51, :99)
    - technician-app/src/features/attendance/geofence.ts:108-112 — depart threshold max(1.5r, r+40) = 120 m for r = 80
    - technician-app/src/features/attendance/geofence.ts:128-133, :244 — contradicted -> 20 s dwell -> second fix; notification only when verdict !== 'contradicted'
    - backend/app/features/attendance/derive.py:94-95 — return distance - accuracy_m <= radius_m, distance
IMPACT: Real indoor arrivals lose their prompt in exactly the 20-60 m Wi-Fi-accuracy band. Slow real departures (walking to 80-120 m) lose the clock-out reminder and the travel prompt. The manager sees evidence rows that contradict themselves.
FIX: 1. Use one shared verdict function equal to the server's overlap rule:
- arrive: contradicted only if d - a > r; confirmed if d - a <= r;
- depart: confirmed if d - a > r; contradicted only if d + a <= r;
- anything else is 'unknown' (trust the OS).
2. Pin test vectors against derive.geofence_flags.
3. Owner raises the fence to >= 100 m (DB row, H4).
The dwell then becomes rare. Every crossing is still enqueued, so the outbox contract is unchanged.

### O01-F05 [P1/risk] The contradicted-path handler outlives Expo's 15 s job, and the crossing is recorded only after the dwell

### O01-F08 [P2/defect/INV] Fire-and-forget syncs in headless task bodies are aborted when the instance is torn down 2 s later
