The answer in three numbers

Three measures, from narrow to wide. The first is the one part 2.5 of the split-rule record names. The second is the failure the two hand-checked summaries showed. The third asks whether the next window redid what it had been handed.

What a compaction hands over

A boundary does not hand over the summary alone. The harness keeps the session's last few messages word for word, and the summary is written without them. Every one of the summaries read ends with the harness's own line saying so.

1. Claims a script can recheck

A claim is one thing a summary names: a commit id, a file path, a pull request and its state, a test result, a branch head, a count of files or rows. Each was checked against what the session had seen before the hand-over, then the repository at that time, then GitHub. Every claim the script marked wrong was then read by hand.

2. Latest state: is the summary behind its own hand-over?

For all hand-overs, the kept tail was read beside the summary's last three sections. A summary is overtaken when it says something is still to be done, is under way or is awaited, and the kept tail shows it done or arrived. This is a hand read of prose, checked on a sample by a second reader. An overtaken statement is not a made-up one: it was right when it was written, and the kept tail carries the newer state.

3. Did the next window redo what it had been handed?

The next window is given the kept tail too. So the script compared the tail with the next window's first six steps: was a file written again with the same text, a state-changing command run again, a message sent again, an agent or workflow started again, a message said again? No hand judgement enters this one. It is a floor on what the lag cost: plan updates, re-reads, status calls and anything reworded were not compared.
