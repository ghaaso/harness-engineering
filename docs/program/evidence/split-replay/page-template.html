Splitting sessions at a line: the rule and its replay

The proposal: run orchestration as a B+ tree spread over sessions. Inner sessions hold routing keys, leaves hold the work, a session whose window passes a split line hands its work to two fresh sessions, and small siblings merge. This page replays that rule over every Claude Code session recorded on this PC, with no model calls.

Untested proposal. The replay counts exposure: where recorded windows passed a line and what a split could touch. It is not a saving, and it cannot show the effect on quality or hallucinations, which is what the idea is aimed at.

Does it pay, by the tests fixed beforehand?

Judged on session windows in the middle case with an even split. The thresholds were written into the record before the replay stage ran. None of the five can show that the idea works or fails on hallucinations.

What the replay cannot show, and the decision

It cannot show

  • Whether the work could be divided. The replay sees token counts, not scopes. The roll-over rows are the case where it could not.
  • Whether a brief is right. It reads no message text, so it cannot tell a correct brief from a wrong one. An "avoided compaction" is a summary not written, nothing more.
  • Quality, hallucinations, throughput, time. None is visible in a transcript's token counts.
  • The costs it leaves out: messages between siblings, work that needs both windows, a child that guesses instead of re-reading.
  • The parent's own steps, merges and the caps. The replay charges nothing for the inner session above the leaves, makes no merges, and applies neither the fan-out cap nor the depth cap.

The trial that would

  • Two comparable lane waves: one under the rule at the chosen line, one with an earlier compaction window at the same token count.
  • Main measure, as first written: a script rechecks each claim that names a path, a commit, a pull request or a test result against the repository. That script was built and run on the record on 14 November. It cannot separate summaries from maintained documents, so the main measure is now a reader's check of the latest state (the box on the right; record, part 6.4).
  • Beside it: review send-backs and rounds, tokens and hours per accepted slice, rule failures, and the fill at every correction.
  • At least ten hand-overs per arm G.
