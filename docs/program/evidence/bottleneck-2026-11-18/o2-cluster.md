# o2 cluster: what cluster schedulers do when CPU, memory or the scheduler itself is the limit

Line references are "txt line N" in the text made by pdftotext from each paper: Borg uses the
`-layout` text (`p.txt`), every other paper the plain text (`r.txt`). All 8 papers were read from
open PDFs; the sections quoted were read in full, the rest of each paper was searched by keyword
and skimmed (the 8th, Autopilot, from a university course copy of the EuroSys PDF).

## Gate summary
- Borg: compressible vs incompressible. "If a machine runs out of non-compressible resources, the Borglet immediately terminates tasks, from lowest to highest priority"; compressible: "throttles usage". quoted, txt line 648-655.
- Borg: reclaiming unused reservations lets non-prod work run on spare capacity; without sharing "20-30% more machines" (median cell). quoted, txt line 477-481.
- Borg: co-location interference is small on CPU: +0.3% CPI per added task, mean CPI 1.58 shared vs 1.53 dedicated ("about 3% worse"). quoted, txt line 468-480.
- Borg: admission by quota, preemption by priority, no preemption inside the production band to stop cascades. quoted, txt line 125-182.
- Autopilot: limit set from usage history cuts slack to 23% (ML) / 31% (window) vs 46-60% manual; OOMs rarer (0.013 / 0.002 vs 0.069 per task-day). quoted, txt line 447, 460.
- Heracles: feedback controller co-locates batch with a latency job; raises machine utilisation to 90% average with no SLO violation; BE off above 85% load. quoted, txt line 280, 989-995.
- Omega: shared-state optimistic concurrency; scheduler decision time is a bottleneck; conflicts cost about 40% more scheduler busyness at the worst cluster. quoted, txt line 163-165, 666.
- Mesos: offers; allocation by fair share or strict priority; revoke (kill) tasks after a grace period; guaranteed allocation below which nothing is killed. quoted, txt line 122-126.
- Sparrow: batch sampling plus late binding gives response within 12% of an ideal scheduler at 80% load; no bin packing, no gang scheduling. quoted, txt line 36, 43.
- Quincy: fair share with preemption beats fair share without preemption; "worst-case slowdowns of around a factor of 100" without it. quoted, txt line 931-932.
- Quasar: users' reservations leave CPU below 20% while reservations reach 80%; performance-target allocation raises utilisation 47%. quoted, txt line 14, 102.

## Papers

### P1. Verma, Pedrosa, Korupolu, Oppenheimer, Tune, Wilkes, "Large-scale cluster management at Google with Borg", EuroSys 2015. Read from: https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43438.pdf. Pages read: all of sections 2, 3.2, 5.2, 5.5, 6; rest skimmed.
- Result (compressible vs incompressible): "A second split is between compressible resources (e.g., CPU cycles, disk I/O bandwidth) that are rate-based and can be reclaimed from a task by decreasing its quality of service without killing it; and non-compressible resources (e.g., memory, disk space) which generally cannot be reclaimed without killing the task. If a machine runs out of non-compressible resources, the Borglet immediately terminates tasks, from lowest to highest priority, until the remaining reservations can be met. If the machine runs out of compressible resources, the Borglet throttles usage (favoring LS tasks) so that short load spikes can be handled without killing any tasks. If things do not improve, Borgmaster will remove one or more tasks from the machine." (txt line 648-655)
- Result (admission): "Quota is used to decide which jobs to admit for scheduling." "Quota-checking is part of admission control, not scheduling: jobs with insufficient quota are immediately rejected upon submission." "every user has infinite quota at priority zero, although this is frequently hard to exercise because resources are over-subscribed. A low-priority job may be admitted but remain pending." (txt line 125-147)
- Result (preemption): "A high-priority task can obtain resources at the expense of a lower-priority one, even if that involves preempting (killing) the latter." "To eliminate most of this [preemption cascades], we disallow tasks in the production priority band to preempt one another." Preempted tasks go "to the scheduler's pending queue, rather than migrate or hibernate them." (txt line 168-180, 272-275)
- Result (reclamation): "we estimate how many resources a task will use and reclaim the rest for work that can tolerate lower-quality resources, such as batch jobs." The reservation starts at the limit, "after 300 s ... decays slowly towards the actual usage plus a safety margin", and "is rapidly increased if the usage exceeds it." Prod tasks are placed by limits and "never rely on reclaimed resources". "If this happens [machine runs out], we kill or throttle non-prod tasks, never prod ones." (txt line 616-633)
- Result (memory vs CPU): "A task that exceeds its memory limit will be the first to be preempted if resources are needed, regardless of its priority ... CPU can readily be throttled, so short-term spikes can push usage above reservation fairly harmlessly." "Using slack memory is disabled by default, because it increases the chance of a task being killed", yet 79% of batch tasks enable it; "the occasional batch task is sacrificed when an LS task needs resources in a hurry." (txt line 626-630, 697-710)
- Result (CPU isolation): LS tasks "can reserve entire physical CPU cores"; batch tasks "are given tiny scheduler shares"; "The Borglet dynamically adjusts the resource caps of greedy LS tasks in order to ensure that they do not starve batch tasks for multiple minutes". (txt line 680-688)
- Conditions: Google cells of thousands of machines; jobs declare limits, priority, latency-sensitive or batch; Borg knows only requests (limits) and measured usage, not durations.
- Measured effect: "segregating prod and non-prod work would need 20-30% more machines in the median cell" (txt line 477-479). Adding a task to a machine "increases the CPI of other tasks by 0.3%"; "increasing machine CPU usage by 10% increases CPI by less than 2%"; correlations "only explain 5% of the variance"; mean CPI 1.58 shared vs 1.53 dedicated, "about 3% worse in shared cells" (txt line 468-480). Aggressive reclamation settings raised OOM events "slightly" and the medium setting was deployed (txt line 639-646). "About 20% of the workload runs in reclaimed resources in a median cell" (txt line 621). Hybrid scoring: "about 3-5% better packing efficiency ... than best fit" (txt line 267-268).
- Needs to know or measure: per-task limit, priority band, latency-sensitive or batch class, usage sampled every few seconds, memory pressure.
- Failure modes: best fit "penalizes any mis-estimations in resource requirements" and hurts bursty loads; worst fit (E-PVM) spreads load "at the expense of increased fragmentation" (txt line 249-260). Early post-hoc enforcement let rogue tasks hurt others, so "some users inflated their resource requests" (txt line 669-673). "occasional low-level resource interference (e.g., memory bandwidth or L3 cache pollution) still happens" (txt line 692-694). Cascading preemption (above).
- On one machine with agents: reasoned. Treat the processor as the compressible resource (share it, throttle it, never kill for it) and memory as incompressible (reserve it, kill lowest priority first); reclaim only for work that survives being killed; keep a never-reclaimed class for the work that must not be disturbed; no preemption among the top class.

### P2. Rzadca, Findeisen, Swiderski, et al., "Autopilot: workload autoscaling at Google", EuroSys 2020. Read from: https://homepages.dcc.ufmg.br/~cunha/teaching/20221/cloudcomp/readings/10-readings/rzadca20autopilot.pdf. Pages read: sections 1-4 (text lines 37-460, 711-714); rest skimmed.
- Result: "A job that exceeds its limits might be throttled or killed, resulting in delaying or dropping end-user requests, so human operators naturally err on the side of caution and request a larger limit than the job needs." Autopilot's "primary goal is to reduce slack - the difference between the limit and the actual resource usage - while minimizing the risk that a task is killed". (txt line 37-38)
- Result (CPU vs RAM enforcement): "If there is little contention ..., tasks are allowed to use CPU beyond their limits. However, once there is contention, limits are enforced and some tasks may be throttled." A hard RAM limit: "killed with an out-of-memory (OOM) error as soon as the task exceeds its limit"; a soft one: "permitted to claim more memory than its limit, but if the overall RAM utilization on a machine is too high, the Borglet starts to kill tasks that are over their limit". (txt line 107-110)
- Result (statistic per class): CPU for batch uses the mean "since if a job tolerates CPU throttling, the most efficient limit for the infrastructure is the job's average load"; serving jobs the 90th or 95th percentile of load-adjusted usage; memory: 98th percentile for low OOM tolerance, the maximum for minimal tolerance; a 10-15% safety margin and the maximum over the last hour. Limits rise quickly and fall slowly (exponentially decaying window). (txt line 239-244, 167)
- Result (back-pressure): "we charge service users for the resources they reserve, rather than the ones they use, and the requested resources decrement the user's quota". Raising a limit "might then no longer fit"; the Borglet then "will terminate some lower-priority tasks"; priority levels were cut "to reduce the amount of this kind of cascading." (txt line 111-112)
- Conditions: Google fleet; sample of 10 000 jobs per group; metrics from 5-minute windows, daily 95th percentiles; usage histories available.
- Measured effect: "The average relative slack of a non-Autopiloted job ranges from 60% (hard limits) to 46% (soft limits); while the average relative slack of a Autopiloted job ranges from 31% (moving window) to 23% (ML)." Absolute slack "more than 12 000 machines" non-Autopilot vs "less than 500 machines" Autopilot (txt line 447-448). After migrating a set of jobs the average slack fell from 75% to 20% (txt line 454). OOMs: "over 99.5% of Autopilot job-days see no OOMs"; ML 0.013 vs window 0.002 per task-day; manual hard limits 0.069 per task-day (txt line 460). Autopiloted jobs are over 48% of fleet resource usage (txt line 74).
- Needs to know or measure: usage time series (5-minute histograms), job class (batch/serving), OOM tolerance, load.
- Failure modes: the paper's own caveat: a limit of 0 would score best on slack, so OOMs must be reported with it (txt line 459). The ML recommender gives more OOMs than the window one at low slack (txt line 659). Offline experiments use unadjusted traces and ignore how an OOM changes later load (txt line 403). A scaling limit (quota, machine size) can still cause OOMs (txt line 440).
- On one machine with agents: reasoned. Setting a memory cap from a high percentile of measured use plus a margin, and a CPU share from mean use for work that tolerates slowdown, is the published recipe; it needs usage history per job class and a tolerance for a killed worker.

### P3. Lo, Cheng, Govindaraju, Ranganathan, Kozyrakis, "Heracles: Improving Resource Efficiency at Scale", ISCA 2015. Read from: https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/43792.pdf. Pages read: sections 1-5 and evaluation (text lines 10-700, 989-1032).
- Result: a feedback controller that "polls the tail latency and load of the LC workload every 15 seconds. ... If the load for the LC workload exceeds 85% of its peak on the server, the controller disables the execution of BE workloads ... BE execution is enabled when the load drops below 80%. BE execution is also disabled when the latency slack ... is negative ... We give all resources to the latency critical workload for a while (e.g., 5 minutes) before attempting colocation again." (txt line 280)
- Result: "If slack is less than 10%, the subcontrollers are instructed to disallow growth for BE tasks ... If slack drops below 5%, the subcontroller for cores is instructed to switch cores from BE tasks to the LC workload." (txt line 281)
- Result (what interference does): "current OS isolation mechanisms are inadequate for colocating LC tasks with BE tasks. Even at low loads, the BE task creates sufficient pressure on shared resources to lead to SLO violations for all three workloads." Sharing a logical core is not an option because "OS scheduling can introduce latency spikes in the order of tens of milliseconds"; real-time classes "are not work-preserving". (txt line 70, 32, 58)
- Conditions: Google websearch, ml_cluster, memkeyval with SLOs of tens of ms to hundreds of microseconds; Intel cache partitioning, per-core frequency control, network shaping; DRAM bandwidth has no hardware isolation, so the controller reads a counter and removes BE cores at 90% of peak bandwidth (txt line 335); convergence "about 30 seconds" (txt line 434).
- Measured effect: "Heracles colocates sufficient BE tasks to maintain an average EMU of 90% and a minimum of 80% without causing SLO violations" on a 12-hour trace with websearch load 20%-90% (txt line 989-995); "no SLO violations while reducing slack by 20-30%" (txt line 1030); "15% throughput/TCO improvement" (txt line 1032). EMU = LC throughput + BE throughput, normalised to running alone (txt line 527).
- Needs to know or measure: the latency target and live tail latency of the protected job, its load, a per-resource sensitivity profile (DRAM model measured offline).
- Failure modes: the interference table shows many cells above 300% of the SLO from a single antagonist; effect varies by workload and load, "thus precluding the possibility of static" partitioning (txt line 25). Needs hardware features (cache partitioning, per-core frequency control) and one controller per resource; constants "were determined through empirical tuning" (txt line 280).
- On one machine with agents: reasoned. Where one job has a latency or deadline target, a slack-driven loop (grow background work only while slack is above a margin, cut it when slack is low, switch it off at high load) is the published way to keep high use without breaking the target. It needs a measured target and a load signal.

### P4. Hindman, Konwinski, Zaharia, Ghodsi, Joseph, Katz, Shenker, Stoica, "Mesos: A Platform for Fine-Grained Resource Sharing in the Data Center", NSDI 2011. Read from: https://www.usenix.org/legacy/event/nsdi11/tech/full_papers/Hindman_new.pdf. Pages read: sections 1-6 (text lines 6-593).
- Result (allocation): "So far, we have implemented two allocation modules: one that performs fair sharing based on a generalization of max-min fairness for multiple resources and one that implements strict priorities." (txt line 122) "if a framework's share is 10% of the cluster, it needs to wait approximately 10% of the mean task length to receive its share." (txt line 123)
- Result (revocation): "if a cluster becomes filled by long tasks, e.g., due to a buggy job or a greedy framework, the allocation module can also revoke (kill) tasks. Before killing a task, Mesos gives its framework a grace period". "if a framework is below its guaranteed allocation, none of its tasks should be killed, and if it is above, any of its tasks may be killed." Killing "is harmful for frameworks with interdependent tasks (e.g., MPI)". (txt line 123-126)
- Result (isolation): OS containers "can limit the CPU, memory, network bandwidth ... of a process tree. These isolation technologies are not perfect". (txt line 130)
- Result (long tasks): "reserve some resources on each node for short tasks ... a maximum task duration ... after which tasks running on those resources are killed ... similar to ... a separate queue for short jobs in HPC clusters." (txt line 222)
- Conditions: tasks short and elastic; frameworks decide placement; Mesos knows only each framework's share and offers.
- Measured effect: "higher allocation of nodes also translates into increased CPU and memory utilization (by 10% for CPU and 17% for memory)" versus static partitioning on a 96-node EC2 cluster (txt line 463); data locality 18% with static partitions, above 90% with 1 s delay scheduling and 95% with 5 s (txt line 538).
- Needs to know or measure: each framework's allocation; optionally a max task length.
- Failure modes (section 4.6): fragmentation ("wasted space ... bounded by the ratio between the largest task size and the node size"); "a framework f with large resource requirements may starve" when small tasks keep finishing, fixed by "a minimum offer size on each slave" (txt line 234-235). Hoarding to get gang scheduling can deadlock (as Omega says, P5).
- On one machine with agents: reasoned. Guaranteed share below which a job is never killed, a grace period before a kill, and a minimum free amount before a big job is offered resources are directly usable rules; they work only if work units are short or restartable.

### P5. Schwarzkopf, Konwinski, Abd-El-Malek, Wilkes, "Omega: flexible, scalable schedulers for large compute clusters", EuroSys 2013. Read from: https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/41684.pdf. Pages read: sections 1-6 (text lines 100-960).
- Result: the scheduler is itself a scarce serial resource. Monolithic: "scalability is still limited by the processing capacity of a single scheduler"; "head of line blocking" when a slow service decision delays batch jobs, "can be avoided by introducing parallelism". (txt line 155, 366) Omega gives "each scheduler full access to the entire cluster, ... free-for-all manner, and use optimistic concurrency control to mediate clashes". (txt line 203)
- Result (gang vs incremental): "gang scheduling may be needed by some jobs (e.g., MPI programs), but can unnecessarily delay the start of others"; "Incremental resource acquisition can lead to deadlock if no backoff mechanism is provided, while hoarding reduces cluster utilization and can also cause deadlock." Omega uses "incremental transactions, which accept all but the conflicting changes". (txt line 164-165, 205)
- Conditions: simulators driven by Google trace parameters; tjob = 0.1 s, ttask = 5 ms; cluster about 60% utilised; production "speculatively over-commits resources" but this was not simulated (txt line 347-354).
- Measured effect: Mesos-style offers (pessimistic locks) leave "nearly all cluster resources ... locked down" while a slow scheduler decides, and not all jobs are scheduled; Omega "manages to schedule all jobs" with no head-of-line blocking (txt line 369, 429). Conflict fraction passes 1.0 at tjob(service) about 10 s; the 30 s wait target is missed; busyness "about 40% higher than in the no-conflict case"; per-task decision of 1 s at tjob 0.1 s gives conflict fraction at most 0.2 (txt line 665-667). Gang (all-or-nothing) "increase[s] conflict fraction by about 2x"; coarse conflict detection raises busyness "2-3x"; "incremental transactions should be the default" (txt line 809). Scaling: with one batch scheduler cluster A saturates at 2.5x the load; up to 32 batch schedulers conflicts are offset by lower busyness (txt line 431-432).
- Needs to know or measure: decision time per job and per task, conflict rate.
- Failure modes: wasted rework when conflicts are frequent (txt line 163); high-load clusters show more conflicts; "Mesos uses resource hoarding to achieve gang scheduling, and can potentially deadlock" (txt line 195).
- On one machine with agents: reasoned. If one serial gate exists (a test suite, a lock), long jobs must not queue short ones in front of it; use short per-job transactions that either commit or retry, and do not hold partial resources while waiting for the gate.

### P6. Ousterhout, Wendell, Zaharia, Stoica, "Sparrow: Distributed, Low Latency Scheduling", SOSP 2013. Read from: https://cs.stanford.edu/~matei/papers/2013/sosp_sparrow.pdf. Pages read: sections 1-4, 7 and analysis (text lines 5-525, 592-601).
- Result: "Sparrow provides response times within 12% of an ideal scheduler, schedules with median queueing delay of less than 9ms" on a 110-machine cluster running TPC-H (txt line 36); "batch sampling ... will be able to place all m tasks in empty queues as long as d >= 1/(1 - load)", independent of the number of tasks (txt line 222). Late binding: workers queue a reservation and "send an RPC to the scheduler ... requesting a task" when it reaches the front (txt line 169).
- Result (policy): "Sparrow enforces strict priorities or weighted fair shares when aggregate demand exceeds capacity" by "maintaining multiple queues on worker nodes"; "FIFO, earliest deadline first, and shortest job first all reduce to assigning a priority to each job". (txt line 44, 191) "isolates users with different priorities such that a misbehaving low priority user increases response times for high priority jobs by at most 40%" (txt line 38).
- Conditions: homogeneous slots, sub-second tasks, probe ratio 2, load around 80%. Sparrow "does not allow certain types of placement constraints ..., does not perform bin packing, and does not support gang scheduling." (txt line 43)
- Measured effect: at 80% load per-task sampling gives 2.6x the ideal response time, batch sampling 1.92x (txt line 153, 160); late binding costs "a 2% efficiency loss" from idle workers waiting for an RPC (txt line 170); "reduces median query response time by 4-8x and ... 95th percentile ... over 10x" against random placement (txt line 405).
- Needs to know or measure: queue length (a coarse predictor: "queue length provides only a coarse prediction of wait time", txt line 162); no durations needed.
- Failure modes: "when ... task runtimes are comparable [to the round trip], late binding will not present a worthwhile tradeoff" (txt line 172); no protection against rogue schedulers (txt line 355); fair-share enforcement works better as cores per machine grow (txt line 599).
- On one machine with agents: reasoned. Mostly about many machines; the part that carries over is that when each task is short a decision made at the moment a worker is free (late binding) beats a decision made in advance on a stale queue length.

### P7. Isard, Prabhakaran, Currey, Wieder, Talwar, Goldberg, "Quincy: Fair Scheduling for Distributed Computing Clusters", SOSP 2009. Read from: https://www.sigops.org/s/conferences/sosp/2009/papers/isard-sosp09.pdf. Pages read: sections 1-6 (text lines 44-1300).
- Result (admission): "we implement admission control to ensure that at most K jobs are executing at any time. When the limit of K jobs is reached subsequent jobs are queued and started, in order of submission time". "Setting K too large may make it hard to achieve fairness while preserving locality". Goal: a job taking t seconds alone "should take no more than Jt seconds when there are J jobs concurrently executing". (txt line 261)
- Result (preemption): "killing running tasks of one job to free resources for another job's tasks ... can improve the latter job's latency without sacrificing its data locality but wastes the work of the preempted tasks". When a job exceeds its share "the scheduler will kill its over-quota tasks, starting with the most-recently scheduled task first to try to minimize wasted work." Starvation freedom: "its longest-running task will never be killed". (txt line 70, 379-380)
- Result (flow model): scheduling as min-cost flow where "there is a data transfer cost ... and there is also a cost in wasted time to killing a task that has already started to execute", both in one unit (txt line 391).
- Conditions: 243 computers, tasks independent so killing one affects no other; homogeneous machines; fairness counted in computers per job only.
- Measured effect: "Policies that do not allow preemption see worst-case slowdowns of around a factor of 100 for some small jobs"; fairness with preemption has "worst-case slowdown ... well under a factor of 10" (txt line 931-932). "policies that enforce fairness and include preemption ... reduce Unfairness almost by a factor of two ... with ... minimal degradation of Makespan" (txt line 1132). Solver: average 7.64 ms, maximum 57.59 ms; "a little over a second" for 2500 computers and 100 jobs (txt line 1296). Hysteresis variants "improve data locality ... at the expense of Makespan" (txt line 1293). With a constrained network QFPX improved network-bound jobs by 32% over QFP and 87% over GFP (txt line 1160).
- Needs to know or measure: each task's data location and size, running time so far (kill cost), job count, fair share.
- Failure modes: costs must be independent; "correlated constraints ... difficult to see how to encode" (txt line 1373); "fairness is expressed purely in terms of the number of computers"; no network sharing (txt line 1376). Without preemption a job with long tasks hogs the cluster (txt line 378).
- On one machine with agents: reasoned. Cap the number of concurrently admitted jobs, kill the newest over-quota work first, and never kill a job's oldest task; this needs work that can be killed and restarted and a way to price the loss.

### P8. Delimitrou and Kozyrakis, "Quasar: Resource-Efficient and QoS-Aware Cluster Management", ASPLOS 2014. Read from: http://csl.stanford.edu/~christos/publications/2014.quasar.asplos.pdf. Pages read: sections 1-5 and evaluation (text lines 6-1240); Paragon (ASPLOS 2013) could not be fetched and is only described by Quasar.
- Result: "Quasar ... does not rely on resource reservations, which lead to underutilization as users do not necessarily understand workload dynamics". Users give a performance target (QPS or completion time); a short profile (two entries per row, "a few seconds up to a few minutes") is expanded by collaborative filtering into scale-up, scale-out, heterogeneity and interference estimates; "a greedy algorithm" picks the "least amount of resources needed to satisfy a workload's performance target"; a feedback loop corrects misclassification. (txt line 7, 357-361, 549)
- Result (interference): sensitivity is measured by injecting two micro-benchmarks and raising intensity "until the workload performance drops below an acceptable level of QoS (typically 5%)". (txt line 541)
- Conditions: 40-server cluster and 200-node EC2 cluster; Hadoop, Storm, Spark, memcached, Cassandra.
- Measured effect: Twitter production cluster under Mesos: "aggregate CPU utilization is consistently below 20%, even though reservations reach up to 80% of total capacity"; memory use 40-50% (txt line 14). Quasar "improves server utilization at steady state by 47% on average at high load" (txt line 102); Hadoop jobs "by an average of 29% and up to 58%" faster (txt line 891); memcached/Cassandra throughput under auto-scaling is 24%/12% lower and meets latency for 80% of requests vs 98.8% for Quasar (txt line 1148); overheads "up to 9%" for short batch jobs (txt line 1238). Exhaustive classification raises decision time "by two orders of magnitude" (txt line 547). Phase detection: reactive-only "detects 94% of phase changes" (txt line 695).
- Needs to know or measure: a performance target per job, a few profiling runs, a history of earlier jobs.
- Failure modes: a single profiling run per classification "results in high errors" (txt line 545); accuracy drops when columns exceed rows (txt line 543); profiling runs need sandboxing to avoid side effects (txt line 697).
- On one machine with agents: reasoned. Replaces "how many cores or how much memory do you want" with "what rate do you need" and profiles a short run; a machine with few jobs gives too little history to classify, so the profile-then-correct loop is the part that applies.
