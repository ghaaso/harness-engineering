## Summary
- Every controller here has the same shape: measure ONE delay-like or loss-like signal at the point where work waits (queue wait, p90 response time, a timeout), compare with a fixed target, and move ONE actuator (admission rate, credit pool, a thread count, a window) additively up and multiplicatively down.
- The signal choice is argued, not assumed: queueing time, not response time (DAGOR, Breakwater), not queue length (Breakwater), not CPU utilisation (DAGOR). Queue wait names an overloaded resource wherever it is; utilisation does not.
- No paper here has a rule that "detects which resource is the bottleneck and switches method". The closest are MIMO control of CPU and memory with two knobs (P6) and SEDA's per-stage controllers (P1); both leave the choice of knobs to the human.
- Parameters are set by experiment, not derived: SEDA says so outright (P2 l.161-162), Breakwater re-tunes every system per workload (P4 l.412), DAGOR's 20 ms threshold is "empirical" (P5 l.170).
- Stated failure modes: stale feedback when messages are rare (P4), noise and limit cycles from aggressive gains (P6), linear models failing under wide load variation (P2 l.595), subsequent (chained) overload (P5).
- Nothing here was measured on a processor/memory/serial-step mix of local worker processes; all experiments are servers under request load.

## Papers

### P1. Welsh, Culler, Brewer, "SEDA: An Architecture for Well-Conditioned, Scalable Internet Services", SOSP 2001. Copy read: http://sosp.org/2001/papers/welsh.pdf. Text: seda/paper.txt (904 lines).
- Signal measured: input queue length per stage (thread pool controller); output event rate of the stage (batching controller). SUMMARY/QUOTED below.
- How it is measured: periodic sampling of the stage's input queue; moving average of output rate "across many samples" (l.312, l.352).
- Switching or control rule: QUOTED (l.312): "The controller periodically samples the input queue and adds a thread when the queue length exceeds some threshold, up to a maximum number of threads per stage. Threads are removed from a stage when they are idle for a specified period of time." Batching: QUOTED (l.313, l.352): "searching for the smallest batching factor that sustains high throughput. It operates by observing the output rate of events from a stage ... and decreases the batching factor until throughput begins to degrade."
- Measured effect: the paper's case is the failure of the alternatives. QUOTED (l.87): "As the number of concurrent tasks increases, throughput increases until the number of threads grows large, after which throughput degrades substantially." QUOTED (l.108): the event-driven server's "throughput remains constant across a huge range in load, with the latency of each task increasing linearly." QUOTED (l.478): the server "Haboob's throughput is stable as the number of clients increases, sustaining over 200 Mbps for 1024 clients." Figure values for the thread pool controller: in a figure, not read.
- Conditions of the experiment: 4-way 500 MHz Pentium III, 2 GB, Linux 2.2.14, Java (Sandstorm) (l.87, l.358). A 2001 web server.
- What must be true for it to apply: the work is split into stages with queues; the bottleneck is visible as a queue at a stage; OS scheduling left alone (l.354: controllers "naive about the resource management policies of the OS").
- Failure modes: QUOTED (l.42): fixed-limit thread pools "can introduce a great deal of unfairness to clients: when all server threads are busy or blocked, client requests queue up in the network". The authors call the thread controller and batching controller "two simple examples" (l.353) with no stability analysis (REASONED: none in the text).
- What it would mean for several processes on one machine: REASONED. The queue in front of a stage is the signal that shows where the wait is, whether the cause is CPU, a lock or a serial step; the actuator (threads) is the one that must be bounded because throughput falls past a thread count.

### P2. Welsh, Culler, "Adaptive Overload Control for Busy Internet Servers", USITS 2003. Copy read: https://www.usenix.org/legacy/events/usits03/tech/full_papers/welsh/welsh.pdf. Text: usits2/paper.txt (659 lines). (USITS is a USENIX symposium; outside the brief's list by name, USENIX-published; the brief names SEDA/USITS as a seed.)
- Signal measured: 90th-percentile response time per stage (l.119-120).
- How it is measured: QUOTED (l.152): "The controller records up to nreq response-time samples and calculates the 90th-percentile sample", smoothed by an EWMA (l.155); a timer runs it when traffic is low (l.151).
- Switching or control rule: QUOTED (l.151): "additive-increase/multiplicative-decrease tuning of the token bucket rate based on the current observation of the 90th-percentile response time." QUOTED (l.160): "If err > errd, the token bucket rate is reduced by a multiplicative factor adjd. If err < erri, the rate is increased by an additive factor proportional to the error". Per-class version lowers lower-priority classes first (l.183-186).
- Measured effect: QUOTED (l.337): "the overload control mechanism is effective at meeting the response time target despite a many-fold load increase" (target 10 s, Arashi e-mail service, 15-minute runs per point). QUOTED (l.389): under a load spike with a 1 s target, "about 70-80% of requests are rejected during the spike, but response times for admitted requests are kept very low." Controller trace: l.308 "responds to a spike in the response time by exponentially decreasing the token bucket rate".
- Conditions of the experiment: QUOTED (l.305): service on "a 1.2 GHz Pentium 4 machine running Linux 2.4.18", clients on 1-16 machines, 20 ms think time, rejected users retry after 5 s.
- What must be true for it to apply: requests can be refused cheaply; a tail-latency target exists; requests are of types that can be handled per stage.
- Failure modes: QUOTED (l.162): "there are no guarantees that they are optimal ... the behavior of the controller is sensitive to the setting of the smoothing filter constant, as well as the rate increase and decrease". QUOTED (l.338): a rare request type (<1% of load) exceeded its target because "the controller ... is therefore unable to react as quickly". QUOTED (l.595): "good models of system behavior are often difficult to derive ... linear models ... may not be accurate in describing systems with widely varying loads". Section 5.3 (l.592-598) is a literature note on control theory, including Diao et al. (P6): QUOTED (l.593): their Apache scheme "effectively protects server resources from oversaturation, it results in poor client-perceived performance."
- What it would mean for several processes on one machine: REASONED. A tail-latency target on queue/response time and AIMD on a rate is a ready rule, but it admits or refuses work and needs no knowledge of which resource is short; it does not choose between methods.

### P3. Jacobson (and Karels), "Congestion Avoidance and Control", SIGCOMM 1988 (the paper in the version of November 1988). Copy read: https://ee.lbl.gov/papers/congavoid.pdf. Text: jac/paper.txt (1215 lines).
- Signal measured: packet loss, detected as a retransmit timeout. QUOTED (l.579-587): "If packet loss is (almost) always due to congestion and if a timeout is (almost) always due to a lost packet, we have a good candidate for the `network is congested' signal." Round-trip time and its variance estimate the timer (l.20, l.448).
- How it is measured: retransmit timer from a mean-plus-variance RTT estimator (l.448: "essentially eliminates spurious retransmissions").
- Switching or control rule: QUOTED (l.29-30): "The flow on a TCP connection ... should obey a `conservation of packets' principle". Rules: slow-start (cwnd 1, plus 1 per ack, "takes time R log2 W", l.87-91) and congestion avoidance: QUOTED (l.681-683): "On any timeout, set cwnd to half the current window size (this is the multiplicative decrease)." and "On each ack for new data, increase cwnd by 1/cwnd (this is the additive increase)."
- Measured effect: QUOTED (l.851): senders without congestion avoidance "send, on the average, 25% more than will fit in the wire"; with it "about 20 seconds of damped oscillation ... The remaining time the senders run at the wire bandwidth." QUOTED (l.893): old TCPs used only "75% of the link bandwidth ... for data". Test: four senders on a shared bottleneck, 25 KBps link (l.851).
- Conditions of the experiment: 4.3BSD hosts, deliberately overloaded 16 KB windows, one bottleneck link (l.695, l.734).
- What must be true for it to apply: loss is almost always congestion (l.579); sources are cooperating and all run the same rule; the timer is sound (l.561).
- Failure modes: QUOTED (l.658): symmetric multiplicative increase "is a mistake. The result will oscillate wildly and, on the average, deliver poor throughput." Noise sensitivity is "quadratic in w" (l.630, footnote 6). QUOTED (l.632, footnote 7): "We copied Jain's scheme after hearing his presentation ... the scheme was, in a sense, universal".
- What it would mean for several processes on one machine: REASONED. Each worker shrinks its own share fast on a shared-resource signal and grows it slowly; it needs no global coordinator. It carries no information on which resource is short.

### P4. Cho, Saeed, Fried, Park, Alizadeh, Belay, "Overload Control for us-Scale RPCs with Breakwater", OSDI 2020. Copy read: https://www.usenix.org/system/files/osdi20-cho.pdf. Text: bw/paper.txt (965 lines).
- Signal measured: server-side queueing delay (not queue length). QUOTED (l.137): "when RPC service times have high dispersion, queue length is a poor indicator of request latency. A more reliable signal is queuing delay".
- How it is measured: QUOTED (l.217-241): each Shenango core's packet queue and thread queue keep "the timestamp of the oldest item"; the runtime "returns the maximum of the packet queue's delays plus the maximum of the thread queue's delays". Delay from head-of-line blocking is avoided by a threading model change (l.142).
- Switching or control rule: QUOTED (l.154-161): the server keeps a credit pool Ctotal "such that the measured queuing delay (dm) remains close to a target queuing delay (dt)", every network RTT: "If dm is less than dt, Breakwater increases Ctotal additively. Otherwise, it decreases Ctotal multiplicatively, proportional to the level of overload." Plus demand speculation and an AQM drop at 2 x dt (l.184, l.412).
- Measured effect: QUOTED (l.520): at capacity "801k requests per second for goodput ... around 5% overhead when compared to the maximum throughput with no overload control." QUOTED (l.568): "5.7% more goodput compared to SEDA and 6.2% more goodput compared to DAGOR ... at a load of 2x capacity". QUOTED (l.569): "17.5% more goodput than SEDA and 10.2% more ... than DAGOR" at 2x demand, 100 us service time, 1000 clients. QUOTED (l.597): "SEDA takes around 1.6 s to recover its goodput"; DAGOR 500 ms. CoDel at the server loses goodput as demand grows because dropping still costs CPU (l.88).
- Conditions of the experiment: QUOTED (l.406): CloudLab xl170, 10-core Intel E5-2640v4, 25 Gbps, 1 server + 10 clients, server on up to 10 hyper-threads; SLO budgeted per run; parameters of all three systems tuned for best goodput and re-tuned when service time, distribution or client count changes (l.412; QUOTED: SEDA "does" need re-tuning for a different number of clients; Breakwater and DAGOR do not).
- What must be true for it to apply: QUOTED (l.194): "a low-latency network stack ... minimal variability in packet processing and no head-of-line-blocking" so queueing delay is accurate; short RPCs; one server whose capacity the clients share.
- Failure modes: QUOTED (l.89-90): client-side rate limiting reacts "delayed by a network RTT" and "the delay in getting feedback increases with the number of clients". QUOTED (l.587): "overcommitment can occasionally result in large bursts of incoming requests." SEDA: QUOTED (l.588) "it is hard to tune SEDA dynamically".
- What it would mean for several processes on one machine: REASONED. The strongest argument that the controlled variable should be time-in-queue of the oldest item, and that a measured queue time must exclude delay that overload did not cause (e.g. one long job ahead of others). A serial step with long jobs would break a queue-length signal first.

### P5. Zhou, Chen, Lin et al., "Overload Control for Scaling WeChat Microservices" (DAGOR), SoCC 2018. Copy read: https://www.cs.columbia.edu/~junfeng/papers/dagor-socc18.pdf. Text: dagor/p2.txt (531 lines, plain mode).
- Signal measured: average request queuing time in a window. QUOTED (l.170): "each server refreshes its monitoring status of the average request queuing time every second or every 2000 requests, whenever either criteria is met."
- How it is measured: time a request waits in the pending queue before service starts (l.164, l.164 def.).
- Switching or control rule: QUOTED (l.170): "the threshold of the average request queuing time to indicate server overload is set to 20 ms" (given a 500 ms task timeout). On overload the expected incoming amount for the next period is cut by alpha, otherwise raised by beta; QUOTED (l.234): "we set alpha = 5% and beta = 1%" (symbols read as stated in the paper; the text shows them as dropped characters); admission level is the largest prefix sum of a request-priority histogram under that amount (l.234).
- Measured effect: QUOTED (l.469): "when subsequent overload is involved ... DAGOR exhibits around 50% higher success rate than CoDel and SEDA in the workload of M2". For simple overload "all the overload control techniques perform roughly the same". Figures with curves: in a figure, not read.
- Conditions of the experiment: QUOTED (l.290): in-house cluster, "Intel Xeon E5-2698 @ 2.3 GHz CPU and 64 GB DDR3", 10 Gigabit Ethernet; production deployment claimed "five years" (l.40).
- What must be true for it to apply: requests carry a priority assigned at the entry and inherited downstream; services call each other (the "subsequent overload" case); a fixed 500 ms timeout suits the 20 ms threshold.
- Failure modes: QUOTED (l.168): response time "is prone to false positives of overload" in a call chain; QUOTED (l.169) on CPU: "high load does not necessarily infer overload. As long as the server can handle requests in a timely manner ... it is not considered to be overloaded, even if its CPU utilization stays high." Breakwater found its response delay slow at large client counts (P4 l.587, l.597).
- What it would mean for several processes on one machine: REASONED. States directly that high CPU utilisation is not the overload signal; wait time is. The 20 ms and 5%/1% values are tuned to WeChat and are not portable to a task-length mix of minutes.

### P6. Diao, Gandhi, Hellerstein, Parekh, Tilbury, "MIMO Control of an Apache Web Server: Modeling and Controller Design", American Control Conference 2002 (not in the brief's venue list; it is the seed paper that was openly available; the NOMS 2002 and Real-Time Systems 2002 papers were not found open). Copy read: https://cs.uwaterloo.ca/~brecht/servers/readings-new/acc02final2.pdf. Text: diao/p2.txt (410 lines, plain mode).
- Signal measured: CPU and memory utilisation of the Apache process (two outputs). QUOTED (l.24): "CPU and MEM are server-side metrics and thus can be easily measured."
- How it is measured: time-averaged values over a sample interval; QUOTED (l.71): model eigenvalues "seem to converge" for sample times "above 5 seconds"; at low sample times CPU variability skews the model.
- Switching or control rule: two actuators, MaxClients and KeepAliveTimeout (l.27-28). A first-order linear 2x2 MIMO ARX model fitted by least squares (l.65-66; "R2 increased by less than 2%" when going to higher order); PI control law on the tracking error; gains by pole placement then LQR. QUOTED (l.227): pole placement "decouples the closed loop system ... results in unnecessarily large control gains which results in a degradation of control performance"; LQR "was used". QUOTED (l.179): "Aggressive controllers often utilize high gains which cause excessive reactions to stochastics ... These drastic changes might lead to saturation, which can cause instability in the form of limit cycles".
- Measured effect: SUMMARY from the text, no settling-time number read: QUOTED (l.382): the LQR controller gave "smaller gains ... CPU and MEM are less oscillatory than before. At the same time, the controller is still fast enough to track the desired utilizations." Robustness QUOTED (l.396): with arrival rate changed from 0.05 to 0.5 and "We did not rebuild the system model", "even though the model prediction is not very accurate, the controller still performs well." Numeric results in figures: in a figure, not read.
- Conditions of the experiment: QUOTED (l.35): one Apache server on a LAN, synthetic WAGON-model workload, Webstone 2.5 file distribution. Reference values for CPU and MEM chosen from the model's DC gain.
- What must be true for it to apply: a linear model is adequate inside the operating region; references must be feasible: QUOTED (l.296): "(CPU= 0.8, MEM= 0.4) is not a feasible combination of reference values."
- Failure modes: QUOTED (l.401): "limits of the models we employ when dealing with notoriously nonlinear metrics such as response times ... the selection of sample time remains an ongoing research issue." Welsh and Culler (P2) judge the result to protect the server but give poor client-perceived performance.
- What it would mean for several processes on one machine: REASONED. The only paper here that controls two resources (CPU and memory) at once with two actuators and models their coupling, and it shows that a pair of targets can be unreachable together. It does not detect which is the binding one; the references were fixed by an administrator.

### P7. Nichols, Jacobson, McGregor (ed.), RFC 8289 "Controlled Delay Active Queue Management" (CoDel), IETF RFC 2018 (experimental). It is a substitute: the CACM 2012 article "Controlling Queue Delay" (Nichols, Jacobson) was not downloadable as text (see "Could not open"). Copy read: https://www.rfc-editor.org/rfc/rfc8289.txt. Text: rfc8289/rfc.txt (1403 lines).
- Signal measured: packet sojourn time (time in queue), tracked as a local minimum over an interval. QUOTED (l.382-386): "Instead of averages, we recommend tracking the minimum sojourn time; then, if there is one packet that has a zero sojourn time, there is no persistent queue. A persistent queue can be detected by tracking the (local) minimum queue delay".
- How it is measured: one state variable that records how long the minimum has been above the target (l.408-411).
- Switching or control rule: drop when the minimum sojourn stays above TARGET for INTERVAL; drop rate then increases (control law at about l.1053). QUOTED (l.195): "CoDel configures itself based on a round-trip time metric that can be set to 100 ms". QUOTED (l.766-778): INTERVAL "100 ms works well across a range of RTTs from 10 ms to 1 second"; "TARGET SHOULD be set to 5 ms for normal Internet traffic."
- Measured effect: SUMMARY of the RFC: QUOTED (l.792): "below a TARGET of 5 ms, utilization suffers for some conditions and traffic loads; above 5 ms showed very little or no improvement in utilization." QUOTED (l.499): targets "between 1 and 20 milliseconds for RTTs from 30 to 500 ms and link bandwidths of 64 Kbps to 100 Mbps" explored by simulation. Throughput and delay figures: not in the text read.
- Conditions of the experiment: simulation (l.497-500); the RFC itself is a specification.
- What must be true for it to apply: the standing queue can be told from a burst by the interval (l.400: interval "at least a round-trip time"); a drop is a cheap, informative signal to the sender (TCP).
- Failure modes: SUMMARY from P4: at microsecond service times dropping costs CPU and goodput falls (P4 l.88); from P5: no help in chained overload (P5 l.469).
- What it would mean for several processes on one machine: REASONED. The minimum over a window is a rule to tell a persistent backlog from a burst; a test suite that runs once per merge cycle should look like a burst, a lock held for minutes like a standing queue.

## Across the papers (agreements, disagreements, gaps)
- Agreement: the actuator is additive-increase, multiplicative-decrease (P2, P3, P4, P5); the target is a fixed number set by hand (P2 l.120, P4 l.412, P5 l.170, P7 l.778). Gains are kept low to avoid noise-driven oscillation (P6 l.179, P3 l.658).
- Agreement: signal at the wait point beats a utilisation signal (P4, P5, P7). SEDA itself uses queue length for threads (P1) and Breakwater says that is a poor indicator with dispersed service times (P4 l.137): a disagreement between P1 and P4.
- Disagreement: control-theoretic design (P6: identify a linear model, PI, LQR) versus ad hoc rules tuned by experiment (P1, P2, P3, P5). P2 (l.592-598) says the former needs models that are hard to derive; P3 notes TCP's rules "were empirically determined".
- Gap 1: none of the papers switches between two different actuators according to which resource is saturated. P6 controls two resources but with fixed references. REASONED.
- Gap 2: none measures a serial step (one job at a time); the signal "wait for a single-server stage" would be a queue with capacity 1. REASONED.
- Gap 3: all experiments are request-serving systems with short requests; whole tasks that last minutes change the sample time (P6 l.71: sample times above 5 s) and the AIMD cadence. REASONED.
- Not tested in these papers: memory pressure as the bottleneck; a mixed-load local machine; AI coding agents.
