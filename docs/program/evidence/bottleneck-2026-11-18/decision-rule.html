From the current bottleneck to the method

One calculation, repeated every time a piece of work starts or finishes. For each resource, work out how many units it can carry right now. Run at the smallest number. The resource that gives the smallest number is the bottleneck at that moment.

A unit is one piece of work that starts at one moment: an agent's piece, a run of the test suite, a model run, a build. First on this page: how each conclusion was reached and what is still a guess. After that, a demonstration you can move.

The rule acts only at the gate: it holds new units back. It stops running work in one case, memory at its floor, because memory fails as a cliff and not as a slope.

Several writers on one file: the one real switch

Scheduling needs no switch, because the smallest number is recomputed at every event. How writers share a file is different: either each works on its own copy and the copies are merged, or one owner writes at a time. The choice is made per file, by cost, and the cost is counted in whatever is scarce.

The rule, in order

  1. Measure each kind of unit first. Busy threads, peak memory, time in the check, time outside it, tokens. A new kind runs alone until its figures are steady.
  2. Work out each number at every start and finish: memory, processor, the check, shared files, tokens, and how many units are ready.
  3. Run at the smallest. Two resources within one unit of each other count as two limits at once. If "ready" is the smallest, capacity is idle: start more work.
  4. Act only at the gate. An agent's unit is minutes of work, too costly to throw away.
  5. Choose the next unit that fits what is free on every resource at once. Short check jobs first. A unit queued for the check holds nothing else.
  6. Cross-check with the wait. A queue at the check that never empties means the check is the bottleneck, whatever the processor shows.

Tokens are a budget, not a rate. Units side by side cost the same tokens in total as one after another, so the allowance limits how many run at once only when a window is nearly spent. Otherwise it decides how many units can be done before the reset, and on which model.

Not in any paper read

  • An allowance that refills over hours or days, or tokens beside processor and memory.
  • A serial step shared by separate programs. Every paper's serial section lives inside one program.
  • Units that last minutes with 3 to 16 workers. The papers' thresholds were tuned on work lasting microseconds, so only the shape of each rule carries over. Every number has to be computed here.

To set the numbers: eight measurements

No number in the rule is set yet. Seven of these are small runs and wait for your word. One is a count from a log we already have.

  1. Per kind of unit: peak memory and busy threads over time. needs a run
  2. The time a unit spends outside the check, per piece and per change. needs a run
  3. Whether one suite run slows down when a second runs beside it. needs a run
  4. The suite with its test files side by side. needs a run
  5. Conflict counts: a merge of dummy edits on our own neighbouring lines. needs a run
  6. Tokens per unit by kind and by model; whether the 5-hour window is fixed or rolling; how cached reads count. needs a run
  7. The lane's wait with one slot against two. a count from the log
  8. A memory-bandwidth counter, only if the first three show a slowdown that memory and threads do not explain. needs a run
