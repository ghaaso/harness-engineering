Results for CureFound

What five research tracks measured while Claude Code agents built FixFlow and the Clinic Workshop, in plain words, and what each result means for CureFound's design, evaluation and build.

Prepared for Muhammad Bilal and the CureFound team. Compiled from the uncommitted research record on branch docs/orchestration-design-2026-10; five Sonnet digests on 2026-11-13. Every number carries the source document's own confidence tag.

CureFound, as the title defense describes it

Routed disease-specialist models and a graph-checked LLM for rare-disease drug repurposing; case study, lysosomal storage disorders. Offline: PrimeKG (20 sources, 17,080 diseases) partitioned into about ten MONDO areas, one RotatE link-prediction model per area (PyKEEN), stored in Neo4j for linking and evidence paths. Online: a router picks the top two specialists, they score in parallel (FastAPI), an aggregator merges percentiles weighted by router confidence, Cypher finds evidence paths of at most three hops with hubs penalised, a local LLM explains and every claim is checked; React and D3 interface. Graph frozen at December 2023 and leakage-checked. Strict test: where Arimoclomol and Levacetylleucine rank out of about 8,000 for Niemann-Pick type C, while Miglustat must come back.

Fan-out multiplied the prefix, not the work.

Levers, in order of size

  1. Cap the orchestrator window at 150–200k (one phase per session, earlier compaction). Exposure: 39 % (FixFlow) and 74 % (Clinic) of cache-read tokens sit in calls past 200k.
  2. Strip the subagent prefix. About 60k tokens per agent window, 27 % of all tokens, 47 % of FixFlow's. Deferred tool schemas, fewer connectors and no skills in agent sessions remove most of it.
  3. Fewer steps. 58 % of calls only read or search; batching two lookups into one command removes about a third of all calls, and with them a third of the re-reads.
  4. Stop carrying the model's own output. 31 % of Clinic's tokens. Write large files through a script instead of inline tool content; compact after a write-heavy phase.

Not the bottleneck

  • Model mix. Opus made 65 % of calls and read 52 % of tokens; Fable 6.5 % of calls, 16 %; Sonnet 28 %, 32 %. Routing changes the rate per token, not the token count.
  • File reads. 26 % of tokens, and only 0.5–1.5 % of a window is content re-fetched inside the same window. A session-local read cache saves almost nothing.
  • Any one file. The hottest file in either repo is 1.5 % of its tokens.
  • Human prompts. 80 and 151 real prompts, about 162 API calls each. The usage is in the machine's steps.

1.2 Caching: seven findings

"Caching" meant several different things across the tracks. Each finding below rests on a number from the transcripts or from a trial that was run.

1
Prompt caching already works. The cost is re-reading, not first reads. M
98.2 % of the context sum is cache reads: 4,253M cache-read, 78M cache-write, 20M output, about 0 uncached input. Price-weighted with cache reads cheap, the fill shares hold (fetched 27.5 %).
2
A session-local file cache saves almost nothing. E
Exact repeats inside a window are 0.00 %; content truly seen before in the same window is 0.5–1.5 %. "Opened again" (7.0 % of context) is mostly a different range of the same file. Lines re-read with no edit between are 0.5 % of tokens.
3
A cross-session hot set exists, but no digest has been shown to replace the lines. E
3.3 % of paths (72 paths) hold half of the fetched tokens; paths read in five or more windows hold 73 %; 74.2 % of fetched tokens went to files the window never edited. Fetched content entered once as about 19M tokens and was processed about 950M times, about 50 passes per token. The form that could pay "lasts across sessions and returns something shorter than the lines. Nothing has shown that a shorter digest can stand in for the lines."
4
A graph-traversal cache has nothing to save. M
All 477 "what depends on this file" queries on the FixFlow graph take about 1 ms together. Cross-session re-reading "is the knowledge store's ground, not a graph's."
5
A lookup appended as a tool result keeps the prompt cache; an injection at the top breaks it.
Graph or index output must be pulled as a tool result, never pushed into the system prompt or CLAUDE.md, where every commit would invalidate the cached start of every window.
6
Heavier context machinery lost to a notes file. M
A snapshot/restore compaction adapter on another project: same recall (15 of 15) and task success, but +6.1 % tokens over a plain notes file and +17.0 % over native compaction; final audit "context gain proven: false". A compact context packet trial: identical acceptance, near-identical time. A synthetic packet pilot: 20.6 % fewer bytes, no outcome measured. A corpus map: 3,361 records for a 167 KB corpus, extraction recall 0.52, its validation contract never run. In the compile's words: "a disciplined short notes file matched the heavier machinery, and nothing here was shown to save tokens."
7
Unknown: how cache reads count against the five-hour limit.
October used about 778M tokens, 94 % cache reads, with 14 limit episodes; subagents caused 91 of 104 limit errors and made 82.4 % of 4,155 calls. Until the counting rule is known, no cut to cache-read tokens can be promised to reduce limit stops.

1.3 The reasoning-cache library (modelled; no verdict)

The library is a separate memory of strong-model solutions. A cheap model (Sonnet) fetches a stored solution, adapts it and uses it; a problem it cannot solve climbs a ladder (Sonnet, Opus, Fable), is solved once and stored. The unit is a fix-sized task of about ten cheap calls; one period is 30 days. Three ways of working were modelled: the strong model directly, the cheap model with the ladder and no library, and the cheap model with the library. The map has 40 states, 83 branches and 61 settings M; of its 60 drawn unknowns, 51 are guesses G, 7 come from outside studies S and 2 are measured M.

A cached answer is reused only if all of these hold: an entry exists; a lookup is triggered; the right entry comes back; it is good, not bad; it passes the screen; it is in the window when needed; and the cheap attempt then comes out right.

1.4 The repo graph test (built and tuned; held-out not run)

The question: does a typed graph of the repository help an agent find the right files better than text search or a relational store? The first test (a file-level in-memory graph: 618 files, 1,119 code links, 1,086 doc citations, 197 KB, 0.2 s to build; one query; 200 sampled searches of which about 7 % were connection questions) concluded "no graph database, no cache, few tokens to win". The owner rejected it on 2026-11-12: a self-made graph was compared with an established relational engine; there was no ranking, no hop tuning and no algorithm tuned to this repo; the scoring ignored the value the answers carry; the repo was the wrong test bed. The verdict was withdrawn and a protocol frozen before any arm was built.

The frozen protocol

  1. Four things vary separately: FACTS (which typed nodes and edges exist) × ALGORITHM (direction, hop budget, ranking) × OUTPUT (what the model receives, in tokens) × ENGINE (where the facts live). Given identical facts and algorithm, two engines must return the identical answer; a mismatch is a bug, not a result. The engine is scored on what it does change: native algorithms, query effort, latency, size, memory, update cost.
  2. Seal the held-out set first. FixFlow main at a31924a; 140 usable task commits split by date: 65 TUNE (June) and 75 HELD-OUT (July–August). Nothing is ever tuned on HELD-OUT; it is run once. Never in a query: the commit message, files added by the task commit, anything from the task commit or later.
  3. Arms and floors. Scripted text search (what sessions do today); two floors every arm must beat (same directory, plain co-change); SQLite with a strong design; an established graph engine with its native algorithms; cross-checked re-implementations whose outputs must be identical on TUNE before anything is scored. One shared packer and tokenizer.
  4. Sweep on TUNE only, then freeze the hash. Hops 1–6 and unbounded; per-edge-type budgets (metapaths); direction; edge classes added one at a time; ranking (traversal order, degree-normalised, personalised PageRank at restart 0.15/0.30/0.50, co-change weights, text-match, hybrids); hub handling (in-degree cuts at 5, 10, 15; transport-node exclusion); granularity; output form; token budget 2k/4k/8k/16k. Choose the simplest configuration within one standard error of the best. Report whole curves, never one point.
  5. Primary metric: recall of the reference files and definitions within an 8,000-token answer on T1 HELD-OUT. Smallest difference worth acting on: 0.05 recall. With 75 held-out commits the smallest detectable difference is about 0.09, so "inconclusive" is a likely outcome and is reported as "no evidence either way at this size", never as "the graph does not help." A design wins only if its interval excludes zero, its median tokens per answer are no higher, and the sign agrees on at least three of T1, T2, T3, TQ.

What the verifiers corrected in the research

  • The 2026 study crediting the graph for gains is superseded by its v2 (9 Nov 2026), which credits the embedding index.
  • The engine benchmark summary (DuckPGQ best) was stale; the newer README puts FalkorDB, a CSR engine and Ladybug ahead.

  • Co-change coverage drop comes from new files, not renames. The critic noted that same-commit co-change as ground truth favours co-change predictors, and that the research was not yet enough.

How far the build got

  • Build A: facts, sealed tasks, relational and search arms. 188 parent builds, byte-identical rebuilds, 1,569 tasks; relational and reference agree with 0 mismatches on 25,120 comparisons; 8 facts-audit defects found and fixed.
  • Build B: the graph engines (LadybugDB, DuckDB with DuckPGQ), already running in a Docker image.
  • Build C: stage-1 sweeps and grading on TUNE (chart above). File-granularity recall degenerated because padded answers list every file, so the primary is restricted to signature and snippet forms.
  • Build D: frozen records and an 85-run held-out plan; question runs were held, then lifted after two preflight fix rounds. No held-out run is recorded. Waiting on the owner: the engine choice is formally his, the S2 community-draws question, whether to run the quiet-machine bench, and the held-out run itself.

Lessons the documents state, in their words

  • Verify a plan rewrite by content, not by commit message.
  • Write the gate record before dispatching the next workflow.
  • Allocate a capped verification budget by priority, not first-come (G2 lost its skeptics to the first four analysts).
  • An "accepted" row must never sit beside a failed AFTER check. Unknown is recorded as "unknown", never 0.
  • Decisive checks use if/raise, never a bare assert.
  • The resolution for long sessions is procedural, not tooling: one phase per new session, state in the repo, a Plan @ sha line and a decisions list in the draft PR body.
  • Give the assessment the actual text it is to judge; an idea sweep that reads records, not code, is a proposal, not a finding. Every §9 proof in the compile is a proposal; nothing there was run except the token tally.

Harness v2, the design that follows from all this, runs in five phases sized by these measurements: keep the work safe (sized by the 25 power-offs); one fast check (855 s → 284 s); gate and review as six no-token scripts (29 of 87 sweep ideas fit); first use on a real host; one token budget per window with the compaction trial narrowed to Sonnet slice sessions. Twenty-three owner decisions are listed; six are answered.

Part 2 · What this means for CureFound

2A. For CureFound's own design and evaluation

The strongest links are not about tokens. They are about how to test a graph-and-ranking system honestly when the positives are few, which is the exact problem the graph protocol was written to solve. Each item names the number it rests on.

1. Separate facts, algorithm, output and engine, as the graph protocol does.
Three engines gave identical answers given identical facts and algorithm. Neo4j is an engine choice: score it on native algorithms, latency, size on disk and query effort, never on answer quality. Tune the PrimeKG edge set first (make each edge class switchable, as the protocol did) and the ranking second, and keep a relational or in-memory reference arm so that any mismatch is caught as a bug.
Rests on: relational = LadybugDB = DuckPGQ at 0.7843; 0 mismatches on 25,120 comparisons; byte-identical rebuilds of 188 parent commits.
2. Hop depth trades recall against precision; the hub penalty and ranking carry the precision.
On code graphs, going from 1 to 3 hops took recall from 0.38 to 0.87 while precision fell from 0.32 to 0.06. CureFound's three-hop evidence paths will be high recall and low precision, so sweep hops 1–3, hub in-degree cuts and per-edge-type budgets (metapaths) rather than one global hop limit. Hybrid rankers beat single rankers only slightly here, so expect modest gains from combining the specialist score with path-based ranking, and measure them.
Rests on: recall 0.38 / 0.72 / 0.87, precision 0.32 / 0.11 / 0.06 at 1 / 2 / 3 hops; top-10 precision 0.26 co-change, 0.24 PageRank, 0.28 combined.
3. Name the floors every arm must beat, and beat them by a pre-registered margin.
The plain co-change floor came within 0.03 of the tuned graph on the tuning set. CureFound's floors are degree or popularity ranking (the Bonner 2022 hub bias itself, which the title defense already names) and an unpartitioned single model of the TxGNN kind. The specialists have to beat both, and the margin has to be declared before the run.
Rests on: co-change floor 0.7521 vs tuned 0.7843; search 0.7394; same-directory 0.7191.
4. Pre-register the protocol, and say what "inconclusive" is called before any arm exists.
Seal the held-out set, sweep on the tuning set only, declare one primary metric and a smallest difference worth acting on, report whole curves, and decide the wording of a null result. CureFound's strict test has two held-out positives for one disease; at that size the smallest detectable difference is enormous, so the honest report is "no evidence either way at this size", never "the specialist helps" or "does not help". Gain power the way the protocol does: many diseases in the lysosomal area, with approvals split by date into a tuning period and a held-out period, and a rolling-origin re-run over several split dates as a secondary analysis.
Rests on: 75 held-out commits → smallest detectable difference about 0.09 against a declared 0.05; split 65 TUNE (June) / 75 HELD-OUT (July–August).

5. Apply the protocol's leakage rule, not just a date freeze.
The protocol never lets a query see the commit message, files added by the task commit, or anything from the task commit or later, and it drops same-PR sibling commits from co-change. For CureFound that is: nothing dated after the December 2023 freeze, and also drop evidence edges that derive from the publication that reported the approval, which a date freeze alone does not catch.
Rests on: the sealed task sets T1–TQ and the "never in a query" rule; the critic's note that same-commit ground truth favours co-change predictors.
6. The one thought-structure with evidence is candidate selection by an executed check.
Tree and graph prompting showed no gain over plain sampling on current models. Choosing among candidate fixes by an executed test did. That maps directly onto "explain + verify": generate several candidate explanations or evidence paths and keep the one that passes the graph check, instead of one long chain of reasoning that is then checked once.
Rests on: 25.7 % → 27.0 % → 32.0 % resolved (SWE-bench Lite, 40 candidates per issue) S.
7. Instrument the grounded-LLM pipeline as a funnel, not one end accuracy.
A retrieved fact helps only if it exists, is retrieved, is the right one, is good, passes the check, is in the window, and the model then gets it right. In the library model the match and capture steps carried most of the weight, and in real cases the check step broke most often. CureFound's stages are MONDO linking hit, evidence path found, path passes the verifier, and claim consistent with the path. Record each pass rate separately; the product tells you where to work.

8. Caching for the explainer LLM: stable prefix first, per-query evidence last, claim checks batched.
A lookup appended as a tool result keeps the prompt cache; an injection at the top of the window breaks it. Cost is calls × window, so one call that checks all claims against the path costs a fraction of one call per claim. Do not carry long earlier outputs forward between checks.
Rests on: 98.2 % of the context sum is cache reads; 54.6 % of calls only read or searched and re-read 43.6 % of tokens; the model's own output is 26–32 % of a window.
9. A caveat on scope.
The harness research ruled out "a model-extracted graph, graph server and embeddings" for navigating a code repository, and the one 2026 study that credited a graph was superseded by a version crediting the embedding index. Both verdicts are about repo navigation, not about CureFound, whose task is link prediction where embeddings are the method. Take the evaluation discipline, not the verdict.

2B. For building CureFound with Claude Code agents

If CureFound's code, training scripts and interface are built by agents the way FixFlow and the Clinic Workshop were, the token and reliability findings apply directly. The failure shape of free-tier Colab and Kaggle sessions is the same as the power-offs here: work is lost unless it is checkpointed and resumable.

1. Budget = calls × window.
One phase per session with state in the repo; cap the orchestrator window at 150–200k; compact earlier rather than at the limit.
Rests on: 39 % and 74 % of cache-read tokens in calls past 200k; main-session windows of 396k and 333k per call; 48 compactions, 38 of them at the Opus 367k trigger.
2. Strip the agent prefix.
Each agent pays about 60–70k tokens before any work, 34k of it tool definitions and roughly 50k schemas in all. Fewer tools, connectors and skills in agent sessions; deferred tool schemas; a short tool list for gate subagents (decision D18 in the harness design).
Rests on: fixed prefix 27 % of all tokens, 47 % of FixFlow's; 1,118 agent windows of about 12 calls each.
3. Batch lookups.
58 % of calls only read or search, and each is a full re-read of the window. Two lookups per command removes about a third of calls and their re-reads.
Rests on: 64 % / 52 % of calls were read or search only, holding 55 % / 41 % of tokens.
4. Write big files through a script, never by echoing their contents through the model.
Training configs, partition manifests and generated data should be produced by a script the agent runs, not pasted as tool content; compact after a write-heavy phase.
Rests on: the model's own earlier output is 31 % of Clinic's tokens (thinking 12 %, echoed commands 9 %, written file contents 8 %).
5. Keep the work safe.
The harness answer to 25 unexpected power-offs is an off-machine copy, a resume list and a restart chain. For specialist training on Colab and Kaggle that is a checkpoint per disease area, a resume list of which areas are done, and a nightly copy off the session. "Update one disease area at a time" is already the right partition for cheap restarts.
Rests on: 25 power-offs since 1 October, build load explaining at most 6; the clinic repo kept with no remote by choice.
6. Size parallel runs from one measured peak-memory number.
The 3.0× on the check came from slots sized by measurement, not by guessing. Running ten RotatE specialists at once on one machine needs the same single measurement first.
Rests on: 855 s → 284 s over 12 runs; two containers at once 266–267 s against about 440 s in a row.
7. Run verification by priority, record the gate before the next step, verify by content.
Allocate a capped verification budget by priority, not first-come; write the gate record before dispatching the next workflow; "unknown" is recorded as unknown, never 0; decisive checks use if/raise, never a bare assert; verify a rewrite by content, not by commit message.
Rests on: G2's 12 skeptics consumed by the first four analysts; the review's 7 refuters lost to a usage limit; a plan rewrite once verified only by its commit message.
8. Skip the heavy context machinery for now.
A disciplined short notes file matched a snapshot/restore adapter and a compact packet; the library is unproven and at parity in its own model; a session read cache saves about nothing. Spend the effort on a good CLAUDE.md, a memory index and project documents, which is where all six seen savings came from.
Rests on: +6.1 % / +17.0 % tokens for the adapter at equal recall; library 1.03 / 1.01 against the ladder; in-window repeats 0.5–1.5 %; 6 of 15 savings seen, all through existing notes.
