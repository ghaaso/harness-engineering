# refute:KS-V3:repo

**Claim:** KS-V3  **Lens:** repo  **Verdict:** NARROWED

`ks record --lookup` does give v_missed_existing a writer, but the claim as written fails on four points. "Existed at the lookup's index watermark" has no mechanical meaning with the data §3.6 keeps. The term-overlap class labels 6 of 7 measured paraphrase misses "threshold" and labels a different-symptom sibling "vocabulary". k ≥ 3 has no denominator or window and is not expected to fire before KS-9. And any tier can write the counted outcome by hand. The dense carve-out fixes the coverage-0 dead end in principle, but it is unspecified against the status filters and has no calibrated floor.

## Attacks

- **[fell]** 1. Replay 'at the lookup's index watermark'. Is the watermark state reconstructible (event set, recipe version, thresholds), or does the replay run against today's index and over-count?
    - evidence: Design §3.6 l.290: the lookup row keeps the canonical query, handles, internal top-20 with features, what was shown, thresholds fired, gate verdict, outcome, tokens, model, tier and wall time. It records no watermark, no journal digest, no runner/schema version and no visible-entry set. Per-event provenance (l.247) adds recipe_version and scrub_ruleset_sha only, with no timestamp; architect-A's `recorded_at` ('informational') is not repeated in §3. The index 'watermark' is a sha256 over sorted event ids (l.228, l.402 'built from event set X'), which is not invertible. Rebuild ingests in (lamport, event_id) order (KS-F4), so ingest order is lost. Lamport counters are per-entry, so there is no global clock. Lookups live only in the host-local log and 'a restore excludes lookups by design' (l.226, §5.6 l.361). The only as-of mechanism defined is 'fold the event set of a journal commit into a scratch index with the same tools/ks version' (l.361). A lookup is not tied to any journal commit: mechanical events are committed only at `ks close` (l.223), while the index ingests files from disk. Measured: FTS5 MATCH never returns a row sharing no term with the query. In scratch match.mjs the right entry was absent for both paraphrases, and wrong entries came back on 'in'/'the'. So the stored top-20 holds no as-of evidence for exactly the class D16 counts. Mechanically, 'existed at the watermark' can mean only 'present in the index the detectors query now'. An entry recorded by a parallel session between the miss and the record (the §7.5 stampede, or §8 rule 3 lazy seeding) is then found by detector 1, ruled `same`, and counted.
    - consequence: §3.6: the lookup row must carry the index watermark, the tool versions and a corpus generation (a hash over the sorted (entry_id, content_sha) pairs visible at lookup time). The member list is persisted once per generation in the host-local log. §7.3 filters detector candidates by membership and classifies against the entry version in that generation. A lookup with no generation recorded yields 'unverifiable', never a count.
- **[fell]** 2. The detectors' false-'same' rate: the path join fires on shared files, Jaccard shares BM25's blind spot, and hindsight-worded draft handles find the entry the author already knows. Does that inflate k?
    - evidence: scratch join.mjs (read-only git) used 10 seed footprints built from the mainline fix squashes 2fe77f5, 1c546a3, da988e2, 79a8dd4, 6928828, c79bec7, ea48987, the 46 migrations and ex3's three files, fix_diff and check_input tiers only. 12 of 45 seed pairs share a file. customer_messaging/service.py and test_messaging_integration.py are in 4 footprints, CLAUDE.md in 3, and jobs/service.py, main.py and eas.json in 2. Of the 45 non-seed fix commits on main, 23 would surface ≥1 existing entry (mean 1.11, max 8). So the Opus ruling is the only filter and runs on about half of records. Detector 2's recall on KS-C10's same-cause repeats: only 1 of 4 pairs shares a changed file (b7a5b98→6928828 via package.json; 2f09cec→f29f62f, 789d522→0a3b38e and 75b51f9→981ae08 share none). The draft's hindsight wording does not reach the class, which is computed between the missed query and the entry. What inflates k is that a correct hindsight 'same' on a different-symptom sibling is labelled vocabulary. The ex1-shaped stdlib pair (Python's 'TypeError: comparing strings with non-ASCII characters…' against Node's 'RangeError [ERR_CRYPTO_TIMING_SAFE_EQUAL_LENGTH]…') shares zero porter terms (scratch terms.mjs [2]), and §8 rule 1 puts those siblings under one root_cause row.
    - consequence: §7.3/§7.4: define `same` as 'the draft would carry the entry's root_cause_id and fix'. A sibling with a different symptom is `related` and is classed handle_gap, never vocabulary. State that detector 2 misses most same-cause-different-file repeats, so v_missed_existing is a lower bound for that class too.
- **[held]** 3. The Opus ruling is an LLM relevance judgement (M-02 30) that now counts toward an install decision. What in the text bounds it?
    - evidence: Bounded only by §7.4 l.457 (the PR's Opus reviewer 're-checks every same/related/new ruling') and by D16 l.714 (the trigger only opens an owner decision: 'no model is installed before it fires'). §7.3 l.453 states the M-02 30 caveat explicitly. Not bounded by: a second independent ruling, any fixture or golden set for same/related/new, a recorded reviewer-agreement event, or any definition of `same` (none in §4.5, §7.3 or §7.4). The ruling also writes a `proposed_handle` (l.453), a retrieval change, though it activates only through KS-R3 approval.
    - consequence: §7.4: the reviewer's agree/disagree is written as an event, and D16 counts only rulings the reviewer agreed with. The KS-9 report lists each counted miss (query digest, entry id, class) so the owner reads the three items behind any trigger. Add KS-2 fixtures for the same/related boundary (the ex1 sibling pair).
- **[fell]** 4. Lower bound and denominator: does 'k of n' stop a tiny-n install, and what should the rule say?
    - evidence: D16 l.714 opens the install decision 'when k ≥ 3 vocabulary-class misses have been recorded', 'reported as k of n examined misses at KS-9'. n is reported, never gated, and no window is stated, so the ratchet the adjudication flagged (verdicts.txt l.147: '3 ever with no denominator ratchets toward an install') survives. scratch bounds.mjs gives one-sided 95% Clopper-Pearson bounds for k=3: n=3 lower 0.368; n=10 lower 0.087; n=20 lower 0.042; n=50 lower 0.017; n=300 lower 0.0027 (upper 0.026). Yet all of these fire identically. For a 5% lower bound at n=50, k ≥ 6 is needed. n counts only examined misses, and k does not ask for distinct entries: three misses of one entry before its proposed_handle is approved count as three.
    - consequence: §11 D16, §4.5, KS-9: fire only when k ≥ 3 vocabulary misses on ≥ 3 distinct entries, among n ≥ 10 examined error/prose lookups, with the one-sided 95% Clopper-Pearson lower bound on k/n ≥ the owner rate (default 5%, the old D16 arm). The count is windowed since the last recipe or threshold change. KS-9 reports 'insufficient data' when n < 10, never 'not fired'.
- **[fell]** 5. Cause pre-classification by term overlap after canonicalisation, scrubbing, stemming and stop words: can a class be a recipe artefact, and is edit distance computed on terms or on the query?
    - evidence: Measured with node:sqlite 3.53.4 FTS5 'porter unicode61' (scratch terms.mjs, coverage.mjs). (a) Placeholders tokenize as words: '<NUM>' and '{num}' give the term num, '<UUID>' gives uuid. Two unrelated masked texts share 'num' and land in 'threshold' (terms.mjs [4]). (b) FTS5 has no stop list and the design names none. Over a synthetic 15-entry corpus, 7 of 8 ex3-shaped paraphrase queries are misses (coverage < 0.3). Of those 7, six share incidental terms ('the', 'job', 'two', 'a', 'in') and are classed threshold; only 1 is vocabulary. 'settlement duplicated in the ledger view' has coverage 0.000 (the IDF of 'the' is clamped to 1e-6) yet shares 'the', so it is classed threshold. (c) A one-term typo ('dispacher', 'recieve') shares zero terms and so is both vocabulary and typo, and the design states no precedence. (d) Edit distance ≤ 2 is unspecified as term-level or query-level. At term level it fires on unrelated short tokens: app/api 1, pin/pid 1, jsx/tsx 1, main/mail 1, seed/need 1, py/js 2. At query level 'eas build failed' against 'gas build failed' is 1. Elasticsearch's AUTO fuzziness (exact for ≤ 2 chars, 1 edit for 3–5, 2 for > 5) still admits app→api. (e) The paths in a query normalise to tokens (backend, app, main, py) that are shared with any entry naming a Python file.
    - consequence: §4.5/§7.3 replace the KS-O17 rule with a precedence-ordered, IDF-weighted class. handle_gap: the query carried a tmpl/sig/frames/ctx/ident value the entry lacks. typo: an out-of-corpus query term of ≥ 5 chars within distance 1 of an entry term, or ≥ 8 chars within distance 2, computed per term. vocabulary: coverage of the missed entry < ε (e.g. 0.05), with placeholder tokens and a fixed stop list excluded from 'shared'. threshold: ε ≤ coverage < θ_cand. Golden fixtures go in KS-2.
- **[fell]** 6a. Dense-only carve-out against KS-F11 and §4.1: what stops a dense neighbour surfacing an entry that is refuted at this footprint, superseded, fixed_off_main or contradiction-capped? Is the status filter applied before or after the vector rank?
    - evidence: §4.4 l.321 adds 'a dense-only rank-1 hit with a rank margin may raise an entry to candidate', but §4.1 step 4 l.303 still defines a candidate as only 'coverage ≥ θ_cand or any exact handle or a lead-shaped hit'. The status, existence and contradiction filters sit in step 2 (l.301), before ranking (step 3), and §4.4 does not say the dense path passes through them. sqlite-vec docs (vec0 page): only vec0 metadata or partition-key constraints apply during KNN; a JOIN filter is not described. 'Refuted at this footprint' and the existence filter are per-caller predicates, so they cannot be vec0 metadata and must post-filter. Whether 'rank-1' and its margin are computed before or after that post-filter is unstated: a suppressed rank-1 then either shadows the true neighbour or hands rank-1 to an entry that was never separated by the margin. Precedence for KS-R4's one candidate slot between a lexical and a dense-only candidate is also unstated. fixed_off_main and conflict are already capped at candidate, so they are not worsened. KS-F11 is not contradicted: probe-in-lookup still never drops open_defect/do_not_apply.
    - consequence: §4.4 and §4.1 step 4: the dense path takes k ≥ 20 from the KNN, applies every step-2 filter, then computes rank-1 and the margin on the filtered list. Superseded entries redirect to the successor. The lexical candidate keeps the single slot when one exists. Add the dense disjunct to step 4's candidate definition.
- **[unverifiable]** 6b. Can a margin-only dense rule abstain on out-of-corpus queries?
    - evidence: A KNN always returns a rank-1. The carve-out has a margin but no absolute similarity floor, and the margin's units and calibration are unstated: KS-4 freezes only θ_lead, θ_cand and μ (§4.2 l.308), and KS-5's out-of-corpus 'must abstain' set never sees vectors. Measuring the false-candidate rate needs a pinned embedder, which cannot be installed here.
    - consequence: §4.4/§4.2: an absolute floor plus the margin, both calibrated by leave-one-handle-out on the hard-negative and out-of-corpus set and frozen as config.set before vectors are switched on, with the out-of-corpus candidate rate reported.
- **[held]** 6c. Does a dense candidate on a prose-only entry with no check spec dead-end?
    - evidence: §4.1 step 5 l.304: 'inconclusive behaves as a miss and escalates'. §7.1 l.433: `show` prints the summary and dead ends under an UNVERIFIED banner on a candidate, and the fix only after `applies`. For a rule_without_case entry, or Docker-only checks with Docker off, the candidate yields information and never the fix. That is the stated candidate contract, not a silent dead end.
    - consequence: §4.4: one sentence that a dense candidate follows the same rule (summary and UNVERIFIED negatives; no fix without an `applies` run).
- **[fell]** 7. RT-06: can a §4.5 view read zero for a reason other than 'no misses', and does 'unexamined' cover it?
    - evidence: 'unexamined' (l.325) counts only miss rows present in this host's index when `ks close` runs. Not covered: (i) an escalation with no lookup at all: there is no row, and §7.8 l.479 makes this self-reported. (ii) A lookup that exited 3: there is no lookup id to pass to --lookup (l.431). (iii) A restore or second host: 'a restore excludes lookups by design' (l.226). The §4.6 view (l.333) joins lookup.miss to outcome, so journaled missed_existing outcomes join to nothing and read 0. (iv) A rebuild on any tool-version mismatch (l.224): whether `rebuild` re-ingests store/local is unstated, so every recipe or scrub bump may zero every lookup-based view. (v) Worktree version skew: 'the old CLI rebuilds its own index file' (l.525), so lookups and records may sit in different index files. (vi) `ks close` never run because ks was missing or exited 3/4 (§7.6 l.467): no report. Covered: a miss followed by a record without --lookup, which is optional per l.436.
    - consequence: §4.5/§4.6/§3.1: missed_existing outcome events (journaled) carry the class, the lookup kind, the query digest, the corpus generation and the entry version, so the view survives restore and rebuild without the local lookup row. State that rebuild re-ingests store/local. Paths (i)–(vi) report NULL 'unknown' with a reason, never 0.
- **[fell]** 8. Can KS-O18's k ≥ 3 vocabulary misses fire in practice, given §7.3's record criteria, a ~15-entry pilot corpus and KS-C10's prior?
    - evidence: Main's history: 2026-05-31 to 2026-08-03 (git log), about 65 active days; 50 fix-prefixed subjects; KS-C10's 3–5 same-cause repeats give 2.6–4.3 repeats per 8-week KS-9 window. scratch bounds.mjs multiplies stated factors: earlier case in store, lookup made, lookup missed, vocabulary class (0.34 = Chaparro's title-only zero-term share as an optimistic ceiling; the measured class rate is 1/7, about 0.14) and recorded with --lookup. Optimistic: E[k] = 0.11–0.18 and P(k≥3) = 1.8e-4 to 7.9e-4 per window. Central: E[k] ≈ 0.01. Detector 2 sees 1 of 4 of the repo's repeat pairs. In-window the trigger is effectively decorative; over a year at optimistic factors, P(k≥3) is about 0.1.
    - consequence: §9 and D16 state this base rate. KS-9 reports k of n with the bound and 'insufficient data', so a non-firing trigger is never read as evidence that lexical retrieval suffices.
- **[fell]** 9 (own). Can k be fed without the record-time check and ruling?
    - evidence: §7.1 l.434 exposes `ks outcome <lookup-id> missed_existing --entry <id> --cause vocabulary|…` as a CLI verb, and passing --cause there sidesteps the 'mechanical' classification. 'Opus, from the record-time check' is policy only. The fold rejects only *curated* events from non-Opus or same-as-author actors (l.288), and §5.3 l.349 lists outcome among the mechanical events cheap agents append. Writer identity is self-declared (§5.3, §9). Any tier can therefore write the outcome that D16 counts, with a hand-picked cause.
    - consequence: §7.1/§3.6: remove missed_existing from `ks outcome`; only `ks record --lookup` writes it. The class is computed by the CLI and never taken from argv. The fold rejects a missed_existing outcome without a same-session `recorded` event and a reviewer-agreement event.
- **[fell]** 10 (own). Does n mean what D16 needs, given lookup kinds and the single --lookup id?
    - evidence: Every lookup prints 'KS miss|candidate|lead <id>' (l.431), and §7.2 l.446 adds three `--diff` lookups per code phase that are mostly 'nothing protected'. Those are recorded as misses, so the 'unexamined' count and any miss-based denominator are dominated by diff, action and prescription lookups that are not defect lookups. `ks record` takes one --lookup id (l.436) while a solve can follow several step-zero lookups (§7.2); the rest become 'unexamined' though they belong to the same examined solve.
    - consequence: §3.6: a lookup `kind` ∈ {error, prose, diff, action, prescription}; n and 'unexamined' count error/prose kinds only. `ks record --lookup` accepts every lookup id that preceded the solve.

## Counter-evidence

1. Nothing defines the watermark. §3.6 (l.290) stores no watermark, generation or tool versions on the lookup row. The index watermark is a non-invertible digest (l.228, l.402). Lookups are host-local and excluded from restore (l.226). The only as-of mechanism is per journal commit (l.361), which a lookup is not tied to. FTS5 MATCH never returns a zero-overlap row, so the stored top-20 keeps no as-of trace of a vocabulary-class entry (measured).

2. The cause classes are recipe artefacts, measured with node:sqlite FTS5 'porter unicode61'. Masked placeholders become shared terms ('<NUM>' gives num). With no stop list, 6 of 7 paraphrase misses over a synthetic 15-entry corpus are classed threshold, one of them at coverage 0.000. The ex1-shaped stdlib sibling messages share zero terms and are classed vocabulary, though they are a different symptom of one root cause. A one-term typo is both typo and vocabulary. Term-level edit distance ≤ 2 matches app/api, pin/pid, jsx/tsx and main/mail.

3. The trigger is not gated by n. D16 (l.714) fires at k ≥ 3 regardless of n: 3/3 has a 95% lower bound of 0.37 and 3/300 of 0.0027, and both fire.

4. The trigger is not expected to fire in the KS-9 window. At KS-C10's prior and optimistic factors, E[k] ≤ 0.18 and P(k≥3) < 10⁻³ per 8-week window.

5. Detector 2's coverage cuts both ways. It surfaces ≥ 1 seed entry for 23 of 45 non-seed fix commits on main, but finds only 1 of the 4 same-cause-different-file repeat pairs.

6. The counted outcome is open to any tier. `ks outcome … missed_existing --cause` is an any-tier mechanical verb that the fold does not reject (l.288, l.349, l.434).

7. The §4.6 view can read zero for the wrong reason. Its join over host-local lookups returns 0 after a restore, a rebuild or a lookup-free escalation, and 'unexamined' covers none of these.

8. The dense path is unspecified against the step-2 filters. The status, refuted-at-footprint and existence filters sit before ranking (l.301). §4.1 step 4 (l.303) was not amended. sqlite-vec applies only vec0 metadata constraints during KNN, so the per-caller filters must post-filter, and §4.4 does not say whether rank-1 and its margin are computed before or after that post-filter.

## Narrowed claim

What survives:

- `ks record --lookup <id>` gives v_missed_existing the writer v1.2 lacked. The record-time Opus examination is the right place for it, and a journaled missed_existing outcome can make the measurement a lower bound.
- Admitting a dense-only hit at candidate level is the only way an installed embedder could ever recover a coverage-0 miss.

What fails as written in v1.3:

- "Existed at the lookup's index watermark" is not computable from the data §3.6 keeps, so the check runs against today's index and can count entries recorded after the miss.
- The term-overlap class sends most real paraphrase misses to "threshold" and sends different-symptom same-cause misses to "vocabulary". So k does not measure what embeddings would fix.
- k ≥ 3 is ungated by n and unwindowed, and at the repository's recurrence prior is not expected to fire before KS-9.
- Any tier can write the counted outcome by hand.
- The §4.6 view reads zero after a restore or rebuild, and after escalations made without a lookup.
- The dense carve-out has no stated filter order and no calibrated floor.

With the amendments, the mechanism is a lower-bound measurement that can open the D16 question, not decide it.

## What would settle the unverifiable items

Settled here by measurement: the cause-class behaviour, the footprint-join reach, the bounds and the expected-k arithmetic.

Open items and what would settle each:

1. **Dense false-candidate rate (6b).** After a D16 install, run KS-5's out-of-corpus and hard-negative probes through the dense path at the frozen margin and floor, and report the candidate rate. This needs the pinned bge-small and sqlite-vec, which cannot be installed here.
2. **Over-count in practice (attack 1).** A KS-2 fixture: a lookup misses; an entry is recorded by another session; the solver then records with --lookup. The check must not count it.
3. **Restore and rebuild survival (attack 7).** A KS-2/KS-8 fixture: `ks rebuild`, and a restore to a scratch clone, must leave v_missed_existing unchanged.
4. **Same/related agreement (attack 3).** A reviewer-agreement count over the first ten rulings at KS-9.

## Proposed amendments

- **§3.6 (lookup row)** — Add to every lookup row: the index watermark (the meta journal digest); schema, recipe_version, runner_version and scrub_ruleset_sha; a corpus_generation (sha256 over the sorted (entry_id, content_sha) pairs visible to this index), with the member list written once per generation to the host-local log; and a lookup kind ∈ {error, prose, diff, action, prescription}. State that `ks rebuild` and a version-mismatch rebuild re-ingest store/local. _(why: Attacks 1, 7 and 10: 'existed at the watermark' is otherwise undefined and lookup-based views reset on rebuild.)_
- **§7.3 (missed-existing check)** — Replace 'the entries that existed at that lookup's index watermark' with: the detectors' candidates are restricted to members of the lookup's corpus_generation, and the class is computed against the member version (content_sha) under the lookup's recipe_version. A lookup without a recorded generation, or whose member list is not on this host, yields `missed_existing_unverifiable`, never a counted outcome. `ks record` accepts every --lookup id that preceded the solve. State that detector 2 (the fix-diff join) found only 1 of the repository's 4 same-cause-different-file repeat pairs, so the view is also a lower bound for that class. _(why: Attacks 1, 2 and 10.)_
- **§4.5 (cause classes) and §12.7 KS-O17** — Classes in precedence order, computed by the CLI. handle_gap: the query carried a tmpl/sig/frames/ctx/ident value the entry lacks, i.e. a different manifestation of the same cause. typo: an out-of-corpus query term of ≥ 5 characters within edit distance 1 of an entry term (≥ 8 characters within 2), computed per term. vocabulary: IDF-weighted coverage of the missed entry below ε (owner parameter, start 0.05), with masked placeholder tokens (num, uuid, path…) and a fixed stop list excluded from 'shared'. threshold: ε ≤ coverage < θ_cand. KS-2 golden fixtures: the ex1 Python/Node sibling messages are handle_gap; a paraphrase set is vocabulary; a placeholder-only overlap is vocabulary, not threshold; a one-term typo is typo. _(why: Attack 5: the raw zero-shared-terms rule classed 6 of 7 measured paraphrase misses as threshold and classed the different-symptom sibling as vocabulary.)_
- **§11 D16, §4.5, §12.7 KS-O18, §10 KS-9** — The install decision opens only when all of these hold: k ≥ 3 reviewer-agreed vocabulary misses on ≥ 3 distinct entries; n ≥ 10 examined error/prose misses of existing entries; the one-sided 95% Clopper-Pearson lower bound on k/n ≥ the owner rate (default 5%). Count within a window since the last recipe or threshold change. KS-9 reports k, n and the bound, and says 'insufficient data' when n < 10. Add to §9: at KS-C10's prior, E[k] per 8-week window is below about 0.2 even with optimistic factors. _(why: Attacks 4 and 8: k ≥ 3 fires identically at 3/3 and 3/300 and ratchets over time; the in-window base rate makes the bare count decorative.)_
- **§7.1 (ks outcome) and §3.6 (fold)** — Remove `missed_existing` and `--cause` from `ks outcome`; only `ks record --lookup` writes the outcome, with the class computed by the CLI. The fold rejects a missed_existing outcome that has no `recorded` event from the same session and no reviewer-agreement event. _(why: Attack 9: as written, any tier can increment k with a hand-picked cause, because outcome is a mechanical event the fold does not reject.)_
- **§7.4 (who confirms)** — Define `same` as 'the draft would carry the existing entry's root_cause_id and fix; the record extends that entry instead of creating one'. A sibling with a different symptom or fix is `related`, and only `same` counts. The reviewer's agree/disagree is written as an event, and D16 counts only agreed rulings. KS-9 lists each counted miss (query digest, entry id, class) for the owner. _(why: Attacks 2 and 3: the same/related boundary decides whether a miss counts, and the only bound on the LLM ruling is the re-check.)_
- **§4.5/§4.6 (views) and RT-06** — Make v_missed_existing a view over journaled outcome events that carry the class, lookup kind, query digest, corpus generation and entry version, not a join to host-local lookup rows. Each of these reports NULL 'unknown' with a reason, never 0: no lookup log on this host (restore or second host); lookups in another index version; `ks close` not run; exit-3 lookups. KS-9 reads the self-reported escalations-without-lookup beside it. _(why: Attack 7: after a restore or rebuild, and after lookup-free escalations, the §4.6 join reads 0 and 'unexamined' does not cover it.)_
- **§4.4 and §4.1 step 4 (dense carve-out)** — The dense path takes k ≥ 20 from the KNN and applies every step-2 filter (superseded redirects to the successor, withdrawn dropped, refuted-at-this-footprint suppressed, existence demotion, contradiction cap). These are per-caller predicates that cannot be vec0 metadata, so they post-filter. Rank-1 and its margin are then computed on the filtered list, and the hit must also clear an absolute similarity floor. Floor and margin are calibrated by leave-one-handle-out on the hard-negative and out-of-corpus set and frozen as config.set before vectors are switched on. The lexical candidate keeps KS-R4's single slot when one exists. Add the dense disjunct to step 4's candidate definition. A dense candidate follows the candidate contract: summary and UNVERIFIED negatives, never the fix without `applies`. _(why: Attacks 6a and 6b: filter order and slot precedence are unstated, a KNN always returns a rank-1, and the margin is uncalibrated.)_
- **§10 KS-2 Done-when** — Add: an entry recorded after the miss is not counted; the ex1 sibling pair is handle_gap; the paraphrase fixtures are vocabulary; a placeholder-only overlap is not threshold; `ks rebuild` leaves v_missed_existing unchanged; `ks outcome` refuses missed_existing. _(why: Attacks 1, 5, 7 and 9: the current done-when ('a same ruling lands a missed_existing outcome with a cause class') tests none of the failure paths.)_

## Changes a §12.7 ruling?

This verdict changes three §12.7 rulings:

- **KS-O17:** the mechanical cause pre-classification (zero shared terms = vocabulary; partial overlap below θ_cand = threshold; edit distance ≤ 2 = typo; missing handle kind = handle gap) is replaced by a precedence-ordered, IDF-weighted classification with placeholders and stop words excluded. `missed_existing` is also removed from the any-tier `ks outcome` verb, and 'existed at the lookup's index watermark' is defined as membership in a corpus generation recorded on the lookup row.
- **KS-O18:** 'k ≥ 3 … reported as k of n' becomes a gated rule. It needs k ≥ 3 on distinct entries, n ≥ 10, a one-sided 95% lower bound ≥ the owner rate, and a window since the last recipe or threshold change. The point-3 adjudication's own fourth incompleteness (the ratchet) is not fixed by v1.3's text.
- **KS-O19:** amended, not reversed. The dense path applies the step-2 filters before rank-1 and margin are computed, carries a calibrated absolute floor, and is added to §4.1 step 4's candidate definition.

## Could not run

- The dense-path false-candidate rate on out-of-corpus queries: it needs sqlite-vec and a pinned bge-small through transformers.js, and nothing may be installed.
- Any replay against a real store index, corpus generation, host-local lookup log or `ks rebuild`: tools/ks and the store do not exist.
- The real seed footprints' `read` tier (transcript-parse captures), which would only widen detector 2's join; it was measured on the fix_diff and check_input tiers alone.
- The recurrence factors (share of repeats whose first case is in the store, lookup compliance, record rate): stated as assumptions in bounds.mjs, not measured; KS-0 and KS-9 measure them.
