# lane:T-01

lane=T-01 tool_status=ok facts=28 candidates=16

## Summary
Caching/memoization prior art says four things for this store. (1) Treat each entry as a memoised task with a recorded dependency trace: a set of (dependency, content-hash) pairs captured at the moment the discriminating check last passed (Shake verifying traces, Bazel/CloudBuild constructive traces, rustc red-green). Dependencies must include environment (Node, Expo SDK, Gradle, OS), because untracked dependencies are the documented way such caches go wrong (a la carte 6.3; Bazel remote-caching docs). (2) Invalidate by event, lazily, with early cutoff: a changed dependency only marks the entry 'needs re-verify'; the reader re-runs the check; if it still reproduces the root cause the entry is re-stamped (Salsa backdating) rather than discarded. TTL is at most a backstop; the web-cache evidence (Gwertzman/Seltzer) accepts a few percent stale, which this store cannot. (3) Negative entries follow RFC 2308: scoped to the narrowest key, carrying their authority and the world-state they were asserted against, bounded in life, and stored as tombstones so a stale writer cannot resurrect a refuted entry (Cassandra tombstones). A cached 'no' is a lead to retry when dependencies change, never a prohibition (RFC 8767 warns stale negatives delay newly valid answers). (4) Write-through at fix time with a provisional status and a compare-and-set against the code version the check actually ran on (Facebook 'stale sets' and leases); the cheap reader performs read repair by appending mechanical confirmed/refuted events, never rewriting the diagnosis (Dynamo, Cassandra). Serve-stale (RFC 5861/8767) inverts here: a stale entry may be shown only as a flagged hypothesis. Most infrastructure cited (Dynamo, Skyframe, Facebook memcache) is orders of magnitude too large; borrow the ideas only.

## Candidates
- **Per-entry dependency trace (verifying-trace pattern): (dependency, content-hash) pairs captured when the check last passed** [technique] strong — Direct repurposing of Shake/Bazel/rustc traces. ## Design implications
- (strong) Key the validity of an entry on a recorded dependency trace, not on age: for each entry facet (diagnosis, fix, each failed approach) store the (dependency, content-hash) pairs it relied on when its discriminating check last passed. Dependencies must include the check command itself and environment dimensions (Node, Expo SDK, RN, Gradle/NDK, OS, Postgres version, which service is deployed from which directory), because untracked dependencies are how memoisation silently goes wrong. [F01, F03, F05, F07, F27]
- (strong) A trace match is necessary but not sufficient; a trace mismatch is not refutation. Order the lookup pipeline: fuzzy symptom match proposes candidates, trace comparison classifies each as unchanged or drifted, and the discriminating check on current code decides. Never act on a hit without running the check, regardless of trace state; use the trace only to label, rank and decide how loudly to warn. [F02, F03, F09, F28]
- (strong) Invalidate by event and lazily with early cutoff: a changed dependency only marks the entry 'needs re-verify' (computed from git diff and lockfile diff at phase boundaries or at read time, no daemon). If the check still reproduces the root cause, re-stamp the trace to current hashes (backdating) and record a confirmed event instead of dropping the entry. This keeps false invalidation and owner workload low. [F02, F08, F09, F10, F17]
- (strong) TTL is not a validity mechanism for this store. Web-cache literature accepts several percent stale for bandwidth savings; this store's dangerous failure is a false positive. If used at all, age only schedules re-verification of entries whose dependencies are weakly tracked, and never extends validity. [F16, F15, F26]
- (moderate) Do not combine facets from different verification states into one answer (Frankenbuild). An entry's diagnosis, fix and failed-approach facets each carry their own trace and status; a consumer should take a facet only if that facet verifies, and must not splice a still-valid diagnosis from entry A with a fix from entry B verified in a different environment. [F04, F03]
- (strong) Negative entries follow RFC 2308: (a) a 'failed approach' claim is scoped to the narrowest key, carries its evidence and the trace under which it was observed (the SOA analogue: no authority, no caching), has bounded life tied to its trace, and is presented as an ordering hint rather than a prohibition because a refuted approach may become viable after dependency changes and stale negatives delay newly valid answers; (b) a plain miss is never stored as a claim that 'nothing exists', only logged as a miss event for the hit/refute/miss analytics and later linked to the entry created. [F11, F12, F14]
- (strong) Refuted and invalidated entries become tombstoned status rows (never hard-deleted, with evidence and commit), so a stale draft or a worktree holding an older copy cannot resurrect them, and so refute rates can be computed later. Apply a grace policy: a tombstone may be compacted only after no worktree or session older than it can still write. [F20, F18]
- (strong) Write-through at fix time: the solver writes a provisional entry when the fix lands, with the trace captured against the commit the check actually ran on, using a conditional write on expected base version to reject stale sets. Promote provisional to confirmed only after reproduction by a different agent or session. Write-back (deferred write) loses the diagnosis on session death or context compaction; write-around leaves the expensive derivation unrecorded. [F17, F21, F18]
- (strong) Repair on read, by the reader, but only mechanically: the cheap agent that runs the gate appends confirmed/refuted/invalidated events and re-stamps traces; semantic revision of the diagnosis or failed-approach list is queued for a stronger tier. Because read repair only touches entries that get read, run a cheap periodic dependency-hash scan at phase boundaries to surface drift in never-read entries. [F18, F19]
- (moderate) Consistency target is read-your-writes for the writing agent plus monotonic reads across agents (a refutation once seen is never un-seen), not strong consistency. Achieve it with an append-only event log and a derived status ordered by code lineage (commit ancestry the event was evaluated on) rather than wall-clock timestamps, so concurrent writers commute and a late 'confirmed' from old code cannot overwrite a newer 'refuted'. All agents and worktrees must reach one canonical store (single file path or server), since SQLite WAL is same-host only and per-worktree copies would be unreconciled replicas. [F18, F22, F23, F24]
- (moderate) Serve-stale semantics are inverted for this store: a drifted entry is returned only as a clearly labelled lead (diagnosis path, failed approaches, and 'STALE: dependencies changed: ...' with no actionable fix), and when the check cannot run in the current environment (for example an Android native build on the Windows box) the entry is shown 'unverified' and needs higher-tier or human confirmation before acting. [F13, F14]
- (weak) Optional: a short-expiry claim row at miss time stops two top-tier sessions from re-deriving the same defect in parallel (Facebook lease against thundering herd; Gray and Cheriton expiry so a crashed session does not block). Only worth building if parallel sessions on the same symptom actually occur. [F17, F25]

## Rejected paths
- Time-based expiry (TTL) as the primary invalidation mechanism — Web-cache evidence (Gwertzman and Seltzer) shows TTL and adaptive TTL accept several percent stale responses, tolerable for pages but not for a store where one false positive reuse is the dangerous failure. A TTL also expires still-valid entries and keeps invalid ones alive until the clock runs out. Event-driven, dependency-tracked invalidation is available because the dependency set (files, versions, platform) is knowable from git.
- Invalidate immediately when any dependency file changes (Make-style dirty bit) — A dirty bit cannot support early cutoff (a la carte 4.2.1): touching a large shared file would invalidate every entry that mentions it, producing mass invalidation and eventually owner distrust. Re-running the check and backdating is cheaper and more precise.
- Deep (terminal-input-only) traces as the entry key — Recording only coarse terminal inputs such as the repo commit or the package.json hash gives fast keys but cannot early-cut-off and risks Frankenbuild inconsistency; the dependency set should be the narrow set the root cause actually reads plus the environment.
- Stale-while-revalidate: serve the stale entry as the answer and revalidate in the background — The web rationale is latency; here acting on a stale answer is the false positive. Only 'stale as a labelled lead' survives (RFC 8767 allows stale only after refresh fails and flags it).
- Write-around or write-back for entry creation — Write-around leaves the expensive diagnosis unrecorded until some later miss; write-back risks losing it when the session ends or compacts. Write-through with a provisional status is the safe policy.
- Caching 'no entry exists' as an authoritative negative — RFC 2308 caches a negative only with its authority record and a short bounded lifetime; a miss in a store with a few hundred entries just means the symptom handles did not match, and caching that would suppress escalation exactly when a new entry should be created. Log misses as analytics events only.
- Last-write-wins by wall-clock timestamp for conflicting status updates — Dynamo's LWW picks the largest physical timestamp, which would let a confirmation from an older commit overwrite a newer refutation. Order by code lineage and fold append-only events.
- Adopting Dynamo-style quorum, vector clocks or Merkle trees — Built for replicated multi-node stores orders of magnitude larger; this store has one canonical copy and a few hundred rows, so only read repair, tombstones and application-level merge transfer.

## Facts
- F01 [LOAD-BEARING] (verified, paper; invalidation/provenance/data_model) Build Systems a la Carte (Mokhov, Mitchell, Peyton Jones, ICFP 2018) splits a build system into a scheduler and a rebuilder. Rebuilder strategies: dirty bit (Excel; Make's mtimes act as one), verifying traces (record hashes of the values of dependencies used last time; if any differ the key is dirty; Shake, Ninja), constructive traces (additionally store the resulting value, many traces per key, shareable; Bazel, CloudBuild, Cloud Shake), deep constructive traces (record only terminal input hashes; Buck, Nix). The paper says the trace store 'constitutes the build system's memory'.
    https://www.microsoft.com/en-us/research/wp-content/uploads/2018/03/build-systems.pdf (ICFP 2018 version, read via pdftotext; section 4.2.1-4.2.4, Table 2, 5.3, 5.4)
- F02 [LOAD-BEARING] (verified, paper; invalidation/canonicalisation) Early cutoff: when a task is re-executed and its result is unchanged from the previous build, dependent tasks need not run. Shake and Bazel support it; Make and Excel do not (a dirty bit cannot be un-set without also leaving dependents dirty). All trace types except deep constructive traces support it; deep traces can cut off only at n levels. Minimality (Definition 2.1): a task executes at most once per build and only if it transitively depends on inputs that changed.
    ICFP 2018 build-systems.pdf, section 2.3, Definition 2.1, 4.2.1, 4.2.2, 4.2.4
- F03 [LOAD-BEARING] (verified, paper; invalidation/limits) The paper's section 6.3 'Impure Computations' names three ways memoisation breaks: untracked dependencies (e.g. a C compile lists source.c but not the gcc version), non-determinism, and volatility (volatile tasks cannot be cached; they are modelled as depending on a RealWorld key changed every build). It notes sandboxing is used to guard against missing dependencies but none is perfect.
    ICFP 2018 build-systems.pdf, section 6.3
- F04 [LOAD-BEARING] (verified, paper; invalidation/data_model/limits) 'Frankenbuild' (section 6.4, Fig. 11): with deep constructive traces plus a non-deterministic task, a cached downstream artifact can be inconsistent with its immediate dependency, because the cache key looked only at terminal inputs. The paper says the resulting store is incorrect under all its correctness definitions.
    ICFP 2018 build-systems.pdf, section 6.4 and Fig. 11
- F05 (verified, paper; invalidation/provenance) Self-tracking (section 6.5): some build systems (Excel, Ninja) recompute a task when the task itself changes, not only when its dependencies change. Shake by default assumes rules do not change and offers shakeVersion ('Change the version number to force a complete rebuild') as the manual override.
    ICFP 2018 build-systems.pdf section 6.5; https://hackage-content.haskell.org/package/shake-0.19.9/docs/Development-Shake.html; https://github.com/ndmitchell/shake/blob/master/docs/Manual.md
- F06 (verified, primary_docs; invalidation/engine) Shake's change detection is configurable: ChangeModtime (default), ChangeDigest (touch does not force rebuild), ChangeModtimeAndDigest (rebuilt only if both changed; mtime checked first), ChangeModtimeAndDigestInput, ChangeModtimeOrDigest. shakeFiles (default .shake) stores metadata; shakeShare / shakeCloud give a shared cache. Shake avoids rebuilding dependents when a rebuilt output is unchanged (early cutoff) and tracks non-file dependencies (file existence, environment variables, directory contents, tool versions).
    https://hackage-content.haskell.org/package/shake-0.19.9/docs/Development-Shake.html (Change type, shakeChange, shakeFiles, shakeShare); https://raw.githubusercontent.com/ndmitchell/shake/master/docs/Why.md
- F07 (verified, primary_docs; invalidation/provenance/limits) Bazel's action cache key is derived from an action's declared inputs, output names, command line and explicitly passed environment variables. The action cache (AC) maps action hash to result metadata; a content-addressable store (CAS) holds output files keyed by content hash. Tools outside the workspace and undeclared inputs are not tracked, so two users with different compilers can share a wrong hit. Anyone with write access can poison the cache and the cache does not record which build produced an output; the docs advise clearing it entirely when poisoned.
    https://bazel.build/remote/caching (read 2026-11-02)
- F08 (verified, primary_docs; invalidation/engine) Bazel Skyframe: a graph of SkyKey/SkyValue/SkyFunction nodes. Invalidation is bottom-up from changed inputs. Change pruning: if a re-evaluated node yields the same value as before, nodes invalidated because of it are restored (editing a C++ comment yields an identical .o, so the linker does not rerun). Reads that bypass registered dependencies create hidden dependencies and incorrect incremental builds.
    https://bazel.build/reference/skyframe
- F09 [LOAD-BEARING] (verified, primary_docs; invalidation/provenance) rustc red-green incremental compilation: queries are fingerprinted by arguments; results compared by hash. try-mark-green: if all recorded reads of a query are green, mark it green without re-executing; if any read is red, re-execute and compare the result hash with the saved one, and if equal mark it green. So an upstream change whose result is unchanged does not re-run dependents. Reads are replayed in recorded order because a later read may only be valid if earlier ones are unchanged.
    https://rustc-dev-guide.rust-lang.org/queries/incremental-compilation.html
- F10 (verified, primary_docs; invalidation/data_model) Salsa (Rust incremental framework) adds two refinements to red-green: backdating (if a re-executed function returns the same value, keep the old result's changed_at so dependents are not re-run) and durability (inputs tagged by how rarely they change, e.g. dependencies high, workspace low; a function depending only on high-durability inputs is confirmed valid after a low-durability change without walking its dependency edges).
    https://salsa-rs.github.io/salsa/reference/algorithm.html
- F11 [LOAD-BEARING] (verified, primary_docs; data_model/provenance/invalidation) RFC 2308 (Mark Andrews, March 1998): negative caching is mandatory for caching resolvers (section 8). NXDOMAIN is cached against <QNAME,QCLASS>; NODATA against <QNAME,QTYPE,QCLASS> (section 5). Authoritative negative answers MUST carry the zone SOA (section 3); the cached SOA MUST be kept with the negative entry (section 5) and negative responses without an SOA SHOULD NOT be cached. Negative TTL = min(SOA MINIMUM, SOA TTL).
    https://www.rfc-editor.org/rfc/rfc2308.txt sections 3, 5, 8
- F12 [LOAD-BEARING] (verified, primary_docs; invalidation/limits) RFC 2308 section 5 on how long to remember 'nothing here': the protocol allows up to 68 years, so resolvers should impose their own cap, which SHOULD NOT exceed the cap for positive answers and should be tunable; 'values of one to three hours have been found to work well'; 'values exceeding one day have been found to be problematic'. Server-failure and dead-server negatives may be cached at most 5 minutes (section 7). Security section: a very high negative TTL enables denial-of-service.
    https://www.rfc-editor.org/rfc/rfc2308.txt sections 5, 7, 11
- F13 (verified, primary_docs; invalidation/retrieval) RFC 5861 (Mark Nottingham, May 2010, Informational): stale-while-revalidate=N lets a cache serve a stale response for N seconds while revalidating in the background; stale-if-error=N lets a stale response be used when the origin returns 500/502/503/504, regardless of other freshness info, up to N seconds of staleness. Stale responses carry non-zero Age and a Warning header. Defined only as HTTP Cache-Control extensions.
    https://www.rfc-editor.org/rfc/rfc5861.txt sections 3, 4
- F14 [LOAD-BEARING] (verified, primary_docs; invalidation/limits) RFC 8767 (Standards Track, March 2020): an expired record may be used 'as though it is unexpired' only when it cannot be refreshed authoritatively (section 4); stale answers carry TTL 30 seconds (recommended); a stale-timer cap of 1-3 days and a TTL cap of 7 days are suggested (sections 4-5); the failure-recheck timer is no more than 5 minutes per RFC 2308. Section 7/10 note stale negative records can delay use of newly published TLSA/DS records and stale mappings can be abused; serve-stale never turns a successful lookup into a failure because it is used only after refresh fails.
    https://www.rfc-editor.org/rfc/rfc8767.txt sections 4, 5, 6, 7, 10
- F15 (verified, primary_docs; invalidation/provenance) RFC 9111 HTTP Caching (June 2022, obsoletes RFC 7234): freshness lifetime from max-age/Expires, else a heuristic lifetime typically about 10% of time since Last-Modified (4.2.2); stale responses may be served only if disconnected or explicitly permitted (4.2.4); revalidation uses conditional requests with validators ETag/Last-Modified and a 304 refreshes the stored response (4.3); a cache MUST invalidate the target URI after a successful unsafe method (PUT/POST/DELETE) and invalidation covers only the caches the request passes through, so it gives no global consistency (4.4).
    https://www.rfc-editor.org/rfc/rfc9111.txt sections 4.2, 4.2.2, 4.2.4, 4.3, 4.4
- F16 (verified, paper; invalidation/limits) Gwertzman and Seltzer, 'World Wide Web Cache Consistency' (USENIX 1996): the Alex weak-consistency protocol (an object is revalidated when time since last validation exceeds a threshold times the object's age) can be tuned to return stale data less than 5% of the time and beat TTL and invalidation on bandwidth/server load; pure invalidation gives 0% stale but needs server changes and per-copy bookkeeping; weak protocols are simpler and more fault-tolerant because stale entries expire without special recovery logic. TTL suits content with known lifetimes. Results depend on workload (synthetic workload gave far higher stale rates).
    https://www.usenix.org/legacy/publications/library/proceedings/sd96/full_papers/seltzer.txt
- F17 [LOAD-BEARING] (verified, paper; concurrency/invalidation/workflow) Facebook 'Scaling Memcache at Facebook' (NSDI 2013) section 3.2.1: a 'stale set' happens when a client sets a value that does not reflect the latest value because concurrent updates were reordered. A lease is a 64-bit token bound to the key, handed to a client on a miss; the client presents it on set, and memcached rejects the set if a delete invalidated the token ('similar to load-link/store-conditional'). The same lease throttles thundering herds (one client per key repopulates). Invalidations are derived from the database commit log by a daemon (mcsqueal) and stored in reliable logs so lost or misrouted invalidations can be replayed (section 4); deletes can carry a hold-off that rejects adds for a few seconds.
    https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf (read via pdftotext; sections 3.2.1, 4.1, 4.2)
- F18 [LOAD-BEARING] (verified, paper; concurrency/invalidation/workflow) Dynamo (DeCandia et al., SOSP 2007): on a read the coordinator waits for outstanding responses; 'If stale versions were returned in any of the responses, the coordinator updates those nodes with the latest version. This process is called read repair because it repairs replicas that have missed a recent update at an opportunistic time and relieves the anti-entropy protocol from having to do it.' Anti-entropy uses per-key-range Merkle trees (leaf = hash of key, branch checkable independently) to find out-of-sync keys. Conflict resolution is either by the store (simple policies such as 'last write wins' by physical timestamp) or by the application (semantic merge, e.g. shopping cart). Sloppy quorum plus hinted handoff keep writes available.
    https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf (read via pdftotext; read-repair text in the experiences section, anti-entropy in 4.7, reconciliation in 4.4-4.5; exact section numbers not captured by the extraction)
- F19 (verified, primary_docs; concurrency/invalidation) Cassandra 5.0 docs on read repair: default BLOCKING mode repairs out-of-date replicas before responding, giving monotonic quorum reads but not partition-level write atomicity; background (probabilistic) read repair (read_repair_chance) was removed in 4.0 (CASSANDRA-13910); only replicas involved in the read are repaired; read repair 'does not replace full repairs'; it is skipped at consistency ONE/LOCAL_ONE; mismatches are detected by digest (hash-only) reads then merged by timestamp.
    https://cassandra.apache.org/doc/latest/cassandra/managing/operating/read_repair.html (5.0 docs, read 2026-11-02)
- F20 (verified, primary_docs; data_model/concurrency/provenance) Cassandra treats a delete as an insertion of a time-stamped tombstone; default gc_grace_seconds is 864000 (10 days), after which the tombstone can be compacted away; a replica that returns after the grace period 'may' reintroduce the deleted data because the deletion was missed.
    https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html
- F21 (reported, blog; workflow/concurrency) Write policies (Wikipedia 'Cache (computing)'): write-through writes synchronously to cache and backing store (simple, no dirty tracking, common when multiple writers would otherwise need coherency protocols); write-back writes only to the cache and updates the backing store later on eviction, requiring dirty-bit tracking and risking loss of unflushed data; write-around/no-write-allocate writes straight to the backing store and populates the cache only on read misses, usually paired with write-through.
    https://en.wikipedia.org/wiki/Cache_(computing) (writing policies section)
- F22 (verified, blog; concurrency) Vogels, 'Eventually Consistent - Revisited' (23 Dec 2008): client-side consistency models are strong, weak, eventual, causal, read-your-writes (special case of causal), session, monotonic read, monotonic write. N/W/R quorum: if W+R > N reads and writes overlap and strong consistency can be guaranteed; if W+R <= N reads may miss recent writes; if W < (N+1)/2 conflicting writes become possible.
    https://www.allthingsdistributed.com/2008/12/eventually_consistent.html
- F23 (verified, primary_docs; concurrency/engine) SQLite WAL mode: readers do not block the writer and the writer does not block readers, but 'there can only be one writer at a time'; each read transaction sees a single point-in-time snapshot; all processes must be on the same host and WAL does not work over a network filesystem; checkpoint starvation can grow the WAL without bound if there is always an active reader; applications must handle SQLITE_BUSY (busy timeout).
    https://www.sqlite.org/wal.html
- F24 (verified, primary_docs; concurrency/engine) PostgreSQL 18 docs section 13.2: Read Committed (default) takes a snapshot per statement; Repeatable Read and Serializable snapshot at first statement; applications at those levels must be prepared to retry on serialization failure (SQLSTATE 40001); read-only transactions never have serialization conflicts; writers wait on writers for the same row.
    https://www.postgresql.org/docs/18/transaction-iso.html

## Open questions
- What exactly is a 'dependency' of a defect entry at sufficient granularity: whole files, git blob hashes, hunks/line ranges, or symbols? Coarser is cheaper but causes more re-verification; a design decision for the data-model lane, to be settled with real seed entries from CLAUDE.md traps (for example the eas.json empty-env trap depends on one file plus the EAS CLI behaviour, which is not in the repo and so is untracked).
- How should entries whose cause is external behaviour (EAS CLI, Railpack detection, Supabase pooler, Sentry plugin) be traced? The external tool version is the only trackable handle and is often not recorded; these may need a small manually maintained 'environment manifest' key, which adds tracking burden the owner wants to avoid.
- Can every discriminating check be automated and cheap? Native Android compile is not gated in CI and not runnable on the Windows box; such entries can only be 'unverified' unless a check surrogate (grep for a config pattern) is accepted as a valid gate.
- Non-deterministic or flaky root causes (race conditions such as the documented outbox race): per a la carte 6.3 volatile or non-deterministic tasks cannot be cached the same way. Does the store record them with a 'probabilistic reproduction' check and a lower promotion bar?
- Which negative-result lifetime policy is acceptable: pure event-driven (reopen when trace changes) or event-driven plus a cap measured in phases? No empirical data exists; RFC 2308's 1-3 hour guidance is for DNS and does not translate to a time unit here.
- Is a second-agent reproduction required for 'confirmed', and who pays for it when only the top-tier model can reproduce? Policy for the workflow lane.
- Does the owner run parallel sessions on the same symptom often enough to justify the claim-lease mechanism?
