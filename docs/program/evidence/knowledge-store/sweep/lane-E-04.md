# lane:E-04

lane=E-04 tool_status=ok facts=26 candidates=13

## Summary
At tens-to-hundreds of documents, no dedicated search server adds retrieval capability that SQLite FTS5 (BM25, column weights, prefix, trigram, snippet) or Postgres tsvector plus pg_trgm cannot supply. What they add is built-in typo tolerance and optional hybrid vector search. What they cost is a resident daemon, an API/master key, an upgrade/dump story and a telemetry switch the owner must remember. Only Meilisearch is a credible optional "search tier" for this workload: MIT community edition, a Windows .exe and a ~106 MB compressed Docker image, telemetry off with `--no-analytics` / `MEILI_NO_ANALYTICS=true`, an experimental MCP route, and local-only hybrid via `userProvided` or `huggingFace` embedders. Its writes are asynchronous (task queue), which complicates a CLI that must read its own writes. Typesense is lighter at idle (~20-30 MB) but is GPL-3, RAM-resident, Linux/Docker/WSL-only on Windows, and I found no documented telemetry switch. Quickwit and OpenSearch/Elasticsearch/Vespa are log-scale or JVM-scale systems and are absurd here (Vespa needs a 4 GB container minimum for a corpus under 1 MB; the JVM engines need 4 GB Docker Desktop plus ~1.1 GB images). Sonic stores only identifiers, so it cannot return the entry. Zinc, OpenObserve, Manticore and Quickwit all phone home by default, each with a disable switch. Telemetry-off must be pinned as a deployment invariant for any engine chosen. Several size and idle-RAM figures come from vendor pages, not measurements; measure RSS before committing.

## Design implications
- (strong) Do not make a dedicated search server a required component. At tens to hundreds of entries, FTS5/pg_trgm already covers the fuzzy-handle retrieval need, and an extra daemon adds the ops burden the owner wants to reduce. Keep the entry store transactional (provenance, outcomes, invalidation) and treat any engine as a rebuildable derived index behind the abstraction layer, so Meilisearch can be added later if a precision test shows FTS5/pg_trgm is inadequate. [E04-F22, E04-F23, E04-F24, E04-F25]
- (strong) If Meilisearch is added as an optional search tier, pin telemetry off in the launch definition (`MEILI_NO_ANALYTICS=true` plus `--no-analytics`), use only the community build, and allow only `userProvided` or `huggingFace`/local `ollama` embedders. Add a startup assertion or CI check that fails if any embedder source is `openAi` or `rest`. [E04-F01, E04-F02, E04-F07]
- (moderate) Any engine-backed write path needs a wait-for-searchable step (poll the task to `succeeded`) before a record is declared stored. Otherwise a cheap agent can miss an entry written seconds earlier by another worktree. This argues for the database being the system of record with the index updated asynchronously. [E04-F05, E04-F26]
- (moderate) Default-on telemetry is the norm in this lane (Meilisearch, Quickwit, Zinc, OpenObserve, Manticore). Make 'telemetry disabled' an explicit deployment invariant with a smoke test that blocks egress and checks the engine still works. Typesense must be checked by egress-blocking before any use, because its docs are silent. [E04-F01, E04-F10, E04-F14, E04-F20, E04-F21]
- (strong) Rule out the log-scale and JVM engines (Quickwit, OpenSearch, Elasticsearch, Vespa) as production or dev options. The floors (4 GB container for Vespa and the Docker-Desktop OpenSearch setup, JVM heap rules, a Linux-only Quickwit) are orders of magnitude above the corpus. Cite them only for design ideas (ES-compatible query DSL, unified lexical+vector ranking). [E04-F13, E04-F14, E04-F16, E04-F17, E04-F18, E04-F24]
- (moderate) Search engines do not supply the safety-critical half of the system (verification gate, event-driven invalidation, outcome history). A good ranker raises hit rate, but the false-positive defence lives outside it. Precision tuning should use conservative thresholds, such as Typesense's `drop_tokens_threshold=0` / Meilisearch's `rankingScoreThreshold`, so a weak match returns nothing rather than a plausible-looking wrong entry. [E04-F07, E04-F11, E04-F25]
- (weak) Plan separate retrieval handles per entry type (exact canonicalised error template, normalised symptom text, file/symbol path, free-text description). Trigram or typo-tolerant matching suits the free-text handle; template and path handles want exact or prefix matching, which FTS5/Postgres already do. [E04-F08, E04-F11, E04-F22, E04-F23]

## Rejected paths
- Run Quickwit (or Tantivy-based Quickwit) as the symptom index — Log-scale design, Linux-only, telemetry on by default, no Windows build. Tantivy alone needs a Rust toolchain absent from the dev box and gives no fuzzy matching out of the box.
- Run OpenSearch, Elasticsearch or Vespa locally — Documented 4 GB container floors, 1.1-1.2 GB images, JVM tuning and WSL sysctl changes, for a corpus under 1 MB.
- Use Sonic as the main index — It stores identifiers only (no entry text), speaks TCP only and has no Windows mention, forcing a second store and consistency problem.
- Use a remote embedder (OpenAI/rest) for hybrid search in Meilisearch or Typesense — It sends defect text to a third party, which the data-control constraint disqualifies.
- Pick Typesense on its low idle RAM alone — GPL-3.0, RAM-resident index, WSL/Docker-only on Windows, and no documented telemetry switch means its egress posture is unproven.
- Treat ZincSearch or OpenObserve as lightweight Elasticsearch substitutes — Zinc's licence is unasserted and activity is low; OpenObserve is an AGPL observability platform. Both default telemetry on.

Licences: ELv2 and SSPL (2021), with AGPL announced 2024-08-29 as a third option, so it is OSI-open again. The ELv2 restrictions (no managed-service resale, no circumventing licence keys) do not bite an internal tool.

- E04-F18 (verified, primary_docs; engine/ops_cost/limits) Vespa (Apache-2.0, active): the Docker docs state 'a single-node Vespa application requires a minimum of 4 GB for the Docker container'. Too little memory puts the `vespa` service in a restart loop. An idle container still uses CPU and memory. The `vespaengine/vespa:latest` image appears at 1.2 GB in the docs' example listing. It runs a JVM config server plus a config sentinel, and the docs show reduced JVM settings (-Xmx128M) only for functional tests.

- E04-F19 (verified, source_repo; engine/retrieval/ops_cost) Sonic (MPL-2.0, active) is an identifier index, not a document index. It stores no text beyond a word graph for autocomplete and typo correction. It claims about 30 MB RAM (peak 28 MB at 1M messages on a 2014 laptop). It speaks only the TCP 'Sonic Channel' protocol, with no HTTP. Packages are Debian 12 builds, Cargo or Docker, and Windows is not mentioned. The calling code must keep the entry text elsewhere and map IDs back, which is a second store to keep consistent.

- E04-F20 (verified, primary_docs; egress/engine) ZincSearch (Go): `ZINC_TELEMETRY` defaults to true ('Send anonymous telemetry info'). The GitHub API reports its licence as NOASSERTION, and the last push was 2026-09-16, so it is low-activity. OpenObserve is AGPL-3.0, an observability platform for logs, metrics and traces, with `ZO_TELEMETRY` defaulting to true (set false to disable) and a separate `ZO_USAGE_REPORTING_ENABLED` defaulting to false. OpenObserve is built for a different job (logs/traces/metrics at scale).

- E04-F21 (reported, primary_docs; egress/engine/ops_cost) Manticore Search is GPL-3.0 and active (last push 2026-11-01). Telemetry is opt-out: set the env var `TELEMETRY=0`, or `telemetry = 0` in the `searchd` section. The docs say metrics include a `machine_id` taken from /etc/machine-id, plus version and OS. Windows: WSL2 is recommended. Native Windows binaries exist but lack replication and need Docker for Manticore Buddy. The Docker Hub `dev` tag is about 196-211 MB compressed. No idle-RAM figure was obtained. It speaks the MySQL protocol and HTTP.

- E04-F22 [LOAD-BEARING] (verified, primary_docs; retrieval/engine/ops_cost/concurrency) SQLite FTS5 provides `bm25()` ranking with per-column weights, prefix queries (optionally prefix-indexed), a `trigram` tokenizer for substring matching, `highlight()` and `snippet()`, NEAR and column filters. It has no edit-distance typo tolerance (an app must use `fts5vocab` and its own logic). It is embedded and file-based, so nothing needs to run and it adds no egress surface.
    https://www.sqlite.org/fts5.html (fetched 2026-11-02; only first 100k of ~172k chars read)
- E04-F23 [LOAD-BEARING] (verified, primary_docs; retrieval/engine/egress) PostgreSQL `pg_trgm` (a trusted contrib module, installed with CREATE EXTENSION; PG18 docs) provides `similarity()`, `word_similarity()`, `strict_word_similarity()`, the `%` operator with a 0.3 default threshold, and GIN/GiST trigram indexes that also accelerate LIKE/ILIKE/regex. Together with built-in tsvector full-text search this gives fuzzy symptom matching inside the Postgres the project already runs. The data stays off the managed Supabase host only if the knowledge store lives in a local or self-hosted Postgres.
    https://www.postgresql.org/docs/current/pgtrgm.html (fetched 2026-11-02)
- E04-F24 [LOAD-BEARING] (inferred, inferred; ops_cost/limits/engine) At 10^2 entries of a few KB each (under 1 MB of text) every server-class engine here is idle capacity with a fixed floor: Vespa 4 GB container minimum and a 1.2 GB image; OpenSearch 4 GB Docker Desktop and a 1.16 GB image; Elasticsearch JVM heap with the 50% rule; Quickwit built for log-scale object-store indexing. Meilisearch (256 MB documented minimum, ~106 MB image) and Typesense (~20-30 MB idle) fit the footprint but still add a daemon, a key and a version to track. The 4 GB and 256 MB figures are documented floors; entry size and corpus bytes are my estimate.
    Derived from E04-F04, F09, F16, F18; corpus size estimated from CLAUDE.md workload (tens to hundreds of entries)
- E04-F25 [LOAD-BEARING] (inferred, inferred; retrieval/data_model/provenance/engine) What a dedicated engine adds over FTS5 or Postgres FTS at this scale: (1) native typo tolerance (Meilisearch, Typesense), where FTS5 has none and pg_trgm approximates it; (2) a built-in hybrid keyword plus vector query (Meilisearch with huggingFace/userProvided, Typesense with ts/ models), which sqlite-vec or pgvector could also provide; (3) ranking knobs and facets that matter mostly beyond thousands of documents. It does NOT add provenance, invalidation, verification or an outcome history. Those must live in a transactional store, so a search engine would at best be a derived index over a system of record.
    Synthesis of E04-F05, F07, F08, F11, F22, F23
- E04-F26 (inferred, inferred; concurrency/workflow/ops_cost) Operational risk for agents sharing a search daemon across parallel worktrees: Meilisearch serialises writes through one task queue, and an agent that reads before its task reaches `succeeded` sees stale results (F05). Typesense and Manticore are single servers too, so every session needs the daemon up and an API key available. An embedded file DB such as SQLite has none of this. Concurrent writers there need WAL and busy_timeout, which other lanes cover.
    Derived from E04-F05 and E04-F09
