## Summary
For tens to a few hundred entries, the strongest retrieval design is a deterministic, explainable pipeline. First, canonicalise the query and look up exact handles (error code, tool, path, symbol, canonical template) and applicability facets. Second, rank with multi-field BM25, which SQLite FTS5 gives for free. Third, apply abstention rules built from features that do not depend on raw score scale, then run the entry's own verification gate. Primary sources and a local experiment show raw BM25 scores are rank-only and depend on corpus size and document frequency, not match quality. On a 5-document FTS5 table, any unique single-term match scored exactly ln 3 whatever the quality, and a term in 4 of 5 documents scored about 1e-6. So an absolute score threshold is invalid; use rank margin, IDF-weighted query-term coverage, and exact-handle hits, calibrated on a labelled set. RRF is rank-only, so it cannot abstain. Dense retrieval has no evidence of helping at this scale: BM25 stays strong on BEIR out-of-domain, dense models fail on entity/identifier queries, and BM25 beat embeddings even on a 46-document set. It would also need a local model. Keep dense and cross-encoders deferred until measured vocabulary-mismatch misses justify them. MinHash/LSH and SimHash are designed for billions of documents; at N of 500 or fewer, exact pairwise Jaccard suffices. Rocchio maps best to document-side feedback: a confirmed query becomes a new handle, a refuted query becomes a 'not when' discriminator. Pseudo-relevance feedback is rejected (query drift). Evaluation: leave-one-handle-out queries, hard-negative near-miss queries, and logged lookup outcomes, with the rule of three for false-positive bounds.

## Design implications
- (strong) Do not use a raw BM25 (or FTS5 bm25()) score as an absolute threshold or as a confidence. Primary sources say BM25 preserves rank order only and cannot be reversed into a probability, and a local FTS5 test shows scores on a tiny corpus encode corpus size and document frequency (a unique single-term match scores exactly ln 3 on 5 documents; a term in 4 of 5 scores about 0). Use scores only to order candidates within one query. [F02, F04, F05, F07]
- (strong) Pipeline for this store, in order: (0) canonicalise the symptom text (Drain-style masking of paths, numbers, hashes, versions; keep codes, tool names, identifiers); (1) exact-handle and applicability-facet prefilter (platform, runtime, dependency versions, files/symbols still present), deterministic and explainable; (2) multi-field BM25 over the survivors (symptom wordings, canonical templates, title, cause, tags) with field weights, returning ordered candidates plus per-term evidence; (3) abstention rules on score-free features; (4) the entry's own discriminating verification check on current code before anything acts on it. A cheap agent may read the top 3-5 and judge plausibility (step 3.5), but that judgement is advisory and never replaces step 4. [F11, F21, F24, F26, F13]
- (moderate) Make the lookup three-valued: miss, candidate, lead, using two thresholds set on a labelled set and chosen to keep the false-lead rate low at the cost of more misses. Features: exact-handle hit; IDF-weighted query-term coverage of the best entry (0 to 1); rank margin between top1 and top2. These are my proposals (inferred) and need calibrating, but they avoid dependence on raw score scale. RRF (if a second ranker is ever added) cannot provide abstention because it uses ranks only. [F18, F25, F26, F08]
- (moderate) Start lexical-only. At this scale there is no evidence dense retrieval beats BM25 (BEIR out-of-domain, LIMIT even at 46 documents, entity-style queries), a local embedding model is an install and a second index to keep in sync, and a hosted embedder would send defect text to a third party. Add a dense signal fused by RRF only if the evaluation harness shows misses caused by zero vocabulary overlap, and run it locally. Cross-encoders are unjustified for a shortlist of 5-10 entries. [F09, F10, F11, F12, F13]
- (moderate) Handle-type diversity is the practical answer to 'same cause, different wording'. Store several handle types per entry (canonical error template, raw error text, symptom paraphrases in the words of different agents, affected files/symbols, tool and platform, a short cause statement) and rank across fields with weights. Feedback is document-side: a confirmed lookup appends the canonicalised query as a new handle; a refuted lookup appends a 'not when' discriminator or negative handle. This is Rocchio's idea moved from query to entry, and every change is a provenance row. [F16, F03]
- (strong) Reject pseudo-relevance feedback and automatic query expansion: they trust the top hits, which is the failure we are guarding against. [F16]
- (moderate) Use exact pairwise Jaccard on token shingles for write-time near-duplicate warnings and handle redundancy checks. MinHash/LSH/SimHash are web-scale designs (SimHash paper: 8 billion pages) and unnecessary at N of 500 or fewer. Near-duplicate detection only finds lexical similarity; merging entries that share a cause but not words remains an agent or owner decision. [F14, F15]
- (moderate) Measure on a tiny corpus honestly. Build the test set from the store itself: leave-one-handle-out queries, hard negatives (same tool or words, different cause; CLAUDE.md's Sentry-in-eas.json vs Sentry-plugin-in-app.json pair is one), out-of-corpus queries that must abstain, LLM-generated paraphrase queries spot-checked by a person, and real lookups logged with outcomes (confirmed, refuted, missed). Report P@1, MRR, abstention accuracy on negatives, and false-lead rate with a rule-of-three upper bound (zero false leads in 50 negatives only bounds the rate at about 6%). Compare configurations with paired differences on identical queries, since small query sets give unreliable system comparisons. [F19, F20, F22, F23]
- (moderate) Engine implication for retrieval: ranking quality at this scale is decided by tokenisation, field weights and canonicalisation rather than by the engine. FTS5 (available in Node 24's node:sqlite with no install) provides adequate BM25 with column weights; Postgres built-in ranking lacks IDF; a hand-rolled BM25 module is a justified fallback if FTS5's hard-coded constants or tokenisation block progress. Keep the retrieval interface (canonicalise, prefilter, rank, abstain) behind the abstraction layer so the ranker can change without touching data. [F04, F05, F06, F24]
- (weak) Retrieval logging is also the provenance and analytics feed: each lookup should record the canonicalised query, candidates shown, which thresholds fired, gate result, and later outcome. The same rows give the hit/refute/miss rates and the growing labelled set, so no separate analytics pipeline is needed for retrieval quality. [F20, F22]

## Rejected paths
- Absolute raw-BM25 score threshold, or treating the score as a probability — BM25 is rank-only by derivation (Robertson and Zaragoza Sec 2.5); on tiny corpora the score is set by N and df (local FTS5 test: unique single-term match = ln 3; term in 4 of 5 rows = about 1e-6); practitioners confirm scores are not comparable across queries.
- Using RRF (or any rank-only fusion) as the confidence signal — RRF scores depend only on ranks, so the top document always has a positive score; there is no way to abstain from it.
- Pseudo-relevance feedback / automatic query expansion — Query drift when the top hits are wrong; the opposite of precision-first.
- LLM re-ranker or cheap-agent judgement as the gate — Benchmarks show LLM rankers can be competitive (F13) but there is no calibration evidence for symptom-to-defect matching; its errors are exactly the false positives to be prevented. Keep it advisory; the gate is a check that reproduces the root cause on current code.
- MinHash/LSH or SimHash index for near-duplicate detection — Built for web-scale collections; at 500 entries exact pairwise Jaccard is trivial and exact.
- PostgreSQL ts_rank as the ranker — Documented to use no global statistics; no IDF means rare error tokens are not up-weighted.
- Hosted embedding or hosted re-ranking APIs for entry text — Would send defect data to a third party; disqualified for production use.

## Facts
- F01 (verified, blog; retrieval/limits) BM25 score = sum over query terms of IDF(q) * f*(k1+1) / (f + k1*(1-b+b*|D|/avgdl)). k1 is usually chosen in [1.2, 2.0] absent tuning; b is usually 0.75 (b=0 turns length normalisation off, b=1 is full). The IDF variant ln((N-n+0.5)/(n+0.5)+1) is always positive; without the +1 it goes negative for terms in more than about half the documents (negativity is my derivation from the formula).
    https://en.wikipedia.org/wiki/Okapi_BM25 (read 2026-11-02)
- F02 [LOAD-BEARING] (verified, paper; retrieval/limits) Robertson and Zaragoza state the BM25 derivation keeps only rank order (probability ranking principle) and several dropped components would be needed for a good probability estimate, so the weighting 'is not easily reversible to give us such an explicit estimate'. Hence BM25 scores are ranking scores, not calibrated probabilities of relevance. Section 2.5, pp. 345-346.
    https://staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf (Found. and Trends in IR 3(4), 2009; text extracted from the downloaded PDF)
- F03 (verified, paper; retrieval/data_model) The same monograph defines BM25 term-frequency saturation (a single term's contribution cannot exceed an asymptotic limit however often it occurs) and soft length normalisation B = (1-b)+b*dl/avdl with 0<=b<=1 (Sec 3.4.2, 3.4.5, eq 3.12). Per-field weighting is BM25F (Sec 3.x).
    https://staff.city.ac.uk/~sbrp622/papers/foundations_bm25_review.pdf
- F04 [LOAD-BEARING] (verified, source_repo; retrieval/engine/limits) SQLite FTS5 bm25() hard-codes k1=1.2 and b=0.75, computes idf = log((nRow-nHit+0.5)/(nHit+0.5)) and clamps it to 1e-6 when idf<=0 (a term in about half or more of the rows contributes almost nothing), and returns the score multiplied by -1 (lower is better). Per-column weights are passed as extra bm25() arguments.
    https://raw.githubusercontent.com/sqlite/sqlite/master/ext/fts5/fts5_aux.c; https://sqlite.org/fts5.html
- F05 [LOAD-BEARING] (verified, local_file; retrieval/limits/engine) Local experiment (Node v24.22.1 built-in node:sqlite, SQLite 3.53.4, FTS5 enabled; nothing installed). On a 5-row table, a term present in 4 of 5 rows scored bm25 = -0.000001 for every row; any single rare term unique to one row scored -1.0986 = ln 3 regardless of how well the row otherwise matched. In a second 5-row table, 'build fails' scored -1.95 and 'deploy' -1.07 against different single rows. So on a tiny corpus the score reflects N and document frequency, not match quality, and is not comparable across queries.
    local experiment, node -e with node:sqlite, 2026-11-02 (reproducible with the same two inserts and bm25() queries)
- F06 [LOAD-BEARING] (verified, primary_docs; retrieval/engine) PostgreSQL 18 ts_rank/ts_rank_cd use term frequency, proximity, A-D weights and optional length normalisation, but 'the ranking functions do not use any global information, so it is impossible to produce a fair normalization to 1% or 100%'. The page does not mention IDF; so built-in Postgres full-text ranking has no corpus-level term rarity weighting (my reading: a rare error token counts the same as a common word).
    https://www.postgresql.org/docs/current/textsearch-controls.html (PG 18, footer 18.6)
- F07 [LOAD-BEARING] (reported, blog; retrieval/limits) Raw lexical scores are meaningful only within one query. Elastic forum answers say scores are relative to the query that produced them and cannot be normalised across queries; an arXiv study of retrieval over tutoring conversations normalised BM25/ColBERT scores within each query's top 10 to make one threshold workable; a Pinecone answer notes per-query max-score normalisation still leaves distributions varying by query and suggests a re-ranker's output for threshold filtering. Practitioner sources, not benchmarks.
    https://discuss.elastic.co/t/is-the-elasticsearch-relevance-score-an-ordinal-or-interval-value/36061.md ; https://arxiv.org/pdf/2411.07598 ; https://community.pinecone.io/t/normailized-score-when-using-hybrid-search-which-is-only-supported-now-with-dot-product-instead-of-cosine-similarity/3051
- F08 (verified, paper; retrieval) Reciprocal Rank Fusion: RRFscore(d) = sum over rankings r of 1/(k + r(d)), with k=60 fixed in a pilot and not altered afterwards; it beat Condorcet Fuse and CombMNZ and almost invariably improved on the best combined ranker in TREC experiments (Cormack, Clarke, Buettcher, SIGIR 2009). Elastic's RRF uses default rank_constant 60 and the fused value uses ranks only, not the retrievers' raw scores.
    http://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf (text extracted from downloaded PDF); https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion
- F09 [LOAD-BEARING] (reported, paper; retrieval/limits) BEIR (18 datasets, zero-shot): the abstract calls BM25 a robust baseline; re-rankers and late-interaction models give the best average zero-shot results at high compute cost; dense and sparse neural retrievers are cheaper but often underperform. Per the ar5iv full text: BM25 trails neural models by 7-18 points on in-domain MS MARCO, dense models ANCE and TAS-B are significantly worse than BM25 on datasets such as BioASQ and Touche-2020, and BM25 plus a 6-layer MiniLM cross-encoder over the top 100 gains about 11% average over BM25, beats BM25 on 16/18 datasets (not ArguAna, Touche), at 350 ms or more per query. Corpora are thousands to millions of documents, none as small as this store.
    https://arxiv.org/abs/2104.08663 (abstract, verified); https://ar5iv.labs.arxiv.org/html/2104.08663 (figures via page summariser, reported)
- F10 [LOAD-BEARING] (reported, paper; retrieval/limits) Weller et al., 'On the Theoretical Limitations of Embedding-Based Retrieval' (arXiv 2508.21038, ICLR 2026): the number of top-k subsets a single-vector embedding can return is limited by embedding dimension, and state-of-the-art embedders fail on the simple LIMIT benchmark. Per the ar5iv text: on full LIMIT (about 50k docs, 1000 queries) BM25 gets Recall@100 of 93.6 against 18.9 for the best embedder; on the 46-document 'small' version BM25 gets Recall@2 of 97.8 and 100 at Recall@10. This is a stress benchmark, not a workload like ours, but it shows corpus smallness alone does not make dense retrieval win.
    https://arxiv.org/abs/2508.21038 (abstract, verified); https://ar5iv.labs.arxiv.org/html/2508.21038 (numbers via page summariser, reported)
- F11 (verified, paper; retrieval/canonicalisation) Sciavolino et al. (EMNLP 2021): dense retrievers perform far worse than sparse methods on EntityQuestions (simple, entity-rich questions) and generalise only to common entities unless the question pattern was seen in training.     https://arxiv.org/abs/2109.08535
- F12 (verified, paper; retrieval) Ma, Sun, Pradeep, Lin (2021): the original DPR paper under-reported the BM25 baseline, so its dense-sparse hybrid gains were also understated; hybrids remain the usual way to add dense signals to a lexical baseline (abstract only).

- F14 (reported, paper; retrieval/limits) Broder (1997): resemblance of two documents is the Jaccard coefficient of their w-shingle sets, estimated from fixed-size min-wise permutation sketches (for example 100 permutations; sketches of a few hundred bytes); containment needs sketches that grow with the document. Charikar (STOC 2002) introduced the random-hyperplane/rounding LSH family behind SimHash (link to cosine similarity is the commonly cited result, not confirmed on the pages I read). Manku, Jain, Das Sarma (WWW 2007) used 64-bit simhash fingerprints with Hamming distance k=3 on 8 billion web pages. All three are engineered for web-scale collections.
    https://www.cs.princeton.edu/courses/archive/spring13/cos598C/broder97resemblance.pdf (via search excerpts); https://www.cs.princeton.edu/courses/archive/spr05/cos598E/bib/p380-charikar.pdf ; https://research.google/pubs/detecting-near-duplicates-for-web-crawling/
- F15 (inferred, inferred; retrieval/limits/ops_cost) At N of 500 entries or fewer, all-pairs comparison is about 125,000 pairs of short token sets, which is milliseconds; no LSH index, signature store or probabilistic bound is needed for write-time near-duplicate detection. MinHash/SimHash earn their cost only when pairwise comparison is infeasible.
    inferred from F14 and the stated workload (tens to a few hundred entries)
- F16 [LOAD-BEARING] (reported, blog; retrieval/provenance) Rocchio relevance feedback moves the query toward the centroid of relevant documents and away from non-relevant ones, with typical weights alpha=1, beta=0.75, gamma=0.15 (survey); Wikipedia notes modern systems often set the negative weight to 0 or keep only the strongest non-relevant documents, and that the method fails on multimodal classes, where one concept has several far-apart clusters (its example: 'Burma' vs 'Myanmar'). Pseudo-relevance feedback assumes the top-k are relevant and can drift on queries whose top results are off-topic. 'Multimodal class' is exactly our 'one root cause, many symptom wordings' case.
    https://en.wikipedia.org/wiki/Rocchio_algorithm ; https://arxiv.org/pdf/1708.00247 (survey, via search excerpt)
- F17 (reported, paper; retrieval/limits) Cronen-Townsend, Zhou, Croft (SIGIR 2002): the clarity score (KL divergence between query and collection language models) correlates with average precision and can flag ineffective queries without relevance judgements; later work reports other predictors (for example score-standard-deviation) often correlate better. Query-performance prediction is the established literature on 'is this query likely to have failed'.
    https://ir.webis.de/anthology/2002.sigirconf_conference-2002.40 ; https://www.dcs.gla.ac.uk/~ronanc/papers/cumminsSIGIR11.pdf (via search excerpts)
- F18 (reported, paper; retrieval/limits) Chow (IEEE Trans. Inf. Theory IT-16(1), 1970, pp. 41-46) gives the optimum reject rule and the error-reject trade-off: abstain when the top posterior is below a threshold. Secondary sources note the rule needs accurate posterior estimates and is the standard baseline when estimates are noisy. A two-threshold (candidate vs lead) design is a three-way variant of this reject option.
    https://researcher.watson.ibm.com/publications/on-optimum-recognition-error-and-reject-tradeoff (citation only); https://rcs.cic.ipn.mx/2006_26/Art06_Determination of the Optimum Error and Reject Validity Regions as Functions of threshold in the Case of Three Classes.pdf
- F19 (reported, paper; limits/retrieval) Voorhees and Buckley (SIGIR 2002) estimate that error rates in concluding one retrieval system beats another from few topics are larger than anticipated, and recommend enough topics; with tens of labelled queries, differences between configurations must be large or paired to be believable.
    https://www.nist.gov/node/707561 ; https://www.paperdigest.org/certificate/991eb580b7f0afdd (abstract-level)
- F20 [LOAD-BEARING] (reported, paper; limits/retrieval) Rule of three (Hanley and Lippman-Hand, JAMA 1983;249:1743): observing zero events in n trials gives an approximate 95% upper bound of 3/n on the event rate (n=50 gives about 6%; best for n above about 30; exact at n=20 is about 14% vs 15%). Applied here: zero false positives across 50 independent hard-negative lookups only bounds the false-positive rate at about 6%, not at zero, so the verification gate cannot be dropped on the strength of a clean test run.
    https://en.wikipedia.org/wiki/Rule_of_three_(statistics) ; https://jamanetwork.com/journals/jama/article-abstract/389714
- F21 (reported, paper; canonicalisation/retrieval) Drain (He, Zhu, Zheng, Lyu, ICWS 2017) parses log lines online with a fixed-depth parse tree after regex preprocessing of domain-specific tokens, grouping by length then leading tokens and a similarity threshold; Drain3 (IBM) defaults are similarity 0.4, depth 4. This is the prior art for turning machine text into templates before indexing.
    https://logparser.readthedocs.io/en/latest/tools/Drain.html ; https://pypi.org/project/drain3/0.6/ (via search excerpts)
- F22 (verified, paper; retrieval/seed_corpus) InPars (Bonifacio et al., arXiv 2202.05144): few-shot LLM prompting generates synthetic queries for documents, and retrievers fine-tuned on the synthetic data beat BM25 and recent self-supervised dense methods. The same mechanism (LLM writes queries a user would type for a given document) is the cheap route to a labelled test set of paraphrased symptom queries, with human spot-checks.
    https://arxiv.org/abs/2202.05144
- F23 (verified, local_file; seed_corpus/retrieval/limits) CLAUDE.md names pairs of traps whose surface symptoms overlap but whose causes and fixes differ: an empty EXPO_PUBLIC_SENTRY_DSN in eas.json makes every eas build fail, while the Sentry Expo plugin in app.json breaks the gradle build; both pass `expo export` in CI. These are natural hard negatives (same tool, similar words, different root cause) for the lookup test set, and the seed corpus the store will first hold.
    CLAUDE.md, section 'Build & deploy traps' (project root of this worktree)
- F24 (verified, primary_docs; retrieval/engine/data_model) FTS5 facts for the pipeline: porter wraps another tokenizer (default unicode61) and stems; the trigram tokenizer matches no rows for query substrings shorter than 3 characters; the hidden 'rank' column can be remapped per query to bm25() with column weights, giving multi-field BM25-style ranking inside SQLite. node:sqlite in Node 24 ships FTS5 (see F05).
    https://sqlite.org/fts5.html (first 100k characters read)
- F25 (inferred, inferred; retrieval/limits) Design inference: RRF output depends only on ranks (F08), so any non-empty ranked list yields a top document with a positive fused score; RRF therefore cannot by itself support abstention. Abstention must use separate evidence: exact-handle hits, rank margin, IDF-weighted query-term coverage, and ultimately the verification gate.
    inferred from F08 and F25 reasoning
- F26 (inferred, inferred; retrieval/limits) Design inference for score-free thresholds. (a) Exact-handle hit: canonical error template, error code, tool name, file path or symbol equals a stored handle (deterministic, no scoring). (b) Coverage: sum of IDF over query terms matched in the best entry / sum of IDF over all query terms that occur anywhere in the corpus; bounded 0 to 1, robust to the N-dependence shown in F05. (c) Rank margin: top1 versus top2 on the same query only. Thresholds are set on the labelled set, one for 'show as a possible lead' and a stricter one for 'treat as a lead and run the gate', in the spirit of Chow's reject option (F18).
    inferred from F02, F05, F07, F18

## Open questions
- Threshold values (coverage cut-off, margin cut-off, how many hits to show) are not derivable from literature; they must be calibrated on the labelled set once roughly 30-50 entries and 100+ queries exist. Is that set big enough for stable thresholds? By the rule of three (F20) only to a rough bound.
- Do unicode61/porter in FTS5 tokenise build-tool output usefully (paths, camelCase, snake_case, version strings), or is a custom pre-tokeniser needed? Not tested; I only tested simple words.
- How reliable is a cheap-tier agent at judging 'same root cause?' on a 3-5 entry shortlist? No literature found for this domain; measure it as a separate metric in the harness.
- Which exact weights for fields (symptom handles vs cause vs title) and whether b (length normalisation) should be switched off because handles are short and similar in length. FTS5 cannot change b or k1; this would be the trigger for the hand-rolled ranker.
- Does the owner want candidate-level hits shown at all, or only leads? A miss is safe, but too many misses makes the store feel useless to the cheap agents; the balance is an owner decision informed by measured miss rate.
- Which local text embedding model, if any, would be acceptable (size, licence, Windows/Linux runtime) if the harness later shows vocabulary-mismatch misses. Not researched in this lane.
- BEIR and LIMIT numbers were read through a page summariser (ar5iv), not from the PDF; confirm the specific figures before quoting them in the design document.
