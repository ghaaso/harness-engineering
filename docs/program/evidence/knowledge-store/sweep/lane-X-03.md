## Summary
No single tool captures an entry's dependency footprint on this stack. Three automatic captures, each seeing a different kind of footprint, cover most cases. (1) Claude Code PreToolUse/PostToolUse hooks (or a post-hoc parse of the session transcript) log the files a diagnosing agent read and edited. That is a cheap, Windows-native candidate set, but it over-captures and it misses anything read through Bash. (2) Running the discriminating check once under V8 or coverage.py coverage gives the files and functions the root cause actually executes; function bodies can then be hashed so a whole-file edit does not invalidate the entry. It cannot see config files or external tools. (3) A fixed environment probe (node/npm/python/eas/expo versions, lockfile and Dockerfile hashes, config key paths) is selected per entry from the tool names in the agent's Bash commands. File-access tracers are the weakest fit. fsatrace has no prebuilt Windows binary and cost 46% overhead on Windows in Rattle's paper. Rattle and tup are whole build systems. Bazel's sandbox enforces a declared input set and does not discover one. Procmon and ETW need the Windows kernel driver and give system-wide noise. strace inside a Docker container is the one viable file tracer. The recipe misses remote-resolver traps (EAS cloud image and Gradle, Railpack/Railway detection) and data-state, time and race causes. For the remote-resolver traps, capture what the tool prints about its own resolution (for example the EAS image name in the build log). Over-capture only costs a re-verification; under-capture risks a false positive. Prune the footprint only on evidence.

## Design implications
- (strong) Store a footprint as typed items with a provenance tier per item (read, fix-diff, executed, env-probed, tool-reported, lookup-chain), never as a flat file list. Invalidation then marks an entry 'needs re-verification' with the item that changed; it never deletes the entry. Dropping an item needs evidence. [F27, F28, F30]
- (strong) Capture happens once, when an agent records an entry, by a single command (for example `kb capture <entry>`). It reads the hook log or transcript for the session and subagent, takes the fix commit's changed files, runs the stored discriminating check under coverage, runs the environment probe for the tools named in the session's commands, and scans pasted tool output for resolution lines. The owner and the agent never list dependencies by hand. [F08, F09, F10, F11, F12, F16]
- (strong) Use hooks (or the transcript) for the candidate set and coverage for the causal set. The union goes in the footprint. The tier that appears in both is the high-confidence core, and read-only items that never executed are low-weight but still invalidate. This sidesteps over- and under-capture without a hand-maintained manifest. [F10, F12, F17, F27, F28]
- (strong) Invalidate at symbol level: hash the normalised source of each executed function (Python ast, TypeScript compiler API) with a whole-file blob OID as fallback. Normalise paths to repo-relative POSIX form and hash LF-normalised content so Windows and Linux agree. For JSON/TOML/YAML config, hash key paths (app.json#expo.plugins, eas.json build env) instead of the whole file. [F17, F22, F24, F31]
- (strong) Config and external-tool causes are not visible to coverage or hooks, so they need the environment probe and the tool-reported-resolution scan. For EAS the resolved image name and eas-cli version are the capturable items. For Railpack/Railway the lookup chain of version sources, the launch directory, and the presence of vite.config.* are the items. [F19, F20, F21, F29, F30]
- (moderate) Entries whose root cause sits in a remote resolver must carry a flag that their gate cannot be a local reproduction. The gate becomes 'inspect the tool's resolved output now and compare it to the recorded one'. Treat tool version bumps and floating defaults (EAS 'auto', Railpack 'lts', cli.version '>= 13.0.0', python:3.12-slim) as automatic invalidation triggers. [F19, F20, F21, F29]
- (moderate) A cheap completeness check on the Node side is to rerun the check under --permission with --allow-fs-read limited to the footprint; an access-denied error means the footprint is incomplete. A strace container run is the Linux-side calibration. Neither needs to be in the default path. [F07, F13]
- (moderate) Per-session hook logs must be written to per-session files (keyed by session_id and agent_id) and merged at capture time, so parallel worktrees and subagents never contend on one file. [F08, F09]
- (moderate) File-access tracers (fsatrace, Procmon, ETW) should not be in the Windows dev path: no prebuilt fsatrace binary, 46% Windows overhead in the paper, and the others are system-wide. Keep strace-in-Docker as an optional Linux calibration only. [F01, F02, F06, F07, F26]
- (moderate) The backend has no lockfile and no coverage tool in its dev dependencies, and root Vitest has no coverage package. The first implementation phase therefore needs two small dev-dependency additions (coverage for Python, @vitest/coverage-v8 or direct NODE_V8_COVERAGE use for Node) or must fall back to NODE_V8_COVERAGE and package-set snapshots only. [F15, F16, F21]

## Rejected paths
- Hand-maintained dependency manifest per entry — Contradicts the owner's 'less to track' constraint, and hand lists go stale in the unsafe direction (missing items cause false positives).
- Building fsatrace from source on Windows as the standard capture tool — Needs a 32/64-bit mingw toolchain, no prebuilt binary, 46% measured Windows overhead, 32-bit-parent/64-bit-child blind spot, and cannot see remote EAS/Railway work.
- Adopting Rattle, tup or Bazel as the way to get footprints — They are build systems that must own the commands and, for tup and Bazel, are Linux/macOS-centred (tup's 'c' flag is ignored on Windows; Bazel's sandbox page does not mention Windows). They do not attach a footprint to a diagnosis.
- Relying on hook file reads alone as the footprint — Over-captures exploratory reads and misses files read inside Bash commands, so it would be both noisy and incomplete.
- Time-based expiry as the footprint substitute — Already ruled out by the agreed framing; invalidation is event-driven. Footprint items are what make event-driven invalidation possible.
- Procmon or ETW as an automatic capture step — System-wide noise, elevation needed (inferred), no documented headless path in the pages read.
