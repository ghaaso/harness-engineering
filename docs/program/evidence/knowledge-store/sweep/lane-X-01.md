## Summary
WebSearch was refused (budget exhausted), so I used WebFetch on primary docs, GitHub APIs and source files, plus two local tests. The two round-1 designs are not rivals. The SQLite file is the same in both. The real question is which thing is the source of truth. Recommendation: (1) immutable per-entry event files in a dedicated store repo, kept outside the code repo and its worktrees, synced by git over SSH to a bare repo on the VPS, with a rebuildable per-host SQLite/FTS5 index; (2) a single SQLite file on the dev box with one-way backup (VACUUM INTO or sqlite3_rsync) to the VPS. Ranked by ongoing workload, (2) is cheaper on day one but cannot take VPS writes and needs a backup job. (1) wins once two hosts write. (2) is also stage 0 of (1), because the index is that file. Tested on this Windows box: 4 concurrent WAL writer processes had 0 errors, backup under load passed integrity_check, and restore then write worked. Tested in a scratch git repo: events in distinct files merge cleanly, including under squash merge, while a shared append file conflicts without merge=union. Events committed only on an abandoned branch vanish from main. Every candidate engine (sqlite3_rsync, Litestream, libSQL, rqlite, cr-sqlite, Dolt, VPS service) either replicates one way, needs the network for writes, or is a cluster or VCS built for a much larger workload. No tested path exists for sqlite3_rsync from Windows to Linux; it needs a binary I may not install.

## Design implications
- (moderate) The two round-1 designs are compatible. The dev-box SQLite file (option a) should be the derived local index, and immutable event files in a store repo (option b) should be the replicated truth. Start with the SQLite file and CLI, and add the event-file journal and sync when a second host needs to write. [F01, F10, F20]
- (strong) Keep the store OUTSIDE every worktree and outside the code repo: an absolute path, or something derived from git's common dir. All worktrees then see one data set (F19). Entries cannot vanish when a feature branch is abandoned or squash-merged (F20). A store inside a worktree would fork per worktree, and events committed only on a deleted branch disappear from main. [F19, F20, F22]
- (strong) Answer for an entry written in a worktree whose branch is abandoned or squash-merged: if the entry lives in the separate store repo, nothing happens to it. If it was committed in the code repo's feature branch, an abandoned branch drops it from main (recoverable only via reflog for about 30 days plus a 2-week prune grace), and a squash keeps the file but loses the original commit SHAs. Never use a feature-branch commit SHA as an anchor. Anchor entries on blob or tree hashes of the files they depend on, plus dependency and platform versions, which survive a squash. A hit whose anchor files changed is simply an invalidation event. [F20, F22, F23]
- (strong) Use one immutable file per event (content-hash or ULID name, canonical JSON, LF). Distinct paths merge conflict-free, while a shared append file conflicts and union merge has unreliable order. State changes (confirmed, refuted, invalidated, revised) are new event files. Pin LF in the store's .gitattributes so hashes agree across Windows and Linux. [F20, F21, F24]
- (strong) Make the SQLite index per host and rebuildable. Only same-host processes open it (WAL). Never place it on a network share, in a synced folder, or on Docker-for-Windows bind mounts. The tested pattern: busy timeout around 5 s, WAL, multiple writer processes on one Windows box without errors. [F01, F08, F10]
- (moderate) Backup and restore drill (tested pieces marked): (1) backup = 'git push' of the store repo to a bare repo on the VPS, as every clone is a full copy; plus a snapshot of the index via node backup() or VACUUM INTO to a temp file with an integrity_check then rename, which I tested on Windows under write load; (2) restore = 'git clone' the bare repo and rebuild the index from the event files, or copy the snapshot and enable WAL, which I tested; (3) drill monthly or per release by cloning into a temp directory, rebuilding, and comparing the entry count and a hash of all event IDs against the live store. sqlite3_rsync is an optional faster snapshot transport, not a requirement, and I could not test it. [F06, F07, F09, F10, F03]
- (strong) Behaviour with the VPS unreachable. With the git-event-file design the dev box is fully functional: it reads from its local index, writes new event files, and commits locally. Sync is a deferred push and pull, and retries are safe because event IDs are unique. With a VPS-resident service (rqlite, libSQL, a store daemon over SSH or MCP-HTTP) the dev box loses writes, and also reads unless it keeps a cache. Treat that as disqualifying for the agent lookup path. [F14, F13, F08, F20]
- (moderate) Do not use a merging database to solve a problem the event-file design does not have. cr-sqlite is per-column last-write-wins and rqlite and Dolt are cluster or VCS systems sized well beyond a few hundred rows. Dolt additionally ships default-on telemetry that must be disabled and verified. Cite Beads and Dolt for design lessons only (hash IDs, export is not truth, full-fidelity backup). [F14, F15, F16, F17, F18]
- (moderate) The egress constraint decides the sync remote. A bare git repo on the VPS over SSH keeps defect text owner-controlled, while the existing code remote (GitHub, per the gh CLI usage) does not. Use a separate store repo and remote, and never push the store to the code remote. Use SSH keys, and plain WireGuard if a tunnel is needed. Tailscale's coordination server and default log upload are third-party, so Headscale would be the only acceptable mesh option. [F26, F27, F28]
- (moderate) Agent access should be a CLI invoked on the same host as the agent, with an MCP stdio wrapper over the same CLI. A remote HTTP MCP endpoint is optional later and must meet the spec's Origin validation, localhost bind and authentication requirements. This avoids a new network auth surface for a one-developer shop. [F25]
- (strong) Version gate: any host that opens the index must run SQLite >= 3.51.3 (or the 3.50.7 / 3.44.6 backports) to avoid the WAL-reset corruption bug, and, if sqlite3_rsync is used, both ends should be >= 3.50.0. Node 24's bundled 3.53.4 on the dev box satisfies this. The VPS runtime must be checked at install time. [F02, F03, F09]

## Rejected paths
- Putting event files on feature branches of the code repo, or in a docs/ folder inside a worktree — Entries on an abandoned branch vanish from main (tested), and a squash drops original commit SHAs. A worktree-local DB forks per worktree.
- A shared append-only JSONL log merged with merge=union — Without union the same-file append conflicts (tested). With union, git's own docs say the line order is arbitrary and must be verified, and the result cannot be checked for duplicate or ordered IDs.
- SQLite file on a network share or synced folder (SMB, NFS, OneDrive-style) shared by Windows and Linux — WAL needs same-host shared memory and SQLite's own docs say network locking and fsync are unreliable. Sync tools that move or miss -wal files corrupt databases.
- sqlite3_rsync as a bidirectional sync — It is one-way. The replica is overwritten, so writes made on the replica are lost.
- libSQL/sqld — No Windows binary, upstream steers to Turso, last server release 2025-02-14, and no offline writes.
- cr-sqlite — Per-column last-write-wins loses concurrent edits, no event log in v1, and the latest release is from January 2024.
- Tailscale (hosted coordination server) as the transport — Third-party control plane and default log upload, which breaks the egress rule. Plain SSH or WireGuard is enough.
- git notes for entry storage — Anchored on commit SHAs that squash and branch deletion drop; not synced by default; the rewrite config is unset by default.

## Facts
- F01 [LOAD-BEARING] (verified, primary_docs; concurrency/engine/ops_cost) SQLite WAL requires all processes on the same host; it does not work over a network filesystem because the wal-index is shared memory (an mmapped file next to the database).
    https://www.sqlite.org/wal.html (read 2026-11-02; sections 1, 2.2, 7)
- F02 [LOAD-BEARING] (verified, primary_docs; concurrency/limits/engine) A SQLite WAL-reset data race can corrupt a WAL-mode database when two connections write or checkpoint at the same instant. It is present in 3.7.0 through 3.51.2 and fixed in 3.51.3 (2026-03-13), with backports in 3.44.6 and 3.50.7. Any host that runs the store (dev box, VPS) must use a fixed version.
    https://www.sqlite.org/wal.html section 11 (read 2026-11-02)
- F03 [LOAD-BEARING] (verified, primary_docs; engine/ops_cost/concurrency) sqlite3_rsync makes REPLICA a copy of ORIGIN. It is one-way. ORIGIN may be in use and the result is a consistent snapshot. REPLICA is read-only while the tool runs, and any independent writes to it are overwritten. Remote use needs SSH and the sqlite3_rsync binary on the remote PATH (or --exe). From 3.50.0 (2025-05-29) the WAL and page-size requirements are gone. Mixing a 3.50+ side with a 3.49.1-or-earlier side can hang (workaround: --protocol 1). At least one side must be local; one database per invocation.
    https://sqlite.org/rsync.html (read 2026-11-02)
- F04 (verified, primary_docs; engine/ops_cost) sqlite3_rsync Windows notes: the page says a single-letter host is treated as a drive letter, and the author had no success running SSHD on Windows, so it gives no instructions for syncing with a remote Windows machine. The dev box can therefore only be the local side, with the VPS as the remote SSH side.
    https://sqlite.org/rsync.html (read 2026-11-02)
- F05 (verified, primary_docs; engine/ops_cost) The official SQLite download page lists sqlite-tools-win-x64 for version 3.54.1, containing sqlite3.exe, sqldiff.exe, sqlite3_analyzer.exe and sqlite3_rsync.exe. The page gives no release date.
    https://www.sqlite.org/download.html (read 2026-11-02)
- F06 [LOAD-BEARING] (verified, primary_docs; engine/ops_cost/concurrency) SQLite's 'How to corrupt' page names three safe ways to copy a live database: sqlite3_rsync (3.47.0+), VACUUM INTO, and the backup API. A plain file copy is safe only when no transaction is in progress, and the -wal/-journal file must travel with the database. Moving or deleting hot journals, or copying a database without its journal, can corrupt it.
    https://www.sqlite.org/howtocorrupt.html sections 1.2-1.4 (read 2026-11-02)
- F07 (verified, primary_docs; ops_cost/engine) VACUUM INTO writes a consistent, transactional snapshot to a new file (the target must not exist or must be empty). The source is untouched and a live source is fine. It fails if the calling connection has an open transaction. A crash mid-run can leave a corrupt output file, so write to a temp name and rename after an integrity check.
    https://www.sqlite.org/lang_vacuum.html (read 2026-11-02)
- F08 (verified, primary_docs; engine/concurrency/access) SQLite's own advice for use over a network is to avoid network filesystems. Either use a client/server engine, or keep WAL SQLite on the data host behind a proxy that relays remote requests. File locking and fsync over NFS/SMB are unreliable and not tested by the SQLite project.
    https://www.sqlite.org/useovernet.html (read 2026-11-02)
- F09 [LOAD-BEARING] (verified, local_file; engine/access/ops_cost) The Windows dev box already has Node v24.22.1, whose built-in node:sqlite reports SQLite 3.53.4. That is at or above the F02 fix level. node:sqlite is Stability 1.2 (release candidate) in v24 docs. It has backup(sourceDb, path) since v23.8.0, and the source stays usable during a backup, but writes from other connections restart the backup. It needs no install.
