# lane:E-02

lane=E-02 tool_status=ok facts=21 candidates=10

## Summary
None of DuckDB, LanceDB or Kuzu is a sensible PRIMARY store for tens-to-hundreds of entries with a few concurrent agent writers. Read-only doc fetches only; no code or defect text was sent to any search.

DuckDB (2.0.0 LTS, released 2026-10-21) is an OLAP engine with one read-write process per file, or many read-only processes. Its FTS is BM25 with Porter stemming, but the index does not update automatically unless built with incremental=1. Its HNSW persistence is still experimental and not recommended for production. Its best role is an optional analytics layer: ATTACH a SQLite file or a Postgres database READ_ONLY and run outcome analytics (hit/refute/miss, cost saved) without owning the data. At a few hundred rows plain SQL on the primary does this too, so the layer is optional. The Node client @duckdb/node-api supports Windows x64.

LanceDB (npm 0.41.0, Apache-2.0, Windows x64 prebuilt) is designed for millions of vectors. Its own FAQ says ~100K records need no vector index. Its genuinely useful ideas are versioning with tags, checkout and restore (cite for design) and BM25 FTS. Rows added after the FTS index was built are not indexed until optimize(). Concurrent local multi-process write behaviour is undocumented and has reported commit-conflict issues.

Kuzu is rejected. The repository was archived 2025-10-10 after an Apple acquisition (EU filing; Apple has not announced it). The npm package is deprecated and builds from a 525 MB source tarball. Forks (LadybugDB, RyuGraph, Bighorn) are young, with unconfirmed Windows and Node support. A graph view of entry dependencies can be a recursive CTE or an edge table in the primary.

## Design implications
- (strong) Do not make DuckDB, LanceDB or Kuzu the primary store. Pick a primary with a safe multi-writer story and text/vector-friendly features (SQLite/Postgres lanes), and treat DuckDB as an optional read-only analytics view attached over it when outcome analytics outgrow plain SQL. [F05, F07, F08, F20, F21]
- (strong) Any FTS index (DuckDB, Lance) is a snapshot needing explicit rebuild/optimize after writes. Whatever engine is chosen, the write path must rebuild or incrementally maintain the index in the same transaction or step, or retrieval silently returns stale results. A stale index is a precision hazard on top of the false-positive risk. [F03, F15]
- (strong) Skip ANN/vector indexes entirely at this scale. Brute-force similarity over a few hundred vectors is faster than any index overhead. DuckDB HNSW persistence is unsafe, and Lance says ~100K records need no index. [F04, F18, F21]
- (moderate) Model entry history as an append-only event table (confirmed/refuted/invalidated/revised) in the primary store and borrow the Lance 'immutable versions + named tags' idea for naming knowledge-base snapshots; do not depend on Lance to implement it. [F16]
- (strong) Do not build on Kuzu or its young forks. Represent entry-to-file/symbol/dependency edges as an edge table and query them with recursive CTEs, which any primary supports and which keeps invalidation (what changed -> which entries depend on it) inside one engine. [F11, F12, F13, F21]
- (moderate) If DuckDB is used at all, pin DuckDB 2.0.x only after the first patch release (planned November) and keep it strictly read-only against the primary. The 2.0 file format is not readable by older versions, so DuckDB-owned files must be disposable or regenerable from the primary. [F01, F02]
- (moderate) Egress is a install-time concern only for DuckDB (extension binary download), so pre-stage extensions via extension_directories for the Linux VPS. LanceDB's telemetry posture is unverified and must be checked before any adoption. [F09, F19]

## Rejected paths
- DuckDB native file as the shared primary store with agents writing from several worktrees — One read-write process per file. Parallel agents would need a single-writer daemon or the new Quack server, which is extra ops for one developer and not needed at this write volume.
- DuckDB VSS HNSW index for entry similarity — Persistence is experimental, with possible corruption after a crash. The docs advise against production use, and ANN is unnecessary at a few hundred vectors.
- Kuzu (or a fork) as a graph store for entry dependency/provenance edges — The upstream repo is archived and the company acquired, the npm package is deprecated and source-built, and the forks are young. An edge table plus recursive CTE meets the need with no extra engine.
- LanceDB as the single store for entries, FTS, vectors and versions — Designed for millions of vectors. FTS is stale for new rows until optimize(). Concurrent local multi-process writes are undocumented. Telemetry posture unverified. Its versioning idea is worth citing but does not carry the outcome semantics.
- MotherDuck for shared analytics — Sends code and defect data to a third party. Disqualified for production.
