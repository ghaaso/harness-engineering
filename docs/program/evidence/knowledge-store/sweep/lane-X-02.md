# lane:X-02

## Summary
The gate is the false-positive defence, so how it runs is a security and correctness problem, not plumbing. Two things matter most. First, the verdict must be harness-owned, never inferred from an exit code. git bisect run treats exit codes 1-127 (except 125) as bad, which includes 127, command not found. Python and Node crashes also exit 1, and pytest returns 5 when it collects no tests. Every one of these would read as "defect reproduced" or "defect gone" without the check testing anything. A check should count as `applies` only if the runner's own result file shows a named test or probe ran and failed on an assertion. Everything else is `inconclusive`, which behaves as a miss. Second, the isolation story differs by OS. Native Windows has no usable headless sandbox. Claude Code's own sandbox is off on native Windows, and its MCP tools and hooks run outside the sandbox anyway. Windows Sandbox's `wsb exec` returns no output and needs an RDP session. The practical Windows answer is the Docker Desktop that is already installed: `--network none` or an `--internal` network, a read-only root, a detached worktree mounted read-only, an allow-list environment, and a throwaway postgres:16-alpine. It also works unchanged on a Linux VPS. The repo makes this urgent. `backend/tests/conftest.py` TRUNCATEs every table on whatever `FIXFLOW_TEST_DATABASE_URL` names, and `Settings` defaults to the compose database on localhost:5432. Web search budget ran out mid-lane, so Google flaky-test statistics and Bazel flag details are unverified.

## Candidates
- **Minimal gate-runner contract (inputs, effects, output, tri-state)** [pattern] strong — A single CLI, `gate run <entry_id>`, exposed by CLI and MCP, is the only way a check executes.

INPUTS (a JSON spec, hash-pinned):
- check_id
- kind: one of test_id | structural_probe | scripted
- argv: an array, never a shell string
- repo_sha: the commit under test, run in a fresh `git worktree add --detach` that must be clean
- profile: python-backend | node-web | node-mobile-jest
- needs_db: bool
- timeout_s
- expects: { named test ids or probe id, min_executed >= 1 }
- control: { fails_at_sha, passes_at_sha }
- requires_capability[]
- approval: { approver, spec_sha256, approved_at }

The runner mints a nonce.

ALLOWED EFFECTS:
- Read: the worktree, mounted read-only.
- Write: a tmpfs scratch directory and a results directory, the only writable paths.
- Env: an allow-list only (PATH, HOME=scratch, TZ=UTC, LANG, CI=1, plus FIXFLOW_* pointing only at the throwaway database); nothing else is inherited.
- Network: none, or an --internal docker network containing only the throwaway postgres.
- Never present: host home, docker socket, .env files, tool logins, host ports.
- Resource caps: memory, pids, cpus, wall-clock.
- Dependencies: come from a prebuilt read-only image keyed by lockfile hash, built by a trusted separate step.
- Fail closed: if the sandbox cannot start, the result is inconclusive/sandbox_unavailable. There is no unsandboxed fallback.

OUTPUT (JSON written by the runner, never by the check):
- schema_v, check_id, spec_sha256, repo_sha, tree_clean
- verdict, reason_code
- evidence: { tests_selected, tests_executed, named_ids_seen, failure_type: assertion|error|none, result_artifact_sha256 }
- attempts[], control_runs[]
- duration_ms, sandbox_profile, env_fingerprint (key names only), egress_blocked_count, runner_version

TRI-STATE:
- applies = root cause reproduced. Requires an approved spec hash, the sandbox fully engaged, the named id executed, an assertion-type failure (not an error), and agreement across reruns. When a control exists, it must also reproduce on the pre-fix control.
- not_applies = a valid, non-vacuous run reached its end sentinel and the defect condition was absent, consistently.
- inconclusive = everything else, with a reason_code from: sandbox_unavailable, unapproved_spec, tree_dirty, timeout, oom, vacuous (pytest exit 5 / no tests), collect_error, infra_exit (126/127/137...), flaky, capability_missing, egress_attempted, control_not_reproduced.

Semantics: only `applies` lets an agent act on an entry. `not_applies` feeds relevance feedback (refute or invalidate candidate). `inconclusive` is a plain miss that escalates. The runner CLI's own exit codes are 10 applies, 11 not_applies, 12 inconclusive, and agents read the JSON. Any other code means the runner itself crashed, which counts as inconclusive. This mirrors the git bisect run precedent but reserves exact codes and uses a harness-owned verdict.

## Design implications
- (strong) Make the gate runner the only code path that executes stored checks. It owns worktree, sandbox, env, timeouts and the result file, and agents (cheap or expensive) never exec a stored command themselves. The store holds check specs as data (kind plus argv plus expectations), not shell strings. [F19, F20, F21, F22]
- (strong) Derive the verdict from a runner-owned artifact, not from the child's exit code. Reserve exact codes bisect-style, but treat 126/127, 137, 255, pytest 3/4/5, and Jest no-tests as inconclusive. A crash must never read as 'defect reproduced' because Python and Node crashes exit 1. [F01, F02, F12, F28]
- (strong) Tri-state is applies / not_applies / inconclusive; only `applies` permits action, `inconclusive` is a miss that escalates, and `not_applies` triggers refute/invalidate feedback. 'Could not run' (no Android/EAS, sandbox unavailable, flaky, timeout) is never `not_applies`. [F01, F30, F27]
- (strong) Run every check in a container (Docker Desktop on the dev box, same image on the VPS) with no network or an --internal network, read-only worktree, scratch tmpfs, allow-list env, HOME redirected, no docker socket, resource caps. Fail closed if the sandbox cannot start. There is no unsandboxed fallback. [F03, F06, F07, F05]
- (strong) Never let a check see a real database. Always give DB-needing checks a per-run throwaway postgres:16-alpine on an internal network, and make the runner reject any DB URL whose host is not that container. The repo's conftest TRUNCATEs whatever URL it is given and Settings defaults to localhost:5432 (the compose DB), so an unset or inherited variable is a data-loss path. [F13, F14, F16, F17]
- (moderate) Credential hygiene is layered. Env allow-list plus redirected HOME plus a container with nothing mounted is the boundary; a fresh worktree (which lacks gitignored .env) is only a convenience. Real secrets are probably in the shell, ~/.railway and Railway/Supabase dashboards, not repo files, so scrubbing env and HOME matters more than hiding .env files. [F09, F15, F19, F06]
- (strong) Prefer declarative check kinds (existing test id at a pinned sha, ripgrep/Semgrep/ast-grep structural rules) and make free-form scripted checks the exception, each requiring approval bound to the sha256 of its canonical spec. An edit voids approval, and the approver is never the author. [F20, F21, F23]
- (strong) Require evidence that the check could fail. Store a control pair (fails_at/passes_at shas), assert named test ids actually executed (>= 1, id seen in the result artifact), and have the approver demonstrate fail-on-pre-fix before approval. This addresses vacuous passes such as pytest exit 5 or a Jest run that finds no tests. [F12, F29, F11]
- (moderate) Dependency preparation (npm ci, pip install) is itself code execution and needs network, so keep it in a separate trusted step that builds a read-only image or cache keyed by the lockfile hash (--ignore-scripts where feasible). The check then runs offline. Checks that need a native Android or EAS build declare requires_capability and return inconclusive. [F26, F30]
- (moderate) Flaky handling: rerun only on disagreement, require unanimity for `applies`, record every attempt, and treat a split as inconclusive/flaky with an entry-level flake counter. Do not cite Google's flake-rate figures, which were not verified here; Spotify's described tooling is detection, not a rerun policy. [F27, F28]
- (strong) The Windows dev box should not rely on Windows Sandbox, job objects or Claude Code's native sandbox for isolation. They are headless-unfriendly, resource-only, or unsandboxed on native Windows respectively. Docker (WSL2 backend) is the common denominator with the Linux VPS, and WSL2 plus bubblewrap is the fallback if Docker is ruled out. [F03, F04, F08, F07, F25]

## Rejected paths
- Windows Sandbox as the Windows isolation layer — `wsb exec` has no process I/O and needs an RDP session, single instance only, needs Windows 11 24H2, Windows-only (so no parity with the Linux prod), and wsb.exe was not found on this box. Docker gives the same isolation on both OSes.
- Relying on a read-only Postgres transaction or session default as a safety control — default_transaction_read_only is only a default for new transactions and can be reversed by SET TRANSACTION in agent-written SQL. Use a throwaway database or a SELECT-only role.
- Using the raw exit code of a stored command as the verdict (git bisect run semantics applied unwrapped) — The 'bad' range 1-127 contains 126/127, and Python/Node crashes and pytest failures all exit 1, so crashes and mis-configurations read as 'defect reproduced'. Verdict must come from a runner-owned result artifact.
- Relying on 'the worktree has no .env' or 'the agent is told not to read secrets' as credential protection — A fresh worktree only omits gitignored files in the tree. The check can still read other paths (home directory logins such as ~/.railway, the main checkout) and inherited environment variables; Node spawn inherits the full env by default.
- Adopting Claude Code's sandbox (or its sandbox-runtime) as the gate's boundary on the Windows box — Native Windows commands run unsandboxed, startup failure falls back to unsandboxed by default, and MCP servers and hooks are outside the sandbox.
- Adopting Bazel or Nix as the hermetic runner — Nix sandboxing is Linux/macOS only, Bazel's page does not cover Windows and admits it does not hide the host environment, and both are far heavier than the workload (tens to hundreds of checks, one developer).

## Facts
- F01 [LOAD-BEARING] (verified, primary_docs; workflow/limits) git bisect run: the command must exit 0 if the current source is good/old, and exit with a code from 1 to 127 inclusive, except 125, if bad/new. Any other exit code aborts the bisect. 125 means the revision cannot be tested and is skipped. exit(-1) leaves 255 and so aborts.
    https://git-scm.com/docs/git-bisect (manual for Git 2.56.0, read 2026-11-02)
- F02 (inferred, inferred; workflow) Consequence of F01 for stored checks: because 126 and 127 (not executable, command not found) fall inside the 'bad' range, a missing interpreter is classed as bad. Bisect's good/bad/skip/abort is a sound tri-state precedent only if the wrapper reserves exact codes and treats everything else as abort or skip. It is not safe to use the raw child exit code as the verdict.
    inferred from F01
- F03 [LOAD-BEARING] (verified, primary_docs; access/egress/limits) Claude Code's sandbox is built on @anthropic-ai/sandbox-runtime. It uses Seatbelt on macOS and bubblewrap plus socat on Linux and WSL2, with a separate network namespace on Linux. 'On native Windows, Claude Code runs commands unsandboxed.' WSL1 is unsupported.
