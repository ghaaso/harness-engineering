# lane:E-09

lane=E-09 tool_status=ok facts=30 candidates=15

## Summary
Best answer to "history plus branch/worktree merge without a second server" is the index-is-a-cache pattern, with immutable event files in git as truth and a rebuildable local index. Fossil tickets do this today, git-bug does it via an op-DAG, and Beads did it as JSONL plus SQLite until it abandoned it for Dolt (v1.x). That pivot is the main warning: mutable one-record-per-line JSONL needed a custom merge driver and a daemon. Recommended shape (inferred): append-only, immutable events, one small file per event named by content hash, with supersede and refute recorded as new events. Git then merges them as pure adds, so no conflicts and no custom driver (the built-in merge=union is the fallback). Truth lives on a branch, or in a shared custom ref if instant cross-worktree visibility is needed (refs/ are shared across worktrees; branch files are not). The index is a gitignored node:sqlite (RC in Node 24, no install) or in-memory file rebuilt from the events. A hash chain like the repo's staff_ledger_chain gives tamper evidence at zero cost. Dolt is the real alternative for native branch/merge/diff/cell-level conflicts and can sync through a git remote, but costs a ~103 MB binary, usually a server process, and shows no worktree story. A SQLite file in git is rejected as truth (binary, WAL/journal pairing hazards, no merge). immudb, XTDB, Datomic, TerminusDB and lakeFS are cite-design-only or rejected: wrong scale, server/JVM weight, or licence. Egress: everything here is self-hostable. The only documented egress is the explicit Dolt/git remote and the Beads install script. Dolt's own telemetry stance is unverified.

## Design implications
- (strong) Make immutable, uniquely identified events the unit of truth and merge, with each state change (create, confirm, refute, invalidate, revise) a new event, never an in-place edit. Every successful prior system that merges across clones does this (Fossil, git-bug), and Beads classic, which kept mutable records per line, is the one that needed a custom merge driver and was later replaced. [F02, F05, F13, F29]
- (strong) Treat any query engine (SQLite via node:sqlite, or later another) as a disposable, gitignored index rebuilt from the events, with a recorded 'built from event set X' watermark. This gives engine swappability behind the abstraction layer and removes the need to merge database files. [F05, F20, F19, F17]
- (strong) Do not commit a SQLite database file or rely on sqldiff/textconv as the merge story: those only improve reading diffs, and the merge of two binary versions is a conflict. Use .dump or NDJSON only as read-only views. [F15, F16, F17]
- (strong) Cross-worktree visibility is a separate problem from merge. Files on a branch are seen only after merge or checkout, while refs are shared by all worktrees at once. Decide explicitly between (a) a tracked directory plus a sync step at phase boundaries and (b) a custom shared ref with compare-and-swap writes. Option (a) is simpler for a solo developer; (b) is what git-bug and Dolt's git remote do. [F08, F13, F11]
- (moderate) One file per event, named by content hash and written temp-then-rename, is the lowest-risk layout: it removes line-level merge conflicts, avoids multi-writer append races on one file, and keeps merge=union as an unneeded fallback. It matches the CLAUDE.md preference for less to track. [F07, F30, F27]
- (moderate) Dolt is the credible upgrade path if native branch/merge/diff semantics on tabular data become necessary, since it gives column-level conflict tables and git-remote sync with no hosted service. It should sit behind the abstraction layer as an optional engine, not be the first choice: ~103 MB binary, a server process for concurrent writers, no worktree guidance, and git-remote history squashes after 64 commits so git history is not a provenance record. [F09, F10, F11, F01, F03]
- (moderate) Provenance and tamper evidence can reuse the repo's existing hash-chain pattern (sha256 of version, payload, previous hash) or content-addressed filenames; a verifiable-ledger database such as immudb is unneeded for one trusted developer. [F28, F21]
- (moderate) A zero-install, no-new-binary path exists: git 2.56 plus Node 24's node:sqlite (RC). The unprobed items are FTS5 availability and the stability of an RC module, so the abstraction layer should keep a plain in-memory fallback index. [F19, F27]
- (moderate) Beads is evidence about failure modes of the JSONL+SQLite+daemon design (auto-import timing, per-workspace daemon, socket/lock files to gitignore, a merge driver per file) and is a signal that the most visible adopter chose Dolt for 'proper merge semantics'. It is the strongest argument for keeping events immutable and index-free of any daemon. [F02, F03, F04]

## Rejected paths
- Committing a SQLite database (or SQLite plus textconv/sqldiff) to git as the source of truth — No three-way merge for binary files; WAL/journal pairing and live-copy corruption hazards; sqldiff skips PK-less tables and can corrupt FTS5; textconv diffs are one-way.
- Adopting Beads as the knowledge store — It is an issue/dependency tracker on a fast-changing Dolt backend with default agent-hook installation; the schema does not model symptom handles, verification gates or outcome history. Cite its design only.
- Adopting Fossil alongside git — A second SCM and sync model for a one-developer, git-worktree workflow, however elegant its append-only ticket design.
- git notes as the primary store — Keyed to commits rather than symptoms; need extra config to survive rebase and to push or fetch.
- lakeFS, TerminusDB, XTDB, Datomic, immudb as the production store — Each adds a server or JVM stack, a restrictive or non-OSS licence (BSL, closed-source binaries) or a scale mismatch of orders of magnitude, and none improves on git for cross-worktree merge.
