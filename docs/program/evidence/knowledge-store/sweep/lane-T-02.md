# lane:T-02

lane=T-02 tool_status=ok facts=34 candidates=15

## Summary
The theory points to one design. Each entry is an immutable identity plus an append-only stream of outcome events (recorded, confirmed, refuted, invalidated, revised, superseded, withdrawn). The current view is a fold over that stream, as in Microsoft's event-sourcing pattern (F07). At tens to hundreds of entries the fold is a SQL view or a rebuild on read. Snapshots, CDC, brokers and Merkle trees are not needed (F25, F26). Corrections are new events, never edits. Each event carries typed facets (symptom, failed approaches, fix, validity, gate), the OpenLineage idea (F03), in PROV vocabulary: invalidated = wasInvalidatedBy, revised = wasRevisionOf (F01, F02). The bitemporal split (F09) holds, with one change. Transaction time is the event log. The "valid time" axis is not wall-clock; it is a predicate over git. OSV's GIT ranges (F13) and a build-system verifying trace (F14) supply the model. At confirmation, record the mainline commit and the blob OIDs or symbol hashes of the files the diagnosis depended on. At lookup, compare them to HEAD with git diff --quiet and git merge-base --is-ancestor (F15, F16). A changed footprint means suspect and forces the gate; an unchanged footprint is necessary but not sufficient, so the gate still runs. FixFlow squash-merges now (F20), so store mainline SHAs and blob OIDs, never PR-branch SHAs. A hash chain adds little here (F21): the threat is accidental overwrite, not an adversary. XTDB and Datomic are cited for design only.

## Candidates
- **Append-only outcome-event stream with current view as a fold (event sourcing at small scale)** [pattern] strong — Exactly fits: tens to hundreds of entries, few writes, a provenance history per entry (confirmed, refuted, invalidated, revised, superseded) that must never lose anything, and a current view that is cheap to recompute. At this volume the fold is a SQL view or rebuild on read, so snapshots, brokers, CQRS read stores and event versioning machinery are unnecessary. The Microsoft page itself warns the pattern is costly for most systems; the justification here is narrow and real (audit of what failed and why, relevance feedback, analytics from the same log). Keep it to ONE aggregate (the entry) and compensate with new events, never edits.

## Design implications
- (strong) Model each entry as an immutable identity plus an append-only entry_event stream. The kinds are recorded, confirmed, refuted, invalidated, revised, superseded, withdrawn and reaffirmed-after-gate. The current status, text and footprint are a pure fold over the stream. No UPDATE or DELETE on events is allowed (enforced by the engine), corrections are new events, and replacement is a new revision row with revision_of (PROV wasRevisionOf). Lookups, misses and hits go in a separate lookup_event table with the same envelope, so analytics do not pollute entry history. [F01, F02, F07, F08, F27]
- (strong) Separate two axes on every event: record time (event timestamp and per-entry sequence; display only, order is the sequence) and code state (observed_commit plus a footprint of blob OIDs or symbol hashes, dependency lockfile hashes and platform tags). Never use wall-clock age to decide validity. Staleness is computed at lookup by comparing the recorded footprint to HEAD (git diff --quiet on the recorded paths, or blob OID equality). Changed means 'suspect', which routes the entry through the verification gate; it never means 'refuted' automatically. [F09, F14, F16, F17]
- (strong) An unchanged footprint is a necessary precondition, never a sufficient one, and must never skip the gate. A verifying trace is only as complete as its recorded dependencies; a dependency outside the footprint (a transitive package, a config in another repo, a Gradle or EAS setting) can change silently. Footprint capture is therefore part of writing an entry (what files, packages and platform did the diagnosis depend on), and the discriminating check remains the false-positive defence. [F14, F13]
- (strong) Record only durable git anchors: main-line commit SHAs and blob OIDs, never PR-branch SHAs. Recent PRs land as squash commits, so branch SHAs become unreachable from main. Before using a recorded commit, test it with git merge-base --is-ancestor <recorded> HEAD; exit 1 or an error means 'unreachable', and the check falls back to the blob-OID footprint. For a fix expressed as a patch, store its git patch-id so the same change can be recognised after a rebase. [F15, F17, F18, F20]
- (moderate) Where a root cause has a known lifetime, express it as OSV-style GIT ranges: introduced and fixed commit hashes, with every cherry-pick or re-application listed as its own fixed event. Evaluate it over the commit DAG with rev-list or is-ancestor. Make this optional metadata on the validity facet, because most entries only know 'verified at commit X on footprint F'. [F13, F15]
- (moderate) Store the payload as typed facets in a JSON column, each tagged with a schema version: symptom (raw text plus canonical template), failed_approaches (what was tried, why it failed, evidence), root_cause, fix, validity, verification_gate, cost. A facet is replaced whole by a new event, not patched. This is the OpenLineage mechanism (named facets, schema reference, tolerant of unknown facets) and keeps schema evolution cheap without a migration per field. [F03, F04, F08, F29]
- (moderate) Fold rules must be precision-biased and deterministic: a refute dominates a concurrent confirm until a later event observed on current code clears it; superseded and withdrawn entries are excluded from retrieval but remain readable; a re-confirmation updates the footprint only when the gate passed on current code. Refute events record the gate output and the footprint they were observed on, so relevance feedback and the 'revised' event can say exactly what changed. [F07, F13, F28]
- (strong) At this scale do not build projections incrementally. Re-fold on read (a SQL view or a short function), with no snapshots, cursors, CDC or message broker. The existing job_event/dispatch_cursor outbox is the wrong template, since a seq cursor can skip late commits and the repo's own 'gap-free' claim is doubtful. Revisit only if the event table reaches the 10^5-10^6 range. [F07, F22, F25, F26]
- (moderate) Concurrent writers (parallel worktrees, subagents) are handled by one write path (the CLI or MCP server owns the store), a unique (entry_id, entry_seq) for optimistic concurrency, and a client-supplied event_id for idempotent retry. If SQLite is the engine, WAL allows many readers and one writer but only on one host. If the store must be reachable from both the Windows dev box and a remote host, it needs a service or Postgres in front, not a shared file. [F07, F32, F33]
- (moderate) Tamper evidence is a v1 non-goal. The threat is accidental mutation by an agent or script, which engine-level insert-only enforcement and a content-hash event id already cover. A prev_hash chain (reusing the chain.py design: genesis, version-tagged hash input, honest-limit note) can be added later; if added, anchor the head hash in git to cover the truncation gap the chain cannot detect itself. Merkle logs and consistency proofs (CT, Crosby-Wallach) stay cited design only. [F21, F23, F24]
- (weak) Analytics fall out of the same logs: hit, refute and miss rates come from lookup_event joined to outcome events, and cost saved can be estimated as the recorded original-diagnosis cost (tier, tokens, wall time, stored on the recorded event) minus the cheap lookup-plus-gate cost. The estimate is inferred, since nothing here has measured it. Store cost at write time, or it cannot be reconstructed later. [F07, F27]
- (moderate) Use PROV and OpenLineage vocabulary for naming and schema discipline only. No RDF store, no OpenLineage server or client, no lineage catalog. They solve interoperability and scale this project does not have, and each adds a service for one developer to run. [F01, F02, F03, F30, F31]

## Rejected paths
- Use a bitemporal database (XTDB, or Postgres 18 temporal constraints plus hand-made system versioning) with wall-clock valid time — The validity question is 'which code states does this hold for', which is a predicate over the git DAG, not an interval of dates. Wall-clock valid time would encode a proxy (e.g. 'valid until the next deploy') that breaks under rebases, branches and out-of-order deploys. XTDB is also a separate server platform of unclear stability; Postgres 18 temporal constraints give range keys but no system versioning.
- Time-based expiry or TTL on entries — Contradicts the agreed event-driven invalidation. Age says nothing about whether the files, dependencies or platform the diagnosis depended on changed; a TTL would expire valid entries and keep stale ones.
- Record validity as a PR-branch commit SHA or as a single 'validated at commit X' without a footprint — Under squash merging the branch SHA becomes unreachable from main (and a bare 'at commit X' tells you nothing about which files mattered). It would turn every entry into 'unreachable' or force a full re-derivation.
- Treat 'footprint unchanged' as proof the entry still applies — A verifying trace only covers recorded dependencies. Unrecorded or transitive changes make this the exact false-positive failure the program most fears. It must only lower the cost of the gate (skip a full re-diagnosis), never replace the gate.
- Incremental projections via CDC, an outbox cursor, or materialized views — Solves read scaling and decoupling for large systems. Here the full fold is a few thousand rows; the machinery (Kafka Connect, replication slots, refresh scheduling, cursor-skip bugs) is pure added tracking for one developer.
- Hash chain or Merkle tree as a core requirement — The adversary model is absent. Insert-only enforcement and a content hash address accidental overwrite. The chain's tail-truncation blind spot would need an external anchor anyway.
- git notes or events-as-git-objects (git-bug style) as the system of record — Commit-keyed notes detach on squash and rebase, default to manual merge conflicts, and cannot serve fuzzy retrieval. Events stored as git objects defeat the 'real engine behind an abstraction' rule. Neither is needed once one service serialises writes.
- Adopt a lineage catalog (Marquez, DataHub, Amundsen) or PROV-O RDF tooling — Warehouse-scale pipeline lineage with multi-service deployments; Amundsen is archived. Only their modelling ideas transfer.

- F01 [LOAD-BEARING] (verified, primary_docs; provenance/data_model/invalidation) PROV-DM defines Invalidation as 'the start of the destruction, cessation, or expiry of an existing entity by an activity' (wasInvalidatedBy). Revision is not a separate core relation: it is a subtype of wasDerivedFrom marked with prov:type Revision. Core relations are wasGeneratedBy, used, wasInformedBy, wasDerivedFrom, wasAttributedTo, wasAssociatedWith, actedOnBehalfOf. W3C Recommendation, 30 April 2013.
    https://www.w3.org/TR/prov-dm/
- F02 (verified, primary_docs; provenance/data_model) PROV-O (OWL2 encoding, W3C Rec 30 April 2013) lists wasRevisionOf, wasInvalidatedBy, invalidatedAtTime and generatedAtTime as Expanded terms, not Starting Point terms. It defines a qualification pattern: an influence can be reified as an intermediate node (qualifiedInvalidation, qualifiedRevision, qualifiedDerivation) that cites the influencer and carries extra properties such as atTime. Defs: wasRevisionOf = 'a derivation that revises an entity into a revised version'; invalidatedAtTime = 'time at which an entity was invalidated (i.e., no longer usable)'. The qualified-node pattern is the PROV analogue of an outcome event carrying its own evidence.
    https://www.w3.org/TR/prov-o/
- F03 [LOAD-BEARING] (verified, primary_docs; data_model/provenance) OpenLineage (spec 1.55.0 docs) attaches facets to three entities: Run, Job and Dataset. A facet is an atomic piece of metadata identified by name. Emitting a facet with the same name for the same entity replaces the previous instance entirely. Custom facets use a project-named prefix, class name {prefix}{name}{entity}Facet, key {prefix}_{name}. _schemaURL should be immutable (e.g. contain a git SHA, not a branch). Custom facets can later be promoted to the standard spec.
    https://openlineage.io/docs/spec/facets/
- F04 (verified, primary_docs; data_model/provenance) OpenLineage JSON schema 2-0-2: BaseFacet has _producer (uri) and _schemaURL (uri), both required, additionalProperties true. RunEvent requires eventTime, producer, schemaURL, run, job; eventType enum START, RUNNING, COMPLETE, ABORT, FAIL, OTHER.     https://openlineage.io/spec/2-0-2/OpenLineage.json
- F05 (verified, primary_docs; data_model/provenance) OpenLineage run cycle: events for one run are accumulative by default and consumers must combine them to get the full picture. COMPLETE, ABORT and FAIL are terminal: no further events for that run follow. OTHER may be sent before a terminal state and even before START.     https://openlineage.io/docs/spec/run-cycle/
- F06 (verified, blog; data_model/engine) Fowler (Event Sourcing, 12 Dec 2005, an unrevised draft): capture all changes as a sequence of events; state can be discarded and rebuilt by replay; snapshots are an optimization; replay supports temporal queries and retroactive correction. Drawbacks he lists: replaying code changes (bug fixes, new business rules) can get 'very messy' and need bitemporal logic; external side effects must be suppressed during replay; hard to retrofit later.
    https://martinfowler.com/eaaDev/EventSourcing.html
- F07 [LOAD-BEARING] (verified, primary_docs; data_model/concurrency/engine/ops_cost) Microsoft Azure Architecture Center, Event Sourcing pattern (page metadata ms.date 2026-03-27, updated 2026-09-25): events are immutable and stored append-only; current state is derived by replay or kept in materialized views (read-only projections); snapshots are 'an optimization, not a replacement' and can be regenerated; the only way to undo is a compensating event; optimistic concurrency rejects an append if the stream changed since it was read; consumers must be idempotent (track last processed sequence per consumer). The page warns it is a complex pattern and 'for most systems and most parts of a system, traditional data management is sufficient', and that it is unsuited to prototypes, short-lived systems or reference data. It advises applying it selectively, e.g. to a ledger, and not everywhere.
    https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
- F08 (verified, primary_docs; data_model/provenance) Same Microsoft page: design events to capture business intent, not just resulting state ('two seats were reserved' beats 'remaining seats changed to 42'); state-only events reduce the store to a change log with no meaning. Version events (tolerant deserialization, version id in envelope, upcasting); in-place migration of historical events is a last resort because it breaks the audit trail. Bugs that wrote wrong events leave those events in the store, so projections must tolerate or compensate for them.
    https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing
- F09 [LOAD-BEARING] (verified, blog; data_model/invalidation/provenance) Fowler, Bitemporal History (7 April 2021): actual time (valid/effective) is when a fact was true in the world; record time (transaction) is when the system learned it. Retroactive changes mean actual history is NOT append-only but record history is: new knowledge is appended and prior records are never overwritten. A query takes both dates, e.g. salaryAt(actualDate, recordDate), and record time can default to 'now'. He notes corrections can have downstream consequences that bitemporal data alone does not resolve.
    https://martinfowler.com/articles/bitemporal-history.html
- F10 (verified, primary_docs; data_model/engine) XTDB docs ('Time in XTDB'): system time (transaction time) is maintained by the database, not user-editable, with _system_from/_system_to columns (null _system_to = current version). - F13 [LOAD-BEARING] (verified, primary_docs; invalidation/data_model/provenance) OSV schema 1.9.2 models 'affected' as ranges of type GIT over a repo: events introduced / fixed / last_affected / limit hold full commit hashes, and evaluation 'requires the repository's commit graph' (u < v means u is a possibly distant parent of v). Duplicate ids resolve by latest 'modified'; 'withdrawn' (a timestamp) retracts an entry with the reason in 'summary'; aliases and related link entries; database_specific cannot affect evaluation. This is direct prior art for 'valid for commits between A and B' evaluated on the commit DAG.
    https://ossf.github.io/osv-schema/
- F14 [LOAD-BEARING] (verified, paper; invalidation/provenance/data_model) Build Systems a la Carte (Mokhov, Mitchell, Peyton Jones, ICFP 2018, DOI 10.1145/3236774) separates scheduler from rebuilder; the Haskell 'build' package documents two trace types. A verifying trace (VT) stores per key its dependencies with their hashes and the result as a hash; verifyVT decides up-to-date by comparing current dependency hashes to the stored ones. A constructive trace (CT) stores the value itself so a matching trace can be reused without recomputing. Recording dependency content hashes at compute time and re-hashing at lookup is exactly the event-driven invalidation (not time-based) a knowledge entry needs. Definitions read from Hackage build-1.0 Build.Trace docs; the paper PDF was not machine-readable via the fetch tool.
    https://hackage.haskell.org/package/build-1.0/docs/Build-Trace.html ; https://www.microsoft.com/en-us/research/publication/build-systems-a-la-carte/

## Open questions
- Footprint capture: who decides which files, symbols, packages and platform facts an entry depends on? A cheap agent writing 'files I touched' will miss config and dependency causes. Options: record paths from the diagnosing session's diffs and reads automatically, require a manual dependency list for build and deploy traps (eas.json, gradle, Railway settings, lockfiles), or both. Not settled by any source read.
- Symbol-level footprint: is a normalised function-body hash worth building (language-specific parsing for Python and TypeScript), or is whole-blob OID plus path granularity good enough? Whole-file granularity will mark many entries suspect after unrelated edits (cost: more gate runs, not false positives). No measurement exists for this repo.
- Where does the authoritative store live if agents run on the Windows dev box and later on a VPS or home box? SQLite WAL is same-host only; a single service or Postgres removes that limit but adds an always-on component. Decide jointly with the engine lanes.
- How should refutation by a gate be scoped: against the footprint it was observed on (a refute that clears when the code changes) or permanently until revised? The precision-biased default is permanent until revised; whether that over-suppresses is unmeasured.
- Conflict between XTDB sources: its GitHub releases page shows v2.2.0 as Latest and not pre-release, but a search summary said 2.x is still beta. The release years were not shown (day and month only). Only matters if XTDB is reconsidered.
- Whether recorded cost-saved estimates are comparable across model tiers over time (prices and context sizes change); store raw tokens and tier, not dollars, and derive cost later.
- Entries recorded before a code area was rewritten under a rename: git diff -M and --follow detect renames heuristically (default 50% similarity); how should a footprint follow a renamed or split file? Probably record blob OIDs and fall back to path rename detection, untested.
- Not read: the full ICFP 2018 paper (PDF not machine-readable through the fetch tool), the Snodgrass book, Marquez's data-model doc, DataHub's entity/URN/timeseries pages, and the SQL:2011 standard itself.
