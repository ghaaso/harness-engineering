# lane:E-03

lane=E-03 tool_status=ok facts=24 candidates=13

## Summary
Postgres can do every retrieval job this store needs with core and contrib features only: tsvector/websearch_to_tsquery with ts_rank_cd for token queries, pg_trgm (word_similarity, GIN) for fuzzy error-text and identifier matching, relational tables plus JSONB for provenance and outcome history, and MVCC for concurrent worktree agents. Those features, and the PG16 image, are already in the team's operational family (docker-compose.yml:9 and ci.yml:88 use postgres:16-alpine with a named volume). The question is not capability but cost: a second always-on stateful service, on a Docker Desktop that is not set to auto-start on this box (AutoStart false), for tens to hundreds of rows. Every benefit is real but is bought at a scale (millions of rows, many concurrent clients) that this workload never reaches. pgvector (PostgreSQL licence) works but needs an embedding model that must also run locally, and exact search is fine at this size, so it is optional. ParadeDB pg_search is AGPL-3.0, a covering index, and aimed at TB scale; pg_textsearch (PostgreSQL licence, PG17/18, preload restart) is cleaner but lacks phrase and fuzzy support; AGE and logical replication/CDC are overkill; LISTEN/NOTIFY is lossy for disconnected listeners so invalidation should be a re-computable query, not a push. Agent access: psql is the safest; the archived reference MCP server had a documented read-only bypass; Postgres MCP Pro (MIT, restricted mode) and pgEdge (PostgreSQL licence) are credible, and neither README mentions telemetry. Verdict: a strong fallback if concurrent multi-process writers or server-side SQL power are required, but not the default for a one-developer, tens-of-rows store; an embedded engine wins on ops cost. PGlite is single-connection so it does not solve the multi-worktree concurrency case.

## Design implications
- (strong) If Postgres is chosen, the retrieval stack should be tsvector (simple or english config) plus pg_trgm on canonicalised error templates, with vector search and BM25 extensions left out; both required pieces are in stock contrib, so a standard postgres image suffices and no custom image is needed. [F01, F02, F03, F18]
- (strong) ts_rank scores are not normalised and not comparable across queries, so precision tuning must use per-query thresholds or rank-cutoff relative to the top hit, and a hard gate that returns nothing below a floor. Only the verification step, not the score, may authorise reuse. [F01, F03]
- (strong) Do not rely on LISTEN/NOTIFY for invalidation. Agents are short-lived processes and a disconnected listener misses events; store dependency fingerprints per entry and re-verify at retrieval or by a CLI sweep (event-driven by code change, not time). [F12, F24]
- (moderate) The justification 'already in the production DB family' is weak for a store of hundreds of rows: familiarity with SQL and migrations is the benefit (and can be had from an embedded Postgres-flavoured or SQL engine), while the cost of a second always-on service falls on one developer whose Docker Desktop does not auto-start. The only argument that survives scrutiny is multi-process write concurrency across worktrees. [F21, F22, F23, F20]
- (strong) Any MCP/CLI access path must enforce read-only at the database role level (SELECT-only role, or no write tools exposed), not only via an MCP read-only wrapper; the archived reference server's bypass shows wrapper-only safety fails. Writes should go through a narrow CLI command that takes structured fields. [F14, F15, F16]
- (moderate) Semantic vector search should not be introduced to increase recall unless misses are measured, because it needs a local embedding model to respect the egress rule and adds fuzzy matches to a design whose dangerous failure is a false positive. [F05, F07]
- (moderate) Analytics (hit/refute/miss rates, cost saved) do not need CDC or a second instance; an append-only outcome table in the same database queried with GROUP BY is enough at this scale. [F13]
- (moderate) On Windows with Docker Desktop, the data directory must live in a named volume, not a bind mount from the Windows drive; the repo's compose file already does this. For Postgres 18 images the volume mount path changed, so the image tag and mount path must be pinned together. [F17, F18, F22]
- (weak) If the store is rebuildable from a text source of truth (entries as reviewed files in git, database as a derived index), the Postgres instance becomes disposable, which removes the backup and major-upgrade burden and makes a separate instance low-risk. This is a design choice outside this lane that interacts strongly with the engine decision. [F19]

## Rejected paths
- ParadeDB pg_search as the search engine — AGPL-3.0, TB-scale design, covering index with REINDEX on column changes, replication behaviour unverified, and BM25 adds nothing measurable at hundreds of rows.
- Apache AGE for the symptom/cause/file graph — Custom image and per-connection setup for a graph that is a few join tables at this size.
- Logical replication to an analytics copy — Operational weight for queries that are simple GROUP BYs over a tiny table.
- The archived reference Postgres MCP server — Archived, unpatched read-only bypass.
- Supabase MCP server for the knowledge store — Designed for Supabase projects; the knowledge store must be separate from production and not on Supabase.
- Bind-mounting the Postgres data directory from the Windows drive — Docker's own guidance prefers named volumes or WSL for databases.
- LISTEN/NOTIFY as the invalidation channel — Not durable for disconnected listeners; agents are not long-lived.

## Facts
- F01 [LOAD-BEARING] (verified, primary_docs; retrieval/limits) ts_rank ranks by lexeme frequency; ts_rank_cd is cover-density ranking (Clarke, Cormack, Tudhope 1999) that also considers proximity and needs positional info (ignores stripped lexemes). Both take optional weights {D,C,B,A} default {0.1,0.2,0.4,1.0} and a normalization bitmask (length, unique words, 32 = rank/(rank+1)). They use no global statistics, so scores cannot be normalised to a true 0-1 scale and are not comparable across queries; ranking must read each matching tsvector (docs call it potentially expensive, irrelevant at this scale).
    https://www.postgresql.org/docs/current/textsearch-controls.html (PostgreSQL 18.6 docs)
- F02 (verified, primary_docs; retrieval/access) websearch_to_tsquery turns raw user-style text into a tsquery (unquoted terms ANDed, "quoted" becomes phrase <->, 'or' becomes |, '-' becomes !) and never raises a syntax error, so arbitrary agent-supplied symptom text can be passed safely. It does not understand tsquery operators or weight labels in the input.
    https://www.postgresql.org/docs/current/textsearch-controls.html (PostgreSQL 18.6)
- F03 [LOAD-BEARING] (verified, primary_docs; retrieval/canonicalisation) pg_trgm provides similarity(), word_similarity(), strict_word_similarity() with operators %, <%, <<% and GUC thresholds (defaults 0.3, 0.6, 0.5), plus GIN (gin_trgm_ops) and GiST (gist_trgm_ops, nearest-neighbour via <-> only on GiST) indexes. GIN/GiST also accelerate LIKE/ILIKE and regex (~, ~*). Non-alphanumerics are ignored when forming trigrams. It is a 'trusted' extension (installable by a non-superuser with CREATE on the database). The doc page does not say how non-ASCII letters are handled.
    https://www.postgresql.org/docs/current/pgtrgm.html (PostgreSQL 18.6)
- F04 (verified, primary_docs; retrieval) pg_trgm docs describe a typo-correction pattern: build a word list from ts_stat() over a 'simple'-config tsvector and index it with gin_trgm_ops; the list is static and must be regenerated periodically. This is the documented way to combine FTS with fuzzy token correction.
    https://www.postgresql.org/docs/current/pgtrgm.html
- F05 [LOAD-BEARING] (verified, source_repo; retrieval/limits) pgvector (v0.8.7 per README): HNSW (better speed-recall, slower build, more memory) and IVFFlat; indexed vector limit 2,000 dims (halfvec 4,000); needs Postgres 13+. Approximate-index filtering is applied after the index scan (with default hnsw.ef_search=40, a 10%-selective filter returns about 4 rows) so filters can starve results; iterative index scans (since 0.8.0) mitigate this. README says exact search needs no index, gives perfect recall, and is reasonable for small tables or small filtered sets. README documents hybrid search by combining FTS with vectors and merging via Reciprocal Rank Fusion. At tens-to-hundreds of rows, no vector index is needed at all.
    https://github.com/pgvector/pgvector (README, v0.8.7)
