# lane:X-06

lane=X-06 tool_status=ok facts=25 candidates=11

## Summary
Local-only scrubbing is feasible without Python or any service. Recommended stack: a Node scrub module inside the canonicaliser, layered as (1) exact-value redaction of the live secrets in process env/.env, (2) secretlint used as a library (MIT, Node, DB-connection-string and basic-auth rules, Windows exe exists), (3) a few custom regexes for gaps (postgresql+asyncpg:// URLs, Authorization/Bearer, Railway/Supabase/R2 tokens, JWT), (4) libphonenumber-js findPhoneNumbersInText(text,'PK') plus PK mobile/CNIC regexes, (5) a fail-closed second pass with the gitleaks binary (MIT, windows_x64.zip, stdin mode) that rejects the write if anything still matches. Rejected: trufflehog (AGPL-3.0, live verification and update check on by default, 6% precision in the one benchmark that includes it) and detect-secrets (Python, last release May 2024, verification on by default). Presidio is cited for design only: Python plus a spaCy model download, no Pakistan entities, default phone regions exclude PK, no Urdu NER pipeline. Names and addresses cannot be detected reliably by any local tool here, so they need a structural rule: never store raw production-data output, store templates with typed placeholders. Egress: the model provider is unavoidable. Claude Code sends all prompts and tool output to Anthropic. Retention is 30 days to 5 years by account type, ZDR is Enterprise-only, and Fable-class models need 30-day retention. Local transcripts also keep tool results in plaintext. The owner should rule that the egress rule means no live credentials and no customer PII in store content, enforced at both write and return time.

## Design implications
- (strong) Treat the model provider as inside the trust boundary that matters but outside the owner's control, and write the egress rule in two parts: (a) no store content, service or backup is sent to any third party other than the model provider the agents already use; (b) nothing that enters model context, whether via the store or not, may contain live credentials or customer PII. Part (b) is enforceable by a scrub-before-return guard; a literal 'no data to the model provider' rule is unachievable with Claude Code, since all prompts and tool output go to the API. [X06-F01, X06-F02, X06-F04, X06-F05]
- (strong) The owner's account type is the pivotal unknown for retention and training: consumer accounts can be 5 years retained and trained on if the setting is on, commercial accounts 30 days (or none per the API page), ZDR needs a negotiated Enterprise arrangement, and Fable-class Covered Models need 30-day retention even under ZDR. The design should not assume ZDR and should list account type as an owner decision with 'consumer with training off, 30 days' as the conservative default assumption. [X06-F01, X06-F02, X06-F04, X06-F07]
- (strong) Scrubbing must happen at write time, not only at backup time, and again on every return, because backups, FTS indexes, local transcripts (plaintext, 30 days default) and the provider all receive whatever the store holds or returns. Backups then inherit scrubbed content and need no separate scrubber, but need a scheduled gitleaks dir audit. [X06-F05, X06-F10]
- (strong) Do not rely on a single off-the-shelf scanner: gitleaks lacks rules for DB URLs, Railway, Supabase and R2, secretlint may not match driver-qualified postgresql+asyncpg:// URLs, and the only independent benchmark shows precision from 6% to 46% and recall from 31% to 88% across tools. Layer exact-value redaction, secretlint, custom regexes and a gitleaks fail-closed second pass, and treat any second-pass finding as a rejected write. [X06-F10, X06-F11, X06-F16, X06-F17, X06-F25]
- (strong) Customer names and addresses are the unsolved class: no local, offline tool in scope detects them reliably (spaCy has no Urdu pipeline, Presidio has no PK entities). Control them structurally: forbid storing raw production-data query results or customer payloads, accept only structured fields from agents, and keep placeholders where templates are derived from such text. The fixture set should include a customer-row-in-error-message case that documents this as a known scanner miss. [X06-F14, X06-F15, X06-F24]
- (moderate) Use typed, deterministic placeholders and exempt SHAs, UUIDs, Alembic revisions and epoch-ms timestamps from redaction so scrubbing does not destroy the symptom handles the canonicaliser and retrieval depend on; measure over-redaction on a must-survive fixture group. [X06-F23, X06-F20]
- (moderate) Reject TruffleHog and avoid detect-secrets and Presidio as dependencies. If the engine is exposed as a CLI or MCP tool, the scrubber should ship in the same Node process as the canonicaliser, with gitleaks as the only external binary, pinned by version and checksum, run with network access denied in a firewall test. [X06-F12, X06-F13, X06-F14, X06-F09]
- (moderate) Record scrubber identity on each entry (tool names and versions, rule-set hash, scrub timestamp) in the provenance history so a later rule improvement can trigger a re-scrub of old entries as an invalidation event, and so a refuted 'leak' can be traced. [X06-F23, X06-F08, X06-F16]
- (weak) Client-side Claude Code settings (deny-reads on .env and credential files, shorter cleanupPeriodDays, CLAUDE_CODE_SKIP_PROMPT_HISTORY for sensitive sessions) are cheap complements that the owner can adopt without touching the store; they limit local plaintext exposure but not provider ingestion. [X06-F05, X06-F06]

## Rejected paths
- Run TruffleHog (even with --no-verification) as the primary scrubber — AGPL-3.0, verification and update-check on by default so one missing flag sends credentials to third parties, sentry-go and OpenTelemetry in go.mod with no documented off switch, 77 MB binary, 6% benchmark precision, no stable library API.
- Presidio as a REST sidecar or Python library for PII — No Pakistan entities, default phone regions exclude PK, English-trained NER and no Urdu spaCy pipeline, Python 3.11+ plus a large model download, no Node SDK, no published accuracy; a heavy second runtime for tens of entries and still blind to the PII class that matters (names, addresses).
- detect-secrets as the Node-reachable secret scanner — Python only, no release since 2024-05-06, verification network calls on by default, line-oriented with documented misses, absent from the independent benchmark.
- Rely on Anthropic ZDR so scrubbing is unnecessary — ZDR is Enterprise-only and per-org, excludes third-party tools and MCP servers, Covered Models (Fable/Mythos) need 30-day retention regardless, flagged data can be kept 2 years, and local transcripts are plaintext on disk anyway.
- Scrub only when producing backups or exports — The live DB file, FTS index, CLI output and local Claude Code transcripts would still hold raw secrets and PII; the leak happens at the first write or return, not at backup time.
- Whole-text high-entropy redaction as a catch-all — The benchmark names weak entropy filters as a top false-positive cause (commit IDs, dummy strings); here it would also erase SHAs, UUIDs and revision ids that serve as retrieval handles.

## Open questions
- Owner ruling needed: does the no-egress rule cover the model provider? Recommended wording: the store sends nothing anywhere except via the CLI/MCP responses the agents already receive, and those responses must contain no live credentials and no customer PII (enforced by the return-time guard). Alternative: treat provider ingestion as out of scope and scrub only at write; this leaves tool output unguarded.
- Which Anthropic account type and plan does the owner use for these sessions (consumer Pro/Max with the training toggle, Team/Enterprise, or API keys), and is the training/improvement setting on? This decides 30 days vs 5 years retention. The user email domain suggests a consumer account but the plan was not verified.
- The two Anthropic pages disagree on commercial API retention (Claude Code page: standard 30 days; API page: conversation content not retained by default except Covered Models). Ask Anthropic or the Privacy Center which governs Claude Code with API keys.
- Do Fable-class sessions (the orchestrator) have to be excluded from handling raw defect text? They require 30-day provider retention and cannot be ZDR.
- Does secretlint's database-connection-string rule match postgresql+asyncpg:// URLs, and what does lintSource return for ranges? Needs a run in an installable sandbox, which this research was not permitted to do.
- No runtime network capture of gitleaks or secretlint was possible; confirm 'no default network calls' with a deny-all-egress run before production.
- False-positive rates on build/deploy/log text are unmeasured; the only benchmark is source code from public repos. A small labelled sample of the owner's own logs (kept local) would give a real FP and FN rate for the layered pipeline.
- Are unhyphenated 13-digit CNICs and Pakistani landline numbers likely in defect text, or is the PII mostly the mobile numbers captured at intake? That decides whether the context-word CNIC rule is needed on day one.
- Does the owner want the raw copy kept at all (T-04 raw-copy-plus-recipe)? If the raw artefact lives outside the store with only a scrubbed template inside, the PII problem shrinks to near zero.
- Whether Pakistani data-protection law or the client's contract imposes obligations on logs containing customer data was not researched.
- Search budget was exhausted mid-run, so newer secret-detection benchmarks (2024-2026), LLM-based redaction studies, and any log-text-specific FP evidence were not searched; only WebFetch of known URLs was possible after that.
