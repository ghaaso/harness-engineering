## ex1-non-ascii-compare-digest-500
surfaced: Found by a prior audit and listed in docs/HANDOFF-2026-07-28-open-work.md:587 ('the two non-ASCII compare_digest' bugs); fixed in PR #168 (merged 2026-07-28). Not a production incident report: no runtime log of an exploit is recorded. [verified: commit message and handoff]
symptom as seen:
    TypeError: comparing strings with non-ASCII characters is not supported (message reproduced locally on Python 3.12.14 by calling hmac.compare_digest('abc', 'ébc'); the exact traceback in prod is not_recorded)
    HTTP 500 instead of 401/403 on GET /api/ops/* when header X-Ops-Proxy-Token contains a non-ASCII byte
    HTTP 500 on the PUBLIC WhatsApp webhook (GET verify-token query param and the X-Hub signature header) when the value contains a non-ASCII character
    Sibling symptom in ops-server.mjs: RangeError from crypto.timingSafeEqual (unauthenticated POST kills the Node process, exit code 1, connection reset, Railway restart loop)
root cause: [verified, commit 9b98c88 message] hmac.compare_digest raises TypeError when either str operand contains non-ASCII. Header values arrive as bytes and Starlette decodes them latin-1, so a single 'é' on the wire becomes a non-ASCII str and the auth comparison throws instead of returning False. Three call sites compared an attacker-controlled str against a configured secret: ops proxy-token gate (ops/deps.py), WhatsApp webhook verify token (customer_messaging/router.py), webhook signature header (customer_messaging/service.py verify_webhook_signature). Same family in the Node BFF: length guard compared String.length (UTF-16 units) against timingSafeEqual over UTF-8 bytes. Root-cause class (inferred): 'comparison primitive is partial over its input domain, applied to untrusted input'.
fix commits: 9b98c88 (squashed to 2fe77f5, PR #168)
fix: Added core.security.compare_secret(candidate, expected): returns False if expected is None/empty or candidate is None (fail closed), otherwise sha256-hashes both sides to 32-byte digests and calls hmac.compare_digest on bytes, so it is total over all inputs and leaks no length. All three Python call sites were routed through it. For ops-server.mjs the length guard was replaced with a sha256-digest compare, readBody was hardened to a plain-object contract (JSON.parse('null') returns null without throwing), the WHOLE handler was wrapped (new URL on a malformed Host header was a third route to the same crash), and process-level guards were added. CLAUDE.md now carries the rule 'compare shared secrets with compare_secret, never hmac.compare_digest on a str'.
ruled out:
    - A naive `typeof body.password` guard against the null body — typeof null === 'object', so the guard does not catch JSON.parse('null'); readBody had to be changed to a plain-object contract instead. [git show 9b98c88 (commit message)]
    - Keeping a String.length-based length check before timingSafeEqual — String.length counts UTF-16 code units while timingSafeEqual compares UTF-8 bytes; 'é'.repeat(len) passes the guard and throws RangeError with no knowledge of the password. Replaced by digest compare (also removes the length oracle). [git show 9b98c88 (commit message)]
    - Handoff's prescription for the related metrics bug: build labels from scope['route'].path — That key does not exist: Starlette 0.49.3 Route.matches builds a child scope of exactly {endpoint, path_params} (verified by the fixer against the installed library). Labels now come from FastAPI APIRoute.path_format via an endpoint->template map. (Same commit, sibling defect; shows the store must hold 'prescribed fix was wrong' notes.) [git show 9b98c88 (commit message)]
    - Severity claim 'metrics route table grows without bound -> OOM' — Corrected in the commit: label set was bounded (FastAPI str convertor puts raw string in path_params); it is metrics correctness, not availability. [git show 9b98c88 (commit message)]
    - Unit test over an exported ops-server function as the proof — A unit test cannot see a process kill; the new tests spawn the real server and assert the process is still alive after each hostile request. Old route-label tests built a synthetic scope, which is why they could not see the label bug. [git show 9b98c88 (commit message); tests/ops-server.test.mjs]
