A dot is the median over 5 passes, the bar the spread from the fastest to the slowest pass, and the small ticks each pass. The time axis is logarithmic: each grid line is ten times the one before. The plain reading
On the selected method, SQLite was fastest: 14.5 ms per ranking on the tuning graph and 32.7 ms on the frozen graph, against 41.5 and 71.2 ms for LadybugDB (graph) and 70.3 and 98.7 ms for the DuckDB graph layer (one thread, warm). These differences hold in wall and CPU time in all 5 passes.
On the PageRank variants, the arm that runs PageRank in application code was fastest: frozen graph, 4-hop variant, 17.1 ms for LadybugDB (PageRank in JavaScript over a cached adjacency), 58.4 ms for the DuckDB graph layer and 256 ms for SQLite (about 270 SQL statements per ranking). This compares PageRank implementations, not graph operators.
Every time here is milliseconds; one model step takes seconds. A model step takes about 6.6 s at the median, so engine speed does not enter the token bill. Answers were the same in every engine (section E).

How it was run, in the audit's words
The engine timing ran after the held-out run was scored, on tuning inputs only: 200 tuning seeds on one June commit graph (2,450 nodes, 7,077 edges), 200 file nodes of the frozen commit graph (5,464 nodes, 16,462 edges) and the 20 tuning questions. No held-out task or question was timed.
The three engines took turns in short blocks inside one container on six pinned CPUs, one engine at a time (no two blocks overlapped in time), over five passes from 08:05 to 11:21 UTC on 2026-11-13; every engine was first in about a third of the rounds.
The PC was busy throughout: other work used a median of about 6 of its 24 logical CPUs during the blocks. 148 of the 2,148 block attempts in the passes were repeated because other work exceeded 12 CPUs, and 6 blocks were kept and flagged after three repeats; dropping them changes nothing.
All three engines returned the same ranked answer for every seed, in every pass, at every thread setting, warm and cold, and the same answers to the 20 questions.
An independent recomputation from the raw block files reproduced every number in the engine table and all 180 engine-to-engine verdicts.
For the selected configuration (the frozen primary), SQLite answered fastest: median 14.5 ms per ranking on the tuning graph and 32.7 ms on the frozen graph, against 41.5 and 71.2 ms for LadybugDB and 70.3 and 98.7 ms for DuckDB with the DuckDB graph layer (one thread, warm). These differences hold in wall and CPU time in all five passes.
Between LadybugDB and DuckDB-with-the DuckDB graph layer no difference is stated for the frozen primary warm median (71.2 against 98.7 ms): LadybugDB was lower in all five passes, but the 27.5 ms gap is smaller than the 36 ms spread between DuckDB's passes, so under the declared rule it stays inside the noise.
For the PageRank configurations (the 4-hop choice and the 2-hop base), the arm that runs PageRank in JavaScript over a cached adjacency (LadybugDB) was fastest, and the arm that runs it as about 270 SQL statements per ranking (SQLite) was slowest: frozen graph the 4-hop choice 17 ms, 58 ms and 256 ms (LadybugDB, DuckDB, SQLite). With the application caches dropped, LadybugDB is 51 ms and still lowest. This compares PageRank implementations, not graph operators.
For the 20 question lookups SQLite took about 0.3 ms per question, LadybugDB about 1.9 ms and DuckDB about 9 ms (warm median, frozen graph).
Building a store took about 0.35 to 0.9 s for SQLite, 0.6 to 0.7 s for DuckDB and 3.1 to 3.7 s for LadybugDB (median over five builds), and a one-file update 0.18 to 0.27 s for SQLite and DuckDB (no difference between them beyond the noise) against 0.52 to 0.63 s for LadybugDB; the stores hold different extra tables, so this compares the three designs, not the engines alone.
Every per-query time is a few milliseconds to a few hundred milliseconds on graphs of a few thousand nodes; the test does not show whether these differences matter for an agent working in a session.

What these timings do not show: that a graph engine is faster or slower than SQL in general (the order depends on the method and on where its ranking runs); that LadybugDB's engine computes PageRank (it runs in JavaScript); that one engine should be adopted on this evidence; anything about held-out tasks, larger graphs, other repositories or other machines; or whether an agent finishes work faster.

survives: LadybugDB's personalised PageRank runs in application code over a cached adjacency (40 iterations in JavaScript over a transition CSR fetched by one Cypher query and cached per configuration).

survives: SQLite's walk is a recursive common table expression (bounded hops; unbounded hops use a level-wise loop of SQL statements driven by application code).

survives: Where the frozen primary's ranking (degree-normalised spreading, addendum 2 item 20) runs: LadybugDB fetches arcs and out-degrees by Cypher and spreads the activation in application code (JavaScript), so for LadybugDB this ranking is not in the engine; SQLite and the DuckDB graph layer spread it in SQL, one statement per BFS level, the level loop driven by application code; SQLite's unbounded walk is likewise a level loop in application code.
