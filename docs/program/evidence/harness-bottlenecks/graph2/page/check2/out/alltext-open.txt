Does a graph database belong in the agent harness? What the held-out test found

When an agent changes one file, can a tool put the other files and definitions it will need in front of it? Seven tools answered the same 418 change-completion tasks from 75 real commits of July and August 2026 that no setting was tuned on, each with an 8,000-token answer. Tags on every number say whether it is held-out (the one fair run) or tuning (where settings were chosen, so optimistic); engine times carry timing run (tuning inputs only), and other people's figures or your session records outside source.

What this page answers, and what it does not

It answers two questions. Do three storage engines differ: SQLite (relational), LadybugDB (graph) and the DuckDB graph layer, holding the same facts? Does a parser-built code graph beat a scripted search at finding the other code that a real change touched? It does not test a layer of meaning that a model reads from documents (what graphify adds), facts with time validity, cached conclusions with invalidation, orientation (summaries and maps), an agent actually using any of these tools, or the tokens a working session spends.

Your five questions, answered in one line each
Does the way a graph stores things change the answer?
No. Given the same facts and the same method, SQLite, LadybugDB and DuckDB returned the same answers (770 of 770 tasks). The facts in the store and the method decide the answer. E
Are the answers scored for the value they carry?
Partly. A changed file or definition counts only when the tool actually showed it inside the 8,000-token answer, and a definition only when its own lines were shown. Every item counts the same; how much an agent gains from it was not measured. B
Do the type of graph, the algorithms and the number of hops matter?
Hops and which facts are stored moved tuning recall by up to 0.346; ranking algorithms by at most 0.023; the one graph-only algorithm that reached the final gave no gain of 0.05 or more. F
Was the graph given a fair, optimised form against an established relational engine?
Each engine had 60 tuned configurations on the same 65 tuning commits, its own native algorithms were tried, and audits fixed graph-side defects before scoring. E
Would it be more token efficient?
Every tool filled the same 8,000-token answer, so the test compares how much each found per token, not tokens saved: the typed store found more, on mobile-app changes. Engine times are milliseconds and do not enter the token bill; an agent's tokens were not measured. C G H K

What it shows. The engine did not change the answer, and on the selected method SQLite (relational) answered fastest, in milliseconds that do not enter the token bill. A typed store of connections found more of a change than a scripted search at the same answer size, and the whole gain sits in mobile-app changes. No agent was run; what you asked that this did not cover is in K.

BWhat was compared, and how was each answer scored?

How to read it. The cards are the seven tools: what each reads and how it answers. The three typed stores in the dashed box hold the same facts and run the same method. Below them, one task as a picture. At the bottom, step through three real tasks with Back and Next.

Typed stores: the same facts (files, functions, routes, tables, settings, tests and how they connect, including which files changed together before) in three engines

SQLite (relational)
typed store
Reads
Only the facts built from the parent commit of each task (never the task commit or anything later).
Answers
A recursive SQL query walks from the seed file and symbol over the typed edges, scores every reached file, and the shared packer prints the best files first as a path line plus the signature lines of their definitions until the token budget is used.
What it is

The extracted facts (typed nodes such as files, functions, routes, tables and settings, and typed edges such as imports, calls, HTTP route to client call, test to code, table reads and writes, and co-change history) loaded into SQLite tables with indexes in both directions.

LadybugDB (graph)
typed store (graph engine)
Reads
The same fact files as the relational store.
Answers
Native graph queries for the walk; the same ranking and packer. Its best native form (its best form) adds a stored Louvain community (a standard clustering) grouping to personalised PageRank; the PageRank iterations themselves run in application code.
What it is

The same facts loaded into LadybugDB, an embedded property-graph database with typed variable-length paths and a graph-algorithm extension (PageRank, Louvain communities, k-core).

DuckDB graph layer
typed store (graph engine)
Reads
The same fact files as the relational store.
Answers
Property-graph and recursive SQL queries for the walk; the same ranking and packer. Its k-hop walk is recursive SQL, not a graph operator.
What it is

The same facts in DuckDB with the DuckPGQ extension, which adds property-graph queries (bounded variable-length paths, PageRank) to SQL.

Reference implementation (check only)
cross-check only · not scored
Reads
The same fact files.
Answers
Computes the same walk and ranking directly. Used only to check that the three stores return the same answers; never scored.
What it is

A plain JavaScript implementation of the shared specification, holding the graph in memory.

Scripted search
baseline
Reads
The source tree exported at the parent commit, plus (for its padding tail) the earlier commit history.
Answers
Ranks files by weighted hit counts, then appends a co-change padding tail (files that changed together with the seed file in earlier commits); same packer and budget as every arm.
What it is

A fixed script modelled on the searches sessions run: text search of the source tree for the seed's names, its module path and its route strings, then follows the seed's import lines. It is a fixed script, not an agent searching with judgement.

Changed-together floor
floor
Reads
Earlier commit history (ancestor commits only, same-PR siblings dropped) and file paths.
Answers
Prints those files in that order with their signature lines until the budget is used. Every method must beat it.
What it is

No search and no graph: the files that changed together with the seed file in earlier commits, most often and most recently first, then the same-directory order.

Same-folder floor
floor
Reads
File paths at the parent commit.
Answers
Prints those files in that order with their signature lines until the budget is used. Every method must beat it.
What it is

No search and no graph: the files in the seed's own directory, then its capability folder, then outward.

One task, as a picture
1. Seed
One file and one symbol that a real commit changed. The tool sees the code as it was just before that commit.
→
2. The tool's answer
A ranked list of files, each printed as its path and the signature lines of its definitions, packed until 8,000 tokens are used. Every tool gets the same packer and the same budget.
→
3. Compared with the commit
The other files and definitions the same commit changed (the reference) are counted: recall = found ÷ all of them.

Recall is the share of the files and definitions the real change touched that the tool put in front of the reader. As scored, it is the share of reference files and definitions (those the same commit changed) that appear inside an 8,000-token answer, averaged over a commit's tasks and then over commits. A definition counts only when its own lines are shown. Every item counts the same: recall does not weigh how important an item was, and it does not count context a change needed but did not edit.

From the 388 tuning change-completion tasks whose reference has 3 to 8 units (files plus definitions), so that an example fits on the page: (1) typed clearly beats search = typed recall minus search recall at 8,000 tokens of at least 0.30; (2) tie = typed, search and the co-change floor all have the same recall, strictly between 0 and 1; (3) search or the co-change floor beats typed = the better of the two minus typed of at least 0.30. In each group the tasks are sorted by that difference (for the tie, by reference size), then by task id, and the median task is taken (the lower one when the count is even). Never held-out.

Why 5 SQLite and 3 DuckDB ranked lists differ beyond what is shown

The 8 (arm, task) pairs are 2 distinct queries: one seed at one parent commit appears in change completion, the cross-runtime subset and tests to update, and another in change completion and tests to update. In every pair the shown items (80 or 86 items, scores included), the budgets, the seeds and the 50-path sample beyond the budget are identical, and every score field is identical. The hash covers about 3,900 ranked nodes with their raw scores; the reference arm rounds scores to 12 decimals, so a last-digit difference in a deep-tail score or the order of two nodes with equal rounded scores, somewhere past position 130, changes it. The stored answers hold only the hash of that tail, so which of the two it was cannot be told from them. No reported measure reads beyond the items packed into the 16,000-token answer: the scorer reads only items, budgets and seeds.

How it was run, in the audit's words
The engine timing ran after the held-out run was scored, on tuning inputs only: 200 tuning seeds on one June commit graph (2,450 nodes, 7,077 edges), 200 file nodes of the frozen commit graph (5,464 nodes, 16,462 edges) and the 20 tuning questions. No held-out task or question was timed.
The three engines took turns in short blocks inside one container on six pinned CPUs, one engine at a time (no two blocks overlapped in time), over five passes from 08:05 to 11:21 UTC on 2026-11-13; every engine was first in about a third of the rounds.
The PC was busy throughout: other work used a median of about 6 of its 24 logical CPUs during the blocks. 148 of the 2,148 block attempts in the passes were repeated because other work exceeded 12 CPUs, and 6 blocks were kept and flagged after three repeats; dropping them changes nothing.
All three engines returned the same ranked answer for every seed, in every pass, at every thread setting, warm and cold, and the same answers to the 20 questions.
An independent recomputation from the raw block files reproduced every number in the engine table and all 180 engine-to-engine verdicts.
For the selected configuration (the frozen primary), SQLite answered fastest: median 14.5 ms per ranking on the tuning graph and 32.7 ms on the frozen graph, against 41.5 and 71.2 ms for LadybugDB and 70.3 and 98.7 ms for DuckDB with the DuckDB graph layer (one thread, warm). These differences hold in wall and CPU time in all five passes.
Between LadybugDB and DuckDB-with-the DuckDB graph layer no difference is stated for the frozen primary warm median (71.2 against 98.7 ms): LadybugDB was lower in all five passes, but the 27.5 ms gap is smaller than the 36 ms spread between DuckDB's passes, so under the declared rule it stays inside the noise.
For the PageRank configurations (the 4-hop choice and the 2-hop base), the arm that runs PageRank in JavaScript over a cached adjacency (LadybugDB) was fastest, and the arm that runs it as about 270 SQL statements per ranking (SQLite) was slowest: frozen graph the 4-hop choice 17 ms, 58 ms and 256 ms (LadybugDB, DuckDB, SQLite). With the application caches dropped, LadybugDB is 51 ms and still lowest. This compares PageRank implementations, not graph operators.
For the 20 question lookups SQLite took about 0.3 ms per question, LadybugDB about 1.9 ms and DuckDB about 9 ms (warm median, frozen graph).
Building a store took about 0.35 to 0.9 s for SQLite, 0.6 to 0.7 s for DuckDB and 3.1 to 3.7 s for LadybugDB (median over five builds), and a one-file update 0.18 to 0.27 s for SQLite and DuckDB (no difference between them beyond the noise) against 0.52 to 0.63 s for LadybugDB; the stores hold different extra tables, so this compares the three designs, not the engines alone.
Every per-query time is a few milliseconds to a few hundred milliseconds on graphs of a few thousand nodes; the test does not show whether these differences matter for an agent working in a session.

What these timings do not show: that a graph engine is faster or slower than SQL in general (the order depends on the method and on where its ranking runs); that LadybugDB's engine computes PageRank (it runs in JavaScript); that one engine should be adopted on this evidence; anything about held-out tasks, larger graphs, other repositories or other machines; or whether an agent finishes work faster.

survives: LadybugDB's personalised PageRank runs in application code over a cached adjacency (40 iterations in JavaScript over a transition CSR fetched by one Cypher query and cached per configuration).

survives: SQLite's walk is a recursive common table expression (bounded hops; unbounded hops use a level-wise loop of SQL statements driven by application code).

survives: Where the frozen primary's ranking (degree-normalised spreading, addendum 2 item 20) runs: LadybugDB fetches arcs and out-degrees by Cypher and spreads the activation in application code (JavaScript), so for LadybugDB this ranking is not in the engine; SQLite and the DuckDB graph layer spread it in SQL, one statement per BFS level, the level loop driven by application code; SQLite's unbounded walk is likewise a level loop in application code.
