Does a graph database belong in the agent harness? What the held-out test found

When an agent changes one file, can a tool put the other files and definitions it will need in front of it? Seven tools answered the same 418 change-completion tasks from 75 real commits of July and August 2026 that no setting was tuned on, each with an 8,000-token answer. What this page answers, and what it does not

It answers two questions. Do three storage engines differ: SQLite (relational), LadybugDB (graph) and the DuckDB graph layer, holding the same facts? Does a parser-built code graph beat a scripted search at finding the other code that a real change touched? It does not test a layer of meaning that a model reads from documents (what graphify adds), facts with time validity, orientation (summaries and maps), an agent actually using any of these tools, or the tokens a working session spends.

Added since: a replay of cached answers with invalidation (section L), for answers a program computes from the graph only. No model was called and no agent ran, so conclusions a model makes were not cached. And graphify itself, its code layer only, run scripted on the same tasks (section M), with no model and no agent.

Your five questions, answered in one line each

Does the way a graph stores things change the answer?
No. Given the same facts and the same method, SQLite, LadybugDB and DuckDB returned the same answers (770 of 770 tasks). The facts in the store and the method decide the answer. E
Are the answers scored for the value they carry?
Partly. A changed file or definition counts only when the tool actually showed it inside the 8,000-token answer, and a definition only when its own lines were shown. Every item counts the same; how much an agent gains from it was not measured. B
Do the type of graph, the algorithms and the number of hops matter?
Hops and which facts are stored moved tuning recall by up to 0.346; ranking algorithms by at most 0.023; the one graph-only algorithm that reached the final gave no gain of 0.05 or more. F
Was the graph given a fair, optimised form against an established relational engine?
Each engine had 60 tuned configurations on the same 65 tuning commits, its own native algorithms were tried, and audits fixed graph-side defects before scoring. E
Would it be more token efficient?
Every tool filled the same 8,000-token answer, so the test compares how much each found per token, not tokens saved: the typed store found more, on mobile-app changes. Engine times are milliseconds and do not enter the token bill; an agent's tokens were not measured. C G H K

What it shows. The engine did not change the answer, and on the selected method SQLite (relational) answered fastest, in milliseconds that do not enter the token bill. A typed store of connections found more of a change than a scripted search at the same answer size, and the whole gain sits in mobile-app changes. No agent was run; what you asked that this did not cover is in K.

How to read it. The cards are the seven tools: what each reads and how it answers. The three typed stores in the dashed box hold the same facts and run the same method. Below them, one task as a picture. At the bottom, step through three real tasks with Back and Next.

Typed stores: the same facts (files, functions, routes, tables, settings, tests and how they connect, including which files changed together before) in three engines

SQLite (relational)

typed store
ReadsOnly the facts built from the parent commit of each task (never the task commit or anything later).AnswersA recursive SQL query walks from the seed file and symbol over the typed edges, scores every reached file, and the shared packer prints the best files first as a path line plus the signature lines of their definitions until the token budget is used.
What it is

The extracted facts (typed nodes such as files, functions, routes, tables and settings, and typed edges such as imports, calls, HTTP route to client call, test to code, table reads and writes, and co-change history) loaded into SQLite tables with indexes in both directions.

LadybugDB (graph)

typed store (graph engine)
ReadsThe same fact files as the relational store.AnswersNative graph queries for the walk; the same ranking and packer. Its best native form (its best form) adds a stored Louvain community (a standard clustering) grouping to personalised PageRank; the PageRank iterations themselves run in application code.
What it is

The same facts loaded into LadybugDB, an embedded property-graph database with typed variable-length paths and a graph-algorithm extension (PageRank, Louvain communities, k-core).

DuckDB graph layer

typed store (graph engine)
ReadsThe same fact files as the relational store.AnswersProperty-graph and recursive SQL queries for the walk; the same ranking and packer. Its k-hop walk is recursive SQL, not a graph operator.
What it is

The same facts in DuckDB with the DuckPGQ extension, which adds property-graph queries (bounded variable-length paths, PageRank) to SQL.

Reference implementation (check only)

cross-check only · not scored
ReadsThe same fact files.AnswersComputes the same walk and ranking directly. Used only to check that the three stores return the same answers; never scored.
What it is

A plain JavaScript implementation of the shared specification, holding the graph in memory.

Scripted search

baseline
ReadsThe source tree exported at the parent commit, plus (for its padding tail) the earlier commit history.AnswersRanks files by weighted hit counts, then appends a co-change padding tail (files that changed together with the seed file in earlier commits); same packer and budget as every arm.
What it is

A fixed script modelled on the searches sessions run: text search of the source tree for the seed's names, its module path and its route strings, then follows the seed's import lines. It is a fixed script, not an agent searching with judgement.

Changed-together floor

floor
ReadsEarlier commit history (ancestor commits only, same-PR siblings dropped) and file paths.AnswersPrints those files in that order with their signature lines until the budget is used. Every method must beat it.
What it is

No search and no graph: the files that changed together with the seed file in earlier commits, most often and most recently first, then the same-directory order.

Same-folder floor

floor
ReadsFile paths at the parent commit.AnswersPrints those files in that order with their signature lines until the budget is used. Every method must beat it.
What it is

No search and no graph: the files in the seed's own directory, then its capability folder, then outward.

One task, as a picture

1. Seed

One file and one symbol that a real commit changed. The tool sees the code as it was just before that commit.
→

2. The tool's answer

A ranked list of files, each printed as its path and the signature lines of its definitions, packed until 8,000 tokens are used. Every tool gets the same packer and the same budget.
→

3. Compared with the commit

The other files and definitions the same commit changed (the reference) are counted: recall = found ÷ all of them.

Recall is the share of the files and definitions the real change touched that the tool put in front of the reader. As scored, it is the share of reference files and definitions (those the same commit changed) that appear inside an 8,000-token answer, averaged over a commit's tasks and then over commits. A definition counts only when its own lines are shown. Every item counts the same: recall does not weigh how important an item was, and it does not count context a change needed but did not edit.

Three worked examples (tuning tasks, never held-out)

Example

From the 388 tuning change-completion tasks whose reference has 3 to 8 units (files plus definitions), so that an example fits on the page: (1) typed clearly beats search = typed recall minus search recall at 8,000 tokens of at least 0.30; (2) tie = typed, search and the co-change floor all have the same recall, strictly between 0 and 1; (3) search or the co-change floor beats typed = the better of the two minus typed of at least 0.30. In each group the tasks are sorted by that difference (for the tie, by reference size), then by task id, and the median task is taken (the lower one when the count is even). Never held-out.

No model and no agent: every answer is computed by a program from the graph, and the true answer was recomputed every time to check what the rule served.

  4. 4 · CheckThe true answer is recomputed anyway. A served answer that differs is counted as wrong (stale).

What it shows

  • With the "nothing else" patterns recorded, the fact-level rule served 25,490 of 29,097 lookups from the cache (87.6 %), and none of the answers it served differed from the answer recomputed from the extractor's facts. On the 112 questions whose answer changes at least once it served 82.5 %. An audit recomputed the true answer at all 40,880 lookups with its own loader and its own reconstruction of what each rule served, using the finished test's original SQL programs and reference code, and found 0 disagreements. A mistake shared with those programs, about what a question means, would not show.
  • Comparing only the fields a program read, with early cutoff, raised the share served to 96.2 % (94.2 % on the changing questions), still with no stale answer.
  • File-level invalidation, and fact level without the patterns, served wrong answers: 6.5 % and 6.8 % of what they served over all questions, 13.2 % and 13.6 % on the changing questions. 133 of the 134 cases behind them were a new relation appearing in another file.
  • Rules based on age cannot tell a stale answer from a fresh one: a time-to-live of 20 commits served 94.4 % of lookups, and 12.0 % of what it served was wrong (23.0 % on the changing questions).
  • The change-completion ranking rests on a median of 323 files per answer. No rule that checks what the answer rests on served more than 24.5 % of its lookups; the age-based rules served most lookups, and 41.8 to 89.5 % of what they served was wrong.
  • The share served by both fact-level rules (which served no wrong answer in these lanes) falls as the gap between lookups grows (main-chain lanes, not re-checked by the audit).
  • 138 of the 250 questions (55.2 %) never changed their answer over this history, and 13,857 of the lookups (47.6 %) are of those questions. Every rule is right on them, so the rates over all questions are higher than on the questions that test invalidation.

What it does not show

  • Model-made conclusions were not cached, and they are the costly ones: only answers that a program computes from the graph in milliseconds were. And no agent decided to look anything up: the replay asked every live question at every saved version, and trusted the rule, not a reader.
  • That fact-level invalidation is safe in general. Zero stale answers is what a correct recorder must give when a program reads the graph only through it: it is expected by construction. It shows the recorder has no gaps for these nine programs on this history, not for conclusions a model draws from reads nobody records.
  • That the cached answers are right about the code. "Stale" means different from the answer recomputed from the same extractor's facts; an extraction error that persists is invisible.
  • Any token saving. No tokens were measured. The token picture is an estimate under one assumption, priced three ways, and against a typed query it is zero.
  • A share served that an agent would see: the replay set the schedule, and nearly half the lookups are of questions that never change.
  • A temporal knowledge graph, a graph database, facts read by a model, or traversal caching.
  • Other repositories, larger graphs or other change rates (about 155 commits on main over 9 weeks), or that a wide question cannot be cached in a bounded form, which was not tried.

What this shows

  • On the held-out change tasks, the typed store put more of the real change in front of the reader than graphify’s code layer queried through our adapter, at 2,000, 4,000 and 8,000 tokens, by the declared rule. Part of that gap is file size: graphify puts large, highly connected files first.
  • Against scripted search and both floors the verdict is inconclusive, and each verdict moves with five commits. On ranking measures that do not charge for file size, graphify ranks above the same-folder floor.
  • Graphify’s code layer builds no route, table, setting or changed-together relation, so files linked to the seed only that way are out of its reach by construction.
  • Given the raw question text with no agent and no vocabulary step, its printout contained far fewer of the reference items than the typed store’s or scripted search’s answers.
  • On these tasks its code layer showed no capability this test lacked; graphify’s published numbers measure other things.

What this does not show

  • Its model-read document layer was not run, nor its community labels and report. The one independent gain reported for graphify sits in that layer, with an agent.
  • No agent used it: whether an agent using graphify would do better or worse, call it at all, or read fewer files.
  • Anything about tokens in a session: every answer of every tool filled its budget, and no session ran.
  • Other repositories, other languages, orientation questions, or graphify versions other than 0.9.108.
  • That no graphify configuration or usage could do better: 13 shipped single-call options were scored on tuning, against 60 configurations per typed arm.
  • That graphify’s graph is right or wrong edge by edge: only rankings were scored.
  • Why graphify’s published numbers look good elsewhere, or whether they hold.
