# Lane: small answers, and how a model should use a graph (research notes, 2026-11-13)

Written for a reader with no context. This lane covers two bodies of work: (A) choosing which part of a graph to hand a language model when the answer must fit a token budget, and (B) the interface through which a model asks a graph questions. It ends with a concrete answer builder and a concrete tool design, each decision tied to its source.

## 0. How this was done, and what the labels mean

- Everything below was read on 2026-11-13 through a page-to-markdown fetch tool. That tool has a small model summarise the page, so what I hold is an extraction, not the raw text. Where an extraction contradicted itself I say so in the entry. PDFs did not parse through the tool; I used the arXiv HTML versions. Nothing was installed or downloaded, nothing from the project was sent to any outside service (searches used only public paper and tool names), and I wrote nothing to the repository or the build folder except this file.
- Strength labels. **Strong**: independent, controlled, replicated. **Medium**: controlled but by the method's own authors, or a single preprint, or independent but small. **Weak**: self-reported, single small study, vendor material, or a claim I only saw in a search snippet.
- "Read" means the arXiv HTML or page body was fetched and the numbers come from it (usually the first 100,000 characters; I say when the tail was unread). "Snippet" means I only saw a search-result summary of it.
- Terms used throughout. A **token** is the unit a model reads and bills; here the v1 harness counts tokens with a deterministic regex approximation (not a model tokenizer). **Recall** is the share of the truly relevant items that an answer contains. A **knapsack** problem is choosing items, each with a value and a cost, to maximise total value under a cost cap. A **submodular** value function is one where adding an item helps less the more you already have (diminishing returns); **monotone** means adding never hurts. **MMR** (maximal marginal relevance) is a rule that picks the next item by relevance minus similarity to what is already picked. A **Steiner tree** is the cheapest connected subgraph that contains a given set of terminal nodes; the **prize-collecting** variant (PCST) also pays a penalty for every node left out, so it chooses which nodes to include. An **ego-graph** is the neighbourhood of one node out to some number of hops.

## 1. What v1 does, and what the first two rounds left open in this lane

v1 (as I read it in `graph2/build/arms/common/packer.js` and the protocol): a ranker orders candidate nodes; `project()` turns them into output units at file or symbol granularity; `pack()` then takes units **in rank order** until the budget (2k, 4k, 8k or 16k tokens) is full, cuts the last unit at the budget, and appends a "[+N more not shown]" footer. A shared padding tail (same-directory or co-changed files) is added so that every arm's answer fills its budget; that was deliberate, to compare arms at equal answer size. There are four output forms (path; path plus signature; path plus line range; snippet).

So v1's selection rule is the same as Aider's repository map: rank, then prefix. It uses no per-item cost, no stopping rule, no redundancy control and no choice of detail level. That is the gap this lane addresses.

What round 1 (`research/lane-agent-graphs.txt`) said that this lane builds on: cap output in tokens; return paths, signatures and relation lines rather than source; prefer precision; expose a few tools beside grep and read; do not let the model write Cypher; keep hops at 1 or 2. What it did not do: it gave no theory for how to cut a ranked list to a budget, no evidence on how facts should be laid out, no tool-definition cost, and it ruled out LLM-written Cypher without any accuracy data (this lane adds CypherBench numbers, section 6.3). Round 2 (`widen/lane-agents.md`) added that the entry point and adoption matter more than structure; it too has no selection or format theory. Both left "does ranked 2-3 hop closure computed by the tool beat leaving chaining to the model" open; section 6.1 gathers the knowledge-graph question-answering literature that bears on it.

## 3. Selection: from a ranked candidate set to the smallest sufficient answer

### 3.1 The problem, stated precisely

The ranker gives each candidate item i a score; calibrated, it is a probability p_i that the item is relevant to the agent's task. Each item has a rendered cost c_i in tokens. The answer is a set S. Two things cost tokens: every item in S (read once, then re-read on every later call because it stays in context), and every relevant item that is not in S (the agent has to find it by search and read, expected cost F tokens). Notation F is the fallback cost. This is a budgeted selection problem with a value function, and the literature on it is knapsack and submodular optimisation.

### 3.2 Rank-prefix versus knapsack, and the guarantees on offer

- **Modular value (sum of probabilities).** If the value of an answer is the expected number of relevant items it contains, value is a plain sum and the problem is the 0/1 knapsack. Ordering by p_i / c_i (value density) is the classical fractional-knapsack rule and is within one item's value of optimal; an exact dynamic program over (items x budget) is trivial here (a few thousand candidates times 8,000 tokens is about 10^7 steps). I did not open a primary source for the textbook knapsack facts in this session; they are standard but unverified here.
- **Submodular value (coverage, diversity).** For a monotone submodular function under a cardinality limit, the greedy algorithm gets at least 1 - 1/e (about 0.63) of the optimum (Nemhauser, Wolsey and Fisher 1978; cited secondarily in AdaGReS 2512.25052 and RCD 2605.00336, which I read; the 1978 paper itself I did not open).
- **Submodular value under a cost budget (the token case).** Khuller, Moss and Naor (1999, Information Processing Letters 70(1)) gave a 1 - 1/e approximation for budgeted maximum coverage using greedy plus partial enumeration; Sviridenko (2004) extended it to general monotone submodular functions with enumeration of 3 elements. Source: search snippets and secondary papers only (strength for the guarantee itself: strong theory, but I did not read the primary text). The cheap version, "ratio greedy (best value per token) plus the best single item", has a proven factor of 0.405 per arXiv 2008.05391 (read abstract page), which also reports a gap in Khuller et al.'s older proof of 1 - 1/sqrt(e) (0.393) and improves on Wolsey's 0.357 and (1 - 1/e)/2 (0.316). Leskovec et al. (KDD 2007, CELF) run both unit-cost greedy and ratio greedy and keep the better, with the (1 - 1/e)/2 guarantee and a "lazy" evaluation speed-up (up to 700 times faster than plain greedy in their test); I saw this only through slides and snippets. Lin and Bilmes (NAACL 2010) used budgeted submodular selection for multi-document summarisation (abstract only: beat the best DUC 2004 system on ROUGE-1).
- **What the guarantees mean here.** They are worst-case bounds against an exact optimum. At this graph size (thousands of candidates) the exact optimum of the modular case is cheap to compute, so the approximation factors are mainly useful to explain why ratio greedy is a safe default for the non-modular case, not as a reason to choose an approximation. At 10 or 100 times the size (50,000 to 500,000 nodes), the 8,000-token budget still limits answers to a few hundred items, and lazy greedy stays fast; nothing here is a scale problem.

### 3.3 Stopping: the smallest sufficient answer, not a full budget

v1 fills every budget. The decision-theoretic stopping rule below is my derivation, not a published result; it is the modular case of the knapsack with a value on avoiding a search.

- Including item i costs c_i tokens for sure and saves F_i tokens with probability p_i (the search the agent would otherwise run). Include it only when p_i * F_i > c_i, that is, when density p_i / c_i exceeds a threshold lambda = 1 / F. The cap B is then a second, separate limit.
- Illustration with numbers from other notes, not new measurements: the first test found a typed query answered in about 31 tokens where scripted search read about 695 (cited in `widen/lane-agents.md`), so F is of the order 700 tokens; a symbol-signature item costs about 33 tokens (section 2.1); the held-out precision at 10 items was about 0.26 to 0.28 (`research/critic.txt` design notes). Then lambda is about 0.0014 per token and an item pays for itself while p_i is above about 33 / 695 = 4.7 %. That says filling to a long list is rational until relevance drops under roughly 5 %, so the stop will bind at large budgets, not small ones, and the number depends entirely on how F is measured and on calibration.
- Published relatives. **Adaptive-k** (arXiv 2506.08479, read): choose k at the largest drop in the sorted similarity scores, plus a fixed buffer of 5, searching only within the top 90 % of ranks; on 128k-token contexts it used about 99 % fewer input tokens than full context on factoid QA (GPT-4o) and matched or beat fixed top-k, where the fixed-k "oracle" is the best of five settings chosen after the fact (so optimistic). Limits stated by the authors: designed for natural-language text, weaker on structured formats, vulnerable to adversarial gaps. Strength: medium. **Sufficient context** (Joren et al., arXiv 2411.06037, read): a context is sufficient if some plausible answer can be inferred from it; an autorater reached 93 % accuracy on 115 labelled cases (Gemini 1.5 Pro, 1-shot); models given insufficient context still hallucinated 15 to 40 % of the time (Gemini 1.5 Pro 40.4 %), and even with sufficient context hallucinated 14.3 % (Gemini 1.5 Pro) to 25.4 % (Gemma 27B). The point for us: "sufficient" can be checked and matters, but it was developed for text question answering with proprietary 2024 models; no code or graph version exists. Strength: medium. **Precision-first scoring** in Cognition's SWE-grep (weighted F-beta with beta 0.5, because polluting context hurt more than omitting; vendor blog, weak) points the same way as the threshold rule.
- **G-Retriever** (2402.07630, read): its prize-collecting selection cut the graph handed to the model from 100,627 to 610 tokens on WebQSP (99 %) and from 1,396 to 235 on SceneGraphs (83 %). Strength: medium (authors' own numbers; baselines were other methods, not a no-retrieval-limit run). It shows how large the headroom is when the starting graph is huge; our graph is not.

### 3.4 Redundancy and diversity: MMR and the submodular packers

- **MMR** (Carbonell and Goldstein, SIGIR 1998, abstract page): combine query relevance with novelty to reduce redundancy. The authors' own abstract says the benefit was modest for retrieval and single-document summaries and clearest for multi-document summaries. Strength of the original: weak (a two-page poster).
- **Submodular packers for token budgets, 2026 (recent, not yet replicated by third parties).** "What Survives Into Context" (arXiv 2607.00725 v2, read in full HTML): a cost-per-token greedy over relevance, query-term coverage, saturated facility-location representativeness and source diversity. On HotpotQA, budget 160 tokens, 3B reader, three seeds: F1 0.451 for the packer, 0.429 for the authors' own earlier heuristic, 0.410 for MMR, 0.400 for plain top-k packing, 0.326 for LLMLingua-2 compression. The packer beat top-k by +0.051 (95 % interval +0.030 to +0.072) and the heuristic by +0.022 (+0.002 to +0.041). But against top-k it was null on MuSiQue (-0.003), 2Wiki (+0.016, interval not given) and CovidQA (+0.010); against the heuristic it was null or negative at reader sizes 7B (-0.010), 14B (-0.029, p=0.013 in the heuristic's favour) and 32B (+0.001). The authors say 1 of 14 contrasts was significantly positive and 1 significantly negative, about what chance gives, and call the win conditions (multi-hop structure, binding budget, weak reader) a post-hoc hypothesis. Strength: medium for "a gain over naive packing exists on one multi-hop set with a small reader"; weak for anything wider. RCD (arXiv 2605.00336, read): on summarisation, a routing policy used "Lead" (first items) at 256 tokens or less, MMR for 512 to 1,024, a facility-location and log-determinant objective above that; at 256 tokens on MIMIC extractive ROUGE-1 plain Lead (0.242) beat MMR (0.141) and the submodular objective (0.138); with LLM generation MMR was best at 256 to 1,024 tokens (0.265 to 0.282) and Lead matched it at 2,048 (0.280 vs 0.279). No significance tests. AdaGReS (arXiv 2512.25052, read): a relevance-minus-redundancy greedy with a closed-form redundancy weight; compared only against top-k, no numbers in the text, its own derivation has an inconsistent constant, the proprietary corpus is not released. Strength: weak.
- **Verdict for this graph.** Evidence that diversity control beats a plain ranked list is thin and mostly small, and it was obtained on document passages where near-duplicates are common. Our items are code nodes and their near-duplicates are structural (a symbol and its file, a test and its subject, siblings in one slice). Those are better handled by the hierarchy in 3.5 than by a similarity penalty. I would measure how redundant v1's answers are (share of answer items sharing a file with another item) before building anything, and add an MMR-style term only if that share is large. At 10 or 100 times the size the same holds; redundancy would grow (more near-duplicate neighbours) and diversity terms would matter more.

### 3.5 Summaries and hierarchy: answering at the right level of detail

- **The structure that applies here: a hierarchy of representations of the same thing.** Each node can be shown as a path (13.5 tokens), a one-line signature (33 tokens at symbol level), all signatures in a file (156 tokens mean, 1,446 at p99), or source (270 tokens per symbol, 2,218 per file). Choosing one representation per node under a total budget is the multiple-choice knapsack; choosing a file or its symbols (never both) is a knapsack on a tree with an ancestor rule. The classic Tree Knapsack Problem (select a node implies selecting its ancestors) has an exact depth-first dynamic program in time proportional to nodes times capacity (Johnson and Niemi 1983, INFORMS; snippet), and a multiple-choice tree-knapsack variant was used for level-of-detail simplification of computer-graphics models (snippet). Mapping this to "file versus its symbols versus their snippets" is my inference; I found no source applying it to code or to language-model contexts. Strength: theory is old and solid; the application is unproven.
- **GraphRAG's hierarchy** (Edge et al., arXiv 2404.16130, read): hierarchical Leiden communities with LLM-written summaries at four levels. Reading context cost against reading the whole source text: root level C0 uses 26,657 tokens (2.6 %) on a podcast corpus of about 1M tokens (8,564 nodes, 20,691 edges) and 39,770 (2.3 %) on a news corpus; C1 about 22 % and 21 %; C2 about 56 % and 57 %; the lowest level C3 about 74 % and 67 %. Win rate against plain vector retrieval on "global sensemaking" questions: comprehensiveness 72 to 83 % (podcast) and 72 to 80 % (news), diversity 75 to 82 % and 62 to 71 %; directness favoured vector retrieval. Judged by an LLM (125 generated questions per corpus), on global questions only; no fact lookup, no hallucination rate. Strength: medium.
- **The independent check** (Han et al., "RAG vs GraphRAG", arXiv 2502.11371 v3, read): plain retrieval beat community-based global search on detail questions (NQ F1 64.78 vs 54.48; HotpotQA 60.04 vs 45.16; NovelQA 57.12 vs 39.17 accuracy; Llama 3.1 8B) and matched or beat it on summarisation scores; global search helped only on corpus-level diversity. When plain retrieval was given as many tokens as the graph method on MultiHop-RAG (70B), it scored 71.01 against 71.17, so most of that benchmark gain was input size. Construction cost: 5,560 s for community GraphRAG versus 135 s for plain retrieval on that set. Strength: medium (one group, one model family). Conclusion: LLM-written summaries of communities answer broad "what is this area" questions and lose specifics; our use case is mostly specific lookups, and the repository already has its own hierarchy (runtime, vertical slice, file, symbol). Do not build summarisation machinery for this graph. The only broad question worth serving is orientation, and round 2 found overview files give no success gain and cost over 20 % more tokens (AGENTS.md study, abstract only).
- **Community detection as a prior.** Traag, Waltman and van Eck (Scientific Reports 2019; abstract via search): Louvain can return badly connected communities (up to 25 % badly connected, up to 16 % disconnected in their test networks); Leiden is proven to return connected communities and is faster. v1 used Louvain. Swapping is cheap, but on this graph the slice folders already give the grouping, so expect a small effect. **k-core** hierarchies: Hossain and Sariyuce (KDD 2026, arXiv 2603.05207, read) argue modularity methods are unstable on sparse knowledge graphs (average degree 2.88 to 4.42; 55 to 60 % of nodes had degree 1) and propose deterministic k-core levels; with GPT-3.5-turbo the k-core variants won about 70 to 75 % of judged comparisons against Leiden-based levels, but with GPT-5-mini on full data win rates fell to 45 to 55 % with many ties, and the token-budget sampler cut tokens by up to about 40 %. Strength: medium for text corpora, none for code. Our graph has mean degree 6, median 4, and 10 % of nodes with degree 1, so it is not in that regime. I found no study of k-truss or nested stochastic block models for language-model context selection (one search); I cannot say anything about them beyond that.

### 3.6 Connected subgraphs: prize-collecting Steiner tree and its relatives

- **What G-Retriever does** (arXiv 2402.07630, read to character 100,000 of 100,953): node prizes by rank of cosine similarity (top k get k-i, the rest 0), edge prizes likewise, objective prize minus edge cost times a per-edge cost C_e; hyperparameters k=3 for nodes and edges, C_e=1 on SceneGraphs; k=3 nodes, k=5 edges and C_e=0.5 on WebQSP; k=0 (whole graph) on ExplaGraphs. Solver: near-linear-time Goemans-Williamson variant. Table 6 ablation on WebQSP Hit@1 has no "remove PCST" row; "without retrieval" lost 9.43 % (63.84 vs 70.49) but "without the textualised graph" lost 19.19 % and "without graph encoder" 22.51 %. So the paper does not isolate what the Steiner step adds over simpler selection. Its own stated limitation: static retrieval. Strength: medium for the retrieval-size reduction, weak for the claim that the Steiner objective itself is what helps. Graph sizes in its data: WebQSP subgraphs average 1,371 nodes, 4,252 edges; comparable to our whole graph per question, so its pruning job is bigger than ours.
- **Independent head-to-heads.** SubgraphRAG (arXiv 2410.20724, read to 100,000 of 133,865): a small MLP scores every triple using directional distance encodings from the question entities and takes the top 100 triples (about 2.3 % of candidates), one LLM call, no graph optimisation; Hit 89.80 (GPT-4o) and 86.61 (Llama 3.1 8B) on WebQSP; random triples scored 60.14 with Llama 8B; weaker readers got worse as more triples were added (Llama 8B) while stronger readers improved (GPT-4o-mini), so subgraph size must match reader capacity; the paper reports that personalised PageRank did not reliably help as a feature. It compares against G-Retriever in its table (the numbers I saw in a snippet, 53.41 and 73.46, I could not map to metrics). Strength: medium, authors' own benchmark. Ex-GraphRAG (arXiv 2605.21994, read): on STaRK-Prime with an 8B model, single-hop PCST merged with top-25 similar nodes lifted Hit@1 by 1.4 %, top-25 alone lost 9.8 % single-hop and 27.6 % with three-hop expansion; three-hop PCST was worse than single-hop for two of four encoders; no token counts, one dataset. AGRAG (arXiv 2511.05549, read to 100,000 of 144,156): Steiner tree over query-mapped facts (2-approximation) then greedy expansion that can close cycles; its own example shows a bare tree returning the wrong answer ("Tumors" instead of "Blood vessels") and only the cyclic expansion getting it; the Steiner-only ablation matched the full method on fact retrieval and complex reasoning and lost on summarisation and creative tasks; average subgraphs 19.7 to 23.7 nodes. Strength: weak to medium.
- **The algorithm.** Goemans and Williamson (SIAM J. Comput. 1995; secondary sources only) gave a primal-dual 2-approximation, (2 - 1/(n-1)) in O(n^3 log n); Johnson, Minkoff and Phillips (SODA 2000) is the standard study of prize-collecting variants including budget and quota forms, which are at least as hard to approximate as set cover (snippet; paper not found). `pcst_fast` (Hegde, Indyk and Schmidt, ICML 2015) is the C++ nearly-linear implementation with a Python wrapper, 2-approximation in its default pruning mode (snippet and README).
- **Exact is feasible at our size.** The Dreyfus-Wagner dynamic program finds the minimum Steiner tree exactly in time about 3^k times polynomial in n for k terminals (snippets: O*(3^k n + 2^k n^2 + nm) in arXiv cs/0611101; improved to O*(2.684^k) by Fuchs, Kern and Wang). With 3 to 8 terminals and 5,464 nodes that is milliseconds to a few seconds; the approximation matters only beyond about 10 to 12 terminals or at web scale. So at our size nothing needs an approximate Steiner solver, and no install is needed for one.
- **Where it fits our questions, and where it does not.** A Steiner tree answers "how are these two or three things connected, and through what" (the other half of a contract; a route from a screen to a table) and explains a multi-seed question with a small connected subgraph; it is not a recall method. For "what else changes with this file" the v1 result was that co-change and personalised PageRank beat hop reach, and nothing in the literature says a Steiner tree beats top-k scoring on a recall metric. If edge cost is set to minus the logarithm of the edge's reliability, the cheapest connection is the most probable chain of edges (a standard transformation; my application, not tested). Strength of evidence that it helps agents on code: none found (one search for PCST or Steiner on code repositories returned nothing).

What this adds up to for our answers. (1) Format changes accuracy and tokens, with size of effect varying from a few points to tens of points on toy graphs and from nothing to about 10 points on the one code study, which is small. (2) Putting each node's neighbours together (adjacency or tree) is never clearly worse than a flat edge list and costs 39 to 57 % fewer tokens on our graph (section 2.3). (3) Triples are not worse than prose; do not spend tokens on sentences (15 % more tokens than triples, no evidence of a benefit). (4) Edge order matters mostly to small fine-tuned models; keep neighbourhoods contiguous and sorted by rank. (5) Position effects exist for older models over long inputs; at answer sizes of 1,000 tokens the evidence of harm is weak (RCD found Lead minus Shuffled of at most 0.017 ROUGE-1 at 256 tokens, 0.001 at 1,024, GPT-4o); putting the highest-ranked items first costs nothing. (6) The cost of a long answer is not just its own tokens: Du et al. show input length alone costs accuracy for open models even when retrieval is perfect.

## 4. Interface: how a model should traverse a graph

### 4.1 Step-by-step traversal in knowledge-graph question answering

What to take from this, with its limits. All of these are Freebase or Wikidata questions with short answers and a model that must reason over relations; none is about code. They agree on four points. First, a small fixed set of read operations is enough (2 to 4 for StructGPT and Graph-CoT, a bigger set only for a fine-tuned 7B model). Second, the largest single quality lever is how well the candidate relations are pruned (ToG's LLM-versus-BM25 gap, StructGPT's 74 % selection errors, RoG's planning gap), not the number of beams. Third, the iterative design costs calls and tokens (11.6 calls and 7,069 tokens per question for ToG versus 1 to 2 calls for prepared-subgraph designs at comparable or better Hit rates), though the tables mix different readers so they are not controlled comparisons. Fourth, demonstrations or examples of tool use matter enormously for a base model (Graph-CoT without them is near zero) and much less for a current frontier model with well-written tool descriptions, which none of these papers tested. Strength: medium for each, weak across papers (different readers, years, metrics).

### 4.2 Interfaces of code-graph agents and what they measured

- **LocAgent** (arXiv 2503.09089, read): three tools. `SearchEntity` takes keywords and returns entities at three detail levels (full code when 3 or fewer matches, a module skeleton for large files, ids only when more than 3 match). `TraverseGraph` takes start entity ids, a direction, a hop count, entity types and relation types, and returns a tree (indentation shows distance from the root). `RetrieveEntity` returns full attributes. Ablation on a fine-tuned Qwen2.5-7B (file Acc@5 / module Acc@10 / function Acc@10): full 88.32 / 82.85 / 71.53; no `TraverseGraph` 86.13 / 78.47 / 66.06; hops fixed at 1: 86.86 / 80.29 / 66.79; contain edges only 86.50 / 79.56 / 66.42; no `RetrieveEntity` 87.59 / 81.39 / 69.34; no `SearchEntity` 68.98 / 61.31 / 53.28; no BM25 index 75.18 / 68.98 / 60.22. So the lexical entry point is worth 19 points of file accuracy and traversal about 2. Cost per instance on SWE-bench Lite: $0.66 and 7 rounds with Claude 3.5; $0.05 and 6 rounds with the fine-tuned 7B. No token counts per output format. Strength: medium (authors' system, Python only, one benchmark).
- **Aider repository map** (source read, `aider/repomap.py`): a graph of files with an edge from each file referencing an identifier to the file defining it; edge weight is the square root of the reference count times multipliers (10 if the identifier appears in the chat, 10 for long descriptive names of 8 or more characters, 0.1 for names starting with an underscore, 0.1 if more than 5 files define it, 50 if the referencing file is in the chat); personalised PageRank with the files in the chat as the restart set; the ranked definition lines are fitted to a token budget by binary search over how many to show (default 1,024 tokens, 8 times that when no file is in the chat, capped by the context window minus 4,096), accepting any tree within 15 % of the budget even if slightly over; tags cached per file by modified time; the map is reused unless the last one took over 1 second to build. No published ablation of the map's effect (Aider's own pages). Strength of effect: none measured. It is rank-prefix selection with a global graph and no stopping rule, which is what v1 does.
- **The small-agent study** (arXiv 2610.33958 v2, read to 100,000 of 111,175): 9 open-weight models, 170,500 episodes, a placebo arm, 5 seeds. Tools: grep (max 40 matches), read_file (default 80 lines, max 120), list_dir (max 100 entries), semantic_search, find_entity (max 20 definitions), graph_neighbors (1 or 2 hops over all edge types, max 50 lines); every tool output cut to 4,000 characters. Gains for small models (+0.06 to +0.10 Acc@10 up to 14B; +0.026 at 32B, adjusted p=0.056). Whole-set effects of exact ids: with the ids the model can copy, the canonical-versus-exact-id scoring shrank the gain by about 45 % for Qwen3-0.6B and about 27 % for 1.7B; the placebo prints ids the same way and still loses, so formatting alone is not the effect. The page gave no per-hop table in what I read (the 0.47 to 0.55 per extra hop figure cited in round 1 came from an earlier version and I could not find it in v2), and no experiment that varied output caps or ranking of neighbours. Strength: medium to strong for the headline, silent on our design question.
- **Map-based servers in Claude Code** (arXiv 2611.07286, round 1 and round 2): the returned text was snippets grouped by file plus relation lines such as `calls: A -> B`; a hook forced one map query before reads; tokens fell 17 to 39 % with success about flat. The effect of the output format was not isolated.
- **SWE-agent's agent-computer interface** (arXiv 2405.15793, read to 100,000 of 204,413): on SWE-bench Lite a "summarised search" that lists matching files and counts resolved 18.0 %; an "iterative search" that pages through matches with a `next` command 12.0 %; no search tools at all 15.7 %. The file viewer showing 100 lines resolved 18.0 %, 30 lines 14.3 %, whole file 12.7 %. Search returns at most 50 results and withholds the list above that, telling the agent to write a more specific query, to keep context free of noise; the trade-off is an extra model call. An edit command with a syntax check resolved 18.0 % versus 15.0 % without and 10.3 % for shell-only editing. Strength: medium, but it is the only controlled study of how output size, pagination and caps change an agent's success, and it used a 2024 model. Two results transfer directly: do not design pagination as step-through, and a middle-sized window beats both small and unbounded output.
- **CodexGraph**, round 1 (arXiv 2408.03910): the model writes Cypher against Neo4j; removing the Cypher-writing agent dropped CrossCodeEval exact match from 27.90 to 8.30; tokens per SWE-bench sample 102.25k against 76.01k for AutoCodeRover; Qwen2-72B solved 1.95 % against 9.34 %. See 6.3.

### 4.3 Query language, a few fixed tools, or a prepared subgraph

- **Query language written by the model.** Text-to-Cypher accuracy is limited even for strong models on small schemas. CypherBench (arXiv 2412.18702 v2, read to 100,000 of 138,887): property-graph views of Wikidata with on average 7.5 relation types and 18.7 properties per graph, a schema size comparable to text-to-SQL benchmarks; execution accuracy zero-shot: Claude 3.5 Sonnet 61.58 %, GPT-4o 60.18 %, Qwen2.5-72B 41.87 %, Llama 3.1 8B 18.82 %, Llama 3.2 3B 11.20 %; no model under 10B parameters reached 20 %. Common errors: reversed edge direction, entity linking, pattern not aligned with the question. Neo4j's own Text2Cypher benchmark (snippet) names GPT-4o among the best on execution but I did not read its numbers. Combined with CodexGraph's collapse on a weaker model and its token overhead, the evidence is that free-form query writing adds a failure mode and a cost the fixed tools do not have. Strength: medium. Caveat: these tests are question answering over entity facts, not code, and run models of 2024 vintage; a 2026 frontier model would be better, but I found no study showing the failure rate is under, say, 10 % on a 36-edge-kind schema like ours.
- **Fixed tools.** LocAgent (3 tools), the small-agent study (6 tools including grep and read), StructGPT (2 to 3 per data type), Graph-CoT (4), Codebase-Memory (14 tools, round 1), CodeGraph (1 tool, one call returning source plus paths; weak, self-reported). Anthropic's tool-writing guidance (read) says build a few well-chosen tools for high-impact workflows, consolidate multi-step operations into one call (their examples: one `search_logs` instead of `read_logs`, one `get_customer_context` instead of three lookups), and warns that overlapping tools distract the model. No controlled number is published for the consolidation advice. Strength: medium for the 3-tool pattern (it recurs), weak for any specific count.
- **Prepared subgraph.** RepoGraph injected an ego-graph into the agent's prompt (round 1), SubgraphRAG and G-Retriever prepare a subgraph before one call, and the map-first hook in arXiv 2611.07286 forces one query before reads. For frontier models in agent loops the controlled evidence is weak and mixed (round 2: success flat, tokens down, confounded by the hook). The AGENTS.md study found repository overview files did not help and cost over 20 % more (abstract only). A prepared subgraph is cheap when it is keyed to the task (the files the agent already named) and wasteful as a standing overview.
- **Evidence on adoption.** CodeCompass (round 2): 51 of 88 trials (58 %) with the graph available made no graph call; those trials scored 80.2 % coverage against 99.5 % for trials that called it. The small-agent study: `find_entity` was called in 96 % of 14B episodes but 45 % of 32B episodes. In the Hono replication (round 2) a control question never called the tool and one whole run had silently not connected it. The lesson for design: reaching the tool is a precondition that must be measured per run.

### 4.4 Tool descriptions and definitions: what they cost and what makes a model call a tool

- **Definitions are a standing cost.** Anthropic (advanced tool use, read): 58 tools across 5 servers used about 55,000 tokens before any work (about 950 tokens per tool on average); with 50 or more MCP tools about 77,000 tokens loaded upfront, versus about 8,700 with on-demand tool search (their stated reduction is 85 %; the figures given imply about 89 %). On their internal MCP evaluation accuracy with tool search rose from 49 % to 74 % for Opus 4 and from 79.5 % to 88.1 % for Opus 4.5. Their guidance: use tool search when definitions exceed about 10,000 tokens or there are 10 or more tools. RAG-MCP (arXiv 2505.03275, read): choosing among many tool descriptions in the prompt gave 13.62 % tool-selection accuracy; retrieving the few relevant ones first gave 43.13 % and cut prompt tokens by about 49 % (qwen-max, web-search subset, 20 trials; the paper says "over 50 %"). Both show the cost and error rate grow with the number and size of definitions. Strength: medium (vendor-internal; small academic benchmark). Four small tools sit far below any of these thresholds, so tool search is not needed.
- **Description wording changes selection.** "From Docs to Descriptions" (arXiv 2602.18914, read): with one dimension of description quality improved at a time, tool selection probability among 10 servers (gpt-4o-mini, 1,000 queries; random is 10 %) rose by 11.6 points for functionality (stating what the tool does), 8.8 for accuracy, 5.9 for completeness and 1.5 for conciseness; in a competitive setting a compliant description was chosen 72 % of the time against a 20 % uniform baseline. Strength: medium (one small model, synthetic queries). "MCP tool descriptions are smelly" (arXiv 2602.14878, read to 100,000 of 233,070): 97.1 % of 856 tools in 103 servers had at least one description defect; model-written augmented descriptions raised task success by a median 5.85 points on MCP-Universe (231 tasks) but raised execution steps by a median 67.46 %, and 16.67 % of cases got worse; shorter targeted variants (purpose, usage guidelines, limitations) matched the full ones, and removing examples did not hurt significantly. Strength: medium; the 67 % step increase is the cost side of richer descriptions.
- **Anthropic's tool-writing guidance (read; no controlled numbers except one example).** Return high-signal fields and natural-language names instead of opaque ids; offer a `response_format` choice (in their Slack example detailed 206 tokens, concise 72); paginate, filter and truncate with sensible defaults (Claude Code caps tool responses at 25,000 tokens by default); make error messages tell the model what to do next. Their one worked claim is that small description refinements gave large benchmark gains, without a figure.
- **Tool use examples** raised accuracy on complex parameter handling from 72 % to 90 % in Anthropic's internal test (set not described). Our parameters are few and simple; the smelly-description study suggests examples are the first thing to drop.

### 4.5 The re-read arithmetic (my derivation, from other notes' measurements)

Every tool definition is part of the prompt on every model call, and every tool result stays in the context for every later call. In the owner's token accounting, which counts cache reads (round 2 notes that cache reads were 96 to 98 % of baseline tokens in one published trace), a definition of D tokens costs D times T for a task of T calls, and a result of r tokens produced at call t costs r times (T - t + 1).

- One avoided scripted search is worth roughly (695 - 31) tokens per lookup times the number of calls remaining (the 31 and 695 are the first test's per-lookup figures cited in `widen/lane-agents.md`; they were measured on lookup questions, not on "find another file to change"). With T = 40 and the lookup at a random point, about 20 calls remain, so one avoided search saves about 13,000 tokens of reading.
- Three tools of about 120 tokens each (my assumption for a short description plus schema; not measured) cost 360 x 40 = 14,400 tokens over the task. That is paid back by about 1.1 avoided searches. Four tools at the 950-token average Anthropic measured would cost 152,000 tokens over 40 calls and need about 11 avoided searches. The number of tools and the size of each definition therefore deserve the same discipline as the size of an answer. The assumption to check in the pilot is whether definitions are cached and how the owner's total-token metric counts them.
- Corollary: a smaller answer has a larger effect than its raw size suggests, because it is paid again on every later call; this is the stated reason to prefer the stop rule in 3.3 over filling the budget.

## 5. The answer: an answer builder and a tool interface

### 5.1 Answer builder (replaces rank-prefix `pack()`)

Inputs: ranked candidate nodes with calibrated probabilities p_i (calibration from the ranking lane; fit isotonic or Platt scaling on the tuning commits so that p means a hit rate), per-representation costs c_ir from the renderer (already stored: the node `tokens` field plus the form renderings), the call's budget B and a stop density lambda.

1. **Choose a representation per node** among {path only, signature, symbol-signature group for the top definitions in a file, snippet}. Value of representation r for node i = p_i times q_r, where q_r is the probability that this representation spares the agent a follow-up read; q_r is estimated from tuning data (for example, share of cases where the item's own signature or range sufficed to locate the edit) or set by a small grid. Solve the multiple-choice knapsack by sorting representations on the upper convex hull of (cost, value) and taking steps in decreasing marginal value per token, or exactly by dynamic programming (n of a few thousand, B up to 16,000: about 5 x 10^7 steps). The ancestor rule (a symbol line is not shown if its whole file is shown in a form that contains it) makes the structure a tree knapsack (3.5).
2. **Stop** when the next step's value density falls below lambda, even if budget remains. Set lambda from the fallback cost, F, measured on the tuning commits as the tokens the scripted baseline spends to locate one relevant item that the answer omitted; do not hand-set it.
3. **Optionally** subtract an MMR-style redundancy term only if section 3.4's redundancy audit shows a large share of repeated structure.
4. **Order** the shown items by descending value, grouped by file, with the one-line "why" tag per item; **footer** states what was left out in narrowing terms (counts by relation kind and by slice, with the argument that would include them), not as "next page" (SWE-agent's step-through result).
5. **For connection questions** run the Steiner step: exact Dreyfus-Wagner on the typed graph with edge cost = minus log of edge reliability, over the terminals the agent named; return the tree as a path listing with the evidence line of each edge. For more than about 10 terminals fall back to `pcst_fast`.

## 6. Where the literature shows these ideas failing, or a simple baseline matching them

1. **Graph structure for agents.** The only pre-registered study (2610.33958) found an embedding or lexical entry point explained the gain; graph tools added a significant gain for one model in nine. For frontier agents, tokens fall and success stays flat (round 1 and 2). Nothing in this lane's reading shows that a better answer builder changes that; what it can change is tokens per answer and recall per token.
2. **Submodular and diversity packers.** Gain over plain top-k was +0.051 F1 on one multi-hop dataset and null on three others (2607.00725); MMR beat plain packing by +0.010 F1 there; the authors expect about one false positive in 14 contrasts. On summarisation, plain "Lead" beat both MMR and the submodular objective at 256 tokens (RCD).
3. **Steiner and PCST.** G-Retriever never ablated the Steiner step; SubgraphRAG got 89.80 Hit (GPT-4o) with plain top-100 triple scoring and no graph optimisation; AGRAG shows a bare tree dropping the answer; Ex-GraphRAG got +1.4 % from PCST plus top-25 against top-25 alone losing 9.8 %, with three-hop worse than single-hop for two of four encoders.
4. **Community summaries.** Plain retrieval beat community global search on every detail benchmark in the independent evaluation, and at equal tokens it matched community local search (71.01 vs 71.17).
5. **LLM-driven traversal.** ToG needed 11.6 calls and 7,069 tokens per WebQSP question against 2 calls and 231 to 521 tokens for the prepared-path designs, with GPT-4 Hit of 75.1 (GCR's measurement) against 85.7 to 92.6 for the others.
6. **Format.** Effects are small to moderate and often model-dependent; where they are large (adjacency matrices, shuffled edge lists) they hit small fine-tuned models. The code-specific format study has 37 samples.
7. **Richer tool descriptions.** Success +5.85 points at the price of +67 % steps and 16.67 % of cases worse (2602.14878).

## 7. Recommendations (each with the test on tuning data)

Evaluation setting for all tests: the v1 tuning split (65 commits, 388 T1 seeds, plus T3 and TQ questions as available), recall versus tokens curves at 2k, 4k, 8k and 16k, tokens to reach 80 % recall, and the area under the recall-versus-tokens curve. Because a stop rule makes answers shorter, compare arms on the curve, not at a fixed budget. A caution on power from the design checks: the paired spread of recall@10 between two arms across commits was 0.263 per commit, so 65 tuning commits give a standard error of about 0.033 and only differences near 0.065 or more can be told from noise at 95 %; use paired differences on tokens-at-equal-recall, which I expect to be less noisy but have not measured.

The recommendations are carried in the structured output; the short version:

1. Replace rank-prefix with value-density selection plus a cost-based stop (adopt as a trial arm; zero installs; cheap).
2. Add per-node representation choice (multiple-choice and tree knapsack) (trial; zero installs; effect expected mostly at file and snippet granularity).
3. Calibrate ranker scores into probabilities (adopt, prerequisite; zero installs).
4. Redundancy term only after an audit shows repeated structure (trial, low priority).
5. `connect` by exact Steiner for multi-seed and "other half" questions (trial; for explanation tasks only).
6. File-grouped tree output as default format (adopt pending a model-in-the-loop reading test).
7. Three fixed tools with intent enum, caps and narrowing footer (adopt; to be tested in the agent pilot).
8. Do not build: model-written query language tool; ToG-style multi-call LLM traversal; LLM-written community summaries; a learned subgraph scorer.
9. Leiden in place of Louvain as the prior (trial; low expected effect).

## 9. Installs the recommendations would need (the owner decides)

- Selection and stop rule: none (a few hundred lines in the existing Node harness; exact knapsack dynamic programs need no library).
- Calibration: none in Node by hand (isotonic regression is a short pool-adjacent-violators routine); or scikit-learn (about 30 MB wheels) in the Python the build already uses. Runs offline on Linux.
- Exact Steiner: none (write Dreyfus-Wagner in JavaScript). Optional `pcst_fast` (pip; C++ extension with Python wrapper; small; builds offline on Linux with a compiler) only if terminals exceed about 10.
- Leiden: `igraph` plus `leidenalg` or `python-igraph` (pip wheels, tens of MB, offline on Linux) if the prior is swapped.
- Format reading test and the agent pilot: no software, but model tokens (see the structured output).
