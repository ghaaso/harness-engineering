# Lane: time, cached conclusions and invalidation (research notes, written 2026-11-13)

Purpose. The owner asked from the first day about temporal structure, caching and invalidation for the code graph, and said that a graph built by intuition rather than from the documented theory handicaps the idea. This lane goes to the theory underneath "derived answers kept correct as the code changes", says which published algorithm each hand-built part of the earlier cache replay corresponds to, and says what the principled design is for this repository.

Read-only. Nothing was installed or downloaded as a tool. Public papers, documentation and source pages were read; nothing about the owner's project went into any search, URL or request. Two small scripts of mine (in the session scratchpad, `lane-time/delta_stats.js` and `lane-time/digest_near.js`) read the finished test's fact snapshots read-only to measure how large a "what changed" digest is (section 7). They wrote nothing to the repository.

## How to read the strength labels, and how the sources were opened

- STRONG: independent, controlled, replicated. MEDIUM: peer-reviewed with real data but by the system's own authors, or small. WEAK: single study, vendor, preprint, abstract-level. THEORY: a formal result with proofs; it says what is guaranteed, not how much it helps.
- "read" means the paper or page body was opened and the numbers come from it. For PDFs I saved the file through the fetch tool and extracted the text locally with pypdf, so those are read in full text. For web pages the fetch tool returns a summary made by a small model; where I rely on a number from such a summary I say "page summary". "abstract-level" means only the abstract or a search-result summary was seen. Anything not opened is listed in section 11.
- Scale. This graph has about 5,400 nodes and about 10,800 to 16,500 edges per snapshot, 190 snapshots, about 230 commits. For every technique I say whether its benefit exists at this size.

## 0. The short answer

1. The principled architecture for "derived answers kept correct as the code changes" has five parts, and every part has a long-published form: base facts (the parser output, versioned by git commit and extractor version); rules (the question programs); materialised answers; provenance (what each answer rests on); and a maintenance policy. The maintenance policy has two published families: incremental view maintenance (counting, delete-and-rederive, DBSP, differential dataflow) and recorded dependencies with verifying traces and early cutoff (build systems: Shake, Skyframe, Salsa, rustc). On deterministic answers over complete recording they give the same guarantee: the served answer equals a from-scratch recomputation (Build Systems a la Carte, Definition 3.1; DBSP, the definition Q^Delta = D o Q o I). They differ in cost model, not in soundness.
2. At this repository's size a Datalog or incremental-maintenance engine buys speed that is not needed (the finished replay answered 247 questions in 6.0 ms and a whole-graph ranking in about 14 ms, so there is almost nothing to save in computer time). What a declarative rule language does buy, and the build-system route does not give for free, is that the dependencies are extracted from the rules instead of being instrumented by hand. The risk that hand-instrumentation leaves is documented in Skyframe: a read that bypasses the registered path can produce incorrect incremental builds. The cheaper way to get that safety here is a single read API plus an exhaustive single-fact mutation test (recommendation R3). No engine needs installing for it.
3. The hand-built "nothing else matches" patterns of the cache replay correspond exactly to three published ideas, each with a name: predicate locks and the phantom problem (Eswaran, Gray, Lorie, Traiger, 1976), query-update independence (Blakeley, Larson, Tompa 1986; Levy and Sagiv 1993), and why-not provenance (Chapman and Jagadish 2009; Lee, Ludascher, Glavic 2017). In build systems the same thing is a first-class node for a directory listing (Skyframe) and in truth maintenance it is the OUT-list of a justification (Doyle 1979). So the replay re-found a known requirement correctly. What the published versions add are proofs for stratified negation and recursion (Motik et al. 2019), and a way to get the dependency from the rule rather than from instrumentation.
4. A conclusion written by a language model fits the same architecture but breaks two assumptions that every published algorithm makes: determinism of the function, and completeness of the recorded inputs. The build-systems paper already has the right vocabulary for this: such a task is a non-deterministic task with untracked dependencies, correctness has to be relaxed to "the stored result is one possible recomputation", and early cutoff by output equality is unsound for deep traces. The workable design, supported by the one production system I found (GitHub Copilot memory, vendor-reported), is not to re-derive the conclusion but to re-verify its recorded premises, using the recorded deterministic queries as premises, and to treat the prose as suspect when a premise's result changed. The independent literature on LLM self-verification says the trigger must be an external signal (a diff of deterministic premises), not the model re-reading its own answer.
5. For an agent that resumes work, a temporal model adds only a small amount beyond what git and one snapshot per commit already give: the diff of two memoised snapshots, filtered to the neighbourhood of what the agent touched, plus a list of the agent's stored conclusions whose premises intersect the diff. I measured the digest sizes on the finished test's snapshots (section 7): near a typical file the digest is empty or a handful of edges when the agent was last here one or two commits ago, and about 27 edges (2-hop) after about 8 commits. An interval store, bitemporal tables, or a temporal graph database add nothing here that this does not give, and their storage economy only starts to matter at roughly 10 to 100 times the history.
6. Nothing in the published evidence shows that a temporal layer or cached conclusions reduce an agent's tokens on code. The one agent-facing number from a production system (Copilot memory, merge rate 90 % against 83 %) is vendor-reported with no sample size and measures outcome, not tokens. Independent studies of cached LLM conclusions on code are neutral or negative (section 9). The design below is therefore justified by correctness and by cost accounting, and each part has a zero-model test on tuning data before any model tokens are spent.

## 2. The theory, by topic

### 2.1 Incremental view maintenance (IVM): keeping a derived answer equal to a recomputation

Problem statement (Motik et al. 2019, read in full text, 59 pages): a derived relation (a materialisation) is stored; when base facts change it must be updated, and recomputing everything from scratch can be very inefficient. The families:

- Counting: store, per derived fact, the number of derivations; delete the fact when the count reaches zero. Gupta, Mumick, Subrahmanian (SIGMOD 1993) for nonrecursive programs including negation and aggregation (I read this only through Motik's description and a search summary; the 1993 paper and the 1995 survey could not be opened). Motik et al. give the first counting algorithm they know of that handles recursive rules correctly.
- Delete and Rederive (DRed), same 1993 paper: first delete everything that depends, directly or indirectly, on a deleted fact (an overestimate), then rederive the facts that still hold, then add insertions. No extra bookkeeping; handles recursion; inefficient when facts have many derivations.
- Forward/Backward/Forward (FBF), Motik et al.: DRed plus backward chaining to find alternative proofs eagerly.
- Datalog with stratified negation (negation only on lower strata) is covered by all three in Motik et al.
- What was measured (Motik et al. 2019): six real datasets with 12.5 million to 387 million explicit facts and 19.8 million to 1.3 billion derived facts, programs with 210 to 21,385 rules, own system RDFox. The authors find no clear overall winner: FBF fastest on small updates, counting best on large deletions, DRed competitive on large updates; counting's overhead is reconstructing old and new states; the cost correlates with materialisation size. They also prove no algorithm is optimal on all inputs for recursive rules, and that for nonrecursive rules counting always considers only the inferences that change. Strength: MEDIUM to STRONG (peer reviewed, extensive, but one group's system); THEORY for the optimality results.
- Applies at this size? The comparison between algorithms does not (it is at 10^7 to 10^9 facts). The structural facts do: (a) v1's retrieval is bounded-depth reachability (k-hop with a depth cap, 12 in the finished test), which is a fixed union of joins, i.e. nonrecursive, so counting is exact and optimal for it; (b) unbounded reachability is the hard case for incremental maintenance: Motik's survey records that the existence of a first-order maintenance scheme for deletion in transitive closure was a long-open problem, that none exists with only unary auxiliary relations (Dong et al.), that Libkin and Wong's solution needs exponential extra space, and that Datta et al. (2015) later showed directed reachability is in the dynamic complexity class DynFO. At 5,000 nodes none of this matters for speed.

DBSP (Budiu, McSherry, Ryzhyk, Tannen; arXiv 2203.16684 v1, March 2022, read in full text; VLDB 2023 version not opened): a streams-over-abelian-groups model in which a database is a stream of snapshots DB, the transactions are the stream of differences T, integration I sums the differences and differentiation D takes them. The incremental version of any query Q is defined as Q^Delta = D o Q o I; the chain rule (Q1 o Q2)^Delta = Q1^Delta o Q2^Delta lets any query be incrementalised piece by piece; linear operators (selection, projection, union) are their own incremental version; join is bilinear with the familiar formula; sets are made into groups by Z-sets (tuples with integer weights, deletion is weight -1); recursion is a feedback loop whose incrementalisation is semi-naive evaluation; stratified negation (antijoin) reduces to a join followed by a set difference, with `distinct` needing O(size of relation) memory. The paper says the Z-set multiplicities are related to the derivation-counting approaches, and that it covers non-monotonic Datalog. The v1 text I read contains no empirical evaluation; implementations are Feldera and (earlier) DDlog. Strength: THEORY. Relevance here: it gives one definition of "correct" for any maintenance scheme (equals recomputation) and shows that delta-in, delta-out maintenance of a rule set is mechanical. It is also the cleanest formal statement of "time as a stream of snapshots whose differences are the changes", which is the temporal model the owner asked about (section 2.5).

Differential dataflow (McSherry, Murray, Isaacs, Isard; CIDR 2013, read in full text): the state of the computation varies over a partially ordered set of versions rather than a totally ordered sequence, and the set of updates is kept in an indexed structure (a difference trace) instead of being folded into the current state and discarded. Authors' example: a Twitter mention graph for 24 hours, connected components; sliding the window by one second processes 67 differences, which they put at 0.003 % of the work of a full prioritised re-evaluation. Strength: MEDIUM (authors' own prototype Naiad, one workload). Relevance: this is the published model for "keep deltas indexed by version so any version's state can be rebuilt and compared", with versions allowed to be a partial order, which is what a commit DAG is.

Reported against enthusiasm: a 2026 demo paper on FlowLog, a compiler from Souffle-style Datalog to differential dataflow (SPLASH 2026 companion, authors' own, 24 workloads), reports that differential-dataflow-based DDlog used a median 6.3 times (5 to 13 times) more peak memory than FlowLog, and cites empirical studies reporting memory overhead for DDlog that is sometimes orders of magnitude higher than alternatives. It also reports retracting one fact from a points-to result of 4,986,481 tuples took about 7 ms against 2.23 s for full recomputation (320 times). That is the best case for incremental maintenance, and it is at five million derived tuples; this repository's derived relations are three orders of magnitude smaller. Strength: WEAK to MEDIUM (demo paper, authors' own benchmark). Also from the GitHub page of DDlog (page summary): the repository was archived by its owner on 13 July 2026 and is read-only, so it is not a dependency to start on.

### 2.2 Datalog as the language of code analysis, and why

- Doop (Bravenboer and Smaragdakis, OOPSLA 2009, read in full text): a whole Java points-to analysis specified in Datalog, with the authors' argument that implementing and optimising complex mutually recursive definitions by hand at an operational level costs prohibitive human effort, whereas a declarative specification admits automatic optimisation and leaves room for simple manual tuning. Measured: on the DaCapo benchmarks the same analysis ran 15 to 16 times faster than the BDD-based Paddle framework with identical results (1-call-site-sensitive average 16.3 times; 1-object-sensitive 15 times), and unoptimised Datalog typically ran more than 1000 times slower than the optimised one. Strength: MEDIUM (authors' own, but a widely replicated approach). The reason to choose Datalog in this paper is declarativeness plus automatic optimisation of recursion on a very large analysis, not incrementality.
- Souffle (Scholz, Jordan, Subotic, Westmann, CC 2016; GitHub page summary): synthesises a parallel C++ program from a specification; also has an interpreter (PLDI 2021) and provenance support (TOPLAS 2020); licence UPL-1.0; about 1.2 thousand stars. No incremental mode was mentioned on the page. I could not open the CC 2016 paper.
- CodeQL: the earlier round recorded the stated reason from the ECOOP 2016 footnote (SQL systems handled deeply nested joins and recursion badly). I did not re-open it.
- Glean (Meta; blog "incremental", page summary): facts are typed and immutable; each carries a unit label (typically a file name); an incremental database stacks on a base and hides the units that changed; ownership is propagated through the fact graph so that a fact referred to by a visible fact stays visible even if its own unit is hidden, and a derived fact is visible only when every fact it was derived from is visible, written as an ownership expression such as {P} & {Q}. Measured by Meta: about 7 % larger database, 2 to 3 % indexing overhead for Python (within noise for Hack), queries under 10 % slower after caching, search-heavy queries up to about 3 times slower; incremental derivation in time proportional to the increment is implemented only for some query kinds, and Meta calls the general case a hard problem. Strength: STRONG as an engineering description of a production system; no agent or token measurement. Relevance: Glean's ownership expression is lineage (a set of units) combined with AND over the derivation, i.e. the same object as the dependency set in K0 at file grain.
- The bounded-scale conclusion: code-analysis systems chose Datalog because the analyses are large, recursive and mutually dependent, where hand-written operational code is the bottleneck. None of those reasons is present at 5,400 nodes with 8 to 9 fixed question programs.

### 2.3 Provenance: the formal version of "the facts this answer rests on"

- Why-provenance / lineage (Buneman, Khanna, Tan 2001; Cui 2000; not opened, cited through Green et al.): the set of input tuples that contribute to an output tuple.
- Provenance semirings (Green, Karvounarakis, Tannen, PODS 2007, read in full text): annotate each tuple with an element of a commutative semiring; positive relational algebra and Datalog evaluate over any such semiring, and a semiring homomorphism commutes with queries (Prop. 3.5). Different semirings give set semantics, bag semantics, incomplete-database conditions (PosBool, which the paper identifies with the Imielinski-Lipski c-table algebra), why-provenance (sets of tuple ids, with union for both operations) and the most general one, polynomials N[X], which record how a tuple is derived: the paper's own example shows two output tuples with identical why-provenance but different polynomials (2s^2 + rs against 2r^2 + rs), i.e. why-provenance cannot tell which tuple was used how many times. The paper lists negation as further work: it would need an extra operation akin to proper subtraction in the natural numbers. Strength: THEORY.
- Negation: Amsterdamer, Deutch, Tannen (TaPP 2011, arXiv 1105.2255; abstract read) show that attempts to extend semiring provenance to relational difference violate some equivalence axioms that hold for ordinary set and bag queries, and that for some semirings any extension must. Same authors, "Provenance for Aggregate Queries" (arXiv 1101.1110; abstract read): aggregation needs provenance on values, not only on tuples, and difference can be encoded via aggregation. So an answer built from negation or aggregation has provenance that is harder and wider than a positive answer's. K0's completion ranking (an aggregate over a connected region, a median 3,633 nodes per answer) is the empirical face of this.
- Why-not provenance (explaining a missing answer): Chapman and Jagadish (SIGMOD 2009; search summary only: finds the operator where an expected tuple is dropped); Lee, Koehler, Ludascher, Glavic (arXiv 1701.05699, 2017, read in full text) and the extended PUG paper (arXiv 1808.05752, read): a rewriting of Datalog rules with negation that also records failed derivations, so a missing answer can be explained, implemented in SQL over a relational database, "scales to large instances". This is the formal object behind a dependency on absence.
- Strength of the whole block: THEORY plus MEDIUM engineering. None of it measures an agent.

### 2.4 Relevance of an update to a stored answer, and predicate locks

- Irrelevant updates (Blakeley, Coburn, Larson; VLDB 1986 and TODS 1989; VLDB 1986 PDF read in full text): necessary and sufficient conditions for detecting when an update of a base relation cannot affect a derived relation (an irrelevant update), for select-project-join views, for insertions, deletions and modifications. Elkan (updates given as queries) and Levy and Sagiv (VLDB 1993, "Queries independent of updates", for Datalog programs; search summary only) extend it. Motik et al. list these as a problem closely related to view maintenance: determining whether updating the base relations affects the view at all. Strength: THEORY.
- Predicate locks (Eswaran, Gray, Lorie, Traiger, CACM 1976, read in full text): a transaction needs to lock a logical subset of the database, specified by a predicate, rather than a physical one, motivated by phantoms: records that do not yet exist but would satisfy the predicate. A stored answer that depends on a query pattern (all edges of kind X into node Y) has the phantom problem when a new edge of that kind appears.
- Skyframe (Bazel documentation, page summary): the directory listing `readdir()` is itself a node, and a glob depends on directory listings; reading file system data without registering a dependency can cause incorrect incremental builds. This is the build-system answer to phantoms: make the predicate read a first-class node.
- Static against dynamic relevance. The theory above is static: it asks, from the rule text and the kind of update, whether the update can matter on any instance. A verifying trace is dynamic: it records what this answer actually read on this instance. Dynamic is tighter for a specific answer and costs recording; static is cheap and coarser. The finished replay used only the dynamic form; a static kind-level filter was not tried (recommendation R2).

### 2.5 Temporal graph models

- Time-varying graphs (Casteigts, Flocchini, Quattrociocchi, Santoro, arXiv 1012.0009; abstract read) and the survey of temporal networks (Holme and Saramaki, arXiv 1108.1780; abstract read): the formal vocabulary (edges present at times, journeys that respect time order). Wu, Cheng, Huang, Ke, Lu, Xu (VLDB 2014, "Path problems in temporal graphs", read in full text): in a temporal graph the subpaths of a shortest path need not themselves be shortest, so they define four minimum temporal paths (earliest-arrival, latest-departure, fastest, shortest) and solve earliest-arrival by one scan of the time-ordered edge stream in O(n + M) time, M being the number of temporal edges. Tested on 12 real temporal graphs. Strength: MEDIUM (peer reviewed, authors' own implementation). For code: a time-respecting path would be, for example, a co-change chain A with B at time t1, B with C at t2 >= t1. I found no study that shows this helps predict code changes; see HistoRank below.
- Snapshots against deltas for historical graphs (Khurana and Deshpande, ICDE 2013, DeltaGraph; ar5iv page summary): a hierarchical index over the history whose leaves are snapshots that are not stored; interior nodes are graphs derived from lower levels; retrieval of snapshots with millions of nodes and edges in several hundred milliseconds or less, by the authors' account; best variant at least 4 times faster than Copy+Log; naive log replay 20 to 23 times slower; datasets up to 10 million starting edges and 100 million events; 100 snapshots held in memory in about 600 MB against 50 GB stored disjointly. Strength: MEDIUM (authors' own). It is relevant only at scale: this repository has 190 snapshots of about 4.1 MB each (778 MB total in the finished test's cache, from lane-temporal), and a snapshot rebuilds from a commit in about 5 s.
- Bitemporal modelling. Two time axes: valid time (when a fact holds in the modelled world) and system/transaction time (when the database learned it). SQL:2011 standardises period tables for both (Kulkarni and Michels, SIGMOD Record 2012; only search-result summaries opened, the PDF was blocked). Datomic records a transaction id and an added/retracted flag on every datum and offers `as-of` (the database at a past point), `since` (only what was added after a point) and `history` (all datoms including retractions); the page does not model valid time (Datomic docs, page summary). XTDB models both valid time and system time, with closed-open periods and non-destructive corrections, and says one leader node processes transactions serially (XTDB docs, page summary). Graphiti/Zep use four timestamps per fact (earlier lane, read from source). Strength: these are engineering designs; none comes with a measurement of an agent.
- What this means for a commit-versioned code graph (my reasoning): the commit DAG already is transaction time, and the working-tree overlay is "uncommitted transaction time". Valid time in the sense of Zep (when the fact held in the world) is not a separate axis for code: a call edge holds exactly in the commits whose tree contains it. So "bitemporal" collapses to one axis plus a second axis only for the stored conclusions: when the model concluded it, with which graph version. A `since` view is the diff of two memoised snapshots.
- Temporal ranking evidence (HistoRank, Mondal, Roy, Roy, Schneider, SANER 2020, read in full text): five rankers for co-change candidates on ten open-source systems; MAP between 0.0497 (jEdit) and 0.3730 (Ctags); recency ranking was best on 3 systems, file-proximity (a static, structural measure) best on 6, similarity on 1; recency was significantly better than support and confidence ranking (Wilcoxon, p = 0.04) but not significantly different from file-proximity or similarity; confidence ranking was the worst on all ten; the variant of their selector that emphasises the most recent co-change performed best. Strength: MEDIUM. Reading: recency helps ranking over the usual support and confidence, but static structure matters about as much, and the effect is a few points of MAP, not a large one.

### 2.6 Truth maintenance: beliefs that are retracted when their premises change

- Justification-based TMS (Doyle, Artificial Intelligence 12, 1979; the paper itself not opened, its abstract and de Kleer's description read): every belief is a node with justifications; a justification of the simple SL kind has an in-list and an out-list; a node is believed (IN) if some justification has every in-list node IN and every out-list node OUT. The out-list is how a non-monotonic belief (believe A unless there is evidence to the contrary) is represented, which is exactly the shape of a claim that no other caller exists. Doyle's TMS also needs a constraint-satisfaction step to settle which nodes are IN, which de Kleer calls cumbersome, and requires well-founded support, so circular support is outlawed.
- Assumption-based TMS (de Kleer, Artificial Intelligence 28, 1986, read in full text, 36 pages): label each datum with the minimal sets of assumptions (environments) under which it holds; contexts switch at no cost; a label is consistent, sound, complete and minimal. De Kleer describes the justification-based TMS as, among other roles, a cache of all inferences ever made, and the ATMS as an intelligent cache; he notes that the justification-based design holds one context at a time and offers no way to return to an earlier state. He also says retracting a justification is inherently inefficient for every TMS, and compares it to garbage collection. The ATMS label of a node corresponds to the why-provenance in positive Boolean form: Green et al. show PosBool gives the c-table algebra; the equivalence of ATMS labels with that structure is my inference, which I did not see stated in the sources I opened.
- Cost: Motik et al. point out that a TMS that stores every justification of every derived fact is infeasible at their scale because the number of derivations is often orders of magnitude larger than the number of derived facts. At this repository's scale that is not a constraint for a few thousand conclusions.
- Strength: THEORY; the engineering evidence is from the 1980s and is about problem solvers, not about language models.

### 2.7 Incremental computation and build systems

- Build Systems a la Carte (Mokhov, Mitchell, Peyton Jones, ICFP 2018, read in full text, 29 pages). Definitions. Minimality (Def. 2.1): each task runs at most once per build, and only if it transitively depends on an input that changed since the previous build. Correctness (Def. 3.1): input keys are unchanged and, for every non-input key, recomputing its task gives the value stored in the result. Rebuilders: a dirty bit (Make, Excel) cannot do early cutoff because dependents are already marked dirty (Excel over-approximates dependencies statically and marks a cell dirty if the formula refers to a dirty cell or calls INDIRECT); a verifying trace stores hashes of the dependencies' values used last time and rebuilds if any hash differs (Ninja, Shake); a constructive trace also stores the value so it can be fetched (Bazel, CloudBuild); a deep constructive trace records only terminal inputs (Buck, Nix) and, for two or more levels, requires the tasks to be deterministic, and cannot do early cutoff except at n levels. Early cutoff: if a rebuilt task's value equals the old one, stop. Impurities (section 6): untracked dependencies (for example the compiler version), non-determinism (the correctness definition is relaxed to: the stored value is one of the possible results of recomputing), and volatile tasks, which cannot be cached and are modelled as depending on a special RealWorld key that changes every build. Strength: THEORY plus STRONG engineering.
- Skyframe (Bazel docs, page summary): functions must be deterministic, get all input through the environment, and change pruning resurrects dependents when a rebuilt node equals its old value.
- Salsa (rust-analyzer's framework; docs page summary): each memoised function stores its return value, its dependencies and the revisions at which they last changed; if a re-executed dependency returns an equal result its changed-revision is not advanced ("backdating"); durability levels let a function that depends only on slowly changing inputs skip walking its edges. The page did not state purity or determinism requirements.
- Adapton (Hammer et al., PLDI 2014; only a search summary seen) and nominal Adapton (Hammer et al., OOPSLA 2015, arXiv 1503.07792, abstract read): demand-driven incremental computation, and a formal proof of from-scratch consistency, meaning the incremental result always equals re-running the computation. Self-adjusting computation (Acar, CMU thesis 2005; search summary only): dynamic dependence graphs plus change propagation. Strength: THEORY.
- Relevance: these are the settled theory of recorded dependencies, verifying traces and early cutoff. They assume pure, deterministic functions; section 5 is about what happens when one function is a language model.

### 2.8 Evidence on cached model-made conclusions

(From this lane's reading; the earlier lanes added the first four.)
- ETH Zurich study of LLM-written repository context files: no significant resolution gain and about 20 % higher cost; developer-written files +2.4 %, not significant (earlier lane, read). MEDIUM to STRONG.
- VibeMemBench: 11 of 12 memory-system pairings did not beat memory off; the form of the stored record was the main failure (earlier lane, read). MEDIUM.
- SWE Context Bench: an unfiltered or wrongly chosen summary reused across tasks scored 22.22 % against a 26.26 % no-experience baseline; a perfectly chosen small summary scored 34.34 % (earlier lane, read). MEDIUM.
- GitHub Copilot memory (GitHub blog, 9 January 2026; page summary): each memory has four fields (subject, fact, citations, reason); a citation is a code location such as a file path with a line number; before using a memory the agent is prompted to read the cited locations; if the code contradicts it or a citation does not exist the agent stores a corrected memory; if the citation checks out the memory is re-stored to refresh its timestamp. The authors' stated reason: finding the right memory is hard but checking one is easy, and offline curation (deduplication, conflict resolution, branch tracking, expiry) would add engineering and model cost and would still need reconciliation at read time. Reported results: coding agent pull-request merge rate 90 % with memories against 83 % without, code review positive feedback 77 % against 75 %, both said to be highly significant (p below 0.00001), no sample sizes; an adversarial test with seeded contradicting memories and fake citations is said to have shown agents checking citations and correcting memories, with no numbers. Strength: WEAK (vendor, no n, no tokens). Secondary coverage claims a 28-day expiry and under 50 ms start-up cost; the primary page, as summarised, states neither, so I do not rely on them.
- Invalidation Contracts for Cross-Episode Agent Memory (Wu and Canedo, arXiv 2609.00243, 31 August 2026; abstract read): cached recovery suggestions from API errors are stamped with versions so a client can evict stale entries; about 9,400 episodes, seven models, two domains. Row-level invalidation recovered 29 to 33 % of baseline token cost on four of seven models; table-level invalidation also evicted valid co-located entries and dropped post-drift first-try success to 0 % on five of seven models; eviction precision was 1.00 at row level under their oracle; the contract added 15 % to payload; the same bytes gave 100 % first-try compliance on one model and 11 % or below on another, because that model refused fixes that added fields the original request lacked. Strength: WEAK (two authors, preprint, abstract only, a different task from code). Reading: invalidation granularity matters in the same direction as K0's file against fact result, and whether a cached item is used depends on the model, not on the protocol.
- Context rot (arXiv 2606.09090, June 2026; read via page summary): a rule-based checker (DOCER) extracts code identifiers from CLAUDE.md-style files with regular expressions and checks with `git grep` whether each existed at the file's first commit and exists at HEAD. 18,048 references checked in 356 repositories; 230 (1.27 %) stale; 82 of 356 repositories (23.0 %) had at least one; in a manual check of 50 stale references by one annotator, 32 were genuine, 12 false positives, 6 ambiguous. The paper evaluates no model-based detection and no effect on agent performance. Strength: WEAK to MEDIUM. Compare with the earlier research's count for this repository's docs, 517 of 1,268 backticked file names not resolving, which is far higher because it includes names that were never paths.
- Attribution faithfulness (Wallat et al., arXiv 2412.18004; abstract read): up to 57 % of citations in attributed answers are not faithful, meaning the model cites documents that match its prior beliefs rather than the ones it relied on (post-rationalisation). Question-answering over documents, not code. Strength: WEAK to MEDIUM. Relevance: a model's own list of "what I relied on" cannot be trusted as the premise set without a check.
- Self-verification (Huang et al., arXiv 2310.01798; Stechly, Valmeekam, Kambhampati, arXiv 2402.08115; abstracts read): without external feedback models struggle to correct their reasoning and sometimes do worse; GPT-4 self-critique on Game of 24, graph colouring and STRIPS planning caused a significant performance collapse while a sound external verifier gave significant gains and re-prompting with the verifier's feedback kept most of the benefit. Models of 2023 and 2024; no numbers in the abstracts; newer models were not tested there. Strength: MEDIUM (independent, replicated direction, but dated).
- Belief-revision memory systems: a NeurIPS 2026 listing (Belief Context Graph, abstract-level only) proposes typed dependency, supplementation and contradiction edges for long-horizon agents and reports a better accuracy-to-resource trade-off with no numbers I could see; separately a single-author arXiv preprint (Kumiho, arXiv 2603.17244, abstract read) claims formal belief-revision semantics (the AGM postulates) for versioned agent memory with dependency edges; its headline LoCoMo-Plus figure is the author's own, and the benchmark authors' reproduction came in several points lower. Strength: WEAK. I found no peer-reviewed system that applies a truth maintenance system to model-made conclusions with measured results.

## 3. The K0 cache replay, part by part, against the published algorithms

What K0 built (from its NOTES.md): every read goes through a recorder that logs (a) facts: each node and canonical edge read, with a hash of the whole record and a semantic hash of the fields actually used; (b) negative dependencies: every query pattern run (out-edges or in-edges of a node restricted to kinds, nodes with a path, nodes with a name) with a hash of its matched set; (c) files: the paths behind the reads; (d) sub-derivations (reach sets, ranked list) as separate units with their own dependencies. Policies compared: none, repo, file, fact_pos (no patterns), fact, fact_sem (semantic hash), cutoff, cutoff_sem, ttl5, ttl20, never.

| K0 part | Published algorithm or idea it corresponds to | What the published version does that K0's version does not | Guarantee the published version gives |
|---|---|---|---|
| Recorder log of every node and edge read | Lineage / which-provenance (Buneman, Khanna, Tan 2001; Cui 2000) as the dependency list of a task in a verifying trace (Mokhov et al. 2018, section 4.2.2); Glean's ownership of a derived fact (AND over the facts it derived from) | Why-provenance keeps minimal witness sets, so an answer with an alternative derivation survives deleting one of its facts; semiring polynomials N[X] keep how many times each fact was used (Green et al. 2007). Counting keeps a derivation count per answer fact. K0's flat read set treats any changed read as invalidating, even when another derivation remains | Lineage is sound and conservative: if no recorded fact changed, the answer is unchanged. Finer provenance gives fewer false invalidations, not more safety. K0's measured over-invalidation: 88.8 % of `fact`'s recomputations returned the same answer, 66 % for `fact_sem` (797 of 1,201), which counts both alternative derivations and irrelevant changes |
| Semantic hash of only the fields read (`fact_sem`: 95.9 % served against 87.6 %) | Irrelevant-update detection (Blakeley, Coburn, Larson 1986) done dynamically; equivalently, treating each read field as its own input, as build systems do when they split an input to get finer dependencies | The published test is static and instance-independent, decided from the selection and projection conditions of the rule, so no recording cost and a proof that the update cannot matter. ## 4. Answer 1: the principled architecture for derived answers kept correct as code changes

### 4.1 The layers (each with its published form)

| Layer | Content | Key | Published form |
|---|---|---|---|
| L0 base facts | Parser output per commit: nodes, typed edges | (commit, extractor version). Optionally per file keyed by blob id | Immutable fact store with units (Glean); content-addressed memo (Bazel, Nix); git is the version store |
| L1 derived cross-file facts | Joins that no single file determines: URL to route, import resolution, call resolution, table reads and writes, route prefixes | Derived from L0 | Datalog rules / derived predicates (Glean, Doop); K0 found a route id that changed because a prefix was set in another file |
| L2 materialised answers | One per question program and arguments | (program version, arguments, graph version) | Materialised view; build-system value |
| L3 provenance | The reads behind each answer: fact reads with a semantic hash, pattern reads with a hash of the matched set, sub-derivation links | per answer | Verifying trace; lineage; predicate reads |
| L4 maintenance | Validate on demand: compare recorded hashes with the current graph; on mismatch recompute; compare; cut off | | Shake / Skyframe / Salsa; or counting / DRed if answers become expensive |
| L5 conclusions | Model-made findings with premises | section 5 | JTMS justifications / Copilot citations |

### 4.2 Is a Datalog engine the right implementation at this size, or are recorded dependencies with early cutoff equivalent here?

- Equivalent in guarantee. Both deliver "the served answer equals a recomputation": Build Systems a la Carte Definition 3.1 for the trace approach; DBSP's definition of the incremental query and Motik et al.'s proofs for the maintenance approach. For positive monotone programs the pattern-hash validation is the same test as asking whether the change set intersects a body atom of a rule, which is the relevance test of Blakeley et al. and the trigger of semi-naive evaluation. For programs with negation over a lower stratum, a pattern hash that changes when a matching fact appears or disappears is the antijoin dependency, and DBSP derives it mechanically (section 7.5 of that paper).
- Different in cost. IVM pays per change; verifying traces pay per lookup (validation is 0.3 to 3.8 ms per snapshot over 350 questions in K0) and recompute when invalid. IVM pays off when recomputing is expensive and changes are small and many; here recomputing costs about 24 microseconds per question and the replay found 1.4 % of lookups change. The published cross-over is also a warning: Motik et al. found that on large deletions the cost of maintenance can exceed the cost of rematerialising, and note that even an optimal maintenance algorithm can lose to rematerialisation (for instance when the whole explicit dataset is deleted).
- Different in where the dependencies come from. Rules give them by construction; a trace gets them by instrumentation. At this size this is the only real argument for a declarative layer. It is met more cheaply by (a) a single read API through which every program must read (K0 already has one, `rec.js`) and (b) a property test that checks the recorder against truth for every possible single-fact edit (R3). That is the same discipline Skyframe documents.
- Different in what they can wrap. A Datalog IVM engine wraps deterministic rules. It cannot wrap a model call. The build-system formalism can: the model call is a task whose correctness is relaxed (section 5).
- Where it changes at 10 and 100 times the size. At 10 times (50,000 nodes, 2,300 commits): full-snapshot storage per commit (4.1 MB) would be about 9.4 GB for all commits (my arithmetic from the finished test's 4.1 MB per snapshot), so snapshots must become a cache of a pure function of (commit, extractor version), rebuilt on demand in about 5 s, or be stored with sharing; the ranking answer (about 14 ms) would be about 140 ms; recompute still wins. At 100 times (500,000 nodes, 23,000 commits): the ranking is about 1.4 s per answer, snapshots must share structure (DeltaGraph: hierarchical deltas; Glean: stacked databases), and incremental maintenance of the unbounded or whole-graph derived views starts to pay (the FlowLog best case is 320 times at five million derived tuples). These are extrapolations of linear cost, not measurements.

### 4.3 What I recommend as the architecture (and what I reject)

- Build now, in plain code: L0 as a memo table keyed by (commit, extractor version); L2 to L4 as K0 built them, with the single read API enforced; a conclusion ledger for L5 (section 5).
- Add to L4 two cheap policies that K0 did not run: a static kind-level relevance filter (R2) and an exhaustive single-fact mutation test (R3).
- Do not adopt a graph database, an interval store, a bitemporal store, or a Datalog engine now. Revisit when a derived view that the agent needs costs more than about one second to recompute, or when the history or graph grows by about 100 times.

## 5. Answer 2: how a conclusion made by a language model fits the architecture

### 5.1 What the premises are

A model's conclusion is a task in the sense of Build Systems a la Carte with four properties that the algorithms assume away:

1. The function is non-deterministic and not even a function of its recorded inputs: the same premises can give different text (value-level non-determinism).
2. It has untracked dependencies: model version, prompt, sampling settings, and everything else in the context window.
3. Its read set is not recorded unless the harness records it: the model "read some facts and some text and reasoned".
4. Its output is text, so "equal to the old output" (early cutoff) is not a well-defined test unless the output is structured.

Premise classes, from most to least checkable:

| Class | What is recorded | How it is re-checked | Cost |
|---|---|---|---|
| A. Graph query reads | Query program version, arguments, result hash, plus the K0 pattern dependencies | Re-run the recorded query at the new graph version and compare the result hash (deterministic, so exact; this is a verifying trace with early cutoff, and it is the Salsa backdating step: premise changed but the value the model saw did not) | milliseconds |
| B. Text reads | File path, line range, content hash of the range, and the hash of the enclosing symbol | Compare hashes; if the range moved, relocate by symbol; if the file is gone, premise missing. This is Copilot's citation check made deterministic | microseconds |
| C. Absence premises ("I searched and found nothing", "no other caller") | The search (pattern or query), its scope (file set or kind set) and the result hash | Re-run the search and compare. This is a predicate read, the phantom case; without the scope the premise cannot be re-checked | milliseconds |
| D. Documents and human statements (invariants file, handoff, owner instruction) | Document version hash and the section anchor | Hash compare; a heading or section removal is a premise failure | microseconds |
| E. Unrecorded context (background knowledge, earlier turns, un-logged reads) | Nothing | Cannot be checked: untracked dependency | n/a |
| F. Environment | model id, prompt hash, extractor version, graph version | Part of the key; a change makes the record a candidate for re-derivation, not for silent reuse | n/a |

Two sets of premises should be kept: the hard set (everything the harness saw the model read through tools: classes A to D, complete and mechanical, an over-approximation like lineage) and the declared witness set (what the model says it relied on). The attribution literature says the declared set can be unfaithful (up to 57 % of citations in attributed answers in the one study), so it is a hint for prioritising checks and for rendering a short explanation, not the soundness basis. This is a design choice of mine; no published system does this split. Copilot uses only the declared set (citations) and re-reads them at use.

### 5.2 When it becomes suspect, and what happens

- Mapping to truth maintenance: a conclusion is a node whose justification has an in-list (premises that must hold) and an out-list (absence premises, class C). When a premise's recorded result no longer matches, the justification is invalid and the node goes OUT as a belief, but is kept, with its justification, as an explanation (Doyle's TMS keeps justifications; the ATMS label tells which assumption sets support it). The ATMS point that labels are computed so that one can "switch context at no cost" corresponds, here, to the answer to "was this conclusion valid at the commit where I wrote it": yes, the record is a fact about the past.
- Status values, in order of cost to act on: VALID (all hard premises re-verified with equal results; serve as is); VALID-BY-CUTOFF (a premise's inputs changed but its recorded query result is equal; serve, no model); SUSPECT-WEAK (a hard premise changed but all declared witnesses are unchanged; serve with the changed premise shown); SUSPECT (a declared witness changed or an absence premise result changed; do not serve as fact; show the old conclusion with a premise diff); UNVERIFIABLE (class E premises or class F mismatch; serve only as a hint). Nothing is deleted.
- Retraction cost: de Kleer calls justification retraction "inherently inefficient", but that is about a general belief network. For a ledger of a few thousand conclusions with a premise-to-conclusion index, finding the suspect set after a commit is a join of the commit delta with the premise index: microseconds to milliseconds.

### 5.3 What the literature says about re-checking

- Verifying is cheaper than regenerating is a vendor claim (GitHub argues that retrieval is hard but verification is easy), supported by an A/B (90 % against 83 % merge rate) without sample sizes. WEAK.
- Re-checking by the model alone is not reliable: without an external signal self-correction does not help and can hurt (Huang et al.; Stechly et al., GPT-4 era). The recommendation that follows is that the trigger and the evidence for a re-check must be deterministic: show the model the old conclusion and the premise diff (old result against new result) and ask it to confirm or revise; do not ask it to re-read the whole area.
- A re-check of a premise whose output did not change is free (cutoff). That depends on classes A to D having deterministic results, which they do. It does not extend to the prose conclusion: early cutoff on the conclusion text is unsound, because recomputation would give different words even with identical premises (Mokhov et al.: with non-deterministic tasks the correct statement is "one possible result", and deep traces break).
- Granularity: the Invalidation Contracts study found that coarse invalidation destroys co-located valid entries and fine invalidation does not (WEAK, abstract only), the same direction as K0's file against fact result. A conclusion's premises should therefore be recorded at query-result granularity, not file granularity.
- The cost reality: stored LLM-written context did not help on average and cost more in two independent studies (ETH Zurich about 20 % more cost; SWE Context Bench free summary reuse below baseline). A ledger does not make those conclusions better; it only stops stale ones being served. Its benefit is bounded by how often conclusions are reused, which is untested.

### 5.4 A part of the problem that moves out of the model

Most of the checkable content of an agent's conclusion is a claim that is already a deterministic query ("route R is called by screen S", "setting K is read in file F", "no test reaches function G"). Such a claim should not be stored as a model conclusion at all: store it as a materialised answer (class A) with its recorder, and let it be recomputed or revalidated mechanically. Only the interpretation (why it matters, what to do) remains a model conclusion, and that part has the premise of the claim. How much of the agents' findings are of this kind is measurable from existing transcripts without any model call (R9).

## 6. What the temporal literature adds, stated honestly

For this use case I find the following genuinely useful, with sources:

- Snapshot at commit K is the as-of-K view. The commit DAG is the version store and git's content addressing already gives structural sharing at file level. A graph snapshot is a pure function of (commit, extractor version) and can be treated as a cache entry (a constructive trace in the build-systems sense), not as a second database.
- The diff of two snapshots is the delta stream of the DBSP/differential view. `since` in Datomic is the same idea.
- A derived answer that records its premises is the one structurally new capability (section 2.3 and 2.7), and it is not specific to knowledge graphs.
- Time-respecting path structure (Wu et al.) and interval-stamped edges (Debrouvier et al.'s temporal property graph model, T-GQL, VLDB Journal 2021, abstract-level only) are available, but I found no code study that shows they predict changes better than recency-weighted co-change; HistoRank (MEDIUM) shows recency helps over support and confidence and that static file proximity helps about as much.
- Temporal knowledge graph embedding and forecasting (the bulk of the temporal-KG literature) predicts missing future facts; its two surveys I opened (arXiv 1905.11485, 2403.04782) say nothing about retrieval for agents or memory in their abstracts, and I did not read them further. That belongs to the embedding lane.

## 7. Answer 3: "what changed near this since I last looked", and its cheapest sound form

### 7.1 Construction (all plain code)

1. The agent's session stores a marker for each time it read the graph: the commit hash (or tree hash), the extractor version and a hash of the working-tree overlay. A marker is a transaction-time anchor in the bitemporal sense.
2. On resume, compute the delta between the marker's snapshot and the current snapshot (or the working-tree overlay): added and removed nodes and edges, and edges whose evidence changed. Cost: two memoised snapshots (K0 measured 98 ms to load and hash one) and a set difference.
3. Filter to the neighbourhood of what the agent touched: k-hop node set around the agent's anchors (files edited, files read, files named in stored conclusions), with hubs not expanded.
4. Join the delta with the premise index of the agent's stored conclusions (section 5): list those whose premises changed, with the status values of section 5.2.
5. Report the delta as a bounded list (kind, endpoints, added or removed), ordered by distance to the anchors. This is a `since` view.

Soundness: sound for what the extractor sees, for the same reason a snapshot is exact; the delta cannot miss a change in the extractor's facts. It misses what the extractor does not model (the K0 limits), and misses a rename as anything but delete plus add: git's rename detection is heuristic, and node identity in the graph is by path and symbol, so a moved symbol appears as a removed id and an added id; I did not measure how often renames occur in the history.

Why no interval store: the only questions an interval store answers faster are "since when has this edge existed" and "how long has it been stable", which a scan over the 190 snapshots (about 2 million edge rows) answers in seconds if ever needed; they are not the resume questions.

### 7.2 Measured digest sizes (mine, read-only on the finished test's 190 snapshots; indicative)

Method. Delta between a snapshot and its first-parent-tree parent for all 189 steps (`delta_stats.js`): an edge counts as changed if its key (kind, source, target) appears or disappears, or its evidence path or confidence changes; line-number shifts are not counted.

| Quantity over 189 steps | Median | 90th percentile | Max |
|---|---|---|---|
| Edges added, removed or evidence-changed per step (all kinds) | 115 | 645 | 1,703 |
| The same, excluding history-derived `co_changed` edges | 81 | 512 | 1,448 |
| Co-change edges changed per step | 2 | 139 | 449 |
| Nodes added plus removed per step | 26 | 153 | 490 |

A snapshot has a median of 10,847 edges, so a typical commit changes about 1 % of edges. 72 of 189 steps change 50 or fewer non-history edges and 144 change 200 or fewer.

Near an anchor (`digest_near.js`; main-chain snapshot pairs every 4th starting at index 10, 20 randomly drawn non-test files per pair, seeded; delta excludes `co_changed`; "near" means the changed edge has at least one endpoint inside the anchor's k-hop node set in the union of both snapshots; nodes with more than 60 neighbours are not expanded beyond the first hop):

| Gap between "last looked" and now | Pairs, anchors | Whole-graph delta median / p90 | Near, 1-hop: median / p90 / share zero | Near, 2-hop: median / p90 / share zero |
|---|---|---|---|---|
| 1 snapshot (mean 1.6 commits) | 22, 440 | 182 / 762 | 0 / 6 / 70.5 % | 2 / 51 / 41.8 % |
| 5 snapshots (mean 7.9 commits) | 21, 420 | 776 / 2,140 | 2 / 36 / 40.0 % | 27 / 213 / 11.4 % |
| 20 snapshots (mean 31.4 commits) | 18, 360 | 4,505 / 6,099 | 13 / 111 / 21.7 % | 151 / 714 / 3.1 % |

Reading: after one or two commits the digest near a random file is empty in most cases (70.5 % at 1-hop), so the answer "nothing changed near you" is both common and nearly free; after about 8 commits a 2-hop digest has a median of 27 changed edges, which is small; after about 31 commits it has a median of 151, which needs ranking or a cap. The anchors are random files, not an agent's recent work, which is likely to sit in more active areas, so these are lower bounds on activity near an agent's real anchors. Not measured: tokens per edge line, whether the digest contains the change an agent needs, or any agent behaviour.

Indicative selectivity of a static kind-level filter (R2), using my own reading of which edge kinds the question programs use (so approximate): over the 189 steps, no edge of kind `reads_setting` is added or removed in 72.0 % of steps; none of `migration_touches` or `writes_table` in 65.6 %; none of `calls_url` or `registers_route` in 64.6 %; none of `constrains` in 88.4 %; none of the `calls`, `calls_url`, `test_calls_route`, `mocks`, `overrides` family in only 21.2 %. So a kind-level filter would cheaply validate narrow programs and do almost nothing for the call-graph programs, which the fact-level policy already serves at 87.6 %.

## 9. Reported against my own enthusiasm

- Nothing I found shows that a temporal layer, a cache of model conclusions, or provenance-based invalidation reduces an agent's tokens on code. The strongest agent-facing number is vendor-reported with no sample size and measures merge rate. The independent studies (ETH Zurich, VibeMemBench, SWE Context Bench) show stored model-written context neutral to harmful on average.
- K0's token figures are estimates under one assumption, not savings, and against typed queries a cache hit avoids zero tokens, because a typed query already returns an answer of the same size. Nothing in this lane changes that. The whole token case for caching rests on conclusions that cost a model a lot to derive, which has never been measured here.
- The published algorithms solve a problem this repository mostly does not have. Motik et al.'s algorithms are for 10^7 to 10^9 facts; at 10^4 a full recomputation costs microseconds to milliseconds.
- K0's recorder was complete for nine programs, and the audit checked 40,880 lookups. That does not make the approach safe for model conclusions, where reads are not recorded and the function is not deterministic.
- On a temporal ranking signal: recency helped over support and confidence on co-change in one study (MAP differences of a few points, p = 0.04 against support and confidence) and static file proximity did as well or better on six of ten systems. v1 already has a recency weight.
- Incremental maintenance has hard theory: for general recursive queries no maintenance algorithm is optimal on all inputs (Motik et al.), and whether deletion from unbounded reachability can be maintained with first-order queries was an open problem until the DynFO result of 2015. This is why v1's depth-capped k-hop is a good choice for maintenance as well as for retrieval.
- Matching, not beating, baselines: Letta's grep-and-open filesystem agent matched graph memories on their own conversation benchmark (earlier lane). For code, tuned grep beat a graph server on F1 in a sverklo post (earlier lane). A temporal layer would have to beat that baseline, not the absence of one.

## 10. Recommendations (concrete; tests use the tuning split only, the held-out commits stay sealed)

R1. Conclusion ledger with typed premises (adopt; build in plain code).
- What: a record per model conclusion: structured claim (where possible a deterministic query plus its answer), premise list of classes A to D with hashes, hard set and declared witness set, environment key (model, prompt hash, extractor version, graph version), status among VALID / VALID-BY-CUTOFF / SUSPECT-WEAK / SUSPECT / UNVERIFIABLE, premise-to-conclusion index for finding suspects after a commit.
- Theory: JTMS justifications with in and out lists (Doyle 1979); build-system tasks with non-determinism relaxed (Mokhov et al. 2018, section 6.3); lineage; Copilot's cite-and-verify (vendor).
- Replaces in v1: nothing; v1 stores no conclusions. It formalises K0's recorder as the premise layer.
- Expected effect: stale conclusions are never served as facts; revalidation of premises costs milliseconds and zero model tokens in the common case where premise results are equal. Token effect not predicted.
- Test on tuning data: (i) zero-model: replay the 189 tuning-window steps with the 250 K0 questions as stand-in conclusions; hard-set validation must give 0 stale and the over-invalidation rate per premise class must be reported; (ii) small model-in-the-loop pilot on agent findings extracted from existing session transcripts: label each finding "still true at commit C+k" by deterministic re-derivation where the claim is a query and by a strong model plus a human check otherwise; compare precision and recall of three triggers (hard set changed; declared witness changed; either); the rejection rule is a trigger that misses more than a small fraction of false findings or flags nearly everything.
- Install: none.
- Verdict: adopt.

R2. Static kind-level relevance filter in front of the fact-level check (trial).
- What: for each question program, the set of edge kinds and node kinds it can read, derived from the program text (a static analysis of its read API calls); an update that adds or removes no fact of those kinds cannot change the answer.
- Theory: irrelevant-update detection (Blakeley, Coburn, Larson 1986); query-update independence (Levy and Sagiv 1993).
- Replaces in v1: nothing; adds a tier before K0's `fact`.
- Expected effect: validation without touching the graph for narrow programs (indicative: 65 to 88 % of steps for the settings, migrations, route-client and invariant programs; 21 % for the call-graph family); stale rate zero by construction if the read API is the only path.
- Test: rerun K0's replay with this policy on tuning snapshots; stale must be 0; report hit rate and validation time against `fact` and `fact_sem`. Rejection: validation time not lower than the K0 `fact` check (0.31 ms per snapshot) or any stale answer.
- Install: none.
- Verdict: trial (cheap; expected small gain in compute, none in tokens).

R3. Single read API enforced, plus an exhaustive single-fact mutation test of the recorder (adopt).
- What: every question program must read the graph only through the recorder, enforced by a lint over the program files; then, at one snapshot, for every node and edge in the graph (about 5.4 thousand nodes, 10.8 to 16.5 thousand edges) apply the edit "remove it" and, for every kind and plausible endpoint pair in a sample, "add it", and check for each of the 250 questions that validation says valid only if the recomputed answer is equal.
- Theory: Skyframe's "unregistered dependency" warning; the independence problem (Levy and Sagiv) solved by enumeration on a small instance; K0's replay covers only edits that real history happened to make.
- Replaces in v1: the reliance on history coverage.
- Expected effect: finds any program whose recorder has a gap; K0 predicts zero for its nine programs. About 22 thousand removals times 250 questions at about 24 microseconds per recorded question is of the order of two minutes (my arithmetic).
- Test: the test is the experiment; stale count must be 0 for fact-level policies; any nonzero is a bug in a program or the recorder.
- Install: none.
- Verdict: adopt.

R4. Snapshot as memo table; temporal queries as snapshot diff; no interval store (adopt for now; revisit at about 100 times the size).
- What: keep a snapshot cache keyed by (commit, extractor version); a `since` view = diff of two snapshots filtered to a k-hop neighbourhood with hubs not expanded, ordered by distance, capped; plus the suspect-conclusion list from R1.
- Theory: DBSP stream of snapshots and differences; Datomic `since`; Glean stacking; DeltaGraph only at scale.
- Replaces: nothing in v1.
- Expected effect: the digest measured in section 7.2 (median 0 to 2 edges near one file after about 2 commits, 27 after about 8, 151 after about 31 at 2 hops).
- Test: compare token size and content against the scripted baseline `git diff --stat` between the two commits restricted to the same neighbourhood's directories, on tuning pairs; measure the share of the next commit's changed files that appear inside the digest's 2-hop set. Rejection: the digest is not smaller than the scripted diff for the same information, or contains the next changed files no more often than a recency-only list.
- Install: none.
- Verdict: adopt.

R5. Working-tree overlay in the Glean style (trial).
- What: units are files; base = cached snapshot of HEAD; changed files re-extracted and their base units hidden; derived cross-file facts (URL to route, imports) re-derived for the affected units; answers validated against the overlay.
- Theory: Glean incremental databases and ownership (Meta, page summary; the only production design on code with published overhead numbers).
- Replaces in v1: whole-commit rebuilds (about 5 s) for uncommitted edits.
- Expected effect: answers reflect the agent's own edits within seconds; only changed files are re-parsed.
- Test: random uncommitted edits to files at tuning commits; overlay result must equal a full rebuild of the edited tree (graph equality), and report time against 5 s.
- Install: none.
- Verdict: trial.

R6. Do not install a Datalog or incremental-maintenance engine (reject for now).
- Theory: Motik et al. (cross-over; "no clear winner"); K0 timings; DDlog archived.
- Conditions to revisit: a derived view the agent needs recomputes in over about one second, or growth by about 100 times. First choices then: Souffle (one-shot rules plus provenance) or Feldera (incremental).
- Verdict: reject for now; list is in section 8.

R7. Temporal features of the ranking: test only (trial).
- What: add (a) an ablation of recency decay half-life on co-change weights and (b) a "latest co-change" recency ranker; do not add time-respecting paths unless (c) a two-hop time-respecting co-change chain shows more recall than a static two-hop chain.
- Theory: HistoRank (recency vs support and confidence); Wu et al. for time-respecting paths.
- Replaces in v1: the single recency weight.
- Expected effect: small (a few MAP points in the one study).
- Test: tuning commits only, one parameter at a time, paired by commit with intervals; rejection if no improvement beyond the interval; check that confidence is not used as the primary ranker (it was worst on all ten systems in HistoRank).
- Install: none.
- Verdict: trial, low priority.

R8. Document-citation edges carry a deterministic "resolves at this commit" status (adopt; mostly exists).
- What: for each doc-to-file or doc-to-identifier citation edge, store whether the target resolves in the snapshot (the finished test already has missing_ref nodes); premises of conclusions that rest on a document are class D with the section anchor.
- Theory: context-rot's reference check (1.27 % of references stale; 23 % of repositories); lineage; Copilot's citation check.
- Test: for each of the tuning snapshots, compute the share of documents whose citations stop resolving after a commit that removes or renames their target; check that resolution flips are detected with no false negatives against a full re-resolution.
- Install: none.
- Verdict: adopt.

R9. Measure how much of agents' findings are deterministic claims (adopt; analysis only).
- What: classify about 50 findings from existing session transcripts into "expressible as one of the typed queries", "expressible with a new query", "interpretation only".
- Why: decides whether the ledger mostly holds materialised answers (revalidated for free) or mostly prose (suspect on change).
- Test: the classification is the test; report counts per class and the per-class premise count.
- Install: none.
- Verdict: adopt; no model tokens needed beyond reading.
