## 1. Short answers to the five questions

**(1) At this size, which of these ideas changes anything an agent would notice, in tokens or in seconds?**
None of the speed ideas. On the frozen-commit graph (5,460 nodes, 17,370 distinct typed edges) a whole-graph breadth-first search over a plain typed-array adjacency takes about 80 microseconds (median over 514 file nodes), a two-hop neighbourhood about 1 microsecond, and a complete 40-iteration personalised PageRank about 1.6 milliseconds (local). The slowest engine query already measured in this project took about 270 ms, which is 4 percent of the roughly 6.6 s a single model step takes (baseline from `engines_checked.json`). The cheapest representation is about 100 times faster than the relational one on bounded hops, but 100 times of a few microseconds is still not a thing a person or a model step can see. Neither storage choice, nor any index, reordering or compression, changes the number of tokens in an answer (section 6). What does change wall-clock is the NUMBER OF CALLS per question (the SQLite arm ran about 270 SQL statements per ranking and took 256 ms; one in-process pass takes about 2 ms) and cold start (LadybugDB's facts load, about 90 to 180 ms). Those are design choices about interfaces, not about storage engines.

**(2) At what size does each idea begin to matter?** Table in section 3. Short form: engine-level traversal speed differences matter from roughly 10^5 nodes with frontiers in the tens of thousands (round 1's local test: CSR 18x to 30x faster than a recursive query at 6 hops, 2.6 to 46 ms at 1M nodes); reachability and distance indexes from roughly 10^5 to 10^6 nodes and tens of thousands of point queries per second; a full transitive-closure bit matrix stops being feasible between 10^5 and 10^6 nodes (4 MB at 5.5k nodes, 355 MB at 55k, 35.5 GB at 546k); reordering and compression when the adjacency no longer fits in the processor cache (the published cases start at hundreds of millions of edges); validity-interval storage of history when snapshots times edges reaches the gigabytes (here 20 MB against 0.5 MB, so already 71 times smaller but not yet necessary).

**(3) What can "spatial topology" mean for code?** Four concrete things, each with its own representation (section 5): containment (repo, runtime, slice, directory, file, symbol: a tree, already encoded by the path in the node id), the slice and runtime quotient (58 super-nodes, 172 distinct dependency links between them: a small summary graph), cross-runtime links (typed edges, 129 dependency-kind edges cross a runtime boundary: an edge table), and closeness in import and call structure (distance in the graph: a traversal, or an index if point queries become frequent). None of the four needs a graph database; all four are tiny.

**(4) Does the storage choice affect the SIZE OF AN ANSWER in tokens?** No, with two indirect exceptions that are not storage engines. The three engines returned identical ranked answers on every seed (engine audit). Answer size is set by which items are selected (a two-hop ball has a median of 110 members; the ten-times-smaller typed one-hop answer is a different question), what is returned about each (an identifier, a signature, or the body: reading the code of a median two-hop ball is about 146,000 tokens by the project's own per-node token field, against roughly 700 to 1,800 tokens for the identifiers alone, estimated), and how it is written out (grouping identifiers by directory about halves the identifier text). The containment hierarchy is what makes that last step possible, which is the one place where "spatial" structure touches answer size.

**(5) Storage decisions worth making deliberately now.** (a) Fact identity, ownership and validity: ids that do not break when a line number moves, an owner file on every fact, and a validity interval of commits instead of a copy per commit. 736 of the 2,179 node ids that vanished between consecutive snapshots are line-number identity breaks, which would falsely invalidate cached conclusions. (b) The unit of work: one in-process call per agent question over a typed edge table that is loaded into plain arrays, instead of many statements to an engine. This is a design of the interface and costs no installation. Everything else in this document is "not at this size".

## 2. The baseline timing, explained

Baseline (`build-f/engines_checked.json`, tuning inputs only, 2,450-node and 5,464-node graphs): every query 0.3 ms to 270 ms; SQLite 14.5 and 32.7 ms for the selected ranking, LadybugDB 41.5 and 71.2, DuckDB with DuckPGQ 70.3 and 98.7; PageRank-style configurations 17 ms (LadybugDB), 58 ms (DuckDB), 256 ms (SQLite, which runs about 270 statements per ranking); question lookups about 0.3 ms (SQLite), 1.9 ms (LadybugDB), 9 ms (DuckDB); builds 0.35 to 3.7 s; identical answers everywhere.

My own measurements on the frozen snapshot (all local, JavaScript, Node 24, one machine, medians over 514 file-node sources; undirected projection of all 36 edge kinds, answers equal to the engine's set semantics, zero mismatches between SQLite and the arrays):

|---|---|---|---|---|
| 1 | 10, 35, 135 | 0.2 us | 6 us | 28x |
| 2 | 110, 405, 1,397 | 0.7 us | 45 us | 64x |
| 3 | 786, 2,099, 3,333 | 5.2 us | 484 us | 93x |
| 4 | 2,752, 4,199, 5,045 | 28 us | 2.9 ms | 103x |

- Reading: the recursive query costs about 0.3 microseconds per edge examined and the array about 0.01 (derived from round 1's 10k-node run: 8.0 ms against 0.28 ms for 5,506 nodes reached). The gap is the per-row cost of a general query interpreter against a pointer-free array scan, and it grows with the number of edges touched, exactly as round 1's table showed (29x at 10k nodes, 23x at 100k, 18x at 1M, 6 hops). This is the whole content of "index-free adjacency is faster": it is true, it is a constant factor on top of work that is already microseconds here.
- Why the engine numbers are 10 to 1,000 times larger than those microseconds: they time a complete ranking (a 40-iteration spreading over the whole neighbourhood, with fetches, conversions, process hops) and, for SQLite, about 270 statements per ranking. A comparable 40-iteration power iteration over the whole graph in plain typed arrays took 1.64 ms median (p90 1.93, max 3.13), 2.84 ms with a full sort for the top 20 (local). The LadybugDB arm's 17 ms for its PageRank configuration is about 10 times my figure; I did not inspect its code, so I do not claim why. The audit already says the three arms do not isolate a graph operator, and this agrees.
- Four orders of magnitude of difference between a bare traversal (0.1 to 100 us) and the slowest measured query (270 ms) is per-call overhead and application code, not graph storage. That is the theory-backed explanation of why "three storage engines gave the same answers" and why speed differences between them were inside noise for the selected configuration.

## 3. Technique by technique: what the literature says, what I measured, where it starts to matter

Scale facts for this graph (frozen snapshot, local): 5,460 nodes; 17,370 distinct (source, destination, kind) edges after dropping dangling ones; 36 kinds in use. The engine audit loaded 5,464 nodes and 16,462 edges of the frozen graph; I did not reconcile the difference. Adjacency as plain arrays: 31,292 arcs undirected = 147 KB; 16,662 arcs forward = 88.5 KB; 7,937 arcs for the dependency-kind subset = 53.6 KB (4-byte ids plus offsets). The exported node and edge files hold 1.9 MB and 5.2 MB: the properties (signatures, evidence, attributes) are 98 percent of the bytes, adjacency is 2 percent. Undirected degree: mean 5.7, median 3, 99th percentile 43, maximum 134 (a test file); 28 percent of vertices with an edge hold 67 percent of edge endpoints, against 9 to 26 percent of vertices holding 80 to 94 percent in the web and social graphs of Faldu et al.: this graph is much less skewed, which matters for every hub-based technique below.

### 3.1 Physical designs for adjacency

Designs: (a) index-free adjacency, where each record holds direct pointers to its neighbours (Neo4j's record chains; Besta et al. list direct pointers as the optimisation that avoids maintaining an index for traversal, and note it makes relocating records costlier); (b) compressed sparse rows (CSR), two integer arrays with offsets (LadybugDB and Kuzu use CSR-style join indices next to columnar storage; the FalkorDB engine stores adjacency as sparse matrices); (c) an edge table in a relational engine with a covering index in both directions.

What the measurements show, by size (all taken from sources, none re-run by me except where "local"):

- Lookups and one to two hops: tie or relational slightly ahead on 3 GB to 10 GB benchmark data (Pacaci et al. 2017, round 1, medium: old engine versions) and on LDBC scale factor 100 for one-hop (Kuzu CIDR 2023, DuckDB won one-hop; medium). Local: SQLite 6 us against 0.2 us on one hop.
- Frontiers of tens of thousands of nodes, many hops: CSR 18x to 30x faster than a recursive query (round 1 local, 10k to 1M nodes; medium; 29 to 148 times on this graph).
- Selective multi-hop joins at 100 million edges and above: graph-style plans 5 to 100 times faster than plain relational plans, while with weak filters hash joins win (Kuzu CIDR 2023, round 1; medium). GRainDB (round 1) put row-id join indexes into DuckDB and cut median time 3.6x on JOB and 22.5x on LDBC SNB: giving a relational engine the graph access path closes most of the gap (medium).
- Folklore versus controlled measurements: a quoted "friends of friends, one million users, 2 ms against days" claim (Adell 2013, via Hohenstein and Jergler) is contradicted by Hohenstein and Jergler's own PostgreSQL run on 500,000 nodes with 50 edges each, a five-way self-join: no index 59.7 s warm, with index 4.5 s warm (13x from one index); and by a 2015 comparison they cite in which MySQL was about 6 times faster than Neo4j at 5 hops. Weak to medium (one lab, one query shape, laptop, default configuration of a 128 MB cache). Vicknair et al. (2010; 1,000 to 100,000 node random DAGs, MySQL 5.1 against Neo4j 1.0) saw Neo4j faster on bounded-depth traversal, "sometimes by a factor of 10" in the authors' words, with times of a few to a hundred milliseconds, but their MySQL arm issued one SELECT per visited node from a Java client: the difference is round trips (weak). Lissandrini et al. (VLDB 2018; up to 76M nodes and 314M edges; Neo4j, OrientDB, Sparksee, Titan, ArangoDB, BlazeGraph, and PostgreSQL through Sqlg) found the relational-backed system "significantly" worse on traversals, BFS and shortest path, and best on 1 to 2 hop queries with edge-label filters; their relational arm translates Gremlin to joins (medium). The published results therefore split by implementation of the relational arm and by size, not by "graph versus relational".
- Storage size: relational stores were smaller than native graph stores for the same data in two independent studies (Pacaci SF3: Neo4j 20 GB, PostgreSQL 11 GB; Vicknair: Neo4j 1.25 to 2 times MySQL at 1,000 to 100,000 nodes); a specialised compact layout beats both (Joern flatgraph 625 MB against OverflowDB 2,555 MB, round 1, from the project's own benchmark page). "A graph database holds relations in a small size compared to a relational one" is not supported by any source I found.

Applies at this size: no effect an agent can see. At 10 times (55k nodes): still microseconds to a few milliseconds per bounded query; at 100 times (546k nodes) a whole-graph traversal is about 49 ms in my synthetic test (section 3.8) and a six-hop SQL query would be seconds, which is the first point at which an in-process array would be worth having over an engine for that query class.

### 3.2 Reachability and distance indexes

Definitions: a reachability query asks whether a path exists from s to t; a distance query asks how long the shortest path is. A transitive closure stores the answer for every pair (O(1) query, O(n squared) space in the worst case). A "2-hop" or labelling index gives each vertex a small set of "hub" vertices with distances, so that distance(s,t) is the minimum over the hubs both share (Cohen et al. 2002, the basis of the following). Pruned landmark labelling (PLL) builds these labels with breadth-first searches from vertices in order of degree, cutting a search wherever existing labels already give the distance. GRAIL gives each vertex d random interval labels from d depth-first traversals of the condensed graph: a pair is definitely not reachable if its intervals are not nested; if they are, a pruned search decides.

Published evidence:
- PLL (Akiba et al. 2013; eleven real graphs, 63k nodes and 148k edges up to 7.4M nodes and 194M edges; undirected, unweighted; medium: the authors' own experiments, a widely used method whose replication I did not check): average query times 0.5 to 16 microseconds, preprocessing from seconds to about 4 hours (15,164 s for the slowest), index sizes from tens of MB up to about 22 GB, against a plain BFS at 3.2 ms (smallest graph) to 1.5 s (largest). Their own condition: small-world networks with strong hubs; road networks are a different case. The smallest graph in the study has about 12 times as many nodes as this one.
- GRAIL (Yildirim et al. 2010; weak to medium; their own experiments): the abstract says more sophisticated methods work better on small graphs and GRAIL is the one that scales to millions of nodes; the authors write that depth-first search is "quite attractive" on their small datasets (graphs of roughly ten thousand nodes and up) because it costs nothing to build, and report GRAIL 2 to 20 times faster than plain DFS on small dense graphs and 2 to 27 times on large real ones, with query times given as totals for 100,000 queries.
- The 2025 survey (Zhang, Bonifati, Ozsu; 33 techniques; survey, no new experiments; medium): partial indexes without false negatives, such as BFL, are preferred because most real queries have the answer "no" (the reachability ratio is low); example given: 3 million vertices and 16 million edges, index built in 1.3 s, 132 MB, 0.26 microseconds per query; for dynamic graphs, 2-hop indexes are the more suitable family because they do not need strongly connected components maintained, tree-cover and interval methods remain an option only for graphs that stay acyclic with infrequent updates; designing partial indexes for dynamic graphs "remains an open challenge".

Local measurements on this graph (the dependency-kind subset is acyclic: all 5,460 strongly connected components are single nodes; the all-kinds forward graph has one component of 433 nodes):

| structure | result |
|---|---|
| closure of the dependency subgraph | 110,086 reachable ordered pairs = 0.4% of n squared; bit matrix 3.6 MB; built in 3.5 ms; median node reaches 2 nodes, p90 70, max 454 (all nodes as sources) |
| closure of all-kinds forward graph | 2,815,443 pairs = 9.4%; 3.1 MB bit matrix; 7.7 ms; file-node sources reach a median of 4,328 nodes |
| GRAIL (condensed dependency graph; 200,000 random pairs, 0.36% reachable) | share of the "no" pairs answered by labels alone: 83.4% (d=1), 89.7% (2), 93.3% (3), 95.5% (5); build 3 to 6 ms; 2 x d x n numbers stored |
| point reachability query | closure lookup 0.07 us; plain BFS with early exit 0.4 us (dependency graph), 3.8 us (all-kinds forward) |
| PLL, undirected all kinds | 70 ms to build; 191,459 label entries, 35 per vertex (max 93); about 935 KB at 5 bytes per entry, which is 6.5 times the size of the adjacency it speeds up; query 0.65 us against 41 us for BFS with early exit; zero disagreements with BFS on 2,000 pairs |

Reading for this use case:
1. These are all point-to-point indexes. The agent's questions ("what is connected to this", "what breaks if this changes") are single-source questions that need the whole set of reachable nodes and a ranking. For a single source, one BFS (80 microseconds) is the optimal algorithm; asking an index for all 5,460 targets takes 5,460 x 0.65 us = 3.5 ms, 40 times slower than the search it was meant to replace.
2. Reach sets of the dependency subgraph are tiny (median 2 to 5), so even a materialised sparse closure only helps if the same question is asked tens of thousands of times a second. A closure is O(sum of reach sizes), not O(n squared): at 110,086 pairs it is under 1 MB as pairs.
3. Where an index pays off, by the sources: when BFS cost per query exceeds a few milliseconds AND the same graph answers many point queries. BFS here is 80 us. The crossover for PLL in its own paper is the smallest graph it uses (63k nodes, BFS 3.2 ms against 0.5 us); for GRAIL "DFS is attractive" below tens of thousands of nodes. My synthetic scale test (section 3.8): whole-graph BFS is 1.2 ms at 55k nodes and 49 ms at 546k, so a distance index starts to matter between 10^5 and 10^6 nodes, if point queries are what is asked.
4. PLL is hub-dependent: on this repository's real graph it needs 35 entries per vertex; on a synthetic preferential-attachment graph of the same mean degree and no code structure it needed 63 at 5.5k nodes and 230 at 54.6k (59.9 MB, 36 s in my unoptimised JavaScript, no bit-parallel search), because that graph has few shortcuts via hubs. Index size grows with how hub-poor the graph is, which is a property of the schema (this graph is less skewed than web graphs, see above), not only of size.
5. Dynamic updates: edges are added more often than removed in the history (median 60 added, 3 removed per commit), which suits insertion-only indexes (DBL) in theory, but the removals that do occur (p90 67, max 789) are the hard case. Hanauer et al. 2020 (medium; fully dynamic single-source reachability, several algorithm families, real and generated graphs, C++) found plain static BFS and DFS recomputation, even with caching and laziness, could not compete with the best dynamic algorithms on their instances, and that all algorithms benefited from falling back to recomputation past a threshold. Earlier all-pairs studies cited there (graphs up to 700 vertices) found the opposite: simple static search beat the dynamic algorithms. Nothing in that literature addresses graphs of a few thousand nodes with a full rebuild that takes 25 ms.

Verdict at this size: no reachability or distance index. Do not build transitive closures, GRAIL labels or PLL.

### 3.3 Labelling schemes for hierarchies (the concrete form of "inside" and "ancestor of")

Theory: number tree nodes by a depth-first walk (preorder rank and postorder rank); then v is a descendant of u exactly when pre(u) < pre(v) and post(v) < post(u): constant time, a rectangle query in the plane of (pre, post) (Dietz 1982 is the origin I could not open; Grust, van Keulen, Teubner built the XPath accelerator on it, which "can be implemented and queried using well-established relational index structures, notably B-trees and R-trees" and covers all XPath axes). Agrawal, Borgida and Jagadish (SIGMOD 1989; abstract only) extended interval labelling to compress the transitive closure of DAGs. A second family writes each node's path from the root as its label (Dewey or materialised path; PostgreSQL's `ltree` type indexes it with B-tree, hash or GiST and gives ancestor and descendant operators; documentation level only). In a relational engine without these, "is inside directory D" costs a recursive query.

Local: the repository's node ids already are materialised paths (`file:backend/app/features/jobs/service.py`, `sym:...#name`). 5,399 of 5,460 nodes carry a path; the path tree has 646 vertices (105 of them with children), maximum depth 6. An ancestor test with pre/post integers took 8.1 ns, with a path-prefix string compare 16.6 ns, in 2 million random pairs, and they agree. In SQLite, a prefix scan on a text primary key is an index range scan if the column is indexed with the BINARY collating sequence and `GLOB`, or `LIKE` with `case_sensitive_like` on (SQLite's optimiser documentation, section 5, via summarising fetch); the default case-insensitive `LIKE` does not use a binary index, which is a trap worth knowing.

Verdict: the containment hierarchy is already encoded for free by the id; adding interval columns changes nothing at 646 tree vertices. They begin to matter only if the hierarchy is stored in a relational engine as parent pointers and the ancestor query must avoid a recursive join over tens of thousands of nodes, or when rewriting numbers on every insert is cheap (it is: the tree is rebuilt from paths per commit).

### 3.4 Reordering and compression for locality

Theory: relabel vertices so that neighbours get nearby ids, which (a) puts related adjacency in the same cache lines and (b) makes gaps between neighbour ids small and cheap to code. WebGraph (Boldi and Vigna 2004; medium, a primary compression study) reaches 3.08 bits per link on a 118-million-page, one-billion-link web graph, and 2.89 for its transpose, mostly by exploiting the lexicographic URL ordering (consecutive pages link to nearby pages). Faldu et al. (2019; medium, real machine, 40 application and dataset combinations; 25 MB last-level cache) found lightweight reordering gave 16.8 percent average speed-up for their best method against 11.6 percent for the best earlier one, on graphs of 18 million to 64 million vertices and 172 million to 2.1 billion edges, where the "hot" vertices alone needed 9 to 230 MB of cache; they also show reordering can destroy community structure and lose the gain, and the most thorough method (Gorder) is too slow to be practical. Balaji and Lucia's slides (35 MB cache machine) conclude that reordering pays only if the preprocessing is amortised over enough runs and the graph has skew.

Local: path-and-line order gives 9.66 bits per arc with Elias-gamma gap coding, the order the extractor already writes gives 10.39, a random order 18.21, reverse Cuthill-McKee 11.65, degree order 14.18, against 32 bits plain: the filesystem order is the locality ordering here, as the URL order was for the web, and ignoring it costs 1.9x in coded size. But the whole forward adjacency is 65 KB plain and 20 KB coded, so this is a saving of 45 KB. The adjacency of a graph 100 times bigger (546k nodes, 14.6 MB) still fits in the last-level cache of an ordinary desktop processor; the published cache effects start where the working set exceeds 25 MB by a factor of ten.

Verdict: not at this size, not at 100 times. Keep the extractor's file-order numbering (it already is the good ordering) and do not add a reordering step. It begins to matter around 10^7 or more nodes.

### 3.5 Materialised views and caching of traversals

Theory: store the result of an expensive derived relation and keep it correct as the base changes. Counting and DRed (Gupta, Mumick, Subrahmanian 1993; abstract-level): count derivations for non-recursive views; for recursive views delete a superset then re-derive. Build systems' "early cutoff" (Mokhov et al.; abstract-level) stops propagating a change when a rebuilt intermediate result equals the old one. Glean (documentation, no timings; the one production code-fact store I read about) records for every fact the set of "units" that own it (recommended: one unit per file or module, about 10 to 100 times more facts than distinct ownership sets), hides all facts of excluded units to build an incremental database on top of a base one, and makes a derived fact visible only if all the facts it was derived from are visible.

Local: a bounded traversal costs 0.1 to 100 microseconds; the closure of the dependency subgraph (the only candidate "view") builds in 3.5 ms. The cost of rebuilding EVERY index from scratch for a snapshot (three adjacency structures, strongly connected components, closure, GRAIL, PLL) was a median 25 ms (p90 45, max 61) over all 190 cached snapshots, against about 5.3 s to extract the facts of one commit (`build-b/facts-NOTES.md`, cited in `widen/critique-assumptions.md` line 156): indexes are 0.5 percent of the cost of producing the facts. So a cache of traversal results has nothing to save, which agrees with the finding of the earlier research that "a cache over traversal has nothing to save" for cheap facts. What costs tokens, and so is worth caching, is a CONCLUSION produced by a model step; the correctness mechanism for that (dependency sets, ownership by file, early cutoff) is what the Glean design and the build-systems theory describe, and it is the decision in 4(a) of section 7.

### 3.6 Temporal storage and identity

Three common designs: a full copy per snapshot; deltas plus occasional full snapshots (the DeltaGraph family, not read here); one record per fact with a validity interval. Local over the 190 cached snapshots (237 nodes and 800 edges at the first, 5,464 and 18,875 at the last): 1,737,146 edge records if every snapshot is stored in full; 21,748 distinct typed edges; 24,579 validity intervals (an edge that vanishes and returns counts twice). Interval storage is 71 times fewer records: about 20 MB against 0.5 MB at 12 and 20 bytes a record (my assumed record sizes). Per commit, edges added: median 60, p90 388, max 1,039; removed: median 3, p90 67, max 789; nodes added median 17, removed median 1; total change is about 0.9 percent of the edges.

Identity is the bigger finding. Of the 2,179 node ids that disappeared between consecutive snapshots, 736 (34 percent) are ids that embed a line number (`sec:<path>#L<line>` for document sections, `urlsite:<path>:<line>:...` for client URL sites) while a node with the same kind, path and name appears in the same step: the thing did not change, its address did. Counting them as deletions and additions fragments every validity interval of an edge that touches them, and would invalidate any cached conclusion that depends on them. (This is an upper bound: names are not always unique.) By kind, vanished ids are document sections 492, functions 419, client URL sites 357, tests 193, files 163.

### 3.7 Graph engines at small scale: what the benchmarks do and do not say

All results above agree on one thing: at up to a few million edges, engine choice changes latency by milliseconds, and the direction depends on implementation details of the weaker arm (indexes, round trips, cache size). Round 1 recorded LDBC-shaped benchmarks at 17 million edges where most queries tie within 1 to 5 ms and the slowest engine takes 1.4 s on one query of thirty. No source I found tests a code-shaped graph (imports, calls, tests, documents, history), and none measures agent tokens. The Joern code-analysis precedent is that general-purpose graph databases were replaced by a purpose-built layout because of memory, not latency (round 1, snippet level; the Joern documentation page I opened describes only a Neo4j-based older setup and gives no reason).

## 4. Crossover summary: where each idea starts to matter

| idea | benefit at this size (5.5k nodes) | where the literature or my scale test puts the crossover | at 10x (55k) | at 100x (546k) |
|---|---|---|---|---|

## 5. What "spatial topology" can mean for code, and which representation serves each

1. Containment ("is inside"). Repository, runtime, slice, directory, file, symbol. A tree (here 646 path vertices, depth 6, 105 directories). Representation: the path in the id (a Dewey label); optional pre/post integers if a relational ancestor query is needed. Query cost: a range scan or a string prefix; 8 to 17 nanoseconds per test in memory.
2. Slices and runtimes (the architecture map). The quotient graph that merges nodes by (runtime, slice): 58 super-nodes (runtime sizes: backend 2,827, mobile 1,201, docs 582, web 548, ops 239, repo 38); 569 distinct slice-level links over all edge kinds, 172 over dependency kinds; 31.3 percent of all edges and 29.3 percent of dependency edges cross a slice, 11.2 and 1.6 percent cross a runtime. Written out as adjacency text, the dependency map is 38 lines, 3,243 characters, about 800 to 1,100 tokens (estimate, no tokenizer offline). Representation: a materialised GROUP BY view, valid until an edge's slice endpoints change. The import-linter contracts in the repository are the same idea in another form: a partial order or independence relation on slices.
3. Cross-runtime and cross-capability links ("where the other half of a contract lives"). Typed edges that cross the boundary, by the share of each kind that crosses a runtime: URL-call-to-route (`calls_url`) 91 percent of 77, `constrains` 100 percent of 85, `same_capability` 100 percent of 24, `cites` 82 percent of 496, `mentions` 76 percent of 1,233; `test_calls_route` 11 percent of 376. Representation: an edge table with an index on (kind, source) and (kind, destination), or per-kind arrays; every query is a one-hop, microseconds to read, a handful of nodes to return.
4. Closeness in import and call structure. Distance and neighbourhood. Observation about v1 itself, not about storage: `calls` edges run from a file to a symbol, not symbol to symbol, so the dependency-kind subgraph is acyclic and shallow (median reach 5 nodes at any hop count, p90 38, max 454, forward; 3, 30, 120 for dependents from file nodes), while the all-kinds undirected graph reaches half of all nodes by 4 hops (median 2,752) and nearly all by 6 (5,381). That is why the k-hop retrieval needs ranking: not because traversal is slow, but because the neighbourhood is the whole repository. Representation: arrays for traversal; no index.

## 6. Does the storage choice change the size of an answer in tokens?

No. Three layers set the size, and none of them is the engine:
- Selection. The two-hop ball over all edge kinds around a file has a median of 110 members (p90 405); the typed one-hop dependency neighbourhood has a median of 2. Choosing the question and the cutoff changes size by about two orders of magnitude.
- Representation of each member. Per-node token field in the exported graph: median file 686 tokens, p90 2,754, max 140,607; summing it over the median two-hop ball gives about 146,000 tokens (p90 437,000), though this double counts a file and its symbols. Identifiers alone: mean id 62.5 characters, so the median ball is 5,404 characters, roughly 1,350 to 1,800 tokens at 3 to 4 characters per token (my estimate; there is no tokenizer offline, so use the model's own count before trusting it).
- Serialisation. Same ball, same content: one full id per line, 5,404 characters; grouped by path (path once, then names), 4,180; front-coded by directory (directory once, then file, then symbols), 2,876 (median ratio to full ids 0.51). So a 49 percent reduction of identifier text comes from the containment hierarchy used as a compression dictionary (the same locality principle as WebGraph, applied to text). Whether it changes accuracy is a separate question: the literature says the text encoding of a graph matters (Fatemi et al., abstract: choosing a suitable encoder changes graph reasoning performance by 4.8 to 61.8 percent depending on the task; "Lost in Serialization": models are not invariant to node relabelling, edge reordering or formatting; abstract-level, weak for this use because those are small synthetic graph tasks).
- Disk size is a different thing: adjacency is 2 percent of the exported bytes; the three stores (SQLite 4.5 MB, DuckDB 16 MB, LadybugDB 15.5 MB on the 2,450-node tuning graph, with different extra tables) differ in properties and indexes. None of that reaches the model.

Indirect routes that do exist: a store that can answer a narrower, typed question cheaply lets the agent ask it (a design effect through the schema, not through physical layout); and ids that are human-readable paths let a front-coded answer exist. Both are in section 7.

## 7. Recommendations

Each has: what, theory, what it replaces, expected effect, test on tuning data that would show it does not help, installation, verdict. The owner decides on installs; every item below needs none unless stated.

**R1. Stable fact identity, ownership and validity intervals (storage decision a).**
- What: (i) node ids built from stable keys (kind, path, name, plus an ordinal only where names collide), with line numbers as attributes; (ii) an `owner` (the extracting file or files) on every edge and node; (iii) `valid_from` and `valid_to` commits on every fact instead of a stored copy per snapshot; (iv) every cached conclusion stores the set of facts it read.
- Theory: Glean's ownership units (one per file) and visibility rules; early cutoff from build systems (stop when a rebuilt result equals the old one); validity-interval storage from temporal databases (interval encoding; here 71x fewer records).
- Replaces: line-number-bearing ids (`sec:...#L12`, `urlsite:...:348:...`) and the snapshot-per-commit cache keyed by commit.
- Expected effect: removes up to 736 of 2,179 spurious vanishings over the 189 steps (34 percent of id churn) and the false invalidations they cause; reduces 1.74M edge records to about 25k. No token effect on a fresh answer; it is what lets a cached conclusion survive an unrelated commit.
- Test on tuning data: replay the 190 snapshots; for each commit count conclusions invalidated under (a) current ids, (b) stable ids, (c) file-hash keys; the idea fails if (b) does not reduce invalidations by a third or more, or if more than a few percent of stable keys collide (name collisions inside a file).
- Install: none. Verdict: adopt.

**R2. One in-process call per question over arrays built from the fact table (storage decision b); engine choice is not a lever.**
- What: load the typed edge list into forward and reverse arrays grouped by edge kind at session start (a CSR, 0.15 MB, built in 4 ms median), compute the ranking in one pass, return the cut-off list; keep SQLite (or the existing Postgres) as the system of record. Index the edge table on (kind, src, dst) and (kind, dst, src) for typed one-hop queries.
- Theory: index-free adjacency or CSR gives a constant factor on traversal (28x to 148x measured here); per-statement overhead dominates small queries (270 statements = 256 ms in the SQLite arm); round 1's local bench and GRainDB show the factor comes from the access path, not from the product category.
- Replaces: ranking implemented as many statements to an engine; three-engine comparison as a research axis.
- Expected effect: per-ranking time from 14.5 to 98.7 ms (selected configuration, engine arms, tuning and frozen graphs) to the order of 2 to 3 ms for a comparable pass (my 40-iteration loop, not the exact configuration); no token effect; avoids LadybugDB's 90 to 180 ms cold load. Seconds saved per task are in the tens of milliseconds, so this is justified by simplicity, not speed.
- Test: add a typed-array arm to the existing interleaved engine bench on the tuning seeds; require identical ranked answers on all 200 seeds; if the arm is not at least 5 times faster than the best engine arm on the frozen primary, drop it as pointless. The agent test decides whether any of it is visible.
- Install: none (plain typed arrays in Node or Python's numpy, both already present). Verdict: adopt as implementation detail only if the agent harness actually pays for per-call latency; otherwise no change.

**R3. Containment-aware answer format (front-coded by directory).**
- What: serialise any list of nodes as directory, then file, then symbols, instead of one full id per line; for graphs of the architecture map, group by slice.
- Theory: WebGraph's locality and front coding of sorted keys; the containment tree as a dictionary. Evidence: local, 49 percent fewer characters (median) on 514 two-hop balls.
- Replaces: one full id per line.
- Expected effect: about half of the identifier tokens in an answer made of ids; from the estimate, 1,350 to 1,800 tokens down to 720 to 960 for a median two-hop ball.
- Test: re-serialise the tuning-set answers in three formats and count tokens with the real tokenizer; then run the same agent task with each format; it fails if accuracy drops by more than the noise of the agent test, or if real-token savings are under 20 percent.
- Install: none. Verdict: trial (cheap, only token-relevant item in this lane).

**R4. Slice quotient as a precomputed map view.**
- What: materialise the 58-node slice and runtime graph with typed counts, refreshed per commit (it is a GROUP BY).
- Theory: graph summarisation and containment quotients; the import-linter contracts as a partial order.
- Replaces: nothing in v1 (new); adjacent to summary-based retrieval covered by another lane.
- Expected effect: a whole-repository dependency map in about 800 to 1,100 tokens (estimate); whether it saves agent search tokens is untested.
- Test: give agents the map or not on the same tasks; it fails if search tokens do not fall.
- Install: none. Verdict: trial, owned jointly with the summaries lane.

**R5. Do not build: closure tables, GRAIL, PLL, reordering, compression, incremental index maintenance, a graph database for speed.**
- Reasons and numbers: sections 3.2 to 3.5. Each is a point-to-point or all-pairs structure that does not serve a single-source ranking; each saves microseconds on a rebuild-everything budget of 25 ms against 5.3 s extraction; each starts to matter at 10^5 to 10^7 nodes.
- Re-open when: nodes pass about 10^5 and a question needs thousands of point queries; or a six-hop query is required on a million-node graph; or snapshots times edges pass several gigabytes. The test then is the same replay on a larger repository: time the bounded query against its index at that size.
- Install: Ladybug (MIT, wheel 5.8 MB, round 1), DuckDB with DuckPGQ (15.4 MB, 2.0.0), Neo4j (JVM server, GPL, 380 MB image) all remain unnecessary at this size; if ever needed, DuckDB runs offline on Linux in a container. Verdict: not at this size.

## 8. What the earlier rounds missed or got partly wrong in this area

- Round 1 treated storage as a speed contest and never connected speed to the agent's seconds or tokens. Its own numbers (latency under about 10 ms is irrelevant against a 6.6 s model step) already imply the answer, and the engine bench confirmed it, but the research recommended work (precomputed closure or "dependents within k" tables for hot files, per-edge-kind reverse adjacency) whose benefit is zero here: the closure of the dependency subgraph is 110k pairs and a BFS over it is 0.1 microseconds.
- Round 1 did not cover reachability and distance indexes, interval or prefix labelling, reordering and compression, validity-interval storage, or identity stability. This lane found that the largest storage-related risk is not speed or size but identity: a third of vanished ids are line-number address changes.
- Round 1 reported that reachability within 1 to 3 hops is as fast with a covering-index recursive query as with its CSR. My run on the real graph finds arrays 28x to 93x faster at 1 to 3 hops (6 us to 484 us against 0.2 us to 5 us). The main reason is probably the one round 1's own caveat names: its CSR baseline allocated an O(N) "seen" array for every query, which inflated CSR at large N; mine reuses a stamped array. A second difference is the graph: round 1's was synthetic with 5 edges per node, here hubs make 3-hop reach 786 on median. Both agree that in absolute time the SQL query is half a millisecond at three hops.
- Round 1 marked the Joern precedent as snippet-level; the page I opened gives no migration reason. It remains snippet-level.
- The second round's "cache over traversal has nothing to save" is right for traversal and the replay result stands; the storage-level corollary (ownership by file, stable ids) was not drawn, and the id problem was not seen.
