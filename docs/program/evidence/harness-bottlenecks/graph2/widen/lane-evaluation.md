# Lane: evaluation designs (2026-11-13)

Question: how do we measure what a knowledge graph is for, without the flaws of the finished test?

Reading rules used here. Every source line says who measured, on what, against what, and a strength mark: STRONG (independent, controlled), MEDIUM (peer-reviewed or preprint by people with no product to sell, but small or not replicated), WEAK (self-reported by the tool's authors, a vendor blog, a search-result summary I could not confirm in the paper text). A star count is adoption, not evidence of effect. Numbers marked "MY CALCULATION" are mine, with the assumptions written next to them, and are not from any source. Dates: today is 2026-11-13; the arXiv numbers below are as the pages showed them.

---

## 0. Where the owner is right and where he is not (evaluation lane only)

Right:
1. The finished test scored "which other files did this commit change". That is co-change. Its own verifier said so before the run (research/critic.txt, "Truth circularity"; research/lane-scoring.txt). Context a change needs but does not edit earns zero. The test ran no agent (protocol-addendum-6.md items 19 and 20 say so themselves). So it cannot say whether a graph lowers tokens, turns or mistakes for an agent. It also dropped the recorded-session lookups (protocol-addendum-4.md item 7: T5 not run because the seeds are free text).
2. The headline numbers of the popular tool he names measure something other than what he asked. See section 1, row G1.

Not right, or not shown:
1. The finished test is not evidence that "graphs fail". Its own addendum 6 item 9 forbids that sentence. It showed: three engines on the same facts and the same method return the same answers; a typed store beat a scripted search by 0.076 recall; a community prior added 0.015 with an interval that includes zero. Those are results about stores and one ranking tweak on one label, not about agents.
2. The independent evidence that a graph helps a coding agent is thin and mixed (rows C1 to C3 below). Most positive numbers come from the tools' own authors, on small sets, with one run per task. A fair reading is "not tested properly yet", on both sides.

### Other facts used
- Non-determinism of model-built graphs: one multi-layer knowledge graph paper (arXiv 2609.11493, search snippet only) repeated entity extraction on the same chunks at temperature 0.2 and got 94 entities in one run and 91 in another; another snippet reports the strongest graph builder tested produced correct tuples 68 percent of the time (arXiv 2603.14828 snippet). WEAK, snippets only.
- Trace replay: NVIDIA's Dynamo documentation says static replay of a recorded agent trace reuses the captured request schedule, does not re-decide tool use, and tells readers to capture a new live run when a changed response would choose a different tool or branch (https://docs.nvidia.com/dynamo/agents/agent-simulation). It is about serving load, not tool quality, but the limit applies to us: a replay cannot show what an agent would have done with a different tool. MEDIUM as a statement of limits.
- LLM judge bias (position, verbosity, self-preference, prompt sensitivity of code judges) is documented in several sources found by one search (e.g. arXiv 2410.02736 "Justice or Prejudice"; a 2026 code-judge study arXiv 2604.23178); I did not open them. WEAK-MEDIUM. SWE-QA used five-pass majority voting and anonymised, shuffled order as the mitigation.

## 2. Task designs (answer to part 1)

The repo has: about 230 commits (233 non-merge on main; 140 usable T1 commits; 126 with code and tests; 96 that change an existing test; 29 fix commits with at least 2 code files; research/lane-scoring.txt), about 1,050 recorded session transcripts with 181 search-then-read pairs (139 distinct, 26 on product code), a CLAUDE.md invariants document, and handoff and lifecycle-audit documents that name defects and their fixes (73 documented items, 36 connecting 2+ files, about 10 to 12 mapped to a fix commit). The 75 held-out commits of the finished test are now spent for any design that uses the same tuning knowledge; they are usable as development material for new label kinds, not as a clean final set (section 5).

The arms for every live design are the same: A0 the agent's own default tools (search and read); A1 plus a typed-store tool API (neighbors, impact, path, explain, search); A2 plus a model-built knowledge graph or summary layer indexed at the parent commit; A3 (headroom only) A0 plus the gold context handed over; and a placebo A0p that adds a tool with equal description size that returns nothing useful, so "any extra tool or seed" is separated from "this graph" (Agent Retrieval Bench's random non-gold seed arm plays the same role; B3).

### D1. Replayed commits, live agent, paired ablation (primary; credits orientation and needed-but-unchanged context)
- Template: C2's on/off ablation, B2's context labels, B3's edit2ripple, comment2context, trace2code rules.
- Tasks: 40 commits drawn from the 96 that change an existing test and whose tests can be run at the parent (not verified: whether backend integration tests and mobile Jest can run at old parents; this needs a feasibility run first). Task statement written from the commit subject and body by someone who has not seen the diff, as if before the fix. Environment: single-commit checkout of the parent, no `.git` history, no network, the live working tree not mounted (K1, K2; and see section 3, leak L2).
- Reference, built before any arm runs and sealed, three layers:
  1. Edited layer: existing files and definitions the commit changed (what the finished test used).
  2. Needed-but-unchanged layer, from five sources, each kept as its own column so results can be split by label source: (a) tests that fail when the commit's production diff is applied without its test edits (TEBench stage construction, B6); (b) files that a recorded session of that very commit opened and then reasoned about or cited without editing (CATM-style follow-on rule, B8); where no session exists the column is empty, not guessed; (c) files edited by a follow-up fix to the same area within a fixed window (14 days, my choice) because that fix is direct evidence the first change missed them; the lifecycle-audit documents record exactly such cases; (d) invariants in CLAUDE.md, as it stood at the parent, whose anchor symbols the diff touches, scored as "cited or not" in the agent's final change note; (e) a sufficiency check as in B2: a fixed model given only layers 1 and 2 plus the task must pass the tests; where it fails, a human adds what is missing and the item is flagged.
  3. Outcome layer: the hidden tests pass or fail, run by script.
- Primary outcome: tokens to a passing change (see section 3). Guard outcome: pass rate must not be worse by more than a stated margin. Secondary: share of layer 1 and layer 2 files opened before the first edit; share of opened files in no layer (waste); number of invariants cited; times the agent acted on wrong or stale tool output.
- What it credits: a graph that points the agent to the caller it must not break, to the contract, to the test that will fail, earns recall in layer 2 and fewer turns; a graph that only returns co-edited files earns nothing extra over A0, which is the honest reading of the finished test.

### D2. Break-oracle impact questions, execution-derived reference (credits "connections that will or won't break with changes"; cheap, no agent needed for the first pass)
- Template: B7 (mutation or injected-change impact sets) and B6's three-version staging.
- Tasks: 60 to 100 real production diffs from past commits, plus injected small changes of fixed kinds (rename a route field, change a response shape, change a function's return type, change a setting key, drop a column) made by script. Each is "if this is changed, what else must change or will break".
- Reference: apply the change at the parent and run, by script, the repo's own checkers: the test suites, mypy strict, the TypeScript compiler, import-linter. The impact set is the failing tests, the files with type errors, and the violated contracts. This is independent of the extractor that the graph arms use, which removes the circularity the earlier verifier warned about. Add the control "changes that break nothing" (about a third of tasks) so a tool that always returns many files is penalised.
- The agent or tool may not run the checkers (otherwise the answer is trivial). Answer scored as precision, recall and F1 within a token budget (4k, 8k, 16k), file-level and definition-level.
- Limits: test suites miss breakage (one snippet reports 47 percent and 35 percent detection of direct and indirect artificial faults, unverified), so recall against this reference is a lower-bound-type measure; contracts that live only in documents (invariants) are not covered, so D1's layer 2(d) covers them. Cross-runtime coupling (response-schema field to the client key) is invisible to mypy and tsc; there the reference needs a contract test or a hand check.

### D3. Trace replay of recorded session lookups (screening only; costs no agent tokens)
- Template: ARB's "logged agent context selection" and TraceProbe's anchor idea; Dynamo's replay limits.
- Tasks: the 181 recorded search-then-read pairs (139 distinct), including the 27 free-text lookups the finished test dropped. A fixed text-to-seed step (the same rule for every arm, written and frozen first) turns each recorded query into a seed.
- Label: the file the agent opened next, kept only if it was then edited, cited or reasoned about within the next 6 calls (CATM-style rule, B8). Many lookups are opens of programme documents (106 of 181), not product code (26); those test the document-store question, not the code graph, so report them as separate strata.
- Measures: whether the used file is in the tool's answer at 2k and 4k tokens; tokens of the recorded tool results the agent actually received (taken from the transcript) against the tokens the tool answer costs.
- Honest limits: it is a counterfactual on a recorded path; the agent's next step would have differed with a different answer (Dynamo guidance); the label is "what a past agent read", which ARB shows misses gold in 27 to 35 percent of samples; docs/programme material was untracked, so the corpus cannot be rebuilt as it stood. Use only to find where to look and to size D1, not to decide.

### D4. Cached-conclusion reuse and invalidation over a replayed history (credits caching; new design, no published template)
- Template: STALE's three probes (S1), MemoryAgentBench's fact-update (S2), the stale-context harness's "did the agent verify" measure (S3), and ordinary cache measures.
- Setup: build the conclusion cache, or the model-built graph, at an early commit c0. Walk forward through the next m commits (10 to 20) in order, updating the store only by its own invalidation rule. At each step, ask the same set of about 40 claim-questions ("which tables does route X write", "what does the completion path refuse once a bill is sent") in fresh sessions.
- Arms: no cache (derive again each time); cache with no invalidation; time-to-live; file-hash anchored invalidation (a claim is dropped when any file it cites changed); dependency-propagated invalidation (a claim is dropped when anything its cited code depends on changed). The last is the only one that needs a graph.
- Strata, chosen from the history before the run: claims whose answer did not change and whose anchors did not change; claims whose answer changed and whose anchors changed (easy invalidation); claims whose answer changed while their own anchors did not (the dependency case; this is where a graph could earn its keep and a file hash fails); claims whose anchors changed but whose answer did not (needless invalidation).
- Reference: whether each claim's answer changed at each step, decided by two blind readers reading the code (third reader on disagreement), not by running any arm's extractor. Do not ask a model to judge freshness: a 2026 preprint titled "Don't ask the LLM to track freshness" argues for deterministic rules (search summary only; I did not open it).
- Measures: stale-answer rate (a changed claim answered with the old value); false-invalidation rate; tokens spent re-deriving; net tokens saved including the cost of validating; whether the agent verified a cached claim before using it (S3).
- Cost: needs the dependency-case stratum to exist. Unverified whether this repo's history has enough such cases; count them first from the diff of hand-checked answers on a small sample.

### D5. Fresh typed-question set with agent in the loop (credits orientation; cheapest live design)
- Template: SWE-QA's question taxonomy and agent arm (B1), Codebase-Memory's tool-versus-explorer comparison (C1), with the repairs below.
- Tasks: 80 to 120 new questions of 8 to 12 kinds: single hop, multi-hop across runtimes (screen to route to service to table), impact, "which invariant applies", "what is the other half of this rule", plus 20 to 30 free-text orientation questions answered against a written rubric. The 50 questions of the finished test were used once on held-out; write a new set, with the writers not seeing any arm's output, and keep the kinds list but not the questions.
- Reference: two blind readers per question with evidence lines and a third on disagreement (the finished test's method), never derived from the extractor or from the graph arm.
- Scoring: exact-set questions by script (F1 of the answer set); rubric questions by a judge from a different model family than the agent, five-pass majority, order shuffled, a human check on a 20 percent sample (B1's method plus the bias list in section 3).
- Outcome: tokens to a correct answer; correct within a token cap (curve at 4k, 8k, 16k, 32k); and honest abstention (an answer of "unknown" on a question the store cannot answer must beat a wrong answer).

Which design decides what:
- D1 decides "does an agent spend fewer tokens, not make more mistakes, and read the context it needs".
- D5 decides the same for questions, at lower cost and larger n.
- D2 decides "does the tool know what will break" with a reference nobody on the graph side wrote.
- D4 decides "does caching with invalidation save tokens without stale answers".
- D3 only prioritises.

## 3. Measures and statistics (answer to part 2)

### Measures
Token accounting (all in tokens, none in money):
- Report four buckets separately for every run, as the spend study did (V3): uncached input, cache-write input, cache-read input, output. Report the sum of prompt sizes over all model calls ("cumulative input"), which counts every tool result again on every later turn; the peak context size; and the tokens that tool results add to the context.
- Count the tool's own schema and description tokens against its arm, every turn. The typed side's costs (knowing the schema, writing query programs) were left uncounted in the finished test; here they cannot be.
- Index build tokens (model-built graph) reported separately, then amortised over the number of questions asked per index state (D4's incremental build makes this honest).
- Randomise arm order and interleave arms in time, because the first arm to run on a repository warms the provider's prompt cache and cache-read tokens differ by state; report cache-read separately so the primary outcome can be taken on uncached plus output plus cache-write if needed.

Effort and quality: tool calls, turns, wall-clock time (with the tool's own latency shown separately); pass or fail by script; layer-1 and layer-2 recall before the first edit; waste (opened files in no layer); stale or wrong tool outputs followed; invariants cited; tool adoption (share of runs that called the tool at all, and calls per run).

Value per token: quality against token cap as a curve; tokens per correct answer; area under correct-rate against tokens cap from 0 to 32k, one deterministic tokenizer for every arm. "Fewer tokens with a missing prerequisite is not a win" (the A6-10 rule from research/lane-scoring.txt, reused).

### Statistics
- Unit: the task (commit), paired across arms; where several tasks share a PR or a code area, cluster on that. Per task, average the k runs of each arm first; run-to-run noise is then inside the task mean.
- Tokens: analyse on the log scale; per-task log ratio of the two arms' means; report the geometric-mean ratio ("graph arm used 0.8x the tokens") with a 95 percent interval from a cluster bootstrap over tasks (10,000 resamples) and a sign-flip permutation test. Normal-theory intervals are not used (V4).
- Pass or fail: per-task success rate (k runs), paired difference, bootstrap interval; also pass^k (all k runs pass) because a tool that sometimes misleads shows up there (Anthropic's agent-eval write-up, known to me only through secondary summaries; the pass@k and pass^k definitions are standard).
- A mixed model with a random task intercept and a random task-by-arm slope, fitted as a check. The size of that slope (called tau below) is the quantity that decides how many tasks are needed (section 5), and it is unknown for this repo until a pilot.
- The claim to test is non-inferiority on success plus superiority on tokens: "tokens lower by at least X percent, and success no worse than a margin M". Set X and M before running; the owner may choose them. Equivalence (two one-sided tests) for "no difference" claims, as the finished test's protocol already planned.
- Multiplicity: two pre-declared contrasts (A1 against A0, A2 against A0) with Holm; everything else labelled exploratory; per-stratum results (by label source, by seed runtime, by task kind) are descriptive, never a claim. The finished test's rule that the split by seed location must be shown with the result (addendum 6 item 11) carries over.
- Intent-to-treat: all runs in an arm count, including runs where the agent never called the tool. A per-protocol (tool used) analysis is shown beside it, flagged as non-randomised.
- Pilot first, then freeze: estimate sigma within runs and tau from 12 tasks x 3 runs per arm; fix the sample size, the margins and the tokenizer; hash the protocol; run once.

## 4. Leaks and biases (answer to part 3)

Model-built graph (the index has read the repository):
- L1. Built from the wrong snapshot or from more than the parent. A model that builds a graph from HEAD, or from a working tree that holds later docs (the handoff and lifecycle documents describe fixes and defects that came after many commits), puts the answer into the index. Control: export each task's parent with `git archive`, build only from that export, log every path read (the finished test's read-log audit), and for a sequential index build the index once at the oldest parent and update it commit by commit in order, so no state ever reads past its own commit. This is also the realistic use and the cheapest way to pay for model-built extraction on 140 parents.
- L2. The index builder or the agent reaching the live tree. In the finished run, every arm container mounted the live working tree read-only, with full git history and untracked copies of sealed notes; protocol-addendum-6.md item 7 records this and says only the arm code kept later commits out of reach. Control: single-commit repository, no history, no mount of the live tree, no network (Cursor's recommendations, K2; SWE-bench's fix, K1), and a post-run audit of transcripts by an agent blind to pass or fail, with an exclusion ledger published with the result (C2 excluded 26 cells this way).
- L3. The extraction model's memory. A model that built the graph in the same session, or the same account with auto-memory on, carries project facts between arms and between the build and the question. Control: fresh sessions with memory and project-instruction files from after the parent disabled; the parent-era CLAUDE.md is the only instruction file allowed; separate sessions for build and for answer.
- L4. Circular references. Questions or labels generated from the graph's own extraction make the graph look perfect (HybridRAG-Bench builds questions from the same graph it evaluates; arXiv 2602.10210, found through a search summary). Codebase-Memory's graded reference came from the tool's own first author (C1). Control: references from execution (D1 layer 2a, D2) or from blind readers who never see a graph; label-source columns reported separately; for layer 2 labels that come from static call analysis, do not let the same analysis build an arm's edges, or report that arm's score on those items apart.
- L5. Non-reproducible builds. Repeated model extraction on the same input gave 94 and 91 entities in one snippet-level report. Control: build the index k = 2 times on a sample of 10 parents and report the difference in answers; cache and freeze the built graph per commit before any question is asked; count the build in tokens.
- L6. Question or task kinds chosen because the graph can answer them. Control: the selection filter is written from the parent commit and the task kind list before arms are built; unreachable share reported per arm (the finished test already reported this).
- L7. Index staleness as a feature of the design, not a bug of the test. If the index is built once and updated, stale edges are possible. That is the point of D4; outside D4, score a stale return as wrong.

Agents as subjects:
- A1. Run-to-run noise: single-run success swings of 2.2 to 6.0 points on 500 tasks with ten repeats (V1); token geometric SD of x1.34 within one cell on one model and five tasks, with the largest runs up to 30x the smallest on some tasks (V2, V3). Control: k = 3 runs per task and arm minimum, paired, with the variance estimated in the pilot, not assumed.
- A2. Placebo and priming: an extra tool changes behaviour by its mere presence and its description tokens. Control: the placebo arm A0p; tool descriptions counted in tokens; the same description length and style across A1 and A2.
- A3. Under-use: an agent may never call the tool. Control: ITT analysis plus adoption rate reported; a second condition where the first step is a forced orientation call, to separate "the tool is not useful" from "the agent does not reach for it".
- A4. The agent finding the answer elsewhere: git history, online fixes, memory (K1, K2). Control: L2 above.
- A5. Drift: model version, provider behaviour and cache state change during a multi-week run. Control: pin model identifier and version, interleave arms, record dates; two arms running in one container at the same time were noted in the finished test (addendum 6 item 8), so randomise slot order and record it.
- A6. Judge bias (position, verbosity, self-preference, prompt sensitivity): judge from another model family, anonymised arms, shuffled order, five-pass majority, deterministic graders wherever the answer is a set or a test result, and a human check on a sample (V4 and the judge-bias sources above).
- A7. Logged labels under-credit: agents miss all gold files on 27 to 35 percent of samples (B3), and "read" is not "needed" (B8 follow-on rule). Control: do not use "files the agent read" as the sole label.
- A8. Opened-versus-used: higher retrieval recall did not guarantee that the context was used (B2). Control: the outcome is the change and its tests, not retrieval alone.
- A9. Authors grading their own tool, one repository, one model, no runs reported (C1; G2 with n = 6): do not accept such figures as a prior of large size; accept them only as reasons to design the test.

## 5. Realistic size (answer to part 4)

Do not treat any figure below as a measurement of this repository. They come from my model with the inputs shown, and the unknown that matters most (tau, the spread of the arm effect across tasks) cannot be known before a pilot.

### Tokens: detecting a 20 percent reduction
MY CALCULATION. Model: log tokens; run-to-run log SD within a task and arm sigma = ln 1.34 = 0.293 (V2, one model, five tasks); an extra task-by-arm spread tau (how much the graph's effect differs from task to task); two-sided 5 percent, 80 percent power, paired over tasks; k runs per arm. Variance of the per-task mean log ratio = 2 sigma^2 / k + tau^2. Tasks needed:

| Target reduction | tau | k=1 | k=2 | k=3 | k=5 |
|---|---|---|---|---|---|
| 20 % | 0 | 28 | 14 | 10 | 6 |
| 20 % | 0.15 | 31 | 18 | 13 | 9 |
| 20 % | 0.30 | 42 | 28 | 24 | 20 |
| 20 % | 0.45 | 59 | 46 | 41 | 38 |
| 10 % | 0.30 | 185 | 125 | 105 | 88 |
| 30 % | 0.30 | 17 | 11 | 10 | 8 |

Minimum detectable token reduction at k = 3: n = 20 tasks gives 16.2 percent (tau 0.15) or 21.4 percent (tau 0.30); n = 30 gives 13.4 or 17.8 percent; n = 40 gives 11.7 or 15.6 percent; n = 60 gives 9.7 or 13.0 percent.

Reading: past about 3 runs per task, more repeats stop paying because tau dominates; more tasks pay. If tau is 0.3, 24 tasks at 3 runs detects a 20 percent change for one contrast. Two contrasts with Holm correction raise that by roughly a fifth, so about 30 tasks.

Caveats: V2's x1.34 comes from five tasks and one model; with a different agent and a tool that changes behaviour the spread can be larger (V3 reports ratios of 2x on average and up to 30x for some tasks). If the real sigma is double (0.586), the k = 3 variance rises from 0.080 to 0.251 at tau = 0.15 (about 3.2 times the tasks) and from 0.147 to 0.319 at tau = 0.30 (about 2.2 times the tasks), so the 24-task figure would become roughly 52 (my arithmetic from the same formula; not tabulated above). A 20 percent target on total tokens is demanding because a graph tool only changes the orientation part of a run, not the editing and testing part; a pilot should measure the orientation share first.

### Success rate: a +10 point change is out of reach on this repo
MY CALCULATION by simulation (task difficulty spread on the logit scale 1.0 or 2.0, a shift giving +10 points at mean about 0.5, normal-approximation test, 3,000 replications): power for +10 points is 0.14 to 0.40 at 1 run per task and 0.32 to 0.94 at 3 runs, depending on task count: n = 30 gives 0.32 to 0.39 at k = 3; n = 80 gives 0.66 to 0.80; n = 120 gives 0.84 to 0.94. This repo has at most about 96 commits that change an existing test, and fewer will be runnable at old parents. So success can serve as a guard, not as the headline. Standard error of a paired success difference with no real effect: 5 to 6 points at n = 40, k = 3, giving a one-sided 95 percent non-inferiority margin of about 8 to 10 points at best. In other words a 40-task run can rule out a large loss in pass rate, not a small one.

For recall-style labels (the finished test's primary): paired SD 0.29 and 75 commits give a minimum detectable difference of about 0.094 (research/lane-scoring.txt); the same note says about 264 commits would be needed for 0.05. Cheap labelled sets (D2, D5) are where n can be raised, because they need no environment.

### Proposed size
1. Feasibility, no agents: can tests, mypy, tsc and import-linter run at old parents? How many of the 96 candidate commits survive? How many D4 "dependency-case" claims exist in history? Build the label layers for a sample of 12 commits and see how many layer-2 items per commit there are. (If layer 2 is nearly empty on most commits, D1's premise fails and that is itself a result about this repo.)
2. Pilot: 12 tasks x 4 arms (A0, A0p, A1, A2) x 3 runs = 144 runs. Output: sigma, tau, adoption rate, orientation share of tokens, leak audit result, grader reliability. Freeze the protocol after it.
3. Main D1: 40 tasks x 3 arms (A0, A1, A2; A0p on a half) x 3 runs = 360 runs plus the placebo, run once, interleaved and order-randomised. Detects about 12 to 16 percent token reduction for one contrast if tau is 0.15 to 0.30; success as non-inferiority with a margin near 10 points.
4. D5: 100 questions x 3 arms x 2 runs = 600 short runs. Reference cost is human reading: two readers per question plus a third on disagreement, which is the bottleneck, not tokens.
5. D2: 80 changes, scripted, no agent at first (tool answers scored directly); then a subsample of 30 with an agent.
6. D4: 40 claims x 15 steps x 4 arms; run only if the feasibility count finds at least about 30 dependency-case (changed-answer, unchanged-anchor) claim-steps.
7. D3: replay the 139 distinct lookups; no sample-size claim; screening only.

Fresh data: the finished test's 75 held-out commits are spent for T1 and were seen in aggregate by the designers. For D1 treat them as development tasks and take the final set from commits after the freeze (the repository's product history on main ends in early August; later commits on other refs are mostly documents, research/critic.txt "CONFLICTS") or from commits made while the test runs (a prospective set whose protocol is hashed first). Two analyses to keep: report on the development set and on the fresh set separately; do not pool them for the headline.
