BUILD RECS:
  - Treat the data structure as the design variable: build the repo graph as typed nodes (file, symbol, test, doc, route, table) and typed edges (imports, calls, tests, documents, http-route-to-client-call, same-slice-across-runtime) with integer ids, and keep both a forward and reverse CSR. At 10^3 to 10^6 nodes a typed-array CSR in memory is 24 MB for 5M edges and answers 6-hop reachability in a few ms (local test), so the engine question is mostly about queries, ranking and persistence, not raw traversal.
  - Choose the engine contenders by fit: LadybugDB (embedded, CSR, Cypher with TRAIL/ACYCLIC/SHORTEST, algo extension) as the established-graph-engine arm; Neo4j Community 2026.10.2 as the reference native engine if a JVM server is acceptable; DuckDB 2.0 + DuckPGQ as the graph-flavoured relational arm. Skip Kuzu 0.11.3, CozoDB, AGE, Memgraph/FalkorDB (Docker/WSL on Windows), PostgreSQL SQL/PGQ (reverted).
  - Specialise to the repo: precompute per-edge-kind reverse adjacency, import-linter slice boundaries as edge attributes, cross-runtime edges from URL literal to route decorator, and cap hops by edge kind (imports unbounded with set semantics, calls 3 to 4, docs 1). Hop depth is a first-class parameter: report results at 1, 2, 3, 4, 6 and unbounded because the winner changes with it.
  - Rank nodes once (in-degree, PageRank, or personalised PageRank from the query file) and store the score as a property so ranked retrieval is a lookup, not an iterative query. Verify Ladybug's algo extension installs on this PC before depending on it (needs network for INSTALL algo).
  - Use trail or acyclic semantics only when path objects are returned; for 'what depends on X' return a node set with set semantics so every engine can give an identical answer.
  - Pin versions and read the licences before choosing: LadybugDB changes quickly (0.19.1 in Aug to 0.22.3 in Nov 2026) and its file format is not guaranteed stable.
TEST RECS:
  - Strongest relational arm: DuckDB 2.0.0 (recursive CTE with USING KEY, hash joins; also run DuckPGQ GRAPH_TABLE) and SQLite or PostgreSQL 18 as the production-shaped arm. Schema: typed node table and typed edge table with integer ids, composite primary key plus covering indexes in both directions (dst, kind, src) and (src, kind, dst), WITHOUT ROWID in SQLite. Traversal: level-wise BFS or recursive CTE with a depth cap and UNION (set semantics); path arrays only if paths are returned; bidirectional BFS from the application for point-to-point shortest path. Precompute closure or 'dependents within k' tables for hot files and store rank (degree, PageRank) as a column.
  - Graph arms: LadybugDB (embedded) and Neo4j Community 2026.10.2 (+ GDS only if ranking is tested), plus a typed-array CSR in memory as the ceiling. Tune each the way its docs recommend (Ladybug: indexes, ANALYZE, projected properties; Neo4j: indexes, warm cache) so no arm is a straw man.
  - Pin semantics before comparing answers: same output shape (node set vs path list), same direction, same depth cap, TRAIL or ACYCLIC vs set semantics stated, same tie rule for shortest paths. Check result equality on every query before timing; log mismatches as findings, not noise.
  - Score the answer, not only the latency: for each question, compare returned items to a ground-truth set built from an independent method (grep + import resolver + route-to-client match) and report precision, recall and rank quality, plus result size in tokens as the agent would receive it. Latency under about 10 ms is irrelevant against a 6.6 s model step.
  - Sweep hop depth 1, 2, 3, 4, 6 and unbounded, and sweep fan-out (a hub file vs a leaf file), because published results flip with both. Report the reached-set size next to each time.
  - Use the EMS repo with its history (459 commits) so churn edges (co-change, fix commits) can be added as a relational and a graph edge kind; test incremental update cost per commit, not only read time. Rebuild from scratch and incrementally, and time both.
  - Measure on this PC with cold and warm caches, many sources per cell (30 or more), medians and p95, and record memory of each process. Run Neo4j with a fixed heap; do not compare a server in a VM with embedded engines without stating it (the 2026 benchmark did and said so).

TABLE Where each side wins, as supported by the sources
  | Lookups and 1 to 2 hops on up to millions of edges: tie or relational slightly ahead (Pacaci 2017; Kuzu CIDR 2023; 2026 n-hop benchmark)
  | Reachability within 1 to 3 hops, bounded fan-out: recursive CTE with covering index is as fast as CSR (local test) and 4x faster than Neo4j APOC at 1 to 3 hops (MetaQA, single author)
  | Frontier in the tens of thousands (4 to 6+ hops): CSR 18x to 30x faster than recursive CTE (local test)
  | Point-to-point shortest path with early stop: graph engine 81x to 135x over a naive Postgres CTE BFS (MetaQA)
  | Selective filters + multi-hop joins: graph-style plans (Kuzu, GRainDB) 5x to 100x over plain DuckDB/Umbra plans; weak filters + big many-to-many: hash-join relational plans win (Kuzu CIDR, GRainDB)
  | Property-filtered variable-length paths: both families blow up on intermediates; only query-specific early filtering helps (arXiv 2604.02553)
  | All-paths enumeration returning path objects: graph engines natively return them; SQL needs path arrays; result size explodes on dense cyclic graphs in either (AGE issue; MetaQA all paths 28 ms vs 334 ms)
  | Ranking: no query language iterates PageRank; needs algo library (Ladybug algo, GDS, MAGE, DuckPGQ) or a stored column computed once in SQL

  * [depends/high] Same nodes, edges and 'same query' do not give the same answer unless path mode, output shape and tie rules are pinned :: Neo4j and Memgraph enforce trail semantics (no repeated edge) during matching; Kuzu, DuckDB and a commercial RDBMS use walk and filter to trails afterwards (arXiv 2604.02553). Ladybug defaults to WALK. AGE enforces edge-uniqueness and returns every path, while a recursive CTE with UNION returns de-duplicated node ids; an AGE maintainer states they answer different questions. DuckPGQ offers only ANY SHORTEST. Reachability as a set of nodes is the case where SQL set semantics, CSR BFS and Cypher agree (my local test: identical counts in every cell; MetaQA test: identical candidate sets). (arxiv.org/html/2604.02553v2; mid.mail-archive.com/dev@age.apache.org/msg08100.html and msg08106.html; docs.ladybugdb.com)
