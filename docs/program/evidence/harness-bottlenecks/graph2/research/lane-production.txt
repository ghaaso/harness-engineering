BUILD RECS:
  - Build one typed edge list first (file, symbol, route, doc, test, import-linter contract, cross-runtime HTTP edges, git co-change) and load it into every candidate store; a property graph is two tables, so make the table form the shared source of truth.
  - Strong relational baseline: integer ids and dictionary-encoded kinds; tables file, symbol, edge(src,dst,kind,weight,evidence_file,line), route, doc_ref, cochange, edge_unresolved (raw plus resolved); covering indexes (src,kind,dst) and (dst,kind,src); index symbol(name) plus a lower-cased or FTS5 copy; WITHOUT ROWID or clustered; STRICT tables; ANALYZE; WAL; check every query with EXPLAIN QUERY PLAN for scans.
  - Write recursion correctly: UNION for a visited set (SQLite) or DuckDB USING KEY; depth column with a WHERE depth < k bound; MIN(depth) per node; ORDER BY plus LIMIT inside the recursive select for top-N; do not enumerate paths unless paths are the answer.
  - Precompute a bounded closure table reach(src,dst,dist) up to the calibrated k, refreshed per file on content_hash change (Glean derived-predicate and stack-graph per-unit style), so k-hop queries become index lookups.
  - Put answer shaping in the store for both sides: per-file and per-symbol cards (signature lines, SCIP and Aider style), a ranking column (distance, in-degree, co-change weight), and a token-budgeted top-N output. Without this the relational side is handicapped on the owner's actual objective.
  - Graph-side algorithms worth building on an in-memory adjacency projection (CSR arrays built from the table, the Joern pattern) rather than a graph DBMS: personalised ranking, bounded k-shortest or label-sequence constrained paths (route to handler to service to repository), co-change-weighted proximity, community detection. These are the places a graph can add value that tables do not give for free.
  - Calibrate hop depth and edge weights from this repo's history before the test, as Google did: measure graph distance between files that actually changed together in the 72 fix commits and the other commits; freeze k and weights, then compare.
  - Treat Kuzu forks (Ladybug, RyuGraph), DuckDB with DuckPGQ, and Neo4j as optional engine candidates only; Postgres 19 SQL/PGQ should not be assumed. Install sizes were not checked. Anything installed needs the owner's decision.
  - Include a granularity ablation (file-level vs symbol-level edges): Ekstazi, Nx and Turborepo show coarse can be cost-effective and Meta shows unweighted closure over-selects.
TEST RECS:
  - Same edge set in every store; verify identical result sets for identical queries (LDBC validation step) before scoring anything; report any mismatch (Marlow's 416 vs 415 shows how it slips).
  - Declare the schema and every index, materialised view and setting for each store, as LDBC does; give each candidate comparable tuning effort and document it; run EXPLAIN QUERY PLAN on the relational side and show no scans.
  - Query classes by hop depth, reported separately, never averaged: name lookup; k=1 neighbours; k=2, 3, 5 bounded reverse reachability; unbounded closure; one shortest path; label-sequence constrained path across runtimes; ranked top-N under a token budget. Include both directions (dependents and dependencies).
  - Report cold and warm runs, index and build time, file size per unit of information content (say what each store holds), memory, and incremental update cost for a one-file change.
  - Add a scale-up arm (synthetic replication of the edge list or a larger real monorepo) to find where native adjacency starts to win; at this repo's size no engine difference is expected to show.
  - Score value, not time or size: ground-truth relevant sets from git history (files co-changed in fix commits, test files touched together, doc-code pairs), recall and precision at fixed token budgets, tokens per correct answer, tool calls per task. Keep the grader independent of the system builder (Codebase-Memory and sverklo were graded by their authors).
  - Give the relational baseline the same ranking and card layer as the graph candidate, or the test measures the ranking rather than the store.
  - Include a tuned grep and file-read baseline (sverklo post: tuned grep had higher F1 than the graph server) and hybrid configurations; Codebase-Memory found the graph complemented rather than replaced exploration.
  - State and keep fixed: cutoff k, row ceilings (Codebase-Memory used 100,000), timeouts, and how timeouts or truncated results are counted.

TABLE Usual ways graph-vs-relational comparisons are unfair
  | Relational side untuned: no index or default cache (Hohenstein: 60 s to 6.4 s from one index; LIMIT 1: 4.54 s to 0.057 s; cache 128 MB to 1 GB: 4.54 s to 0.46 s)
  | Relational side through a translation layer or naive schema (Sqlg via Gremlin; hiedb without a name index)
  | Hand-built in-memory structure vs server engine (owner's objection) or the reverse, tuned engine vs naive list
  | Only one query class or one hop depth (relational wins 1-2 hop single label; native wins depth 3+ on large graphs)
  | Warm cache only, data fits in RAM, no cold run, fan-out and start nodes chosen to flatter one side
  | Result equality not validated (LDBC validates; Marlow's 416 vs 415)
  | Size or cost compared at unequal information content; build time and cold start excluded
  | Timeouts, row ceilings or truncation not disclosed
  | Over-tuning one query; aggregated scores deciding the winner
  | Vendor- or author-run and author-graded benchmarks
  | Naive recursive SQL (605,859,791 rows vs 19,213 with USING KEY on a 424-node graph)
  | Different expressiveness allowed on each side (path operators, ranking, cards available to one store only)

FINDINGS:
  * [relational/high] CodeQL uses a relational data model on its own Datalog engine, and its authors say off-the-shelf SQL performed badly for their queries. :: QL compiles to Datalog and runs on relational tables (one per language construct). ECOOP 2016 footnote 5: early compiler translated QL to SQL on a third-party DB; 'Performance was disappointing, since typical QL compiles to very complex SQL with deeply nested joins and lots of recursion. Most SQL systems are not designed with such queries in mind'. They built a custom engine (no updates or transactions needed) with inlining, join ordering and magic sets. This is evidence against a naive SQL engine for deep recursive joins, and also against a general graph DB: the model stayed relational. (Avgustinov, de Moor, Peyton Jones, Schaefer, 'QL: Object-oriented Queries on Relational Data', ECOOP 2016 (local text: r)
  * [graph/medium] Joern moved from general-purpose graph databases to a purpose-built in-process graph store (OverflowDB, then flatgraph); results are mixed by query type and self-published. :: docs.joern.io: older versions used general-purpose graph DBs plus Gremlin, now parallel low-memory graph APIs. Joern team JMH benchmarks (16 Defects4J projects, 8 GB heap): Neo4j timed out on writes from a mid-size project on and used the most memory; TinkerGraph trailed OverflowDB/flatgraph on most; but on multi-hop AST traversals (astDFS, astUp) TinkerGraph and Neo4j beat OverflowDB until large projects. flatgraph read speed gain over OverflowDB 50% to >99.5%, 25-30% less memory; Linux 4.1.16 CPG 625 MB vs 2,555 MB, 11.97 vs 18.18 min. flatgraph README: ~259 bytes/node in memory, ~36.6 B/node on disk on an ad hoc schema. The store is a custom adjacency structure, not a graph DBMS. 2014 Neo (docs.joern.io/code-property-graph; flatgraph.joern.io/benchmarks; github.com/joernio/flatgraph; github.com/ShiftLeftSecu)
  * [neither/high] Glean is a fact store (RocksDB, typed immutable facts, Datalog-like Angle) and its stated reason is generality, not a verdict on graph or relational DBs. :: Facts form a DAG, predicates ~ tables, stacked immutable databases for incremental indexing, derived predicates ~ materialised views, Angle currently non-recursive. Lookup by qualified name about 1 ms. The Meta post gives no comparison to graph or relational stores and no dataset size figures. (Meta engineering 'Indexing code at scale with Glean'; glean.software/docs/introduction)
  * [depends/medium] Glean beat a SQLite-based index (hiedb) on size and speed, but the relational side lacked a name index and held possibly more data. :: Full Hackage, GHC 9.4.7: hiedb 5.2 GB and 1021 s to index vs Glean 0.8 GB and 470 s. Find references to one name: hiedb 2.3 s (full table scan in name-refs), Glean 0.39 s via Glass, 0.03 s raw. Find definition: 0.18 s vs 0.05 s / 0.01 s; hiedb defs table keyed by (file, occ), not occ. Author notes hiedb may store more, and counts differ 416 vs 415. Shows a production comparison where schema and index choice, not the model, explain part of the gap. (Simon Marlow, 'Indexing Hackage: Glean vs. hiedb')
  * [relational/medium] Sourcegraph benchmarked a graph database (Dgraph) against SQLite for code-intel data and chose SQLite; SCIP replaced the graph-shaped LSIF with flat records stored in Postgres. :: Backend history post: upload size scaled 2.2-2.8x input for SQLite vs 25x for Dgraph; chose SQLite for speed, familiarity, deployment; authors say Dgraph numbers may reflect inexperience and weak schema. SCIP is protobuf documents/occurrences/symbols; LSIF is a graph encoding with opaque ids; SCIP reported 8x smaller and 3x faster than LSIF (quoted from a Meta engineer), LSIF 4-5x larger. Switching ranges to repeated int32 cut index size about 50%. Current server stores SCIP in Postgres codeintel-db (table names from search snippet only). (sourcegraph.com/blog/evolution-of-the-precise-code-intel-backend; sourcegraph.com/blog/announcing-scip; github.com/sourc)
  * [depends/medium] Kythe defines a graph schema but serves from denormalised tables; stack graphs use a graph with a constrained path algorithm for name binding. :: Kythe: nodes (VNames), edges (ref, defines/binding, childof, extends, overrides, typed), facts; storage doc says general graph query performance is not a priority and data is converted to 'denormalized paged association tables, or graph-database triples' for serving, reverse edges generated at serving. Stack graphs: per-file graphs built in isolation, merged at query time, name resolution is path finding with a symbol stack and edge precedence; reasons: incremental at GitHub scale, zero config, per-language declarative rules. Stack-graph storage not stated in the post. (kythe.io/docs/schema, kythe.io/docs/kythe-storage.html; github.blog/open-source/introducing-stack-graphs)
  * [neither/medium] Dependency-graph tools use small in-memory directed graphs with depth or package-level controls; none is a graph DBMS. :: Bazel query: DAG of targets, deps/rdeps with optional depth argument, somepath/allpaths, kind/filter, query vs cquery vs aquery; Sky Query reuses cached Skyframe graph. Nx: project-level graph, cached with daemon, changed file -> owning project -> dependents, lock-file change marks all affected by default, task-input mode added in 23.3 (snippets). Turborepo: package graph plus task graph, package-level affected by default (snippet). grimp/import-linter: ImportGraph with find_downstream_modules(as_package), find_upstream_modules, find_shortest_chains, find_illegal_dependencies_for_layers; no depth argument. madge/dependency-cruiser/pydeps schemas not described in what I read. JetBrains: file- (bazel.build/query/language; nx.dev docs; turborepo.dev docs; grimp.readthedocs.io; plugins.jetbrains.com indexing docs)
  * [graph/high] Google found that test targets more than 10 dependency edges from a change hardly ever break; so hop depth is an empirical, calibratable property. :: TAP uses a reverse dependency graph, MinDist = shortest directed edge count; affected sets up to 1.6 million targets; of 5.5 million affected tests only 63K ever failed; failures are generally 'closer'; Fig. 12 simulates MinDist 6 and 10. Later Google note (snippet) says presubmit selection is mostly static analysis on the build dependency graph plus some dynamic selection. (Memon et al., 'Taming Google-Scale Continuous Testing', ICSE-SEIP 2017 (local text: txt/tap.txt))
  * [depends/medium] Unweighted dependency closure over-selects; Meta replaced it with a learned model, and file-level granularity can beat finer or coarser choices on cost. :: Meta: build-dependency selection says 'impacted' more often than necessary, up to a quarter of all tests per change on mobile; model (gradient-boosted tree on history) catches >99.9% of regressions running about a third of tests that transitively depend on the change; paper: cost halved, >95% failing tests caught. Ekstazi (snippet): file-level chosen over method-level for overhead; Ekstazi# file-level cut test methods 75.6% vs module-level. (engineering.fb.com predictive-test-selection (2018-11-21); Machalica et al. arXiv 1810.05286 (snippet); Gligoric et al. )
  * [relational/high] The 2026 agent-era graph tool Codebase-Memory stores its property graph in one SQLite file and traverses by recursive CTE. :: arXiv 2603.27277 (2026-03-28): typed nodes and edges (CALLS, HTTP_CALLS, IMPORTS, TESTS, FILE_CHANGES_WITH...), BFS via SQL recursive CTE about 0.3 ms at depth 5, configurable depth, Louvain communities, 100,000-row ceiling, no ranking algorithm described. Eval: 31 repos (78 to 49,398 nodes), quality 0.83 vs 0.92 for a grep-and-read agent, about 1,000 vs 10,000 tokens per question, 2.3 vs 4.8 tool calls; first author graded, no blinding mentioned; no relational baseline. Explorer agent won where full source or exhaustive grep mattered. (Vogel et al., 'Codebase-Memory', arXiv 2603.27277)
  * [depends/medium] Agent-tool benchmarks that favour a graph on tokens are author-run, and tuned grep can win on answer quality. :: sverklo post: 60 tasks, 2 repos; smart grep F1 0.67 / 731 tokens / 11.8 calls; sverklo F1 0.58 / 255 tokens / 1.0 call; naive grep F1 0.35 / 15,814 tokens; cold start (3.7 s) excluded; dead-code F1 0.02. Other 2026 claims (CodeGraph 51-64%, grepai 97%, 62x-120x token cuts) are search snippets from vendor or author posts, unverified. Aider repo map (2023): file nodes, reference edges, graph ranking, trimmed to a token budget (default 1k): the clearest example of coupling a graph algorithm to a token budget. (dev.to/nike-17 benchmark post (undated); aider.chat/2023/10/22/repomap.html; search snippets)
  * [neither/high] Careful graph-vs-relational benchmarks fix the data, the queries and the declared schema, include indexes as part of the schema, validate result equality, and split query classes (LDBC). :: LDBC SNB spec v2.2.2: any language or API allowed; relational systems explicitly in scope; schema includes every index, materialised view and non-default setting and must be identical across runs; explicit auxiliary structures counted as schema; validation step compares results to a reference; audited with a full disclosure report; BI workload has 38 choke points in 9 categories including path finding and path cardinality estimation; 2-3 hop patterns reward indexes but cause scattered accesses. (LDBC Social Network Benchmark specification v2.2.2, arXiv 2001.02299v9 (local text: txt/ldbc_snb.txt))
  * [depends/high] A relational system through a Gremlin-to-SQL layer was slowest at BFS depth 3+ and shortest path, but among the fastest at 1-2 hop single-label queries and property search. :: Lissandrini et al. microbenchmarks: same Gremlin queries on all systems, same random start nodes, vendor-recommended settings, 24-core 128 GB host, 2 h timeouts, BFS depth 2-5. Neo4j 3.0 best BFS at all depths; OrientDB and Titan next; Sqlg (Postgres 9.6, one table per vertex type, one join table per edge label) slowest for depth >=3 and shortest path ('accesses all tables for all edges, and performs very large joins'). Authors: with mostly property search and few traversals prefer hybrid/relational; with heterogeneous edge types and traversals prefer native. Caveat: translation layer, not tuned recursive SQL; forced Gremlin. (Lissandrini, Brugnara, Velegrakis, 'Beyond Macrobenchmarks', PVLDB 12(4) (local text: txt/lissandrini2018.txt))
  * [relational/high] Tuning alone moves relational traversal times by 10x to 80x, so an untuned relational baseline is not a fair comparison. :: Hohenstein and Jergler (PostgreSQL 9.5, laptop, 500K nodes x 50 edges and 5M nodes x 4): index on edge table took warm PATHS(5) from about 60 s to 6.4 s; LIMIT 1 in EXISTS sub-queries 4.54 s to 0.057 s; cache 128 MB to 1 GB 4.54 s to 0.46 s (cold barely changed); array columns halved ALL(4) at the cost of 1NF; JDBC fetch size 1 to 1000 took 30 s to 18 s; ALL(9) 8.0 s and ALL(10) 26.4 s warm on 5M nodes. Similar-sounding scenarios differ by about 1000x. Their list of unfairness: overgeneralising one product, small in-memory data, warm starts, default config, over-tuning one query, synthetic scenarios, naive schemas or mismatched languages, data distribution and fan-out, aggregated scores. (Hohenstein and Jergler, 'Database Performance Comparisons: An Inspection of Fairness', DATA 2019)
  * [depends/medium] Headline graph-over-relational multipliers come from untuned or vendor-run setups. :: Neo4j-in-Action table (snippet of Neo4j's page, which returned 404): 1,000 users, depth 4, MySQL 1,543.5 s vs Neo4j 1.359 s, MySQL fails at depth 5; Hohenstein's Postgres tests contradict the pattern. Survey (Suzumura et al., 2021): Vicknair 2010 found MySQL and Neo4j similar up to 100K nodes with structural queries faster in Neo4j; Wycislik found Oracle faster on local clustering coefficient; TigerGraph's own report 4x-100x over Neo4j/Titan is vendor-run. Relational-side research claims (SQLGraph SIGMOD 2015: 2-8x over Titan, Neo4j, OrientDB; Grail CIDR 2015) are also authors' own and snippet-only. (neo4j.com news post (snippet); arXiv 2005.12873v4 (local text); SQLGraph and Grail snippets)
  * [relational/high] Naive recursive SQL is the usual cause of slow relational traversal and is fixable with visited-set semantics. :: DuckDB USING KEY post (2025-05-23): vanilla recursive CTE keeps all intermediate rows; shortest path on a 424-node, 1,446-edge graph processed 605,859,791 rows (text says nearly 1 billion, table says 605.9M) vs 19,213 with USING KEY. SQLite docs: UNION (not UNION ALL) drops duplicates and ends cycles; indexes on both edge columns help; ORDER BY plus LIMIT in the recursive select makes a priority queue; LIMIT always stops recursion. (duckdb.org/2025/05/23/using-key.html; sqlite.org/lang_with.html)
  * [neither/medium] Standard SQL graph syntax is not a safe dependency: Postgres 19 SQL/PGQ appears to have been rolled back, and the best embedded graph engine (Kuzu) was archived. :: SQL/PGQ committed 2026-03-16, rewritten to ordinary joins, no variable-length paths in the listed features; depesz page notes rollback; PostgreSQL 19 RC1 release notes (as of 2026-10-09) do not mention it; DevX (snippet) says reverted in beta 4. DuckPGQ is an experimental DuckDB extension. Kuzu repo archived 2025-10-10 (last release 0.11.3); forks Ladybug (0.17.1, June 2026) and RyuGraph continue it; Apple acquisition reported by heise but unconfirmed (snippets). (depesz.com 2026-07-31 post; postgresql.org/docs/19/release-19.html; The Register 2025-10-14, oneuptime 2026-08-12 (snipp)
  * [depends/medium] Engine choice cannot change the answer set for identical edges and queries; value differences come from content, algorithm and output shaping. :: Inference from the sources: LDBC validates equal results across engines; production systems (Kythe, SCIP, Codebase-Memory) hold the same logical graph in tables or flat records; ranking (Aider), distance cutoffs (Google), learned weights (Meta) and typed cross-file edges are what change what an agent receives. At this repo's scale (my estimate: file graph hundreds to low thousands of nodes, symbol graph tens of thousands) every engine answers in milliseconds (Codebase-Memory: ~0.3 ms depth-5 BFS on up to 49K nodes), so engine speed is not where a graph can win. (synthesis of LDBC spec, Codebase-Memory, TAP, Meta PTS, Aider)
