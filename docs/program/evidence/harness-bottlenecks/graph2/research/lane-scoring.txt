=== scoring | scoring: how to score the graph and relational answers, and the value they carry, fairly. Covers the test protocol and the ground truth this repo can supply.
findings 12 favours {"neither":11,"depends":1}
BUILD RECS:
  - Use one shared extractor that writes a single typed node/edge set loaded into both stores, so the comparison tests storage and queries, not extraction quality.
- Nodes: file, symbol, route, table, doc section.
- Edges: contain, import, call, HTTP route linking client to backend, tested-by, migration-to-model, doc-cites, and co-change from ancestor commits with time decay.
  - Store spans at symbol granularity (file, start line, end line), so either arm can return only the changed definition instead of whole files. Granularity is how 'the data structure changes the answer' gets measured under a token budget.
  - Make co-change an available edge type in both stores. On its own it reaches recall@10 of about 0.54 here. A graph without it competes against a stronger relational table, which is an unfair comparison.
  - Invest in typed cross-runtime edges (client URL literal to route decorator). Cross-runtime tasks are where the baselines are weakest (COxPR@10 0.335), so that is where a graph's typed traversal could show value.
  - Build the graph arm as a hybrid of text search and graph traversal, not traversal alone. In LocAgent's ablation, removing text search cost about 18 points and removing traversal about 5.
  - Every answer should carry a frontier or unresolved list, so an empty result is never read as 'no dependency' (A6-06).
  - Implement the same retrieval designs (k-hop typed BFS, PPR, hybrid BM25-then-graph) in both engines as arm (d). Their ranked outputs must be identical; if they are not, that is a bug to fix before scoring.
TEST RECS:
  - Run these steps as scripts at zero model tokens:
1. Freeze main at a31924a and the split date at 2026-07-01, and hash the config.
2. Build T1, T1x and T2 from task_pool_commits.py. Get symbol references from git diff -U0 hunks mapped to their enclosing definitions at the parent (Python ast; the TypeScript compiler from technician-app/node_modules). Build T3 and T6 from doc_chains.json and doc_symbols.json, and T4 from the register-to-fix map.
3. Seal tasks.jsonl and references.jsonl with SHA-256; the build scripts get no read access to them.
4. For each parent: git archive it, extract the facts, cache them by SHA, and log every path read.
5. Load the facts into the relational and graph arms; implement arm (a) and the (d) designs.
6. Run the sweep on the tune split under an equal configuration budget per arm. Pick by M1 with the parsimony rule (simplest configuration within 1 standard error of the best), then freeze the configuration hash.
7. Check (d) equivalence on the tune split.
8. Run the held-out split once.
9. Unseal the references, score by script, and mechanically check that returned spans exist.
10. Compute statistics.
11. Audit the read logs.
  - Primary metric: symbol-evidence recall at an 8k-token budget on T1 held-out, averaged per seed and then per commit. Pack results ARB-style: path header plus content, last item cut at the budget, headers counted, one deterministic tokenizer for every arm.
  - Secondary metrics:
- recall at 2k, 4k and 16k tokens, plus file-hit recall;
- token precision;
- tokens to reach 80 % and 100 % recall;
- scripted lookups to 80 % recall (convertible to model steps at 6.6 s each);
- MRR and nDCG@10;
- value per token: area under the recall-vs-tokens curve from 0 to 16k;
- prerequisite loss on T3 and T4;
- build time, incremental update time, p50/p95 latency cold and warm, bytes on disk, RAM.
  - Sweep on the tune split only:
- hops 1-5 and PPR alpha 0.5, 0.7, 0.85;
- edge-type sets added cumulatively;
- ranking: BFS, degree-normalised, PPR, co-change weight, BM25, hybrid;
- granularity: file, symbol, chunk.
Report the full hop curve, not just the best point.
  - 'Tuned on both sides' means:
- the same facts for both arms;
- the same number of configurations tried on the tune split;
- each engine's idiomatic indexes and settings (SQLite: indexes, ANALYZE, WAL, FTS5 with recursive CTEs; graph engine: id indexes and its library algorithms);
- the same packaging and tokenizer;
- no per-task rules.
  - Leakage controls:
- build every store at the parent commit, with history from ancestors only;
- drop same-PR sibling commits from co-change (primary), and report with siblings kept as secondary;
- exclude files added in the test commit, and commits with more than 30 files;
- never put the commit message in the query;
- for T3 and T4, build before the doc's commit and remove the doc;
- run a read-log audit.
  - Statistics:
- the unit is the commit, paired across arms, with PR clusters;
- 10k-resample cluster-bootstrap 95 % CIs and sign-flip permutation p-values; no CLT intervals;
- TOST with a smallest effect of interest of ±0.05;
- Holm correction for secondary metrics;
- report the realised paired SD.
  - Decision rules:
- The graph wins only if: the CI of the difference is above 0; median tokens per answer are no higher; prerequisite loss is no worse; and the sign is the same in at least 3 of the 4 sets T1, T2, T3, T4.
- Relational wins under the mirror conditions.
- 'No difference' if the 90 % CI lies within ±0.05.
- Otherwise inconclusive: report 'no evidence either way at this size'. With about 75 held-out commits this outcome is likely.
  - Treat DIR and COxPR as floors that every arm must beat. Do not count them as wins for either store.
  - Steps that need a model in the loop:
- annotate needed-but-unchanged context on 30-50 held-out commits (ContextBench style, with a human audit);
- blind real-task replays under the A6-10 budget (16k tool-result tokens, 30 calls, 2 or more runs per arm), each arm as the only retrieval tool, scored against sealed keys;
- any rewriting of commit subjects into task statements written as if before the fix.

  * [neither/high] Agent Retrieval Bench gives a ready token-budgeted metric (BCY@B) and change-evidence gold labels that match this repo's task types. :: BCY@B packing: ranked files are packed greedily, each as a path header plus content; the last file is cut at the budget, and headers count against the budget.
- A gold file counts as exposed if at least 1 content token is visible.
- Tokens are counted with a deterministic regex code tokenizer.
- Budgets are 4k to 32k, with 8k as the main point.

Gold labels come from change evidence (code2test, edit2ripple, trace2code). The corpus is frozen at the pre-fix base commit, and queries exclude patches and gold paths.

Result: no retrieval family dominates; RepoMap is best at 8k. (Qin, Xie, Agent Retrieval Bench, arXiv 2607.24882)
