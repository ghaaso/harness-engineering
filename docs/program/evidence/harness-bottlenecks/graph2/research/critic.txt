CONFLICTS:
  - The lanes use different task sets that cannot be compared. Algorithms uses 233 non-merge main commits, a count-based 70/30 split (106/45 commits), 169 to 340 seed-file queries and recall per query. Scoring uses 140 first-parent units split by date (65 before July, 75 from July) and recall averaged per commit, over a universe that includes tests and migrations. Co-change@10 recall comes out 0.479 in algorithms/nul_out.json and 0.544 in scoring/baseline_probe.json. One shared task file must be fixed before any arm is scored.
  - The commit counts differ across artifacts: 459 commits on all refs (brief), 368 on main and 233 non-merge (history_stats), 323 commits with 210 used for co-change (schema git_stats, all refs), and 232 or 154 units in the two task-pool files. Main's usable history ends in early August 2026 (usable_by_month shows 2026-08: 2), so 'history to 2026-11-09' is history of other branches, mostly docs. The held-out set is 45 to 75 commits, not five months of product work.
  - Cross-runtime coupling: schema git_stats finds 31 of 33 cross-runtime co-change pairs (support of 3 or more) unlinked by calls, DI or URL. schema join_out finds 30 of 33 within 5 hops of the joined graph. The verifier's v_baserate.js exists because in a graph where most nodes lie within 5 hops of each other, 'within 5 hops' says nothing. Treat cross-runtime coverage as unproven until it is compared with the base rate.
  - The TS extractor is not reproducible. Between the schema run and the verifier rerun, mobile.calls.unresolved went from 2240 to 13 and mobile.calls.external from 1493 to 3720 (the Jest globals were reclassified), and ts_graph.json changed size (633,815 vs 632,149 bytes). The lane patched the extractor in between (patch_jsx.js), so the graph used for any result is not pinned.
  - Query direction: the first test's 'everything that depends on a file' (reverse edges) reaches a recall ceiling of 0.25 against co-change truth. Undirected traversal reaches 0.90 at k=4. Any lane that reasons from the first test's query type is reasoning about the weakest query.
DESIGN:
  - The store and the algorithm are separate variables and must be tested separately. Score the arms as {facts} x {algorithm} x {output format} x {engine}. At this scale (about 3.3k code nodes and 9.5k typed edges, with a joined build of 28 ms), every engine answers in milliseconds, so the engine axis decides expressiveness, maintenance and install cost, not speed or answer quality.
  - Schema: a heterogeneous typed property graph at symbol level. Nodes: function, method, class, component, route, table, column, setting, migration, outbox_kind, doc_section, invariant, commit/PR. Edges: the 19 types already in join_out plus the missing ones listed above. Add a hierarchical rollup (symbol to file to slice to runtime) so an answer can be returned at the granularity the token budget allows.
  - Co-change is the strongest single signal and should be a weighted, time-decayed edge, trained only on commits before the task. On the split run, at k=10: co-change confidence gives precision 0.259 / recall 0.479; undirected import PPR gives 0.243 / 0.454; PPR plus co-change (w=1.0) gives 0.283 / 0.534; BFS-2 gives 0.193 / 0.376; same directory gives an unranked set of about 9.5 files at precision 0.22 / recall 0.29. Fusion helps, but the confidence intervals overlap, and the relational side can compute co-change too.
  - Hop limits: sweep them as a parameter and report curves, never a single k. Undirected import reach saturates by k=3 to 4: a mean of 90 of 369 files at k=3, recall 0.87, precision 0.06. A global k is the wrong control on the typed graph. Screen-to-table takes 6 to 9 raw hops, while a metapath (calls up to 4 hops, then calls_url, route-to-handler, backend calls up to 4 hops, writes_table) returns 4 tables. A hub cut changes impact sets from 28 to 2 nodes. Sweep k in {1..6, unbounded} x direction x edge-type mask or metapath x hub threshold (prodIn > 5, 10, 15, none) x ranking (BFS order vs PPR, cut at a token budget). Plot recall and precision against tokens.
  - Ranking plus a token budget matters more than hop count: return the top items by PPR or fusion until the budget is used, as Aider does, rather than everything within k hops.
  - Engines to compare. Relational: SQLite with its best design (WITHOUT ROWID covering indexes in both directions, a recursive CTE with a depth limit, a materialised closure table, FTS5/BM25 over symbols and doc sections), and optionally Postgres, since prod already runs it. Graph: DuckDB+DuckPGQ, which keeps the engine fixed and changes only the query layer, making it the most controlled comparison; a maintained Kuzu fork (embedded); optionally FalkorDB or Neo4j in Docker. Keep the in-memory CSR/numpy workbench for developing algorithms, not as a contender.
  - The relational design to compare against must hold the same typed facts. Either one edge table (src, dst, type, weight, valid_from_commit) or one table per node kind, plus a co-change table with support and confidence. It must be given the same algorithms (PPR iterated in SQL or app code over SQL rows, metapaths as chained joins, the same hub cut) and the same output formatter. Otherwise the test inverts the first test's unfairness.
  - Expose the same tool API to the agent from every backend: neighbors(node, types, k), impact(node, budget), path(a, b), explain(node), search(text). This keeps the model's skill at Cypher versus SQL out of the comparison. Test free-form query writing (Text2Cypher vs Text2SQL) only as a separate secondary arm.
FAIRNESS RISKS:
  - Truth circularity. Co-change truth favours any arm that uses co-change. Both arms can compute it, so it must be in both or in neither. Truth for structured questions must come from reading the code, not from the extractor both stores share.
  - Temporal leakage. Static facts are built at HEAD for tasks at past parent commits. Same-PR sibling commits are in the training history for 45 tasks, though the COxPR effect is small (0.007 at k=10). Rebuild the facts at each parent commit and drop same-PR siblings.
  - Tuning on the test set. The fusion weights (0.5/1/3), PPR alpha (0.15/0.30) and hub thresholds were all compared on the 45 held-out commits in nul_out.json. Choose them on the June tune split only, then report held-out once.
  - Low power. The paired SD of the recall@10 difference is 0.263 (baseline_probe), so detecting a 0.05 difference at 95 % needs about 110 paired commits. The held-out set has 75, and the fix-only subset has 30, with a CI that crosses zero (-0.043 to 0.246). Report effect sizes with CIs and do not claim a winner on subsets.
  - Unequal effort. The graph arm has had more algorithm and schema work than the relational arm, the inverse of the first test. Every algorithm and optimisation needs a written relational equivalent, or an explicit note that it has none.
  - Wrong quantity. Database size on disk and synthetic 100k-node latency are not the outcome. Tokens of serialised output per unit of relevance, and agent task success, are the outcome.
  - Unrepresentative queries. This repo's recorded sessions contain 26 search-to-read pairs on product code out of 181, and the coding sessions came from a different (Django) project. Real coding questions on this repo must come from replayed commits and hand-written questions, and the source of each must be labelled.
  - Unreachable truth. 33-36 % of files changed in a unit were added in that unit (task_pool added_share), so no store can return them, and 15-19 % of the remaining truth is unreachable within 5 hops. Score only reachable truth, and report the unreachable share for each arm.
  - Stale docs. 517 of 1,268 backticked file names in docs do not resolve in the repo. A doc-linked graph can surface stale citations with confidence. Score stale returns as negatives for both arms.
  - Engine maturity. Kuzu's upstream is archived. Results on a fork may not hold for the owner's long-term choice. Record the version and maintenance state of each engine.
  - The baseline that matters most is missing. Agents today use grep/ripgrep and file reads. Both stores must be scored as additions to grep, not only against each other.
