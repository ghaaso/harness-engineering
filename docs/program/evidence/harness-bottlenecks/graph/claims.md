# Claims to test (drafted by the orchestrator before any check; 2026-11-12)

Context: the owner asked whether a graph database holding the repo's semantic relations and real connections, with a cache on top, would give a lot of information in a small size and so cut token use. The orchestrator built a connection graph of the FixFlow repo by script (build.js, query.js; outputs in build-output.txt, query-output.txt, answer.txt) and pulled every search the November clinic sessions ran (extract.js; extract-output.txt, searches.jsonl, sample.json).

C1. A graph of the repo's real connections is small and cheap to make. FixFlow: 618 tracked files, 2,923 edges (2,033 imports, 53 test mocks, 837 doc citations of files), 180 KB as JSON, 30 KB gzipped, built by a script with no model in about 0.2 s.
C2. One answer is short. "What depends on backend/app/features/jobs/service.py" comes back as about 555 tokens (18 direct dependants, 30 in all, 23 test files, 15 imported names, 24 citation lines in 12 docs). Reading the 18 direct dependants whole is about 70,500 tokens. A plain text search for the direct importers returns about 1,286 tokens.
C3. The database type does not matter at this size. The same edges in a SQLite table with a recursive query give the same answer in about 0.05 ms per query, against 0.002 ms in memory, and the SQLite file is the same size (180 KB). A graph database is not smaller; its advantage is fast deep traversal on very large graphs. The small size comes from storing connections instead of contents. A graph database server would need memory this PC does not have free.
C4. A cache on top has nothing to save. All 477 "who depends on this" queries together take under 1 ms. A full rebuild takes about 0.2 s, so invalidation can be "rebuild on every commit".
C5. Most files have a short reach (median 2 dependants at any distance; 389 of 477 have 15 or fewer). Hub files reach 67 to 112 files (config, db, the API clients), where the list is too long to use as it is.
C6. Some semantic edges can be scripted: a doc that cites a file (837 edges). Deeper ones (this rule constrains that function) need a model to extract. The compile's section 6 (docs/program/HARNESS-BOTTLENECKS-2026-11.md in the FixFlow repo) records the outside evidence: deterministic code graphs give about four points of localisation gain at equal cost; model-extracted graphs cost about a thousand times vector indexing and often underperform plain retrieval.
C7. The demo does not show that sessions would spend fewer tokens. 8,303 of 18,202 November tool calls (45.6 %) contain a search command; the share of those that are connection questions is what the two classifiers are measuring.
C8. The graph replaces locating, not understanding: the model still has to read the code it changes.
C9. Token figures here are characters divided by four, a rough rule.
C10. This is the import-and-caller index already in phase 3 of the harness v2 plan. What stays out: a graph database server, a model-extracted graph, embeddings.
