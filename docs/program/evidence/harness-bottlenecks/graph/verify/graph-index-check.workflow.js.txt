const CLS_PROMPT = (lane) => `You are classifying real searches that coding-agent sessions ran, to learn whether a scripted index of code connections would have answered them.
${COMMON}
Your lane folder: ${G}/verify/${lane}

Read ${G}/sample.json. It holds 200 items drawn at a fixed interval from all 8,303 search-bearing tool calls in one project's November sessions (a Django-style Python project, not the FixFlow repo). Each item has: id, kind (the tool), sub (true if a subagent), search (the command or tool input, cut at 420 characters), said_before (what the model wrote just before, if anything), next_calls (the next two tool calls).

The index being judged is deterministic and built by script, with no model: for every file, which files import it and which named symbols they import; who calls a function; which test files reach a file; which docs cite a file by path; where a symbol is defined, with its line range. It holds connections and locations. It does not hold file contents, log output, test results, git state or prose meaning.

For EACH of the 200 items give:
- cls, the main intent of the call:
  NOT_A_SEARCH: grep, ls or find used only to filter or check the output of something being run (a test run, a script, a git command, a build), or appearing inside a script being written. Not a lookup in the code.
  CONNECTION: asks who imports, calls, uses or references a thing, which tests cover it, which files mention a file or symbol. The answer is a list of places.
  DEFINITION: asks where a named thing is defined, usually reading its body in the same command (grep -n "def x" -A30, sed -n a,b p).
  CONTENT: wants specific content or values: strings, settings, numbers, wording in docs or code, the lines of a known file.
  STATE_OR_LISTING: logs, run output files, directory listings, git state, checking that a file exists.
  UNCLEAR: cannot tell from what is shown.
  If a command mixes several, choose the one that carries most of what it returns.
- graph_answer: "full" if the index alone would have returned what the call was after, in one lookup and in no more tokens; "partial" if it would give the place but the call also needed the lines themselves, or it answers only some of the sub-commands; "none" otherwise.
- step_saved: would having the index plausibly have saved a model step here or just after (for example next_calls shows a follow-up search or read hunting for the same thing)? "likely", "unlikely" or "cannot tell". Be strict: a single command that already finds and reads the thing in one step saves nothing.
- note: at most 12 words, only where the call is a borderline case.

Judge each item on its own evidence. Do not aim for any particular share. Do not skip items: the output must hold exactly 200 entries with ids 1 to 200.
Then give: observations (patterns you saw, with counts where you can), how_sessions_already_search (do they batch several lookups into one command, read ranges or whole files, repeat themselves), and what_an_index_would_change (be concrete and conservative).
Also write your full table to ${G}/verify/${lane}/classification.json and a short report.md.`
