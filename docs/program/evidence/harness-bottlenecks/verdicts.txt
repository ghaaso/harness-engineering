
######## Could Tree of Thoughts, Forest of Thought or Graph of Thoughts help this harness (one Windows PC, a root orchestrator, slice sessions in worktrees, a model-reviewer gate), and if so where, at what cost, and what one trial would settle it?
VERDICT: Not as named methods. The one narrow version with coding evidence is several candidate fixes per serious review finding, picked by an executed test that was written before the candidates. Nobody has shown it cuts fix-induced defects (B01), so run it once as a small, capped A/B trial on one slice. Do not build it into the harness.
CONFIDENCE: medium
EXPLANATION: WHAT THE METHODS ARE. Tree of Thoughts has the model write several partial answers, score each, and grow only the promising ones, so it searches a tree instead of following one line. Its measured gain is on puzzles such as Game of 24 (GPT-4: 4% with chain of thought against 74% with ToT), on a 2023 model that does not reason internally. Secondary sources put its cost at roughly 5 to 20 times plain prompting (research.txt B1 C1). Forest of Thought runs several such trees at once and settles on an answer by consensus and self-correction. Only its abstract could be read: it gives no benchmark, model, number or cost, so it is an unverified claim aimed at math and logic (B1 C3). Graph of Thoughts treats each partial answer as a node that can be merged with others, refined in a loop, or distilled. It was measured only on toy tasks like sorting (62% better than ToT at 31% less cost than ToT), never on merging code or agents' work (B1 C2, C11).

WHAT THE EVIDENCE ESTABLISHES FOR CODE. (1) At matched compute, plain self-consistency (sample several answers, take the majority) often equals or beats the elaborate structures. Debate and Reflexion can get worse as the budget grows (B1 C4; math and QA only). (2) The only family with software evidence is best-of-n patch sampling with test-based selection. Agentless on SWE-bench Lite: majority vote alone resolved 25.67%, adding a regression-test filter 27.0%, adding a generated reproduction-test filter 32.0%. That took 40 candidates per issue at about 78k tokens per issue. Only 94 of 213 reproduction tests were valid, and the best possible pick over the candidates was 42%, so the selector is the weak link (B1 C6, C8). (3) Iterative review-and-fix loops damage working code faster than they repair broken code, and they fall into cycles of adding and removing the same change. A verification gate (rerun the earlier tests, roll back on failure, retry) was the only strategy that helped every model in an 8-turn study (B1 C9; B3 C4, C5; function-level benchmarks, older models). (4) No study measures the exact idea here: N candidate fixes per review finding, chosen by executed tests, with regression as the outcome (B1 C10, unsupported). (5) No controlled study re-tests ToT on 2025-2026 reasoning models (B1 C5, could not check).

WHAT THE TESTBED SHOWS. The selector in the testbed's gate was always a model reading code. The round-2 reviewer 'ran no tests, scripts or database commands' (opening-cutoff-guards/evidence/review-opus-round2.md:3, confirmed in the file). Nine of the eleven slice gates S00 to S10 took three rounds (A2-01). In round 2 or later, a fix produced a new P1 or P2 on 8 of about 20 gated branches: S01, S02, S06, S07, the cutoff guards, S11, the posting follow-ups and the faster check. That includes five fix-induced P1s: W1 in S07 (task.md:258, confirmed), GD-01 and RS-1 in the cutoff guards (task.md:631, confirmed; opening-cutoff-guards/task.md:83), and GV-01 and GV-02 in S11 (A2-02, A2-03, A2-04, the fix_induced table in sweep-tables.txt). The board never consistently splits a round's findings into still open, caused by the fix, and new but independent (A2-04 limits). So no per-finding fix-induced rate exists, only these counts. Nothing converged on a rule. The build stopped on the owner's USER-24 direction (task.md:786, confirmed; A2-10). The failures were state and ordering bugs: a hold that never ends, a recovery boundary lost after a rollback. Only a test written for that invariant catches them. A tree is only as good as that test.

WHAT FRONTIER MODELS ALREADY DO, AND WHAT AN OUTER STRUCTURE STILL ADDS. Opus- and Sonnet-class models with extended thinking already branch, check and backtrack inside one call. So a prompt-level ToT, FoT or GoT, where the model proposes, scores and expands thoughts as text, repeats work the model does internally, at several times the tokens. Its scorer is a model judging its own thoughts, which is the overstating problem (B12) again. That redundancy is reasoned, not measured (B1 C5). An outer structure still adds three things the model cannot give itself. (a) An executable verifier: the model cannot run the test suite inside its thinking, and executed tests were the part of Agentless that carried the gain. (b) Isolation: candidates written in separate worktrees or contexts do not anchor on each other's first idea. They are still one model, so their errors stay correlated. (c) Parallel wall-clock: on this PC the gain is capped by the check queue (B06 to B08) and the usage limit (B03). The outer structure worth testing is therefore not ToT, FoT or GoT. It is best-of-n with an executed, pre-written selector, used in one narrow place.

ALREADY COVERED ELSEWHERE. Fail-before and pass-after per finding is already the ship plan's reviewer rule (ship-plan-section0.md: the reviewer names the test that fails on base and passes on head) plus Horthy G2-F015. The token tally the trial needs is Horthy G2-F183 (trial 2), and the transcript-forensics script shape is in card CR-03. The paired, blind, pre-registered design follows Horthy trial 1 (G4-F034).
WHERE IT HELPS:
- [B01 (fix rounds that create new defects); also B17 (all review is model reading)] The slice's fix step for each round-1 P1 or P2 on money, stock, hold or lock, state-machine, or deploy/restore code: several candidate fixes per finding, in separate worktrees or contexts: The tree is made of K=3 candidate fixes for one finding, written independently from the same brief, with no candidate seeing another. The selector is executed, not a model. First, a reproduction test for the finding, plus a 'how does this state end' test for any new hold or lock (the A2-02 transfer), written once BEFORE any candidate and frozen. Each candidate must make it pass, and it must fail on the base commit. Second, the tests of the touched app plus the serial race tests, run in the Linux container. Third, a guard-removal check: delete the candidate's new guard, and the frozen test must fail (the A2-06 lock-removal idea, made mechanical). Ties go to the smallest diff by files touched. A model reviewer then reads only the winner, as today. | EVIDENCE: Measured but indirect. Agentless: test filters raised SWE-bench Lite resolves from 25.67% to 32.0% over majority vote. The pick recovered 96 of the 126 issues where some candidate was right, and most of the gain came from the reproduction test (B1 C6). A verification gate with rollback was the only strategy that cut regressions for every model in an 8-turn study (B1 C9). Unmeasured: whether this lowers fix-induced P1s and P2s in review-driven rounds (B1 C10 unsupported). The selector's weak point is measured too: generated reproduction tests were valid in only 94 of 213 cases (B1 C6), and plausible-but-wrong patches pass tests (B3 C1: 7.8% and 29.6%). That is why the test is written and frozen before the candidates and checked by guard removal. In the testbed, model-run lock-removal experiments were later found to prove less than claimed at least four times (A2-06), so the guard removal must be scripted, not reported. | COST: About 3x the fix-phase tokens for each finding the method covers. November per-slice tokens were never measured (critic coverage gap), so the real multiple must come from a transcript tally. Checks: K narrow runs per finding instead of one. The full 7-step check (274 to 726 s whole, A2 root_check_per_merge) still runs once, on the winner only. Recorded second-slot waits were 337 to 551 s (sweep-tables A3 slot pairs), so K full checks per finding would land directly in the queue.
- [B12 (reports overstate)] The reviewer's verdict on a fix (the B12 side of the same mechanism): There is no tree here. The by-product of the trial above: because the selector is a script that executes a frozen test and a guard removal, the claim 'the test proves the fix' is checked by running it, not by another model reading the record. That is the transfer A2-05 asks for (a resolvable test id that fails with the guard removed). | EVIDENCE: At least 20 overstatement records in the testbed, with no denominator, so no rate (A2-05). Wrong-but-passing patch rates are measured on SWE-bench (B3 C1). Lane B1 itself says this mechanical rerun is supported and model-judge or debate verification is not (B1 implications, B12). | COST: Small: one script per finding, run inside the narrow test scope above.
WHERE IT DOES NOT:
- B03 usage limit: any tree, forest or graph run as a standing practice: These methods multiply calls. Agentless used 40 candidates per issue, and CodeMonkeys cost about $2,300 for one SWE-bench Verified run (B1 C6, C8, B03 implication). The testbed's own measurement: subagents made 82.4% of calls and caused 91 of the 104 limit errors, and one window carried only about 3.4M subagent tokens (CR-03, CR-04). A standing K-way fan-out on every finding would make the 6 November stoppage come sooner.
- B06, B07, B08 check queue and memory: one full check per candidate: The whole check is 274 to 726 s on merged main (A2 root_check_per_merge). The second slot opens only with 8 GiB free (check.py:80, A3 constants), and recorded second-slot waits are 337 to 551 s, the largest single wait 742 s (critic). K full checks per finding put the cost exactly where the PC is already short. Candidates may only run narrow tests, and one at a time if memory is low.
- B12 and B17: a model judge or debate as the value function (ToT and MCTS-style scoring, SWE-Search's value agent): The overstating problem is the selector. LLM critics claim bugs in bug-free code, and repair rate trails damage rate (B1 C9, B3 C4). Debate and Reflexion can degrade as the budget grows (B1 C4). SWE-Search's gains are self-reported and relative, with no equal-cost comparison (B1 C7). A model scoring model-written branches adds a second layer of unverified claims.
- A forest of reviewers with majority vote on findings (self-consistency applied to review): Voting would throw away real defects. In one small study, 56.5% of confirmed defects were found by exactly one model, and adding a second vendor raised coverage from 33.6% to 57.1% (B3 C9, Stone; small and not peer reviewed). Several independent reviewers help through their union, not through consensus. The testbed's two refute-reviewers, split by area (A2-01), already take the union.
- B04 single orchestrator, and GoT as an orchestration architecture: The structured-reasoning papers are about one problem's answer, not about throughput (B1 B04 implication). The orchestrator's measured problem is context size (3 compactions at 573,774 to 974,246 pre-tokens, CR-05) and serial merging. A graph of thoughts adds more for it to hold. The transferable fragment, bounded distillation of parallel outputs (Parallel-Distill-Refine, math only), is just short structured verdicts, which the harness already demands (orchestration-design.md output contracts).
- B13 shared-document edits merged by GoT-style aggregation: GoT aggregation was measured only on sorting-type tasks. No source shows it merging agents' documents (B1 C11). The testbed's measured failure was the root's own merge edits breaking the check (A2-07: S01 two failures, S02 four consequences). The answer there is per-slice append-only fragments and lock-step tests, not a model merging text.
- B02 gaps found only at the end, and B19 nothing run on a real host: A search over candidates cannot find what was never tested. The missing check was a clean-install journey with real-shaped data (A2-13). FeatureBench shows unit-level success does not predict feature-level success (B3 C10: 11.0% against 74.4%). That calls for an acceptance test, not a reasoning method.
- Candidate designs for new holds, locks or recovery rules (a tree over designs before code): The scorer would be a model judge, because there is no executable test of a design yet. The testbed's lesson points to a cheaper deterministic tool: enumerate the state table (record state x marker x serving; post, abandon, reverse, owner absent) and drill every cell (A2-02, A2-03 transfers). That checklist does the work a design tree would claim to do, with no extra branches.
- B05, B09, B10, B11, B14, B15, B16, B18, B20, B21: These are machine, ops, visibility, housekeeping, platform-parity, load-test and backlog-policy problems. No thought structure bears on them; each needs an engineering fix or an owner policy (lanes B3 to B6).
TRIAL: design: One slice, an A/B within that slice, chosen before the gate runs: the next slice whose round-1 gate returns at least 4 P1 or P2 findings on money, stock, hold or lock, state-machine, or deploy/restore code. Assign each finding by a coin flip recorded in the decisions journal before any fixing. CONTROL arm: today's procedure, one fix per finding by the slice session, then the targeted Opus re-review. CANDIDATE arm, for each finding: (1) a separate Opus agent writes the reproduction test (fails on base, plus a 'how does this state end' test if the fix adds a hold or lock). It is committed and frozen, and its sha256 is recorded before any candidate exists (the answer-key discipline of Horthy G2-F051). (2) K=3 candidate fixes, each an Opus agent in its own worktree with the same brief and no view of the others. Routing puts money and state code on Opus. (3) A script selects: the frozen test must fail on base and pass on the candidate; the touched app's tests and the serial race tests must pass in the Linux container; removing the candidate's new guard must make the frozen test fail. Ties go to the fewest files touched. If no candidate passes, that counts as a failed round, and that finding falls back to the control procedure. (4) Only the winner goes to the same blind targeted Opus re-review as the control. The reviewer is not told which arm a fix came from. No model judge selects anywhere. Nothing goes into the harness unless the stop rule's pass condition is met.
  measurement: Primary: new P1 and P2 findings per fix round that are CAUSED BY THE FIX, per arm. Each re-review finding is classified, by a second blind Opus pass and checked by the root, as (a) old and still open, (b) new and caused by the fix, or (c) new and independent. This is the split card A2-04 says the board never kept. Testbed reference baseline, approximate only because the board did not split consistently: fix-induced P1s or P2s appeared in round 2 or later on 8 of about 20 gated branches, including five fix-induced P1s (W1, GD-01, RS-1, GV-01, GV-02), against 19 round-1 P1s on 12 branches (sweep-tables A2). Secondary: (a) rounds until the finding is closed; (b) how often the winner was candidate 1. If it almost always is, selection adds nothing over one fix; (c) how often the frozen test was found wrong or weak, since that is the selector's failure rate; (d) fix-phase tokens per finding per arm, from a transcript tally over the session JSONL (Horthy G2-F183, CR-03 script shape); (e) narrow-run count, check-minutes and slot waits per arm, from the check's own logs.
  budget: At most 6 findings in the candidate arm, so at most 18 candidate fixes and 6 frozen tests. Fix-phase tokens in the candidate arm capped at 3.5x the control arm's mean per finding. Measure the control arm first. If November per-slice figures are still unmeasured, set the cap after the first two control findings. No candidate work starts within the last 90 minutes of a 5-hour window, nor once the weekly meter is above an owner-set level, because the limit typically hit about 75 minutes into the window in October (CR-03). Checks: candidates run only narrow scope (frozen test, touched-app tests, serial race tests) in the Linux container. The full 7-step check runs once per arm per round, on the selected fix only, never per candidate. Candidate narrow runs run one at a time when free memory is below 8 GiB, matching the existing slot rule (check.py:80).
  stop: Pre-registered. Stop early and record 'do not adopt' if any of these happen: (1) the candidate arm's token use passes the cap on two findings; (2) the winner is candidate 1 in at least 3 of the first 4 findings, so selection adds nothing; (3) the frozen test is found wrong or too weak (passes with the guard removed, or the reviewer shows it tests the wrong invariant) on 2 findings, so the selector cannot be trusted; (4) a usage-limit stop or a slot wait over 742 s, the largest recorded, is caused by candidate runs. Otherwise stop after 6 candidate-arm findings, or when the slice's gate closes if sooner. Adopt as an opt-in for P1 findings on money, state and recovery code only, never as a default, if the candidate arm had zero fix-induced P1s and at least 2 fewer fix-induced P1 plus P2 findings than the control arm. With this sample that is a weak signal, so the result is an option for a second slice, not a rule. Any smaller difference counts as no effect. If the trial does not pass, keep the cheaper part it tests on its own: the frozen fail-before test plus the scripted guard removal, single fix.
DO NOT BUILD:
- A prompt-level Tree of Thoughts, Forest of Thought or Graph of Thoughts layer in briefs or agents (propose, score, expand thoughts as text). Frontier models already search inside extended thinking; the measured gains are on puzzles with a 2023 model at 5 to 20x cost.
- Any MCTS or tree-search coding agent with a model judge as its value function (the SWE-Search or CodeTree pattern). The gains are self-reported and relative, with no equal-cost comparison, and the judge is the overstating problem.
- Majority vote or consensus over reviewers' findings. Single-reviewer finds are most of the real defects, so keep the union.
- Multi-agent debate or Reflexion loops as a reviewer or fixer. At matched compute they are no better than self-consistency and can degrade as budget grows.
- GoT-style model aggregation for merging slice outputs or shared documents. Use per-slice append-only fragments, mechanical merges and lock-step drift tests instead.
- A standing K-way candidate fan-out on every finding, or any candidate run that triggers a full 7-step check per candidate.
- More model-review rounds as the cure for B01. Iterative LLM review invents defects and cycles; the measured mitigation is a test gate with rollback, plus a pre-registered stopping rule.
OPEN RESEARCH:
- Whether ToT- or FoT-style prompting adds anything on 2025-2026 reasoning models at equal budget. No controlled study was found in two searches (B1 C5), so the 'redundant' judgment is reasoned, not measured.
- Whether N candidate fixes per review finding, picked by executed tests, cut fix-induced regressions compared with one fix per round. No study measures it (B1 C10). Only the in-house trial above can answer it for this kind of code.
- The fix-induced defect rate per finding in the testbed itself. A re-read of the S01 to S11 gate records, classifying each round-2 and later finding as still-open, caused-by-fix or independent, would give the trial a real baseline instead of branch counts. It is cheap, read-only work over docs/tasks.
- November per-slice token use and limit hits. The root transcript 7f348b2c and the slice transcripts were never analysed (critic coverage gap). Rerunning the CR-03 forensics script shape on them is a prerequisite for any token cap.
- How long a narrow test run (one app's tests plus the serial race tests) takes in the Linux container. Only whole-check and pass-level timings were measured (parallel pass alone 171 s; serial pass about 104 to 160 s), so the trial's check-minute cost is estimated, not known.
- Full texts of Forest-of-Thought, SWE-Search, CodeTree, CodeMonkeys and the two 2026 regression papers. Only abstracts were read, so model lists and most effect sizes are missing.
- Whether a different-family candidate writer or reviewer reduces correlated errors among candidates. Two small studies conflict (B3 C9).

######## Could spatial and temporal topology in recall from graphs boost token efficiency for this harness, and does the testbed already hold "a SQLite graph-based library for a self-evolving repository"?
VERDICT: Partly, and mostly not through a graph. The tokens went into the root's large resident window (592.7M cache-read tokens over 1,107 calls) and into reports and diffs passing through it. A small SQLite store of what is valid now (slice status, gate verdicts, open findings, decisions), written only by deterministic tools, could let the root run with a small window. A recursive "neighbourhood of this fix" query is a cheap add-on, worth having only if a zero-token replay shows it finds where the fix-induced defects landed. No such library exists in the testbed, and none of the testbed's own trials measured a token gain.
CONFIDENCE: medium
EXPLANATION: WHAT EXISTS. The testbed holds no SQLite graph library and nothing self-evolving (sweep-critic.txt "Confirmed not found"; I confirmed that .claude holds only worktrees/ and that 09-operational/runs/ is empty). It has four near things:
- The corpus map. It is a typed-edge graph of 11 planning files, stored as JSONL rather than SQLite (A6-04). Its validation contract was never run (A6-10).
- The context system. It is compaction steering plus exact grep recall (A5-01, A5-02) and was never installed. Its only token results are increases: +10.31 % (A5-11) and +6.08 % over a plain notes file, +17.02 % over native (A5-13; RESULTS_2026-10-15.md:13-15,22 checked).
- The root's lesson memory (CR-01): 15 markdown files outside git.
- In the other repository, the unbuilt knowledge-store design. It is the likeliest source of the owner's memory (critic, on A5-03).

TERMS FOR THIS HARNESS.
- "Spatial" means the neighbourhood of a thing. In the code: files, symbols, imports, callers, files changed together. In the work: slices, branches and the dependencies between slices.
- "Temporal" means two times for each fact. Valid time is when it was true, keyed to code state: valid from a commit until it is superseded or invalidated. Recorded time is when the harness wrote it: journal sequence and git history.

Compactions came at 573,774, 974,246 and 967,210 tokens, plus a fourth on 11 Nov 00:49Z at 969,988 (CR-05 counted three). They dropped 3,393,198 tokens in total and each paused 101-125 s.

  - git diff/show: 943k (222 calls)
  - other file reads: 831k
  - the board: 118 read/grep calls, 187k, plus 170k from other task.md reads. The board is now 838 lines and 221,112 bytes.
  - git log: 179k

- On top of that came 722k characters of task notifications (115 messages). Reports in total were about 1.1M characters, roughly a quarter of what the root took in.

Which kind of recall would cut each sink:
- Recall by time cuts the board reread and the resident window, but only as an enabler. The saving comes from a small window, and the store is what lets the root shrink without losing state.
- Recall by neighbourhood cuts only the pre-read routing and reviewer localisation.
- Neither cuts reports. Output contracts and files cut those. Subagents can write files (machine-facts.md, B16).
- The outside evidence for "retrieval saves tokens" is retrieval against FULL context: Zep 115k to 1.6k (B2 C1), Mem0 26k to 1.8k at lower accuracy (C2). Graph against a flat indexed table is not shown, and a filesystem agent matched graph memory (C3).
- Deterministic code graphs have a measured localisation gain: about +4 points Acc@5 over strong agents at equal cost (LocAgent, C6), and +4.9 from history (RepoMem, C10). But repos under 10k commits lost 13.1 points, and the testbed has 442 commits.

(b) WHAT THE KNOWLEDGE-STORE DESIGN ALREADY HAS (refs/knowledge-store-design.md §3-5).
- An append-only journal of events in git as truth (recorded time), and a SQLite index that is rebuilt from it, never migrated (§3.1).
- Footprints: typed items such as file blobs, config keys, dependency versions and preconditions (§3.5).
- Validity by code state, invalidated by events and never by age (§5.1, §5.2). This is bi-temporal in substance.
- Lineage through one recursive CTE over entry_link (§3.7).
- A spatial check by identifier, ks lookup --diff (§3.7, §5.2).
- Questions about a past state, answered by folding a journal commit (§5.6).
- Token columns on every lookup (§3.6).

What it lacks:
- Orchestrator state: slice, branch, status, gate round, verdict, finding with severity and file:line, decision with supersession, and dependencies between slices.
- Any import, caller or co-change neighbourhood. Symbol spans are deferred to KS-6b. Graphify was skipped (harness-review.md §5); dependency-cruiser was adopted only as import rules.
- So it cannot answer "what does this fix's blast radius touch, and which open findings and active branches sit there".

(c) THE SMALLEST THING THAT WOULD CUT TOKENS. Build one SQLite file through node:sqlite, using the knowledge store's journal-then-index pattern, as a sibling that does not wait on the knowledge-store pilot.

Tables:
- event(seq, at, commit_sha, actor, kind, payload): append-only.
- slice(id, branch, status) and slice_dep(slice, needs).
- gate_round(id, slice, round, head_sha, verdict).
- finding(id, gate_round, severity, path, line, status, opened_sha, closed_sha, superseded_by).
- decision(id, text, valid_from_sha, superseded_by, superseded_at_sha), with FTS5 over the text.
- file_edge(src, dst, kind = import or co-change, weight, at_sha).
- commit_file(sha, path).

Queries:
1. Now-state: unmerged slices, last verdict, open P1/P2 counts. About 1-2k tokens replace the board.
2. Decisions still valid on a topic: FTS5 where superseded_at is null.
3. Blast radius: changed paths, then reverse imports to depth 2 by WITH RECURSIVE, plus the top co-changed files. Return those files, the open findings on them, and the active branches touching them.
4. As-of a commit, for replay and audit.
5. Open P3s whose file changed since they were opened, flagged for recheck and never auto-closed (B21).

Who writes:
- Only deterministic tools: git, a Python ast import pass, the check's exit records, and gate verdict JSON returned under a schema. File:line is checked mechanically before the write (BAML T-08). The board becomes a generated view (B13).
- A model never extracts facts from prose.

Who reads: the root at every gate, slice leads at start, and the fix-round reviewer through query 3.

SQLite with recursive CTEs is enough. The scale is tens of slices, hundreds of findings and thousands of edges, and the knowledge store already measured its own CTE choice (E-08). No graph engine is needed.

(d) The deciding measurement is in the trial field.

(e) What not to build, and why, is in do_not_build.

(f) "SELF-EVOLVING", HONESTLY. It can mean four things:
1. Entries are written at solve time by the solving session, with footprints.
2. Entries are invalidated by code change, never by age.
3. A recurring lesson is promoted into a deterministic check (a lint rule or test) after an Opus or owner approval. Horthy adopt 1 (G1-F010, G1-F011, G4-F008) is exactly this shape. CR-01 lessons should flow the same way.
4. Hit and miss counters decide what is kept.

It cannot mean any of these:
- A repository that rewrites its own code or rules unsupervised.
- Learning from prose.
- Knowing that an entry is still correct when nothing in its footprint changed (§5.5).
- Improving the models.
- Any gain that is not measured.

The testbed has only item 1 in a weak form (CR-01, A5-17).

WHERE IT DOES NOT:
- Subagent and session reports passing through the root: Measured today: 115 task notifications carried 722,157 characters, plus 238,787 from session event lists and 115,002 from Agent results, roughly a quarter of the root's input. Recall does not shorten what a report says. What cuts this is an output contract: the subagent writes its full report to a file and returns verdict fields only. Subagents can write files (machine-facts.md B16; research B5 C9 contradicted the premise). The store helps only as the place the verdict JSON lands.
- The root reading every diff: git diff/show returned 943,260 characters in 222 root calls, 28 % of root tool results. Reading the diff is the gate's job (A1-01). A neighbourhood list can focus a reviewer but cannot replace reading the change. Moving diff reading to a reviewer agent that returns schema output is the lever, and that is an orchestration choice, not recall.
- Fixed per-session overhead (about 70k tokens): CR-11: tool and MCP schemas, skills, system prompt and memory. Recall does not touch it; trimming tools per agent type does.
- Subagents exploring code with a current frontier model: The localisation gains were measured with 2024-era models on Python SWE-bench (B2 C6, C10). Vendor claims of about 99 % token cuts were contradicted, and one A/B run had the graph arm using more tokens (C9). Claude Code's own team dropped indexes for agentic search but admits the evidence was 'vibes' (C11). The testbed's Graphify arm was built and never queried (A6-13). There is no basis to expect token savings here.
- A young repository's history (temporal recall from git): RepoMem lost 13.1 points on repos with under 10k commits (B2 C10). The testbed has 442 commits since 1 Oct 2026. Co-change edges will be sparse and noisy at first; keep them as a ranked hint only.
- B02 clean-install gaps, B05 to B11 machine issues, B12 overstated reports, B17 to B20 verification: These are acceptance-test, machine and evidence problems. A graph would not have found the missing seeder step (B2 implications for B02). Overstated reports are fixed by recording facts from deterministic tool output and checking file:line mechanically, not by recall.

DO NOT BUILD:
- An LLM-extracted knowledge graph of the docs or the code (GraphRAG, Graphiti-style ingestion, Graphify's LLM pass on docs). Extraction costs about 1000x vector indexing (B2 C4, LazyGraphRAG). Graph RAG often underperforms plain RAG (GraphRAG-Bench). Model-extracted edges add errors, which is the B12 overstatement problem in a new place. The testbed's attestation-only map recovered the human-visible chain at no level and 61 % of its labels were singletons (A6-08).
- A graph database server (Neo4j-class) or Kuzu. The PC is memory-limited, with free memory often 2-6 GB (B08). Kuzu's repo was archived in Oct 2025 (B2 C12). At tens of slices and thousands of edges, SQLite WITH RECURSIVE answers every query named here.
- Embeddings or a vector index (sqlite-vec is pre-v1, C12). The knowledge-store design already found no evidence either way at this scale and gated vectors behind a measured miss trigger (§4.4, D16). Orchestrator facts are ids, paths and statuses, which exact and FTS5 lookups serve.
- A memory layer that pushes context into sessions automatically, through hooks or injection. The store is pull-only, as the knowledge-store design rules. Hooks and the context system were deliberately skipped (harness-review.md).
- Self-modifying rules or code driven by the store. Promotion of a lesson into a check stays an approved, reviewed change.
- Time-to-live or age-based expiry. Invalidate by code change and supersession only (§5.1). The testbed's own context-system work ruled out time-based expiry after it refused valid snapshots (A5-05).
- A separate code-graph tool trial before stage 0. Harness-review §5 already skipped Graphify on staleness and package-age grounds.
