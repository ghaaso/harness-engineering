**Tried and could not break**

- **Route coverage.** Every job-id route in jobs, media and messaging carries the service-layer guard or is manager-only (assign, void, travel trail, evidence-gaps, tech-metrics). The Cloud send checks the actor before it sends. Telemetry and attendance take no job id.
- **Where R11 commits.** The routes share one session, and `get_session` only closes it, so a refused 403/409/422 rolls the claim back with the write. `send_cloud_message` writes in a savepoint. The only service rollback after a claim is the payment dedup race, which ends as an idempotent replay.
- **R11's predicate** equals explicit `/claim` (not closed, unassigned). The claim event carries no `client_id`, so it cannot collide with the write's own event. No consumer of job events acts on a claim event.
- **Races.**
  - Implicit claim against a manager's assign or a close: re-evaluated under READ COMMITTED.
  - Same technician, implicit against explicit claim: one claim event.
  - Lock order: every write takes the job row first, so I found no deadlock.
- **The installed app's payment `client_id`** is a fresh `Crypto.randomUUID()` per tap (`ArrivalJobBillScreen.tsx:252`). The 409 for a reused key cannot park a genuine payment. The same key with a different method is an idempotent success; a voided original replays as success.
- **Closed-job rule and 409 text.** `_closed_job_refuses_money_write` is the only predicate. All closed 409s end `(current status: closed)`. No in-repo client regexes that suffix.
- **`manager_id`.** Request schemas carry no actor field, and pydantic ignores extra fields, so an old client's `manager_id` is neither trusted nor a 422.
- **Pagination** is opt-in, and the default response is unchanged.
- **Error bodies.** 403 and 409 bodies carry ids only, no customer data.
- **Repo conventions.** No migration, no `pyproject` change, no secret pattern in the diff. Commit hygiene and the Co-Authored-By trailers are fine. CI is green.
