5. LOCKS AND BOOT TIME
Measured with the lane's sampler plus an in-container `pg_locks` sampler (about 70 ms granularity), Postgres 17.11:

| Size | Wall time | Locks held |
| --- | --- | --- |
| 5,000 billed jobs + 5,000 payments | 2.42 s (lane: 2.57 s) | about 1.3 s (seen from 0.93 s to 2.23 s) |
| 50,000 + 50,000 (105,000 chain entries) | 16.04 s | about 14.7 s |

- At both sizes the lock set confirms the lane's list. `staff_ledger_chain` holds AccessExclusive, ShareRowExclusive, Share and ShareUpdateExclusive; `job`, `job_payment`, `shop` and `technician` hold ShareRowExclusive.
- `job_bill_revision`'s AccessExclusive is invisible to both samplers (the table is created inside the open transaction; INFERRED). A one-sample ExclusiveLock on the chain is a relation-extension lock (INFERRED).
- Phases at 50,000: billed-jobs read 0.17 s; materials read 1.05 s; revision inserts 3.2 s; payments read 0.4 s; building the events about 1.3 s; chain inserts 8.1 s.
- What the operator sees on failure: an alembic traceback, no uvicorn, a restart loop, and the tunnel's 503. Nothing is left half-applied.
- If a stray client (a pg_dump, an old container, a script) holds a chain lock at boot, the boot fails after 3 s and retries (INFERRED).
- Deadlocks: every job path takes the job row lock, then the chain lock. Staff-ledger paths take only the chain lock. The verify takes the chain lock and then plain reads. The P8a script takes a voided payment's row lock, then the chain lock. A live void's `voided = false` UPDATE never waits on an already-voided row. So there is no cycle (INFERRED). The migration can only collide with a process running at the same time as the boot.

6. THE UNIQUES AND CONCURRENCY (INFERRED from code; the lane says no real-race test exists)
- seq is head+1 under the advisory lock, and a rollback removes the entry with its row, so there are no gaps.
- Replays return before any append (`jobs/service.py` payment replay paths). The `IntegrityError` path rolls back before the chain append.
- A void appends only when the row was flipped; the script appends only when rowcount is non-zero.
- A second `void_attributed` for one payment is refused by `(payment_id, event_type)`. A second script run finds no candidates.
- A payment and its void at once: both take the job row lock, and the void needs the payment to be committed.
