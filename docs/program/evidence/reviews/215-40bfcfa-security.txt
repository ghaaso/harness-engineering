1. THE OPS LOGIN (`ops-server.mjs`)

Held under attack, all run against the server started locally (Node v24.22.1); log in the coordinator's scratchpad, `rv215/sec/logs/probe.log`.
- Lock after five failures. After five wrong passwords from one IP, the right password got 429 with Retry-After (VERIFIED-BY-COMMAND). Code: `ops-server.mjs:656-661`, `:207-214`.
- No race. 30 parallel requests from one IP, each with its full body, got exactly 5 x 401 and 25 x 429 (VERIFIED-BY-COMMAND). Between the second lock check, the password check and recording the failure there is no `await` (`:673-681`), so the whole step runs in one go.
- Password compare. Both sides are hashed with sha256, then compared with `timingSafeEqual` (`:165-170`). This is the Node twin of the backend's `compare_secret`. A non-ASCII password, a number, or a `null` body each got 401, never 500 (VERIFIED-BY-COMMAND).
- Session token compare. `timingSafeEqual` sits inside a `try` (`:147-151`). A non-hex or short signature returns false. Changing `exp` gave 401 (VERIFIED-BY-COMMAND).
- Body cap. A declared `Content-Length` of 16385 got 413 before any read (VERIFIED-BY-COMMAND; `:559-563`).
- Boot refusals. These refused to start: password unset, password of 15 characters, password of 8 two-byte characters, session secret of 31 characters. No run printed any value (VERIFIED-BY-COMMAND; `:53-58`, `:63-68`).
- Nothing leaks. The 401 body is `{"error":"wrong password"}`: no length, no secret. The server's output never contained the password (VERIFIED-BY-COMMAND).
- Unauthenticated reach. Only static files and `POST /api/ops/login` are reachable without a token. `/api/ops/health`, `/api/ops/metrics` and `/api/ops/railway/logs` all got 401 (VERIFIED-BY-COMMAND; `:688`).
- Session storage. There is no cookie, so cookie flags do not apply. The token is a Bearer token kept in localStorage under `fixflow_token` (`src/shared/lib/api.js:15`, `:32`), with a 12-hour lifetime (`ops-server.mjs:69`) (VERIFIED-IN-CODE).

Who can set `CF-Connecting-IP`:
- From the internet, only Cloudflare's edge sets it (INFERRED from Cloudflare's documented behaviour; not checked here).
- Inside the compose, the backend, web and cloudflared share `opsnet` with ops (`docker-compose.prod.yml:120`, `:158`, `:200`) and can send any value.
- A compromised backend or web container could therefore guess without limit by changing the header each time. It could also lock the owner out by sending five failures with the owner's IP, which the backend sees in its own requests. That needs a compromise first (INFERRED).
- A header longer than 64 characters falls back to the socket peer (`:184`). Five such failures locked the header-less peer key, and other IPs were unaffected (VERIFIED-BY-COMMAND).

Findings:
- NEW-5 (the lane's own journal entry), MINOR, `ops-server.mjs:182-186` and `:215-219`. The per-IP lock is no limit for an attacker with many addresses. Input: lock IP A with five failures, then send one failure from each of 10,000 new IPv6 addresses. That took 0.8 s locally, after which A got five more guesses (401 x5). With 9,990 addresses, A stayed locked (429 x5) (VERIFIED-BY-COMMAND, `rv215/sec/logs/evict.log`). Eviction removes the entry that failed longest ago, so pushing a locked entry out costs no more than switching addresses, which an IPv6 /64 already allows. The 16-character minimum password and Access in front keep this from mattering. Smallest fix, later: key IPv6 addresses by their /64 prefix in `clientIp`.
- NEW-1, MINOR, `ops-server.mjs:207-224` and `:679-684`. Login events are never logged. A failed login, a lock engaging and a success all write nothing. The only `console.*` calls are at boot and in the error handlers (`:54`, `:64`, `:748`, `:758`, `:761`, `:770`). A spray against `ops.` would leave no trace for the owner (VERIFIED-IN-CODE). Fix: one `console.warn` when a lock engages, with the IP, the failure count and the lock seconds.
- NEW-2, NIT, `:144-148`. The token's hex signature can carry junk. `Buffer.from(sig, "hex")` stops at the first non-hex character, so a valid token with `zz` appended still gets 200 (VERIFIED-BY-COMMAND). No security effect, because the valid signature is still required.
- NEW-3, NIT, `:53`, `:63`. The boot rules check length only. A password of 16 spaces and a secret of 32 `a` characters both start the server (VERIFIED-BY-COMMAND).
- Slow requests (NOTE). `requestTimeout` and `headersTimeout` are set at `:766-767`. In four later runs a slow-header or idle socket got a 408 after 24.5 to 28.6 s. A body trickled under the cap got a 408 after 17.6 s (VERIFIED-BY-COMMAND, `rv215/sec/logs/slowhdr*.log`). Node only checks these timeouts every 30 s, so the real limit is about 10 to 45 s. In the first run, one slow-header socket was still open after 70 s; that could not be reproduced, including after 10,050 earlier requests, and is unexplained. The image runs `node:22-alpine` (`Dockerfile.ops:30`); the probes ran on Node 24.

Backlog, unchanged by this PR (the lane already journaled it): the 12-hour token cannot be revoked short of rotating the secret; a 500 on an authenticated route returns the upstream error text (`:737`, `:503`, `:521`, `:730`); the log `limit` parameter has no ceiling (`:708`); no security headers on any response.

3. MEDIA AS AN ABUSE SURFACE

Held (VERIFIED-IN-CODE, plus the lane's backend gate log for 40bfcfa: 1462 tests passed, 0 skipped, integration ran; `test_parallel_reservations_cannot_overshoot_the_cap` and `test_a_declared_length_is_a_signed_header` both passed):
- The cap is per principal. `created_by` is always set, because `Principal.tech_id` is `str` (`identity/schemas.py:45`) and the router passes it (`media/router.py:102`).
- The cap is counted under the lock. `media/service.py:153-163` and `repository.py` `lock_reservations` take `pg_advisory_xact_lock(hashtext('media_reservation'), hashtext(:who))`.
- A 413 for a declared oversize comes before any row (`service.py:149-152`). A declared size is signed into the URL (`:181-183`; `core/storage.py` `params["ContentLength"]`).
- No one can lock a technician out through someone else's actions. Only that principal's own pending rows from the last 600 s count (`repository.py:118`).
- There is no re-presign route. The router has four routes, at `router.py:60`, `:118`, `:162`, `:190`.
- Another principal's media id at finalize gets 403 unless the caller is the job's actor (`service.py:217-218`).
- The stale sweep cannot be steered into deleting someone else's evidence. Storage keys are built by the server as `{job_id}/{phase}/{uuid4}.{ext}` (`:167`); only the extension comes from the client, and it cannot contain `/`. The sweep only selects `PENDING` rows (`repository.py:146`). The canary keys come from the database. A client cannot create a key that collides with or prefixes another row's key (INFERRED from uuid4).

Findings:
- NEW-4, MINOR, already present before this PR but touched by it, `service.py:216-242` and `router.py:132-155`. After finalize, the upload URL still works for the rest of its 600 s, which lets the uploader replace or destroy evidence on a closed job.
  - Input: reserve a closing clip without `size_bytes`, PUT it, finalize, close the job. Then, within 600 s of the reservation, PUT any bytes to the same URL. A replacement of any size up to R2's single-PUT limit (about 5 GiB, INFERRED) stays forever: the sweep reads only pending rows, and finalize never looks again.
  - Or PUT more than 64 MiB and call `/complete` again. Finalize does not check the row's status, and the router does not check whether the job is closed (only reserve does, at `router.py:92`). The object is purged and, because of this PR's commit at `router.py:154`, the uploaded row is now deleted for good. That gets around the closed-job evidence freeze in `delete` (`service.py:276-277`).
  - Before this PR the same move purged the bytes and left a phantom uploaded row. The PR makes the loss visible to the evidence-gaps report rather than hiding it, so it does not weaken anything (INFERRED).
  - Only the person who made the reservation can do this, using their own token.
  - Smallest fix, as a follow-up: in `complete_upload`, return the item unchanged when `media.status` is already uploaded (no re-HEAD, no delete). Record the ETag at finalize. Switching `media_require_declared_size` on bounds the size of a re-PUT.
- Residual, not a fix for this head (5.2.4, an ASVS L3 item). The cap limits how many uploads are open at once, not how much one account can store. One account with no declared size can leave 20 reservations per 10 minutes unfinalized: 120 an hour, 2,880 a day. Each PUT has no size limit, and those objects stay until the first 03:45 run after 48 h. Reserve, PUT up to 64 MiB, finalize can repeat without limit. Six compromised accounts would make about 17,280 stale rows a day; that is more than the 10,000 rows a run examines (`SWEEP_PAGE_SIZE` 500 x `SWEEP_MAX_PAGES` 20), so the sweep would fall behind and report `truncated` (INFERRED).
- The size binding holds only when a size is declared. The deployed APKs declare none and the setting ships OFF (`core/config.py`, `media_require_declared_size: bool = False`). Whether R2 actually refuses a PUT of a different length is not verified; that is an owner step.

Tests that fail on base and pass on head, per the lane: `test_the_live_reservation_cap`, `test_parallel_reservations_cannot_overshoot_the_cap`, `test_a_declared_size_is_bound_or_refused`, `tests/test_storage.py::test_a_declared_length_is_a_signed_header`, `test_an_oversized_finalize_leaves_no_pending_row`.
