B. THE SWEEP

Could not break:
- Paged or truncated listing: `list_keys` (`storage.py:169-181`) follows the continuation tokens, and the check is exact membership with the full key as prefix.
- Clock: the 48 h cutoff is the app's UTC clock against `created_at`, which is the database's `now()` at reservation. Skew does not matter at that scale.
- Upload in flight: impossible on a row older than 48 h, because the upload URL lives 600 s and nothing re-mints a URL for an existing row (grep).
- Finalized between read and delete: the delete is an unconditional delete by primary key. A finalize can land only if the bytes exist (then the row is kept) or the size lookup transiently fails, so at worst a phantom row is removed.
- Close-gate evidence: closing rows are never deleted. K2 confirms the guard and that the evidence-gaps report keeps working.
- Wrong bucket with finalized rows: the canary aborts the run (K3).
- Overlap: `add_daily_job` uses APScheduler's default single instance, on one replica.
- Page ceiling: 20 pages of 500, then `truncated`.
- Key encoding: INFERRED safe, because botocore both sets and decodes `EncodingType=url`. Not verified against R2.

Findings:
- F2 MINOR. `service.py:333-334`: `if canaries and not ...`. With no uploaded rows (a new install), the canary is skipped and a wrong or empty bucket deletes every stale non-closing pending row. The CLAUDE.md scheduler row ("aborts unless R2 lists a recently finalized key") is then false. Fix: abort when `canaries` is empty and candidates exist, or reword CLAUDE.md.
- F3 MINOR. No deletion is logged per row. There is one INFO count line after commit (`sweep.py:595-608`) and warnings on abort. A run is distinguishable from a no-op only by its counts; which rows or keys went is recorded nowhere. Fix: log id, job_id, phase, storage_path and outcome for each delete.
- NIT. One transaction covers the whole run (up to 10k rows and 20k R2 calls): locks are held until the end, and a late error loses every decided delete; commit per page. A truncated run restarts from the oldest row, so 10k or more kept rows starve the rest again. `media_stale_pending_hours` has no floor; a value under 600 s deletes reservations whose upload is still in flight.

C. CAP, PRESIGN, AND THE 413 COMMIT

- What the cap counts: pending rows with `created_by` equal to the principal and `created_at` within the last 600 s, across all jobs (`repository.py:110-123`).
- The lock: `pg_advisory_xact_lock(hashtext('media_reservation'), hashtext(who))` is taken in the request transaction, before the count and the insert. The router's commit or the session close releases it. K4 shows the real-Postgres test catches its removal.
- What a refusal leaves: no row and no lock. The R11 claim is rolled back too, since there is no commit.
- No size declared: the URL is unbound, as before.

Findings:
- F1 MAJOR (forces the change). `router.py:154` together with `service.py:239`: an oversized finalize on a CLOSED job now commits the deletion of that job's only pending closing row. Two effects: a technician can delete frozen evidence (the same tech's DELETE on that row is refused with 403); and the job silently drops off `/api/jobs/evidence-gaps`, whose `total > 0` test needs that row. The sweep's own `SWEEP_ROW_KEPT_PHASES` exists precisely to avoid this.
  Concrete input: (1) tech t8, assigned, reserves a closing clip; (2) the job closes while the upload is in flight; (3) the tech uploads 64 MiB + 1 byte; (4) `POST .../complete` returns 413; (5) evidence-gaps then returns `[]`.
  The probe `test_rv215_closed_gap_probe.py` passes on base, fails on the head (`assert 1062 in []`), and passes again under break K5 (commit removed).
  Fix: pass the job status into `complete_upload`. On a closed job (at least for the closing phase), delete the oversized object but leave the row pending, as the sweep does. Add the probe as a test.
- F4 MINOR. The 413 commit also commits an R11 claim and its `claim` job_event created by `access_by_token` (`jobs/service.py:1124-1131`). The docstring there says "a refused write rolls the claim back". Input: a manager unassigns job J; tech B finalizes an oversized object on J; the response is 413 and B now holds J. Fix: say so in the docstring, or fold it into F1's fix.
