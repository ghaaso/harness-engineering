FINDINGS

1. MINOR, forces the change. After a failed first snapshot, a later retry can land between a discard's entry and its row's removal. The audit would then halt the fleet on a row the technician really discarded.
- The claim. `discardLog.ts:19-21` says: "an entry is never written between the snapshot's read and the removal of its row". That holds only while the snapshot has never failed.
- Why it fails. `beforeQueueWrite` lets the write through when the snapshot attempt failed (`lib/syncGate.ts:48-53`). `ensureSnapshot` retries 30 s later, on whatever write asks next (`drainGate.ts:77`, `:411-422`). So once attempt 1 has failed, `appendDiscard` (`discardLog.ts:108`) writes its entry without waiting. A retry that starts before the row is removed (for example `outbox.ts:251` then `:259`) reads both the entry and the row.
- The sequence (scratch PROBE G, passed): (1) attempt 1 fails: the record parts cannot be written; (2) `discardItem("pay-1")` appends entry E, and the trace write is slow, for example because the app went to the background mid-discard; (3) 30 s later, any queue write retries the snapshot, and the retry succeeds; (4) the removal runs; (5) the stored manifest now holds `discards: [E]` and `records.outbox: ["pay-1"]`, and the row is gone from the phone.
- What the audit does with it. Under point 9, E is "held by the manifest", so it is never evidence for that row. The row is not on the server and not in the after-report, so it reads `missing`: exit 3.
- Two other ways to reach the same state (INFERRED, not tested): a snapshot that wrote its parts but not its head; and a headless context taking its snapshot while the foreground discards (two contexts, two memos).
- Smallest fix: refuse a discard until this build's snapshot is stored. Add a strict variant of the seam, for example `snapshotHeld(): Promise<boolean>`; `appendDiscard` throws when it is false. The row stays, and the screens already show `DISCARD_NOT_RECORDED`. `removePendingMedia` already parks a deleted clip when its entry is refused (C48). Test: attempt 1 fails, then a discard leaves no entry and keeps its row.
- If the coordinator rules it a residual instead, the comment at `discardLog.ts:19-21` and contract point 9 must name it.

2. THE BOUNDARY
- Discard while the snapshot is being taken: it waits (`:108`). Pinned by the lane test "the data layer writes no entry while this build's snapshot is still being taken".
- Killed between the append and the trace, or between the snapshot and its storage: if the entry was appended under an earlier build N and the app died before the removal, build N+1's manifest holds both the entry and the row; the row stays listed, so the listing judges it (safe). If the snapshot was read but not stored, the next attempt re-reads (safe, except for finding 1).
- `removeDiscard` after a trace that could not be stored: the id appears in no later document (lane test). Only under finding 1 could a stored manifest hold it. Even then it only stops that id counting as evidence, and the row stays listed, so it is harmless.
- The next build: v42's manifest holds v41's discard by the same id (lane test "a discard after the snapshot is not in that manifest...").
- Relaunch: the list is rebuilt from the parts with the same ids and no retake (same lane test). The mapper gives the same result when run twice.
- Corrupt list: `[]` plus `unreadable_stores` (lane test). The audit must refuse to judge it (finding 2).
- Safe direction (finding 1): a discard made after the snapshot ends up in the list.
