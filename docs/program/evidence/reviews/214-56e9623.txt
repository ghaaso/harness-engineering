Findings:
- MINOR: the confirmation rounds the saved rate to whole rupees. `LabourRateCard.jsx:61` and `:102` use `formatPKR`, which rounds. Typing `1200.5` saves 120050 paisa but shows "Saved: Rs 1,201 per hour." The stored value is right; the message is wrong. Smallest fix: accept whole rupees only (`Number.isInteger(rupees)` in `valid` at `:46`, plus `step="1"`), or show the figure with paisa.
- MINOR: a stored or copied rate of 0 is called "unknown" or "not set". The server allows 0 (`min_int=0`) and bills labour at Rs 0.
  - `job.js:58` `r > 0` makes a completion copied at 0 show "Labour rate unknown". Base showed Rs 0 here (probe: `labour=null total=null`).
  - `jobsApi.js:182` reads 0 as null, so the card says "Not set — completions cannot be priced until it is." (`LabourRateCard.jsx:99`).
  - Only reachable by setting 0 directly through the API; the card itself refuses 0.
  - Fix: treat a copied `completion.labourRate` of 0 or more as known in `rateFor`, and keep the `> 0` rule for the preview rate only.
- NIT: no upper bound or confirmation on a money setting. `1e+22` gets sent; the server is expected to refuse it with 422 (INFERRED, not run). A realistic typo such as 120000 rupees saves with no check, and the server has no maximum either. This is a product-level guard, not this PR's defect.
- NIT: a 5xx is described as unreachable. `LabourRateCard.jsx:70` says "could not be reached" for a server error as well.
- NIT: the card never re-reads after a save (`:60`), so a second tab shows a stale "Current rate".
