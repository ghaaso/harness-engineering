2. C63 AND C68 AGAINST THE ROWS (REFUTED BY DEFAULT)

- What "received" is read from. Both clocks are Postgres `now()`, the start time of the writing transaction, so they are the same clock.
  - Documents: `app_event.server_time`, set by `server_default=text("now()")` (`app/features/telemetry/models.py:63-65`; the ingest at `service.py:47-59` sets no time).
  - Writes: `job_event.created_at`, also `server_default=sa_text("now()")` (`app/features/jobs/models.py:275-277`).
- Same instant falls on the safe side (checked in code and by probe P2):
  - `_later_write` skips `e.created_at <= row.receipt` (`:2607`).
  - The C68 path needs `e.created_at > shown`, strictly later (`:2611`).
  - `_last_seen` needs `a.receipt > row.receipt` (`:1220`).
  - The C63 pin check uses `>=` (`:1748`), so a pin at the manifest's own instant counts as a write, not as prior state.
  - Probe results: a write at the report's instant gives `missing`; the owner's write at the manifest's instant with another amount gives `missing`; a pin at the manifest's instant gives `missing`.
- The direction of the risk.
  - A write whose transaction started after the report was received started after the phone built that report, so it came after the phone listed the version.
  - The opposite race lands on the safe side. If the version's own send was in flight while the phone built the report, its transaction can start before the report was received. The write is then rejected, the row reads `missing`, exit 3, and the note says "received before after-report ... showed that version still on the phone" (probe P4 "c68-early").
  - That is a look for the owner, never a wrong `superseded`. Whether the phone can build its report during an in-flight send is a phone-side question; not checked here (INFERRED).
- One write per row (`s.evidence_used`):
  - It is cleared once in `match_rows` (`:1817`), so state matches take evidence before point 15 or C68 can.
  - Rows are then judged in `_judge_order` (`:2437`: receipt, manifest, install, queue, key).
  - Events are sorted by `(created_at, id)` (`:2603`), and `_last_seen` sorts reports by `(receipt, event_id)` (`:1219`).
  - Probe P1 ran three installs over 6 row orders x 24 report orders x 2 event orders, once with distinct receipts and once with equal ones. Every run gave the same outcome set.
  - The lane's `test_c68_one_write_by_the_versions_owner_answers_one_row` covers the case of scarce evidence.
- No crossing to another job, kind or slot.
  - Only events of the row's own job are read (`:2598-2603`).
  - A version has the same key as its row, and the key already names the kind, the job and, for a transition, the action (`transition:${action}:${id}`).
  - The `version.owner` path matches on the version's own kind through `_in_slot`, and an untagged action is refused (`:2536`).
  - Probe P3 results: a bill on another job, a `complete`, `pin` or untagged bill event, and a `closed` event against a `wait` version all read `missing`. Only `on_hold` read `superseded`.
- Voided payment, job closed since, reopened state.
  - `payment` and `void` are not in `SLOT_KINDS` (`:398`), so they never reach point 15 or C68.
  - A job closed since the manifest leaves the row `missing` and judged as any other row; closed before the manifest stays `residue`.
  - Reopen has its own tag, so it never matches another action.
- Read-only and bounded. The delta adds no SQL. The reads are still the existing `ANY(:ids)` / `t_open`-bounded queries inside the one read-only snapshot.
- Tried and could not break: a wrong `superseded` through C68. The after-report lists every queued record of the install, whatever its owner (docstring `:192-195`), and the outbox never deletes. So a version gone from the newest report either landed or was discarded.
- Backlog (not a fix):

  - If that version was discarded by its other owner, the discard appears only in `unmatched_discards`. It is a negotiate or completion, not money, and C68 allows this.
