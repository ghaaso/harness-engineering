G1 (FORCES THE CHANGE; UNSAFE DIRECTION; IT PREDATES THE DELTA)
- What happens. Neither a row's own discard entry nor a discard trace is checked against the row's manifest: entries in `_take_discard_from`, `:2130-2150`, where `elif row.owner:` needs only `owner_t == row.owner`; traces in `_settle_unlanded`, `:2158`. So a discard of an earlier version of the same slot, made before the manifest, clears the row.
- Input that reproduces it. Under build N, t1 discards `negotiate:J` (trace tr0, entry e0), then queues 100 again. Build N+1 snapshots manifest m2, which lists that row. t2's live negotiate on the same phone removes the queued row and lands (N7). The newest report lists nothing and carries e0. Result: the row is `discarded` (by e0, and also by tr0 through the trace path), exit 0. It should be `missing`.
- Owner-less rows have the same hole. The own-entry path takes t2's entry even when the showing report carried it, so C72's carried rule is never asked.
- Smallest fix. Traces: ignore a trace with `server_time <= row.receipt` (the phone sends nothing before the manifest's receipt, `drainGate.ts` step 4, so the server's clock alone is enough). Entries: cancel any entry already carried by an after-report of the same install received before the row's manifest, as a multiset, the way C72 does. A trace of a pre-manifest discard still unsent at the update has no server-side fix. That needs a ruling: for example, the manifest could carry the discard list's length, or the log's local `entry_id`.

BACKLOG (NOT FORCING)
The multiset key includes `at` and `kind`. If a later build ever changed how it writes out stored entries, an old entry would look new: probes with `at` dropped, or `kind` renamed, both gave `discarded`. Sending `entry_id` (already in the phone's log, local only) would make the match exact across builds.
