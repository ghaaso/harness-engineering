- Why the check does not catch it. `takeOrLoad` checks for a head only once, at the start (`drainGate.ts:327`). It then reads (`:365`), writes the parts under keys that do not depend on the manifest (`:379`), and writes the head (`:403`). Nothing stops a second context that passed the check before the first context's head existed. `snapshotStoredNow` (`:489`) sees the faster context's head and allows the discard.
- The sequence (scratch PROBE I, passed): (1) the headless context starts its snapshot, sees no head, and stalls in its read; (2) the foreground starts, sees no head, and takes and stores its own head (manifest F); (3) a discard in the foreground passes `snapshotStored` and appends entry E; (4) the headless read finishes now, so it sees E and the row; (5) the headless context overwrites the same part keys and the head (manifest S, a different `manifest_id`); (6) the foreground removes the row.
- Result: the stored manifest S holds `discards: [E]` and `records.outbox: ["pay-1"]`. Under point 9 this reads `missing`, exit 3.
- The same race also costs: the slower context overwrites the faster one's parts under the same keys. If F was already uploaded, the phone's stored head now has another id.
- How real it is: it needs two JS contexts both starting their first snapshot of a build together. The bootstrap expects exactly that: a headless task on MY_PACKAGE_REPLACED (`lib/syncGate.ts:5-7`). It is still a device unknown, and the discard has to fall inside the slower snapshot's few seconds.
- Smallest fix: in `takeOrLoad`, read the head key again after `readAllRaw` and before writing any part. If a head now exists, give up this snapshot and load that head instead. Any discard needs a stored head, so a snapshot that gets through this check did its read before any discard could happen. It also stops the part keys being clobbered. A gap of a few ms remains between the check and the head write, because AsyncStorage has no compare-and-set; name it in the comment.
