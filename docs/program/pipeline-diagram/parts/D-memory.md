## Flow
(1) INTO the store.
KS design: solver (Opus/Fable) resolves a problem that needed escalation, 2+ failed approaches or a burned build -> ks record (fixed schema, with ruled-out approaches from the PR journal) -> write gate (scrub, near-duplicate, missed-existing check, selectivity, precision check on known-good code, self-match refusal, mainline sha) -> ks capture (footprint, preconditions) -> ks control (control pair, mutants, inject-control) -> entry lands provisional, inert as a lead -> PR's Opus reviewer (never the author) refutes, re-runs controls, ks approve -> journal commit pushed -> after merge ks close anchors the fix to the squash commit. Cheap agents may only append mechanical events and proposals (need Opus accept or a second independent confirmation). Wrong entries kept out by: fail-closed scrub, control pairs, approver-not-author, blind re-ruling, refutation scoped to a footprint, withdrawn/superseded status (never deleted).
LIB (built): any session writes a record to its own journal file when the thing becomes true, with evidence; hook refuses non-append edits; pre-commit refuses invalid records; a correction is a new record with supersedes; child sessions only propose corrections, the top session adjudicates; the top session rebuilds the board by hand; summary/textbook figures never used for decisions (read the source, write a quoted record).

(2) OUT of the store.
KS design: trigger = about to escalate, retry a failed build, apply a prescribed fix, or at first commit/PR-ready/review/close for a diff -> ks lookup (canonicalise, scrub, prefilter by handles/status/facets, rank, abstain) -> miss / candidate / lead line, capped 2,000 chars; pull-only, nothing injected -> ks verify runs the entry's check and preconditions on the caller's tree -> only "applies" releases the fix text -> apply, re-run the original failing command, record outcome; on miss, ks claim and escalate passing only the lookup id. Do-not-apply warnings are never withheld but go to the reviewer.
LIB (built): hook injects the board at session start; session runs lookup.sh or grep; if nothing, say "not recorded"; before relying on an x-record, read the place it cites.

## Loops
- Outcome loop (KS): resolved/not_resolved after a verified hit -> confirmed counter, proposed handle, or refuted at that footprint plus Opus revision.
- Gate_absent loop (KS): not_applies on a shown solved hit -> proposed not_when (inactive until Opus accepts).
- Missed-existing loop (KS): a miss later ruled "same" as a stored entry -> proposed_handle from the missed wording; counts k of n feed the embeddings trigger D16.
- Invalidation loop (KS): footprint/dependency/platform change -> suspect -> verify re-runs controls -> reaffirmed or controls_broken -> Opus revision.
- Compliance and checkpoint loop (KS): KS-9 reads hit rate, false leads, late catches (missed_dna), unavailable share, cost -> continue, extend once or retire; size checkpoint at about 1,000 entries recalibrates thresholds.
- Pilot self-grading guard (KS): thresholds frozen at KS-4 so KS-5 cannot tune them.
- Recall test loop (LIB): test questions -> changes to board and lookup.sh -> test again.
- Library stock loop (LP model): good entries age into bad, bad entries retire slowly; stock feeds coverage and wrong-entry share; promoted checks from good entries reach every gate.
- Promotion loop (D17): validated trap -> CI test -> no lookup needed.

## Jargon
journal: file history that is only ever added to. index: search database rebuilt from the journal. footprint: files and settings an entry depends on. trace: fingerprints of the footprint when last verified. handle: a search key for an entry. canonical template: error message with variable parts masked. BM25: standard word-matching relevance score. FTS5: SQLite full-text search feature. IDF: how rare a word is. coverage: share of the query's rare-word weight an entry matches. margin: coverage gap between first and second result. abstain: return nothing when unsure. lead: hit trusted enough to verify and use. candidate: weak hit shown for information. gate: check that must pass before acting. control pair: known-bad and known-good case a check must separate. mutant: deliberate small code change to test a check. precondition: extra fact a check needs to be valid. early cutoff: skip rework when a recheck shows nothing changed. do-not-apply entry: record warning that a suggested fix is wrong. open defect: known unfixed bug entry. pull-only: store speaks only when asked. Lamport counter: logical clock ordering events. fold: compute current state from events. stale: out of date. supersede: replace by a newer record. adjudication: final decision between conflicting records. top session: the session the owner talks to. child session: session started by another from a brief. tier: model class (Haiku, Sonnet, Opus, Fable). escalate: hand a problem to a stronger model. ladder: cheap try, retry, Opus, Fable order. funnel: stages a reused answer must survive. promoted check: stored check moved into shared tests. lexical retrieval: matching by words, not meaning. embedding: numeric meaning vector of text. Clopper-Pearson: confidence bound for a proportion. reasoning cache: store of solved reasoning for reuse. cache read: re-reading already-cached prompt tokens.

## Unclear
- Two memory stores overlap: KS (designed store with command-line tool, database and checks, for FixFlow) versus LIB (built journal + board for harness research). KS stores problems with machine-run checks and invalidation; LIB stores rulings, facts, mistakes as text with no checks ("footprint: nothing checks it yet"). Documents do not say whether LIB is meant to become KS or replace it; LP says its case judgements partly used KS (126 of 590 step judgments).

- LP/PLR counts differ between versions (PLR: 37 states, 75 branches, 57 unknowns; LP: 40 states, 83 branches, 61 settings). LP is later.
- KS says the store injects nothing (no hook) but D21 proposes an optional edit-time hook; LIB does use a start hook. Different stores, different rule.
- Whether the KS pilot (KS-5) ever ran: not stated. Verdict on the library overall: not stated (LP "no judgment").
- Fix withholding in KS is a CLI behaviour only; agents could read the journal files directly (KS 9).
