# A7 option 3: calibrated per-file probability, weighted
Lens: graph first. The same graph model, but the output is a probability per file, not a place in a list.

**Mechanism.** *Output.* p(Q,v) = sigmoid(s(Q,v) + b_Q). s is the question-relative score of the graph model; slot nodes for new files are as in option 1. b_Q = logit(r_R,t) is a base-rate offset computed, not learned. r_R,t is the mean number of other files per unit, over files alive, in the repository's units before t. So "1 in 40" and "1 in 40,000" repositories start from their own rate (M3, no identity).
*Loss.* A weighted binary cross-entropy. It is a sum over files, so a Horvitz-Thompson weight gives an unbiased estimate of the full loss over all alive files (D 3.2). The log-of-sum bias of option 1 does not arise:
L(Q) = -sum_{p in P} log p_p - sum_{n in N_in} log(1 - p_n) - sum_{j=1..m} (1/(m pi_j)) log(1 - p_{n_j}).
N_in is the neighbourhood candidates, all scored. The n_j are drawn from the remaining alive files, excluding P, with known pi_j.
*Use.* The agent reads files in order of p until the sum of p reaches its budget. The expected number of right files is sum_v p_v. A slot with high p says a new file belongs there.
*Weights.* omega_Q as D11. No 1/|P| here: each file is its own event.

**Needs from other parts.** A1.a.1, A2.a.1, A3.a.3 or A4.a.1, A5.c.1, as option 1. A6: C(Q) and pi. A9: the base rate computed once per asking time. A10: a reliability reading per repository.

**Can.** Say how many files are right, and how sure. Several right files are natural: they are independent events. M7 by construction: known probabilities, no right file as a negative, an unbiased full-set loss. M3: the offset carries the repository's scale. M2: the exact channels pass as in option 1.

**Cannot.** Aim at the top of the list: a model calibrated on average can still misorder the first ten. It is fitted on probability, not order. Keep variance down when pi_j is small: a uniform draw over 50,000 files weights each drawn negative 50,000/m, so one high-scoring far file swings the loss. Hence pi must lean on A6's retrieval score. Stay calibrated if a repository's habits differ from its own past: after a move to squashed pull requests, r_R,t is wrong until the history catches up. Nearest veto W9: P is excluded from the draws. W3: b_Q is a statistic recomputed at t, not a stored code.

**Rests on.** D 3.2, D 2.9, D 7.4, D11, D12; N 13.6, N 9.5; assumption: the harness needs a number of files, not only an order, since its cost is the files read. Count first: per repository, the spread of r_R,t over time.

**Refuted if.** On unseen validation repositories, the share of right files among those with p in a bin departs from the bin's p beyond the resampling interval, worst in the smallest and largest strata. Or sum_v p_v does not track |P| better than a constant per repository.
