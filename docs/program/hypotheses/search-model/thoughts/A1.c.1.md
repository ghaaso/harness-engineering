# A1 option 1: exact typed path sums, ranker reads
Lens: exact relational computation first. Whatever can be computed exactly from the store relative to the question is computed, and a learned ranker reads it.

**Mechanism.** The store, cut at the asking time t, is read as a typed directed graph: question q, starting files S (linked by "in the change", "named in the text", "in the trace"), events e (units of work, commits) with size |e| and age a_e = t - time(e), files, and the D5 links (import resolved / unresolved-by-name, use, test by import, test by name, folder). For each candidate c the model reads a vector of exact sums over a fixed set P of typed path patterns of length at most two from q to c, each pattern fixed by the relation kinds the data has, not by search:
- history: F_{k,tau}(q,c) = sum_{s in S_k} sum_{e : s,c in e} 1/(|e|-1) * exp(-a_e/tau), for each starting kind k and each tau in a fixed bank of time scales; the same with weight 1 (raw count); the youngest age; and J(q,c) = number of events holding c and at least two starting files;
- code links: count of each link kind s -> c and c -> s, and of each two-step pattern s -r1-> x -r2-> c;
- symbols: number of names used or added in the question text, diff or trace that c defines; number of paths or strings in the text that resolve to c;
- text: BM25 of the question against c's path and content, idf taken from the files alive at t; cosine between the question and c's chunks under a frozen pretrained code-and-text encoder (cut-off before the test cut-off), as max and top-3 mean.
Question-independent features of c: degree per link kind and direction; decayed change rate; age; size; test flag; folder depth; language.
Every amount enters three ways: log(1+x); its percentile among the candidates of this question; x over the largest value among them. The repository's description (size, history length, merge habit) enters as a few relative numbers beside them. A missing value is a flag, never a zero. A learned ranker reads the vector.

**Needs from other parts.** A3/A5: the tau bank and whether decay is also learned. A6: the candidate set. A7: the ranker's form and loss. A4: the final list of patterns.

**Can.** M2 by construction: the decayed one-over-size count is F itself. M1 by construction: every feature is a function of (q, c), so two candidates with the same surroundings differ when their paths to q differ. M3 by construction: no identities, amounts relative. M4 by construction if the loader cuts the store at t. M5 by construction for the listed kinds and directions, parameters bounded by |P|. M6 in part: symbols and text reach files with no history. M7: computed once per question on a processor, linear in the events touched.

**Cannot.** It is the hand-built table of D 9.2: a pattern not in P is lost. Counterexample: c was co-changed with a file that imports a starting file (three hops) and that is the true signal; no feature sees it. Text meets code only through scalars: a diff renaming an argument that c's call sites must follow is invisible unless the name is in the symbol set. Nearest veto W10 (a tree on amounts): avoided, amounts are relative. W12: P follows the relation kinds, not a sweep.

**Rests on.** D 9.2, D 9.4, D 7.5, D 8.1, N 9.5, N 9.10, N 13.9; record: `research-tree/build/improve/units/T3/report.md` item 1; record: `research-tree/build/improve/units/T2/report.md`; count first: the share of right files reached by any pattern in P, per repository.

**Refuted if.** A learned relational model (option 2) beats it on the right files that no pattern in P reaches, on unseen repositories.
