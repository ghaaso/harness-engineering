# A5 option 2: time-respecting messages, time-free frozen LM
Lens: language model first; this option departs from it. The material puts time in the computation graph (N 13.9), and language models "are NOT trained to predict the future"; here the graph carries all of time.
**Mechanism.** The LM encodes content only, keyed by content hash (D3, D5). A hash's vector does not depend on the asking time and is computed once. Which hash a file has at t is chosen by the tree at the main-line state before t.
Time lives in a relational graph built per question at load: only events with t_e < t, sampled by a recorded design (D 9.4). A message from event e to file c is m_e = g(phi(a_e), |e|, kind) * h_e, aggregated by sum (N 9.5). a_e: age in repository units; h_e: the event's vector; g: a small network. phi(a) = [exp(-a/tau_1)..exp(-a/tau_K), cos(omega_j a + b_j)]: a fixed decay bank (keeps the exact count reachable) plus learned periodic terms (order and rhythm). On two-hop paths the order of the two events is an input. With h_e = 1 and g = w(|e|) exp(-a/tau_k), the message sum is exactly the decayed, size-weighted count.
**Needs from other parts.** A1: the content encoder and the per-hash cache. A3: how event messages reach the candidate's score. A4: the kind in g. A9: the sampling design and its probabilities. A7: the head.
**Can.** M4 by construction: messages and sampling depend on t (D 9.4), and the LM holds no time. Its pretraining may have read later public versions; the D12 reading by creation date stays. M2 by construction: sum aggregation with the fixed bank (N 9.5); a learned g can add terms but cannot remove the exact path. M3 by construction: coefficients only (N 3.1), ages in repository units.
**Cannot.** The LM cannot weigh a commit message by its age against the question's text; time and text meet only in g and in the score head, so "the newest change says the opposite" is invisible. With neighbour sampling the count is exact only in expectation, unless sampled events are re-weighted by one over their probability (D 3.2, D 2.10). Nearest veto W4 (the recorded time-ordered models read only the 20 to 32 latest events); not under it, since the sum runs over every event before t or a sample with known probabilities. Nearest W2: no mean, no softmax over events.
**Rests on.** N 13.9; N 9.5; N 3.1; D 2.10, D 3.2, D 6.2, D 9.1, D 9.4. record: `research-tree/build/improve/units/T3/report.md` items 2, 4, 7, 8. assumption: periodic terms help only if rhythm matters; their weights test that. count first: events per file before t, to know whether sampling is needed.
**Refuted if.** Removing the periodic terms, fixed bank kept, leaves validation unchanged and the learned g matches one fixed kernel: time then needs no learning. Or option 1, with time read by the LM, scores higher on the same examples, per repository.
