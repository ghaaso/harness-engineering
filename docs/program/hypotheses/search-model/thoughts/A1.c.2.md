# A1 option 2: raw rows, trained encoder, sum aggregation
Lens: exact relational computation first. This option departs from it: the material (D 9.2, N 13.9) says a fixed feature table loses whatever it did not foresee, so the model reads the rows themselves.

**Mechanism.** The input is the relational entity graph of D 9.3 cut at the asking time t, not features. Node kinds: question, file, event, symbol. Each keeps its own columns:
- question: its text, diff or error text, as token chunks;
- file: its content at t, as chunks; path tokens; size, language, test flag;
- event: size |e| and age a_e = t - time(e), entered as log(1+|e|), 1/|e|, and a fixed sinusoidal code of log(1+a_e) (no learned table of times);
- link: one-hot kind and direction as an edge feature.
Text and code go through one pretrained encoder (cut-off before the test cut-off) that is trained further on training repositories and training times only (D 6): contrastive, question chunks against the chunks of right files. Its output is a node feature, not a score.
Relativity is put in the input, not learned: every node carries marks "is a starting file of kind k", "is the question", "is the candidate" (root marking, N 9.10). Messages are summed, never averaged, so counts pass (N 9.5); a message from an event is multiplied by its 1/|e| and its time code (N 13.9). Other amounts are made relative to the repository: log of the amount over the repository's median at t.
Exact quantities are not dropped: the one-over-size decayed count F of option 1 is an attribute of the candidate's link to the question, so the learned part only has to add to it.

**Needs from other parts.** A4: weights per relation (shared basis). A6: which subgraph is loaded per question. A9: the cost of training the encoder. A2: how the marked question meets the candidate.

**Can.** M2 by construction, through sum and the 1/|e| weight on messages. M1 by construction, through the marks. M3 by construction (no identities, no table of times). M4 by construction if the loader cuts at t. M6 in part: content similarity links any file with related text directly; two-hop patterns no one listed can be learned. It learns aggregates option 1 did not foresee (D 9.2, N 13.9).

**Cannot.** Reach past its layers (N 5.5): a three-hop pattern needs three layers and over-squashes at large folders and hub files (N 11.1). Count cycles beyond what its marks give (N 9.6). A trained encoder can fit the training repositories' vocabulary: a repository whose words are all new may get weaker text features than a frozen encoder would give, so transfer rests on the held-out test. Nearest veto W7 (features without the graph): it carries the graph by its edges. W5: far reach is not left to layers alone; content similarity reaches directly.

**Rests on.** D 9.2, D 9.3, D 6.4, N 9.5, N 9.10, N 13.9, N 8.4, N 11.1; record: `research-tree/build/improve/units/T3/report.md` items 3 and 5 (a graph part with mean aggregation scored below counting without the count features); assumption: summing with 1/|e| on messages repairs what mean aggregation lost there, because N 9.5 names the mean as the cause; count first: the largest event and folder sizes per repository (hub cost).

**Refuted if.** On unseen repositories it does no better than option 1 on the right files outside option 1's patterns, or its trained encoder scores below the frozen one on repositories created after the cut-off.
