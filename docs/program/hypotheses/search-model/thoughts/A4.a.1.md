# A4 option 1: rooted relational sum, shared bases
Lens: graph first. The model computes on the typed neighbourhood handed over by the data, with the question as a node of it.

**Mechanism.** Relations are the link kinds of D5/D14, each taken twice, forward and reverse: question to file (in the change, named in the text, in the trace), import resolved, name matched but unresolved, use, test by import, test by name, folder to file, file to event. That is about 11 kinds, so R = 22 relations. Each layer computes, on the neighbourhood cut at the asking time t:

h_v' = sigma( W_0 h_v + sum_r sum_{u in N_r(v,t)} g_r(e_uv) W_r h_u ),  with W_r = sum_{b=1..B} a_rb V_b.

- There is no division by |N_r|. Aggregation inside a relation is a sum, and across relations it is a sum too (N 13.3), so counts survive (N 9.5).
- g_r is a gate computed from the edge's own amounts (an event's size and age). Through event nodes, the message from start file s to candidate c is a sum over their shared events e of g(size_e, age_e).
- B basis matrices are shared by all relations, so the parameters are B d^2 + R B per layer. They grow by B numbers per added kind, not by d^2 (N 13.2).
- The question node carries a mark, and so does each start file, by its kind of link to the question (marking the root, N 9.10). A candidate's vector is therefore computed from a question-specific rooted subgraph. The score is read from the candidate's last-layer vector (N 5.4).

**Needs from other parts.**
- A1: node inputs and relative amounts.
- A3/A5: the form of g, which must be able to express exp(-age/tau)/size.
- A6: far files.
- A9: neighbour sampling reweighted by its known probabilities (D 2.9), because hubs explode the computation (N 14.2).

**Can.** Direction: forward and reverse have their own maps, so "A imports B" is not "B imports A" (N 2.2, N 13.2). The relation patterns of N 13.8:
- Antisymmetry: separate maps.
- Symmetry: folder and co-change pass through a shared folder or event node, so they are symmetric by structure.
- Composition: chained linear maps compose ("linear functions are chainable"), for example the test of an import.
- One-to-many: no tail is forced onto a point.

Levels:
- M5: by construction.
- M2: by construction for the joint-change count, given g.
- M1: by construction, through the rooted mark.
- M3: by construction (no identities; the coefficients do not depend on the graph, N 8.1).
- M4: rests on the loader (D 9.4).

**Cannot.**
- See past L hops (N 5.5).
- Tell apart candidates whose typed rooted subtrees and inputs match (N 9.4, N 9.8). Counterexample: two test files of one module, both linked by name and by import, neither changed before, get the same score.
- Give a rare relation (in the trace, where error data is thin) a direction outside the span of the shared bases.
- Keep an unnormalised sum on a scale that transfers: a file imported by 2,000 others gets a huge sum unless amounts are relative to the repository.

Nearest vetoes:
- W2: avoided, because it sums.
- W8: avoided, because there is no shallow scoring rule.
- W5: avoided only if A6 supplies reach.

The measured GraphSAGE model differed from this option in three places: mean aggregation, no root mark, kinds collapsed. So its null does not bear on this option (record: `research-tree/build/improve/units/T3/report.md`).

**Rests on.** N 2.2, N 9.4, N 9.5, N 9.10, N 13.2, N 13.3, N 13.8, N 14.2; D 2.9, D 9.4; record: `docs/program/hypotheses/search-model/FACTS-MODELS-SO-FAR.md`.
- assumption: the link kinds are different interactions (N 13.1).
- count first: per kind, the share of mutual pairs, the fan-out and the share of right files it reaches.

**Refuted if.** On validation repositories, read per repository, the same network with all kinds merged into one relation plus a one-hot kind feature (N 13.1) scores within this one's interval. Or this network, given only event links, cannot match the counting baseline.
