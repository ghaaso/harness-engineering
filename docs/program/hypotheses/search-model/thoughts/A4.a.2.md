# A4 option 2: typed path counts as structure features
Lens: graph first. This option departs from it: the graph is not learned over. It is turned into exact counts of typed paths.

**Mechanism.** Every relation r (the kinds of D5/D14, forward and reverse) is a sparse matrix A_r cut at the asking time t. Its entries are 1, or, for file-event links, a weight g(size, age).

For a question q with start set S, every candidate c and every relation sequence pi = (r_1..r_k) with k <= K:

P_pi(q,c) = [ A_{q->S} A_{r_1} ... A_{r_k} ]_{q,c}

- It is computed once, outside training, by applying the matrices one after another from the start set (N 2.3, N 14.4).
- Example: "start file, its event, the event's other files" gives the decayed, size-weighted count of joint changes exactly.
- Each count is expressed relative to the repository's distribution of the same path type (D 8.1).
- The scorer takes [log(1 + P_pi)] with a learned coefficient per path type, together with what A2 supplies.

Two bounds keep the number of path types small:
- K.
- Only types that occur in enough training repositories are kept, fixed on training data (D 6.4). Count first.

**Needs from other parts.**
- A1/A2: content and question features.
- A3/A5: g.
- A7: the scorer and its loss.
- A6: candidates beyond K hops.

**Can.**
- Direction and composition, by construction: a path type is a composition with its order kept. "Imported by a test of a start file" differs from "imports a test of it".
- Antisymmetry and inverse: reverse relations are distinct sequences.
- Symmetry: a co-change through an event reads the same both ways.
- One-to-many: these are counts, not points.

No relation kind of the data is unrepresentable, so W8 is not met.

The counts are exact, and no aggregation can lose them (M2 by construction, N 9.5). They are powers of typed adjacency, the inductive structure features that lift message passing above 1-WL (N 9.10). M3 by construction, since only per-type coefficients are learned. M5 by construction. M1 in part: paths start from the question's own start set.

The record points here: the hand-made count features carried the graph network's whole score (record: `research-tree/build/improve/units/T3/report.md` items 5, 6). This option keeps that strength and adds typed composition and direction.

**Cannot.**
- See what lies along a path. Counterexample: two imports of length two, one through a utility hub that every file imports and one through a module of the same feature, count the same. A learned message could weight them by the middle file's content.
- Form aggregates it was not given. Its path types are chosen beforehand (D 9.2: "features are chosen arbitrarily"; a lossy projection, D 4.3).
- Score a path type unseen in training. On a new repository with an unseen kind (a language whose imports cannot be resolved), that type has no coefficient.
- Reach past K. The number of types grows as (2R)^K, so K stays small.

Nearest vetoes:
- W7: avoided, because the counts are the graph.
- W10: avoided only because the counts are relative.
- W5: met unless A6 supplies reach.

**Rests on.** N 2.3, N 9.5, N 9.10, N 13.8, N 14.4; D 4.3, D 6.4, D 8.1, D 9.2; record: `research-tree/build/improve/units/T3/report.md`.
- assumption: right files are reached through short typed compositions. This rests on the 8.5, 45 and 11 points of right files that lie within two hops of imports and folders (`docs/program/hypotheses/search-model/FACTS-MODELS-SO-FAR.md`).
- count first: right files reached per path type and per K, by repository.

**Refuted if.** On validation repositories, path counts with the kinds merged (untyped paths) score within the typed ones' interval. Or a learned relational network (option 1) on the same neighbourhood scores above this option per repository, in the segment of right files that have a code link but no joint change.
