The data: what is wrong with it, and what to build instead

Nothing was built, collected or downloaded for this. It is the argued plan for the data that the model will be trained and tested on. The second hypothesis, for the model, follows.

The answer in short

  1. The current data cannot carry the goal, and most of the fault lies in what was collected, so repair is not enough. Three repositories that were at hand; the history cut down to file lists and then to pairs; commit messages reduced to their first line; no content; commit messages used as "task words"; nothing for the error question.
  2. Rebuild the collection. Repositories are drawn at random, by a stated design, from a list of all public repositories active in a stated year; whole repositories are held out; the owner's two are never trained on.
  3. Keep the raw record (the clone and the host's answers) and derive from it a store of single, time-stamped facts. Every input and every label is built from that store as of the moment of the question.
  4. Three questions, three kinds of example, each in tiers by how real its question is. The error question is the weakest part of any design: real error texts tied to a fix exist only where projects report them or keep tests that run. How many there are is the first count.
  5. Before any training: seven counts, the first three on the repositories we already have, with no download.

Limits, said plainly

  • The merge was one pass by one mind. No rival merge was made, the merged design was not scored by the same recorded steps as the five designs, and where the designs disagreed I chose in that pass or put the point off. A real graph of thoughts would have worked on exactly those points. That is the weak spot of this hypothesis.
  • The four runs were given the yardstick, which already demands a lossless store, a designed sample and time-correct inputs. That all five designs agree on those points repeats the yardstick; it is not independent proof. The runs earned their place by what they added beyond it.
  • Hiding which design was which from the judge would have hidden nothing: the starting points show in the text and one design is my own. So every verdict is recorded with the entries it rests on and can be checked.
  • This cannot prove the design right. It gives the best-argued one and names the counts that are still needed.

What is wrong with the data we have

  1. Three repositories, taken because they were at hand, all three in training and in test. One is 82 % of the pooled score. Nothing can be said about a repository never trained on. (Data 1.2, Data 2.6, Data 3.1; Model 8.1, Model 8.4)
  2. A commit is stored as a list of paths. No diff, no content, no symbols, no author, no pull request, no issue. What was not recorded no model can recover. (Data 9.2, Data 4.3)
  3. The message is the first line only. The extraction asks git for the subject line and cuts that to 600 characters; the body is never read. (Data 1.1; our own record)
  4. Records are capped and dropped while collecting. No merges; seven file endings; only commits of 2 to 50 code files; an added file is never a right file. Afterwards a cap cannot be told from the world. Leaving files out by their ending is also a node sample of the repository's graph: links to left-out files are never seen. (Data 1.1, Data 2.1)
  5. Models were fed pairs and yes-or-no facts. From pairs the changes cannot be rebuilt. (Data 4.3, Data 4.8; Model 9.5)
  6. A content input was empty for 88 to 99 % of the training cells of two repositories. A gap made by collection is a pattern a model learns and the test does not share. (Data 5.3, Data 3.3)
  7. Too little reach. 30, 66 and 21 % of the right files never changed with the starting file before; imports reach 25, 18 and 25 % of right files, folders 29, 18 and 37 %, names 6 to 9 %. No references, no test relations. (Model 5.5; our own record)
  8. The "task words" were commit messages, written after the change, with the edited paths removed by script. That is a text written after the answer was known. (Data 6.1; our own record)
  9. Links are recorded with silent gaps. Imports come from a line pattern; what it cannot resolve is dropped, and a failed search leaves an empty list with no mark. A missing link cannot be told from an absent one. (Data 1.1, Data 5.3)
  10. Time is the commit time of a flattened history. A commit made on a branch counts as history from its own date, although nobody on the main line could see it before the merge. How often this happens is a count. (Data 9.4, Data 4.4)
  11. The cut-off is per block of 10 or 20 commits, not per question. Not a leak; a gap that real use does not have. (Data 7.1)
  12. A commit of n files gives n examples, and the largest repository gives most of them. The one-over-n weight was found by trial; it is the correction for sampling by events and should have been derived. (Data 2.2, Data 3.2)
  13. The yardstick has a ceiling of about a quarter and is read pooled. (Data 7.3; Model 13.6)
  14. Nothing is stated or tested. No keys, no automatic leak test, no description of each repository. (Data 4.2, Data 4.5, Data 6.3)
  15. The error question has no data at all.

What is sound and kept as rules: a strict "before" cut in time, a file identity that survives renames, naive baselines beside every model, results per repository. (Data 6.1, Data 1.2, Data 7.2, Data 7.3)

2The population, the list and the draw

The options weighed

  • (a)The three at hand.not chosen
  • (b)Popular repositories, a curated list or a ready benchmark set.not chosen
  • (c)A crawl outward from known repositories.not chosen
  • (d)The host's search, sliced until every slice is complete (Repair).not chosen
  • (e)A plain random draw from a list.not chosen
  • (f)A stratified random draw, in two phases, of clusters of repositories from the public archive of the host's events (Population).chosen

The choice

(f).

  • Population. Public repositories whose main line received changes of several files during a 12-month window ending at a cut-off date, with a stated minimum of history. The minimum is set after the list's spread is seen, with the owner's two well above it. It defines the population; it is not a cap on records.
  • List. Every repository with a push in that window in the public archive of the host's events.
  • Unit. A cluster: forks and copies are one project (fork link, shared first commit, shared content after cloning).
  • Draw. Phase one at random from the list by what the archive shows (activity, number of people pushing). For that draw the host's public description is fetched. Phase two is drawn from phase one by size, length of history, main language and date of creation. Small repositories and short histories are over-drawn. Every cluster keeps its probability of inclusion.
  • Held out. Test and validation clusters are drawn first, from every stratum, and removed before training is drawn.
  • How many. Computed from a pilot of about 30 drawn repositories: the spread of a baseline's score between repositories against its spread inside one. Until then, for planning only: about 150 test and 60 validation clusters, and between 400 and 1,500 for training.
  • Licence. Recorded per repository. Nothing collected is passed on to anyone. Whether the list is limited to licences that plainly allow this use is the owner's ruling; until he rules, no repository is left out for it.

Why

The repository is the unit of the claim, so it is the unit that is sampled, held out and averaged over. The entries on sampling speak of the nodes of one graph; they are applied here, by extension, to repositories drawn from a population. Population is the only design whose list is a census of what it defines, which is what makes a random draw possible at all. Strata are limited to what the draw must control; a team's habits (how it links issues, how it packages changes) are measured per repository and used to read results, since more strata leave cells that cannot be filled. The five designs' planning numbers range from 400 to 3,000 because none could compute them: they follow from the pilot.

Why the others lost

(a): a convenience sample (Data 1.2, Data 3.1; veto: a sample of convenience read as general). (b): chosen on a trait tied to the outcome, large and team-made, the opposite of the owner's kind; a set chosen by others by unknown rules (Data 2.8, Data 1.1; Model 8.4). (c): exploration over-samples the well connected and makes samples look alike whatever the truth (Data 2.3, Data 2.8). (d): not ruled out by an entry; set aside because a search index is a recording of unknown reach and its completeness cannot be checked (Data 1.1); kept as a cross-check on the pilot. (e): sound but wasteful: most draws are tiny or dead, and the kinds that must be read alone get too few (Data 2.7).

It rests on

Data 1.2 Data 2.3 Data 2.6 Data 2.7 Data 2.8 Data 2.9 Data 3.1 Data 3.2 Model 8.1 Model 8.4 assumption (its reasoning is in "why") count first: the size of the list and its spread by activity, size, people and language count first: a pilot of 30 drawn repositories our own record

It is wrong if

The pilot shows scores differ little between repositories beside their spread inside one (a few repositories processed deeply would then do); or the owner's two lie outside every stratum; or clustering after cloning joins so many clusters across the split that the weights lose their meaning.

3What is stored: the raw record, and beside it a store of single facts

The options weighed

  • (a)File lists per commit (now).not chosen
  • (b)One wide table of examples with features.not chosen
  • (c)A graph of files with joint-change edges.not chosen
  • (d)A store of yes-or-no facts.not chosen
  • (e)Two layers: the raw clone and the host's answers kept untouched; a derived store, one fact per row, rebuilt from the raw layer by code.chosen

The choice

(e). The derived store follows git's own form (Code): content by its hash; the tree of each commit; each commit with its parents, both of its times and its full message; each change with old and new content and lines added and removed, merges included, nothing filtered. Beside these: when a commit reached the main line; the facts parsed from a piece of content, keyed by that content alone; their resolution, keyed by the tree; pull requests with their commits in order; issues with every version of their text; links between them with kind and time; error texts with their source; the repository with its cluster, stratum and probability. Rules about which commits count (endings, sizes, merges) are views, each written down. Authors are resolved (one person, several names) and stored as a keyed code per repository, never as text. Changes made by bots and generated files are flagged.

Why

The raw layer makes "nothing was lost" a test, not a claim: the store must be rebuildable from it. Facts that become known at different times sit in different tables, so none waits for another. Keying parsed facts by content alone, and their resolution by tree, keeps each dependency inside one table, where a key enforces it for free. Authors are personal data and an entity that needs resolving; bots are the recording system acting on itself.

Why the others lost

(a), (b), (c), (d): each is a projection from which the recorded changes cannot be rebuilt, and (c) turns the change, an event with its own time, size and text, into an edge (Data 4.3, Data 4.8, Data 9.2, Data 9.3; veto: a projection that cannot be rebuilt).

It rests on

Data 4.1 Data 4.3 Data 4.4 Data 4.7 Data 4.8 Data 4.9 Data 9.2 Data 9.3 Data 1.1 Data 1.2 Model 13.9 our own record

It is wrong if

A diff rebuilt from the store differs from git's for any sampled commit, or a derived table cannot be rebuilt from the raw layer by its code.

4How deeply each repository is processed

The options weighed

  • (b)Two tiers (Population): thousands with history and file lists only, a few hundred with everything.not chosen
  • (c)Depth by what is dear: everything that comes from git for every sampled repository; the host's records for a sub-sample drawn with known probability; re-run tests for a sub-sample of that.chosen

The choice

(c). The second sub-sample over-draws repositories that link issues to fixes, with the probability kept. That habit can be estimated from the clone alone (merge messages and closing words), before any request to the host.

5What is taken from the code itself

The options weighed

  • (a)History only.not chosen
  • (b)Imports and folders by a line pattern (now).not chosen
  • (c)A parser per language over every piece of content, with resolution per tree.chosen
  • (d)A language server per snapshot.not chosen
  • (e)Stored text embeddings in place of content.not chosen

The choice

(c). Per piece of content: what it defines, the names it uses, its imports as written, strings that look like paths or routes, comments; its size and language. Per tree: imports and uses resolved to files, each failure kept with its reason. Test links of two kinds, by import and by name, each with its rule. Folders. A name that matches but cannot be resolved is a kind of link of its own. Every kind of file is kept; how deeply it could be parsed is recorded. The diff of every change is kept.

Each kind of link keeps the rule that made it, because what counts as a link depends on how it is found. A failure with its reason is a value; a silent gap is not. How far references and test links reach has never been counted here.

6Time: when a fact became visible, and the moment of asking

The options weighed

  • (a)Commit time in a flattened history (now).not chosen
  • (b)Author time.not chosen
  • (c)A cut per block (now).not chosen
  • (d)Every fact carries the time it became visible; the loader serves a question only facts visible strictly before its asking time.chosen

The choice

(d). A commit's content and changes are visible from the time it reached the main line; an issue text from the time of that version; both commit times are kept, and a rewritten history is flagged where they disagree. The asking time is defined per question (decision 8 to decision 10). The loader asserts, per example, that nothing served is dated at or after it. Whatever is learned from data (word weights, scalers, any tuning of an encoder) is learned on training repositories and training times only.

The time a fact was recorded and the time it could be known are two facts and belong apart. Putting the cut in the loader makes it a property of the data path, not of each input's author.

7The cuts: by repository and by date

The options weighed

  • (a)A split in time inside each repository (now).not chosen
  • (b)A split by repository alone, each held-out repository asked over its whole span (Code, Questions).not chosen
  • (c)A split by repository and a cut-off date together (Population).chosen

The choice

(c) for the main reading, with three stretches of time: training facts; then validation questions, on which every setting is chosen; then, after the cut-off date, test questions. A gap as long as one change usually lives separates the stretches, so that one piece of work never straddles a boundary. The cut-off date is set no earlier than the training cut-off of any pretrained part the model uses: no such part can then have read the answers of the main reading. Test repositories with no question after the cut-off are counted and reported.

Why

It is how the model would be used: trained up to a date, then met with a repository it has not seen. The two readings are both computed, and their difference measures what the later knowledge was worth; so the disagreement between Population and Code is settled by a number, not by preference.

Why the others lost

(a): no repository is unseen (veto: no whole repository held out). (b): not ruled out; a model trained on later years of other repositories answers earlier questions, which is knowledge of the future in the plain sense of Data 6.1. N's objection is that a date cut throws questions away. Kept as a second, marked reading.

8The change question

The options weighed

  • (a)One changed file asks for the others of its commit, by path only (now).not chosen
  • (b)The same with the file's own diff as input.chosen
  • (c)The first commit of a pull request asks for the files its later commits touch.chosen

The choice

(c) as the first tier and (b) as the second, marked. The unit of work is the merged pull request, else the commit. Asking time: the first commit, read against the main line before it. "First" is by author time, since rewriting a branch resets commit times; a rewritten pull request is flagged. Why the others lost

10The error question

The options weighed

11How examples are drawn and weighted

The options weighed

  • (a)Every example weight one (now).not chosen
  • (b)One unit of work weighs one, split over its examples; scores per repository, then weighted by one over the inclusion probability.chosen
  • (c)Dropping large or bulk changes.not chosen

The choice

(b). In training every repository carries the same total weight, with a bound on the weight of a single example so that a tiny repository's few questions do not dominate; the bound is set on validation repositories. The size of a change is stored as a fact a model can read, not only baked into a weight. Bulk changes are flagged and read apart. Candidates are all files alive at the asking time; negatives used in training are drawn by a stated design, with the probabilities kept, and are never a right file of the same question.

Why

The inclusion probabilities are known exactly, so the correction is derived, not found: one over the number of examples a unit gives. The material gives the weight for an average; for training it is silent, which is why the bound is an assumption with a test. A file that was needed but not changed is counted as wrong: a "negative" may be a missed answer, and that gap is not random.

Why the others lost

(a): drawing by events over-represents what takes part in many, so a change's share grows with its size and a repository's with its length (Data 2.2, Data 2.8). (c): a cap that cannot afterwards be told from the world (Data 1.1; veto: a cap set while collecting).

It rests on

Data 2.2 Data 2.8 Data 2.9 Data 3.2 Data 3.3 Data 1.1 Model 13.6 assumption (its reasoning is in "why")

It is wrong if

With the weights, validation scores are lower in every stratum than without them.

12Tests of generalisation, baselines and measures

The options weighed

  • (a)One pooled score of hits in the top ten over ten (now).not chosen
  • (b)Several readings kept apart, each per repository and per segment, with measures that rank the right files against all others.chosen

The choice

(b). Readings: an unseen repository after the cut-off date (the main claim); a repository seen in training, after the cut-off; the owner's two (decision 15); cold start, a held-out repository with its history cut to its first 10, 100 and 1,000 commits; the whole span of held-out repositories, marked. Baselines on the same examples: for a change, counting with the one-over-n weight, recently changed, same folder, import neighbours; for task words, text search over paths and content and the files the text names; for an error, the files in the trace. Measures: the rank of each right file among all files alive; the share found in the top 1, 5, 10 and 20; the reciprocal rank of the first; hits in the top ten over the smaller of ten and the number of right files. Per repository first, then the mean weighted by one over the inclusion probability, with intervals by resampling clusters inside strata. Read by stratum, tier, length of history, kind of file, whether the right file had earlier joint change or a code link, and whether the repository was created after the cut-off of every pretrained part (nothing of such a repository can have been read before). The test is scored once.

Why

The owner's condition is the first reading; a model can pass the second and fail the first, so one figure cannot stand for both. Cold start is where the owner's small repositories live.

Why the others lost

(a): a pooled figure hides segments and is mostly one repository; its ceiling is about a quarter (Data 7.3; our own record).

13Checks on the data

The options weighed

  • (a)Trust the extraction and read its code (now).not chosen
  • (b)State what must hold, test it on every build, and plant faults that the tests must catch.chosen

The choice

(b). Keys and dependencies, reduced to a smallest set, tested and never called proved. A loss test: diffs rebuilt from the store. Leak tests: the loader's assertion; inputs built from the store cut at the asking time must equal inputs built from the whole store; a planted later fact must never arrive; a model given shuffled labels must fall to chance. A description of every repository (sizes of changes, merges, bulk changes, squashing, issue use, languages, tests). A table of missing values per column and repository with the cause, compared between training and test; no row is dropped for a gap. The sample held against its list. Content shared across the split. The regression check of decision 1.

Why

A dependency can be refuted by data and never proved by it, so the useful act is to state it and keep trying to refute it. The description is also the first step of the model's design: which patterns the data has. Writing down how each kind of link and each source of labels was observed is what would let the observing itself be modelled later, should the counts show that a habit (such as linking issues) skews a question (Data 3.4).

Why the others lost

(a): a leak is silent, and a rule nobody wrote down cannot be refuted by any data (Data 6.3, Data 4.2).

14What is handed to a model

The options weighed

  • (a)Pairs and yes-or-no facts (now).not chosen
  • (b)Only a flat table of features per question and candidate.kept in part
  • (c)The whole repository as one graph or one text.not chosen
  • (d)Per question, a typed neighbourhood cut at its asking time.chosen

The choice

(d). The question as a node (text, diff or error text); the files it starts from, linked to it by kind: "in the change", "named in the text", "in the trace"; candidate files with their raw content at that time; events (units of work, commits) as nodes with their size and their time relative to the question; typed, directed links. Amounts relative to the repository's own scale, with the repository's description beside them. Flags for missing values. No stored identity of a file or a repository. The flat table of (b) is derived from the same neighbourhood at loading, for a tree ranker and for the baselines. Where a neighbourhood must be sampled, how it was sampled is recorded.

Why

Events as nodes let a model sum and count; the links from the question to the files it names give a text question something to be relative to; relative amounts keep a new repository inside the range the model saw. A neighbourhood per question records one node's surroundings; because the store is whole, how two neighbourhoods overlap can always be recovered. What a model does with it is the second hypothesis.

Why the others lost

(a): projections; a yes-or-no fact cannot count (veto: a projection that cannot be rebuilt; Model 9.5). (b) as the only form: features chosen beforehand, and what was summed away is gone (Data 9.2). (c): the largest do not fit, and it is blind to time unless cut per question (Data 9.4; Model 14.1).
