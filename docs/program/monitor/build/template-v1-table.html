Session monitor: proposal and first picture

One page that shows every session in order, who started it, what it is doing, and whether each hook checked it. The picture below is not a sketch: it is drawn from the sessions and hook logs already stored on this PC.

Every session, in the order it ran

One row per session, oldest first. The bar shows when it was working (quiet hours are cut out at the dashed lines). The small marks under a bar are its helpers. A thin line drops from a session to each session it started. The nine columns on the right are the hooks: did each one check this session. Click a row for what the session was doing.

How it works

already on disk1. What is recorded
  • Each session's own log: every call, its time, its plan steps, its closing summary
  • Each helper's log, kept beside its session
  • Each hook's log: what it allowed and what it refused
  • The table of rules and what enforces each

new, small2. Reader
  • A small program on this PC
  • Follows those files and reads only the new lines
  • Calls no model, so it uses no tokens
  • Changes nothing it reads
→
new3. Expected against seen
  • From the session's log: the calls a hook should have checked
  • From the hook's log: the calls it did check
  • A difference is a rule that was not enforced, shown the moment it happens
→
new4. The page
  • Needs-a-look strip at the top
  • Sessions in order, who started whom
  • What each is doing, in its own words
  • Redraws by itself as the files change
→
new5. Hold switch
  • A Hold button on any session
  • It writes a flag; the first hook refuses that session's next call
  • The session stops within one step, without a message from you and without tokens

What it cannot see

LimitWhat it means
Rules that exist only as textA rule with no hook leaves no log, so the page can only list it as "not watched". It cannot say whether it was followed.
What a session is doingTaken from the session's own plan steps and closing summary. It is the session's word, not a check of the work.
Who started the older sessionsThe app began writing that link only recently. For older sessions it is matched by title, and where no match exists the row shows no parent.
A few seconds of delayA session's log is written slightly after each call, so the page trails the session by seconds.
Sessions that run in the cloudTheir logs are not on this PC.
App updatesThe log format belongs to the app and can change. The reader is one small file, so a change is a small repair.

From this picture to the live page

StepWhat it does
1. One log line for every hookEvery hook writes the same line on every call: time, session, helper, call, allowed or refused. Today three hooks do not name the session, which is why some cells show "?".
2. The rule table as dataEach rule says which hook enforces it and on which calls. Then "expected" is computed for all nine hooks, not three, and rules with no hook appear as "not watched".
3. The reader as a live programThe read step that made this picture, kept running: it follows the files and pushes each change to the page.
4. The hold switchThe button and the flag the first hook obeys.
5. Hooks in every folderThe page shows which hooks are on in each folder a session runs in, so a run started elsewhere cannot go unwatched without it showing.

Running it costs no tokens. Building it is ordinary code: no install and no download; it uses the Node already on this PC.
