On 2026-11-12 the owner rejected my test of their graph-database idea. I had built a quick file-level import graph as a JSON list, compared it with the same edges in SQLite on one query, and judged usefulness from 200 searches sampled from another project. The owner's objections, in their words: "the type of graph we make makes a huge difference including the algorithms we use on it we dont get anything for free", "a merely self made graph vs a established relational engine is not a fair enough comparison", "are you properly scoring the two answers and the value they carry?", "doesnt how many hops we set the traversal to also impact this?", and "First research on the best advanced optimized way of making it and then start testing it".

**Why:** the owner had asked the same question three times and each of my answers defended a prior verdict with a test that favoured it. A weak version of an idea losing to a strong baseline proves nothing, and the owner reads it as not having taken the idea seriously.

**How to apply:** when the owner proposes an approach and I doubt it, (1) research the strongest known way to build it first, (2) cater it to the repo in question, (3) compare like with like (established engine against established engine, tuned on both sides), (4) define the scoring of answer value before building, (5) sweep the parameters that matter (hop count here) instead of fixing one, (6) run it on the project the owner names, and say plainly if that project lacks the data. Do not give the owner a comparison before a refuter has seen its baseline. My interpretation: this applies to any "would X help" question, not only graphs. Related: [[project-harness-bottlenecks]], [[feedback-architecture-not-status]].

**Addendum (2026-11-12, same day): fix the obstacle, do not record a handicap.** When LadybugDB's algorithm extension failed to load on Windows, I planned to compute ranking outside the engine and note "not built in on this PC". The owner: "if they dont work on windows run a linux machiune we have the resources why are you compromising instead of fixing problems thatll ruin the experiment". **How to apply:** an environment obstacle that would handicap one arm of an experiment gets fixed with the resources on hand before anything is written down as a limitation. On this PC that means a Linux container (Docker Desktop with WSL2 is installed; it is not running by default) and running every arm's engine measurements in that same environment so the comparison stays like for like. Report a limitation only after the fix has been tried and failed. My interpretation: the owner treats Docker and Linux on this PC as already-approved resources for experiments, though new engine or model downloads still get named with source and size.

**Second instance (2026-11-12, the library review, [[project-library-plausibility-review]]).** I priced the owner's reasoning-cache library as exact repeats of solved problems in a thin, pre-development record, then reported that price as the ceiling of the idea ("your work rarely repeats", "Sonnet can't borrow Opus's judgment", "cap the window instead"). The owner: "You're thinking very narrowly and instead of seeing if these problems are workable or not you just deny the possibility"; the repo has "barely even started development"; low repetition now says nothing about repetition across projects or over time; entries were verified when written and cache invalidation is a mature field; the intended mechanism is semantic and technical matching of similar problems, not exact repeats; and a window cap has long-run costs (mistakes, summary loss). **How to apply:** (1) a base rate measured on an early or unrepresentative record is a fact about the record, never about the idea: say so in the headline, not only in the limits; (2) when asked to critique a design, still answer "is each problem workable, and how" and name the use cases with the most potential before any verdict; (3) price the owner's actual mechanism (here similarity-based reuse), not the narrower one on paper; (4) do not recommend an alternative (a window cap) as if it were free when its quality cost is unmeasured; (5) a short summary must keep the uncertainty, not drop it.

**Third push, same day.** After I conceded, the owner still found the answer too absolute: "We need to define the cases before giving absolute opinions like you're giving which is disappointing", "Dont look at things so narrowly", and one of my suggested use cases was "what i didnt say and seems like a dumb idea". **How to apply:** (6) answer per case, with the conditions under which each holds, before any overall opinion; (7) an average hides the tail: check the top tier and the hard cases where the gap is total, not only the mean gap; (8) restate the owner's goal in their words before judging against it (here: equal output on a cheaper model, to cut cost); (9) a limitation that is really the system's intake (a new hard problem gets escalated and stored) is not an objection; (10) do not add my own redesign of their idea unless asked; engage with the mechanism they proposed (here: merging partial solutions through a graph).

**Fourth push, same day: the method the owner wants for a design.** "I feel like im the only one being sensible, pushing back at you giving good ideas while you're just sitting there either being wrong or repeating my ideas back to me"; "First we'd have to identify the actual limitations of this design not what you've been doing so far, and then focus on solving them until we reach something absolutely unsolvable or gains become near to zero". **How to apply:** for any design the owner cares about, run limitation, then best known fix, then what is left, then fix that, and stop a chain only at something unsolvable (say why) or near-zero gain (give the estimate). A limitation is a mechanism-level obstacle, never a base-rate doubt about whether it will pay. Bring my own concrete additions (data structure, named algorithm, who runs it, cost, cheapest test) and prior art from other fields; agreeing with the owner or restating their idea is not a contribution. This supersedes item (10) when the owner asks for ideas.

**Fifth push, same day: discuss before fixing, and find limitations by simulation.** I launched a nine-agent solve round and the owner cut in: "hey reason and discuss the limitations with me before attempting a fix". I stopped it. Then, on my abstract list of eleven limitations: "i think thats mostly right but i think you're still missing more, simulate the whole process of how the proposed design works and you'll start to see where it causes issues or breaks. Which part of the design and what not". **How to apply:** (a) no fixes and no solve workflows until the owner has agreed the list of limitations; the discussion is with the owner, in conversation turns, not delegated; (b) to find a design's limitations, walk one concrete case through every step and ask at each step who acts, what is in its window at that moment, what it cannot know yet, and what happens in parallel and later; group what breaks by part of the design. On 2026-11-13, after the graph test reported "the graph engines gave the same answers as SQLite", the owner said: "if our experiments are all failing then how the hell does graphify show such good results and it has a ton of stars in its repo, are we using strictly graphs or knowledge graphs or TKGs i suspect you're still being narrow minded with the architecture you have flaws in your reasoning and especially your assumptions".

He was right on the main point. **How to apply:**

=== reference-bash-tool-limits.md

name: reference-bash-tool-limits
description: Bash tool quirks on this Windows setup — commands over about 8 KB are cut, and double backslashes in heredocs collapse
metadata:
  type: reference
---

Two Bash tool quirks seen on this PC (Git Bash), 2026-11-11:

- A single Bash command longer than roughly 8 KB is truncated silently; a heredoc then runs to end of input and the file is cut mid-line. Write long files in parts of under about 6 KB and append, then check the tail.
- A double backslash inside a heredoc arrives as a single one, even with a quoted delimiter. In generated JavaScript use String.fromCharCode(92) or a character class instead of an escaped backslash.

`error: unable to open loose object … Filename too long` / `fatal: fetch-pack: invalid

**How to apply:** prefix each git command with the per-command option instead of changing

then `git -c core.longpaths=true sparse-checkout set <dir> <dir>` (cone mode; root files such as

PATH in Git Bash (Windows Store alias) — use `node` for JSON. Related: [[project-fixflow-ship-plan]].
